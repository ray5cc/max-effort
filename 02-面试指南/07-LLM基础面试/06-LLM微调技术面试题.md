## 基础题（适合初级，⭐）

### Q1: 什么是 LLM 微调（Fine-tuning）？与直接使用预训练模型有何区别？

**参考答案：**
LLM 微调是在已经预训练好的大语言模型基础上，使用特定领域或特定任务的数据对模型参数进行进一步训练，使模型适配目标场景的过程。

与直接使用预训练模型的区别：

- **预训练模型**：在海量通用数据上训练，具备通用语言能力，但在特定领域知识、输出格式、行为规范上可能表现欠佳。
- **微调后模型**：通过少量领域数据将领域知识"写入"参数，在目标场景下准确率更高、延迟更低（无需冗长 Prompt）、行为更可控。

微调本质上是对预训练知识的"精炼"而非重新学习，因此所需数据量远小于预训练（通常 1000～100,000 条即可显现效果）。

**扩展知识：** 微调可以分为全参数微调（Full Fine-tuning）和参数高效微调（PEFT）。前者更新所有参数，效果最好但成本极高；后者只更新少量参数，是工业界主流选择。

---

### Q2: LoRA 的全称是什么？它的核心思想是什么？

**参考答案：**
LoRA 全称 **Low-Rank Adaptation of Large Language Models**（大语言模型的低秩适配）。

核心思想：在微调过程中，模型权重的变化量 ΔW 具有**低秩特性**（low-rank），可以用两个小矩阵的乘积来近似表示：

```
ΔW = B · A
其中 B ∈ ℝ^(d×r)，A ∈ ℝ^(r×k)，r ≪ min(d, k)
```

完整的前向传播变为：`W = W₀ + BA`，其中 W₀（原始权重）被冻结，只有 A 和 B 参与梯度更新。

这种设计大幅减少了可训练参数量：以 `d=k=4096, r=16` 为例，LoRA 参数量仅为原始权重矩阵的 0.4%，却能达到接近全参微调的效果。

**扩展知识：** LoRA 训练完成后可以将 BA 直接合并回 W₀（`merge_and_unload()`），合并后的模型与原始模型结构完全相同，推理时零额外开销。

---

### Q3: LoRA 中的 rank（秩）参数 r 的含义是什么？如何选择？

**参考答案：**
在 LoRA 中，rank `r` 决定了低秩矩阵的"中间维度"大小，直接控制了 LoRA 的**表达能力**与**参数量**之间的平衡：

- **r 越大**：表达能力越强，可以建模更复杂的权重变化，但参数量越多、显存占用越高、过拟合风险越大。
- **r 越小**：参数量少、训练快，但对复杂任务可能欠拟合。

**实践选择经验：**

- 简单格式适配/风格迁移：r = 4～8
- 一般指令跟随/问答：r = 16～32
- 复杂推理/代码生成：r = 32～64
- 通常不超过 128（收益边际递减明显）

**扩展知识：** `lora_alpha` 是缩放系数，实际输出会乘以 `alpha/r`。通常设置 `alpha = 2r`（如 r=16 时 alpha=32），这样 alpha/r=2，在不同 rank 设置下保持一致的缩放，避免每次改变 rank 都需要重新调学习率。

---

### Q4: 什么是 SFT（Supervised Fine-Tuning）？其数据格式是什么？

**参考答案：**
SFT（监督微调）是使用标注的输入-输出数据对对语言模型进行微调的过程，是最基础的微调方式。模型通过最大化目标序列的对数似然来学习"给定输入应如何输出"。

标准数据格式（指令跟随格式）：

```json
{
  "instruction": "将以下英文翻译成中文",
  "input": "The quick brown fox jumps over the lazy dog",
  "output": "敏捷的棕色狐狸跳过了懒惰的狗"
}
```

对话格式（Chat 格式）：

```json
{
  "messages": [
    { "role": "system", "content": "你是一个专业的翻译助手" },
    { "role": "user", "content": "将以下英文翻译成中文：The quick brown fox" },
    { "role": "assistant", "content": "敏捷的棕色狐狸" }
  ]
}
```

**扩展知识：** SFT 只训练 Assistant 部分（response tokens）的 loss，不对 Instruction 部分计算 loss（通过 `labels=-100` 掩码实现），确保模型学习的是"如何回答"而非"如何提问"。

### Q5: LoRA 与全参数微调（Full Fine-tuning）相比有哪些优缺点？

**参考答案：**

| 维度           | LoRA                     | Full Fine-tuning    |
| -------------- | ------------------------ | ------------------- |
| 可训练参数     | 0.1%～1%                 | 100%                |
| 显存占用       | 大幅降低（可降 60～80%） | 全量（最高）        |
| 训练速度       | 较快                     | 较慢                |
| 最终性能       | 接近（复杂任务有差距）   | 最优                |
| 灾难性遗忘风险 | 低（原始权重冻结）       | 高                  |
| 存储/分发      | 只需存增量（几十 MB）    | 全量模型（数十 GB） |
| 多任务扩展     | 每个任务一个 Adapter     | 需保存多个完整模型  |

**优点**：极大降低硬件门槛，支持消费级 GPU 微调大模型；天然抑制灾难性遗忘；部署灵活（一份基础模型 + 多个 LoRA Adapter）。

**缺点**：复杂推理任务上可能比全参微调略差 1～3 个百分点；需要额外选择 rank 等超参数；Adapter 管理稍显复杂。

**扩展知识：** 实际生产中可以用 "LoRA + 合并权重" 策略兼得两者优势：训练时用 LoRA 节省显存，部署前合并权重消除推理额外开销。

---

### Q6: 微调和 Prompt Engineering 的区别是什么？各适用于什么场景？

**参考答案：**
两者的本质区别在于知识存储的位置：

- **Prompt Engineering**：知识保存在 Prompt 文本中，每次推理都要携带，不改变模型参数。适用场景：任务逻辑简单、知识可以用少量文字描述、需要快速验证、不具备训练资源。

- **微调**：知识"写入"模型参数，推理时 Prompt 可以极简。适用场景：领域知识大量且固化、需要特定输出格式、需要行为对齐、对延迟和成本敏感（短 Prompt 推理更快更便宜）。

**选择原则**：优先尝试 Prompt Engineering；若效果不达标或 Token 成本过高，再考虑微调；若知识频繁更新，优先 RAG 而非微调。

**扩展知识：** 三种技术（Prompt Engineering、RAG、Fine-tuning）并非互斥，生产级 AI 系统通常同时使用：微调固化行为 → RAG 补充动态知识 → Prompt Engineering 精细控制输出格式。

### Q7: 什么是 RLHF？为什么 LLM 需要 RLHF 对齐？

**参考答案：**
RLHF（Reinforcement Learning from Human Feedback，基于人类反馈的强化学习）是一种利用人类偏好信号来对齐 LLM 行为的训练方法。

**为什么需要 RLHF：**
SFT 只能教模型"如何模仿示例回答"，但无法保证模型"选择出最优回答"。语言模型在 SFT 后可能：

- 生成真实但有害的内容
- 给出正确但不诚实的回答
- 输出冗长、重复的内容
- 不遵从用户意图（帮助性不足）

RLHF 通过收集人类对多个回答的偏好排序，训练 Reward Model 量化"好回答"，再用强化学习（PPO）最大化期望奖励，将模型行为对齐到人类偏好。

**扩展知识：** InstructGPT（OpenAI）是 RLHF 应用的标志性工作，证明了 1.3B 的 RLHF 模型在用户偏好上可以超过 175B 的 GPT-3。

### Q8: 请详细解释 LoRA 的数学原理，包括前向传播公式和初始化策略。

**参考答案：**
LoRA 的数学基础是权重矩阵变化量的低秩分解。

**前向传播：**
设原始权重矩阵 `W₀ ∈ ℝ^(d×k)`，引入两个低秩矩阵 `A ∈ ℝ^(r×k)` 和 `B ∈ ℝ^(d×r)`，其中秩 `r ≪ min(d, k)`。

修改后的前向传播为：

```
h = W₀x + (α/r) · BAx
      ↑           ↑
  原始（冻结）   LoRA 增量
```

**初始化策略（至关重要）：**

- A 矩阵：使用**随机高斯初始化**（kaiming_uniform）
- B 矩阵：初始化为**全零矩阵**

这样初始化时 `BA = 0`，保证训练开始时 LoRA 分支的输出为零，整个模型的输出与原始预训练模型完全相同。如果 B 也随机初始化，训练初期 LoRA 的随机扰动会破坏模型原有的优秀性能，导致训练不稳定。

**参数量计算：**

```
原始: d × k
LoRA: r × k + d × r = r(d + k)
节省率 ≈ 1 - r(d+k)/(dk) ≈ 1 - 2r/min(d,k)  （d≈k时）
```

**扩展知识：** LoRA 论文（Hu et al., 2021）通过实验证明，权重更新矩阵 ΔW 的"内在秩"（intrinsic rank）远小于原始矩阵的满秩，这为低秩假设提供了理论依据。不同类型任务的最优 rank 不同，语言理解任务通常比生成任务需要更高的 rank。

### Q9: QLoRA 在 LoRA 的基础上做了哪些改进？NF4 量化的优势是什么？

**参考答案：**
QLoRA（Dettmers et al., 2023）在 LoRA 的基础上引入三项核心技术，将微调成本降至普通消费级 GPU 可承受的范围：

**1. 4-bit NormalFloat（NF4）量化**
NF4 是专为神经网络权重设计的信息理论最优量化类型。原理：神经网络权重通常服从正态分布 N(0, σ²)，NF4 通过将 4-bit 的 16 个量化区间分配在正态分布的等分位数（quantile）上，使每个区间被填充的概率相等，从而最小化量化误差的期望值。

对比：同样是 4-bit，整数量化（INT4）对均匀分布最优，而 NF4 对正态分布最优，在神经网络权重上量化误差约低 10～20%。

**2. Double Quantization（双重量化）**
量化本身需要存储缩放因子（scale factor），DQ 对这些缩放因子再进行一次 8-bit 量化，额外节省约 0.37 bits/参数（在 65B 模型上约节省 3GB 内存）。

**3. Paged Optimizers（分页优化器）**
利用 NVIDIA CUDA 的统一内存（Unified Memory）机制，当 GPU 显存不足时自动将 AdamW 优化器状态分页到 CPU 内存，防止训练过程中 OOM 崩溃。这使得单卡 24GB 也可以训练 70B 模型（虽然慢，但不会报错）。

**总体效果：** QLoRA 使 65B LLaMA 模型的微调显存需求从 780GB（FP16全参）降至 48GB（单卡 A6000），性能损失约 0.5～1 个百分点。

**扩展知识：** QLoRA 的 LoRA 适配器本身仍以 BF16 精度训练，量化只针对基础模型权重。训练完成后，保存的 adapter 是 BF16 精度的，可以加载到全精度模型上运行。

### Q10: 请描述 RLHF 的完整四个阶段流程。

**参考答案：**

**阶段 1：预训练基础模型（Pretraining）**
在海量无监督语料上进行自回归语言建模预训练，模型学习基础语言能力。（通常这一步已由模型提供商完成。）

**阶段 2：监督微调（Supervised Fine-Tuning, SFT）**
收集高质量的指令-回答数据对（通常由人工标注专家撰写示范回答），对预训练模型进行监督微调，使模型学会遵循指令的基本能力。SFT 模型同时作为后续 PPO 阶段的参考模型（Reference Model）。

**阶段 3：训练奖励模型（Reward Model Training）**
收集偏好数据：对同一个 Prompt，让 SFT 模型生成多个回答，由人工标注员对这些回答进行排序（如 A > B > C）。使用 Bradley-Terry 模型训练 Reward Model，使其能够对任意 (prompt, response) 对打出一个标量奖励分数。

**阶段 4：PPO 强化学习对齐（RL Fine-Tuning with PPO）**
使用 PPO 算法，以 Reward Model 的评分为奖励信号，优化 SFT 模型的参数。同时加入 KL 散度惩罚（KL penalty）防止模型偏离 SFT 参考模型过远（防止"奖励攻击"——模型可能学会欺骗 Reward Model 而非真正变好）。

**扩展知识：** RLHF 需要同时维护 4 个模型（Actor、Critic、Reward Model、Reference Model），工程复杂度极高，这是 DPO 等离线对齐方法被广泛采用的主要原因。

### Q11: DPO 为什么不需要 Reward Model？其目标函数的直觉是什么？

**参考答案：**
DPO（Direct Preference Optimization）的核心洞见是：**RLHF 中的最优策略有闭合解（closed-form solution），该解可以直接用策略模型本身来表示 Reward Function**，因此无需显式训练独立的 Reward Model。

**数学推导直觉：**
在 RLHF 框架中，给定 KL 约束的最优策略满足：

```
π*(y|x) ∝ π_ref(y|x) · exp(r(x,y) / β)
```

对其求解 r(x,y)，得到：

```
r(x,y) = β · log [π*(y|x) / π_ref(y|x)] + Z(x)（常数项可消去）
```

将这个 reward 的表达式代入 Bradley-Terry 偏好模型，就得到了 DPO 的损失函数，完全消除了对独立 Reward Model 的依赖。

**目标函数直觉：**

```
L_DPO = -E[log σ(β·log(π_θ(yw|x)/π_ref(yw|x)) - β·log(π_θ(yl|x)/π_ref(yl|x)))]
```

直觉解释：最大化模型对"好回答"的相对概率提升，同时最小化对"差回答"的相对概率，所有比较都是相对于参考模型（SFT 结果）进行的。

**优势：** 训练稳定（无 PPO 的在线采样不稳定性），工程简单（只需 2 个模型），数据格式标准（chosen/rejected 三元组），是目前开源对齐最常用的方法。

**扩展知识：** DPO 的主要限制是离线学习（offline）——它只能从固定的偏好数据集学习，无法像 PPO 那样通过在线探索发现新的"好"行为。在需要持续自我改进的场景（如数学推理）中，GRPO 等在线方法效果更好。

### Q12: 什么是灾难性遗忘（Catastrophic Forgetting）？如何在微调中缓解这一问题？

**参考答案：**
灾难性遗忘是指模型在学习新任务时，对之前已学习任务的性能急剧下降的现象。在 LLM 微调中，表现为模型在领域任务上精度提升，但在通用语言能力（如常识问答、代码能力）上明显退化。

**主要原因：**

- 学习率过高，覆盖了预训练时形成的权重分布
- 训练轮次过多，模型过度拟合微调数据
- 微调数据分布与预训练数据差异过大

**缓解策略：**

| 策略                   | 原理                           | 适用场景         |
| ---------------------- | ------------------------------ | ---------------- |
| 降低学习率             | 减小权重更新幅度，保留原有知识 | 首选方案         |
| LoRA/PEFT              | 原始权重冻结，天然防遗忘       | 大多数场景       |
| 数据回放（Replay）     | 混合 5～10% 通用数据训练       | 有通用数据权限时 |
| EWC 正则化             | 对重要参数施加更大更新惩罚     | 需要精确控制     |
| 早停（Early Stopping） | 监控通用基准，退化前停止       | 所有场景必备     |

**扩展知识：** 评估是否发生灾难性遗忘的标准做法是在微调前后对 MMLU、HellaSwag、ARC 等通用基准同时评测，如果下降超过 2 个百分点则需要干预。

### Q13: 什么是偏好数据集（Preference Dataset）？如何构建高质量的偏好数据？

**参考答案：**
偏好数据集是用于 DPO/RLHF 对齐训练的数据格式，每条数据包含：

- `prompt`：用户输入
- `chosen`（winner）：人类偏好的"好"回答
- `rejected`（loser）：人类不偏好的"差"回答

**构建高质量偏好数据的要点：**

**1. 标注者选择**
使用具备领域背景的专家标注（非众包），确保偏好判断的专业性和一致性。标注者之间的 Cohen's Kappa 一致性系数应高于 0.6。

**2. Prompt 多样性**
覆盖目标场景的各类型 Prompt，避免数据集过度集中于某一类问题，否则对齐会对其他类型问题产生负效应。

**3. Chosen/Rejected 差异显著**
两个回答的质量差距应该足够明显（清晰的偏好），模糊的偏好（标注者无法确定孰优孰劣）会引入噪声，降低训练效果。

**4. 正反例平衡**
避免 chosen 总是比 rejected 更长，否则模型可能学到"越长越好"这一错误归纳（DPO 的已知偏见）。

**5. 数据量**
DPO 通常需要 2,000～20,000 条高质量偏好数据，质量比数量更重要。

**扩展知识：** 可以用 AI 辅助构建偏好数据集（Constitutional AI 方法）：由强模型生成多个回答，再由另一个强模型根据原则（Constitution）判断偏好，大幅降低人工标注成本。

### Q14: DeepSpeed ZeRO 的三个阶段各分片了什么内容？

**参考答案：**
ZeRO（Zero Redundancy Optimizer）通过将训练状态分片（Sharding）到多卡来消除冗余存储。

训练时 GPU 显存主要被三类内容占用：

- **模型参数（Parameters）**：约占 2 bytes/参数（BF16）
- **梯度（Gradients）**：同参数，约 2 bytes/参数
- **优化器状态（Optimizer States）**：AdamW 需要 m、v 两个动量，约 8 bytes/参数（FP32）

三个阶段的分片策略：

| 阶段   | 分片内容                 | 显存节省（N卡） | 通信开销 |
| ------ | ------------------------ | --------------- | -------- |
| ZeRO-1 | 优化器状态               | ≈ 4×            | 低       |
| ZeRO-2 | 优化器状态 + 梯度        | ≈ 8×            | 中       |
| ZeRO-3 | 优化器状态 + 梯度 + 参数 | ≈ N×            | 高       |

以 7B 模型（14GB BF16），8 卡为例：

- 无 ZeRO：每卡需约 112GB（参数+梯度+优化器）
- ZeRO-3：每卡约 14GB，理论上可在 8 × 16GB 卡上训练

**扩展知识：** ZeRO-Offload 是 ZeRO-2 的扩展，将优化器状态和梯度卸载到 CPU 内存，适合显存极度受限的场景（但训练速度降低约 30%）。

### Q15: GRPO 与 PPO 的核心区别是什么？为什么 DeepSeek-R1 选择 GRPO？

**参考答案：**
**核心区别：优势函数（Advantage）的估算方式不同**

PPO 需要一个独立的 Critic（价值网络）来估算状态价值 V(s)，进而计算优势 A = r - V(s)。这意味着需要同时维护并更新 Actor 和 Critic 两个大模型。

GRPO（Group Relative Policy Optimization）不使用 Critic 模型，而是通过**组内相对比较**来估算优势：

1. 对同一个 Prompt，使用当前策略采样 G 个回答（如 G=8）
2. 对每个回答用规则函数（如代码运行结果、数学答案正确性）打分
3. 计算相对优势：`A_i = (r_i - mean({r_1,...,r_G})) / std({r_1,...,r_G})`

**DeepSeek-R1 选择 GRPO 的原因：**

1. **工程效率**：去掉 Critic 模型，显存占用从 4 模型降至 2 模型，GPU 利用率翻倍
2. **奖励可设计**：数学和代码任务有天然的规则化奖励（答案是否正确、代码是否通过测试），无需训练神经网络 Reward Model
3. **探索与稳定的平衡**：组内对比提供了更稳定的基线（相比 PPO 的价值网络），同时保留了在线探索能力
4. **Format 奖励**：可以同时优化答案正确性奖励和格式奖励（如要求输出 `<think>...</think>` 格式），多目标优化更灵活

**扩展知识：** GRPO 的组大小 G 是关键超参数，G 越大基线越稳定但计算成本越高。DeepSeek-R1 的消融实验显示 G=8～16 效果最优，G=4 时训练不稳定，G>32 收益边际递减。

### Q16: 如何诊断和处理 LLM 微调中的过拟合与欠拟合？

**参考答案：**
**诊断方法**：

```
过拟合信号：
  ✗ 训练 loss 持续下降，但 eval loss 开始上升
  ✗ 训练集上的生成质量远优于验证集
  ✗ 模型输出与训练数据高度相似（抄写而非泛化）
  ✗ 模型丢失了通用基准上的能力（灾难性遗忘）

欠拟合信号：
  ✗ 训练 loss 和 eval loss 均较高且下降缓慢
  ✗ 模型输出格式/风格没有朝目标方向改变
  ✗ 训练多个 epoch 后性能提升不明显
```

**处理策略对比：**

| 问题   | 处理方法                                                                                    |
| ------ | ------------------------------------------------------------------------------------------- |
| 过拟合 | 减少训练 epoch；降低学习率；增大 dropout；使用 LoRA（天然正则）；增加数据量；Early Stopping |
| 欠拟合 | 增加 epoch；提高学习率；增大 LoRA rank；增加可训练模块；检查数据质量；增加数据量            |

**关键监控指标：**

```python
# 建议每隔 N steps 评估一次（N = max(50, total_steps/100)）
# 监控以下指标：
# 1. eval_loss（判断是否过拟合）
# 2. 任务专项指标（如 ROUGE-L、Exact Match、代码通过率）
# 3. 通用基准分数（如 MMLU 子集）防止灾难性遗忘
```

**扩展知识：** 微调 LLM 时过拟合比欠拟合更常见，因为微调数据集通常远小于模型参数量。建议总是启用 Early Stopping，并将训练集的 5～10% 保留为验证集（注意：验证集应与训练集来自同一分布但不重叠）。

### Q17: 请解释 DPO 已知的局限性，以及 IPO、SimPO 等变体如何改进它。

**参考答案：**
**DPO 的已知局限性：**

1. **长度偏差（Length Bias）**：DPO 训练后模型倾向于生成比 chosen 更短的回答，因为最小化 rejected 的对数概率比最大化 chosen 的对数概率更容易。

2. **离线学习局限**：DPO 使用固定偏好数据集，无法通过在线探索发现新的好行为，在动态环境（如持续强化推理能力）中效果受限。

3. **参考模型依赖**：如果参考模型（SFT 基础）质量差，DPO 的对齐效果上限也会受限。

4. **分布外泛化弱**：在分布外（OOD）的 Prompt 上，DPO 的对齐效果下降明显。

**改进变体：**

| 变体               | 核心改进                                    | 解决的问题            |
| ------------------ | ------------------------------------------- | --------------------- |
| IPO（Identity PO） | 直接优化偏好概率而非对数比，防止过优化      | 过优化/奖励攻击       |
| SimPO              | 去掉参考模型，用回答长度归一化奖励          | 参考模型依赖+长度偏差 |
| ORPO               | 将 SFT 和对齐合并为单步，添加比值惩罚项     | 减少训练阶段          |
| KTO                | 只需（prompt, response, label）而非成对偏好 | 偏好数据采集成本      |
| CPO                | Contrastive Preference Optimization         | 提升分布外泛化        |

**扩展知识：** SimPO（Simple Preference Optimization）是近期（2024）较受关注的改进：它去掉了参考模型（完全不需要 π_ref），并用生成序列的平均对数概率（而非求和）作为奖励，从而缓解长度偏差。在多项 MT-Bench 和 AlpacaEval 基准上，SimPO 优于标准 DPO。

### Q18: verl 框架的"混合引擎"设计解决了什么工程问题？

**参考答案：**
**传统 RLHF 训练框架的痛点（分离式架构）：**

在传统方案（如 OpenRLHF）中，训练引擎（DeepSpeed/FSDP）和推理引擎（vLLM）运行在不同的 GPU 进程组上。PPO 的每一步需要：

1. 推理引擎采样生成回答（vLLM 节点）
2. 通过网络传输将权重从训练节点同步到推理节点
3. 计算奖励和梯度，更新 Actor 权重

**权重同步的网络开销**是主要瓶颈：对 70B 模型，BF16 权重约 140GB，跨节点传输（即使是 InfiniBand 400Gbps）也需要数秒，导致 GPU 利用率低下（通常低于 40%）。

**verl 混合引擎的解决方案：**
将训练引擎和推理引擎部署在**同一批 GPU 进程**内，通过共享内存（CUDA IPC / Tensor 指针传递）实现零拷贝权重共享：

```
传统：Training GPUs ──[网络 140GB]──► Inference GPUs
                        ↑ 瓶颈

verl：[Training Engine + Inference Engine] 在同一 GPU 组
      DeepSpeed 更新权重 → 直接通过 Tensor 引用共享给 vLLM
```

**效果：** 消除了跨节点权重同步的网络开销，GPU 训练吞吐量（TFLOPs）提升约 40%，同等显存下可支持更大 batch 的在线采样。verl 的混合引擎还支持动态切换模式：训练时用 ZeRO-3 分片，推理时重组为 Tensor Parallel 分布（vLLM 偏好的并行策略），最大化两种场景的利用率。

### Q20: 在有限资源（单卡 24GB VRAM）下如何微调 7B 模型？请设计完整方案。

**参考答案：**
单卡 24GB VRAM 是消费级 GPU 的典型配置（RTX 3090/4090），微调 7B 模型需要使用多种技术组合：

**方案设计：QLoRA + Gradient Checkpointing + Gradient Accumulation**

```python
# 显存估算（7B 模型）
# BF16 全参：7B × 2 bytes = 14GB（仅权重）
# + 梯度：14GB
# + AdamW 优化器状态：56GB
# 合计：~84GB → 超出 24GB 限制

# QLoRA 方案显存分解：
# NF4 量化模型权重：7B × 0.5 bytes ≈ 3.5GB
# BF16 LoRA 参数（r=16, 约0.5% 参数）：≈ 0.07GB
# BF16 梯度（仅 LoRA 部分）：≈ 0.07GB
# AdamW 优化器（仅 LoRA 参数）：≈ 0.28GB
# 激活值（batch_size=1, seq_len=2048）：≈ 4～8GB
# 合计：约 8～12GB → 适合 24GB 卡
```

**关键配置：**

```python
# 1. 4-bit 量化基础模型
bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype=torch.bfloat16,
    bnb_4bit_use_double_quant=True,  # 双重量化进一步节省显存
)

# 2. 启用梯度检查点（Gradient Checkpointing）
# 以重新计算换显存，减少约 50% 激活值占用
model.gradient_checkpointing_enable()

# 3. 梯度累积（等效大 batch）
training_args = TrainingArguments(
    per_device_train_batch_size=1,      # 单步 batch 极小
    gradient_accumulation_steps=16,     # 等效 batch_size=16
    ...
)

# 4. 8-bit Adam（可选，进一步节省优化器状态显存）
optimizer = bnb.optim.AdamW8bit(
    model.parameters(),
    lr=2e-4,
)
```

**扩展知识：** Flash Attention 2 可以将注意力计算的显存复杂度从 O(n²) 降至 O(n)，在长序列（2048+）场景下显存节省可达 50%，是单卡微调的必备优化。通过 `attn_implementation="flash_attention_2"` 启用。

### Q24: 【场景】微调后的模型在测试集上表现良好，但上线后用户反馈质量差。请分析可能的原因并给出排查方案。

**参考答案：**
这是一个典型的**训练-服务分布偏移（Train-Serve Skew）**问题，可能原因和排查路径：

**1. 数据分布偏移（最常见）**

- 测试集与训练集来自相同分布，但与真实用户输入分布不同
- 排查：对线上用户请求采样 1000 条，与训练集做相似度分析（TF-IDF / Sentence Embedding）；如果分布差异显著，需要收集真实用户数据做 re-fine-tuning

**2. 推理配置差异**

- 测试时用 greedy decoding，线上用 sampling（temperature > 0）导致输出质量不一致
- 排查：检查推理服务的 `temperature`、`top_p`、`max_new_tokens` 配置是否与测试时一致

**3. 输入格式不匹配**

- 线上请求经过了不同的预处理（tokenization 方式不同、特殊字符处理差异）
- 排查：打印线上请求在送入模型前的原始 token 序列，与测试脚本对比

**4. 模型版本/权重加载错误**

- LoRA adapter 未正确合并，或加载了错误版本
- 排查：在生产环境用已知好例子做手工验证，确认模型权重 SHA 一致

**5. 长度/格式边界情况**

- 训练数据 max_length=2048，但线上有 4096 tokens 的长请求
- 排查：统计线上请求长度分布，识别超出训练范围的异常请求

**系统化排查流程：**

```
线上 bad cases 采样
    → 能否在本地复现？
        └── 能 → 是数据/推理问题
        └── 不能 → 是环境/配置问题
    → 与训练集分布对比
    → A/B 测试（旧模型 vs 新模型）量化差异
    → 针对 bad case 类型扩充训练数据
```

### Q25: 【场景】如何在微调后部署多个 LoRA Adapter（针对不同业务场景），同时保持高推理效率？

**参考答案：**
**核心挑战**：每次切换 LoRA Adapter 都需要重新加载，naive 实现下多个 Adapter 无法同时高效服务。

**方案一：静态合并部署（适合 Adapter 数量少且固定）**
将每个 LoRA Adapter 合并进基础模型，部署为独立实例。

- 优点：推理零额外开销，实现最简单
- 缺点：每个业务场景需要一份完整的模型文件（数十 GB）

**方案二：动态 LoRA 切换（适合中等规模）**
基础模型常驻 GPU，Adapter 参数存在 CPU 内存，按请求动态加载到 GPU。

- 工具：`peft` 的 `set_adapter()` 方法支持毫秒级切换（Adapter 参数仅几十 MB）
- 缺点：同一时刻只能服务一个 Adapter，高并发场景需要请求路由

**方案三：多 LoRA 批量服务（推荐生产方案）**
使用 vLLM 的 `multi-lora` 功能，将不同业务的请求按 Adapter 分组，在同一批次（batch）内同时服务多个 Adapter：

```python
# vLLM 启动时加载多个 Adapter
engine = LLMEngine.from_engine_args(EngineArgs(
    model="base-model",
    enable_lora=True,
    max_loras=8,        # 最多同时加载 8 个 Adapter
    max_lora_rank=64,
))
```

- 优点：GPU 利用率高，支持数十个 Adapter 并发，延迟与单 Adapter 相当
- 缺点：vLLM 版本依赖，所有 Adapter 的 rank 需统一

**方案四：LoRA 组合（LoRA Merge）**
如果多个 Adapter 需要同时激活（如"代码能力"+"中文能力"），可以使用 TIES-Merging 或 DARE 算法对多个 Adapter 权重进行无损合并。

**推荐方案**：生产环境下 vLLM multi-lora 是最平衡的选择，兼顾灵活性（无需重新部署）、效率（批量推理）和扩展性（Adapter 热更新）。
