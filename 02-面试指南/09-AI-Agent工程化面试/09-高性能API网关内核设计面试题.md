## ⭐ 基础题（3 题）

### 1. API 网关解决了什么问题？与反向代理有什么区别？

**参考答案：**

API 网关解决微服务架构中的**横切关注点**问题：认证、限流、日志、监控、请求转换等功能不应在每个服务中重复实现。

与反向代理的区别：

| 维度 | 反向代理（NGINX） | API 网关（Kong/Envoy） |
|------|-------------------|----------------------|
| 核心功能 | 请求转发、负载均衡 | 转发 + 可编程中间件链 |
| 可扩展性 | 配置驱动，扩展需写 C 模块 | 插件体系，热加载 |
| 协议感知 | HTTP/TCP 层 | 理解 API 语义（路径、方法、消费者） |
| 管理方式 | 配置文件 + reload | Admin API + 数据库 + Dashboard |

**追问方向：** AI 应用为什么需要专用网关？（SSE 流代理、Token 计费、Prompt 安全）

### 2. 解释 API 网关的请求生命周期阶段模型

**参考答案：**

以 Kong 为灵感设计的阶段模型：

1. **INIT**：解析请求，创建上下文对象
2. **REWRITE**：URI 重写、Header 预处理（路由匹配前）
3. **AUTH**：身份验证（API Key / JWT / mTLS）
4. **ACCESS**：权限检查、限流
5. **ROUTE/BALANCE**：路由匹配 + 负载均衡选择上游节点
6. **UPSTREAM**：转发请求到后端服务
7. **RESP_HEADER/RESP_BODY**：修改响应头和响应体
8. **LOG**：记录访问日志、收集指标
9. **CLEANUP**：释放资源、回收连接

关键设计点：
- 任何阶段可**短路**（abort），但 LOG 和 CLEANUP 阶段必须执行
- 阶段间通过 Context 对象传递数据
- LOG 阶段即使前面出错也要执行（确保有日志记录）

### 3. 固定窗口计数器限流有什么缺陷？如何改进？

**参考答案：**

**缺陷**：窗口边界处的突发问题。限制 100 req/min，在第 59 秒来 100 个请求（窗口 A 末尾），第 61 秒又来 100 个请求（窗口 B 开头），实际 2 秒内处理了 200 个请求。

**改进方案**：

- **滑动窗口计数器**：维护两个固定窗口，按比例加权计算
  - `estimated = prev_count × (1 - elapsed_ratio) + curr_count`
  - 只需 2 个计数器，近似滑动窗口精度
- **滑动窗口日志**：记录每个请求时间戳，精确计数
  - 精度最高但内存开销大（存储每个请求的时间戳）

### 4. 设计一个支持四级作用域的插件系统

**参考答案：**

四级作用域：**全局 → 服务 → 路由 → 消费者**

设计要点：

1. **作用域继承与覆盖**：窄作用域的同名插件配置覆盖宽作用域
   ```
   全局: rate-limit {limit: 100/min}
   路由 /api/search: rate-limit {limit: 20/min}  ← 覆盖全局
   消费者 pro-user: rate-limit {limit: 500/min}   ← 覆盖路由
   ```

2. **优先级排序**：同阶段内多个插件按 PRIORITY 降序执行
   - Auth (2000) → RateLimit (1000) → Transform (500)

3. **解析算法**：
   ```python
   def resolve(ctx):
       matched = {}
       for scope in [GLOBAL, SERVICE, ROUTE, CONSUMER]:
           for binding in bindings:
               if matches(binding, scope, ctx):
                   matched[binding.plugin.NAME] = binding  # 覆盖
       return sorted(matched.values(), key=priority, reverse=True)
   ```

4. **热更新**：新配置验证 → 创建新实例 → 原子替换 → 销毁旧实例

### 5. 对比令牌桶和漏桶算法，各适合什么场景？

**参考答案：**

| 维度 | 令牌桶 | 漏桶 |
|------|--------|------|
| 输出速率 | 可突发（桶中有存量令牌） | 恒定（固定速率漏出） |
| 突发处理 | ✅ 允许短暂突发 | ❌ 队列排队等待 |
| 请求延迟 | 低（有令牌即放行） | 可能增加（排队） |
| 实现复杂度 | 中等 | 中等 |

**场景选择：**
- **令牌桶**：面向用户的 API（允许突发操作，如批量刷新页面）→ AWS API Gateway 使用
- **漏桶**：调用第三方付费 API（严格控制速率，避免超额费用）
- **滑动窗口计数器**：通用限流（精度好、内存小）→ Kong / Cloudflare 使用

**分布式限流关键**：使用 Redis Lua 脚本保证原子性（INCR + EXPIRE 必须在一个脚本中）。

### 6. 如何设计网关的健康检查机制？

**参考答案：**

**双模检查 = 主动 + 被动**：

- **主动检查**（Active）：定期向 `/health` 发探测请求
  - 发现恢复更及时
  - 消耗额外带宽
  
- **被动检查**（Passive）：统计真实请求的成功/失败
  - 零额外开销
  - 发现故障快，但无法检测恢复

**三态状态机**：
```
HEALTHY → (连续失败 ≥ N) → UNHEALTHY
UNHEALTHY → (主动探测成功) → RECOVERING
RECOVERING → (连续成功 ≥ M) → HEALTHY
```

**恢复阶段的渐进流量**：RECOVERING 状态的节点只分配 25% 权重，避免大量流量打到刚恢复的节点。

### 7. 解释分布式限流的挑战和解决方案

**参考答案：**

**挑战**：多个网关实例共享限流状态，需要保证一致性和性能。

**方案 1：中心化 Redis**
- 所有实例共享 Redis 计数器
- 用 Lua 脚本保证原子性
- 延迟增加 1-2ms（网络往返）
- 适合大多数场景

**方案 2：本地限流 + 全局协调**
- 每个实例本地限流（限额 = 总限额 / 实例数）
- 定期同步到中心存储
- 延迟最低，但精度下降
- 适合对延迟极度敏感的场景

**方案 3：滑动窗口 + Redis Pipeline**
- 批量发送 Redis 命令减少往返
- 使用 Redis Cluster 分片减少热点

**关键实现细节**：Redis Lua 脚本必须包含 INCR + EXPIRE + 判断，三步不可拆分。

### 8. 为什么可观测性必须嵌入网关内核？

**参考答案：**

**原因**：网关是所有请求的入口，拥有最完整的请求视图。

需要在每个阶段埋点：
- **INIT**：创建 Trace Span，传播 W3C Trace Context
- **AUTH**：记录认证方法和结果
- **ACCESS**：记录限流决策（通过/拒绝）
- **UPSTREAM**：记录上游选择和延迟
- **LOG**：汇总所有阶段的耗时

**Metrics 设计注意**：
- 标签基数控制（路径归一化 `/users/123` → `/users/:id`）
- 避免 user_id 等高基数标签（会导致 Prometheus OOM）
- 关键指标：请求量、延迟分位数（p50/p95/p99）、错误率、上游健康状态

## ⭐⭐⭐ 高级题（3 题）

### 9. 设计一个 AI 网关的 SSE 流代理机制

**参考答案：**

**核心挑战**：LLM 返回 SSE 流（5-120 秒），不能缓冲整个响应。

**设计要点**：

1. **禁用缓冲**：
   ```
   proxy_buffering off;
   X-Accel-Buffering: no;
   ```

2. **逐块透传**：
   ```python
   async for chunk in upstream.content.iter_any():
       client.write(chunk)
       await client.drain()
   ```

3. **客户端断开检测**：捕获 `ConnectionResetError`，及时终止上游请求（释放 GPU 资源）

4. **超时策略**：
   - 连接超时：10s
   - 首字节超时：60s（等待 LLM 开始生成）
   - 块间超时：120s（两个 chunk 之间）

5. **流式 Token 计数**：在转发过程中累积 content 字段，流结束后统计总 Token

6. **流结束注入**：在 `[DONE]` 事件后注入 usage 统计信息

**追问**：如何处理客户端断开后 GPU 资源释放？→ 取消上游请求 + 通知推理引擎释放 KV Cache。

### 10. 如何设计网关的控制面/数据面分离架构？

**参考答案：**

参考 Kong 的混合部署模式：

**控制面（Control Plane）**：
- 管理配置（路由、插件、上游）
- 提供 Admin API
- 配置存储在 PostgreSQL
- 不处理数据流量

**数据面（Data Plane）**：
- 处理实际请求
- 完全无状态（配置从控制面拉取）
- 限流/缓存数据存 Redis
- 可任意水平扩展

**配置同步方式**：

| 方式 | 延迟 | 复杂度 | Kong 使用 |
|------|------|--------|----------|
| 长轮询 | 5-10s | 低 | ✓ (DB 模式) |
| WebSocket | <1s | 中 | ✓ (混合模式) |
| 文件系统 | 手动 | 最低 | ✓ (声明式) |

**关键保证**：
- 配置版本单调递增，防止回退
- 数据面启动时本地缓存最新配置（控制面不可用时仍可运行）
- 配置变更需验证后再应用

### 11. 设计一个完整的 API 网关限流 + 认证 + 可观测性方案

**参考答案（场景题）**：

**需求**：支持 10 万 QPS，3 种认证方式，多维度限流，全链路追踪。

**架构**：
```
Client → LB → Gateway (N instances) → Upstream Services
                 ↕
               Redis (限流 + 缓存)
               PostgreSQL (配置)
               Prometheus (指标)
               Jaeger (追踪)
```

**执行流程**：
1. **INIT**：创建 Trace Span
2. **AUTH**：策略模式尝试 API Key → JWT → mTLS
3. **ACCESS**：三维限流 (consumer: 100/min, route: 1000/min, global: 10000/min)
4. **BALANCE**：加权轮询 + 健康检查过滤
5. **UPSTREAM**：连接池复用 + 超时控制
6. **LOG**：结构化日志 + Metrics + Trace 上报

**性能优化**：
- Redis Pipeline 批量限流检查
- 连接池预热
- 路由匹配用前缀树（Radix Tree）
- Metrics 标签归一化

## 🎯 场景设计题（2 题）

### 12. 设计一个支持 Prompt 注入检测的 AI 网关

**题目**：你的公司提供 LLM API 服务，需要在网关层检测并拦截 Prompt 注入攻击。请设计完整方案。

**参考要点**：

1. **多层检测**：
   - L1 关键词匹配（快速过滤明显攻击）
   - L2 正则模式匹配（检测变体）
   - L3 分类模型（高精度但有延迟）

2. **处理策略**：
   - Block（拦截）/ Warn（标记但放行）/ Log（仅记录）
   - 按 confidence 分级处理

3. **性能考量**：
   - L1/L2 延迟 <1ms，可同步执行
   - L3 延迟 10-50ms，可异步执行（先放行后分析）

4. **误报处理**：
   - 白名单机制（可信消费者跳过检测）
   - 人工审核队列

### 13. 设计一个高可用的网关蓝绿部署方案

**题目**：在不影响现有 SSE 长连接的前提下，将网关从 v1.0 升级到 v1.1。

**参考要点**：

1. **SSE 连接保护**：
   - 旧版本实例不立即下线，等待 SSE 连接自然结束（设最大等待 5 分钟）
   - 新连接全部路由到新版本

2. **流量切换**：
   - 金丝雀：5% → 25% → 50% → 100%
   - 每步观察错误率和延迟指标

3. **回滚机制**：
   - 旧版本实例保留 30 分钟
   - 错误率超阈值自动回滚

4. **配置兼容**：
   - 新旧版本共享 Redis 和 PostgreSQL
   - 配置格式向后兼容
