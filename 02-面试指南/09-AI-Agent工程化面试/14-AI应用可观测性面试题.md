## 参考答案

### Q1: 可观测性三大支柱在 AI 应用中的特殊性

<details>
<summary>参考答案</summary>

**Metrics（指标）、Traces（追踪）、Logs（日志）三大支柱在 AI 应用中都有独特需求。**

#### 三大支柱对比

| 支柱 | 传统应用 | AI 应用 |
|------|---------|---------|
| Metrics | QPS/延迟/错误率 | + TTFT/TPS/Token Cost/KV Cache % |
| Traces | HTTP 请求链路 | + LLM 调用链/Agent 多步执行 |
| Logs | 错误日志/访问日志 | + Prompt/Completion/工具调用 |

#### AI 特有指标

```
性能指标：
  TTFT (Time to First Token): 首 Token 延迟
  TPS (Tokens per Second): 生成速度
  E2E Latency: 端到端延迟（含 Prefill + Decode）

成本指标：
  Token Usage: prompt_tokens + completion_tokens
  Cost per Request: 每次请求的美元成本
  Daily/Monthly Cost: 按团队/模型汇总

质量指标：
  LLM Response Quality: 回答质量评分
  Hallucination Rate: 幻觉率
  Tool Call Success Rate: 工具调用成功率
```

</details>

### Q2: AI 应用核心监控指标

<details>
<summary>参考答案</summary>

**按 RED 方法（Rate/Error/Duration）+ AI 特有指标构建监控体系。**

#### 核心指标清单

| 类别 | 指标 | 告警阈值（参考） |
|------|------|----------------|
| 延迟 | TTFT P50/P95/P99 | P95 > 2s |
| 延迟 | TPS（tokens/second） | < 20 tokens/s |
| 吞吐 | QPS（请求/秒） | 超过容量 80% |
| 错误 | Error Rate | > 1% |
| 错误 | 429 Rate (被限流) | > 5% |
| 资源 | GPU 利用率 | > 95% 持续 5min |
| 资源 | KV Cache 使用率 | > 90% |
| 资源 | Pending Requests | > 10 |
| 成本 | 小时/日/月 Token 消耗 | 日超均值 3x |
| 质量 | 回答质量评分 | 平均 < 3/5 |

#### Prometheus 指标示例

```python
# 自定义 Prometheus 指标
from prometheus_client import Histogram, Counter, Gauge

llm_ttft = Histogram('llm_ttft_seconds', 'Time to first token',
                     ['model', 'provider'],
                     buckets=[0.1, 0.2, 0.5, 1, 2, 5, 10])

llm_tokens_total = Counter('llm_tokens_total', 'Total tokens used',
                           ['model', 'type'])  # type: prompt/completion

llm_cost_usd = Counter('llm_cost_usd_total', 'Total cost in USD',
                       ['model', 'team'])

kv_cache_usage = Gauge('kv_cache_usage_percent', 'KV Cache utilization')
```

### Q3: TTFT 和 TPS 分开监控

<details>
<summary>参考答案</summary>

**TTFT 反映用户等待时间（Prefill 性能），TPS 反映生成速度（Decode 性能）。瓶颈不同，优化方向不同。**

#### 两个指标的本质

```
TTFT (Time to First Token)：
  用户发送请求 → 收到第一个 token
  反映：Prefill 阶段性能
  瓶颈：GPU 算力（Compute-bound）
  影响因素：Prompt 长度、GPU 型号、队列深度

TPS (Tokens per Second)：
  第一个 token → 后续 token 的生成速度
  反映：Decode 阶段性能
  瓶颈：显存带宽（Memory-bound）
  影响因素：batch size、模型大小、量化方案
```

#### 为什么分开

| 场景 | TTFT | TPS | 诊断 |
|------|------|-----|------|
| 长 Prompt 提交 | 高 | 正常 | Prefill 耗时长，考虑 Chunked Prefill |
| 并发量增大 | 高 | 正常 | 队列积压，需要扩容 |
| 模型变大 | 正常 | 低 | Decode 变慢，考虑量化或换硬件 |
| KV Cache 满 | 高 | 低 | 资源紧张，需要扩容或优化 |

</details>

### Q4: LLM 调用链分布式追踪

<details>
<summary>参考答案</summary>

**基于 OpenTelemetry 标准，为每次 LLM 调用创建 Span，记录输入输出和 Token 使用。**

#### 追踪链路

```
[API Gateway] ─── trace_id: abc123
     │
     ├── [Auth Middleware] span: 2ms
     │
     ├── [Agent Loop - Step 1] span: 1.5s
     │    ├── [LLM Call] model: gpt-4o, tokens: 500+200, cost: $0.003
     │    └── [Tool: search] query: "xxx", results: 5
     │
     ├── [Agent Loop - Step 2] span: 2.0s
     │    ├── [LLM Call] model: gpt-4o, tokens: 800+300, cost: $0.005
     │    └── [Tool: read_file] path: "xxx.py", lines: 150
     │
     └── [Agent Loop - Step 3] span: 1.0s
          └── [LLM Call] model: gpt-4o, tokens: 1000+500, cost: $0.008
               → finish_reason: stop
```

#### 实现方式

```python
from opentelemetry import trace

tracer = trace.get_tracer("ai-agent")

async def agent_step(messages):
    with tracer.start_as_current_span("agent_step") as span:
        # LLM 调用
        with tracer.start_as_current_span("llm_call") as llm_span:
            response = await llm.chat(messages)
            llm_span.set_attribute("llm.model", response.model)
            llm_span.set_attribute("llm.prompt_tokens", response.usage.prompt_tokens)
            llm_span.set_attribute("llm.completion_tokens", response.usage.completion_tokens)
            llm_span.set_attribute("llm.cost_usd", calculate_cost(response))
        
        # 工具调用
        if response.tool_calls:
            with tracer.start_as_current_span("tool_call") as tool_span:
                tool_span.set_attribute("tool.name", tool_call.name)
                result = await execute_tool(tool_call)
```

### Q5: LangFuse vs LangSmith 对比

<details>
<summary>参考答案</summary>

**LangFuse 开源自托管适合数据敏感场景，LangSmith 功能更全适合快速迭代。**

| 维度 | LangFuse | LangSmith |
|------|---------|----------|
| 部署方式 | 自托管 / Cloud | SaaS only |
| 开源 | ✅ MIT License | ❌ |
| 数据安全 | 数据在自己服务器 | 数据在 LangChain 云端 |
| Trace 可视化 | ✅ 树形展开 | ✅ 更精美 |
| Prompt 管理 | ✅ 版本控制 | ✅ + A/B 测试 |
| 评估 | 基础（自定义 scorer） | 强大（内置评估器） |
| 数据集管理 | ✅ | ✅ + 标注工具 |
| LLM 集成 | OpenAI/Anthropic 等 | LangChain 深度集成 |

#### 选型建议

```
数据不能出企业网络？ → LangFuse（自托管）
用 LangChain 框架？ → LangSmith（原生集成）
小团队快速验证？ → LangSmith（功能更全）
大团队长期使用？ → LangFuse（无 vendor lock-in）
```

</details>

### Q6: 成本归因系统设计

<details>
<summary>参考答案</summary>

**按团队/模型/功能三个维度归因，支持日/周/月报表和实时告警。**

#### 数据模型

```sql
CREATE TABLE llm_usage (
    id BIGSERIAL PRIMARY KEY,
    timestamp TIMESTAMPTZ NOT NULL,
    team_id VARCHAR(50) NOT NULL,
    virtual_key_id VARCHAR(100),
    model VARCHAR(100) NOT NULL,
    provider VARCHAR(50) NOT NULL,
    feature VARCHAR(100),         -- 功能标签：code_gen/translate/summary
    prompt_tokens INTEGER NOT NULL,
    completion_tokens INTEGER NOT NULL,
    cached_tokens INTEGER DEFAULT 0,
    cost_usd DECIMAL(10,6) NOT NULL,
    latency_ms INTEGER,
    status VARCHAR(20)            -- success/error/timeout
);

-- 物化视图：团队日汇总
CREATE MATERIALIZED VIEW team_daily_cost AS
SELECT team_id, model, DATE(timestamp), 
       SUM(cost_usd), SUM(prompt_tokens), SUM(completion_tokens)
FROM llm_usage 
GROUP BY team_id, model, DATE(timestamp);
```

#### Grafana 看板维度

```
团队看板：各团队日/月消耗趋势
模型看板：各模型使用量和成本对比
功能看板：各功能模块的 Token 消耗
异常看板：成本异常波动告警
```

### Q7: Agent 多步执行追踪的特殊性

<details>
<summary>参考答案</summary>

**传统追踪是请求-响应模式（秒级），Agent 追踪是多步循环模式（分钟级），需要追踪 Agent 的决策过程。**

#### 差异对比

| 维度 | 传统 Web 追踪 | Agent 追踪 |
|------|-------------|-----------|
| 时间跨度 | 毫秒-秒 | 秒-分钟 |
| 调用模式 | 请求→处理→响应 | 循环：思考→行动→观察→思考 |
| 层级深度 | 3-5 层 | 10-50 层 |
| 非确定性 | 低（确定逻辑） | 高（LLM 决策不确定） |
| 需要追踪的 | 服务调用 | + LLM 思考过程 + 工具选择原因 |

#### Agent Trace 结构

```
Trace: "修复 #123 Issue"
  ├── Step 1: 分析问题 (LLM Call, 2.5s)
  │    └── Thought: "需要先看 Issue 描述和相关代码"
  ├── Step 2: 搜索代码 (Tool Call, 0.5s)
  │    └── Tool: grep("error pattern", "src/")
  ├── Step 3: 读取文件 (Tool Call, 0.1s)
  │    └── Tool: read_file("src/handler.py")
  ├── Step 4: 制定修复方案 (LLM Call, 3.0s)
  │    └── Thought: "错误在第 42 行，需要添加 null check"
  ├── Step 5: 编辑文件 (Tool Call, 0.2s)
  │    └── Tool: edit_file("src/handler.py", ...)
  └── Step 6: 运行测试 (Tool Call, 15s)
       └── Tool: run_test("pytest src/tests/")
```

</details>

### Q8: AI 服务告警分级策略

<details>
<summary>参考答案</summary>

**P0-P3 四级，按影响范围和紧急程度分级，每级有不同的响应 SLA 和通知方式。**

#### 告警分级

| 级别 | 触发条件 | 响应 SLA | 通知方式 |
|------|---------|---------|---------|
| P0 紧急 | 服务完全不可用 / 数据泄露 | 5 分钟 | 电话 + 短信 + PagerDuty |
| P1 严重 | 错误率 > 10% / TTFT > 10s / 成本失控 | 15 分钟 | 短信 + Slack |
| P2 警告 | 错误率 > 1% / TTFT > 5s / KV Cache > 90% | 1 小时 | Slack |
| P3 提示 | 日成本超均值 2x / 质量评分下降 | 24 小时 | 邮件 |

#### 告警规则示例

```yaml
# P0: 服务不可用
- alert: LLMServiceDown
  expr: up{job="vllm"} == 0
  for: 1m
  labels:
    severity: P0
  annotations:
    summary: "vLLM 推理服务宕机"

# P1: 成本失控
- alert: CostSpike
  expr: rate(llm_cost_usd_total[1h]) > 3 * avg_over_time(llm_cost_usd_total[7d])
  for: 5m
  labels:
    severity: P1
  annotations:
    summary: "LLM 成本异常飙升"

# P2: 延迟恶化
- alert: HighTTFT
  expr: histogram_quantile(0.95, llm_ttft_seconds) > 5
  for: 5m
  labels:
    severity: P2
```

</details>

### Q9: LLM 回答质量自动化监控

<details>
<summary>参考答案</summary>

**用 LLM-as-Judge 自动评估回答质量，结合用户反馈和 RAGAS 指标构建质量监控体系。**

#### 方案

```
方案1：LLM-as-Judge
  每 N 次请求抽样一次
  用另一个 LLM 评估回答质量（1-5 分）
  评估维度：准确性、完整性、相关性

方案2：用户反馈
  👍/👎 按钮
  计算日/周正反馈比

方案3：RAGAS 自动评估（RAG 场景）
  每日对评估集运行 RAGAS
  监控 Faithfulness/Relevancy 趋势

方案4：对比评估
  模型更新前后对比
  A/B 测试用不同模型
```

#### LLM-as-Judge 实现

```python
async def evaluate_quality(question, answer, context=None):
    eval_prompt = f"""请评估以下 AI 回答的质量（1-5 分）：

5分：完全准确、全面、有帮助
4分：基本准确，有小遗漏
3分：部分准确，有明显不足
2分：大部分不准确
1分：完全错误或不相关

请输出 JSON: {{"score": N, "reason": "..."}}"""
```

### Q10: TTFT 飙升排查

<details>
<summary>参考答案</summary>

**按检查清单逐层排查：GPU 指标 → 队列深度 → 模型配置 → 提供商状态 → 资源竞争。**

#### 排查清单

```
1. 检查 GPU 指标
   ✅ GPU 利用率是否 100%？ → 算力饱和
   ✅ KV Cache 使用率 > 90%？ → 内存不足，请求排队
   ✅ GPU 温度过高？ → 降频保护

2. 检查队列深度
   ✅ pending_requests 数量？ → 流量突增
   ✅ 近期是否有流量激增事件？

3. 检查 Prompt 变化
   ✅ 最近是否改了 System Prompt？ → 变长导致 Prefill 变慢
   ✅ 平均 prompt_tokens 是否增加？

4. 检查外部依赖
   ✅ 如果用云端 API：提供商是否有性能问题？
   ✅ 检查 status.openai.com 或 Anthropic 状态页

5. 检查资源竞争
   ✅ 同节点是否有其他 Pod 抢 GPU？
   ✅ 是否触发了 K8s 资源限制？

6. 快速恢复
   → 扩容推理实例
   → 启用 Fallback 到云端 API
   → 限流保护（拒绝新请求 > 全部超时）
```

#### 面试追问

- **如何预防**？基于 KV Cache 使用率的 HPA 自动扩容 + 前置限流
- **如何区分 Prefill 慢和 Decode 慢**？分别监控 TTFT（Prefill）和 TPS（Decode）

</details>
