## 参考答案

### Q1: SSE vs WebSocket

<details>
<summary>参考答案</summary>

**SSE 单向推送、HTTP 原生、自动重连，完美匹配 LLM 流式输出。WebSocket 双向通信、协议独立，适合实时交互场景。**

#### 核心对比

| 维度 | SSE | WebSocket |
|------|-----|-----------|
| 方向 | 单向（服务端→客户端） | 双向 |
| 协议 | HTTP（标准请求-响应） | 独立协议（ws://） |
| 重连 | 浏览器原生自动重连 + Last-Event-ID | 需手动实现 |
| 代理兼容 | 优秀（标准 HTTP，CDN/Nginx 原生支持） | 需要 Upgrade 支持 |
| 数据格式 | 纯文本（text/event-stream） | 二进制/文本 |
| 连接限制 | HTTP/1.1 每域名 6 个 | 无限制 |
| 适用场景 | LLM 流式输出、通知推送 | 聊天室、游戏、协作编辑 |

#### 为什么 LLM 选 SSE

```
LLM 输出是单向的：模型 → 用户（token by token）
用户输入是独立的 HTTP 请求（POST /v1/chat/completions）

SSE 优势：
1. 简单：HTTP 请求 + text/event-stream 响应
2. 可靠：浏览器原生自动重连
3. 兼容：所有代理/CDN/负载均衡器都支持 HTTP
4. 调试：curl -N 即可观察

WebSocket 过度设计：
1. 双向能力用不上（LLM 不需要客户端推送）
2. 代理支持更复杂（需要 Upgrade 协议）
3. 没有原生重连机制
```

#### SSE 数据格式

```
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive

data: {"id":"chatcmpl-xxx","choices":[{"delta":{"content":"Hello"}}]}

data: {"id":"chatcmpl-xxx","choices":[{"delta":{"content":" World"}}]}

data: [DONE]
```

</details>

### Q2: OpenAI SSE 流式协议

<details>
<summary>参考答案</summary>

**OpenAI 的 SSE 流式协议已成为行业标准——每行以 `data: ` 开头，内容是 JSON，以 `data: [DONE]` 结束。**

#### 协议格式

```
请求：POST /v1/chat/completions
Body: { "model": "gpt-4o", "messages": [...], "stream": true }

响应（SSE 流）：
data: {"id":"chatcmpl-abc","object":"chat.completion.chunk","choices":[{"index":0,"delta":{"role":"assistant"},"finish_reason":null}]}

data: {"id":"chatcmpl-abc","object":"chat.completion.chunk","choices":[{"index":0,"delta":{"content":"Hello"},"finish_reason":null}]}

data: {"id":"chatcmpl-abc","object":"chat.completion.chunk","choices":[{"index":0,"delta":{"content":" world"},"finish_reason":null}]}

data: {"id":"chatcmpl-abc","object":"chat.completion.chunk","choices":[{"index":0,"delta":{},"finish_reason":"stop"}]}

data: [DONE]
```

#### 关键字段

| 字段 | 说明 |
|------|------|
| `delta.role` | 首个 chunk 包含角色 |
| `delta.content` | 增量文本内容 |
| `delta.tool_calls` | 工具调用（增量 JSON） |
| `finish_reason` | null/stop/tool_calls/length |
| `usage` | 最后一个 chunk 包含 token 用量（需 `stream_options.include_usage: true`） |

#### 面试追问

- **为什么 tool_calls 也是流式的**？因为 function 参数可能很长（JSON），需要增量传输
- **如何获取流式响应的 token 计数**？设置 `stream_options: { include_usage: true }`

</details>

### Q3: Fetch + ReadableStream 消费 SSE

<details>
<summary>参考答案</summary>

**核心是 `response.body.getReader()` + TextDecoder + 按行解析。**

```typescript
async function streamChat(messages: Message[]) {
  const response = await fetch('/v1/chat/completions', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ model: 'gpt-4o', messages, stream: true }),
    signal: abortController.signal,  // 支持取消
  });

  const reader = response.body!.getReader();
  const decoder = new TextDecoder();
  let buffer = '';  // 处理不完整行的缓冲区

  while (true) {
    const { done, value } = await reader.read();
    if (done) break;

    buffer += decoder.decode(value, { stream: true });
    const lines = buffer.split('\n');
    buffer = lines.pop()!;  // 最后一行可能不完整，保留在缓冲区

    for (const line of lines) {
      if (line.startsWith('data: ')) {
        const data = line.slice(6);
        if (data === '[DONE]') return;
        
        const chunk = JSON.parse(data);
        const content = chunk.choices[0]?.delta?.content;
        if (content) {
          onToken(content);  // 逐 token 回调
        }
      }
    }
  }
}
```

#### 关键技巧

| 问题 | 解决方案 |
|------|---------|
| 不完整行 | buffer 机制，`lines.pop()` 保留最后一行 |
| 编码 | `TextDecoder({ stream: true })` 处理 UTF-8 多字节 |
| 取消 | `AbortController` 取消 fetch |
| 错误处理 | try-catch 包裹 JSON.parse |

</details>

### Q4: 背压（Backpressure）处理

<details>
<summary>参考答案</summary>

**当消费者（前端渲染）处理速度 < 生产者（LLM 输出）速度时，需要背压机制防止内存溢出。**

#### 场景

```
LLM 输出速度：100 tokens/s
前端渲染速度：60 fps（约 16ms/帧）

如果每个 token 触发一次 DOM 更新：
  → 每秒 100 次 DOM 操作 → 丢帧 → 界面卡顿

解决方案：
  1. 缓冲：将 tokens 攒到下一帧再批量渲染
  2. 流控：ReadableStream 的内置背压机制
```

#### 实现

```typescript
// 方案1：requestAnimationFrame 缓冲
let pending = '';
let rafId: number | null = null;

function onToken(token: string) {
  pending += token;
  if (!rafId) {
    rafId = requestAnimationFrame(() => {
      updateUI(pending);
      pending = '';
      rafId = null;
    });
  }
}

// 方案2：TransformStream 背压
const throttleStream = new TransformStream({
  transform(chunk, controller) {
    controller.enqueue(chunk);
  },
}, new CountQueuingStrategy({ highWaterMark: 10 }));
// highWaterMark=10：队列超过10个chunk时，上游自动暂停
```

#### 面试追问

- **Node.js 中的背压**？`stream.pipe()` 自动处理；手动需要检查 `writable.write()` 返回值和 `drain` 事件

</details>

### Q5: Nginx 代理 SSE 关键配置

<details>
<summary>参考答案</summary>

**核心：关闭所有缓冲层，让数据逐字节透传。**

```nginx
location /v1/chat/completions {
    proxy_pass http://backend;
    
    # 关闭缓冲（最重要！）
    proxy_buffering off;
    proxy_cache off;
    
    # SSE 需要的 Header
    proxy_set_header Connection '';
    proxy_http_version 1.1;
    chunked_transfer_encoding off;
    
    # 超时设置（LLM 生成可能很慢）
    proxy_read_timeout 300s;
    proxy_send_timeout 300s;
    
    # 告诉上游也不要缓冲
    add_header X-Accel-Buffering no;
}
```

#### 为什么每个配置都需要

| 配置 | 不设置的后果 |
|------|------------|
| `proxy_buffering off` | Nginx 攒够 buffer 才发，造成"卡顿后大段文字" |
| `proxy_read_timeout 300s` | 默认 60s，长生成任务中途断开 |
| `proxy_http_version 1.1` | HTTP/1.0 不支持 chunked transfer |
| `Connection ''` | 防止 proxy 添加 `Connection: close` |
| `X-Accel-Buffering no` | 上游 CDN 可能缓冲整个响应 |

#### 面试追问

- **AWS ALB 也有缓冲问题吗**？ALB 本身不缓冲 SSE，但 idle_timeout 默认 60s 需要调大
- **如何验证配置正确**？`curl -N https://your-api/v1/chat/completions` 观察是否逐行输出

</details>

### Q6: 客户端取消与后端停止推理

<details>
<summary>参考答案</summary>

**前端用 AbortController 取消请求，后端检测连接断开后停止 LLM 生成。**

#### 前端

```typescript
const controller = new AbortController();

// 发起请求
fetch('/v1/chat/completions', {
  signal: controller.signal,
  // ...
});

// 用户点击"停止生成"
stopButton.onclick = () => controller.abort();
```

#### 后端（Python FastAPI）

```python
@app.post("/v1/chat/completions")
async def chat(request: Request, body: ChatRequest):
    async def generate():
        async for chunk in llm.stream(body.messages):
            # 检查客户端是否断开
            if await request.is_disconnected():
                # 停止 LLM 生成
                llm.cancel_request(request_id)
                break
            yield f"data: {chunk.json()}\n\n"
        yield "data: [DONE]\n\n"
    
    return StreamingResponse(generate(), media_type="text/event-stream")
```

#### 推理引擎层面

```python
# vLLM：通过 abort 请求
await engine.abort(request_id)
# 这会释放该请求的 KV Cache 块，让其他请求使用
```

#### 面试追问

- **abort 后 KV Cache 会立即释放吗**？是的，vLLM 会立即回收该请求的 KV Block
- **如果不检测断开会怎样**？GPU 继续生成没人读的 token，浪费算力

</details>

### Q7: AG-UI 协议

<details>
<summary>参考答案</summary>

**AG-UI（Agent-User Interface）是为 Agent 交互设计的流式事件协议，比纯 SSE 更丰富，支持状态同步、工具调用进度等。**

#### 核心事件类型

| 事件 | 说明 | 数据 |
|------|------|------|
| `TEXT_MESSAGE_START` | 开始生成文本消息 | message_id, role |
| `TEXT_MESSAGE_CONTENT` | 文本内容增量 | delta (string) |
| `TEXT_MESSAGE_END` | 文本消息结束 | - |
| `TOOL_CALL_START` | 开始工具调用 | tool_name, call_id |
| `TOOL_CALL_ARGS` | 工具参数增量 | delta (JSON string) |
| `TOOL_CALL_END` | 工具调用结束 | - |
| `TOOL_RESULT` | 工具执行结果 | result, call_id |
| `STATE_SNAPSHOT` | Agent 状态快照 | 完整状态对象 |
| `STATE_DELTA` | Agent 状态增量 | JSON Patch |

#### 与纯 SSE 的区别

```
纯 SSE（OpenAI 格式）：
  只有 text delta → 前端只能渲染文字

AG-UI：
  TEXT + TOOL_CALL + STATE → 前端可以：
  - 显示 Agent 正在使用什么工具
  - 实时展示工具执行进度
  - 同步 Agent 内部状态到 UI
```

#### 面试追问

- **谁在用 AG-UI**？CopilotKit 社区主推，是比较新的协议标准
- **与 Vercel AI SDK 的 Data Stream Protocol 区别**？类似思路，但 AG-UI 更聚焦 Agent 场景

</details>

### Q8: SSE 在 HTTP/1.1 的限制

<details>
<summary>参考答案</summary>

**HTTP/1.1 下浏览器每域名最多 6 个并发连接，SSE 会长期占用连接，可能阻塞其他请求。**

#### 问题

```
HTTP/1.1 限制：
  浏览器对每个域名最多 6 个并发 TCP 连接
  一个 SSE 连接 = 长期占用 1 个连接
  
  如果用户打开 3 个 AI 对话标签页 = 3 个 SSE 连接
  只剩 3 个连接给其他 API 请求
  极端情况：6 个 SSE 连接 → 完全阻塞！
```

#### 解决方案

| 方案 | 效果 |
|------|------|
| 升级 HTTP/2 | 多路复用，一个 TCP 连接支持无限流 |
| 域名分片 | api1.example.com, api2.example.com |
| 生成完成后关闭连接 | SSE 只在生成时占用连接 |
| 使用 WebSocket | WebSocket 不受 6 连接限制 |

#### HTTP/2 的根本解决

```
HTTP/2 多路复用：
  一个 TCP 连接 → 无限个 Stream
  每个 SSE 是独立的 Stream
  不存在连接数限制问题
```

</details>

### Q9: 断点续传的 LLM 流式输出

<details>
<summary>参考答案</summary>

**核心：为每个 chunk 编号 + 服务端缓存 + 客户端记录已接收位置 + 断线重连时从断点恢复。**

#### 设计方案

```
服务端：
  每个 chunk 携带序号 event_id
  缓存最近 N 个 chunk（Redis/内存）
  
  data: {"id":"evt-001","content":"Hello"}
  data: {"id":"evt-002","content":" World"}
  data: {"id":"evt-003","content":"!"}

客户端：
  记录最后成功接收的 event_id
  断线重连时：GET /stream?last_event_id=evt-002
  
服务端：
  从 evt-003 开始重放缓存的 chunk
  然后继续实时推送新 chunk
```

#### SSE 原生支持

```
SSE 协议原生支持断点续传：
  服务端：通过 id: 字段标记每个事件
  客户端：自动重连时携带 Last-Event-ID header
  
  id: evt-001
  data: {"content":"Hello"}
  
  id: evt-002
  data: {"content":" World"}
```

#### 工程挑战

| 挑战 | 解决方案 |
|------|---------|
| 缓存大小 | 只缓存当前请求的 chunk，请求完成后清理 |
| LLM 已停止生成 | 重连后检查生成状态，如已完成直接发 [DONE] |
| 有状态 vs 无状态 | 用 Redis 共享状态，支持重连到不同后端节点 |

</details>

### Q10: 三层代理流式卡顿排查

<details>
<summary>参考答案</summary>

**逐层排查定位缓冲层：直连 Backend → 加 Nginx → 加 ALB，用 curl -N 逐层验证。**

#### 排查步骤

```
1. 直连 Backend 验证
   curl -N http://backend:8000/v1/chat/completions
   → 正常逐字输出？→ Backend 没问题

2. 通过 Nginx 验证
   curl -N http://nginx:80/v1/chat/completions
   → 卡顿？→ Nginx 配置问题
   检查：proxy_buffering, proxy_cache, proxy_read_timeout

3. 通过 ALB 验证
   curl -N https://alb.example.com/v1/chat/completions
   → 卡顿？→ ALB 配置问题
   检查：idle_timeout, target group 设置

4. 检查 Response Headers
   X-Accel-Buffering: no  ← 必须存在
   Transfer-Encoding: chunked  ← 正确的传输方式
```

#### 常见根因和修复

| 层 | 常见根因 | 修复 |
|----|---------|------|
| ALB | idle_timeout=60s，长生成超时断开 | 增加到 300s |
| Nginx | proxy_buffering 默认 on | `proxy_buffering off` |
| Nginx | proxy_cache 缓存了流式响应 | `proxy_cache off` |
| Backend | 框架自带响应缓冲 | 确保 StreamingResponse + flush |
| CDN | 缓冲整个响应再转发 | `Cache-Control: no-cache` + `X-Accel-Buffering: no` |

#### 快速验证命令

```bash
# 测量 TTFT（首字节时间）
curl -o /dev/null -s -w "TTFT: %{time_starttransfer}s\n" \
  -N -X POST https://api/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"gpt-4o","messages":[{"role":"user","content":"hi"}],"stream":true}'
```

</details>
