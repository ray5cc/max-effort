### Q1: 企业级 AI 编码助手架构

<details>
<summary>参考答案</summary>

**5 层架构：表现层 → API 层 → Agent 层 → 工具层 → 模型层 → 基础设施。**

#### 架构图

```
┌─────────────────────────────────────────────────┐
│  表现层：Next.js + Chat UI + Code Editor         │
├─────────────────────────────────────────────────┤
│  API 层：认证(JWT) + 限流(Redis) + API 路由      │
├─────────────────────────────────────────────────┤
│  Agent 层：                                      │
│  - ReAct 循环 / Plan-and-Execute                 │
│  - RAG (代码检索 + 文档检索)                      │
│  - Prompt 管理 (版本化 + A/B 测试)               │
│  - 上下文管理 (CLAUDE.md + 渐进加载)             │
├─────────────────────────────────────────────────┤
│  工具层 (MCP Servers)：                           │
│  - GitHub (PR/Issue/Code Search)                 │
│  - 文件系统 (读写代码文件)                        │
│  - 终端 (执行构建/测试/lint)                      │
│  - 代码搜索 (语义搜索 + grep)                    │
├─────────────────────────────────────────────────┤
│  模型层：                                        │
│  - LiteLLM 网关 (统一路由 + Fallback)            │
│  - vLLM (自托管 70B, 代码不出网)                  │
│  - GPT-4o / Claude (云端 Fallback)               │
├─────────────────────────────────────────────────┤
│  基础设施：                                       │
│  K8s + PostgreSQL + Redis + Qdrant               │
│  + LangFuse(追踪) + Prometheus(监控)             │
└─────────────────────────────────────────────────┘
```

#### 关键设计决策

| 决策 | 选择 | 原因 |
|------|------|------|
| 推理引擎 | vLLM 自托管 | 代码不出企业网络 |
| 多模型管理 | LiteLLM 网关 | 统一 API + Fallback |
| 成本优化 | 模型级联 8B→70B | 简单补全用小模型 |
| 工具标准 | MCP 协议 | 标准化、可复用 |
| 代码检索 | 混合检索 + Re-rank | 语义+关键词双保险 |

#### 面试追问

- **安全如何保证**？代码不出网（自托管推理）、沙箱执行、权限分级、审计日志
- **如何评估效果**？代码采纳率、Bug 修复成功率、开发者满意度调查

### Q2: 自托管+云端混合架构

<details>
<summary>参考答案</summary>

**LiteLLM 网关统一管理，敏感请求走自托管，非敏感请求可走云端，通过路由规则自动分流。**

#### 架构

```
请求 → 分类器（敏感/非敏感）
         ↓
  ┌── 敏感（含代码/内部数据）→ 自托管 vLLM (70B)
  │
  └── 非敏感（通用问答）→ 云端 API (GPT-4o)
         ↓
  LiteLLM 网关统一管理路由、Fallback、计费
```

#### 路由规则

```yaml
# LiteLLM 路由配置
model_list:
  - model_name: "code-model"
    litellm_params:
      model: "openai/llama-70b"
      api_base: "http://vllm-internal:8000/v1"
    model_info:
      description: "内部代码生成，数据不出网"
      
  - model_name: "general-model"
    litellm_params:
      model: "gpt-4o"
      api_key: "sk-xxx"
    model_info:
      description: "通用对话，非敏感内容"

router_settings:
  routing_strategy: "tag-based"
  # tag: sensitive → code-model
  # tag: general → general-model
```

#### 面试追问

- **自托管故障怎么办**？非敏感请求可 Fallback 到云端；敏感请求只能等恢复（安全优先）
- **成本对比**？自托管 2×H100 约 $6K/月，等效 GPT-4o API 调用量可能 $20K+/月

</details>

### Q3: 模型级联降低成本

<details>
<summary>参考答案</summary>

**核心思路：用分类器将请求分为简单/复杂，简单请求用便宜小模型，复杂请求用高级大模型。**

#### 实现方案

```
用户请求 → 复杂度分类
              │
    ┌── SIMPLE (70%) ──→ GPT-4o-mini / LLaMA-8B
    │                     成本: $0.15/1M tokens
    │
    └── COMPLEX (30%) ──→ GPT-4o / LLaMA-70B
                          成本: $2.50/1M tokens

整体成本 = 0.7 × $0.15 + 0.3 × $2.50 = $0.855/1M tokens
对比全用 GPT-4o: $2.50/1M tokens
节省: 66%
```

#### 分类器实现

```python
# 方案1：规则分类（零成本）
def classify_complexity(message):
    # 代码生成、长文档分析 → 复杂
    if any(kw in message for kw in ["写一个", "实现", "设计", "分析"]):
        return "COMPLEX"
    # 简单问答、翻译 → 简单
    return "SIMPLE"

# 方案2：小模型分类（极低成本）
def classify_with_llm(message):
    response = llm.chat(
        model="gpt-4o-mini",
        messages=[{
            "role": "system",
            "content": "判断以下问题的复杂度: SIMPLE 或 COMPLEX"
        }, {
            "role": "user",
            "content": message
        }]
    )
    return response.content.strip()
```

#### 质量保证

```
小模型回答 → 质量检查器（规则/LLM-as-Judge）
  质量达标 → 返回
  质量不达标 → 自动升级到大模型重新回答
```

</details>

### Q4: 安全架构设计

<details>
<summary>参考答案</summary>

**核心需求："代码不出企业网络"。需要从推理、传输、存储、访问四个层面保证。**

#### 安全架构

```
┌─ 企业内网 ──────────────────────────────┐
│                                        │
│  用户 → 内网 Web 应用                   │
│           ↓                            │
│  API 网关（认证 + 审计）                │
│           ↓                            │
│  Agent 服务（内网部署）                 │
│           ↓                            │
│  vLLM 推理服务（自托管 GPU 集群）       │
│                                        │
│  所有数据在内网流转，不触碰外网          │
└────────────────────────────────────────┘
    ⛔ 无出站连接到 OpenAI/Anthropic
```

#### 安全措施清单

| 层面 | 措施 |
|------|------|
| 推理 | 自托管 vLLM，模型权重在本地 |
| 网络 | 推理服务无出站网络访问 |
| 传输 | 内网 TLS，VPN 远程访问 |
| 存储 | 对话记录加密存储，定期清理 |
| 访问 | SSO + RBAC，按部门/项目授权 |
| 审计 | 所有操作记录到不可篡改审计日志 |
| 模型 | 定期检查模型不含训练数据泄露 |

</details>

### Q5: 自托管推理宕机容灾

<details>
<summary>参考答案</summary>

**多级容灾：多实例部署 + 健康检查 + 自动恢复 + 降级策略。**

#### 容灾方案

```
正常状态：
  vLLM 实例 A (Primary) ── 处理请求
  vLLM 实例 B (Standby) ── 热备

实例 A 宕机：
  Step 1: K8s 健康检查检测到失败（10s）
  Step 2: 流量自动切到实例 B（0s）
  Step 3: K8s 重启实例 A 的 Pod（60-90s，含模型加载）
  Step 4: 实例 A 恢复后重新加入负载均衡

整个集群宕机（极端情况）：
  Step 1: 检测到所有实例不可用
  Step 2: 非敏感请求 Fallback 到云端 API
  Step 3: 敏感请求返回降级提示
  Step 4: 告警通知 On-call 工程师
```

#### 关键配置

```yaml
# K8s 健康检查
livenessProbe:
  httpGet:
    path: /health
    port: 8000
  initialDelaySeconds: 120  # 模型加载时间
  periodSeconds: 10
  failureThreshold: 3

readinessProbe:
  httpGet:
    path: /health
    port: 8000
  periodSeconds: 5
```

</details>

### Q6: 技术选型决策过程

<details>
<summary>参考答案</summary>

**五步法：需求分析 → 约束识别 → 方案对比 → POC 验证 → 渐进上线。**

#### 实际项目经验示例

```
项目：企业内部 AI 编码助手
需求：代码补全、Bug 修复、代码解释

Step 1: 需求分析
  - 日活 500 开发者，峰值 QPS ~50
  - 平均输入 500 tokens，输出 300 tokens
  - 延迟要求：TTFT < 1s
  
Step 2: 约束识别
  - 安全约束：代码不出网（必须自托管）
  - 预算约束：月 GPU 成本 < $15,000
  - 团队约束：2 名 ML 工程师（运维能力有限）

Step 3: 方案对比
  | 方案 | 模型 | 推理引擎 | 成本 | 运维 |
  |------|------|---------|------|------|
  | A | LLaMA-70B | vLLM | $12K/月 | 中 |
  | B | Qwen-72B | SGLang | $12K/月 | 中 |
  | C | CodeLlama-34B | vLLM | $6K/月 | 低 |

Step 4: POC 验证（2 周）
  - 方案 A 和 C 各搭建一套
  - 用内部代码库测试代码补全质量
  - 结果：70B 明显优于 34B，选方案 A

Step 5: 渐进上线
  Week 1: 10% 用户灰度
  Week 2: 收集反馈，调优 Prompt
  Week 3: 50% 用户
  Week 4: 100% 全量上线
```

</details>

### Q7: GPU 成本系统性优化

<details>
<summary>参考答案</summary>

**六大杠杆：模型级联 → 缓存 → 量化 → 自动扩缩容 → 批处理 → 前缀缓存。**

#### 优化方案和效果

| 杠杆 | 节省幅度 | 实施难度 | 优先级 |
|------|---------|---------|--------|
| 模型级联 | 40-70% | 中 | ⭐⭐⭐⭐⭐ |
| Prompt Caching | 50-90% | 低 | ⭐⭐⭐⭐⭐ |
| 量化 (FP8/AWQ) | 50% GPU 需求 | 低 | ⭐⭐⭐⭐ |
| 自动扩缩容 | 20-30% | 中 | ⭐⭐⭐⭐ |
| Batch API | 50% 费用 | 低 | ⭐⭐⭐ |
| Prefix Caching | 30% Prefill | 低 | ⭐⭐⭐ |

#### 优化计划示例

```
当前：4×H100，月费 $24,000，日均 QPS 30

Phase 1（立即）：
  - 开启 FP8 量化 → 同等质量减少一半 GPU → 2×H100
  - 开启 Prefix Caching → 系统提示词免费
  → 月费降到 $12,000

Phase 2（1-2 周）：
  - 实现模型级联（8B 处理 70% 简单请求）
  → 月费降到 $8,000

Phase 3（持续）：
  - 配置 HPA 自动扩缩容（夜间缩至 1 实例）
  - 非实时任务走 Batch API
  → 月费降到 $6,000

总计节省 75%
```

</details>

### Q8: 从零构建 RAG 问答系统

<details>
<summary>参考答案</summary>

**分 4 个里程碑：MVP → 质量优化 → 生产加固 → 持续迭代。**

#### 里程碑规划

```
M1 - MVP（2 周）：
  - 文档解析（PDF/Markdown）
  - 固定长度分块 + OpenAI Embedding
  - pgvector 向量存储
  - 基础检索 + GPT-4o 生成
  - 简单 Web UI
  
M2 - 质量优化（2 周）：
  - 递归语义分块
  - 混合检索（向量 + BM25）
  - Cross-Encoder Re-ranking
  - RAGAS 评估管线
  - Prompt 优化（引用来源）

M3 - 生产加固（2 周）：
  - 增量索引管线
  - 权限控制
  - 监控告警（LangFuse）
  - 成本优化（缓存 + 级联）
  - 用户反馈收集

M4 - 持续迭代（持续）：
  - 根据评估数据持续优化
  - 支持更多文档格式
  - 多语言支持
  - Contextual Retrieval
```

#### 技术栈选择

```
文档解析：Unstructured / PyMuPDF
分块：LangChain RecursiveCharacterTextSplitter
Embedding：text-embedding-3-small (OpenAI) 或 bge-m3 (自托管)
向量库：pgvector（已有 PG）或 Qdrant
Re-ranking：bge-reranker-v2 或 Cohere
LLM：GPT-4o（云端）或 Qwen-72B（自托管）
评估：RAGAS
监控：LangFuse
```

### Q9: Agent 生产环境故障诊断

<details>
<summary>参考答案</summary>

**五步诊断：确认现象 → 检查监控 → 定位根因 → 紧急恢复 → 事后复盘。**

#### 诊断流程

```
1. 确认现象
   - 错误率多少？影响哪些用户？
   - 错误类型：LLM 错误？工具错误？超时？
   - 何时开始？是否有最近变更？

2. 检查监控
   - Grafana：错误率、延迟、QPS 趋势
   - LangFuse：错误请求的完整 Trace
   - 日志：具体错误信息

3. 常见根因
   | 现象 | 可能原因 |
   |------|---------|
   | LLM 返回 429 | API 限流 / 配额耗尽 |
   | LLM 返回 500 | 提供商故障 |
   | 工具调用超时 | 后端服务故障 |
   | Agent 无限循环 | Prompt 退化 / 模型版本变更 |
   | 回答质量下降 | 模型更新 / RAG 索引过期 |

4. 紧急恢复
   - LLM 故障 → 切换 Fallback 提供商
   - 工具故障 → 降级模式（禁用故障工具）
   - Agent 循环 → 增加步数限制 + 重启
   - 全面故障 → 降级为基础对话模式

5. 事后复盘
   - 时间线还原
   - 根因分析 (5 Whys)
   - 修复措施 + 预防措施
   - 更新 Runbook
```

</details>

### Q10: 最有挑战性的 AI 工程项目

<details>
<summary>参考答案</summary>

**这是一道开放题，用 STAR 方法（Situation-Task-Action-Result）回答。以下是参考模板。**

#### 回答模板

```
Situation（背景）：
  "我们团队负责构建企业内部的 AI 编码助手，
   需要支持 500+ 开发者，处理涉及公司核心代码的请求。"

Task（任务）：
  "核心挑战是在保证代码安全（不出网）的前提下，
   提供接近 GPT-4o 的代码生成质量，
   并将推理成本控制在月均 $15K 以内。"

Action（行动）：
  "1. 选择 LLaMA-70B 自托管，用 vLLM 部署在 2×H100 上
   2. 实现模型级联（8B 处理简单补全，70B 处理复杂生成）
   3. 用 MCP 协议标准化工具集成（GitHub、文件系统、终端）
   4. 建立 RAG 系统索引公司内部文档和代码库
   5. 搭建 LangFuse + Prometheus 监控体系"

Result（结果）：
  "代码采纳率达到 45%（行业平均 30%），
   月成本 $8K（低于预算 47%），
   开发者满意度 4.2/5。
   
   最大的挑战是模型级联的分类准确率，
   经过 3 轮迭代从 70% 提升到 92%。"
```

#### 面试官可能追问的方向

| 追问 | 如何回答 |
|------|---------|
| 为什么选 vLLM 而不是 SGLang？ | 生态成熟、模型支持全、团队熟悉 |
| 遇到过什么生产事故？ | KV Cache 满导致延迟飙升，通过 HPA 解决 |
| 代码采纳率如何衡量？ | 追踪补全建议的接受/拒绝 + 后续编辑距离 |
| 如果预算翻倍会怎么做？ | 升级到 405B 模型 + 增加 RAG 覆盖范围 |
| 如何保证代码质量？ | Agent 自动运行测试 + lint + 人工 Review |

</details>
