### Q01. Function Calling 是什么？它解决了什么问题？

**参考答案**

Function Calling（工具调用）是 LLM 的一种能力扩展机制：开发者在请求时声明若干"工具"的结构化描述，模型在推理时输出一段 **结构化的工具调用意图**（而非直接回答），宿主程序据此调用真实函数，再将结果回传给模型，由模型生成最终答案。核心价值在于打破 LLM 的"无法执行、无法访问实时数据"的边界——将检索、计算、外部 API 等能力以标准化接口接入模型。

```python
# 典型往返流程（OpenAI SDK）
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "北京今天天气？"}],
    tools=[weather_tool_schema],   # 声明工具
)
tool_call = response.choices[0].message.tool_calls[0]
# 宿主程序执行真实调用
result = get_weather(tool_call.function.arguments)
```

**关键知识点**

- 模型只输出"意图 + 参数"，**不直接执行**任何代码，执行权始终在宿主侧。
- 解决的核心问题：信息时效性（实时数据）、精确计算、副作用操作（发邮件、写数据库）三类场景。
- Function Calling 与 ReAct 思想一脉相承，但协议更标准化、延迟更低。

**延伸阅读**

- OpenAI Function Calling 官方文档：<https://platform.openai.com/docs/guides/function-calling>
- ReAct 原论文：<https://arxiv.org/abs/2210.03629>

### Q02. 工具调用与普通对话的流程区别？

**参考答案**

普通对话是单轮或多轮的"用户→模型→回答"闭环；工具调用在中间插入了一个"执行回路"（execution loop），通常需要 **至少两次** API 调用。完整流程如下：

```
用户消息
  ↓ [第一次 API 调用]
模型输出 tool_calls（finish_reason = "tool_calls"）
  ↓ 宿主执行工具
工具结果以 ToolMessage 追加到对话历史
  ↓ [第二次 API 调用]
模型基于工具结果输出最终答案（finish_reason = "stop"）
```

关键区别在于：`finish_reason` 的值、消息列表中新增的 `role: "tool"` 消息类型，以及宿主必须维护完整的消息历史进行追加。

**关键知识点**

- `finish_reason = "tool_calls"` 是判断模型请求调用工具的标志位。
- `role: "tool"` / `role: "tool_result"` 是工具结果专属的消息角色，不同提供商命名稍有差异。
- 循环可能发生多轮（多跳），直到 `finish_reason = "stop"` 才终止执行回路。

**延伸阅读**

- LangChain Agent 执行循环源码：<https://github.com/langchain-ai/langchain/blob/master/libs/langchain/langchain/agents/agent.py>
- Anthropic Tool Use 流程图：<https://docs.anthropic.com/en/docs/tool-use>

### Q03. 如何用 JSON Schema 定义一个工具？

**参考答案**

工具描述本质上是一段 JSON Schema 片段，包含名称、描述和参数三要素。描述质量直接影响模型的工具选择准确率，务必用自然语言清晰说明工具的用途和参数语义：

```json
{
  "type": "function",
  "function": {
    "name": "search_web",
    "description": "搜索互联网获取实时信息。当用户询问最新新闻、当前价格或近期事件时使用。",
    "parameters": {
      "type": "object",
      "properties": {
        "query": {
          "type": "string",
          "description": "搜索关键词，建议精简为 3-5 个核心词"
        },
        "max_results": {
          "type": "integer",
          "description": "返回结果数量，默认 5，最大 20",
          "default": 5
        }
      },
      "required": ["query"]
    }
  }
}
```

**关键知识点**

- `description` 字段是模型决策的核心依据，**应说明何时使用、何时不用**。
- `required` 列表中未列出的参数应提供 `default` 值，避免模型幻觉填充。
- 参数类型支持 `string`、`integer`、`boolean`、`array`、`object`，嵌套 Schema 同样有效。

**延伸阅读**

- JSON Schema 规范：<https://json-schema.org/understanding-json-schema/>
- OpenAI 工具定义最佳实践：<https://platform.openai.com/docs/guides/function-calling/best-practices>

### Q04. 工具执行结果如何返回给模型？

**参考答案**

工具执行完成后，需将结果以 `role: "tool"` 的消息追加到对话历史，并与发起调用的 `tool_call_id` 绑定，让模型能够将结果与调用意图对应。

```python
# 宿主执行工具并构造 ToolMessage
tool_result = execute_tool(tool_call.function.name,
                           tool_call.function.arguments)

messages.append({
    "role": "tool",
    "tool_call_id": tool_call.id,        # 与请求中的 id 对应
    "content": json.dumps(tool_result),   # 统一序列化为字符串
})

# 携带完整历史再次请求模型
final_response = client.chat.completions.create(
    model="gpt-4o",
    messages=messages,
)
```

结果内容建议序列化为 JSON 字符串；若结果过长（超过数千 token），应截断或摘要后再注入，避免超出上下文窗口。

**关键知识点**

- `tool_call_id` 是工具结果与工具请求的关联键，并行调用时每个工具各有独立 ID。
- 若工具执行失败，同样需要返回一条包含错误信息的 `role: "tool"` 消息，而非直接抛弃。
- 结果体积控制：超长结果（如网页全文）应先摘要再注入，避免占满上下文。

**延伸阅读**

- OpenAI 多工具调用返回示例：<https://platform.openai.com/docs/guides/function-calling/parallel-function-calling>
- LangChain ToolMessage 定义：<https://github.com/langchain-ai/langchain/blob/master/libs/core/langchain_core/messages/tool.py>

### Q05. LangChain `@tool` 装饰器的基本用法？

**参考答案**

`@tool` 是 LangChain 将普通 Python 函数快速转换为 `StructuredTool` 实例的语法糖。装饰器会读取函数的 **docstring** 作为工具描述，读取 **类型注解** 自动生成 JSON Schema。

```python
from langchain_core.tools import tool

@tool
def get_stock_price(ticker: str, currency: str = "USD") -> str:
    """查询股票的当前价格。ticker 为股票代码（如 AAPL），currency 为货币单位。"""
    price = fetch_price_api(ticker)       # 实际调用外部 API
    return f"{ticker}: {price} {currency}"

# 工具元信息自动生成
print(get_stock_price.name)          # "get_stock_price"
print(get_stock_price.description)   # 来自 docstring
print(get_stock_price.args_schema)   # 来自类型注解的 Pydantic Schema
```

如需自定义名称或异步支持，可用 `@tool(name="...", return_direct=True)` 或 `async def`。

**关键知识点**

- docstring **质量决定工具描述质量**，应清晰说明功能、参数语义和典型使用场景。
- 底层调用 `StructuredTool.from_function()`，自动用 `pydantic` 解析参数注解生成 Schema。
- `return_direct=True` 表示工具结果直接返回给用户，跳过模型二次归纳。

**延伸阅读**

- LangChain `@tool` 源码：<https://github.com/langchain-ai/langchain/blob/master/libs/core/langchain_core/tools/structured.py>
- LangChain 工具入门文档：<https://python.langchain.com/docs/concepts/tools/>

### Q06. 什么场景下应使用并行工具调用？

**参考答案**

当多个工具调用之间**没有数据依赖**（即 B 不需要 A 的结果）且均为 I/O 密集型操作时，并行调用可显著降低总延迟。典型场景：

1. **多源数据聚合**：同时查询天气、汇率、新闻三个 API。
2. **批量信息检索**：并行搜索多个关键词。
3. **并发写入**：同时向多个系统发送通知。

反例（不应并行）：先搜索文件路径，再根据路径读取内容——存在严格的先后依赖关系。

```python
# OpenAI 原生支持并行调用——单次请求可返回多个 tool_calls
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "北京天气和上海天气分别是多少？"}],
    tools=[weather_tool],
    parallel_tool_calls=True,   # 默认启用
)
# response.choices[0].message.tool_calls 中含两条调用
```

**关键知识点**

- OpenAI API 默认开启并行工具调用；设置 `parallel_tool_calls=False` 可强制串行（用于有状态副作用场景）。
- 并行调用全部完成后，需将**所有**工具结果一次性追加到 messages 列表，再做下一次 API 请求。
- 宿主侧应用 `asyncio.gather()` 并发执行，而非串行等待。

**延伸阅读**

- OpenAI 并行工具调用文档：<https://platform.openai.com/docs/guides/function-calling/parallel-function-calling>
- Python asyncio 并发模式：<https://docs.python.org/3/library/asyncio-task.html#asyncio.gather>

### Q07. 工具调用失败时的处理策略？

**参考答案**

工具调用失败不应直接崩溃，而应将错误信息**结构化地回传给模型**，让模型自主决策：重试、使用替代工具或向用户道歉。

```python
try:
    result = execute_tool(name, args)
    tool_content = json.dumps({"status": "success", "data": result})
except TimeoutError:
    tool_content = json.dumps({"status": "error",
                               "error_type": "timeout",
                               "message": "工具执行超时，请稍后重试"})
except ValueError as e:
    tool_content = json.dumps({"status": "error",
                               "error_type": "invalid_args",
                               "message": str(e)})

messages.append({"role": "tool",
                 "tool_call_id": tool_call.id,
                 "content": tool_content})
```

同时在宿主层加入重试（`tenacity`）、熔断（`circuit breaker`）和超时控制，避免单个工具故障拖垮整个 Agent 链路。

**关键知识点**

- **错误必须回传**：不能忽略失败，否则模型上下文缺失 ToolMessage 会导致 API 报错或逻辑混乱。
- 错误消息应携带 `error_type`，帮助模型做有针对性的恢复决策（重试 vs. 换工具）。
- 在 LangGraph 中可借助条件边将错误状态路由到专门的错误处理节点。

**延伸阅读**

- tenacity 重试库文档：<https://tenacity.readthedocs.io/>
- LangChain 工具错误处理：<https://python.langchain.com/docs/how_to/tools_error/>

### Q08. MCP（Model Context Protocol）是什么？

**参考答案**

MCP（Model Context Protocol）是 Anthropic 于 2024 年底开源的 **标准化 AI-工具集成协议**，目标是成为 AI 工具调用领域的"USB 接口"。它将工具提供方（MCP Server）与工具消费方（MCP Client，如 Claude、LangChain Agent）解耦，任何符合协议的工具可插拔接入任意支持 MCP 的 AI 系统。

```
[AI Agent / LLM Host]
       ↕  MCP Protocol (JSON-RPC 2.0)
[MCP Server: tools / resources / prompts]
       ↕
[实际服务: 数据库 / API / 文件系统 ...]
```

MCP 定义三类原语：**Tools**（可执行操作）、**Resources**（只读上下文数据）、**Prompts**（预制提示模板）。传输层支持 stdio、HTTP+SSE、WebSocket 三种形式。

**关键知识点**

- MCP 解决的核心问题是"N×M 集成爆炸"——N 个模型 × M 个工具的重复适配工作。
- 与 OpenAI Function Calling 最大区别：MCP 是跨模型、跨框架的**开放标准**，而非单一厂商的 API 规范。
- 目前 LangChain、LlamaIndex、Cursor、Claude Desktop 等均已原生支持 MCP。

**延伸阅读**

- MCP 官方规范：<https://modelcontextprotocol.io/specification>
- MCP GitHub 仓库：<https://github.com/modelcontextprotocol/specification>
- Anthropic 发布博客：<https://www.anthropic.com/news/model-context-protocol>

### Q09. OpenAI vs Anthropic vs Google 工具协议的 JSON 格式差异？

**参考答案**

三家主流提供商的工具协议在结构上高度相似，但细节差异不少：

**① 工具声明（tools 字段）**

```jsonc
// OpenAI / Azure OpenAI
{
  "type": "function",
  "function": { "name": "...", "description": "...", "parameters": { /* JSON Schema */ } }
}

// Anthropic Claude
{
  "name": "...",
  "description": "...",
  "input_schema": { /* JSON Schema，字段名不同 */ }
}

// Google Gemini (Function Declaration)
{
  "name": "...",
  "description": "...",
  "parameters": { /* OpenAPI-like Schema */ }
}
```

**② 模型返回的工具调用字段**

| 提供商    | 调用字段                                         | 参数字段                             |
| --------- | ------------------------------------------------ | ------------------------------------ |
| OpenAI    | `tool_calls[].function.arguments`                | JSON **字符串**（需 `json.loads()`） |
| Anthropic | `content[].input`                                | JSON **对象**（直接使用）            |
| Google    | `candidates[].content.parts[].functionCall.args` | JSON **对象**                        |

**③ 工具结果的 role**

- OpenAI：`role: "tool"`，搭配 `tool_call_id`
- Anthropic：`role: "user"`，`content` 为 `type: "tool_result"` 对象
- Google：`role: "user"`，`parts` 中含 `functionResponse`

**关键知识点**

- OpenAI 的 `arguments` 是字符串，常见 Bug：忘记 `json.loads()` 直接使用导致类型错误。
- Anthropic 的工具结果要放回 `role: "user"` 消息中，这与 OpenAI 完全不同。
- LangChain 通过统一的 `AIMessage.tool_calls` 抽象层屏蔽了上述差异。

**延伸阅读**

- OpenAI 工具格式：<https://platform.openai.com/docs/api-reference/chat/create#chat-create-tools>
- Anthropic 工具格式：<https://docs.anthropic.com/en/api/messages>
- Google Gemini Function Calling：<https://ai.google.dev/gemini-api/docs/function-calling>

### Q10. LangChain `BaseTool._run()` 的完整执行链路？

**参考答案**

LangChain Tool 的调用链路经过多层包装，从最外层 `invoke()` 到最内层 `_run()` 的流程如下：

```
tool.invoke(input)
  ↓ [BaseTool.invoke]       # 统一入口，处理 dict/str 输入格式
tool.run(input)
  ↓ [BaseTool.run]          # 执行前置钩子：callbacks、error_handling
  ↓ 调用 _parse_input()     # 用 args_schema (Pydantic) 验证并解析参数
  ↓ [BaseTool._run(**kwargs)] # 开发者实现的核心逻辑（同步）
  ↓ [BaseTool._arun]        # 异步版本（默认在线程池中包装 _run）
  ↓ 后置钩子：callbacks、返回值处理
```

```python
from langchain_core.tools import BaseTool
from pydantic import BaseModel, Field

class SearchInput(BaseModel):
    query: str = Field(description="搜索关键词")

class SearchTool(BaseTool):
    name: str = "search"
    description: str = "搜索互联网"
    args_schema: type[BaseModel] = SearchInput

    def _run(self, query: str) -> str:
        return web_search(query)   # 真实逻辑

    async def _arun(self, query: str) -> str:
        return await async_web_search(query)
```

**关键知识点**

- `run()` 在 `_run()` 外层负责 **异常捕获**，若 `handle_tool_error=True` 则将异常转为字符串返回而非抛出。
- `args_schema` 使用 Pydantic v2 进行参数验证，类型不匹配时直接报 `ValidationError`，不会进入 `_run()`。
- `invoke()` 是 LCEL（LangChain Expression Language）统一接口，使 Tool 可直接作为链节点使用。

### Q11. `StructuredTool.from_function()` 如何自动生成 JSON Schema？

**参考答案**

`StructuredTool.from_function()` 是 LangChain 将普通函数转化为结构化工具的核心工厂方法，其 Schema 生成流程分三步：

```python
from langchain_core.tools import StructuredTool

def calculate_bmi(weight_kg: float, height_m: float) -> str:
    """计算 BMI 指数。weight_kg 为体重（千克），height_m 为身高（米）。"""
    bmi = weight_kg / (height_m ** 2)
    return f"BMI = {bmi:.1f}"

tool = StructuredTool.from_function(
    func=calculate_bmi,
    name="calculate_bmi",          # 可覆盖，默认取函数名
    description="...",             # 可覆盖，默认取 docstring
    # args_schema 可显式传入 Pydantic 模型，否则自动推断
)
```

**自动推断流程**：

1. 用 `inspect.signature()` 提取函数签名中的参数名和类型注解。
2. 动态调用 `create_schema_from_function()` 生成一个临时 Pydantic `BaseModel` 子类。
3. 调用 Pydantic 的 `model_json_schema()` 输出标准 JSON Schema。

**关键知识点**

- 无类型注解的参数默认被推断为 `string` 类型，建议始终添加注解以生成精确 Schema。
- 若函数参数复杂（嵌套 dict、Union），建议**显式传入** `args_schema` Pydantic 模型，比自动推断更可控。
- `from_function()` 是 `@tool` 装饰器的底层实现，两者等价。

### Q12. `create_tool_calling_agent()` LCEL 管道的构成？

**参考答案**

`create_tool_calling_agent()` 是 LangChain 提供的高层工厂函数，返回一条 LCEL（Runnable）管道，内部结构为：

```
prompt | llm.bind_tools(tools) | ToolsAgentOutputParser()
```

详细拆解：

```python
from langchain.agents import create_tool_calling_agent, AgentExecutor
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o")
tools = [search_tool, calculator_tool]

# 内部等价于：
# agent = prompt | llm.bind_tools(tools) | ToolsAgentOutputParser()
agent = create_tool_calling_agent(llm, tools, prompt)

executor = AgentExecutor(agent=agent, tools=tools, verbose=True)
executor.invoke({"input": "今天北京天气如何？", "chat_history": []})
```

**三个组件职责**：

| 组件                     | 职责                                                                        |
| ------------------------ | --------------------------------------------------------------------------- |
| `prompt`                 | 注入系统提示、对话历史、工具调用中间结果（`agent_scratchpad`）              |
| `llm.bind_tools(tools)`  | 将工具 Schema 绑定到模型请求，模型输出 `AIMessage` 含 `tool_calls`          |
| `ToolsAgentOutputParser` | 将 `AIMessage` 解析为 `AgentAction`（继续调用工具）或 `AgentFinish`（结束） |

**关键知识点**

- `agent_scratchpad` 占位符是核心：每轮迭代后，已执行的工具调用和结果会被格式化注入此处，维持 Agent 的"工作记忆"。
- `AgentExecutor` 包裹 agent，负责循环调用直到收到 `AgentFinish`，并处理 `max_iterations` 熔断。
- 相比旧版 `initialize_agent()`，LCEL 管道更透明、可组合，便于插入自定义步骤。

### Q13. 工具结果如何注入对话历史（ToolMessage 角色）？

from langchain_core.messages import AIMessage, ToolMessage, HumanMessage

### Q14. MCP JSON-RPC 传输层的三种实现？

**参考答案**

MCP 使用 JSON-RPC 2.0 作为消息格式，支持三种传输层实现，适用于不同部署场景：

**① stdio（标准输入/输出）**

```python
# 适用于本地工具进程（IDE 插件、桌面应用）
# MCP Server 作为子进程启动，通过 stdin/stdout 通信
server = Server("my-tool-server")
async with stdio_server() as (read_stream, write_stream):
    await server.run(read_stream, write_stream, init_options)
```

**② HTTP + SSE（Server-Sent Events）**

```
Client → POST /messages    （发送请求）
Client ← GET  /sse         （接收流式响应，长连接）
```

适用于远程工具服务、Web 场景，Server 无需维护 WebSocket 连接状态。

**③ WebSocket**

```
ws://tool-server/mcp       （全双工持久连接）
```

适用于低延迟、高频工具调用场景（如实时代码补全工具）。

| 传输方式  | 延迟 | 部署复杂度 | 适用场景        |
| --------- | ---- | ---------- | --------------- |
| stdio     | 最低 | 最低       | 本地工具、CI/CD |
| HTTP+SSE  | 中   | 低         | SaaS 工具服务   |
| WebSocket | 低   | 中         | 实时交互应用    |

**关键知识点**

- stdio 是 MCP 最简单的实现方式，Claude Desktop 等桌面客户端默认使用此模式。
- HTTP+SSE 是目前云端 MCP Server 的主流部署方式，SSE 用于推送进度事件和流式结果。
- 所有传输层底层消息格式完全一致，切换传输层不需要改变业务逻辑代码。

### Q15. LangGraph 中如何设计工具节点和条件边？

**参考答案**

LangGraph 将 Agent 的工具调用循环显式建模为有向图：LLM 节点产生工具调用意图，条件边路由到工具节点或终止，工具节点执行后将结果写回 State，再循环到 LLM 节点。

```python
from langgraph.graph import StateGraph, END
from langgraph.prebuilt import ToolNode

# 定义 State
class AgentState(TypedDict):
    messages: list[BaseMessage]

# 条件函数：判断是否需要执行工具
def should_use_tools(state: AgentState):
    last = state["messages"][-1]
    if hasattr(last, "tool_calls") and last.tool_calls:
        return "tools"     # 路由到工具节点
    return END             # 结束

# 构建图
graph = StateGraph(AgentState)
graph.add_node("llm", call_llm)
graph.add_node("tools", ToolNode(tools))   # 内置工具节点，自动处理并行调用

graph.set_entry_point("llm")
graph.add_conditional_edges("llm", should_use_tools, {"tools": "tools", END: END})
graph.add_edge("tools", "llm")             # 工具执行后回到 LLM

app = graph.compile()
```

**关键知识点**

- `ToolNode` 是 LangGraph 内置节点，自动处理并行 `tool_calls`、异步执行和 `ToolMessage` 构造。
- 条件边（`add_conditional_edges`）是路由决策的核心，函数返回值对应边标签。
- 若需 Human-in-the-loop，在工具节点前加 `interrupt_before=["tools"]` 即可暂停等待人工确认。

**延伸阅读**

- LangGraph 工具调用教程：<https://langchain-ai.github.io/langgraph/tutorials/introduction/>

### Q16. 并行工具调用如何用 `asyncio.gather()` 实现？

**参考答案**

当模型在单次响应中返回多个 `tool_calls` 时，宿主侧应并行执行所有工具，而非串行等待：

```python
import asyncio
import json
from langchain_core.messages import ToolMessage

async def execute_tool_call(tool_call: dict, tools_map: dict) -> ToolMessage:
    """执行单个工具调用，返回 ToolMessage"""
    tool = tools_map[tool_call["name"]]
    try:
        result = await tool.ainvoke(tool_call["args"])
        content = json.dumps(result, ensure_ascii=False)
    except Exception as e:
        content = json.dumps({"error": str(e)})
    return ToolMessage(tool_call_id=tool_call["id"], content=content)

async def run_tools_parallel(
    ai_message,
    tools_map: dict
) -> list[ToolMessage]:
    """并行执行所有工具调用"""
    tasks = [
        execute_tool_call(tc, tools_map)
        for tc in ai_message.tool_calls
    ]
    return await asyncio.gather(*tasks)

# 调用示例
tool_messages = await run_tools_parallel(ai_message, tools_map)
messages.extend(tool_messages)
```

**关键知识点**

- `asyncio.gather()` 并发执行所有协程，总延迟≈单个最慢工具的延迟，而非各工具延迟之和。
- 若工具本身是同步阻塞函数，使用 `asyncio.get_event_loop().run_in_executor()` 包装，避免阻塞事件循环。
- 结果顺序：`gather()` 的返回顺序与传入协程顺序一致，便于与 `tool_call_id` 对应。

**延伸阅读**

- Python asyncio.gather 文档：<https://docs.python.org/3/library/asyncio-task.html#asyncio.gather>
- LangGraph 异步工具执行：<https://langchain-ai.github.io/langgraph/how-tos/async/>

### Q17. 工具超时和重试的最佳实践（`tenacity` 库）？

**参考答案**

外部工具调用是 Agent 链路中最脆弱的环节，必须配置超时和重试策略：

```python
import asyncio
from tenacity import (
    retry, stop_after_attempt, wait_exponential,
    retry_if_exception_type, before_sleep_log
)
import logging

logger = logging.getLogger(__name__)

@retry(
    stop=stop_after_attempt(3),                      # 最多重试 3 次
    wait=wait_exponential(multiplier=1, min=1, max=10),  # 指数退避：1s, 2s, 4s
    retry=retry_if_exception_type((TimeoutError, ConnectionError)),  # 只对网络错误重试
    before_sleep=before_sleep_log(logger, logging.WARNING),  # 重试前记录日志
)
async def call_external_api(params: dict) -> dict:
    async with asyncio.timeout(5.0):   # Python 3.11+ 原生超时
        return await http_client.post("/api", json=params)
```

对于 Agent 整体，建议**同时设置**工具级超时（单次调用）和 Agent 级超时（整个任务），防止无限循环。

**关键知识点**

- **指数退避 + 抖动**（`wait_random_exponential`）可避免多个 Agent 实例同时重试造成的"惊群效应"。
- `retry_if_exception_type` 应仅覆盖**可重试错误**（网络超时、5xx）；业务错误（4xx、参数无效）不应重试。
- LangGraph 的 `max_iterations` 提供 Agent 级别的兜底熔断，配合工具级重试形成双层保护。

**延伸阅读**

- tenacity 文档：<https://tenacity.readthedocs.io/en/latest/>

### Q18. `ToolsAgentOutputParser` 的解析逻辑（tool_calls → ToolAgentAction）？

**参考答案**

`ToolsAgentOutputParser` 是 LCEL Agent 管道的最后一环，负责将 LLM 输出的 `AIMessage` 翻译为 LangChain Agent 的控制流对象：

```python
# 简化的内部逻辑
def parse(self, message: AIMessage):
    # 有 tool_calls → 继续执行工具
    if message.tool_calls:
        actions = []
        for tc in message.tool_calls:
            actions.append(ToolAgentAction(
                tool=tc["name"],
                tool_input=tc["args"],     # 已是 dict，无需 json.loads
                log=f"Invoking: {tc['name']} with {tc['args']}",
                message_log=[message],
                tool_call_id=tc["id"],
            ))
        return actions   # 返回 List[ToolAgentAction]，AgentExecutor 继续循环

    # 无 tool_calls → 终止
    return AgentFinish(
        return_values={"output": message.content},
        log=message.content,
    )
```

`AgentExecutor` 检查返回类型：收到 `List[ToolAgentAction]` 则执行工具并继续循环；收到 `AgentFinish` 则返回最终结果。

**关键知识点**

- `ToolAgentAction` vs `AgentAction`：前者携带 `tool_call_id`，用于构造 `ToolMessage`；后者是旧式 ReAct 解析器产物，无 ID。
- 解析器不执行任何实际工具调用，仅做 **数据类型转换**，保持单一职责。
- 若模型同时输出 `content`（文本）和 `tool_calls`（调用），解析器优先处理 `tool_calls`，文本内容保留在 `message_log` 中。

### Q19. 工具调用安全性防护：如何防范 SSRF 和命令注入？

**参考答案**

工具调用将 LLM 生成内容直接转化为系统操作，是典型的**不可信输入执行**场景，必须在工具实现层强制进行安全过滤。

**① 防范 SSRF（服务器端请求伪造）**

```python
import ipaddress
from urllib.parse import urlparse

BLOCKED_HOSTS = {"localhost", "127.0.0.1", "0.0.0.0", "169.254.169.254"}  # AWS IMDSv1
ALLOWED_SCHEMES = {"https"}

def validate_url(url: str) -> str:
    parsed = urlparse(url)
    if parsed.scheme not in ALLOWED_SCHEMES:
        raise ValueError(f"不允许的协议: {parsed.scheme}")
    hostname = parsed.hostname or ""
    if hostname in BLOCKED_HOSTS:
        raise ValueError(f"禁止访问内网地址: {hostname}")
    try:
        ip = ipaddress.ip_address(hostname)
        if ip.is_private or ip.is_loopback or ip.is_link_local:
            raise ValueError(f"禁止访问私有/链路本地 IP: {ip}")
    except ValueError:
        pass  # 非 IP 地址，继续
    return url
```

**② 防范命令注入**

```python
import subprocess
import shlex

# 错误示例：直接拼接 shell 命令
# subprocess.run(f"ls {user_input}", shell=True)  # 危险！

# 正确做法：使用参数列表，禁用 shell=True
def safe_list_files(directory: str) -> list[str]:
    # 白名单路径校验
    allowed_base = "/data/workspace"
    abs_path = os.path.realpath(os.path.join(allowed_base, directory))
    if not abs_path.startswith(allowed_base):
        raise PermissionError("路径穿越攻击被拦截")
    result = subprocess.run(["ls", "-la", abs_path],
                            capture_output=True, text=True,
                            shell=False)   # shell=False 是关键
    return result.stdout.splitlines()
```

**关键知识点**

- **纵深防御**：除工具层过滤外，建议在 Agent 外层加 **Prompt 防护层**（检测 prompt injection 指令），以及**沙箱执行环境**（容器/seccomp 隔离）。
- 最小权限原则：工具应只申请完成任务所需的最小权限，绝不给 Agent 使用 root 凭证或全局写权限。
- 对于代码执行类工具，必须在隔离沙箱（如 E2B、Firecracker microVM）中运行，禁止在主机进程内 `exec()`。

**延伸阅读**

- OWASP LLM Top 10 — LLM07 不安全插件设计：<https://owasp.org/www-project-top-10-for-large-language-model-applications/>
- E2B 代码沙箱：<https://e2b.dev/docs>
- SSRF 防护指南：<https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html>

### Q20. 动态工具注册机制如何实现（运行时添加工具）？

**参考答案**

动态工具注册需要解决两个问题：**运行时更新工具列表**（让 LLM 知道新工具）和**动态路由执行**（Agent 能找到并调用新工具）。

```python
from langchain_core.tools import BaseTool
from typing import Any

class DynamicToolRegistry:
    def __init__(self):
        self._tools: dict[str, BaseTool] = {}

    def register(self, tool: BaseTool):
        """注册工具，支持热更新（同名覆盖）"""
        self._tools[tool.name] = tool

    def unregister(self, name: str):
        self._tools.pop(name, None)

    @property
    def tools(self) -> list[BaseTool]:
        return list(self._tools.values())

    def get_schemas(self) -> list[dict]:
        """生成当前工具集的 JSON Schema，用于绑定到 LLM"""
        return [t.get_input_schema().schema() for t in self._tools.values()]

    def execute(self, name: str, args: dict) -> Any:
        """动态路由执行"""
        if name not in self._tools:
            raise KeyError(f"工具 '{name}' 未注册")
        return self._tools[name].invoke(args)

# 使用示例
registry = DynamicToolRegistry()
registry.register(search_tool)

# 运行时新增工具（无需重启 Agent）
registry.register(new_calculator_tool)

# 每次 LLM 请求时动态绑定最新工具集
llm_with_tools = llm.bind_tools(registry.tools)
```

**关键知识点**

- 动态注册的工具在**下一次 LLM 请求**时才生效，因为工具 Schema 在每次 API 调用时实时注入。
- 在多 Agent 并发场景下，`_tools` 字典需加读写锁（`asyncio.Lock`）保证并发安全。
- 对于大规模工具库（>50 个工具），动态注册应与 **Tool RAG**（见 Q21）结合，避免每次把全量 Schema 塞入上下文。

- LangChain 动态工具绑定：<https://python.langchain.com/docs/how_to/tools_dynamic/>
- LangGraph 运行时工具更新示例：<https://langchain-ai.github.io/langgraph/how-tos/update-state-from-tools/>

### Q21. 大规模工具库的检索策略（Tool RAG：用向量搜索选工具）？

**参考答案**

当工具数量超过 20-30 个时，将全量 Schema 注入上下文会造成：① token 浪费；② 模型注意力稀释导致工具选择准确率下降。解决方案是**Tool RAG**：将工具描述向量化存储，按用户意图检索 Top-K 相关工具，只注入这部分工具的 Schema。

```python
from langchain_community.vectorstores import FAISS
from langchain_openai import OpenAIEmbeddings
from langchain_core.tools import BaseTool

class ToolRAG:
    def __init__(self, tools: list[BaseTool], top_k: int = 5):
        self.tools_map = {t.name: t for t in tools}
        self.top_k = top_k
        # 以工具名 + 描述构建向量索引
        texts = [f"{t.name}: {t.description}" for t in tools]
        metadatas = [{"name": t.name} for t in tools]
        self.vectorstore = FAISS.from_texts(
            texts, OpenAIEmbeddings(), metadatas=metadatas
        )

    def retrieve(self, query: str) -> list[BaseTool]:
        """根据用户意图检索最相关的工具"""
        docs = self.vectorstore.similarity_search(query, k=self.top_k)
        return [self.tools_map[d.metadata["name"]] for d in docs]

# 每次调用前动态选工具
tool_rag = ToolRAG(all_tools, top_k=5)
relevant_tools = tool_rag.retrieve(user_query)
llm_with_tools = llm.bind_tools(relevant_tools)
```

**关键知识点**

- 向量化的**粒度**很重要：单独索引工具描述可能不够，建议把示例用法（few-shot examples）也纳入索引文本。
- 为防止关键工具漏检，可设置**必选工具白名单**（如身份验证工具），每次请求无条件注入。
- 检索结果应加**缓存**（按 query embedding 相似度缓存），避免每次请求都做向量检索。

### Q22. 工具调用与 Human-in-the-loop 如何结合（LangGraph interrupt）？

**参考答案**

某些工具具有不可逆的副作用（发送邮件、扣款、删除数据），执行前需要人工确认。LangGraph 通过 `interrupt()` 原语实现图执行的暂停与恢复。

```python
from langgraph.types import interrupt, Command
from langgraph.checkpoint.memory import MemorySaver

def human_approval_node(state: AgentState):
    """需要人工审批的工具前置节点"""
    pending_tool = state["messages"][-1].tool_calls[0]
    # interrupt() 暂停图执行，将 value 传给外部
    decision = interrupt({
        "action": "confirm_tool_call",
        "tool_name": pending_tool["name"],
        "tool_args": pending_tool["args"],
        "message": f"是否允许执行工具 {pending_tool['name']}？"
    })
    if decision != "approve":
        # 注入拒绝消息，让 LLM 知道用户拒绝了
        return {"messages": [ToolMessage(
            tool_call_id=pending_tool["id"],
            content="用户拒绝了此次工具调用"
        )]}
    return state   # 放行，继续执行工具节点

# 编译时注入 checkpointer（持久化暂停状态）
app = graph.compile(checkpointer=MemorySaver(),
                    interrupt_before=["human_approval"])

# 外部系统恢复执行
app.invoke(Command(resume="approve"), config={"thread_id": "123"})
```

**关键知识点**

- `interrupt()` 会抛出一个特殊异常，LangGraph 将当前图状态序列化到 `checkpointer`，等待外部 `resume`。
- `thread_id` 是会话隔离键，同一用户的多轮对话共享同一个线程的检查点。
- Human-in-the-loop 不仅用于安全确认，还可用于：**纠错**（用户修改工具参数）、**多步表单填写**（逐步收集信息）等场景。

**延伸阅读**

- LangGraph Human-in-the-loop 文档：<https://langchain-ai.github.io/langgraph/concepts/human_in_the_loop/>
- LangGraph interrupt 源码：<https://github.com/langchain-ai/langgraph/blob/main/libs/langgraph/langgraph/types.py>

### Q23. 如何为工具调用系统设计可观测性（trace tool invocations）？

**参考答案**

工具调用链路涉及多次 LLM 请求和工具执行，可观测性需覆盖：**延迟追踪**、**参数记录**、**错误归因**、**token 消耗**四个维度。

```python
from langsmith import traceable
import time

@traceable(
    name="tool_execution",
    tags=["tool", "production"],
    metadata={"service": "agent-v2"}
)
async def execute_tool_with_trace(
    tool_name: str,
    tool_args: dict,
    tool_call_id: str,
) -> dict:
    """带完整可观测性的工具执行包装"""
    start = time.monotonic()
    span_attrs = {"tool.name": tool_name, "tool.call_id": tool_call_id}
    try:
        result = await tools_map[tool_name].ainvoke(tool_args)
        span_attrs["tool.status"] = "success"
        return result
    except Exception as e:
        span_attrs["tool.status"] = "error"
        span_attrs["tool.error"] = str(e)
        raise
    finally:
        span_attrs["tool.latency_ms"] = (time.monotonic() - start) * 1000
        # LangSmith 会自动捕获 @traceable 函数的输入输出

# 结合 OpenTelemetry 做自托管追踪
from opentelemetry import trace
tracer = trace.get_tracer("agent.tools")

with tracer.start_as_current_span("tool_call") as span:
    span.set_attribute("tool.name", tool_name)
    result = execute_tool(tool_name, args)
```

**关键知识点**

- **LangSmith** 是 LangChain 生态的官方追踪平台，通过 `@traceable` 或自动检测零侵入捕获完整调用树。
- 关键指标：工具调用成功率、P95 延迟、参数错误率（反映工具 Schema 质量）、LLM token 消耗分布。
- 对于私有化部署，可接入 **OpenTelemetry** + Jaeger/Tempo，所有 LangChain 调用已内置 OTEL instrumentation。

### Q24. 多 Agent 系统中工具共享与隔离的设计模式？

**参考答案**

多 Agent 系统中，工具共享带来效率提升，工具隔离带来安全保障，二者需要在架构层面权衡设计。

**① 共享工具池模式（Shared Tool Pool）**

```python
# 所有 Agent 共享一个中心化工具注册表
class SharedToolPool:
    def __init__(self):
        self._registry = {}
        self._permissions: dict[str, set[str]] = {}   # tool_name -> {agent_id}

    def register(self, tool: BaseTool, allowed_agents: set[str]):
        self._registry[tool.name] = tool
        self._permissions[tool.name] = allowed_agents

    def get_tools_for_agent(self, agent_id: str) -> list[BaseTool]:
        return [t for name, t in self._registry.items()
                if agent_id in self._permissions.get(name, set())]
```

**② 工具隔离模式（Sandboxed Tool Scope）**

每个 Agent 拥有独立的工具实例，共享代码但独立状态（如独立的 HTTP Session、独立的数据库连接池）：

```python
def create_agent_tools(agent_id: str, user_context: dict) -> list[BaseTool]:
    """为每个 Agent 实例创建隔离的工具集"""
    return [
        SearchTool(api_key=user_context["search_key"]),   # 独立凭证
        DatabaseTool(schema=f"agent_{agent_id}"),          # 独立 DB 命名空间
        FileTool(base_path=f"/workspace/{agent_id}/"),     # 独立文件沙箱
    ]
```

**③ 工具代理模式（Tool Proxy / MCP Server）**

通过 MCP Server 作为工具代理，在网络层实施访问控制和请求审计，多个 Agent 通过协议而非直接函数调用使用工具。

**关键知识点**

- **敏感工具**（如支付、删除操作）应实施严格隔离，每个 Agent 使用受限凭证和专属命名空间。
- **只读工具**（如搜索、查询）可安全共享，但仍需速率限制防止单个 Agent 过度占用。
- MCP Server 模式天然提供工具隔离层，是多 Agent 系统中推荐的工具共享架构。

- LangGraph 多 Agent 架构：<https://langchain-ai.github.io/langgraph/concepts/multi_agent/>
- CrewAI 工具共享模式：<https://docs.crewai.com/concepts/tools>

### Q25. 工具描述质量对工具选择准确率的影响及优化方法？

**参考答案**

研究表明，工具描述质量是影响工具选择准确率的**最关键单一因素**，远超工具数量和 Schema 复杂度的影响。低质量描述（模糊、缺乏边界条件说明）可导致工具选择准确率下降 20-40%。

**工具描述优化检查清单**：

```python
# 差描述示例
@tool
def search(q: str) -> str:
    """搜索。"""   # ❌ 过于模糊，无适用场景说明

# 优描述示例
@tool
def web_search(query: str, freshness: str = "any") -> str:
    """
    在互联网上搜索实时信息。

    适用场景：
    - 最新新闻、当前价格、近期事件
    - 需要超出训练截止日期的最新信息时

    不适用场景：
    - 数学计算（请使用 calculator 工具）
    - 已知事实的查询（直接从知识库回答）

    参数：
    - query: 精简的搜索关键词，3-5 个词效果最佳
    - freshness: 时效过滤，可选 "day"/"week"/"month"/"any"
    """
    return fetch_search_results(query, freshness)
```

**系统化优化方法**：

1. **基于失败案例迭代**：收集工具选择错误的 case，分析是描述歧义还是边界不清晰。
2. **对比测试（A/B Test）**：对同一工具测试不同描述版本，用 LLM 作为评判者打分。
3. **Few-shot 示例注入**：在描述中添加 2-3 个典型用例（`示例：用户问"今天比特币价格"→ 调用此工具`）。
4. **描述冲突检测**：当多工具功能相近时，明确在每个工具描述中注明与相似工具的区别。

**关键知识点**

- "负向描述"（说明**何时不该用**）与"正向描述"同等重要，可显著减少工具误选。
- 工具描述本质上是向 LLM 注入的 few-shot 先验，应以模型能理解的语言（而非程序员视角）撰写。
- 定期用 Gorilla、ToolBench 等基准评测工具选择准确率，将描述优化纳入 CI/CD 流程。
