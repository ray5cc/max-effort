### Q01. `EventSource` API 的三种状态（CONNECTING/OPEN/CLOSED）及事件监听？

**参考答案**

`EventSource` 是浏览器原生 SSE 客户端，内置三种就绪状态和自动重连机制：

```javascript
const es = new EventSource("/api/chat/stream");

// 三种状态值
// EventSource.CONNECTING = 0  正在建立连接
// EventSource.OPEN       = 1  连接已建立，正在接收数据
// EventSource.CLOSED     = 2  连接已关闭

// 标准事件监听
es.onopen = () => console.log("连接已建立");
es.onerror = (e) => {
  if (e.target.readyState === EventSource.CLOSED) {
    console.log("连接已关闭，不再重连");
  }
};
es.onmessage = (e) => console.log("默认 message 事件：", e.data);

// 自定义事件类型（对应服务端 event: token）
es.addEventListener("token", (e) => {
  const { content } = JSON.parse(e.data);
  appendToken(content);
});
es.addEventListener("done", () => es.close()); // 手动关闭，停止自动重连
```

浏览器在连接中断后会自动重连（默认 3 秒），可通过服务端 `retry:` 字段调整间隔。

**关键知识点**

- `readyState` 是只读属性，反映当前连接状态；`CONNECTING` 状态包括初始连接和自动重连两种情形。
- 必须在收到结束信号后调用 `es.close()`，否则浏览器会无限重连。
- 自定义事件须用 `addEventListener`，`onmessage` 只能捕获 `event: message` 或无 `event` 字段的事件。

**延伸阅读**

- [MDN EventSource](https://developer.mozilla.org/zh-CN/docs/Web/API/EventSource)
- [W3C SSE 规范](https://html.spec.whatwg.org/multipage/server-sent-events.html)

### Q02. 如何用 Fetch API 读取流式响应（`response.body.getReader()`）？

**参考答案**

Fetch Streams API 提供比 `EventSource` 更灵活的流式读取能力，支持 POST 请求和自定义请求头：

```javascript
async function streamChat(prompt) {
  const response = await fetch("/api/chat", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ prompt }),
  });

  const reader = response.body.getReader();
  const decoder = new TextDecoder("utf-8");

  try {
    while (true) {
      const { done, value } = await reader.read();
      if (done) break;

      const text = decoder.decode(value, { stream: true }); // stream:true 处理多字节边界
      // 解析 SSE 格式
      for (const line of text.split("\n")) {
        if (line.startsWith("data: ")) {
          const data = line.slice(6);
          if (data === "[DONE]") return;
          const { content } = JSON.parse(data);
          appendToUI(content);
        }
      }
    }
  } finally {
    reader.releaseLock(); // 释放锁，允许其他读取器使用
  }
}
```

**关键知识点**

- `TextDecoder` 的 `stream: true` 选项保留跨 chunk 的多字节字符边界，避免中文乱码。
- `reader.releaseLock()` 须在 `finally` 块中调用，防止连接异常时资源泄漏。
- Fetch Streams 支持 POST，`EventSource` 只支持 GET，是 LLM 流式输出的更佳选择。

**延伸阅读**

- [MDN Streams API](https://developer.mozilla.org/zh-CN/docs/Web/API/Streams_API)
- [Fetch API 流式读取示例](https://developer.mozilla.org/zh-CN/docs/Web/API/ReadableStream)

### Q03. React 18 `startTransition` 的作用是什么？

**参考答案**

`startTransition` 将状态更新标记为"非紧急过渡"，让 React 优先处理用户交互（如输入、点击），避免流式 token 更新阻塞 UI 响应：

```jsx
import { useState, useTransition } from "react";

function ChatInput() {
  const [tokens, setTokens] = useState("");
  const [isPending, startTransition] = useTransition();

  async function handleStream(reader) {
    while (true) {
      const { done, value } = await reader.read();
      if (done) break;
      const newToken = decode(value);

      // 将 token 追加标记为低优先级过渡更新
      startTransition(() => {
        setTokens((prev) => prev + newToken);
      });
    }
  }

  return (
    <div>
      {isPending && <span className="opacity-50">生成中…</span>}
      <div>{tokens}</div>
    </div>
  );
}
```

若不使用 `startTransition`，每个 token 的同步 setState 都会触发高优先级渲染，导致用户在流式输出期间输入卡顿。

**关键知识点**

- `startTransition` 不延迟渲染，而是降低更新优先级，允许 React 中断并优先处理紧急更新。
- `isPending` 标志位可用于显示加载态，而无需额外状态管理。
- 与 `useDeferredValue` 配合使用：`startTransition` 用于写，`useDeferredValue` 用于读。

**延伸阅读**

- [React 18 并发特性文档](https://react.dev/blog/2022/03/29/react-v18#new-feature-transitions)
- [useTransition API 参考](https://react.dev/reference/react/useTransition)

### Q04. Next.js App Router 中 `loading.tsx` 如何实现流式 SSR？

**参考答案**

Next.js App Router 基于 React 18 `Suspense` 实现流式 SSR，`loading.tsx` 是 `Suspense` fallback 的约定式文件：

```
app/
├── chat/
│   ├── page.tsx        ← 异步服务端组件（触发流式边界）
│   ├── loading.tsx     ← Suspense fallback（立即发送到客户端）
│   └── error.tsx       ← 错误边界
```

```tsx
// app/chat/loading.tsx —— 立即渲染，无需等待数据
export default function Loading() {
  return <ChatSkeleton />;
}

// app/chat/page.tsx —— async 组件触发 Suspense 边界
export default async function ChatPage({ params }) {
  // 这里的 await 触发流式边界：loading.tsx 先发送，数据就绪后替换
  const history = await fetchChatHistory(params.id);
  return <ChatContainer history={history} />;
}
```

HTTP 响应流程：服务端先发送包含 `loading.tsx` 内容的 HTML shell → 数据就绪后通过内联 `<script>` 注入替换内容 → 客户端 hydration。

**关键知识点**

- `loading.tsx` 对应路由段的 Suspense 边界，粒度比手动包裹 `<Suspense>` 更粗。
- 流式 SSR 改善 TTFB（Time To First Byte），用户更快看到页面骨架。
- 嵌套路由可有多个 `loading.tsx`，实现分层流式加载。

**延伸阅读**

- [Next.js Streaming 文档](https://nextjs.org/docs/app/building-your-application/routing/loading-ui-and-streaming)
- [React Suspense for Data Fetching](https://react.dev/reference/react/Suspense)

### Q05. Vercel AI SDK `useChat` hook 提供了哪些状态？

**参考答案**

`useChat` 封装了 SSE 流式通信、消息管理和加载状态，是构建 AI Chat UI 的核心 hook：

```tsx
import { useChat } from "ai/react";

function ChatUI() {
  const {
    messages, // Message[]：{ id, role, content, createdAt }
    input, // string：当前输入框内容
    handleInputChange, // 输入框 onChange 处理器
    handleSubmit, // form onSubmit 处理器
    isLoading, // boolean：是否正在等待/接收响应
    error, // Error | undefined：请求错误
    stop, // () => void：中止当前流式输出
    reload, // () => void：重新发送最后一条消息
    append, // (message) => void：手动追加消息并触发请求
    setMessages, // Dispatch：直接覆盖消息列表（用于加载历史）
  } = useChat({
    api: "/api/chat",
    initialMessages: loadedHistory,
    onFinish: (message) => saveToDatabase(message),
    onError: (error) => toast.error(error.message),
  });

  return (
    <form onSubmit={handleSubmit}>
      <MessageList messages={messages} isLoading={isLoading} />
      <input value={input} onChange={handleInputChange} />
      {isLoading && <button onClick={stop}>停止</button>}
    </form>
  );
}
```

**关键知识点**

- `messages` 数组包含完整对话历史，流式输出期间最后一条 `assistant` 消息实时更新。
- `append` 用于程序化发送消息（如示例问题点击），`setMessages` 用于加载持久化历史。
- `isLoading` 在请求发出到流式响应结束全程为 `true`，可用于禁用输入框。

**延伸阅读**

- [Vercel AI SDK useChat 文档](https://sdk.vercel.ai/docs/reference/ai-sdk-ui/use-chat)
- [Vercel AI SDK GitHub](https://github.com/vercel/ai)

### Q06. 为什么需要 rAF（requestAnimationFrame）批量更新流式文字渲染？

**参考答案**

LLM 流式输出频率可达 20～50 token/秒，若每个 token 都触发一次 React setState，会导致每秒 20～50 次重渲染，造成 CPU 占用飙升和帧率下降：

```javascript
// ❌ 不推荐：每个 token 直接 setState
onToken((token) => setContent((prev) => prev + token));

// ✅ 推荐：rAF 批量合并，每帧最多更新一次（约 16ms/60fps）
function useStreamingText() {
  const [content, setContent] = useState("");
  const bufferRef = useRef("");
  const rafRef = useRef(null);

  const appendToken = useCallback((token) => {
    bufferRef.current += token; // 先写入 buffer，不触发渲染

    if (!rafRef.current) {
      rafRef.current = requestAnimationFrame(() => {
        setContent((prev) => prev + bufferRef.current); // 每帧合并一次
        bufferRef.current = "";
        rafRef.current = null;
      });
    }
  }, []);

  return { content, appendToken };
}
```

rAF 将多个 token 合并到下一帧统一渲染，将重渲染次数从 50次/秒降至 60帧/秒上限，视觉效果相同但性能提升 3～5 倍。

**关键知识点**

- `requestAnimationFrame` 与浏览器刷新率同步（60～120fps），是 UI 批量更新的最佳时机。
- `useRef` 存储 buffer 不触发渲染，是此模式的关键设计。
- React 18 自动批处理（Auto Batching）部分场景可替代手动 rAF，但对高频异步回调效果有限。

**延伸阅读**

- [MDN requestAnimationFrame](https://developer.mozilla.org/zh-CN/docs/Web/API/window/requestAnimationFrame)
- [React 18 Auto Batching](https://react.dev/blog/2022/03/29/react-v18#new-feature-automatic-batching)

### Q07. Chat 消息的四种状态机（pending/streaming/complete/error）各自的 UI 表现？

**参考答案**

```typescript
type MessageStatus = "pending" | "streaming" | "complete" | "error";

interface Message {
  id: string;
  role: "user" | "assistant";
  content: string;
  status: MessageStatus;
}
```

| 状态        | 触发时机                      | UI 表现                              |
| ----------- | ----------------------------- | ------------------------------------ |
| `pending`   | 请求已发出，等待首个 token    | 显示三点跳动动画（skeleton loader）  |
| `streaming` | 收到首个 token，持续接收      | 实时追加文字 + 末尾光标闪烁 `▋`      |
| `complete`  | 流式响应结束（收到 `[DONE]`） | 静态文字 + 显示操作按钮（复制/点赞） |
| `error`     | 网络错误或 API 返回错误       | 红色错误提示 + 重试按钮              |

```tsx
function MessageBubble({ message }: { message: Message }) {
  return (
    <div className="message">
      {message.status === "pending" && <ThinkingDots />}
      {["streaming", "complete"].includes(message.status) && (
        <MarkdownContent content={message.content} />
      )}
      {message.status === "streaming" && <span className="cursor">▋</span>}
      {message.status === "complete" && <ActionBar messageId={message.id} />}
      {message.status === "error" && <ErrorWithRetry />}
    </div>
  );
}
```

**关键知识点**

- 状态机设计避免用多个 boolean 标志（`isLoading`/`hasError`）产生非法状态组合。
- `pending` 与 `streaming` 的区分提升用户感知：前者显示"思考中"，后者显示实际内容。
- `complete` 状态才显示操作按钮，防止用户在流式输出中途触发复制等操作。

**延伸阅读**

- [XState: 状态机建模](https://stately.ai/docs/state-machines-and-statecharts)
- [UI 状态机设计模式](https://kentcdodds.com/blog/implementing-a-simple-state-machine-library-in-javascript)

### Q08. SSE 与 WebSocket 的本质区别（协议/双向性/重连机制）？

**参考答案**

| 维度         | SSE                                       | WebSocket                                     |
| ------------ | ----------------------------------------- | --------------------------------------------- |
| **协议**     | 基于 HTTP/1.1 或 HTTP/2                   | 独立协议（`ws://` / `wss://`），HTTP 握手升级 |
| **方向**     | 单向（服务端 → 客户端）                   | 全双工（双向实时通信）                        |
| **重连**     | 浏览器自动重连，支持 `Last-Event-ID` 续传 | 须手动实现重连逻辑                            |
| **格式**     | 纯文本 `text/event-stream`                | 二进制帧或文本帧，自定义协议                  |
| **代理穿透** | HTTP 兼容，穿透性好                       | 部分代理/防火墙不支持                         |
| **连接数**   | HTTP/2 多路复用，可复用连接               | 每个连接独占 TCP                              |
| **适用场景** | LLM token 推送、通知、日志流              | 实时语音、多人游戏、协作编辑                  |

对于 AI Chat 应用，SSE 是首选方案：基于标准 HTTP，无需额外基础设施，浏览器原生支持自动重连，且 LLM 输出本质上是单向流。

**关键知识点**

- SSE 在 HTTP/2 下可在单个 TCP 连接上多路复用，大规模场景下连接开销远低于 WebSocket。
- WebSocket 握手后协议升级，不再是 HTTP，导致某些 CDN 和负载均衡器处理复杂。
- 需要客户端上行数据（如语音流、实时协作）时才应选择 WebSocket。

**延伸阅读**

- [SSE vs WebSocket 深度对比](https://ably.com/blog/websockets-vs-sse)
- [HTTP/2 Server Push vs SSE](https://developer.mozilla.org/zh-CN/docs/Web/HTTP/Server-sent_events)

### Q09. `TextDecoder` + `ReadableStreamDefaultReader` 处理 UTF-8 多字节字符的边界问题？

**参考答案**

UTF-8 中文字符占 3 字节，当 chunk 边界恰好切断一个汉字时，若不正确处理会产生乱码：

```javascript
// ❌ 错误：stream: false 时跨 chunk 的多字节字符解码失败
const decoder = new TextDecoder();
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  console.log(decoder.decode(value)); // 可能乱码！
}

// ✅ 正确：stream: true 让 TextDecoder 跨 chunk 保留不完整字节
const decoder = new TextDecoder("utf-8");
const reader = response.body.getReader();
let buffer = "";

while (true) {
  const { done, value } = await reader.read();
  if (done) {
    // flush 剩余 buffer
    if (buffer) processLine(buffer);
    break;
  }

  buffer += decoder.decode(value, { stream: true }); // 关键：stream: true

  // 按 SSE 换行切分，保留不完整的最后一行
  const lines = buffer.split("\n");
  buffer = lines.pop(); // 未完整的行留在 buffer
  for (const line of lines) {
    if (line.startsWith("data: ")) processSSELine(line);
  }
}
```

**关键知识点**

- `TextDecoder` 的 `stream: true` 选项使解码器跨 chunk 保留不完整的多字节序列。
- SSE 行切分须保留最后一个不含 `\n` 的片段到下一个 chunk，防止事件被截断。
- `decoder.decode(value)` 不传 `stream: true` 等同于 `stream: false`，即刷新模式，会丢失跨 chunk 字节。

**延伸阅读**

- [MDN TextDecoder](https://developer.mozilla.org/zh-CN/docs/Web/API/TextDecoder)
- [UTF-8 编码规范](https://tools.ietf.org/html/rfc3629)

### Q10. Next.js App Router 与 Pages Router 在流式渲染上的实现差异？

**参考答案**

| 维度           | App Router（RSC）                   | Pages Router                                 |
| -------------- | ----------------------------------- | -------------------------------------------- |
| **流式机制**   | React 18 `Suspense` + RSC 原生支持  | `getServerSideProps` 不支持流式，须手动实现  |
| **数据获取**   | async 服务端组件直接 `await`        | `getServerSideProps` 阻塞式返回全部数据      |
| **流式边界**   | `loading.tsx` / `<Suspense>` 声明式 | 须用 `res.write()` 手动实现 chunked transfer |
| **客户端流式** | `useChat` / Fetch Streams           | 同，无差异                                   |

```tsx
// App Router：声明式流式 SSR
// app/chat/[id]/page.tsx
export default async function Page({ params }) {
  return (
    <div>
      <StaticHeader /> {/* 立即渲染 */}
      <Suspense fallback={<Skeleton />}>
        <AsyncMessages id={params.id} /> {/* 数据就绪后流式注入 */}
      </Suspense>
    </div>
  );
}

// Pages Router：须手动 chunked（不推荐，复杂度高）
export async function getServerSideProps(ctx) {
  // 只能返回完整 props，无法中途 flush
  const data = await fetchAll();
  return { props: { data } };
}
```

**关键知识点**

- App Router 的流式 SSR 将 HTML 分段发送，改善 LCP 和 TTFB，无需等待所有数据。
- Pages Router 若需流式须绕过 `getServerSideProps` 直接操作 `res`，不推荐在生产使用。
- AI Chat 新项目应首选 App Router，充分利用 RSC 和 Suspense 流式能力。

### Q11. Vercel AI SDK 数据流协议（type 0/2/a/d）各字段含义？

**参考答案**

Vercel AI SDK 定义了一套基于 SSE 的自定义数据流协议，每行格式为 `{type}:{JSON_value}\n`：

| 类型码 | 名称               | 数据格式                                | 说明                         |
| ------ | ------------------ | --------------------------------------- | ---------------------------- |
| `0`    | Text delta         | `"token字符串"`                         | LLM 输出的文字 token         |
| `2`    | Data               | `[{...}]`                               | 自定义元数据（如来源文档）   |
| `8`    | Message annotation | `[{...}]`                               | 消息级注解（如工具调用结果） |
| `a`    | Tool call          | `{"toolCallId":...}`                    | 工具调用开始                 |
| `b`    | Tool result        | `{"toolCallId":...,"result":...}`       | 工具调用结果                 |
| `d`    | Finish message     | `{"finishReason":"stop","usage":{...}}` | 流结束，附带 token 用量      |
| `e`    | Finish step        | `{"finishReason":"tool-calls"}`         | 多步骤 Agent 的单步结束      |

```javascript
// 解析示例
function parseStreamLine(line) {
  const colonIdx = line.indexOf(":");
  const type = line.slice(0, colonIdx);
  const value = JSON.parse(line.slice(colonIdx + 1));

  switch (type) {
    case "0":
      appendText(value);
      break;
    case "2":
      setMetadata(value);
      break;
    case "d":
      onFinish(value);
      break;
  }
}
```

**关键知识点**

- `type: "0"` 是最高频的文字 token，需要高效处理以保证渲染流畅。
- `type: "d"` 的 `usage` 字段包含 `promptTokens` 和 `completionTokens`，可用于前端成本展示。
- 自定义 `type: "2"` 数据可通过 `streamData.append()` 在服务端注入，用于传递 RAG 来源等信息。

### Q13. 如何实现 Chat 滚动吸底逻辑（`scrollIntoView` vs `scrollTop` 的性能对比）？

**参考答案**

```tsx
function ChatMessageList({ messages, isStreaming }) {
  const bottomRef = useRef<HTMLDivElement>(null);
  const containerRef = useRef<HTMLDivElement>(null);
  const [userScrolledUp, setUserScrolledUp] = useState(false);

  // 检测用户是否手动上滚（暂停自动吸底）
  const handleScroll = useCallback(() => {
    const el = containerRef.current;
    if (!el) return;
    const distanceFromBottom = el.scrollHeight - el.scrollTop - el.clientHeight;
    setUserScrolledUp(distanceFromBottom > 100);
  }, []);

  // 新消息到来时，若用户未上滚则自动吸底
  useEffect(() => {
    if (!userScrolledUp && isStreaming) {
      // scrollIntoView：简单但触发 layout，性能略差
      // bottomRef.current?.scrollIntoView({ behavior: "smooth" });

      // scrollTop 直接赋值：性能更好，避免 smooth 动画在高频更新时堆叠
      const el = containerRef.current;
      if (el) el.scrollTop = el.scrollHeight;
    }
  }, [messages, isStreaming, userScrolledUp]);

  return (
    <div ref={containerRef} onScroll={handleScroll} className="overflow-y-auto">
      {messages.map((m) => (
        <MessageBubble key={m.id} message={m} />
      ))}
      <div ref={bottomRef} />
    </div>
  );
}
```

`scrollTop = scrollHeight` 性能优于 `scrollIntoView({ behavior: "smooth" })`，因为后者在高频调用时会产生动画队列堆积。

**关键知识点**

- 用户上滚时暂停自动吸底，避免打断阅读历史消息的体验。
- 使用 `scrollTop` 直接赋值而非 smooth 动画，防止流式高频更新时的卡顿。
- 新消息到达时判断 `distanceFromBottom < 100px` 作为"接近底部"的阈值。

### Q14. Zustand 管理 Chat 状态的 store 设计（message 数组的不可变更新）？

**参考答案**

```typescript
import { create } from "zustand";
import { immer } from "zustand/middleware/immer";

interface Message {
  id: string;
  role: "user" | "assistant";
  content: string;
  status: "pending" | "streaming" | "complete" | "error";
}

interface ChatStore {
  messages: Message[];
  isLoading: boolean;
  addUserMessage: (content: string) => string;
  startAssistantMessage: (id: string) => void;
  appendToken: (id: string, token: string) => void;
  completeMessage: (id: string) => void;
  setError: (id: string, error: string) => void;
}

export const useChatStore = create<ChatStore>()(
  immer((set) => ({
    messages: [],
    isLoading: false,

    addUserMessage: (content) => {
      const id = crypto.randomUUID();
      set((state) => {
        state.messages.push({ id, role: "user", content, status: "complete" });
        state.isLoading = true;
      });
      return id;
    },

    appendToken: (id, token) =>
      set((state) => {
        const msg = state.messages.find((m) => m.id === id);
        if (msg) {
          msg.content += token;
          msg.status = "streaming";
        }
      }),

    completeMessage: (id) =>
      set((state) => {
        const msg = state.messages.find((m) => m.id === id);
        if (msg) {
          msg.status = "complete";
        }
        state.isLoading = false;
      }),
  })),
);
```

**关键知识点**

- `immer` 中间件允许直接修改 draft state，内部自动生成不可变更新，避免手动展开对象。
- `appendToken` 通过 `id` 精确定位消息，不触发整个列表重渲染（配合 `React.memo`）。
- 流式场景下 store 更新频率极高，须确保选择器（selector）细粒度，避免无关组件重渲染。

### Q15. Web Worker 用于 Markdown 解析的通信开销与适用阈值？

**参考答案**

Markdown 解析（尤其含代码高亮）是 CPU 密集型操作，可能阻塞主线程：

```javascript
// markdown.worker.js
import { unified } from "unified";
import remarkParse from "remark-parse";
import remarkGfm from "remark-gfm";
import remarkRehype from "remark-rehype";
import rehypeHighlight from "rehype-highlight";
import rehypeStringify from "rehype-stringify";

const processor = unified()
  .use(remarkParse)
  .use(remarkGfm)
  .use(remarkRehype)
  .use(rehypeHighlight)
  .use(rehypeStringify);

self.onmessage = async ({ data: { id, markdown } }) => {
  const html = String(await processor.process(markdown));
  self.postMessage({ id, html });
};

// 主线程调用
const worker = new Worker(new URL("./markdown.worker.js", import.meta.url));
const parseMarkdown = (markdown) =>
  new Promise((resolve) => {
    const id = Math.random();
    worker.postMessage({ id, markdown });
    worker.onmessage = ({ data }) => data.id === id && resolve(data.html);
  });
```

**适用阈值**：Markdown 内容 > 2000 字符（含代码块）或解析耗时 > 16ms 时，才值得引入 Worker 的通信开销（postMessage 序列化约 0.1～0.5ms）。流式输出期间的增量 token 不适合 Worker（开销/收益比差）。

**关键知识点**

- `postMessage` 使用结构化克隆传递数据，大字符串序列化有额外开销。
- Worker 初始化（加载 wasm/依赖）耗时较长，须提前初始化而非按需创建。
- 流式输出结束后的一次性完整渲染（`complete` 状态切换时）是最适合 Worker 的时机。

### Q16. React `useCallback` + `useMemo` 在流式渲染中的防止闭包陷阱技巧？

**参考答案**

流式渲染中每个 token 触发 setState，导致组件频繁重渲染。闭包陷阱指回调函数捕获了旧的 state 值：

```tsx
// ❌ 闭包陷阱：appendToken 捕获了初始的 content 值（空字符串）
function StreamingMessage() {
  const [content, setContent] = useState("");
  const appendToken = useCallback((token: string) => {
    setContent(content + token); // content 始终是 "" ！
  }, []); // 依赖数组为空，永远不更新
}

// ✅ 解法 1：使用函数式更新，不依赖闭包中的 state
const appendToken = useCallback((token: string) => {
  setContent((prev) => prev + token); // prev 始终是最新值
}, []);

// ✅ 解法 2：useRef 存储最新值，绕过闭包
const contentRef = useRef("");
const appendToken = useCallback((token: string) => {
  contentRef.current += token;
  startTransition(() => setContent(contentRef.current));
}, []);

// ✅ useMemo 防止子组件不必要的重渲染
const memoizedMessages = useMemo(
  () => messages.filter((m) => m.role === "assistant"),
  [messages], // 精确依赖，而非整个 store
);
```

**关键知识点**

- 函数式 setState（`prev => prev + token`）是流式更新的最佳实践，完全避免闭包陷阱。
- `useRef` 可作为"逃生舱"存储可变值，不触发重渲染且始终引用最新值。
- `useMemo` 依赖数组须精确，过于宽泛的依赖（如整个 `messages` 数组）在流式更新时会频繁失效。

**延伸阅读**

```tsx
  | { type: "text"; text: string }
  | { type: "image_url"; image_url: { url: string } }
  | { type: "file"; file: { name: string; url: string; mimeType: string } }

  const handlePaste = useCallback((e: ClipboardEvent) => {
    const files = Array.from(e.clipboardData?.files ?? []);

    e.preventDefault();
    setAttachments((prev) => [...prev, ...Array.from(e.dataTransfer.files)]);

  async function handleSubmit(text: string) {
    // 先上传文件获取 URL
    const uploadedUrls = await Promise.all(
      attachments.map((f) => uploadToStorage(f)),

    const content: ContentPart[] = [

    onSend(content);
    setAttachments([]);
  }

  return (

      onPaste={handlePaste}
      onDrop={handleDrop}
      onDragOver={(e) => e.preventDefault()}
    >
      <AttachmentPreviewList files={attachments} />
      <TextArea onSubmit={handleSubmit} />
    </div>
  );
}
```

### Q20. 流式渲染中的"白屏闪烁"问题定位与优化方案？

**参考答案**

白屏闪烁（FOUC）通常由以下原因引起，针对性解决：

```
原因 1：Markdown 渲染切换（纯文本 → ReactMarkdown）
解决：用 CSS opacity transition 替代组件挂载/卸载
```

```tsx
// ❌ 切换导致 DOM 重建，产生闪烁
{
  isComplete ? <ReactMarkdown>{content}</ReactMarkdown> : <pre>{content}</pre>;
}

// ✅ 始终渲染 ReactMarkdown，用 CSS 控制显示效果

  className={`transition-opacity duration-300 ${isStreaming ? "opacity-90" : "opacity-100"}`}
>
  {content}
</ReactMarkdown>;
```

```
原因 2：懒加载组件首次渲染闪烁
解决：预加载（preload）关键 chunk
```

```tsx
// 用户开始输入时预加载 Markdown chunk
function ChatInput() {
  const handleFocus = () => {
    import("react-markdown"); // 预触发 chunk 加载
  };
  return <textarea onFocus={handleFocus} />;
}
```

```
原因 3：代码高亮 CSS 异步加载
解决：将 highlight.js CSS 内联到关键 CSS 中，或使用 CSS-in-JS
```

**关键知识点**

- FOUC 根因通常是组件挂载/卸载（重建 DOM）而非数据变化，应优先用 CSS 控制可见性。
- `opacity` 过渡不触发 layout reflow，性能优于 `display: none → block` 切换。

### Q21. Next.js `generateStaticParams` 与流式渲染的兼容策略？

**参考答案**

`generateStaticParams` 用于静态生成路由，与流式动态渲染存在本质冲突，需要合理划分静态与动态边界：

```tsx
// app/chat/[id]/page.tsx
// 策略：静态生成页面外壳，动态流式加载对话内容

// 1. 预生成已知的热门页面 shell
export async function generateStaticParams() {
  // 只生成公开分享的对话页，不生成私人会话
  const sharedChats = await fetchPublicChats();
  return sharedChats.map((c) => ({ id: c.id }));
}

// 2. 页面组件：静态 shell + 动态流式内容
export default function ChatPage({ params }) {
  return (
    <div>
      {/* 静态部分：随页面 HTML 一起发送 */}
      <ChatHeader />
      <Suspense fallback={<MessageSkeleton />}>
        {/* 动态部分：服务端流式加载 */}
        <DynamicMessages chatId={params.id} />
      </Suspense>
    </div>
  );
}

// 3. 未预生成的路由动态渲染
export const dynamicParams = true; // 默认值，允许动态路由回退到 SSR
```

**关键知识点**

- `generateStaticParams` 生成的页面在构建时固化，不适合动态对话内容；应只静态化页面外壳。
- `dynamicParams = true`（默认）确保未预生成的路由能动态渲染，而非返回 404。
- ISR（增量静态再生）可用于对话分享页面，`revalidate` 设置适当的缓存周期。

```typescript
  );

// Service Worker 离线策略（sw.js）
```

### Q23. 大量消息列表的虚拟滚动（react-virtual）实现与 auto-scroll 兼容？

**参考答案**

消息列表超过 200 条时，DOM 节点数量会导致渲染性能下降，虚拟滚动只渲染可见区域：

```tsx
import { useVirtualizer } from "@tanstack/react-virtual";

function VirtualMessageList({ messages, isStreaming }) {
  const parentRef = useRef<HTMLDivElement>(null);
  const [autoScroll, setAutoScroll] = useState(true);

  const virtualizer = useVirtualizer({
    count: messages.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 80, // 消息平均高度估算
    overscan: 5, // 上下各多渲染 5 条，防止滚动白屏
    measureElement: (el) => el.getBoundingClientRect().height, // 动态测量实际高度
  });

  // auto-scroll：流式输出时滚动到最后一项
  useEffect(() => {
    if (autoScroll && isStreaming) {
      virtualizer.scrollToIndex(messages.length - 1, { behavior: "auto" });
    }
  }, [messages.length, isStreaming, autoScroll]);

  // 用户上滚时关闭 auto-scroll
  const handleScroll = useCallback(() => {
    const el = parentRef.current;
    if (!el) return;
    const atBottom = el.scrollHeight - el.scrollTop - el.clientHeight < 100;
    setAutoScroll(atBottom);
  }, []);

  return (
    <div
      ref={parentRef}
      onScroll={handleScroll}
      style={{ overflow: "auto", height: "600px" }}
    >
      <div style={{ height: virtualizer.getTotalSize() }}>
        {virtualizer.getVirtualItems().map((item) => (
          <div
            key={item.key}
            data-index={item.index}
            ref={virtualizer.measureElement}
            style={{ position: "absolute", top: item.start, width: "100%" }}
          >
            <MessageBubble message={messages[item.index]} />
          </div>
        ))}
      </div>
    </div>
  );
}
```

**关键知识点**

- `measureElement` 动态测量真实高度，对于内容高度不固定的消息（含代码块、图片）至关重要。
- 虚拟滚动与 auto-scroll 兼容的关键是使用 `scrollToIndex` 而非直接操作 `scrollTop`。
- 流式输出中最后一条消息高度持续变化，须频繁触发 `measureElement`，可通过 `ResizeObserver` 监听。

**延伸阅读**

- [@tanstack/react-virtual 文档](https://tanstack.com/virtual/latest)
- [虚拟滚动原理与实践](https://web.dev/articles/virtualize-long-lists-react-window)

### Q24. AI Chat 应用的 Core Web Vitals 优化（LCP/FID/CLS 各自的改进点）？

**参考答案**

| 指标        | 全称                      | AI Chat 典型问题                     | 优化方案                                                            |
| ----------- | ------------------------- | ------------------------------------ | ------------------------------------------------------------------- |
| **LCP**     | Largest Contentful Paint  | 消息列表首屏加载慢                   | SSR/流式 SSR 服务端渲染首屏；字体预加载；图片 `priority` prop       |
| **FID/INP** | Interaction to Next Paint | 流式 token 更新阻塞主线程            | `startTransition` 降低更新优先级；Web Worker 处理 Markdown 解析     |
| **CLS**     | Cumulative Layout Shift   | 消息加载后撑开布局；新消息插入时位移 | 预设消息骨架高度；`content-visibility: auto`；图片指定 width/height |

```tsx
// LCP 优化：关键字体预连接
// app/layout.tsx
export default function RootLayout() {
  return (
    <html>
      <head>
        <link rel="preconnect" href="https://fonts.googleapis.com" />
        <link
          rel="preload"
          as="font"
          href="/fonts/inter.woff2"
          crossOrigin="anonymous"
        />
      </head>
      ...
    </html>
  );
}

// CLS 优化：消息加载骨架指定固定高度
function MessageSkeleton() {
  return (
    <div style={{ minHeight: "60px" }} className="animate-pulse">
      {" "}
      {/* 防止 CLS */}
      <div className="h-4 bg-muted rounded w-3/4" />
    </div>
  );
}
```

**关键知识点**

- INP（Interaction to Next Paint）已取代 FID 成为正式 CWV 指标，衡量所有交互的响应延迟。
- 流式输出中 `startTransition` 是改善 INP 最有效的单一优化手段。
- `content-visibility: auto` 对超长消息列表可跳过屏幕外元素的渲染，降低初始渲染时间。

**延伸阅读**

- [Google Core Web Vitals](https://web.dev/articles/vitals)

### Q25. 设计一个支持协作编辑的多人 AI Chat 应用（CRDT + WebSocket + 冲突解决）？

**参考答案**

多人协作 AI Chat 需要解决三个核心问题：并发编辑冲突、AI 响应的广播、实时状态同步。

**架构设计**：

```
客户端 A ──┐
客户端 B ──┼── WebSocket Server ── CRDT State Store ── LLM Service
客户端 C ──┘        │                     │
                   Redis Pub/Sub    PostgreSQL（持久化）
```

```typescript
    yMessages.push([{ id: uuid(), role: "user", content, userId }]);

}

// AI 响应流式写入共享文档
// 服务端 WebSocket Handler
ws.on("message", async ({ type, roomId }) => {
  if (type === "trigger-ai") {
    const doc = getSharedDoc(roomId);
    const msgId = uuid();
    doc.transact(() => {
      doc
        .getArray("messages")
        .push([{ id: msgId, role: "assistant", content: "" }]);

    const stream = await callLLM(getMessages(doc));
    for await (const token of stream) {
      doc.transact(() => {
        const messages = doc.getArray("messages");
        const last = messages.get(messages.length - 1);

  }
});
```

**关键知识点**

- CRDT（无冲突复制数据类型）无需中央仲裁即可合并并发操作，Yjs 是最成熟的前端 CRDT 库。
- AI 响应只应由一个客户端（或服务端）触发，须通过分布式锁（Redis SETNX）防止重复调用。
- 用户光标位置（"谁在看哪条消息"）通过 Yjs Awareness 协议同步，不走 CRDT 主文档。
