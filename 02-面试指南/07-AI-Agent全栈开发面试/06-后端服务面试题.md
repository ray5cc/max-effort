### Q01. SSE（Server-Sent Events）与 WebSocket 各自适合的 AI 应用场景？

**参考答案**

SSE 是基于 HTTP 的单向推送协议，服务端向客户端持续发送事件流，天然适合 LLM 文字流式输出场景：客户端只需消费 token，无需双向通信。WebSocket 则是全双工协议，适合多模态交互、语音实时对话（ASR + TTS 管道）、多人协作聊天室等需要客户端持续上行数据的场景。

```
SSE 优势：
  - 基于 HTTP/2，可复用连接，无需握手升级
  - 浏览器原生 EventSource API 支持自动重连
  - 防火墙/代理穿透性好

WebSocket 优势：
  - 真正双向实时通信
  - 延迟更低（无 HTTP 头开销）
  - 适合音频流、视频帧等高频双向数据
```

**关键知识点**
- SSE 基于 HTTP `text/event-stream` Content-Type，单向服务端推送，适合 LLM 文字输出流。
- WebSocket 全双工，适合实时语音、多人协作等高频双向通信场景。
- AI Chat 应用 90% 以上场景用 SSE 即可满足需求，且运维成本更低。

**延伸阅读**
- [MDN SSE 规范](https://developer.mozilla.org/zh-CN/docs/Web/API/Server-sent_events)
- [WebSocket RFC 6455](https://datatracker.ietf.org/doc/html/rfc6455)
- [OpenAI Streaming 文档](https://platform.openai.com/docs/api-reference/streaming)

### Q02. FastAPI `StreamingResponse` 如何实现流式输出？

**参考答案**

FastAPI 的 `StreamingResponse` 接受一个异步生成器，逐块将数据写入 HTTP 响应体。配合 OpenAI SDK 的 `stream=True`，可以实现 token 级实时推送：

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
from openai import AsyncOpenAI

app = FastAPI()
client = AsyncOpenAI()

async def token_generator(prompt: str):
    stream = await client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}],
        stream=True,
    )
    async for chunk in stream:
        delta = chunk.choices[0].delta.content
        if delta:
            yield f"data: {delta}\n\n"
    yield "data: [DONE]\n\n"

@app.post("/chat")
async def chat(prompt: str):
    return StreamingResponse(
        token_generator(prompt),
        media_type="text/event-stream",
        headers={"X-Accel-Buffering": "no"},   # 禁止 Nginx 缓冲
    )
```

`X-Accel-Buffering: no` 头部防止反向代理缓冲导致流式效果丢失。

**关键知识点**
- `StreamingResponse` 的 `content` 参数必须是异步生成器（`AsyncGenerator`）。
- `media_type="text/event-stream"` 触发浏览器 SSE 协议解析。
- 生产环境须禁用 Nginx/Traefik 的响应缓冲（`X-Accel-Buffering: no`）。

**延伸阅读**
- [FastAPI StreamingResponse 文档](https://fastapi.tiangolo.com/advanced/custom-response/#streamingresponse)
- [OpenAI Python SDK Streaming](https://github.com/openai/openai-python#streaming)

### Q03. LLM API 的典型延迟来源有哪些（TTFT / TBT / E2E）？

**参考答案**

LLM 推理延迟分为三个核心指标：

| 指标 | 全称 | 含义 | 典型值（GPT-4o） |
|------|------|------|-----------------|
| **TTFT** | Time To First Token | 从请求发出到收到第一个 token 的时间 | 300ms～1s |
| **TBT** | Time Between Tokens | 相邻 token 之间的间隔时间 | 20ms～50ms |
| **E2E** | End-to-End Latency | 完整响应时间 = TTFT + TBT × (output_tokens - 1) | 视输出长度 |

TTFT 受 Prefill 阶段（KV Cache 计算）影响；TBT 受 Decode 阶段 GPU 吞吐限制；E2E 与输出 token 数成线性关系。后端优化方向：引入语义缓存降低 TTFT，批量化请求提升 TBT，Speculative Decoding 同时优化两者。

**关键知识点**
- TTFT 是用户感知流畅度的核心指标，应优先优化。
- TBT 决定字符"打字机"效果的流畅程度。
- Speculative Decoding 可将 TBT 降低 2～3 倍。

**延伸阅读**
- [Anyscale: LLM Performance Benchmarks](https://www.anyscale.com/blog/llm-performance-benchmarks)
- [vLLM Speculative Decoding](https://docs.vllm.ai/en/latest/serving/spec_decode.html)

### Q04. 如何在后端实现对话历史的持久化存储？

**参考答案**

对话历史持久化通常采用**会话级关系型存储 + 缓存加速**的双层架构：

```python
# PostgreSQL 表结构示例
CREATE TABLE conversations (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id     UUID NOT NULL,
    created_at  TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE messages (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    conversation_id UUID REFERENCES conversations(id) ON DELETE CASCADE,
    role            TEXT NOT NULL,          -- 'user' | 'assistant' | 'system'
    content         TEXT NOT NULL,
    token_count     INTEGER,
    created_at      TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_messages_conv_id ON messages(conversation_id, created_at);
```

热数据（最近 N 条消息）存入 Redis List，冷数据（历史记录）留在 PostgreSQL。读取时先查 Redis，未命中再回源数据库并重建缓存。

**关键知识点**
- 消息表须记录 `token_count` 以支持上下文窗口管理。
- Redis `LRANGE key 0 19` 获取最近 20 条消息，性能远优于数据库全表扫描。
- 大文本内容可存 S3/OSS，数据库仅存引用 URL。

**延伸阅读**
- [LangChain ConversationBufferWindowMemory](https://python.langchain.com/docs/modules/memory/)
- [PostgreSQL JSONB vs 关系型存储对比](https://www.postgresql.org/docs/current/datatype-json.html)

### Q05. Token 计量的精确实现方式（tiktoken 的原理）？

**参考答案**

`tiktoken` 是 OpenAI 开源的 BPE（Byte-Pair Encoding）分词器，与模型训练时使用的 tokenizer 完全一致，可精确计算 prompt/completion 的 token 数：

```python
import tiktoken

def count_tokens(messages: list[dict], model: str = "gpt-4o") -> int:
    enc = tiktoken.encoding_for_model(model)
    # 每条消息固定开销 4 tokens（角色标记 + 分隔符）
    tokens = sum(
        4 + len(enc.encode(m["content"])) + len(enc.encode(m.get("role", "")))
        for m in messages
    )
    tokens += 2  # 回复前缀固定开销
    return tokens
```

BPE 原理：将高频字节对合并为单一 token，英文单词通常 1～2 token，中文每个汉字约 1～2 token（cl100k_base 编码下）。计费时应在请求前预估 prompt tokens，在响应后从 `usage.total_tokens` 获取精确值。

**关键知识点**
- `tiktoken` 的 `encoding_for_model()` 自动选择模型对应的 BPE 词表（cl100k_base / o200k_base）。
- 中文汉字在 cl100k_base 编码下平均约 1.3 token/字。
- 预估 token 数用于上下文窗口管理，精确计费用响应中的 `usage` 字段。

**延伸阅读**
- [tiktoken GitHub](https://github.com/openai/tiktoken)
- [OpenAI Token 计算指南](https://platform.openai.com/tokenizer)

### Q06. LiteLLM 统一接口的核心价值是什么？

**参考答案**

LiteLLM 提供统一的 OpenAI 兼容接口，抽象了 100+ LLM provider（OpenAI、Anthropic、Google Gemini、Azure、本地 Ollama 等）的调用差异，核心价值体现在三个维度：

```python
import litellm

# 统一调用接口，切换模型只需改 model 参数
response = litellm.completion(
    model="anthropic/claude-3-5-sonnet-20241022",  # 或 "gpt-4o" / "gemini/gemini-1.5-pro"
    messages=[{"role": "user", "content": "你好"}],
    stream=True,
)

# 内置 fallback：主模型失败自动切换备用
litellm.completion(
    model="gpt-4o",
    fallbacks=["claude-3-5-sonnet-20241022", "gemini/gemini-1.5-pro"],
    messages=[...],
)
```

**关键知识点**
- 统一接口消除 vendor lock-in，业务代码无需感知底层 provider 差异。
- 内置 Router 支持负载均衡、fallback、成本追踪等生产级能力。
- 可作为本地代理服务（`litellm --model ollama/llama3`）降低迁移成本。

### Q07. AI 应用后端中为什么需要语义缓存？

**参考答案**

传统精确缓存（exact-match）对 LLM 场景效果极差，因为用户提问措辞千变万化但语义相近。语义缓存通过向量相似度匹配，将语义相近的查询映射到已缓存的响应：

```
用户提问：
  "如何学 Python？"       → 向量化 → 查缓存 → 命中已缓存的
  "Python 学习路径？"     → 向量化 → 相似度 0.95 → 命中！
  "怎么入门 Python 编程？" → 向量化 → 相似度 0.92 → 命中！

实现架构：
  Query → Embedding Model → 向量 → Redis/Qdrant 近邻搜索
       → 命中（相似度 > threshold）→ 直接返回缓存
       → 未命中 → 调用 LLM → 存入缓存
```

可降低 30%～60% 的 LLM API 调用成本，同时将缓存命中的响应延迟压缩至毫秒级（vs 原本秒级）。

**关键知识点**
- 语义缓存依赖 Embedding 模型（如 `text-embedding-3-small`）将文本转为向量。
- 相似度阈值（通常 0.85～0.95）是缓存命中率与准确性的核心权衡参数。
- GPTCache、LangChain SemanticCache 是常用开源实现。

**延伸阅读**
- [GPTCache GitHub](https://github.com/zilliztech/GPTCache)
- [LangChain Semantic Cache](https://python.langchain.com/docs/integrations/llm_caching/)

### Q08. Circuit Breaker（熔断器）在 LLM 调用中的作用？

**参考答案**

LLM API 调用成本高、延迟大，当 provider 出现故障时若不熔断，请求会堆积导致线程/协程耗尽，引发级联雪崩。熔断器通过状态机保护系统：

```
状态机：
  CLOSED（正常）→ 错误率超阈值 → OPEN（熔断）
  OPEN → 等待恢复时间 → HALF-OPEN（探测）
  HALF-OPEN → 探测成功 → CLOSED
           → 探测失败 → OPEN

Python 实现（pybreaker）：
```
```python
import pybreaker

breaker = pybreaker.CircuitBreaker(
    fail_max=5,          # 连续 5 次失败触发熔断
    reset_timeout=60,    # 60 秒后进入 HALF-OPEN 探测
)

@breaker
async def call_llm(prompt: str):
    return await openai_client.chat.completions.create(...)
```

熔断后应立即返回降级响应（如"服务暂时不可用，请稍后重试"），而非让请求长时间等待超时。

**关键知识点**
- 熔断器防止故障扩散，是 LLM 服务高可用的基础组件。
- 需配合 fallback 策略（熔断后切换备用模型）实现无感降级。
- 熔断阈值（失败次数/错误率）须根据业务 SLA 精细调优。

**延伸阅读**
- [Martin Fowler: Circuit Breaker](https://martinfowler.com/bliki/CircuitBreaker.html)
- [pybreaker GitHub](https://github.com/danielfm/pybreaker)

### Q09. LiteLLM Router 三种负载均衡策略（round-robin/least-busy/latency-based）的适用场景？

**参考答案**

```python
from litellm import Router

router = Router(
    model_list=[
        {"model_name": "gpt-4o", "litellm_params": {"model": "gpt-4o", "api_key": "..."}},
        {"model_name": "gpt-4o", "litellm_params": {"model": "azure/gpt-4o", "api_base": "..."}},
        {"model_name": "gpt-4o", "litellm_params": {"model": "gpt-4o-2024-08-06", "api_key": "..."}},
    ],
    routing_strategy="latency-based-routing",  # 或 "simple-shuffle" / "least-busy"
    num_retries=3,
    fallbacks=[{"gpt-4o": ["claude-3-5-sonnet-20241022"]}],
)
```

| 策略 | 算法 | 适用场景 |
|------|------|----------|
| `simple-shuffle`（round-robin） | 均匀轮询 | 各 endpoint 性能一致，成本均摊 |
| `least-busy` | 选当前并发最低的节点 | 突发流量，防止单节点过载 |
| `latency-based-routing` | EMA 加权，优先选历史延迟低的节点 | 对 TTFT 敏感的实时对话场景 |

**关键知识点**
- `latency-based-routing` 维护每个 endpoint 的指数移动平均（EMA）延迟，自动适应网络波动。
- 多策略可组合：先 `least-busy` 过滤过载节点，再 `latency-based` 选最快节点。
- 跨 AZ 部署时应优先选同区域节点以降低网络延迟。

**延伸阅读**
- [LiteLLM Router 文档](https://docs.litellm.ai/docs/routing)
- [The Power of Two Choices 负载均衡论文](https://www.eecs.harvard.edu/~michaelm/postscripts/handbook2001.pdf)

### Q10. SSE `text/event-stream` 协议格式规范（data/event/id/retry 字段）？

**参考答案**

SSE 协议基于纯文本，每个事件由空行分隔，支持四种字段：

```
# 基础格式
data: 这是消息内容\n\n

# 多行 data（拼接换行）
data: 第一行\n
data: 第二行\n\n

# 带 event 类型（客户端通过 addEventListener 监听）
event: token\n
data: {"content": "你好"}\n\n

# 带 id（断线重连时通过 Last-Event-ID 头恢复位置）
id: 42\n
data: 消息内容\n\n

# retry（指定重连间隔，单位毫秒）
retry: 3000\n\n
```

OpenAI 流式响应格式：每个 SSE 事件的 `data` 字段为 JSON，最后发送 `data: [DONE]` 标记结束。

```python
# FastAPI 生成符合规范的 SSE
async def sse_generator():
    yield "retry: 1000\n\n"  # 告知客户端 1 秒后重连
    for i, token in enumerate(tokens):
        yield f"id: {i}\nevent: token\ndata: {json.dumps({'content': token})}\n\n"
    yield "event: done\ndata: [DONE]\n\n"
```

**关键知识点**
- 事件以 `\n\n`（双换行）结束，单个 `\n` 是字段内换行。
- `id` 字段支持断线续传，客户端重连时携带 `Last-Event-ID` 请求头。
- `event` 字段默认值为 `"message"`，自定义类型须用 `addEventListener` 监听。

**延伸阅读**
- [W3C SSE 规范](https://html.spec.whatwg.org/multipage/server-sent-events.html)
- [MDN Server-sent events](https://developer.mozilla.org/zh-CN/docs/Web/API/Server-sent_events/Using_server-sent_events)

### Q11. 上下文窗口三种管理策略（滑动窗口/摘要/重要性评分）的实现与权衡？

**参考答案**

当对话历史超出模型上下文窗口（如 128k tokens）时，需要裁剪策略：

```python
# 策略 1：滑动窗口 —— 保留最近 N 条消息
def sliding_window(messages: list, max_tokens: int = 4000) -> list:
    result, total = [], 0
    for msg in reversed(messages):
        tokens = count_tokens([msg])
        if total + tokens > max_tokens:
            break
        result.insert(0, msg)
        total += tokens
    return result

# 策略 2：摘要压缩 —— 用 LLM 将旧消息摘要为一条 system 消息
async def summarize_old_messages(old_messages: list) -> str:
    summary = await llm.chat("请将以下对话历史压缩为100字摘要：\n" + format(old_messages))
    return summary

# 策略 3：重要性评分 —— 保留高相关性消息
def importance_scoring(messages: list, current_query: str) -> list:
    scores = [cosine_similarity(embed(m["content"]), embed(current_query)) for m in messages]
    return [m for m, s in sorted(zip(messages, scores), key=lambda x: -x[1])][:10]
```

| 策略 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| 滑动窗口 | 实现简单，延迟低 | 丢失早期重要信息 | 短会话、客服场景 |
| 摘要压缩 | 保留语义精华 | 需额外 LLM 调用 | 长会话、知识密集型 |
| 重要性评分 | 保留最相关消息 | Embedding 计算开销 | RAG 增强型 Agent |

**关键知识点**
- 三种策略可以组合：先滑动窗口粗剪，再重要性评分精选。
- 摘要策略须保留 `system` 消息不压缩。
- 建议在 token 达到窗口 80% 时触发裁剪，保留 20% 余量给响应。

**延伸阅读**
- [LangChain Memory 类型对比](https://python.langchain.com/docs/modules/memory/types/)
- [MemGPT: Towards LLMs as Operating Systems](https://arxiv.org/abs/2310.08560)

### Q12. Langfuse Trace/Span/Generation 三层结构的设计意图？

**参考答案**

Langfuse 借鉴 OpenTelemetry 的分布式追踪模型，将 LLM 应用的观测数据组织为三层树状结构：

```
Trace（一次完整用户请求）
```

### Q13. 如何用 Redis 实现高并发会话存储（键设计/TTL/pipeline 批量操作）？

**参考答案**

```python
import redis.asyncio as redis
import json

class SessionStore:
    def __init__(self):
        self.client = redis.Redis(host="localhost", decode_responses=True)
        self.TTL = 86400  # 24 小时会话超时

    def _key(self, session_id: str) -> str:
        return f"session:{session_id}:messages"  # 键命名空间隔离

    async def append_message(self, session_id: str, message: dict):
        key = self._key(session_id)
        async with self.client.pipeline(transaction=False) as pipe:
            pipe.rpush(key, json.dumps(message, ensure_ascii=False))
            pipe.expire(key, self.TTL)  # 每次写入刷新 TTL
            await pipe.execute()

    async def get_messages(self, session_id: str, limit: int = 20) -> list:
        key = self._key(session_id)
        raw = await self.client.lrange(key, -limit, -1)  # 取最近 limit 条
        return [json.loads(m) for m in raw]

    async def delete_session(self, session_id: str):
        await self.client.delete(self._key(session_id))
```

Redis List 结构天然支持消息追加和按时间序读取，`LRANGE key -20 -1` 高效获取最近 20 条消息，时间复杂度 O(N)（N 为返回数量）。

**关键知识点**
- 键前缀（`session:{id}:messages`）使用命名空间，便于 Redis Cluster 分片和批量清理。
- `pipeline(transaction=False)` 减少网络往返，批量执行多条命令。
- 配合 Redis Cluster 可横向扩展，单分片支持 10 万+ 并发会话。

### Q16. LLM API 限流的两层设计（客户端令牌桶 + 服务端背压）？

**参考答案**

LLM API 通常有 RPM（Requests Per Minute）和 TPM（Tokens Per Minute）双维度限流，需在客户端和服务端双层防护：

```python
# 第一层：客户端令牌桶（防止超出 provider 限额）
import asyncio
from asyncio import Semaphore

class TokenBucketLimiter:
    def __init__(self, rpm: int = 60, tpm: int = 100000):
        self.request_semaphore = Semaphore(rpm // 4)  # 控制并发请求数
        self.token_budget = tpm
        self._refill_task = asyncio.create_task(self._refill())

    async def _refill(self):
        while True:
            await asyncio.sleep(60)
            self.token_budget = 100000  # 每分钟重置

    async def acquire(self, estimated_tokens: int):
        async with self.request_semaphore:
            while self.token_budget < estimated_tokens:
                await asyncio.sleep(0.1)
            self.token_budget -= estimated_tokens

# 第二层：服务端背压（通知客户端减速）
@app.middleware("http")
async def backpressure_middleware(request: Request, call_next):
    if queue_depth() > QUEUE_HIGH_WATERMARK:
        return JSONResponse(
            status_code=503,
            content={"error": "Server overloaded", "retry_after": 5},
            headers={"Retry-After": "5"},
        )
    return await call_next(request)
```

**关键知识点**
- 客户端令牌桶防止触发 provider 的 429 Too Many Requests，减少重试开销。
- 服务端背压通过 HTTP 503 + `Retry-After` 头通知上游限速，形成反馈环路。
- RPM 和 TPM 须分别独立限流，因为单个长请求可能快速耗尽 TPM 配额。

### Q18. `tenacity` 重试库在 LLM 调用中的指数退避配置最佳实践？

**参考答案**

LLM API 调用失败主要来自三类错误：网络抖动（可重试）、限流 429（须等待）、模型错误 500（可重试）。`tenacity` 提供细粒度的重试策略：

```python
from tenacity import (
    retry, stop_after_attempt, wait_exponential,
    retry_if_exception_type, before_sleep_log,
)
import openai, logging

logger = logging.getLogger(__name__)

@retry(
    stop=stop_after_attempt(5),             # 最多重试 5 次
    wait=wait_exponential(
        multiplier=1, min=1, max=60         # 1s → 2s → 4s → 8s → 16s（上限 60s）
    ),
    retry=retry_if_exception_type((        # 仅对以下异常重试
        openai.RateLimitError,
        openai.APIConnectionError,
        openai.InternalServerError,
    )),
    before_sleep=before_sleep_log(logger, logging.WARNING),  # 重试前记录日志
    reraise=True,                           # 耗尽重试后重新抛出原始异常
)
async def call_llm_with_retry(messages: list) -> str:
    response = await client.chat.completions.create(
        model="gpt-4o", messages=messages
    )
    return response.choices[0].message.content
```

对于 429 限流错误，应优先读取响应头 `Retry-After` 中的等待时间，而非固定退避。

**关键知识点**
- 指数退避 + Jitter（随机抖动）防止多客户端同时重试造成二次雪崩。
- `openai.BadRequestError`（400）不应重试，属于客户端错误（如 prompt 违规）。
- 生产环境建议最多重试 3 次，超过后触发 fallback（切换模型）而非无限重试。

### Q19. 如何设计 AI 应用的多租户成本隔离架构（per-user token budget）？

**参考答案**

多租户成本隔离需要在租户级别追踪和管控 token 消耗，核心设计包含三层：

```python
# 第一层：Token Budget 管理（Redis 原子计数）
class TokenBudgetManager:
    async def check_and_consume(self, user_id: str, estimated_tokens: int) -> bool:
        key = f"budget:{user_id}:{today()}"
        async with self.redis.pipeline(transaction=True) as pipe:
            try:
                pipe.watch(key)
                current = int(await pipe.get(key) or 0)
                if current + estimated_tokens > self.DAILY_LIMIT:
                    return False  # 超出预算，拒绝请求
                pipe.multi()
                pipe.incrby(key, estimated_tokens)
                pipe.expire(key, 86400)
                await pipe.execute()
                return True
            except redis.WatchError:
                return await self.check_and_consume(user_id, estimated_tokens)  # 乐观锁重试

# 第二层：成本分摊（按 SKU 计费）
COST_PER_TOKEN = {"gpt-4o": 0.000005, "gpt-4o-mini": 0.0000002}

async def record_usage(user_id: str, model: str, tokens: int):
    cost = COST_PER_TOKEN[model] * tokens
    await db.execute(
        "INSERT INTO usage_records(user_id, model, tokens, cost) VALUES($1,$2,$3,$4)",
        user_id, model, tokens, cost,
    )

# 第三层：配额分级（订阅套餐）
TIER_LIMITS = {"free": 10000, "pro": 500000, "enterprise": float("inf")}
```

**关键知识点**
- Redis 原子操作（WATCH/MULTI/EXEC）保证并发环境下 budget 计数准确。
- 预算检查应在请求前（预估）和请求后（精确）各做一次，避免超支。
- 企业客户可配置独立的 API Key 池，实现物理隔离而非逻辑隔离。

```python
        stream = await client.chat.completions.create(stream=True, ...)
        async for chunk in stream:
            if first_token:
                ttft = time.perf_counter() - start
                span.set_attribute("llm.ttft_ms", ttft * 1000)
                first_token = False
        span.set_attribute("llm.e2e_ms", (time.perf_counter() - start) * 1000)
```
```
3. 告警（错误预算燃尽率）：
   - 1 小时内错误预算消耗 > 5% → 告警
   - 6 小时内错误预算消耗 > 10% → PagerDuty

4. 优化优先级：
   TTFT 高 → 检查模型负载、网络延迟、Prefill 阶段瓶颈
   TBT 高  → 检查 GPU 利用率、批大小配置
   可用性低 → 检查熔断器、fallback 策略
```

**关键知识点**
- SLO 须基于"用户幸福感"而非技术指标：用户更在乎 TTFT 而非总延迟。
- 错误预算（Error Budget）= 1 - SLO 目标，是工程速度与稳定性的平衡杠杆。
- 每次 SLO 违约须做 RCA（根因分析），驱动架构改进而非被动修复。

### Q24. AI 应用 Observability 三支柱（Metrics/Traces/Logs）的统一接入方案？

**参考答案**

OpenTelemetry（OTel）是 AI 应用可观测性的统一标准，三支柱通过同一 SDK 上报：

```python
# otel_setup.py —— 统一初始化
from opentelemetry import trace, metrics
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.metrics import MeterProvider
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter
from opentelemetry.exporter.otlp.proto.grpc.metric_exporter import OTLPMetricExporter

# Traces → Jaeger / Grafana Tempo
trace.set_tracer_provider(TracerProvider())
trace.get_tracer_provider().add_span_processor(
    BatchSpanProcessor(OTLPSpanExporter(endpoint="http://otel-collector:4317"))
)

# Metrics → Prometheus / Grafana Mimir
metrics.set_meter_provider(MeterProvider())
meter = metrics.get_meter(__name__)
llm_request_counter = meter.create_counter("llm.requests.total")
llm_token_histogram = meter.create_histogram("llm.tokens.used")

# Logs → Loki / Elasticsearch（结构化日志 + Trace ID 关联）
import structlog
log = structlog.get_logger().bind(
    trace_id=trace.get_current_span().get_span_context().trace_id
)
```

**统一观测栈选型**：

| 场景 | 开源方案 | SaaS 方案 |
|------|---------|-----------|
| Metrics | Prometheus + Grafana | Datadog |
| Traces | Jaeger / Grafana Tempo | Langfuse / Arize |
| Logs | Loki + Grafana | Datadog Logs |
| LLM 专项 | Langfuse | Helicone |

**关键知识点**
- OTel Collector 作为统一入口，解耦业务代码与后端观测系统。
- 日志中注入 `trace_id` 实现 Logs ↔ Traces 关联，便于问题追溯。
- LLM 专项可观测性（prompt/completion/cost 追踪）须使用 Langfuse 等 LLM-aware 工具。

### Q25. 设计一个支持 10 万 DAU 的 AI 对话服务架构（组件选型与容量规划）？

**参考答案**

**流量估算**：
- DAU 10 万，平均每人 5 次对话/天 = 50 万次请求/天
- 峰值系数 3x，QPS_peak ≈ 50万 × 3 / 86400 ≈ **17 QPS**（并发约 200 长连接）

**架构分层**：

```
客户端
  └── CDN（静态资源 / Next.js 静态页面）
       └── API Gateway（Kong / Nginx）
            ├── 认证服务（JWT 验证，Redis 会话）
            ├── 限流层（令牌桶，per-user RPM/TPM）
            └── AI API 服务（FastAPI，4 Pod × 4 CPU）
                 ├── LiteLLM Router（负载均衡 + fallback）
                 │    ├── OpenAI GPT-4o（主力模型）
                 │    └── Azure OpenAI（备用 + 容量补充）
                 ├── 语义缓存（Redis + Qdrant，预期命中率 30%）
                 ├── 会话存储（Redis Cluster，3 主 3 从）
                 └── 消息持久化（PostgreSQL，主从复制）
                      └── 异步任务（Celery + Redis Queue）
                           └── 可观测性（OpenTelemetry → Grafana LGTM）
```

**容量规划**：

| 组件 | 规格 | 成本估算/月 |
|------|------|------------|
| FastAPI Pod | 4 × (4C8G) | ~$400 |
| Redis Cluster | 3主3从 (4GB/节点) | ~$200 |
| PostgreSQL | 主从 (8C16G) | ~$300 |
| LLM API（OpenAI） | 50万次 × 1000 token = 5亿 token | ~$2500 |

**关键知识点**
- 语义缓存命中率每提升 10%，LLM API 成本降低约 $250/月，是最高 ROI 的优化点。
- PostgreSQL 读写分离 + 读库只读副本，可承载 10 倍以上读请求。
- 预留 3～5 倍容量余量，应对节假日、病毒式传播等突发流量。
