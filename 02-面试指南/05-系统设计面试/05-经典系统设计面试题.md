## 🔥 高频考点速记

> 面试前 10 分钟快速过一遍，覆盖六大案例的核心考点。

### 通用方法论

| 步骤 | 关键动作 | 常见陷阱 |
|------|---------|---------|
| 需求澄清 | 功能/非功能/约束 | 直接画架构图，没确认需求 |
| 容量估算 | DAU → QPS → 存储 → 带宽 | 数量级算错、忽略读写比 |
| 高层设计 | 核心组件 + 数据流 | 组件太多太复杂 |
| 深入设计 | 数据库/缓存/一致性/容灾 | 只谈方案不谈 trade-off |

**容量估算速算公式**：
- QPS = DAU × 每用户日均操作数 / 86400
- 峰值 QPS ≈ 平均 QPS × 2~5
- 存储 = 每条记录大小 × 日新增量 × 保留天数
- 带宽 = QPS × 平均响应大小

### 短链系统（TinyURL）

| 考点 | 要点 |
|------|------|
| ID 生成 | Base62 编码（自增ID / 雪花算法），Hash 截断（MD5/SHA256 取前 7 位） |
| 重定向 | 301 永久（浏览器缓存，减轻服务器压力） vs 302 临时（可统计点击量） |
| 去重 | 布隆过滤器预判 + 数据库唯一索引兜底 |
| 缓存 | 热点短链用 Redis 缓存，LRU 淘汰策略 |
| 读写比 | 典型 100:1，重度读优化 |

### Feed流系统

| 考点 | 要点 |
|------|------|
| 推模式（Fan-out on Write） | 发布时写入所有粉丝收件箱，读取快，写入慢 |
| 拉模式（Fan-out on Read） | 读取时实时聚合关注者动态，写入快，读取慢 |
| 混合模式 | 普通用户推模式 + 大V拉模式，业界最佳实践 |
| 大V问题 | 粉丝数 > 阈值（如 10 万）走拉模式，避免写放大 |
| 排序 | 时间线排序 vs 算法推荐排序（EdgeRank / 机器学习） |
| 存储 | Redis Sorted Set（时间线）+ MySQL/Cassandra（持久化） |

### 即时通讯（IM Chat）

| 考点 | 要点 |
|------|------|
| 长连接 | WebSocket 全双工 vs HTTP 轮询/长轮询 |
| 可靠投递 | 三次握手：发送 → 服务端 ACK → 接收端 ACK |
| 消息去重 | 客户端生成 `client_msg_id`，服务端幂等校验 |
| 消息存储 | 写扩散（每人一份，适合小群）vs 读扩散（一份存储+索引，适合大群） |
| 群聊 | 小群（< 200）写扩散，大群（> 200）读扩散 + 推送通知 |
| 端到端加密 | Signal Protocol / Double Ratchet，服务端不可解密 |
| 多设备同步 | 设备级 sequence + 增量同步 |

### 搜索引擎

| 考点 | 要点 |
|------|------|
| 倒排索引 | 词项 → 文档列表（含位置），核心数据结构 |
| 分词 | 中文：jieba / HanLP；英文：空格 + 词干提取 |
| 相关性 | BM25 = TF-IDF 改进版，k1/b 参数调节词频饱和度和文档长度归一化 |
| 搜索补全 | Trie 前缀树 + 热度排序，支持模糊匹配 |
| 向量搜索 | Embedding + ANN（HNSW/IVF），语义理解 |
| 混合搜索 | BM25 关键词 + 向量语义，RRF 融合排序 |

### 秒杀系统

| 考点 | 要点 |
|------|------|
| 流量削峰 | 答题验证码 + 随机排队 + 令牌桶限流 |
| 库存预扣减 | Redis + Lua 原子操作，DECR 判断 ≥ 0 |
| 防超卖 | Redis 预扣减 + 数据库乐观锁（`stock > 0`）双重保障 |
| 异步下单 | 预扣减成功 → 消息队列 → 异步创建订单 |
| 热点数据 | 库存 Key 分片（stock:item:1~10），分散单点压力 |
| 防刷 | 用户维度限流 + 设备指纹 + IP 黑名单 |

### 分布式文件存储（GFS/HDFS）

| 考点 | 要点 |
|------|------|
| 架构 | Master（元数据）+ ChunkServer（数据块），单 Master 设计 |
| Chunk 大小 | GFS 64MB（减少元数据量），HDFS 128MB |
| 副本策略 | 3 副本，跨机架放置，Pipeline 复制 |
| 一致性 | 租约（Lease）机制，Primary 副本串行化写入 |
| 故障恢复 | 心跳检测 + 自动重新复制 + Checksum 校验 |
| 小文件问题 | 合并小文件（HAR/SequenceFile）、元数据内存压力 |

## ⭐ 基础题（Q1-Q8）

### Q1: 系统设计面试的四步法是什么？每一步需要做什么？

<details>
<summary>参考答案</summary>

系统设计面试通常遵循一个结构化的四步方法论，这不仅是解题框架，也是面试官评估候选人思维方式的关键维度。

#### 第一步：需求澄清（Requirement Clarification）—— 5 分钟

这一步的核心目标是**缩小问题范围**，避免在错误的方向上浪费时间。

需要确认三类需求：

| 需求类型 | 示例问题 |
|---------|---------|
| 功能需求 | "用户能做什么？核心功能有哪些？" |
| 非功能需求 | "预期用户量多少？延迟要求？可用性要求？" |
| 约束条件 | "数据量多大？有没有技术栈限制？" |

**关键技巧**：主动提问而不是假设。例如设计短链系统时，要问"短链是否需要支持自定义？""是否需要统计点击量？""链接是否会过期？"

#### 第二步：容量估算（Estimation）—— 5 分钟

通过 **Back-of-the-Envelope Calculation**，估算系统的规模，为后续架构决策提供数据支撑。

核心估算项：
1. **QPS**（每秒查询数）：DAU × 平均操作次数 / 86400
2. **峰值 QPS**：平均 QPS × 峰值系数（通常 2~5 倍）
3. **存储量**：单条数据大小 × 日增量 × 保留时间
4. **带宽**：QPS × 平均响应大小
5. **内存/缓存**：热点数据比例（通常 20%）× 总数据量

#### 第三步：高层设计（High-Level Design）—— 10 分钟

画出系统的核心架构图，包括：
- 客户端 → 负载均衡 → 应用服务 → 数据库/缓存
- 核心数据流向（读流程、写流程）
- 关键组件的职责划分

**注意**：这一步只需要画出 3~5 个核心组件，不要过度设计。先画最简单能工作的版本，后续再优化。

#### 第四步：深入设计（Deep Dive）—— 15~20 分钟

针对面试官感兴趣的点进行深入讨论：

- **数据库设计**：Schema、索引、分库分表策略
- **缓存策略**：Cache-Aside / Write-Through / Write-Behind
- **一致性保证**：强一致 vs 最终一致，如何处理冲突
- **扩展性**：水平扩展方案、瓶颈分析
- **容灾**：故障检测、自动恢复、数据备份

**关键点**：每个设计决策都要说明 trade-off，展示你的工程思维而非背诵答案。

</details>

### Q2: 如何进行容量估算？请为一个日活 1000 万的短链系统估算 QPS 和存储量

<details>
<summary>参考答案</summary>

容量估算是系统设计面试的必考环节。面试官关注的不是精确数字，而是你的**估算思路和数量级判断能力**。

#### 核心估算方法

容量估算的本质是一个**自顶向下的分解过程**：从业务指标（DAU）出发，逐步推导出技术指标（QPS、存储、带宽）。

#### 短链系统实际估算

**已知条件**：
- DAU = 1000 万
- 每个用户平均每天创建 0.1 个短链（大部分用户只是点击）
- 每个用户平均每天点击 1 个短链
- 读写比约 10:1
- 数据保留 5 年

**第一步：QPS 估算**

```
写入 QPS：
  日新增短链 = 1000万 × 0.1 = 100万/天
  平均写 QPS = 100万 / 86400 ≈ 12 QPS
  峰值写 QPS = 12 × 3 ≈ 36 QPS

读取 QPS：
  日读取量 = 1000万 × 1 = 1000万/天
  平均读 QPS = 1000万 / 86400 ≈ 116 QPS
  峰值读 QPS = 116 × 3 ≈ 350 QPS
```

**第二步：存储估算**

```
每条短链记录大小：
  - short_url:   7 字节（Base62 编码）
  - long_url:  200 字节（平均）
  - created_at:  8 字节
  - user_id:     8 字节
  - 其他元数据: 50 字节
  合计 ≈ 273 字节，取整 300 字节

5 年总存储：
  100万/天 × 365天 × 5年 × 300字节
  = 18.25亿 × 300字节
  ≈ 5475亿字节
  ≈ 548 GB
```

**第三步：缓存估算**

```
采用 80/20 法则（20% 的短链占 80% 的流量）：
  日总读取量 = 1000万
  需缓存的短链数 = 1000万 × 20% = 200万条
  缓存大小 = 200万 × 300字节 ≈ 600 MB
```

**第四步：带宽估算**

```
读取带宽：
  350 QPS × 300 字节 ≈ 105 KB/s（可忽略）

实际瓶颈不在带宽，在于数据库随机读的 IOPS
```

#### 估算结果汇总

| 指标 | 数值 |
|------|------|
| 峰值写 QPS | ~36 |
| 峰值读 QPS | ~350 |
| 5 年总存储 | ~548 GB |
| 缓存大小 | ~600 MB |
| 总记录数（5 年） | ~18 亿条 |

**结论**：这个规模的短链系统，单机 MySQL + Redis 缓存即可应对。当数据量增长到百亿级别时，才需要考虑分库分表。

</details>

### Q3: 设计短链系统时，Base62 编码和 Hash 截断各有什么优缺点？

<details>
<summary>参考答案</summary>

短链生成是 TinyURL 系统设计的核心问题，业界主要有两种方案：**Base62 编码**和 **Hash 截断**。

#### 方案一：Base62 编码

**原理**：将一个唯一的数字 ID（自增ID或雪花算法生成）转换为 Base62 字符串。

Base62 使用 `[0-9a-zA-Z]` 共 62 个字符，7 位可表示 62^7 ≈ 3.5 万亿个短链。

```python
CHARS = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"

def encode_base62(num: int) -> str:
    if num == 0:
        return CHARS[0]
    result = []
    while num > 0:
        result.append(CHARS[num % 62])
        num //= 62
    return ''.join(reversed(result))

def decode_base62(s: str) -> int:
    num = 0
    for ch in s:
        num = num * 62 + CHARS.index(ch)
    return num

# 示例
print(encode_base62(123456789))  # "8M0kX"
```

**优点**：
- 生成的短链长度可控且最短
- 天然唯一，不需要去重
- 支持递增 ID，便于数据库索引

**缺点**：
- 短链可被预测（竞对可以遍历），有安全风险
- 依赖全局唯一 ID 生成器（单点问题）
- 分布式环境下需要号段分配或分布式 ID 生成器

#### 方案二：Hash 截断

**原理**：对长 URL 做 Hash（MD5/SHA256），取前 7 个字符作为短链。

```python
import hashlib

def generate_short_url(long_url: str) -> str:
    hash_hex = hashlib.md5(long_url.encode()).hexdigest()
    # 取前 43 bit（约 7 个 Base62 字符的信息量）
    hash_int = int(hash_hex[:11], 16)
    return encode_base62(hash_int)[:7]
```

**优点**：
- 相同长 URL 生成相同短链（天然去重）
- 无需全局 ID 生成器，去中心化
- 短链不可预测，安全性更好

**缺点**：
- 存在 Hash 冲突，需要冲突解决机制
- 冲突解决增加了写入延迟
- 无法支持同一长 URL 对应不同短链的需求

#### 对比总结

| 维度 | Base62 编码 | Hash 截断 |
|------|-----------|----------|
| 唯一性 | 天然唯一 | 可能冲突，需处理 |
| 可预测性 | 可预测（有安全风险） | 不可预测 |
| 去重 | 不去重（同一 URL 可生成多个短链） | 天然去重 |
| 依赖 | 全局 ID 生成器 | 无 |
| 性能 | O(1) 生成 | O(1) 生成 + 冲突时重试 |
| 业界使用 | Twitter、Instagram | bit.ly 早期 |

**面试建议**：推荐使用 Base62 编码 + 雪花算法，安全性问题可以通过加盐或混淆 ID 顺序解决。

</details>

### Q4: 301 和 302 重定向的区别是什么？短链系统应该用哪个？

<details>
<summary>参考答案</summary>

HTTP 重定向是短链系统的核心机制，`301` 和 `302` 的选择直接影响系统的行为和数据分析能力。

#### 301 永久重定向（Moved Permanently）

浏览器会**缓存**这个重定向映射。下次用户访问同一短链时，浏览器**直接跳转到长链接**，不会再请求短链服务器。

```
第一次访问：
  Browser → 短链服务器 → 返回 301 + Location: https://long-url.com
  Browser → 缓存映射：short.url/abc → long-url.com

第二次访问：
  Browser → 直接跳转到 long-url.com（不经过服务器）
```

#### 302 临时重定向（Found）

浏览器**不缓存**这个重定向映射。每次访问短链都会请求短链服务器。

```
每次访问：
  Browser → 短链服务器 → 返回 302 + Location: https://long-url.com
  （每次都经过服务器）
```

#### 核心区别

| 维度 | 301 永久重定向 | 302 临时重定向 |
|------|-------------|-------------|
| 浏览器行为 | 缓存映射，后续不请求服务器 | 每次都请求服务器 |
| 服务器压力 | 低（大量请求被浏览器拦截） | 高（每次都到达服务器） |
| 数据统计 | 无法统计后续点击量 | 可精确统计每次点击 |
| 链接更新 | 更新后旧缓存失效困难 | 随时可更新目标链接 |
| SEO 影响 | 权重转移到目标 URL | 权重保留在短链 |

#### 短链系统的选择

**大多数商业短链系统选择 302**，原因如下：

1. **数据分析是核心需求**：短链的商业价值在于追踪点击量、地域分布、设备类型等数据。使用 301 会导致大量点击无法被服务端捕获。

2. **链接可变性**：302 允许随时更新短链指向的目标 URL，灵活性更强。

3. **A/B 测试**：同一短链可根据用户画像重定向到不同页面，302 是必要条件。

**如果不需要数据统计，且追求极致性能**（如内部系统），可以选择 301 来降低服务器压力。

```python
# Flask 示例：302 重定向
from flask import Flask, redirect

app = Flask(__name__)

@app.route('/<short_code>')
def redirect_url(short_code):
    long_url = lookup_from_db_or_cache(short_code)
    if long_url:
        # 记录点击统计（异步写入）
        track_click_async(short_code, request)
        return redirect(long_url, code=302)
    return "Not Found", 404
```

</details>

### Q5: Feed 流系统中，"推模式"和"拉模式"分别是什么？各自的优缺点？

<details>
<summary>参考答案</summary>

Feed 流（信息流）是社交平台的核心功能。当用户发布内容后，如何将这条内容展示给所有关注者，有两种经典模式。

#### 推模式（Fan-out on Write / Push Model）

**核心思想**：用户发布内容时，**立即将内容推送到所有粉丝的收件箱**（时间线）。

```
用户 A 发布一条动态（A 有 3 个粉丝：B、C、D）

写入流程：
  A 发布 → 写入 A 的发件箱
           → 写入 B 的收件箱
           → 写入 C 的收件箱
           → 写入 D 的收件箱

读取流程：
  B 打开首页 → 直接读取 B 的收件箱 → 按时间排序展示
```

```diagram
┌─────────┐    发布     ┌──────────────┐   Fan-out    ┌──────────────┐
│  用户 A  │──────────→│  Feed 服务    │────────────→│ 粉丝 B 收件箱 │
└─────────┘            └──────────────┘     │        └──────────────┘
                                             │        ┌──────────────┐
                                             ├──────→│ 粉丝 C 收件箱 │
                                             │        └──────────────┘
                                             │        ┌──────────────┐
                                             └──────→│ 粉丝 D 收件箱 │
                                                      └──────────────┘
```

**优点**：
- 读取极快——只需查询自己的收件箱，O(1) 复杂度
- 适合读多写少的场景
- 时间线已预先排好序

**缺点**：
- 写放大严重——一个拥有百万粉丝的用户发布一条内容，需要写入百万次
- 不活跃用户的收件箱也被写入，浪费资源
- 发布延迟高（需要完成所有 Fan-out 才算发布成功，或者异步处理）

#### 拉模式（Fan-out on Read / Pull Model）

**核心思想**：用户只在自己的发件箱写一份。粉丝打开首页时，**实时去所有关注者的发件箱拉取内容**，合并排序后展示。

```
写入流程：
  A 发布 → 只写入 A 的发件箱（一次写入）

读取流程：
  B 打开首页 → 查询 B 关注的所有人（A、E、F...）的发件箱
             → 合并排序
             → 展示时间线
```

**优点**：
- 写入极快——只需写一份
- 不浪费存储（不活跃用户不产生无意义数据）
- 大 V 发布无压力

**缺点**：
- 读取慢——需要实时聚合多个发件箱的数据
- 读取复杂度高——O(N)，N 为关注人数
- 如果用户关注了 500 个人，每次打开首页都要查 500 个发件箱

#### 对比总结

| 维度 | 推模式 | 拉模式 |
|------|-------|-------|
| 写入开销 | 高（Fan-out 到所有粉丝） | 低（只写一份） |
| 读取开销 | 低（直接读收件箱） | 高（实时聚合） |
| 适合场景 | 粉丝数少、读多写少 | 粉丝数多、写多读少 |
| 实时性 | 高（预先写好） | 取决于聚合速度 |
| 存储开销 | 高（冗余存储） | 低（无冗余） |
| 典型案例 | 朋友圈（好友数有限） | 微博热门（大V 粉丝多） |

**业界最佳实践是混合模式**：普通用户走推模式，大 V（粉丝数超过阈值）走拉模式。Twitter、微博、Instagram 都采用这种方案。

</details>

### Q6: 即时通讯系统为什么选择 WebSocket 而不是 HTTP 轮询？

<details>
<summary>参考答案</summary>

即时通讯（IM）系统的核心需求是**低延迟的双向实时通信**。选择通信协议直接决定了系统的实时性和资源效率。

#### 三种方案对比

**方案一：HTTP 短轮询（Short Polling）**

客户端每隔固定时间（如 3 秒）向服务器发送请求，询问"有没有新消息"。

```
客户端 → 服务器: 有新消息吗？ → 没有
（3秒后）
客户端 → 服务器: 有新消息吗？ → 没有
（3秒后）
客户端 → 服务器: 有新消息吗？ → 有！返回消息
```

**问题**：大量无效请求浪费带宽和服务器资源，延迟最高可达轮询间隔时间。

**方案二：HTTP 长轮询（Long Polling）**

客户端发送请求后，服务器**hold 住连接**直到有新消息或超时。

```
客户端 → 服务器: 有新消息吗？
（服务器 hold 住连接，等待...）
（30秒后有新消息）
服务器 → 客户端: 有！返回消息
客户端 → 服务器: 有新消息吗？（重新建立连接）
```

**改进了延迟**，但仍有问题：频繁建立/断开 TCP 连接开销大、服务端维护大量挂起连接。

**方案三：WebSocket（业界标准方案）**

通过 HTTP 协议握手后**升级为全双工连接**，客户端和服务器可以随时互相发送消息。

```
客户端 → 服务器: HTTP Upgrade 请求
服务器 → 客户端: 101 Switching Protocols

（连接建立后，双向通信）
客户端 ←→ 服务器: 实时消息推送
```

#### WebSocket 的核心优势

| 维度 | HTTP 轮询 | HTTP 长轮询 | WebSocket |
|------|----------|-----------|-----------|
| 延迟 | 高（轮询间隔） | 中等 | 极低（毫秒级） |
| 资源消耗 | 大量无效请求 | 挂起连接占用 | 持久连接，高效 |
| 通信方向 | 单向（请求-响应） | 单向 | 双向（全双工） |
| 连接复用 | 每次新建 | 频繁重建 | 一次建立长期复用 |
| 服务端推送 | 不支持 | 模拟支持 | 原生支持 |
| 适用场景 | 低频更新 | 中频更新 | 高频实时通信 |

#### 为什么 IM 必须用 WebSocket

1. **实时性要求**：消息延迟必须在毫秒级别，轮询无法满足
2. **双向通信**：服务器需要主动推送消息给客户端，HTTP 天然不支持
3. **连接效率**：IM 系统的在线用户可能有百万级，每个连接都需要高效复用
4. **带宽节省**：WebSocket 帧头只有 2~10 字节，远小于 HTTP 头的数百字节

```python
# WebSocket 服务端示例（Python + websockets 库）
import asyncio
import websockets

connected_users = {}

async def handler(websocket, path):
    user_id = await websocket.recv()  # 用户认证
    connected_users[user_id] = websocket
    try:
        async for message in websocket:
            # 收到消息后转发给目标用户
            data = json.loads(message)
            target_ws = connected_users.get(data['to'])
            if target_ws:
                await target_ws.send(message)
    finally:
        del connected_users[user_id]

asyncio.run(websockets.serve(handler, "0.0.0.0", 8765))
```

</details>

### Q7: 什么是倒排索引？它是如何工作的？

<details>
<summary>参考答案</summary>

倒排索引（Inverted Index）是搜索引擎最核心的数据结构，理解它是理解所有搜索系统的基础。

#### 直觉类比

想象一本书的目录是**正排索引**：从章节号找到内容。而书末尾的**关键词索引**就是**倒排索引**：从关键词找到它出现在哪些页。

```
正排索引（Forward Index）：
  文档1 → [词A, 词B, 词C]
  文档2 → [词B, 词D]
  文档3 → [词A, 词D, 词E]

倒排索引（Inverted Index）：
  词A → [文档1, 文档3]
  词B → [文档1, 文档2]
  词C → [文档1]
  词D → [文档2, 文档3]
  词E → [文档3]
```

#### 倒排索引的结构

一个完整的倒排索引由两部分组成：

1. **词典（Dictionary）**：所有出现过的词项（Term），通常用 Hash 表或 B+ 树存储
2. **倒排列表（Posting List）**：每个词项对应的文档列表，包含文档 ID、词频（TF）、位置信息等

```diagram
词典                 倒排列表
┌──────────┐        ┌─────────────────────────────────┐
│ "搜索引擎"│───────→│ (doc1, tf=3, pos=[5,12,28])     │
│          │        │ (doc5, tf=1, pos=[42])           │
│          │        │ (doc9, tf=2, pos=[1,15])         │
├──────────┤        └─────────────────────────────────┘
│ "倒排索引"│───────→│ (doc1, tf=2, pos=[8,35])        │
│          │        │ (doc3, tf=5, pos=[2,7,11,20,45]) │
├──────────┤        └─────────────────────────────────┘
│ "分布式"  │───────→│ (doc2, tf=1, pos=[3])           │
│          │        │ (doc5, tf=3, pos=[1,8,22])       │
└──────────┘        └─────────────────────────────────┘
```

#### 检索过程

当用户搜索"搜索引擎 倒排索引"时：

1. **分词**：将查询拆分为 ["搜索引擎", "倒排索引"]
2. **查词典**：分别查找两个词项的倒排列表
3. **求交集**：找出同时包含两个词的文档（doc1）
4. **打分排序**：根据 TF-IDF 或 BM25 计算每个文档的相关性得分
5. **返回结果**：按得分降序返回

```python
# 简化的倒排索引实现
from collections import defaultdict

class InvertedIndex:
    def __init__(self):
        self.index = defaultdict(set)

    def add_document(self, doc_id: int, text: str):
        words = text.split()  # 简化分词
        for word in words:
            self.index[word].add(doc_id)

    def search(self, query: str) -> set:
        terms = query.split()
        if not terms:
            return set()
        # 对所有词项的倒排列表求交集
        result = self.index.get(terms[0], set())
        for term in terms[1:]:
            result = result & self.index.get(term, set())
        return result
```

#### 为什么倒排索引高效？

- **正排索引搜索**：遍历所有文档检查是否包含查询词，时间复杂度 O(N × M)
- **倒排索引搜索**：直接定位到包含查询词的文档列表，时间复杂度 O(K)，K 远小于 N

对于 10 亿网页的搜索引擎，倒排索引将搜索时间从小时级降低到毫秒级。

</details>

### Q8: 秒杀系统面临的核心挑战是什么？如何进行流量削峰？

<details>
<summary>参考答案</summary>

秒杀系统是高并发场景的极端案例，核心矛盾是**瞬时巨大流量与有限库存之间的冲突**。

#### 秒杀系统面临的四大挑战

| 挑战 | 描述 | 量化示例 |
|------|------|---------|
| 瞬时高并发 | 所有用户在同一时刻涌入 | 100 万用户同时点击 |
| 超卖问题 | 库存扣减的并发安全 | 1000 件商品不能卖出 1001 件 |
| 恶意流量 | 黄牛脚本、机器人刷单 | 正常流量 × 10 |
| 系统雪崩 | 瞬时压力压垮数据库 | MySQL QPS 极限约 5000 |

#### 流量削峰的三板斧

**类比**：流量削峰就像高速公路的收费站——不让所有车同时涌入，而是分批通过。

**第一板斧：前端拦截**

在用户端拦截大量无效请求，将流量从百万级降到十万级。

```diagram
┌───────────────────────────────────┐
│            前端拦截层              │
│                                   │
│  1. 按钮置灰 + 倒计时              │
│  2. 点击后禁用按钮 5 秒            │
│  3. 答题/滑块验证码               │
│  4. 随机延迟（将请求打散到 3~5 秒） │
└───────────────────────────────────┘
     100 万请求 → 过滤到 10 万请求
```

**第二板斧：网关限流**

在 Nginx/API Gateway 层进行限流，将流量从十万级降到万级。

```nginx
# Nginx 限流配置
http {
    # 令牌桶限流：每秒 10000 个请求
    limit_req_zone $binary_remote_addr zone=seckill:10m rate=10000r/s;

    server {
        location /api/seckill {
            limit_req zone=seckill burst=20000 nodelay;
            proxy_pass http://backend;
        }
    }
}
```

核心限流算法：
- **令牌桶**：以固定速率生成令牌，请求消耗令牌，桶满则拒绝
- **漏桶**：以固定速率处理请求，超出容量的请求排队或拒绝
- **滑动窗口**：统计窗口内的请求数，超过阈值则拒绝

**第三板斧：消息队列异步化**

将秒杀请求放入消息队列，后端按处理能力消费，将瞬时峰值转化为平稳流量。

```
用户请求 → 网关限流 → Redis 预扣减 → 消息队列（Kafka/RocketMQ）
                                          ↓
                                    消费者按固定速率消费
                                          ↓
                                    创建订单 → MySQL
```

#### 完整的流量漏斗

```
100 万并发请求
     ↓  前端拦截（按钮/验证码/延迟）
10 万请求到达服务端
     ↓  网关限流（令牌桶/IP 限流）
1 万请求进入业务层
     ↓  Redis 预扣减（库存不足直接拒绝）
1000 个成功预扣减
     ↓  消息队列异步处理
1000 个订单写入数据库
```

每一层都在过滤掉大量无效或过量的请求，最终只有真正有效的请求到达数据库。

</details>
