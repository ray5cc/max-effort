## ⭐ 基础题

### Q1：什么是 CAP 定理？为什么不能同时满足 CAP？

<details>
<summary>参考答案</summary>

**CAP 定理**：分布式系统最多同时满足一致性（Consistency）、可用性（Availability）、分区容忍（Partition Tolerance）中的两个。由于网络分区（P）在分布式环境中不可避免，实际选择只在 **CP** 或 **AP** 之间。

**直觉理解**：两个节点网络断开时，一个收到了写请求——

- 如果拒绝写（保 C 丢 A）→ **CP**（如 etcd、ZooKeeper、HBase）
- 如果接受写但两节点数据不一致（保 A 丢 C）→ **AP**（如 Cassandra、DynamoDB、Eureka）

#### PACELC 定理（CAP 的扩展）

CAP 只讨论了分区时的取舍，但**大多数时候网络是正常的**。PACELC 补充了无分区时的权衡：

```
如果发生分区(P)：选择 A(可用) 还是 C(一致)？
否则(E)：选择 L(低延迟) 还是 C(强一致)？
```

**真实系统分类表**：

| 系统         | CAP 类型 | PACELC 类型 | 说明                                     |
| ------------ | -------- | ----------- | ---------------------------------------- |
| etcd         | CP       | PC/EC       | 始终保一致性，分区时拒绝服务             |
| ZooKeeper    | CP       | PC/EC       | 同 etcd，读也要求一致时需走 sync()       |
| MongoDB      | CP       | PA/EC       | 分区时保可用（可配），正常时保一致        |
| Cassandra    | AP       | PA/EL       | 始终保可用和低延迟，最终一致             |
| DynamoDB     | AP       | PA/EL       | 默认最终一致，可选强一致读（牺牲延迟）   |
| CockroachDB  | CP       | PC/EC       | 跨地域强一致，延迟换一致性               |
| Redis Cluster| AP       | PA/EL       | 异步复制，主从切换可能丢数据             |

**常见误解澄清**：

1. ❌ "CAP 只能三选二" → ✅ P 不可选择，只能在 CP 和 AP 间选
2. ❌ "CP 系统完全不可用" → ✅ 多数派分区仍然可用，只是少数派不可用
3. ❌ "AP 系统没有一致性" → ✅ AP 系统在无分区时通常提供强一致读

</details>

### Q2：最终一致性和强一致性的区别？各自适用什么场景？

<details>
<summary>参考答案</summary>

| 维度         | 强一致性（Linearizability）        | 最终一致性（Eventual Consistency）   |
| ------------ | ---------------------------------- | ------------------------------------ |
| **定义**     | 写成功后，任何读都能立即看到最新值 | 写成功后，读可能暂时看到旧值         |
| **延迟**     | 较高（需等多数节点确认）           | 较低（单节点确认即可返回）           |
| **可用性**   | 较低（分区时可能拒绝服务）         | 较高（分区时仍可服务）               |
| **适用场景** | 银行转账、库存扣减、选举           | 社交点赞数、DNS、CDN 缓存           |
| **代表系统** | etcd、ZooKeeper、Spanner           | Cassandra、DynamoDB、Redis 主从      |

**中间地带——因果一致性**：

比最终一致性强，比强一致性弱。保证因果相关的操作有序，但允许并发操作乱序。MongoDB 的 Causal Consistency Session 就是典型实现。

**大多数互联网应用使用最终一致性**——用户体验上可以接受几秒的延迟，换取更高的可用性和性能。核心金融场景（如支付、转账）除外。

</details>

### Q3：什么是 Raft 共识算法？它解决了什么问题？

<details>
<summary>参考答案</summary>

Raft 让多个节点对数据达成一致（即使部分节点故障）。核心思想是**先选 Leader，再由 Leader 统一管理日志复制**。

#### 三大核心机制

**1. Leader 选举（Leader Election）**

```diagram
                    超时触发           获得多数票
  Follower ──────────────────> Candidate ──────────────> Leader
     ^                            |                        |
     |         发现更高 term       |    发现更高 term        |
     +----------------------------+------------------------+
```

- 每个节点有随机选举超时（150ms~300ms），超时后变为 Candidate
- Candidate 将 term+1，投票给自己，并向其他节点发送 RequestVote RPC
- 获得多数票（n/2+1）即成为 Leader
- **投票规则**：每个 term 只投一票，且只投给日志"至少和自己一样新"的 Candidate

**2. 日志复制（Log Replication）**

```diagram
  Client ──> Leader ──> AppendEntries RPC ──> Follower 1 ✓
                    └──> AppendEntries RPC ──> Follower 2 ✓
                    └──> AppendEntries RPC ──> Follower 3 ✗ (网络超时)

  多数确认(2/3) → commit → 返回客户端成功
```

- Leader 将命令追加到自己的日志，然后并行发给所有 Follower
- **多数节点确认后才提交**（commit），提交后才返回客户端
- Follower 日志与 Leader 不一致时，Leader 会强制覆盖 Follower 的日志

**3. 安全性保证（Safety Properties）**

| 保证                 | 含义                                                         |
| -------------------- | ------------------------------------------------------------ |
| Election Safety      | 每个 term 最多一个 Leader                                    |
| Leader Append-Only   | Leader 不会删除或覆盖自己的日志                              |
| Log Matching         | 两个日志相同位置 term 相同 → 该位置及之前所有条目都相同      |
| Leader Completeness  | 已提交的日志一定会出现在所有后续 Leader 的日志中             |
| State Machine Safety | 所有节点对同一日志位置应用相同的命令                         |

**与 Paxos 的区别**：Raft 限定强 Leader 模型，理解和实现更简单。etcd、Consul、TiKV 都使用 Raft。

**Multi-Raft 简介**：单 Raft 的 Leader 是瓶颈。TiKV 等系统将数据分为多个 Region，每个 Region 一个独立 Raft 组，实现并行复制（详见 Q19）。

</details>

### Q4：什么是两阶段提交（2PC）？它有什么缺点？

<details>
<summary>参考答案</summary>

**2PC 流程**：

```diagram
  协调者(Coordinator)          参与者A        参与者B        参与者C
       |                         |              |              |
       |── Phase 1: Prepare ────>|              |              |
       |── Phase 1: Prepare ──────────────────>|              |
       |── Phase 1: Prepare ────────────────────────────────>|
       |                         |              |              |
       |<── Vote: Yes ──────────|              |              |
       |<── Vote: Yes ──────────────────────────|              |
       |<── Vote: Yes ────────────────────────────────────────|
       |                         |              |              |
       |── Phase 2: Commit ─────>|              |              |
       |── Phase 2: Commit ──────────────────>|              |
       |── Phase 2: Commit ────────────────────────────────>|
```

1. **准备阶段**：协调者问所有参与者"能不能提交？"
2. **提交阶段**：全票 Yes → 提交；任一 No → 回滚

**2PC 的缺点**：

| 问题           | 说明                                                       |
| -------------- | ---------------------------------------------------------- |
| **阻塞问题**   | 协调者故障后参与者无限等待，资源被锁定                     |
| **单点故障**   | 协调者是单点，宕机则整个事务挂起                           |
| **性能差**     | 所有参与者锁定资源直到第二阶段完成                         |
| **数据不一致** | Phase 2 部分参与者收到 Commit、部分没收到 → 不一致         |

#### 3PC 改进

3PC 在 Prepare 和 Commit 之间增加 **PreCommit** 阶段，并引入**超时机制**：

```
Phase 1: CanCommit? → Yes/No
Phase 2: PreCommit  → Ack（参与者进入待提交状态）
Phase 3: DoCommit   → 最终提交
```

**3PC 的改进**：参与者在 PreCommit 后若超时未收到 DoCommit，可以自行决定提交（因为已知所有人都投了 Yes）。减少了阻塞窗口。

**3PC 为什么仍不广泛使用**：

- 网络分区时仍可能不一致（超时自动提交 vs 协调者发了 Abort）
- 多了一轮网络开销，性能更差
- 工程复杂度大幅增加，收益不成比例

**生产中的替代方案**：Saga（补偿事务）、TCC（Try-Confirm-Cancel）、本地消息表 + MQ。

</details>

### Q5：什么是一致性哈希？为什么比普通取模哈希好？

<details>
<summary>参考答案</summary>

**普通哈希的问题**：`hash(key) % N`，当 N（节点数）变化时，几乎所有 key 的映射都会改变，导致大规模缓存失效。

**一致性哈希原理**：

```
              Node A (hash=0)
               /          \
        Node D            Node B
       (hash=270)        (hash=90)
               \          /
              Node C (hash=180)

  key1(hash=45)  → 顺时针找到 Node B
  key2(hash=130) → 顺时针找到 Node C
  key3(hash=200) → 顺时针找到 Node D
```

- 节点和 key 都映射到一个 0~2^32 的环上
- key 沿顺时针方向找到的第一个节点就是负责节点
- **添加/删除节点只影响相邻区域**的 key，其他 key 不受影响

**虚拟节点解决数据倾斜**：

一个物理节点映射 100~200 个虚拟节点到环上，数据分布更均匀。

```
物理节点 A → 虚拟节点 A#1, A#2, A#3, ..., A#150
物理节点 B → 虚拟节点 B#1, B#2, B#3, ..., B#150
```

**实际应用**：
- Redis Cluster 使用 16384 个 slot（本质是一致性哈希的变体）
- Cassandra、DynamoDB 使用一致性哈希进行数据分片
- Nginx upstream 的 `hash $request_uri consistent` 配置

</details>

### Q6：缓存穿透、击穿、雪崩分别是什么？如何解决？

<details>
<summary>参考答案</summary>

| 问题     | 场景                          | 解决方案                             |
| -------- | ----------------------------- | ------------------------------------ |
| **穿透** | 查不存在的 key，缓存永远不命中 | 布隆过滤器 + 缓存空值（TTL 短）     |
| **击穿** | 热点 key 过期，大量请求穿透   | 互斥锁重建 + 逻辑过期               |
| **雪崩** | 大量 key 同时过期             | 随机过期时间 + 多级缓存             |

#### 三种缓存更新策略

**1. Cache-Aside（旁路缓存）** ——最常用

```python
# 读
def get(key):
    val = cache.get(key)
    if val is None:           # 缓存未命中
        val = db.get(key)     # 读数据库
        cache.set(key, val, ttl=300)
    return val

# 写
def update(key, val):
    db.update(key, val)       # 先更新数据库
    cache.delete(key)         # 再删缓存（而非更新）
```

**2. Write-Through（写穿透）** ——强一致

```python
def write_through(key, val):
    cache.set(key, val)       # 写缓存
    db.update(key, val)       # 同步写数据库（原子操作）
```

**3. Write-Behind（写回）** ——高吞吐

```python
def write_behind(key, val):
    cache.set(key, val)       # 只写缓存
    # 异步批量刷入数据库（定时/队列）
    async_queue.push((key, val))
```

#### 延迟双删模式

解决 Cache-Aside 在并发读写时的不一致问题：

```python
def update_with_double_delete(key, val):
    cache.delete(key)           # 第一次删缓存
    db.update(key, val)         # 更新数据库
    time.sleep(0.5)             # 等待主从同步 + 并发读完成
    cache.delete(key)           # 第二次删缓存（删掉并发读写入的脏数据）
```

**为什么需要第二次删除？** 在第一次删除和 DB 更新之间，并发请求可能读到旧 DB 值并写入缓存。第二次删除清理这个脏数据。

#### 热 Key 解决方案

```diagram
    请求 ──> 本地缓存(Caffeine/Guava, TTL=1s)
                 ↓ 未命中
             L2 缓存(Redis Cluster)
                 ↓ 未命中
             数据库
```

- **本地缓存 + L2 缓存**：热点 key 放本地缓存，极短 TTL
- **key 打散**：`hot_key` → `hot_key_1`, `hot_key_2`, ..., `hot_key_N`，随机读取

</details>

### Q7：什么是幂等性？为什么分布式系统必须设计幂等接口？

<details>
<summary>参考答案</summary>

**幂等** = 执行一次和执行多次效果一样。数学表示：f(f(x)) = f(x)。

分布式系统中，网络超时导致客户端重试是家常便饭。非幂等操作（如 `余额 += 100`）重试会导致重复执行。

#### HTTP 方法的幂等性

| 方法   | 幂等 | 说明                                         |
| ------ | ---- | -------------------------------------------- |
| GET    | ✅   | 只读操作，天然幂等                           |
| PUT    | ✅   | 全量更新（SET balance=200），重复执行结果一样 |
| DELETE | ✅   | 删除同一资源多次结果一样                     |
| POST   | ❌   | 创建资源（可能重复创建）                     |
| PATCH  | ❌   | 增量更新（`balance += 100`），重复执行有副作用 |

#### 实现方式

1. **唯一请求 ID + 去重表**

```sql
-- 去重表
CREATE TABLE idempotent_keys (
    idempotent_key VARCHAR(64) PRIMARY KEY,
    response TEXT,
    created_at TIMESTAMP DEFAULT NOW()
);

-- 处理前先查
INSERT INTO idempotent_keys (idempotent_key, response)
VALUES ('req-uuid-123', NULL)
ON CONFLICT DO NOTHING;
-- 若插入成功 → 首次请求，继续处理
-- 若冲突 → 重复请求，返回之前的 response
```

2. **乐观锁（版本号）**

```sql
UPDATE accounts SET balance = 200, version = version + 1
WHERE id = 1 AND version = 5;
-- 受影响行数为 0 → 已被其他事务修改，拒绝本次操作
```

3. **将增量改为设置操作**：`SET balance = 200` 而非 `INCR balance 100`

</details>

### Q8：负载均衡有哪些常见策略？各自适用什么场景？

<details>
<summary>参考答案</summary>

| 策略             | 原理                             | 适用场景                     |
| ---------------- | -------------------------------- | ---------------------------- |
| **轮询**         | 依次分配请求                     | 服务器性能一致               |
| **加权轮询**     | 按权重比例分配                   | 服务器性能不一致             |
| **最少连接**     | 分配给当前连接最少的服务器       | 长连接（WebSocket、DB 连接池）|
| **IP 哈希**      | 按客户端 IP 哈希                 | 需要会话粘性                 |
| **一致性哈希**   | 哈希环映射                       | 有状态服务（缓存层）         |
| **随机**         | 随机选择                         | 快速简单，大规模下趋近均匀   |
| **最短响应时间** | 分配给响应最快的服务器           | 后端延迟差异大               |

**四层 vs 七层负载均衡**：

```diagram
  客户端 ──> L4 负载均衡(TCP/IP层, 如 LVS/DPVS)
                   ↓
             L7 负载均衡(HTTP层, 如 Nginx/Envoy)
                   ↓
             后端服务集群
```

- **L4（传输层）**：基于 IP+端口转发，性能极高（百万级 QPS），不解析内容
- **L7（应用层）**：可解析 HTTP 头/URL/Cookie，支持更灵活的路由规则

**生产常见架构**：DNS → L4(LVS/DPVS) → L7(Nginx/Envoy) → 服务集群

</details>

### Q9：Raft 如何处理网络分区恢复后的日志冲突？

<details>
<summary>参考答案</summary>

**场景重现**：

```
  分区前：Leader A (term=1), Follower B, Follower C

  网络分区：
    分区1: [A]          ← 少数派，A 仍认为自己是 Leader，接收写但无法 commit
    分区2: [B, C]       ← 多数派，B 超时后发起选举，term=2，B 成为新 Leader

  分区恢复后：
    A 发现 B 的 term=2 > 自己的 term=1 → A 自动退位为 Follower
    B 发送 AppendEntries 给 A → A 的未提交日志被 B 的日志覆盖
```

**关键安全性保证**：

1. A 在少数派分区中的写操作**无法获得多数确认**，因此这些日志始终处于 uncommitted 状态
2. 只有已被多数节点确认的日志才算"已提交"，**已提交的日志永远不会丢失**
3. B 成为新 Leader 后，通过 AppendEntries 的 `prevLogIndex` 和 `prevLogTerm` 检查，找到与 A 日志分叉的位置，然后**强制 A 的日志与自己一致**

**这就是为什么 Raft 要求多数派确认**——即使发生分区，已提交的数据不会丢失。

</details>

### Q10：Saga 模式和 TCC 模式分别适用什么场景？

<details>
<summary>参考答案</summary>

|                | Saga                         | TCC                            |
| -------------- | ---------------------------- | ------------------------------ |
| **隔离性**     | 弱（中间状态可见）           | 强（Try 阶段锁定/预留资源）   |
| **实现复杂度** | 低（只需补偿逻辑）           | 高（三阶段全部实现）           |
| **性能**       | 高（无资源预锁定）           | 中（Try 阶段有资源预留）       |
| **适用**       | 长流程业务（订单、物流）     | 短事务高一致（支付、转账）     |
| **回滚方式**   | 反向补偿（已执行的动作逆操作）| Cancel 释放 Try 阶段预留资源  |

#### Saga 编排 vs 协调

```diagram
  编排模式(Orchestration)          协调模式(Choreography)

  Saga 协调器                      Service A ──event──> Service B
      ↓ 命令                                              ↓ event
  Service A                                            Service C
      ↓ 命令
  Service B              适用：服务少、流程简单
      ↓ 命令
  Service C

  适用：服务多、流程复杂
```

- **编排模式**：中心协调器按顺序调用各服务，失败时调用补偿。逻辑集中，易理解。
- **协调模式**：各服务通过事件驱动，无中心节点。去中心化，但流程分散难以追踪。

#### Temporal 工作流引擎

现代分布式事务的新趋势：用 **Temporal**（原 Cadence）编排长事务：

```go
// Temporal Workflow 示例
func OrderWorkflow(ctx workflow.Context, order Order) error {
    // Step 1: 扣库存
    err := workflow.ExecuteActivity(ctx, DeductInventory, order).Get(ctx, nil)
    if err != nil {
        return err  // Temporal 自动重试
    }
    // Step 2: 扣款
    err = workflow.ExecuteActivity(ctx, ChargePayment, order).Get(ctx, nil)
    if err != nil {
        // 补偿：恢复库存
        workflow.ExecuteActivity(ctx, RestoreInventory, order).Get(ctx, nil)
        return err
    }
    // Step 3: 发货
    return workflow.ExecuteActivity(ctx, ShipOrder, order).Get(ctx, nil)
}
```

**Temporal 的优势**：自动重试、超时管理、可视化流程、支持长时间等待（人工审批场景）。

</details>

### Q11：什么是向量时钟（Vector Clock）？它解决了什么问题？

<details>
<summary>参考答案</summary>

**向量时钟**用一个计数器向量 `[A:2, B:3, C:1]` 跟踪每个节点的逻辑时间，可以**精确判断两个事件是"因果相关"还是"并发"**。

#### 比较规则

- `V1 ≤ V2`（V1 每个分量都 ≤ V2 对应分量）→ V1 **发生在** V2 之前（因果关系）
- 否则（存在交叉）→ **并发事件**（可能有冲突，需要应用层解决）

#### 示例

```diagram
  Node A             Node B             Node C
  [1,0,0] write x=1
           ─────────>
                      [1,1,0] write x=2
                               ─────────>
                                          [1,1,1] read x → 因果链完整

  Node A             Node B
  [2,0,0] write x=3  [0,1,0] write x=4

  比较: [2,0,0] vs [0,1,0] → 2>0 但 0<1 → 并发！需要冲突解决
```

**与 Lamport 时钟的区别**：

| 维度       | Lamport 时钟   | 向量时钟           |
| ---------- | -------------- | ------------------ |
| **大小**   | 单个整数       | N 维向量（N=节点数）|
| **能力**   | 只能判断偏序   | 能检测并发         |
| **应用**   | 全序排列事件   | 冲突检测           |

**应用**：DynamoDB（早期）、Riak 用向量时钟检测数据冲突。实际中因向量维度随节点数增长，常用**版本向量（Version Vector）**作为优化。

</details>

### Q12：什么是 Gossip 协议？它的优缺点是什么？

<details>
<summary>参考答案</summary>

**Gossip（流言协议）**：每个节点周期性地随机选几个邻居交换信息，像传谣一样最终所有节点都知道全部信息。

#### 工作流程

```
  T=0:  Node A 知道消息 M
  T=1:  A 随机选 B, C 发送 M    → A,B,C 知道 M
  T=2:  B 随机选 D, A 发送 M    → A,B,C,D 知道 M
        C 随机选 E, A 发送 M    → A,B,C,D,E 知道 M
  T=3:  ...                     → 指数级扩散，O(logN) 轮收敛
```

**三种 Gossip 变体**：

| 变体                | 说明                       | 使用场景           |
| ------------------- | -------------------------- | ------------------ |
| Anti-Entropy        | 周期性全量同步，纠正差异   | 数据修复           |
| Rumor Mongering     | 只传播"新"消息，有概率停止 | 快速传播更新       |
| Aggregation         | 聚合计算（求和/平均/最大值）| 分布式监控         |

**优点**：去中心化、容错性强（没有单点）、可扩展
**缺点**：收敛时间不确定、带宽消耗（冗余消息）、最终一致性（非强一致）

**应用**：
- Cassandra 集群成员管理与故障检测
- Redis Cluster 节点间状态同步
- Consul 的 Serf（成员管理层）
- 区块链 P2P 网络

</details>

### Q13：分布式锁有哪些实现方式？各自的问题是什么？

<details>
<summary>参考答案</summary>

| 实现      | 方式                        | 问题                             |
| --------- | --------------------------- | -------------------------------- |
| Redis     | `SET key val NX EX`         | 主从切换可能丢锁                 |
| Redlock   | 多数 Redis 节点加锁         | Martin Kleppmann 的时钟偏移质疑  |
| ZooKeeper | 临时顺序节点                | 性能较低（每次加锁需创建节点）   |
| etcd      | 分布式锁 API（基于 Raft）   | 需要 etcd 集群                   |

#### Redis 分布式锁实现（Lua 脚本保证原子性）

```lua
-- 加锁（原子操作）
local key = KEYS[1]
local value = ARGV[1]     -- 客户端唯一标识（UUID）
local ttl = ARGV[2]       -- 超时时间

if redis.call('SET', key, value, 'NX', 'EX', ttl) then
    return 1  -- 加锁成功
end
return 0      -- 加锁失败

-- 解锁（只有持锁者才能释放）
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end
return 0
```

#### Redlock 争议（Martin Kleppmann vs Antirez）

**Redlock 流程**：在 5 个独立 Redis 节点中尝试加锁，3 个以上成功 → 加锁成功。

**Martin Kleppmann 的质疑**：
1. **GC 停顿**：客户端获取锁后发生长时间 GC，锁过期，另一客户端获锁 → 两个客户端同时持锁
2. **时钟偏移**：Redis 节点时钟跳变导致锁提前过期
3. **结论**：Redlock 既不够安全（不能替代 ZooKeeper），也不够高效（比单 Redis 慢很多）

**Antirez 的反驳**：
- GC 停顿问题通过合理设置锁超时和使用 Fencing Token 解决
- 现代系统时钟偏移在可控范围内

#### ZooKeeper 临时顺序节点实现

```diagram
/locks/my-lock/
    ├── _c_0000000001  (客户端A创建)
    ├── _c_0000000002  (客户端B创建)
    └── _c_0000000003  (客户端C创建)

规则：序号最小的持有锁，其他 Watch 前一个节点
客户端断连 → 临时节点自动删除 → 下一个客户端获锁
```

#### Fencing Token 模式

```
  Client 1: 获锁 (token=33) → GC暂停 → 锁过期
  Client 2: 获锁 (token=34) → 写数据 (token=34)
  Client 1: GC恢复 → 写数据 (token=33) → 存储层拒绝 (33 < 34)
```

**生产建议**：对一致性要求高用 ZooKeeper/etcd；对性能敏感且可容忍偶尔失败用 Redis 单节点。Redlock 慎用。

</details>

### Q14：什么是读写分离？如何处理主从延迟导致的数据不一致？

<details>
<summary>参考答案</summary>

**基本架构**：写主库，读从库。从库通过 Binlog 异步/半同步复制主库数据。

```diagram
  客户端写 ──> 主库(Master) ──binlog──> 从库1(Slave)
  客户端读 <────────────────────────── 从库2(Slave)
```

**主从延迟可能导致"刚写完读不到"**（read-after-write 一致性问题）。

#### 解决方案

| 方案             | 原理                                   | 适用场景             |
| ---------------- | -------------------------------------- | -------------------- |
| **强制读主**     | 关键查询直接读主库                     | 支付后查询           |
| **半同步复制**   | 至少一个从库确认后才返回写成功         | 对延迟容忍度低       |
| **延迟路由**     | 记录写操作时间戳，< 阈值则路由到主库   | 通用场景             |
| **GTID 追踪**   | 写返回 GTID，读携带 GTID，从库不够新则读主 | MySQL 5.7+       |
| **会话一致性**   | 同一会话的读写始终路由到主库           | 单用户强一致         |

**GTID 方案详解**：

```
1. 写操作 → 主库执行，返回 GTID=uuid:42
2. 读操作 → 携带 GTID=uuid:42 发给代理层
3. 代理层检查从库 Executed_Gtid_Set
   - 从库已执行到 uuid:45 (>42) → 路由到从库 ✓
   - 从库只到 uuid:40 (<42) → 路由到主库 ✓
```

</details>

### Q15：微服务中的熔断器是如何工作的？

<details>
<summary>参考答案</summary>

#### 熔断器状态机

```diagram
                     错误率 > 阈值
    ┌─────────┐  ──────────────────>  ┌──────────┐
    │ Closed  │                       │   Open   │
    │(正常转发)│  <──────────────────  │(快速失败)│
    └─────────┘     探测成功           └──────────┘
         ^              |                    |
         |         ┌────┴─────┐              |
         +─────────┤Half-Open │<─────────────+
           全部成功 │(试探放行) │   冷却超时到
                    └──────────┘
```

- **Closed（关闭）**：正常转发请求，统计错误率（滑动窗口）
- **Open（打开）**：错误率超过阈值 → 直接拒绝请求（快速失败），避免下游雪崩
- **Half-Open（半开）**：等待冷却期后，放行少量探测请求。成功 → Closed；失败 → Open

#### 限流算法对比

| 算法               | 原理                         | 优点               | 缺点                 |
| ------------------ | ---------------------------- | ------------------ | -------------------- |
| **令牌桶**         | 定速产生令牌，取到令牌才放行 | 允许突发流量       | 实现稍复杂           |
| **漏桶**           | 请求入队，匀速出队处理       | 输出平滑           | 无法处理突发         |
| **滑动窗口日志**   | 记录每个请求时间戳，窗口计数 | 精确               | 内存消耗大           |
| **滑动窗口计数器** | 按比例加权前后窗口的计数     | 内存小、基本精确   | 有微小误差           |

#### Bulkhead（舱壁模式）

```diagram
  服务 A 的线程池
  ┌──────────────────────────────────┐
  │ 调用服务B的线程池(max=10)        │  ← 服务B挂了，最多阻塞10个线程
  │ 调用服务C的线程池(max=20)        │  ← 服务C正常，不受影响
  │ 调用服务D的线程池(max=5)         │
  └──────────────────────────────────┘
```

将对不同下游服务的调用隔离在独立的线程池/信号量中，避免某个下游故障拖垮整个服务。

#### Backoff + Jitter（退避 + 抖动）

重试不能用固定间隔，否则所有客户端同时重试（惊群效应）：

```
sleep = min(cap, base * 2^attempt) + random(0, base)
```

**工具**：Resilience4j（Java）、Sentinel（阿里）、go-zero（Go）

</details>

### Q17：设计一个分布式 ID 生成器，要求全局唯一、趋势递增、高性能。

<details>
<summary>参考答案</summary>

#### Snowflake 算法（Twitter）

```
  64位: 0 | 41位时间戳 | 10位机器ID | 12位序列号
        ↑
      符号位(固定0)

  41位时间戳: 2^41 / (365*24*3600*1000) ≈ 69年
  10位机器ID: 2^10 = 1024个节点
  12位序列号: 2^12 = 4096个/毫秒/节点

  单节点理论QPS: 4096 * 1000 = 409.6万/秒
```

#### 各方案对比

| 方案           | 唯一性 | 有序性   | 性能     | 依赖           |
| -------------- | ------ | -------- | -------- | -------------- |
| UUID           | ✅     | ❌ 无序  | ★★★★★   | 无             |
| 数据库自增     | ✅     | ✅ 严格  | ★★☆☆☆   | 数据库         |
| Redis INCR     | ✅     | ✅ 严格  | ★★★★☆   | Redis          |
| Snowflake      | ✅     | ✅ 趋势  | ★★★★★   | 时钟同步       |
| Leaf（美团）   | ✅     | ✅ 趋势  | ★★★★☆   | DB/ZooKeeper   |

#### 时钟回拨问题

```
  正常: T=100ms → T=101ms → T=102ms
  回拨: T=100ms → T=101ms → T=99ms ← 回拨！

  解决方案：
  1. 拒绝生成，等待时钟追上（简单但会有短暂不可用）
  2. 预留扩展位，回拨时切换到下一个序列空间
  3. 使用 NTP 时钟守护进程，减小回拨幅度
```

### Q19：Multi-Raft 和单 Raft 有什么区别？为什么 TiKV 使用 Multi-Raft？

<details>
<summary>参考答案</summary>

**单 Raft 的瓶颈**：所有数据由一个 Raft 组管理 → Leader 成为写入瓶颈，单机磁盘和网络成为天花板。

**Multi-Raft**：数据分成多个 Region，每个 Region 一个独立的 Raft 组 → 并行复制，无单点瓶颈。

#### TiKV 的 Multi-Raft 架构

```diagram
  ┌───────────────────────────────────────────────┐
  │              PD (Placement Driver)             │
  │   - Region 元数据管理                          │
  │   - Leader 调度（均衡各节点的 Leader 数量）     │
  │   - Region 分裂/合并决策                        │
  │   - 热点调度（识别并迁移热点 Region）           │
  └───────────────┬───────────────────────────────┘
                  │
    ┌─────────────┼─────────────┐
    │             │             │
  ┌─┴──┐      ┌──┴─┐       ┌──┴─┐
  │Node1│      │Node2│      │Node3│
  ├─────┤      ├─────┤      ├─────┤
  │R1(L)│<────>│R1(F)│<────>│R1(F)│  ← Region 1 的 Raft 组
  │R2(F)│<────>│R2(L)│<────>│R2(F)│  ← Region 2 的 Raft 组
  │R3(F)│<────>│R3(F)│<────>│R3(L)│  ← Region 3 的 Raft 组
  └─────┘      └─────┘      └─────┘

  L=Leader, F=Follower
  每个 Region 默认 96MB，超过后自动分裂
```

#### Region Split / Merge

- **Split**：Region 数据量超过阈值（默认 96MB）→ PD 下发分裂指令 → 分为两个子 Region
- **Merge**：相邻两个 Region 都很小 → PD 下发合并指令 → 减少 Raft 组数量

#### CockroachDB 的 Range

CockroachDB 类似方案，称为 Range（默认 512MB）。每个 Range 一个 Raft 组。支持**跨 Range 分布式事务**（基于 HLC 混合逻辑时钟 + 并行提交协议）。

**追问链**：

1. **PD 如何检测热点 Region？** → 统计各 Region 的 QPS 和流量，超过阈值时将 Leader 迁移或分裂 Region
2. **Multi-Raft 的 Leader 如何均衡？** → PD 维护每个节点的 Leader 数量，通过 TransferLeader 操作均衡
3. **Region 分裂时如何保证一致性？** → 分裂是一个 Raft 日志条目，在原 Raft 组中 commit 后才生效，新 Region 从分裂点开始独立复制

</details>

### Q20：什么是"脑裂"（Split Brain）？如何避免？

<details>
<summary>参考答案</summary>

**脑裂**：网络分区后，两个分区各自选出一个 Leader，同时接受写请求，导致数据不一致。

```diagram
  正常状态:  [Leader A] ←──→ [Follower B] ←──→ [Follower C]

  网络分区:  [A]  ╳╳╳╳╳╳  [B] ←──→ [C]
              ↑                  ↑
           A仍认为自己是Leader   B被选为新Leader
           两个Leader同时写入 → 脑裂！
```

#### 解决方案

| 方案               | 原理                                           | 适用系统             |
| ------------------ | ---------------------------------------------- | -------------------- |
| **多数派原则**     | 只有获得 n/2+1 票才能成为 Leader               | Raft/Paxos/ZAB      |
| **Fencing Token**  | 每个 Leader 持有递增 token，资源侧只接受更大的  | 分布式锁             |
| **STONITH**        | 确认旧 Leader 真的死了再选新的                  | 传统集群（Pacemaker）|
| **Lease 机制**     | Leader 持有时间租约，过期前其他节点不发起选举   | etcd、Chubby         |

**Fencing Token 详解**：

```
  存储层维护最大 token:

  Client A 获锁: token=33 → 写入 (33 >= max_token=33) ✓ → max_token=33
  Client A GC暂停，锁过期
  Client B 获锁: token=34 → 写入 (34 >= max_token=33) ✓ → max_token=34
  Client A 恢复: → 写入 (33 < max_token=34) ✗ → 被拒绝！
```

**追问链**：

1. **为什么奇数节点更好？** → 3 节点和 4 节点容错能力都是 1（都需要多数 2+1/3+1），但 4 节点多消耗资源
2. **Lease 和心跳的区别？** → Lease 有时间承诺（到期前不会选新 Leader），心跳只是存活检测
3. **K8s 如何避免 etcd 脑裂？** → etcd 基于 Raft（多数派），K8s 本身通过 Leader Election API 确保只有一个 controller-manager 活跃

</details>

### Q21：CAP 中的"一致性"和 ACID 中的"一致性"有什么区别？

<details>
<summary>参考答案</summary>

**完全不同的概念**：

| 维度       | CAP 的 C（Linearizability）     | ACID 的 C（Consistency）         |
| ---------- | ------------------------------- | -------------------------------- |
| **定义**   | 所有节点在同一时刻看到相同数据  | 事务保持数据库约束不变           |
| **层面**   | 分布式系统的数据复制一致性      | 单数据库的业务逻辑约束           |
| **关注点** | 读写顺序，是否能读到最新写入    | 外键、唯一性、CHECK 约束        |
| **谁保证** | 分布式协议（Raft、Paxos）       | 应用代码 + 数据库约束           |

#### 分布式一致性层级

```diagram
  强 ──────────────────────────────────────────── 弱

  线性一致性          顺序一致性       因果一致性       最终一致性
  (Linearizability)  (Sequential)    (Causal)        (Eventual)

  - 全局时间顺序      - 所有进程      - 因果相关       - 最终相同
  - 读到最新写入       看到相同顺序    操作有序         - 无顺序保证
  - 最贵              - 无实时性保证   - 并发操作不保序

  代表: etcd          代表: ZooKeeper  代表: MongoDB    代表: Cassandra
       Spanner            (默认模式)   (Causal Session)      DynamoDB
```

**线性一致性 vs 顺序一致性**：
- **线性一致性**：操作的顺序必须符合真实时间（实时性约束）
- **顺序一致性**：所有进程看到相同的操作顺序，但不要求符合真实时间

**追问链**：

1. **Spanner 如何实现全球线性一致性？** → TrueTime API（原子钟+GPS），给每个事务分配全球有序时间戳
2. **为什么 ZooKeeper 默认是顺序一致性而非线性一致性？** → 读可以走任意节点（可能读到旧值），需要调用 `sync()` 强制读 Leader 才是线性一致
3. **因果一致性在实践中如何实现？** → 向量时钟跟踪因果依赖，或 Lamport 时间戳 + 依赖标记

</details>

### Q22：什么是 CRDTs（无冲突复制数据类型）？它如何实现无需协调的最终一致性？

<details>
<summary>参考答案</summary>

**CRDTs** 是一类数据结构，支持并发更新且**自动合并无冲突**。核心数学性质：合并操作满足交换律、结合律、幂等性。

#### 常见 CRDT 类型

| 类型         | 说明                                       | 合并规则           |
| ------------ | ------------------------------------------ | ------------------ |
| G-Counter    | 只增计数器，每节点独立计数                 | 各节点取 max 后求和 |
| PN-Counter   | 可增可减（两个 G-Counter 差值）            | 增减分别 max 后做差 |
| OR-Set       | 可添加可删除的集合（元素带唯一标签）       | 有 add 标签则存在   |
| LWW-Register | 最后写入胜出（用时间戳或逻辑时钟）         | 时间戳大的覆盖     |
| RGA          | 可复制增长数组（协同编辑用）               | 基于位置标识符排序  |

#### G-Counter 示例

```
  Node A: [A:3, B:0, C:0]  → 本地值 = 3+0+0 = 3
  Node B: [A:0, B:5, C:0]  → 本地值 = 0+5+0 = 5
  Node C: [A:0, B:0, C:2]  → 本地值 = 0+0+2 = 2

  合并后（取各节点最大值）:
  所有节点: [A:3, B:5, C:2] → 全局值 = 3+5+2 = 10
```

**应用**：
- **Redis CRDT**（Redis Enterprise 的跨数据中心复制）
- **协同编辑**：Figma（使用 CRDTs 实现多人实时协作）
- **Riak**：使用 CRDTs 作为内置数据类型

**追问链**：

1. **CRDTs 的局限性？** → 只适合可交换操作，复杂业务逻辑（如转账需要余额检查）不适用
2. **CRDTs vs OT（Operational Transformation）？** → CRDTs 无需中心服务器，OT 需要；CRDTs 内存占用更大
3. **如何处理 CRDTs 的元数据膨胀？** → 定期 GC（tombstone pruning），或使用 causal stability 判断何时可以安全清理

</details>

### Q27：设计一个跨地域数据同步方案（多活架构）

<details>
<summary>参考答案</summary>

#### 需求分析

- 多个数据中心同时提供读写服务（非主从模式）
- 用户就近访问，低延迟
- 跨地域数据最终一致
- 支持冲突检测与解决

#### 整体架构

```diagram
              全球流量调度 (GeoDNS / Anycast)
                 │            │           │
     ┌───────────┘            │           └───────────┐
     ↓                        ↓                       ↓
  ┌──────────┐          ┌──────────┐          ┌──────────┐
  │ 北京 DC  │          │ 上海 DC  │          │ 新加坡DC │
  │          │          │          │          │          │
  │ ┌──────┐ │  async   │ ┌──────┐ │  async   │ ┌──────┐ │
  │ │App层 │ │ <──────> │ │App层 │ │ <──────> │ │App层 │ │
  │ └──┬───┘ │ 复制     │ └──┬───┘ │ 复制     │ └──┬───┘ │
  │    │     │          │    │     │          │    │     │
  │ ┌──┴───┐ │          │ ┌──┴───┐ │          │ ┌──┴───┐ │
  │ │ DB   │ │          │ │ DB   │ │          │ │ DB   │ │
  │ └──────┘ │          │ └──────┘ │          │ └──────┘ │
  └──────────┘          └──────────┘          └──────────┘

  Region 内: 强一致(Raft/同步复制)
  Region 间: 最终一致(异步复制)
```

#### 冲突检测与解决

**1. 向量时钟检测并发写**

```
  北京写 user.name = "张三":  VC = [BJ:2, SH:1, SG:1]
  上海写 user.name = "李四":  VC = [BJ:1, SH:2, SG:1]

  比较: BJ: 2>1, SH: 1<2 → 并发冲突！

  解决策略:
  - LWW (Last Write Wins): 用物理时间戳取最新（简单但可能丢数据）
  - 应用层解决: 返回两个版本让用户/业务逻辑选择
  - CRDTs: 使用可自动合并的数据结构
```

**2. CRDTs 解决特定场景冲突**

```
  购物车(OR-Set CRDT):
  - 北京: 添加商品A   → {A(tag1)}
  - 上海: 添加商品B   → {B(tag2)}
  - 合并: {A(tag1), B(tag2)}  ← 自动合并，无冲突

  计数器(PN-Counter CRDT):
  - 北京: 点赞 +1     → [BJ:1, SH:0]
  - 上海: 点赞 +1     → [BJ:0, SH:1]
  - 合并: [BJ:1, SH:1] → 总计 2  ← 自动合并
```

#### 路由策略

| 数据类型     | 路由策略           | 一致性模型         |
| ------------ | ------------------ | ------------------ |
| 用户 Profile | 按用户归属地写固定 DC | 归属地强一致，跨地域最终一致 |
| 商品信息     | 任意 DC 可写       | 最终一致（LWW）    |

### Q28：设计一个分布式限流系统

<details>
<summary>参考答案</summary>

#### 需求分析

- 多维度限流：用户级、API 级、全局级
- 分布式环境下精确计数

#### 整体架构

```diagram
  请求 ──> 网关/边缘层限流(本地令牌桶, 粗粒度快速拦截)
              │
              ↓ 通过
           应用层限流(Redis 集中式精确计数)
              │
              ↓ 通过
           服务层限流(Sentinel/自适应限流)
              │
              ↓
           后端服务处理请求

  ┌──────────────────────────────────────────┐
  │           Redis Cluster                  │
  │  ┌────────┐ ┌────────┐ ┌────────┐       │
  │  │ Node 1 │ │ Node 2 │ │ Node 3 │       │
  │  │user:*  │ │api:*   │ │global:*│       │
  │  └────────┘ └────────┘ └────────┘       │
  │      滑动窗口计数器 / 令牌桶              │
  └──────────────────────────────────────────┘
```

#### Redis Lua 原子限流脚本（滑动窗口）

```lua
-- 滑动窗口限流 Lua 脚本
-- KEYS[1]: 限流 key (如 "rate:user:12345:api:/order")
-- ARGV[1]: 窗口大小(秒)
-- ARGV[2]: 最大请求数
-- ARGV[3]: 当前时间戳(毫秒)

local key = KEYS[1]
local window = tonumber(ARGV[1]) * 1000  -- 转毫秒
local limit = tonumber(ARGV[2])
local now = tonumber(ARGV[3])

-- 移除窗口外的旧请求
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)

-- 当前窗口内的请求数
local count = redis.call('ZCARD', key)

if count < limit then
    -- 未超限，记录本次请求
    redis.call('ZADD', key, now, now .. ':' .. math.random(1000000))
    redis.call('EXPIRE', key, ARGV[1])
    return 1  -- 允许
else
    return 0  -- 拒绝
end
```

#### 令牌桶实现（Redis Lua）

```lua
-- 令牌桶限流
-- KEYS[1]: 桶的 key
-- ARGV[1]: 令牌生成速率(个/秒)
-- ARGV[2]: 桶容量
-- ARGV[3]: 当前时间戳(秒, 浮点数)
-- ARGV[4]: 请求的令牌数

local key = KEYS[1]
local rate = tonumber(ARGV[1])
local capacity = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local requested = tonumber(ARGV[4])

local last_time = tonumber(redis.call('HGET', key, 'last_time') or now)
local tokens = tonumber(redis.call('HGET', key, 'tokens') or capacity)

-- 计算从上次到现在新增的令牌
local elapsed = math.max(0, now - last_time)
tokens = math.min(capacity, tokens + elapsed * rate)

if tokens >= requested then
    tokens = tokens - requested
    redis.call('HSET', key, 'tokens', tokens, 'last_time', now)
    redis.call('EXPIRE', key, math.ceil(capacity / rate) * 2)
    return 1  -- 允许
else
    redis.call('HSET', key, 'tokens', tokens, 'last_time', now)
    return 0  -- 拒绝
end
```

#### 多维度限流规则

```yaml
rate_limits:
  - dimension: user
    key: "user:{user_id}"
    limit: 100
    window: 60s       # 每用户每分钟100次

  - dimension: api
    key: "api:{path}"
    limit: 10000
    window: 1s        # 每接口每秒10000次

  - dimension: global
    key: "global"
    limit: 50000
    window: 1s        # 全局每秒50000次

  - dimension: ip
    key: "ip:{client_ip}"
    limit: 50
    window: 60s       # 每IP每分钟50次
```

#### 分布式令牌共享（Gossip-based）

当多个网关节点需要共享全局限流配额时：

```
  Gateway 1 (本地桶: 100 tokens/s)
       ↕ Gossip 同步消耗量
  Gateway 2 (本地桶: 100 tokens/s)
       ↕ Gossip 同步消耗量
  Gateway 3 (本地桶: 100 tokens/s)

  全局限额: 300 tokens/s
  每个节点预分配 100 tokens/s
  周期性通过 Gossip 通报消耗速率，动态调整各节点配额
```

**优势**：无需每次请求都访问 Redis，本地判断 + 周期性同步
**劣势**：精度略低（有同步窗口期），但对大多数场景足够

#### 防时钟偏移

分布式限流依赖时间戳，节点间时钟偏移可能导致窗口计算不准确。

**解决方案**：
- 使用 Redis 服务端时间（`TIME` 命令）而非客户端本地时间
- NTP 时钟同步，确保偏移 < 100ms
- 令牌桶算法对时钟偏移天然容忍度高于滑动窗口

#### 需求分析

- 服务实例注册/注销
- 健康检查，自动摘除不健康实例
- 客户端高效发现可用服务实例
- 注册中心自身高可用

#### CP vs AP 选型权衡

| 维度         | CP 方案 (etcd/Consul)          | AP 方案 (Eureka/Nacos)         |
| ------------ | ------------------------------ | ------------------------------ |
| **一致性**   | 强一致（Raft）                 | 最终一致（Peer 复制）          |

| **代表**     | K8s(etcd), Consul              | Eureka, Nacos(AP 模式)         |

**推荐**：大多数微服务场景选 AP（返回稍旧的实例列表好过拒绝服务），关键基础设施（如分布式锁）选 CP。

#### 客户端缓存与容错

```python
class ServiceDiscoveryClient:
    def __init__(self):
        self.cache = {}           # 内存缓存
        self.snapshot_file = "/tmp/service_snapshot.json"

    def get_instances(self, service_name):
        # 1. 优先使用内存缓存
        if service_name in self.cache:
            return self.cache[service_name]
        # 2. 从注册中心拉取
        try:
            instances = self.registry.get(service_name)
            self.cache[service_name] = instances
            self.save_snapshot()    # 持久化到本地
            return instances
        except ConnectionError:
            # 3. 注册中心不可用时，降级读本地快照
            return self.load_snapshot(service_name)

    def on_change(self, service_name, instances):
        self.cache[service_name] = instances
        self.save_snapshot()
```

#### 优雅下线（Graceful Shutdown）

```
  下线流程（先注销再停止）:
  1. 收到 SIGTERM 信号
  2. 向注册中心发送 Deregister 请求
  3. 等待一段时间（如 10s），让客户端缓存更新
  4. 停止接收新请求，处理完存量请求
  5. 关闭进程

  反模式: 直接 kill -9 → 注册中心不知道，客户端继续请求失败实例
```

| 维度         | DNS-based                     | API-based                    |

| **延迟**     | DNS TTL 缓存，变更慢          | 实时推送，秒级生效           |
| **负载均衡** | 仅轮询（DNS 轮转）            | 客户端可实现多种策略         |
| **健康检查** | 依赖外部更新 DNS 记录         | 内置健康检查                 |
| **代表**     | CoreDNS(K8s)、Consul DNS      | Nacos、Eureka、Consul HTTP   |

#### 采样策略

| 策略           | 原理                                 | 适用场景             |
| -------------- | ------------------------------------ | -------------------- |
| **头部采样**   | 在入口决定是否采样（概率/规则）      | 简单，性能开销低     |
| **尾部采样**   | 收集完整 Trace 后再决定是否保留      | 可按延迟/错误筛选    |
| **自适应采样** | 根据流量动态调整采样率               | 高低峰期自动适配     |

```
头部采样: 入口决定 → 简单，但可能错过异常请求
  if random() < 0.01:  # 1% 采样率
      sample = True

尾部采样: Collector 收齐后决定 → 能捕获慢请求/错误
  if trace.duration > 500ms or trace.has_error:
      keep = True       # 超过500ms或有错误的全部保留
  else:
      keep = random() < 0.01  # 正常请求1%采样
```
