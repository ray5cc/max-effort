## ⭐ 基础题

### Q1：什么是 CAP 定理？为什么不能同时满足 CAP？

**参考答案**：

CAP 定理：分布式系统最多同时满足一致性（C）、可用性（A）、分区容忍（P）中的两个。由于网络分区（P）不可避免，实际选择只在 CP 或 AP 之间。

**直觉理解**：两个节点网络断开时，一个收到了写请求。如果拒绝写（保 C 丢 A）→ CP；如果接受写但两节点数据不一致（保 A 丢 C）→ AP。

---

### Q2：最终一致性和强一致性的区别？各自适用什么场景？

**参考答案**：

- **强一致性**：写成功后，任何读都能看到最新值。适用：银行转账、库存扣减
- **最终一致性**：写成功后，读可能暂时看到旧值，但最终会一致。适用：社交媒体点赞数、DNS

**大多数互联网应用使用最终一致性**——用户体验上可以接受几秒的延迟，换取更高的可用性和性能。

---

### Q3：什么是 Raft 共识算法？它解决了什么问题？

**参考答案**：

Raft 让多个节点对数据达成一致（即使部分节点故障）。核心机制：
1. **Leader 选举**：通过随机超时和投票选出唯一 Leader
2. **日志复制**：Leader 将操作复制到多数节点后才确认提交
3. **安全性**：日志不够新的节点不能成为 Leader

**与 Paxos 的区别**：Raft 更容易理解和实现（etcd、Consul 都用 Raft）。

---

### Q4：什么是两阶段提交（2PC）？它有什么缺点？

**参考答案**：

2PC 分为准备和提交两个阶段。协调者先问所有参与者"能不能提交"，全票通过才提交。

**缺点**：
1. **阻塞问题**：协调者故障，参与者无限等待
2. **单点故障**：协调者是单点
3. **性能差**：所有参与者锁定资源直到第二阶段完成

**替代方案**：Saga（补偿事务）、TCC（Try-Confirm-Cancel）。

---

### Q5：什么是一致性哈希？为什么比普通取模哈希好？

**参考答案**：

普通哈希 `hash(key) % N`：N 变化时几乎所有 key 重新分配。
一致性哈希：节点和 key 都映射到环上，key 顺时针找最近节点。添加/删除节点只影响相邻区域。

**虚拟节点**解决数据倾斜：一个物理节点映射多个虚拟位置到环上。

---

### Q6：缓存穿透、击穿、雪崩分别是什么？如何解决？

**参考答案**：

| 问题 | 场景 | 解决 |
|------|------|------|
| **穿透** | 查不存在的 key | 布隆过滤器 + 缓存空值 |
| **击穿** | 热点 key 过期 | 互斥锁重建 + 逻辑过期 |
| **雪崩** | 大量 key 同时过期 | 随机过期时间 + 多级缓存 |

---

### Q7：什么是幂等性？为什么分布式系统必须设计幂等接口？

**参考答案**：

幂等 = 执行一次和执行多次效果一样。分布式系统中网络超时可能导致重试，非幂等操作（如"余额 +100"）重试会出错。

**实现方式**：
- 唯一请求 ID（去重表）
- 乐观锁（带版本号更新）
- 将"增量操作"改为"设置操作"（`SET balance=200` 而非 `INCR balance 100`）

---

### Q8：负载均衡有哪些常见策略？各自适用什么场景？

**参考答案**：

- **轮询**：最简单，适合服务器性能一致的场景
- **加权轮询**：按服务器能力分配，性能不一致时使用
- **最少连接**：长连接场景（WebSocket、数据库连接池）
- **IP 哈希**：需要会话粘性时使用（但不利于扩缩容）
- **一致性哈希**：有状态服务（缓存层）

## ⭐⭐ 进阶题

### Q9：Raft 如何处理网络分区恢复后的日志冲突？

**参考答案**：

分区恢复后，旧 Leader（在少数派分区）发现有更高 term 的 Leader，自动退位为 Follower。它的未提交日志会被新 Leader 的日志覆盖（Leader 的 AppendEntries RPC 会强制 Follower 的日志与自己一致）。

**安全性保证**：只有已被多数节点确认的日志才算"已提交"，不会丢失。

---

### Q10：Saga 模式和 TCC 模式分别适用什么场景？

**参考答案**：

| | Saga | TCC |
|---|------|-----|
| **隔离性** | 弱（中间状态可见） | 强（Try 阶段锁定资源） |
| **实现复杂度** | 低（只需补偿逻辑） | 高（三阶段全部实现） |
| **性能** | 高（无资源锁定） | 中（Try 阶段锁定） |
| **适用** | 长流程业务（订单、物流） | 短事务高一致（支付、转账） |

---

### Q11：什么是向量时钟（Vector Clock）？它解决了什么问题？

**参考答案**：

向量时钟用一个计数器向量 [A:2, B:3, C:1] 跟踪每个节点的逻辑时间，可以精确判断两个事件是"因果相关"还是"并发"。

- V1 ≤ V2（V1 每个分量都 ≤ V2）→ V1 发生在 V2 之前
- 否则 → 并发事件（存在冲突需要应用层解决）

**应用**：DynamoDB、Riak 用向量时钟检测数据冲突。

---

### Q12：什么是 Gossip 协议？它的优缺点是什么？

**参考答案**：

Gossip（流言协议）：每个节点随机选几个邻居交换信息，像传谣一样最终所有节点都知道。

**优点**：去中心化、容错性强（没有单点）、可扩展
**缺点**：收敛时间不确定、带宽消耗、最终一致性（非强一致）

**应用**：Cassandra 集群成员管理、Redis Cluster 故障检测、区块链 P2P 网络。

---

### Q13：分布式锁有哪些实现方式？各自的问题是什么？

**参考答案**：

| 实现 | 方式 | 问题 |
|------|------|------|
| Redis | `SET key val NX EX` | 主从切换可能丢锁 |
| Redlock | 多数 Redis 节点加锁 | Martin Kleppmann 的时钟偏移质疑 |
| ZooKeeper | 临时顺序节点 | 性能较低 |
| etcd | 分布式锁 API（基于 Raft） | 需要 etcd 集群 |

**生产建议**：对一致性要求高用 ZooKeeper/etcd；对性能敏感且可容忍偶尔失败用 Redis。

---

### Q14：什么是读写分离？如何处理主从延迟导致的数据不一致？

**参考答案**：

写主库，读从库。主从延迟可能导致"刚写完读不到"。

**解决方案**：
1. **强制读主**：关键业务（如支付后查询）读主库
2. **半同步复制**：至少一个从库确认后才返回写成功
3. **延迟路由**：记录最近写操作时间，若 < 延迟阈值则读主库
4. **GTID 追踪**：写操作返回 GTID，读请求携带 GTID，从库 GTID 不够新则路由到主库

---

### Q15：微服务中的熔断器是如何工作的？

**参考答案**：

三个状态：
- **Closed（关闭）**：正常转发请求，统计错误率
- **Open（打开）**：错误率超过阈值，直接拒绝请求（快速失败）
- **Half-Open（半开）**：等待冷却期后，放行少量探测请求。成功则恢复 Closed，失败则回到 Open

**工具**：Resilience4j（Java）、Hystrix（已停维）、Sentinel（阿里）

---

### Q16：什么是服务网格（Service Mesh）？它和传统 API 网关有什么区别？

**参考答案**：

Service Mesh（如 Istio + Envoy）在每个服务旁部署 Sidecar 代理，透明处理服务间通信（负载均衡、熔断、加密、链路追踪）。

| | API 网关 | Service Mesh |
|---|---------|-------------|
| **位置** | 入口（南北向） | 服务间（东西向） |
| **颗粒度** | 路由级 | 请求级 |
| **侵入性** | 需要配置 | 透明（Sidecar 注入） |
| **典型产品** | Kong, APISIX | Istio, Linkerd |

## ⭐⭐⭐ 高级题

### Q17：设计一个分布式 ID 生成器，要求全局唯一、趋势递增、高性能。

**参考答案**：

**Snowflake 算法**（Twitter）：

```
64 位：1(符号) + 41(时间戳) + 10(机器ID) + 12(序列号)
```

- 41 位时间戳支持 69 年
- 10 位机器 ID 支持 1024 个节点
- 12 位序列号每毫秒每节点可生成 4096 个 ID
- 单节点 QPS：约 400 万/秒

**注意**：时钟回拨问题 → 拒绝生成 + 等待时钟追上。

### Q18：如何设计一个高可用的分布式配置中心？

**参考答案**：

**架构**：
1. **存储层**：etcd（Raft 保证强一致） + 本地文件缓存
2. **读取**：客户端长轮询/Watch 机制，配置变更实时推送
3. **高可用**：etcd 3 节点集群 + 客户端本地缓存（etcd 全挂仍可用旧配置）
4. **灰度发布**：配置按百分比下发，逐步生效

**典型产品**：Nacos、Apollo、Spring Cloud Config。

---

### Q19：Multi-Raft 和单 Raft 有什么区别？为什么 TiKV 使用 Multi-Raft？

**参考答案**：

单 Raft：所有数据由一个 Raft 组管理 → Leader 成为瓶颈。
Multi-Raft：数据分成多个 Region，每个 Region 一个独立的 Raft 组 → 并行复制，无单点瓶颈。

**TiKV 的做法**：数据按 key 范围分为 Region（默认 96MB），每个 Region 由 3 个副本组成一个 Raft 组。Region 过大自动分裂。PD（Placement Driver）负责调度 Region 和 Leader 的位置。

### Q20：什么是"脑裂"（Split Brain）？如何避免？

**参考答案**：

网络分区后，两个分区各自选出一个 Leader，同时接受写请求导致数据不一致。

**解决方案**：
1. **多数派原则**：只有获得多数票（n/2+1）的节点才能成为 Leader → Raft/Paxos 天然避免
2. **Fencing Token**：每个 Leader 持有递增 token，资源侧只接受 token 更大的写请求
3. **STONITH**：确认旧 Leader 真的死了再选新的（"Shoot The Other Node In The Head"）

---

### Q21：CAP 中的"一致性"和 ACID 中的"一致性"有什么区别？

**参考答案**：

完全不同的概念：
- **CAP 的 C**（Linearizability）：所有节点在同一时刻看到相同的数据
- **ACID 的 C**（Consistency）：事务执行后数据库从一个合法状态转移到另一个合法状态（满足约束条件）

CAP 的 C 是分布式系统的一致性模型；ACID 的 C 是应用层的业务逻辑约束。

---

### Q22：什么是 CRDTs（无冲突复制数据类型）？它如何实现无需协调的最终一致性？

**参考答案**：

CRDTs 是一类数据结构，支持并发更新且自动合并无冲突。核心性质：并发操作可交换（顺序不影响最终结果）。

**类型**：
- G-Counter：只增计数器（每个节点独立计数，合并取最大值）
- OR-Set：可添加可删除的集合（每个元素带唯一标签）
- LWW-Register：最后写入胜出（用时间戳或向量时钟）

**应用**：Redis CRDT、协同编辑（Figma、Google Docs）。

## 🎯 场景题

### Q23：设计一个支持百万 QPS 的短链系统。

**参考答案**：

1. **ID 生成**：Snowflake → Base62 编码（7 位字符可表示 3.5 万亿个短链）
2. **存储**：写入时先写 MySQL（持久化）+ Redis（缓存热点短链）
3. **读取**：Nginx 层 → Redis 缓存查找 → MySQL 兜底 → 301 重定向
4. **扩展**：按短链 hash 分库分表 + 只读从库 + 本地缓存（Caffeine）

**关键决策**：301（永久重定向，浏览器缓存，减轻服务压力）vs 302（临时重定向，方便统计点击数据）。

### Q24：你的电商系统在大促期间数据库扛不住了，如何做紧急容量扩展？

**参考答案**：

**短期（分钟级）**：
1. 开启只读从库接管读请求
2. 增加 Redis 缓存层，热点数据缓存
3. 限流降级非核心功能（评论、推荐系统）

**中期（小时级）**：
4. 增加数据库从库（读扩展）
5. 消息队列削峰（下单请求入队异步处理）

**长期（天/周级）**：
6. 数据库分库分表
7. CQRS 读写分离架构

### Q25：设计一个全球分布的聊天系统（类似 WhatsApp），需要考虑哪些分布式问题？

**参考答案**：

1. **消息路由**：按 chat_id 一致性哈希分配到服务器
2. **消息有序性**：每个会话内用 Lamport 时间戳排序；跨会话无需全局有序
3. **离线消息**：存入 Cassandra（AP 系统，高可用）；上线后推送
4. **多端同步**：向量时钟判断消息已读状态
5. **地理分布**：多 Region 部署，每条消息异步复制到接收方所在 Region
6. **端到端加密**：Signal Protocol，服务器无法解密消息内容

**关键取舍**：选择 AP（消息可能短暂乱序但不丢），而非 CP（用户等待超时体验更差）。
