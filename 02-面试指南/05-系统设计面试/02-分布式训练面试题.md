### Q1：训练一个 7B 参数模型需要多少显存？为什么远超 7B × 2 bytes = 14GB？

<details>
<summary>参考答案</summary>

使用 Adam 优化器 + 混合精度训练时，每个参数需要 **16 字节**，远超 FP16 权重本身的 2 字节：

| 状态            | 精度 | 字节/参数 | 说明                         |
| --------------- | ---- | --------- | ---------------------------- |
| FP16 模型权重   | FP16 | 2         | 前向/反向计算使用             |
| FP16 梯度       | FP16 | 2         | 反向传播产生                 |
| FP32 主权重副本 | FP32 | 4         | 优化器更新后复制回 FP16      |
| Adam 一阶矩 m   | FP32 | 4         | 梯度的指数移动平均           |
| Adam 二阶矩 v   | FP32 | 4         | 梯度平方的指数移动平均       |
| **合计**        | —    | **16**    |                              |

**通用公式**（Ψ 为参数量）：

```
模型状态显存 = Ψ × (2 + 2 + K)  字节
  其中 K = 优化器状态字节/参数
  Adam: K = 4(FP32主权重) + 4(m) + 4(v) = 12
  SGD:  K = 4(FP32主权重) = 4
```

**7B 模型具体计算**：

```
模型状态：7×10⁹ × 16 = 112 GB
激活值（batch=1, seq=2048, hidden=4096, 32层）：≈ 4-8 GB
临时缓冲区：≈ 2 GB
─────────────────────
总计：≈ 118-122 GB
```

> 因此一张 80GB A100 **无法**放下 7B 模型的完整训练状态，需要至少 2 张卡（使用 ZeRO Stage 2+）或启用 CPU Offload。

**注意**：推理只需要模型权重，7B × 2 bytes = 14 GB（FP16），一张卡绑绑有余。训练和推理的显存需求相差约 8 倍。

</details>

### Q2：ZeRO 的三个阶段分别对什么进行分片？每卡显存公式是什么？

<details>
<summary>参考答案</summary>

ZeRO（Zero Redundancy Optimizer）的核心思想是**消除数据并行中的冗余存储**。三个阶段逐步扩大分片范围：

| 阶段    | 分片内容           | 每卡显存（字节/参数）          | 通信量         |
| ------- | ------------------ | ------------------------------ | -------------- |
| Stage 1 | 优化器状态         | 2(权重) + 2(梯度) + 12/N(优化器) = 4 + 12/N | 2Ψ（同 DDP）  |
| Stage 2 | + 梯度             | 2(权重) + (2+12)/N = 2 + 14/N               | 2Ψ（同 DDP）  |
| Stage 3 | + 参数             | (2+2+12)/N = 16/N                            | 3Ψ（含预取）  |

**显存公式推导**（以 Stage 1 为例，N 张卡）：

```
总模型状态 = 16Ψ 字节
Stage 1 只分片优化器状态（12Ψ / N），权重和梯度完整保留（4Ψ）
每卡 = 4Ψ + 12Ψ/N 字节
```

**70B 模型实际计算**（N=8）：

```
Stage 1: 70B × (4 + 12/8) = 70B × 5.5 = 385 GB → 每卡 48.1 GB
Stage 2: 70B × (2 + 14/8) = 70B × 3.75 = 262 GB → 每卡 32.8 GB
Stage 3: 70B × 16/8 = 70B × 2 = 140 GB → 每卡 17.5 GB
```

**通信量分析**：

- **Stage 1/2**：梯度同步通过 Reduce-Scatter + All-Gather 完成，总通信量 = 2Ψ，与标准 DDP 的 All-Reduce 完全相同
- **Stage 3**：额外需要在前向/反向时 All-Gather 参数（每层两次：前向一次、反向一次），总通信量约 3Ψ
- **Stage 3 + Prefetch**：通过 `stage3_prefetch_bucket_size` 异步预取下一层参数，可将通信与计算重叠，有效隐藏延迟

> **选型建议**：Stage 1 首选（通信零开销）；显存不足时升 Stage 2；再不够用 Stage 3（但需注意 1.5× 通信代价）。

</details>

### Q3：DDP 的核心缺陷是什么？ZeRO 如何解决？

<details>
<summary>参考答案</summary>

**DDP（DistributedDataParallel）的核心缺陷**：每张 GPU 保存**完整的一份**模型状态（权重 + 梯度 + 优化器状态），存在严重的内存冗余。

```
DDP 内存布局（N 张卡）：

GPU 0: [完整权重 2Ψ] [完整梯度 2Ψ] [完整优化器 12Ψ] = 16Ψ
GPU 1: [完整权重 2Ψ] [完整梯度 2Ψ] [完整优化器 12Ψ] = 16Ψ
  ...
GPU N: [完整权重 2Ψ] [完整梯度 2Ψ] [完整优化器 12Ψ] = 16Ψ

总显存 = N × 16Ψ，冗余率 = (N-1)/N
N=8 时，87.5% 的显存被浪费！
```

**ZeRO 的解决方案**：每张 GPU 只存 1/N 自己负责更新的那部分状态，不需要的部分通过通信按需获取。

```
ZeRO Stage 3 内存布局（N 张卡）：

GPU 0: [权重分片 2Ψ/N] [梯度分片 2Ψ/N] [优化器分片 12Ψ/N] = 16Ψ/N
GPU 1: [权重分片 2Ψ/N] [梯度分片 2Ψ/N] [优化器分片 12Ψ/N] = 16Ψ/N
  ...
GPU N: [权重分片 2Ψ/N] [梯度分片 2Ψ/N] [优化器分片 12Ψ/N] = 16Ψ/N

总显存 = N × 16Ψ/N = 16Ψ，零冗余！
```

**关键洞察**：ZeRO Stage 1/2 的通信量与 DDP 完全相同（都是 ~2Ψ），并没有增加通信开销。它本质上是将 DDP 的 All-Reduce 拆解为 Reduce-Scatter + All-Gather，利用两步之间的"间隙"释放不需要的内存。

</details>

### Q4：DeepSpeed 初始化时，`deepspeed.initialize()` 做了哪些工作？

<details>
<summary>参考答案</summary>

`deepspeed.initialize()` 是 DeepSpeed 的核心入口，内部执行以下工作：

```python
model_engine, optimizer, _, lr_scheduler = deepspeed.initialize(
    model=model,
    optimizer=optimizer,        # 可选，DeepSpeed 会自动创建
    config="ds_config.json",
    model_parameters=model.parameters()
)
```

**初始化流程**：

1. **分布式环境初始化**：自动调用 `dist.init_process_group("nccl")`（如果尚未初始化），设置 `local_rank`、`world_size`
2. **参数分片**：根据 ds_config 中的 ZeRO Stage，将模型参数按层/桶进行分片分配
3. **优化器包装**：将普通优化器包装为 `DeepSpeedZeroOptimizer`（含梯度分片、通信调度逻辑）
4. **混合精度设置**：配置 FP16/BF16 Loss Scaler（动态损失缩放器）
5. **通信优化**：设置梯度桶（bucket）大小、通信重叠参数、预取策略
6. **Activation Checkpointing**：如配置启用，自动对模型层注入检查点逻辑
7. **返回 Engine**：返回 `DeepSpeedEngine` 对象，提供统一的 `.backward()` 和 `.step()` 接口

**DeepSpeedEngine 的训练循环**：

```python
for batch in dataloader:
    loss = model_engine(batch)         # 前向（自动处理参数 All-Gather）
    model_engine.backward(loss)        # 反向（自动处理梯度分片 + Loss Scaling）
    model_engine.step()                # 优化器步骤 + 梯度清零 + LR调度
```

> 相比原生 PyTorch，DeepSpeed 将 `loss.backward()` + `optimizer.step()` + `scheduler.step()` + `optimizer.zero_grad()` 四步合一。

</details>

### Q5：什么是损失缩放（Loss Scaling）？为什么 BF16 不需要它？

<details>
<summary>参考答案</summary>

**问题背景**：FP16 的最小正规数约 6×10⁻⁸，训练后期梯度值可能远小于此（如 10⁻¹²），导致**下溢（underflow）**变成 0，训练停滞。

**Loss Scaling 机制**：

```
前向：loss_scaled = loss × scale_factor     (如 scale_factor = 65536)
反向：grad_scaled = backward(loss_scaled)   (梯度放大 65536 倍，落入 FP16 范围)
更新：grad_real = grad_scaled / scale_factor (除回去，得到真实梯度)
优化器在 FP32 精度上用 grad_real 更新主权重
```

**动态 Loss Scaling**：DeepSpeed 默认使用动态缩放——初始 scale 很大（如 2¹⁶），如果反向传播产生 NaN/Inf，则将 scale 减半并跳过这步更新；连续 N 步无溢出则将 scale 翻倍。

**BF16 为什么不需要 Loss Scaling？**

| 格式 | 符号位 | 指数位 | 尾数位 | 动态范围       | 精度         |
|------|--------|--------|--------|----------------|--------------|
| FP32 | 1      | 8      | 23     | ~10⁻³⁸ – 10³⁸ | ~7位有效数字 |
| FP16 | 1      | 5      | 10     | ~10⁻⁸ – 65504 | ~3位有效数字 |
| BF16 | 1      | 8      | 7      | ~10⁻³⁸ – 10³⁸ | ~2位有效数字 |

BF16 的指数位数（8位）与 FP32 相同，**动态范围等同于 FP32**（~10⁻³⁸），不存在下溢问题。代价是精度比 FP16 更低（7 vs 10 尾数位），但实践表明对训练收敛影响很小。

**FP8（H100+ 支持）**：

| FP8 格式 | 符号位 | 指数位 | 尾数位 | 用途     |
|----------|--------|--------|--------|----------|
| E4M3     | 1      | 4      | 3      | 前向计算 |
| E5M2     | 1      | 5      | 2      | 反向传播 |

H100 的 Transformer Engine 支持 FP8 自动混合精度：前向用 E4M3（更高精度），反向用 E5M2（更大动态范围防溢出），配合 per-tensor scaling 自动管理精度。

</details>

### Q6：如何将现有 PyTorch DDP 训练代码迁移到 DeepSpeed？需要改哪几行？

<details>
<summary>参考答案</summary>

**主要改 4 处**：

```python
# ===== 原始 DDP 代码 =====
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP

dist.init_process_group("nccl")                        # ❌ 删除
model = DDP(model.cuda(), device_ids=[local_rank])     # ❌ 删除
optimizer = AdamW(model.parameters(), lr=1e-4)

for batch in dataloader:
    loss = model(batch)
    loss.backward()                                     # ❌ 替换
    optimizer.step()                                    # ❌ 替换
    scheduler.step()                                    # ❌ 替换
    optimizer.zero_grad()                               # ❌ 替换

# ===== 迁移后 DeepSpeed 代码 =====
import deepspeed

model_engine, optimizer, _, lr_scheduler = deepspeed.initialize(
    model=model,
    config="ds_config.json",
    model_parameters=model.parameters()
)

for batch in dataloader:
    loss = model_engine(batch)
    model_engine.backward(loss)                         # ✅ 一行搞定
    model_engine.step()                                 # ✅ 一行搞定
```

新增 `ds_config.json`，启动命令改为 `deepspeed --num_gpus=8 train.py`。

**HuggingFace Trainer 集成（更简单）**：

如果使用 HuggingFace Trainer，只需在 `TrainingArguments` 中添加一个参数：

```python
training_args = TrainingArguments(
    output_dir="./output",
    per_device_train_batch_size=4,
    bf16=True,
    deepspeed="ds_config.json",  # 就这一行！
)
trainer = Trainer(model=model, args=training_args, ...)
trainer.train()
```

HuggingFace Trainer 会自动处理 DeepSpeed 初始化、checkpoint 保存和分布式设置。`ds_config.json` 中的 `train_batch_size`、`optimizer`、`scheduler` 等字段可以设为 `"auto"` 来继承 Trainer 的配置。

</details>

### Q7：`ds_config.json` 中的 `gradient_accumulation_steps` 和 `train_micro_batch_size_per_gpu` 如何影响全局 batch size？

<details>
<summary>参考答案</summary>

**核心公式**：

```
全局 batch size = train_micro_batch_size_per_gpu × gradient_accumulation_steps × GPU 数量
```

**示例**：

```
micro_batch = 4
gradient_accumulation_steps = 8
GPU 数量 = 8

全局 batch size = 4 × 8 × 8 = 256
```

**梯度累积的意义**：可以在不增加显存的前提下增大等效 global batch size。显存占用仅受 `micro_batch_size` 影响，因为每次只有一个 micro-batch 在 GPU 上前向/反向。

```json
{
  "train_micro_batch_size_per_gpu": 4,
  "gradient_accumulation_steps": 8,
  "train_batch_size": "auto"
}
```

**注意事项**：

- `train_batch_size` 可设为 `"auto"` 让 DeepSpeed 自动计算，也可显式指定（必须等于公式值，否则报错）
- 梯度累积期间**不进行梯度同步**（通信），只在最后一个 micro-step 做 All-Reduce/Reduce-Scatter，减少通信开销
- 过大的 global batch 可能需要配合学习率 warmup 和 linear scaling rule（`lr ∝ batch_size`）

</details>

### Q8：数据并行（DP）、分布式数据并行（DDP）和完全分片数据并行（FSDP）有什么区别？

<details>
<summary>参考答案</summary>

三者是数据并行技术的演进路线：

```
DP (DataParallel)
  │  单进程多线程，GIL 瓶颈
  ▼
DDP (DistributedDataParallel)
  │  多进程，All-Reduce 同步梯度
  ▼
FSDP (FullyShardedDataParallel)
     多进程 + 参数分片，≈ ZeRO Stage 3
```

**详细对比**：

| 维度         | DP                | DDP                    | FSDP                        |
| ------------ | ----------------- | ---------------------- | --------------------------- |
| 进程模型     | 单进程多线程      | 多进程                 | 多进程                      |
| 通信方式     | 主 GPU 汇总       | NCCL All-Reduce        | NCCL Reduce-Scatter + All-Gather |
| 显存效率     | 差（主 GPU 瓶颈） | 差（完整冗余）         | 优（参数分片）              |
| 扩展性       | 单机              | 多机多卡               | 多机多卡                    |
| GIL 影响     | 严重              | 无                     | 无                          |
| 梯度同步     | 主 GPU 收集       | 桶化异步 All-Reduce    | Reduce-Scatter 到分片       |
| 等价 ZeRO    | —                 | —                      | ≈ ZeRO Stage 3              |

**显存公式对比**（Ψ 为参数量，N 张卡）：

```
DP  每卡显存: 16Ψ（主 GPU） / 2Ψ+临时（工作 GPU）
DDP 每卡显存: 16Ψ（完整冗余）
FSDP 每卡显存: 16Ψ/N（完全分片）
```

**DP 的 GIL 问题**：DP 使用 Python 多线程（`torch.nn.DataParallel`），受 GIL 限制，主 GPU 成为瓶颈——它要负责收集所有 GPU 的输出、计算 loss、分发梯度。实际上主 GPU 的利用率常超 90% 而其他 GPU 空闲等待。

**FSDP 示例代码**：

```python
from torch.distributed.fsdp import FullyShardedDataParallel as FSDP
from torch.distributed.fsdp import ShardingStrategy

model = FSDP(
    model,
    sharding_strategy=ShardingStrategy.FULL_SHARD,  # ≈ ZeRO Stage 3
    # ShardingStrategy.SHARD_GRAD_OP  ≈ ZeRO Stage 2
    # ShardingStrategy.NO_SHARD       ≈ DDP
    mixed_precision=MixedPrecision(
        param_dtype=torch.bfloat16,
        reduce_dtype=torch.bfloat16,
    ),
    auto_wrap_policy=size_based_auto_wrap_policy,
)
```

> **结论**：新项目直接用 DDP（模型放得下）或 FSDP（放不下）。`torch.nn.DataParallel`（DP）已不推荐。

</details>

### Q9：什么是张量并行（Tensor Parallelism）？Megatron-LM 如何切分 Transformer 层？

<details>
<summary>参考答案</summary>

**张量并行（Tensor Parallelism, TP）** 是将单个层的参数矩阵切分到多张 GPU 上，每张 GPU 计算部分结果后通过通信合并。与 ZeRO 的"按需重建完整参数"不同，TP 是"每张卡始终只持有部分参数并直接计算"。

**Megatron-LM 的 MLP 切分**（以 2 GPU 为例）：

```
                    原始 MLP: Y = GeLU(XA) · B

┌──────────────────── GPU 0 ────────────────────┐
│  X ──→ [A 的上半列] ──→ GeLU ──→ [B 的上半行] ──→ Y₀  │
└───────────────────────────────────────────────┘
                                                    ╲
                                              All-Reduce (sum)
                                                    ╱
┌──────────────────── GPU 1 ────────────────────┐
│  X ──→ [A 的下半列] ──→ GeLU ──→ [B 的下半行] ──→ Y₁  │
└───────────────────────────────────────────────┘

切分方式：
  第一个线性层 A: Column Parallel（沿输出维度切分）
  第二个线性层 B: Row Parallel（沿输入维度切分）
```

**为什么 Column → Row？**

- Column Parallel 切分 A 的列，每张 GPU 得到完整的输入 X，计算 XA_i 得到部分输出
- GeLU 是逐元素操作，可以直接在部分输出上执行（不需要通信！）
- Row Parallel 切分 B 的行，每张 GPU 用自己的部分结果乘 B_i，得到部分最终输出
- 最后一次 All-Reduce 求和得到完整输出

**Self-Attention 的切分**类似：Q、K、V 矩阵按 Column Parallel 切分（等价于切分注意力头），输出投影按 Row Parallel 切分。

**f/g 算子**：

```
f: 前向 = identity(无操作), 反向 = All-Reduce
g: 前向 = All-Reduce,       反向 = identity(无操作)

一个 Transformer 层中：
  前向: f → Column Linear → GeLU → Row Linear → g
  恰好 2 次 All-Reduce（g 在前向，f 在反向）
```

**TP 的局限**：每个 Transformer 层内都需要 All-Reduce 通信，因此**强烈依赖高带宽互连**（NVLink 900 GB/s），不适合跨节点（InfiniBand 200-400 Gb/s）。通常 TP degree ≤ 单节点 GPU 数量。

</details>

### Q10：BF16、FP16、FP8 三种精度的区别和适用场景？

<details>
<summary>参考答案</summary>

**位布局对比**：

```
FP32:  [1 符号] [8 指数] [23 尾数]  → 总 32 位
FP16:  [1 符号] [5 指数] [10 尾数]  → 总 16 位
BF16:  [1 符号] [8 指数] [7  尾数]  → 总 16 位
FP8 E4M3: [1]   [4 指数] [3  尾数]  → 总 8 位
FP8 E5M2: [1]   [5 指数] [2  尾数]  → 总 8 位
```

**关键指标对比**：

| 格式    | 动态范围          | 有效精度    | 吞吐倍数(vs FP32) | Loss Scaling |
|---------|-------------------|-------------|--------------------| -------------|
| FP32    | ±3.4×10³⁸        | ~7 位十进制 | 1×                 | 不需要       |
| FP16    | ±65504            | ~3 位十进制 | 2×                 | **需要**     |
| BF16    | ±3.4×10³⁸        | ~2 位十进制 | 2×                 | 不需要       |
| FP8 E4M3| ±448              | ~1.5 位     | 4× (H100)         | per-tensor   |
| FP8 E5M2| ±57344            | ~1 位       | 4× (H100)         | per-tensor   |

**适用场景**：

1. **FP16**：适用于 V100（不支持 BF16）；需配合动态 Loss Scaling；对大 LLM 训练可能出现数值不稳定
2. **BF16**：A100/H100 训练首选；动态范围同 FP32，无需 Loss Scaling；精度够用；LLM 训练标配
3. **FP8 E4M3**：用于前向计算（需要更高精度表示激活值）；H100 Transformer Engine 自动管理
4. **FP8 E5M2**：用于反向传播（需要更大动态范围表示梯度）；配合 per-tensor scaling factor

**H100 FP8 Transformer Engine**：

```python
import transformer_engine.pytorch as te

# 替换 nn.Linear → te.Linear，自动管理 FP8 量化/反量化
model = te.TransformerLayer(
    hidden_size=4096,
    ffn_hidden_size=11008,
    num_attention_heads=32,
)

with te.fp8_autocast(enabled=True):
    output = model(input)
# 自动：前向用 E4M3，反向用 E5M2，per-tensor scaling
```

> **选型建议**：A100 用 BF16；H100 用 FP8（吞吐翻倍，精度损失可控）；V100 用 FP16 + Loss Scaling。

</details>

### Q11：ZeRO 底层使用什么通信原语？与 DDP 的 All-Reduce 有何区别？

<details>
<summary>参考答案</summary>

ZeRO 将 DDP 的 All-Reduce 拆分为两个独立操作：**Reduce-Scatter + All-Gather**。

```
DDP All-Reduce（一步完成）：
  所有 GPU 同时发送梯度 → 求和 → 每张 GPU 得到完整的求和结果
  通信量 = 2Ψ（每个参数发一次、收一次）

ZeRO Reduce-Scatter + All-Gather（两步）：
  ① Reduce-Scatter：所有 GPU 贡献梯度 → 每张 GPU 只收到自己负责的 1/N 求和结果
     通信量 = Ψ × (N-1)/N ≈ Ψ
  ② All-Gather：每张 GPU 广播自己的参数分片 → 所有 GPU 得到完整参数
     通信量 = Ψ × (N-1)/N ≈ Ψ
  总通信量 ≈ 2Ψ（与 All-Reduce 相同！）
```

**关键差异**：ZeRO 在 Reduce-Scatter 后**不立即**执行 All-Gather。它利用这个间隙完成以下工作：

```
时间线：
  Reduce-Scatter(梯度)   →  优化器更新(1/N参数)  →  All-Gather(更新后的参数)
  ↑ 只保留 1/N 梯度         ↑ 只更新自己负责的部分   ↑ 广播更新后的参数
```

ZeRO Stage 1 只在 Reduce-Scatter 后释放优化器冗余；Stage 2 连梯度也释放；Stage 3 连参数也释放，在前向/反向时才临时 All-Gather 重建。

**NCCL 实现**：这些原语在 NCCL 中对应 `ncclReduceScatter()` 和 `ncclAllGather()`，底层在 NVLink/InfiniBand 上通过 Ring 或 Tree 拓扑实现。

</details>

### Q12：ZeRO Stage 3 的前向传播是如何工作的？参数怎样按需重建？

<details>
<summary>参考答案</summary>

ZeRO Stage 3 下，每张 GPU 只保存 1/N 的参数分片。前向传播时按层执行"收集-计算-释放"循环：

```
                    ZeRO Stage 3 前向传播流程

Layer 0:
  ┌─────────┐   All-Gather    ┌──────────────┐   计算    ┌─────────┐
  │GPU0: P₀₀│ ──────────────→ │GPU0: P₀ 完整 │ ───────→ │ 激活值  │
  │GPU1: P₀₁│   (收集所有     │GPU1: P₀ 完整 │          │  A₀     │
  │GPU2: P₀₂│    GPU 的分片)  │GPU2: P₀ 完整 │          └─────────┘
  │GPU3: P₀₃│                 │GPU3: P₀ 完整 │               │
  └─────────┘                 └──────┬───────┘               │
                                     │ 释放完整参数            │
                                     ▼ (只保留自己的分片)      │
Layer 1:                                                      │
  ┌─────────┐   All-Gather    ┌──────────────┐   计算    ┌─────────┐
  │GPU0: P₁₀│ ──────────────→ │GPU0: P₁ 完整 │ ───────→ │ 激活值  │
  │GPU1: P₁₁│   (同时预取     │GPU1: P₁ 完整 │          │  A₁     │
  │GPU2: P₁₂│    Layer 2)    │GPU2: P₁ 完整 │          └─────────┘
  │GPU3: P₁₃│                 │GPU3: P₁ 完整 │
  └─────────┘                 └──────┬───────┘
                                     │ 释放
                                     ▼
  ... 逐层重复 ...
```

**关键优化——预取（Prefetch）**：

在计算第 i 层时，同时 All-Gather 第 i+1 层的参数，使通信与计算重叠：

```
时间 →
GPU 计算: [  Layer 0 计算  ] [  Layer 1 计算  ] [  Layer 2 计算  ]
NCCL通信:   [AG Layer 1]      [AG Layer 2]      [AG Layer 3]
           ↑ 计算与通信重叠
```

通过 `"stage3_prefetch_bucket_size": 5e7` 控制预取粒度。值越大预取越激进、延迟隐藏越好，但峰值显存越高。

**反向传播**方向相反，对每层执行：All-Gather 参数 → 计算梯度 → Reduce-Scatter 梯度 → 释放完整参数。

</details>

### Q13：Activation Checkpointing（梯度检查点）的原理和代价是什么？

<details>
<summary>参考答案</summary>

**问题**：正常训练中，前向传播的所有中间激活值（用于反向传播计算梯度）都保存在显存中。对于大 batch 和长序列，激活值显存可能高达几十 GB。

**激活值显存估算**（Transformer）：

```
每层激活值 ≈ 2 × batch × seq_len × hidden_size × 2 bytes (FP16)
           + attention scores: batch × heads × seq_len² × 2 bytes

LLaMA-7B (hidden=4096, 32层, batch=4, seq=4096):
  每层 ≈ 2 × 4 × 4096 × 4096 × 2 ≈ 256 MB
  Attention ≈ 4 × 32 × 4096² × 2 ≈ 4 GB
  32层总计 ≈ 32 × (0.25 + 4) ≈ 136 GB  ← 激活值远超模型本身！
```

**Activation Checkpointing 策略**：只在选定的检查点边界保存激活，其余的反向传播时重新计算。

```
正常训练（保存所有激活）：
  前向: L₀ → [A₀] → L₁ → [A₁] → L₂ → [A₂] → L₃ → [A₃] → loss
  反向: 用 A₃ 算 grad₃, 用 A₂ 算 grad₂, ... (无需重算)

Activation Checkpointing（只保存检查点）：
  前向: L₀ → [A₀✓] → L₁ → [丢弃] → L₂ → [A₂✓] → L₃ → [丢弃] → loss
  反向: 从 A₂ 重算 L₃ 的激活 → 算 grad₃
        用 A₂ 算 grad₂
        从 A₀ 重算 L₁ 的激活 → 算 grad₁
        用 A₀ 算 grad₀
```

**代价分析**：

| 指标     | 无 Checkpointing | 全量 Checkpointing | 选择性 Checkpointing |
|----------|-------------------|--------------------|-----------------------|
| 激活显存 | 100%              | ~1/√L (L=层数)     | 可调                 |
| 计算量   | 1×                | ~1.33× (额外前向)  | 1.1-1.2×             |
| 实现复杂度| 无               | 低                 | 中                   |

**DeepSpeed 启用方式**：

```python
import deepspeed
deepspeed.checkpointing.configure(
    mp_size=1,                    # 模型并行度
    partition_activations=True,   # 激活值也分片到多 GPU
    contiguous_checkpointing=True # 连续内存存储
)

# 或在 ds_config.json 中：
{
  "activation_checkpointing": {
    "partition_activations": true,
    "contiguous_memory_optimization": true,
    "number_checkpoints": null  // null = 每层都检查点
  }
}
```

> **何时启用**：当激活值显存 > 总显存的 20-30%，或使用长序列（seq_len > 2048）时启用。

</details>

### Q14：ZeRO-Infinity 相比 ZeRO Stage 3 的核心差异是什么？

<details>
<summary>参考答案</summary>

ZeRO Stage 3 将模型状态分片到 GPU 显存内；ZeRO-Infinity 进一步将参数和优化器状态**卸载（Offload）**到 CPU RAM 甚至 NVMe SSD，形成三级存储层次：

```
             ZeRO-Infinity 存储层次

┌─────────────────────────────────────────────────┐
│ GPU HBM (80GB)    │ 带宽: ~2 TB/s              │
│  └─ 当前层参数     │ 角色: 实际计算              │
│  └─ 当前层梯度     │                            │
│  └─ 激活值         │                            │
├─────────────────────────────────────────────────┤
│ CPU RAM (512GB+)  │ 带宽: ~32 GB/s (PCIe 4.0)  │
│  └─ 优化器状态     │ 角色: 优化器更新 (AVX512)   │
│  └─ 参数分片       │ 角色: 参数暂存              │
├─────────────────────────────────────────────────┤
│ NVMe SSD (TB级)   │ 带宽: ~6 GB/s              │
│  └─ 冷数据参数     │ 角色: 超大模型参数存储       │
│  └─ 冷优化器状态   │                            │
└─────────────────────────────────────────────────┘
```

**核心技术**：

1. **异步预取**：在 GPU 计算第 i 层时，从 CPU/NVMe 预取第 i+1 层参数到 GPU，隐藏传输延迟
2. **CPU Adam**：优化器更新在 CPU 上执行（利用 AVX512 SIMD 并行），结果再传回 GPU
3. **Pin Memory**：使用 `pin_memory=true` 页锁定内存，提升 PCIe DMA 传输速度
4. **NVMe 直读**：使用 GDS（GPUDirect Storage）跳过 CPU 缓存，直接 NVMe → GPU

**配置示例**：

```json
{
  "zero_optimization": {
    "stage": 3,
    "offload_param": {
      "device": "nvme",
      "nvme_path": "/local_nvme",
      "pin_memory": true,
      "buffer_count": 5
    },
    "offload_optimizer": {
      "device": "cpu",
      "pin_memory": true
    }
  }
}
```

**代价**：吞吐量显著下降（~30-70%），主要瓶颈在 PCIe/NVMe 带宽。适用场景：GPU 显存极度不足，且训练速度不是首要考量（如学术研究、小团队训练超大模型）。

</details>

### Q15：DeepSpeed Pipeline Parallelism 中的"气泡"问题是什么？如何用 1F1B 调度缓解？

<details>
<summary>参考答案</summary>

**气泡（Bubble）问题**：流水线并行将模型按层切分到不同 GPU Stage。朴素调度（GPipe 风格）中，Stage N 必须等待 Stage N-1 的输出，导致大量空闲时间。

**朴素调度（GPipe）气泡图**（4 Stage, 4 micro-batch）：

```
时间 →
Stage 0: [F₀][F₁][F₂][F₃][ idle  ][ idle  ][ idle  ][B₃][B₂][B₁][B₀]
Stage 1:     [F₀][F₁][F₂][F₃][ idle  ][ idle  ][B₃][B₂][B₁][B₀]
Stage 2:         [F₀][F₁][F₂][F₃][ idle  ][B₃][B₂][B₁][B₀]
Stage 3:             [F₀][F₁][F₂][F₃][B₃][B₂][B₁][B₀]

F=前向, B=反向, idle=气泡
气泡比例 = (K-1) / (2×M) ≈ 37.5%（K=4, M=4）
```

**1F1B（One-Forward-One-Backward）调度**：

```
时间 →
Stage 0: [F₀][F₁][F₂][F₃][B₀][B₁][B₂][B₃]
Stage 1:     [F₀][F₁][F₂][B₀][F₃][B₁][B₂][B₃]
Stage 2:         [F₀][F₁][B₀][F₂][B₁][F₃][B₂][B₃]
Stage 3:             [F₀][B₀][F₁][B₁][F₂][B₂][F₃][B₃]

气泡比例 ≈ (K-1) / (M + K - 1) ≈ 23%（K=4, M=4）
```

核心思想：一旦最后一个 Stage 完成第一个 micro-batch 的前向，立即开始其反向传播，使前向和反向在流水线中"交织"。

**气泡率公式**：

```
GPipe:              bubble = (K - 1) / (2 × M)
1F1B (non-interl.): bubble = (K - 1) / (M + K - 1)
1F1B (interleaved):  bubble = (K - 1) / (M × V + K - 1)  (V=虚拟stage数)
```

其中 K = Stage 数，M = micro-batch 数，V = interleaved 的虚拟阶段数（Megatron-LM 特性）。

**Megatron-LM 的 Interleaved 1F1B**：每个 GPU 负责多个不连续的层（虚拟 Stage），进一步减小气泡。例如 4 GPU 8 层时，GPU 0 处理 Layer 0 和 Layer 4，GPU 1 处理 Layer 1 和 Layer 5。

> **减少气泡的实践**：增大 M（更多 micro-batch）是最有效的方法；使用 interleaved schedule（V>1）可进一步压缩；前沿研究如 Zero-Bubble Pipeline 可将气泡趋近于 0。

</details>

### Q16：ZeRO Stage 3 保存 Checkpoint 有什么注意事项？

<details>
<summary>参考答案</summary>

ZeRO Stage 3 下每张 GPU 只有 1/N 的参数分片，直接 `model.state_dict()` 得到的是**分片**而非完整参数，无法直接用于推理或迁移。

**三种保存方式**：

**方式一：DeepSpeed 原生格式（恢复训练用）**

```python
model_engine.save_checkpoint(save_dir, tag="step_1000")
# 保存结构：
# save_dir/step_1000/
#   ├── mp_rank_00_model_states.pt  (分片参数)
#   ├── zero_pp_rank_0_mp_rank_00_optim_states.pt
#   └── ...
```

每张 GPU 独立保存自己的分片，恢复时必须使用**相同数量的 GPU**。

**方式二：合并为完整模型（推理/部署用）**

```python
# 在 ds_config 中设置：
{ "stage3_gather_16bit_weights_on_model_save": true }

# 保存时自动 All-Gather 合并
model_engine.module.save_pretrained("output_dir")
```

注意：All-Gather 需要每张 GPU 临时持有完整参数，峰值显存 = 分片显存 + 完整模型大小。

**方式三：离线合并（后处理）**

```python
from deepspeed.utils.zero_to_fp32 import get_fp32_state_dict_from_zero_checkpoint

state_dict = get_fp32_state_dict_from_zero_checkpoint("checkpoint_dir")
model.load_state_dict(state_dict)
model.save_pretrained("merged_model")
```

此方法在单独的脚本中运行，不需要多 GPU 环境。

> **最佳实践**：训练过程中用方式一（快速、分布式写入），训练结束用方式三离线合并。避免在训练循环中频繁使用方式二（All-Gather 代价高）。

</details>

### Q17：Ring AllReduce 和 Tree AllReduce 的区别？NCCL 如何选择拓扑？

<details>
<summary>参考答案</summary>

**Ring AllReduce**：

```
   GPU 0 ──→ GPU 1
    ↑            │
    │            ▼
   GPU 3 ←── GPU 2

N 个 GPU 组成环，数据分 N 块：
  阶段 1 (Reduce-Scatter): 每步每 GPU 发送 1/N 数据给邻居，N-1 步完成
  阶段 2 (All-Gather):     每步每 GPU 发送 1/N 数据给邻居，N-1 步完成

通信量: 2 × (N-1)/N × D ≈ 2D（D 为数据总量）
延迟:   2 × (N-1) × α（α 为单步延迟）
```

**Tree AllReduce**：

```
        GPU 0 (root)
       /            \
    GPU 1          GPU 2
    /                  \
  GPU 3              GPU 4

阶段 1 (Reduce): 叶子节点向根发送，逐级求和，log₂(N) 步
阶段 2 (Broadcast): 根向叶子广播结果，log₂(N) 步

通信量: 2 × D（每条边传输完整数据）
延迟:   2 × log₂(N) × α
```

**对比**：

| 指标     | Ring AllReduce           | Tree AllReduce          |
|----------|--------------------------|-------------------------|
| 通信量   | 2×(N-1)/N × D ≈ 2D     | 2D（但树根带宽瓶颈）   |
| 延迟     | O(N) × α                | O(log N) × α           |
| 大消息   | ✅ 带宽最优              | ❌ 树根带宽成瓶颈      |
| 小消息   | ❌ 延迟高                | ✅ 延迟低              |
| 适用场景 | 梯度同步（大数据量）     | 标量广播、小张量通信   |

**NCCL 自动选择策略**：

NCCL 在运行时根据以下因素自动选择拓扑：

1. **消息大小**：小消息（< 256KB）倾向 Tree，大消息（> 1MB）倾向 Ring
2. **GPU 拓扑**：检测 NVLink/PCIe 连接关系，构建最优 Ring 或 Double Binary Tree
3. **节点数**：跨节点通信混合使用 Tree（节点间）+ Ring（节点内）
4. **环境变量**：`NCCL_ALGO=Ring/Tree/CollnetDirect` 可强制指定

```bash
# 查看 NCCL 选择了哪种拓扑
NCCL_DEBUG=INFO python train.py 2>&1 | grep -i "algo"
# 输出: ... Using algo Ring ...
```

</details>

### Q18：GPipe 和 PipeDream 的流水线调度有什么区别？

<details>
<summary>参考答案</summary>

**GPipe（同步流水线）**：

```
策略: 先全部前向，再全部反向（同步更新权重）

时间 →
S0: [F₀][F₁][F₂][F₃][  idle  ][  idle  ][  idle  ][B₃][B₂][B₁][B₀][U]
S1:     [F₀][F₁][F₂][F₃][  idle  ][  idle  ][B₃][B₂][B₁][B₀]    [U]
S2:         [F₀][F₁][F₂][F₃][  idle  ][B₃][B₂][B₁][B₀]         [U]
S3:             [F₀][F₁][F₂][F₃][B₃][B₂][B₁][B₀]              [U]

F=前向, B=反向, U=权重更新, S=Stage
气泡率 = (K-1)/(2M)，K=4, M=4 → 37.5%
```

**PipeDream（异步流水线，1F1B）**：

```
策略: 前向和反向交叉执行（一前一后）

时间 →
S0: [F₀][F₁][F₂][F₃][B₀][F₄][B₁][F₅][B₂][F₆][B₃][F₇]...
S1:     [F₀][F₁][F₂][B₀][F₃][B₁][F₄][B₂][F₅][B₃]...
S2:         [F₀][F₁][B₀][F₂][B₁][F₃][B₂][F₄][B₃]...
S3:             [F₀][B₀][F₁][B₁][F₂][B₂][F₃][B₃]...

气泡率 ≈ (K-1)/(M+K-1)，更小！
```

**核心区别**：

| 维度           | GPipe                    | PipeDream                      |
|----------------|--------------------------|--------------------------------|
| 权重更新       | 同步（所有 micro-batch 后） | 异步（每个 micro-batch 后可更新） |
| 权重一致性     | ✅ 完全一致              | ❌ 存在 Weight Staling          |
| 气泡率         | 高: (K-1)/(2M)          | 低: (K-1)/(M+K-1)             |
| 显存开销       | 中（缓存 M 份激活）     | 高（需缓存多版本权重）         |
| 收敛性         | 等价单卡                | 可能略有偏差                   |

**Weight Staling 问题**：PipeDream 中，micro-batch i 前向时用的权重版本 Wₜ，反向时权重已被更新为 Wₜ₊ₖ，前后不一致可能影响收敛。

**改进方案**：

1. **PipeDream-2BW**：只缓存 2 个版本的权重（当前版本 + 上一版本），用正确版本计算反向
2. **PipeDream-Flush**：周期性清空流水线（等所有反向完成），类似 GPipe 但更频繁
3. **Megatron-LM Interleaved 1F1B**：同步更新 + interleaved stages，兼顾正确性和低气泡

**气泡率对比计算**（K=4 Stages, M=16 micro-batches）：

```
GPipe:              (4-1)/(2×16)     = 9.4%
PipeDream 1F1B:     (4-1)/(16+4-1)   = 15.8%  ← 此处 M 较小时优势更大
Interleaved (V=2):  (4-1)/(16×2+4-1) = 8.6%
```

> **实践建议**：Megatron-LM 的 Interleaved 1F1B（同步更新、低气泡、无 weight staling）是目前最主流的选择。

</details>

### Q19：Gradient Checkpointing 的不同策略有哪些？如何选择？

<details>
<summary>参考答案</summary>

Gradient Checkpointing（也叫 Activation Checkpointing）有多种策略，核心权衡是**显存 vs 计算**：

**策略一：全量检查点（Every Layer）**

每个 Transformer 层都设为检查点，反向时重算每层的内部激活。

```python
# PyTorch 原生
from torch.utils.checkpoint import checkpoint

class TransformerBlock(nn.Module):
    def forward(self, x):
        return checkpoint(self._forward_impl, x, use_reentrant=False)

    def _forward_impl(self, x):
        x = self.attention(x)
        x = self.mlp(x)
        return x
```

- 显存节省：~90%（激活值）
- 计算开销：+33%（每层额外一次前向）

**策略二：选择性检查点（Selective）**

只对显存消耗大的层设检查点（如 Attention 层），MLP 层正常保存激活。

```python
# 只对 Attention 检查点
class TransformerBlock(nn.Module):
    def forward(self, x):
        x = checkpoint(self.attention, x, use_reentrant=False)  # 检查点
        x = self.mlp(x)                                         # 正常保存
        return x
```

- 显存节省：~60-70%
- 计算开销：+15-20%

**策略三：均匀间隔检查点（Every K Layers）**

每 K 层设一个检查点，反向时从最近的检查点开始重算。

```python
# 理论最优：每 √L 层设一个检查点（L=总层数）
# 例如 32 层模型 → 每 5-6 层设一个检查点
checkpoint_layers = {0, 6, 12, 18, 24, 30}
```

- 显存：O(√L) 级别（保存 √L 个检查点 + 最多重算 √L 层的激活）
- 计算开销：+10-15%

**策略四：DeepSpeed 分区检查点（Partition Activations）**

将检查点的激活值也进行分片，每张 GPU 只存 1/N 的激活，反向时 All-Gather 重建。

```json
{
  "activation_checkpointing": {
    "partition_activations": true,
    "cpu_checkpointing": true,
    "contiguous_memory_optimization": true
  }
}
```

**选型决策树**：

```
显存够用？ ─→ 是 → 不启用（最快）
    │
    否
    │
    ▼
长序列(>4K)？ ─→ 是 → 选择性检查点（Attention 层，省 Attention Score 显存）
    │
    否
    │
    ▼
模型层数多？ ─→ 是 → 全量检查点 + DeepSpeed 分区
    │
    否
    │
    ▼
均匀间隔检查点（每 √L 层）
```

</details>

### Q20：大规模训练中的故障恢复机制有哪些？Elastic Training 是什么？

<details>
<summary>参考答案</summary>

大规模训练（数百/上千 GPU）中，硬件故障（GPU 挂、节点宕机、网络抖动）是常态。故障恢复机制是保证训练能够完成的关键。

**1. 周期性 Checkpoint（最基础）**

```
─── 训练时间线 ───
[Train 0-1000步] → [Save CKP] → [Train 1001-2000步] → [Save CKP] → ...
                                      ↑
                                   故障发生
                                      ↓
                          [从 CKP 1000步恢复] → [继续训练]
```

**Checkpoint 耗时估算**：

```
Checkpoint 大小 = 模型状态 + 优化器状态
70B 模型: ≈ 70B × 16 bytes = 1.12 TB（FP32 完整状态）
写入速度: NVMe ≈ 3 GB/s, 网络存储 ≈ 1 GB/s

同步 Checkpoint 耗时: 1120 GB / 3 GB/s ≈ 373 秒 ≈ 6 分钟
每小时保存一次 → 训练开销 ≈ 10%
```

**2. 异步 Checkpoint**

在后台线程写入 Checkpoint，训练不暂停：

```python
# DeepSpeed 异步 checkpoint
{
  "checkpoint": {
    "save_on_each_node": true,    # 先存本地 NVMe（快）
    "async_save": true             # 后台异步上传到共享存储
  }
}
```

**3. PyTorch Elastic（TorchElastic / torchrun）**

允许训练在节点故障后**自动重启**，支持动态扩缩容：

```bash
# 使用 torchrun 启动弹性训练
torchrun \
  --nnodes=4:8 \         # 最少 4 节点，最多 8 节点
  --nproc_per_node=8 \
  --rdzv_backend=c10d \  # Rendezvous 后端
  --rdzv_endpoint=master:29400 \
  --max_restarts=3 \     # 最大重启次数
  train.py
```

**Rendezvous 机制**：当节点加入/离开时，所有存活节点重新"集合"，协商新的 world_size 和 rank 分配，然后从最近的 Checkpoint 恢复训练。

**4. Megatron-LM 故障恢复**

```python
# Megatron-LM 自动检测最新 checkpoint
if args.load:
    iteration = load_checkpoint(model, optimizer, lr_scheduler)
    # 自动跳过已训练的数据（通过 iteration 推算 consumed samples）
```

**5. 大规模集群容错策略**

| 策略               | 说明                                      | 适用规模    |
|--------------------|-------------------------------------------|-------------|
| 周期 Checkpoint    | 每 N 步保存，故障后从最近 CKP 恢复         | 任意        |
| 冗余训练           | 多个 replica 同时训练同一份，一个挂了用另一个| 极大规模    |
| Spot Instance 容错 | 检测 preemption 信号，提前保存 CKP          | 云上训练    |
| In-memory CKP      | Checkpoint 保存在其他节点的 GPU/CPU 内存中  | 高频 CKP    |

> **最佳实践**：每 30 分钟异步 Checkpoint + TorchElastic 自动重启 + 本地 NVMe 快速写入后异步上传至共享存储。

</details>

### Q21：ZeRO vs Megatron Tensor Parallelism，各自适合什么场景？两者可以结合吗？

<details>
<summary>参考答案</summary>

**核心对比**：

| 维度         | ZeRO（数据并行 + 状态分片）             | Megatron Tensor Parallel            |
| ------------ | --------------------------------------- | ----------------------------------- |
| **本质**     | 每张卡存全部层，每层 1/N 的参数         | 每张卡存某些层矩阵的部分行/列       |
| **通信模式** | All-Gather + Reduce-Scatter（在时间上） | All-Reduce（在每一层的计算中）      |
| **通信时机** | 层与层之间（可重叠）                   | 层计算过程中（不可避免）            |
| **适用场景** | 数据并行扩展，模型宽度适中              | 单层参数量极大（宽层），紧密 NVLink |
| **易用性**   | 高（几乎不改模型代码）                  | 低（需要修改矩阵乘法实现）          |

**何时选 ZeRO，何时选 TP？**

```
模型能否放入单节点？
  │
  ├─ 是 → ZeRO Stage 2/3 即可（简单高效）
  │
  └─ 否 → 单层参数矩阵多大？
            │
            ├─ 单层 < 1GB → ZeRO Stage 3 跨节点（通信在层间，可用 IB）
            │
            └─ 单层 > 1GB → 需要 TP（层内切分，必须 NVLink）
                           + 跨节点用 PP/DP
```

**3D 并行组合（ZeRO + TP + PP）**：

```
256 GPU 训练 GPT-3 175B 的 3D 并行布局：

张量并行 (TP=8): 同节点内 8 张 GPU, NVLink 互连
                 ┌───────────────────────────────────────┐
                 │  GPU0  GPU1  GPU2  GPU3                │
  节点 0 (TP组0) │  GPU4  GPU5  GPU6  GPU7                │
                 └───────────────────────────────────────┘
流水线并行 (PP=4): 4 个节点依次承载模型的 4 段层
  节点 0 (Layer 0-23) → 节点 1 (Layer 24-47) → 节点 2 (Layer 48-71) → 节点 3 (Layer 72-95)

数据并行 (DP=8): 8 组完整的 TP×PP 配置，各自处理不同的数据分片
  DP 组间用 ZeRO Stage 1 同步优化器状态

总 GPU = TP × PP × DP = 8 × 4 × 8 = 256
```

ZeRO 处理优化器状态冗余，Megatron TP 处理单层参数过大的问题，PP 处理模型总层数过多的问题，三者正交互补。

**追问链**：

**追问 1：TP 在跨节点时为什么效率低？**

TP 需要在每个 Transformer 层的计算过程中执行 2 次 All-Reduce（前向 g 算子、反向 f 算子）。Transformer 模型有 L 层，每步训练需要 2L 次 All-Reduce。跨节点的 InfiniBand 带宽（200-400 Gb/s）远低于 NVLink（900 GB/s），导致通信成为严重瓶颈。

**追问 2：ZeRO Stage 3 和 FSDP 的 FULL_SHARD 有什么区别？**

本质相同（参数/梯度/优化器全部分片），但实现不同：FSDP 是 PyTorch 原生（无需额外库），基于 FlatParameter 将多个参数展平为一个大张量统一管理；DeepSpeed ZeRO 基于 bucket 机制分桶管理，提供更多配置项（offload、prefetch 粒度等）。

**追问 3：3D 并行中，如果增加节点数量，应该优先增加哪个维度？**

优先增加 DP（数据并行），因为 DP 的通信量最小（只需在训练步之间同步梯度），且对模型代码无侵入。TP 受限于节点内 GPU 数量，PP 受限于模型层数和气泡率。

</details>

### Q22：如何估算给定模型和训练配置下的训练吞吐量？MFU 的意义是什么？

<details>
<summary>参考答案</summary>

**理论 FLOPs 估算**：

LLM 前向传播约 2×参数量 FLOPs/token，训练（含反向）约 6×参数量：

```
FLOPs/token = 6 × Ψ（Ψ 为参数量）
  前向: 2Ψ（矩阵乘法为主）
  反向: 4Ψ（2Ψ 计算梯度 + 2Ψ 计算参数梯度）

7B 模型: 6 × 7×10⁹ = 4.2×10¹⁰ FLOPs/token
70B 模型: 6 × 70×10⁹ = 4.2×10¹¹ FLOPs/token
```

**MFU（Model FLOPs Utilization）**：

```
MFU = 实际 FLOPs/s / GPU 理论峰值 FLOPs/s

计算方式:
  实际 FLOPS = (6 × Ψ × tokens_per_second) / GPU_count
  GPU 峰值:
    A100 BF16 = 312 TFLOPS
    H100 BF16 = 989 TFLOPS
    H100 FP8  = 1979 TFLOPS

示例: 7B 模型在 8×A100 上跑 24000 tokens/s (总):
  每 GPU: 24000/8 = 3000 tokens/s
  实际 FLOPS = 4.2×10¹⁰ × 3000 = 1.26×10¹⁴ = 126 TFLOPS
  MFU = 126 / 312 ≈ 40.4%
```

**MFU 参考值**：

| MFU 范围 | 评价   | 可能原因                              |
|----------|--------|---------------------------------------|
| > 50%    | 优秀   | 配置优化良好                          |
| 40-50%   | 良好   | 正常水平                              |
| 30-40%   | 及格   | 可能有通信/数据加载瓶颈              |
| < 30%    | 差     | 存在严重瓶颈，需要排查                |

**影响 MFU 的因素**：

1. **通信开销**：ZeRO Stage 3 > Stage 2 > Stage 1；TP 增加层内通信
2. **Activation Checkpointing**：增加计算量但不增加有效 FLOPS，降低 MFU
3. **数据加载**：DataLoader 跟不上 GPU 计算速度
4. **Pipeline 气泡**：PP 的 bubble time 是纯浪费
5. **Batch Size**：过小的 batch 导致 GPU 利用率低

> 注意：MFU 只衡量计算效率，不反映通信效率。实际优化时要结合 GPU Utilization（`nvidia-smi`）和 NCCL 带宽利用率综合分析。

**追问链**：

**追问 1：HFU（Hardware FLOPs Utilization）和 MFU 有什么区别？**

HFU 将 Activation Checkpointing 的重算也计入"有效 FLOPS"，因此 HFU > MFU。MFU 更严格，只计算理论最小所需的 FLOPS。学术论文中通常报告 MFU。

**追问 2：如何用 MFU 估算训练时间？**

```
总 tokens = dataset_size × epochs
训练时间 = 总 tokens × (6Ψ) / (GPU数 × GPU峰值 × MFU)

例: 1T tokens 训 70B, 256×A100, MFU=45%:
时间 = 1×10¹² × 4.2×10¹¹ / (256 × 312×10¹² × 0.45)
     = 4.2×10²³ / (3.59×10¹⁶)
     ≈ 1.17×10⁷ 秒 ≈ 135 天
```

**追问 3：为什么 H100 的 MFU 反而比 A100 更难提高？**

H100 的 BF16 算力是 A100 的 3.2 倍（989 vs 312 TFLOPS），但内存带宽只提升 1.6 倍（3.35 vs 2.0 TB/s），网络带宽提升有限。计算/通信比失衡，通信更容易成为瓶颈。

</details>

### Q23：多节点训练时，NCCL 通信性能差的常见原因和排查方法？

<details>
<summary>参考答案</summary>

**常见原因**：

1. **InfiniBand 未启用**：降级为 TCP（带宽从 200+ Gb/s 降至 ~10-25 Gb/s）
2. **NCCL 选错网络接口**：使用了管理网而非数据网
3. **MTU 设置不当**：导致大包分片，增加延迟
4. **RDMA 未正确配置**：RoCE 需要配置 PFC/ECN，IB 需要正确的 GID
5. **PCIe 拓扑不优**：GPU 和 NIC 不在同一 NUMA 节点
6. **NVLink 未启用**：节点内退化为 PCIe 通信

**排查步骤**：

```bash
# 1. 确认 IB 设备可见和状态
ibstat
# 期望输出: State: Active, Physical state: LinkUp, Rate: 200 Gb/sec

# 2. 检查 GPU 拓扑（NVLink 连接关系）
nvidia-smi topo -m
# 期望看到 NV12/NV18 而非 PIX/PHB

# 3. 运行 nccl-tests 测量实际带宽
./build/all_reduce_perf -b 1G -e 1G -f 2 -g 8 -n 20
# 期望: busbw > 150 GB/s (8×A100 NVLink)
# 跨节点: busbw > 20 GB/s (200Gb IB)

# 4. 开启 NCCL 详细调试日志
NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=INIT,NET torchrun ...
# 检查输出中的:
#   - "Using network xxx" → 确认使用了正确接口
#   - "Channel" → 确认通道数
#   - "algo Ring/Tree" → 确认算法选择

# 5. 强制指定 IB 设备和接口
export NCCL_IB_HCA=mlx5_0,mlx5_1     # 指定 IB 设备
export NCCL_IB_GID_INDEX=3            # 指定 GID
export NCCL_SOCKET_IFNAME=eth0        # 指定 socket 接口
export NCCL_IB_DISABLE=0              # 确保 IB 未被禁用

# 6. 检查 PCIe/NUMA 对齐
lstopo --of txt  # 查看硬件拓扑
numactl --show   # 查看 NUMA 绑定
```

**性能基准参考**：

| 配置              | 预期 busbw        | 不达标阈值       |
|-------------------|-------------------|------------------|
| 8×A100 NVLink     | 150-200 GB/s     | < 100 GB/s       |
| 2 节点 200Gb IB   | 22-24 GB/s       | < 15 GB/s        |
| 8×H100 NVSwitch   | 400-450 GB/s     | < 300 GB/s       |

> 实际测量带宽与 `nccl-tests` 理论值差距 > 20% 时，通常是 IB/NVLink 配置问题。

**追问链**：

**追问 1：NCCL_P2P_DISABLE 和 NCCL_SHM_DISABLE 什么时候需要设置？**

当节点内 GPU 无法通过 NVLink/NVSwitch P2P 直连时（如 PCIe 交换机隔离），设置 `NCCL_P2P_DISABLE=1` 退回到共享内存通信。`NCCL_SHM_DISABLE=1` 禁用共享内存，强制使用网络通信（调试用）。

**追问 2：如何诊断是通信瓶颈还是计算瓶颈？**

使用 PyTorch Profiler + NCCL 事件追踪：`torch.profiler.profile(activities=[ProfilerActivity.CUDA], with_stack=True)`。如果 NCCL 通信操作（AllReduce/AllGather）占用时间 > 计算时间的 30%，则为通信瓶颈。

**追问 3：GDR（GPUDirect RDMA）的作用？**

GDR 允许 NCCL 直接从 GPU 显存 RDMA 到远端 GPU 显存，跳过 CPU 内存拷贝。需要 GPU 和 NIC 在同一 PCIe switch 下。设置 `NCCL_NET_GDR_LEVEL=5` 启用。

### Q25：如何设计 Megatron-LM 风格的 3D 混合并行策略？给定 GPU 数量如何分配 TP/PP/DP？

<details>
<summary>参考答案</summary>

**约束条件**：

```
总 GPU 数 = TP × PP × DP

TP (张量并行): ≤ 节点内 GPU 数（必须 NVLink 互连）
PP (流水线并行): ≤ 模型层数 / 最小层数（每 stage 至少 1 层）
DP (数据并行): = 总 GPU / (TP × PP)
```

**分配决策框架**：

```
Step 1: 确定 TP degree
  ├─ 单层参数是否放得进单卡？
  │   ├─ 是 → TP = 1
  │   └─ 否 → TP = ceil(单层大小 / 单卡显存)
  │
  └─ TP 上限 = 节点内 GPU 数（NVLink 约束）
     通常 TP ∈ {1, 2, 4, 8}

Step 2: 确定 PP degree
  ├─ 模型总参数 / TP 后的每卡参数量 > 单卡显存？
  │   ├─ 是 → PP = ceil(模型大小 / (TP × 单卡显存))
  │   └─ 否 → PP = 1
  │
  └─ PP 上限 = 模型层数（每 stage 至少 1 层）
     注意: PP 越大, 气泡越多, 需要足够 micro-batch 来摊薄

Step 3: 确定 DP degree
  DP = 总 GPU / (TP × PP)
  DP 使用 ZeRO Stage 1（开销最小）
```

**实例：256 GPU 训练 GPT-3 175B**

```
硬件: 32 节点 × 8 GPU (A100 80GB), NVLink 节点内, IB 200Gb 节点间

GPT-3 175B 参数:
  96 层 Transformer
  hidden_size = 12288
  单层参数: 12288² × 4 矩阵 ≈ 2.4B → 约 4.8 GB (FP16)
  总参数: 175B → 350 GB (FP16)

Step 1: TP = 8
  单层 4.8 GB 可以放入单卡, 但 TP=8 可以减少激活值显存, 提升计算效率
  8 GPU 正好是一个 NVLink 域

Step 2: PP = 4
  175B / 8(TP) = ~21.9B 参数/TP组
  21.9B × 16 bytes = 350 GB → 需要分到多卡
  PP=4: 每 PP stage 约 24 层, 5.5B 参数

Step 3: DP = 256 / (8 × 4) = 8
  8 路数据并行, 使用 ZeRO Stage 1

进程组 (process group) 布局:
```

```
      TP=8 (NVLink)          TP=8 (NVLink)
  ┌───────────────────┐  ┌───────────────────┐
  │ Node 0: PP Stage 0 │  │ Node 1: PP Stage 1 │
  │ GPU 0-7            │──│ GPU 8-15           │
  └───────────────────┘  └───────────────────┘
          │                        │
  ┌───────────────────┐  ┌───────────────────┐
  │ Node 2: PP Stage 2 │  │ Node 3: PP Stage 3 │
  │ GPU 16-23          │──│ GPU 24-31          │
  └───────────────────┘  └───────────────────┘

  以上为 1 个 DP replica (32 GPU)
  共 8 个这样的 replica = 256 GPU

  DP 组: {GPU_0, GPU_32, GPU_64, ..., GPU_224}  (跨 replica 同位置)
  TP 组: {GPU_0, GPU_1, ..., GPU_7}  (节点内)
  PP 组: {GPU_0, GPU_8, GPU_16, GPU_24}  (跨节点, 同 TP rank)
```

**Megatron-LM 启动命令**：

```bash
python -m torch.distributed.launch \
  --nproc_per_node=8 \
  --nnodes=32 \
  pretrain_gpt.py \
  --tensor-model-parallel-size 8 \
  --pipeline-model-parallel-size 4 \
  --num-layers 96 \
  --hidden-size 12288 \
  --micro-batch-size 1 \
  --global-batch-size 1536 \
  --seq-length 2048 \
  --bf16
```

**追问链**：

**追问 1：如果 GPU 数量不能被 TP×PP 整除怎么办？**

必须确保总 GPU = TP × PP × DP，三者的乘积等于总 GPU 数。可以调整 PP 或 DP 来匹配。如果实在无法整除，可以留出部分 GPU 不参与训练（浪费较小）。

**追问 2：Expert Parallelism（MoE 模型的专家并行）如何与 3D 并行结合？**

MoE 模型新增第四个维度 EP（Expert Parallel）。每个专家分配到不同 GPU，All-to-All 通信交换 token。布局变为 TP × PP × DP × EP。Expert 间通信量较大，通常也放在节点内。

**追问 3：Context Parallelism（序列并行）和 TP 有什么区别？**

TP 切分参数矩阵（模型维度），CP 切分序列维度（seq_len）。CP 将长序列分段到不同 GPU，每段独立计算 Attention 后通过 Ring Attention 交换 KV。适用于超长上下文（128K+）训练。两者可同时使用。

### Q26：训练过程中 Loss Spike 的常见原因和排查方法？

<details>
<summary>参考答案</summary>

**Loss Spike 的常见原因**：

```
Loss Spike 分类:

1. 数据相关
   ├─ 损坏样本（编码错误、截断、空样本）
   ├─ 极端值（异常长文本、特殊 token 堆叠）
   └─ 数据分布突变（不同数据源切换时）

2. 优化器相关
   ├─ 学习率过高（尤其 warmup 后突然增大）
   ├─ 梯度爆炸（gradient norm 突增）
   └─ 权重衰减不当

3. 数值精度相关
   ├─ FP16 溢出（loss scaling 跟不上）
   ├─ Attention Score 过大（softmax 饱和）
   └─ LayerNorm/RMSNorm 不稳定

4. 系统相关
   ├─ 从 checkpoint 恢复后数据顺序变化
   ├─ Pipeline 并行中的数值误差累积
   └─ 异步通信导致的梯度不一致
```

**排查方法**：

**Step 1: 监控梯度范数**

```python
# 训练循环中添加
grad_norm = torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
if grad_norm > 10.0:  # 异常高
    logger.warning(f"Step {step}: grad_norm={grad_norm:.2f}, loss={loss:.4f}")
    # 记录当前 batch 的数据 hash 用于复现
```

**Step 2: 检查 Loss Scaling 历史**

```python
# DeepSpeed 内置
if hasattr(model_engine.optimizer, 'cur_scale'):
    scale = model_engine.optimizer.cur_scale
    if scale < 1:  # Loss scale 降到 1 以下说明频繁溢出
        logger.error(f"Loss scale dangerously low: {scale}")
```

**Step 3: 数据检查**

```python
# 记录异常 batch
for batch_idx, batch in enumerate(dataloader):
    loss = model(batch)
    if loss.item() > 2 * running_avg_loss:
        # 保存异常样本用于事后分析
        torch.save(batch, f"anomaly_batch_{step}_{batch_idx}.pt")
```

**Step 4: 稳定性修复手段**

| 问题             | 修复方法                                   |
|------------------|--------------------------------------------|
| 梯度爆炸         | 降低 `max_grad_norm`（1.0 → 0.5）         |
| FP16 溢出        | 切换到 BF16                                |
| Attention 不稳定 | 使用 Flash Attention（数值更稳定）         |
| 数据异常         | 添加数据过滤/异常检测预处理                 |
| LR 过高          | 降低峰值 LR，延长 warmup                   |

**PaLM 论文的做法**：Google 在训练 PaLM 540B 时遇到 ~20 次 loss spike。他们的方案是：从 spike 前 100 步的 checkpoint 恢复，并跳过导致 spike 的 ~200-500 个数据 batch。

**追问链**：

**追问 1：如何区分 loss spike 是数据问题还是优化器问题？**

如果 gradient norm 同时 spike，大概率是数据问题（异常样本产生异常梯度）。如果 gradient norm 正常但 loss spike，可能是模型内部数值问题（如 attention score 溢出）。可以用相同数据重跑一步验证。

**追问 2：BF16 训练是否完全不会出现数值问题？**

不是。BF16 虽然不需要 loss scaling，但其尾数精度低（7 bit vs FP16 的 10 bit），在累加操作中可能产生精度损失。例如大 batch 的梯度求和、大矩阵的 reduce 操作。Megatron-LM 对关键的 reduce 操作使用 FP32 累加。

**追问 3：Z-loss 正则化是什么？如何帮助训练稳定？**

Z-loss 对 logits 的 log-sum-exp 添加 L2 正则化（`z_loss = 1e-4 * logsumexp(logits)²`），防止 logits 值过大导致 softmax 数值不稳定。PaLM 和 Chinchilla 都使用了这种技术。

</details>

### Q28：线上推理场景，DeepSpeed-Inference 和 vLLM 该如何选择？

<details>
<summary>参考答案</summary>

**核心对比**：

| 维度                 | DeepSpeed-MII              | vLLM                           | TensorRT-LLM              |
| -------------------- | -------------------------- | ------------------------------ | -------------------------- |
| **核心优化**         | Dynamic SplitFuse          | PagedAttention + Cont. Batch  | FP8 量化 + 图优化          |
| **吞吐量**           | 高                         | 最高                           | 最高                       |
| **P99 延迟**         | 最优（SplitFuse 均匀化）  | 良好                           | 良好                       |
| **KV Cache 管理**    | 传统预分配                | PagedAttention（按需分页）    | 预分配                     |
| **显存利用率**       | 中等                      | 最高（虚拟内存风格）          | 中等                       |
| **模型支持**         | 较广                      | 最广（社区活跃）              | 有限（需模型转换）         |
| **量化支持**         | INT8                       | AWQ/GPTQ/FP8                  | FP8/INT4（最强）           |
| **上手难度**         | 中等                      | 低                             | 高                         |
| **生态**             | DeepSpeed                  | 独立社区                      | NVIDIA                     |

**场景选型**：

```
你的场景是什么？
│
├─ 追求极致吞吐，高并发请求
│   → vLLM（PagedAttention + Continuous Batching 优势明显）
│
├─ 已有 DeepSpeed 训练基础，快速部署
│   → DeepSpeed-MII（生态一致，配置简单）
│
├─ 需要极低 P99 延迟（金融/实时对话）
│   → DeepSpeed-MII（Dynamic SplitFuse 均匀化延迟分布）
│
├─ 需要广泛模型支持（最新开源模型第一时间适配）
│   → vLLM（社区最活跃，更新最快）
│
├─ 需要 INT4/FP8 极致量化
│   → TensorRT-LLM（NVIDIA 官方，量化效率最高）
│
└─ 预算有限，单卡部署
    → vLLM 或 llama.cpp（取决于模型大小和精度需求）
```

**PagedAttention 原理简述**：

```
传统 KV Cache:
  为每个请求预分配最大 seq_len 的连续显存 → 显存碎片严重，利用率 ~50%

PagedAttention (vLLM):
  KV Cache 按固定大小 block (如 16 tokens) 分配
  使用 block table 映射逻辑位置 → 物理块
  类似操作系统的虚拟内存分页 → 显存利用率 ~95%

请求 A: [Block 0] → [Block 3] → [Block 7] → [Block 2]  (非连续)
请求 B: [Block 1] → [Block 5] → [Block 4]              (非连续)
空闲:   [Block 6] [Block 8]                             (可随时分配)
```

**DeepSpeed Dynamic SplitFuse**：

将长 prompt 拆分（Split）为多个小块，与短 generation 请求融合（Fuse）到同一 batch，使每个 batch 的计算量更均匀，避免长 prompt 独占 GPU 导致其他请求排队。

> **结论**：大多数场景推荐 vLLM（生态好、吞吐高、易用）；对延迟敏感选 DeepSpeed-MII；极致性能选 TensorRT-LLM。

</details>

### Q29：设计一个 70B 模型的训练方案（给定 64 张 A100 80GB）

<details>
<summary>参考答案</summary>

**一、显存估算**

```
模型: 70B 参数 (如 LLaMA-2 70B)
硬件: 8 节点 × 8 GPU = 64 × A100 80GB
网络: 节点内 NVLink 600GB/s, 节点间 InfiniBand 200Gb/s

模型状态:
  FP16 权重:      70B × 2 = 140 GB
  FP16 梯度:      70B × 2 = 140 GB
  FP32 主权重:    70B × 4 = 280 GB
  Adam m/v:       70B × 8 = 560 GB
  总计:           1120 GB

可用显存: 64 × 80 = 5120 GB (4.6× 余量)
```

**二、并行策略选择**

**方案 A：纯 ZeRO Stage 3**

```
每卡显存 (N=64):
  模型状态: 1120 / 64 = 17.5 GB
  激活值 (batch=4, seq=4096, AC): ~10 GB
  缓冲区: ~5 GB
  总计: ~32.5 GB << 80 GB ✅ 余量充足

优点: 实现简单, 显存充足可用大 batch
缺点: Stage 3 通信量 3Ψ, 跨节点 IB 可能成瓶颈
```

**方案 B：3D 并行（推荐）**

```
TP=4 × PP=2 × DP=8

  TP=4: 节点内 4 GPU 做张量并行 (NVLink, 通信密集)
  PP=2: 模型分 2 段 (前 40 层 + 后 40 层)
  DP=8: 8 路数据并行 + ZeRO Stage 1

每卡显存:
  模型参数 (TP=4): 70B / 4 / 2(PP) = 8.75B → 17.5 GB (FP16)
  优化器 (ZeRO-1, DP=8): 8.75B × 12 / 8 = 13.1 GB
  激活值 (AC, batch=2): ~6 GB
  总计: ~37 GB < 80 GB ✅

优点: 通信更高效 (TP在NVLink, DP只需同步优化器)
缺点: 需要 Megatron-LM, 实现复杂
```

**三、Batch Size 与训练配置**

```
方案 B 配置:
  micro_batch_size = 2
  gradient_accumulation = 16
  global_batch_size = 2 × 16 × 8(DP) = 256

序列长度: 4096
每步 tokens: 256 × 4096 = 1,048,576 ≈ 1M tokens/step
```

**2. Scheduler（资源调度器）**

```
调度策略:

┌─ Gang Scheduling (分布式训练必须)
│   所有 GPU 必须同时分配，不能分批启动
│   避免部分分配导致资源浪费
│
├─ Priority-based Preemption (抢占)
│   高优先级任务可抢占低优先级任务
│   被抢占任务自动保存 checkpoint 并重新排队
│
├─ Bin Packing (装箱算法)
│   小任务尽量打包到同一节点，减少碎片
│   大任务优先分配拓扑相近的节点 (同交换机/同机架)
│
├─ Topology-Aware Placement
│   优先分配 NVLink 互连的 GPU 给 TP 组
│   优先分配同一 IB 交换机下的节点给 PP/DP
│
└─ Fair Share (公平份额)
    多租户环境下按团队配额分配
    超额使用的团队在资源紧张时优先被抢占
```

**3. Resource Manager（GPU 资源管理）**

```python
# 资源管理核心逻辑
class ResourceManager:
    def allocate(self, job: Job) -> List[Node]:
        # 1. 筛选满足要求的节点
        candidates = self.find_nodes(
            gpu_type=job.gpu_type,
            free_gpus_per_node=job.gpu_per_node
        )

        # 2. 拓扑感知排序（同交换机、同机架优先）
        candidates.sort(key=lambda n: (
            n.switch_id,    # 同交换机
            n.rack_id,      # 同机架
            n.free_gpu_count  # 空闲 GPU 多的优先
        ))

        # 3. Gang allocation（全部或不分配）
        if len(candidates) >= job.node_count:
            nodes = candidates[:job.node_count]
            self.reserve(nodes, job)
            return nodes
        else:
            return None  # 排队等待
```

**三、关键设计决策**

**Gang Scheduling（群组调度）**

分布式训练必须所有 GPU 同时就绪。使用两阶段提交：

```
Phase 1: 预留所有节点的 GPU (Tentative)
Phase 2: 确认所有预留成功 → 启动任务
         若任何节点预留失败 → 释放所有已预留资源
```

**Spot Instance 容错**

```
云上训练使用 Spot/Preemptible 实例节省成本 (50-70%):

1. 监听 preemption 通知 (AWS: 2分钟提前通知)
2. 收到通知 → 立即触发 checkpoint 保存
3. Checkpoint 完成 → 优雅退出
4. 调度器自动申请新的 Spot 实例
5. 新实例就绪 → 从 checkpoint 恢复训练

成本对比:
  On-demand A100: $3.5/h/GPU × 64 GPU × 720h = $161,280/月
  Spot A100:      $1.2/h/GPU × 64 GPU × 720h = $55,296/月
  节省: ~65%
```
