## ⭐ 基础题

### Q1：训练一个 7B 参数模型需要多少显存？为什么远超 7B × 2 bytes = 14GB？

**答**：使用 Adam 优化器 + 混合精度训练时，每个参数需要 **16 字节**：

| 状态            | 精度 | 字节/参数 |
| --------------- | ---- | --------- |
| FP16 模型权重   | FP16 | 2         |
| FP16 梯度       | FP16 | 2         |
| FP32 主权重副本 | FP32 | 4         |
| Adam 一阶矩 m₁  | FP32 | 4         |
| Adam 二阶矩 m₂  | FP32 | 4         |
| **合计**        | —    | **16**    |

7B 模型：7×10⁹ × 16 = **112 GB**。

---

### Q2：ZeRO 的三个阶段分别对什么进行分片？每卡显存公式是什么？

**答**：

| 阶段    | 分片内容   | 每卡显存（字节/参数） | N=8 时 70B 每卡显存 |
| ------- | ---------- | --------------------- | ------------------- |
| Stage 1 | 优化器状态 | 4 + 12/N              | ~48 GB              |
| Stage 2 | + 梯度     | 2 + 14/N              | ~33 GB              |
| Stage 3 | + 参数     | 16/N                  | ~17.5 GB            |

---

### Q3：DDP 的核心缺陷是什么？ZeRO 如何解决？

**答**：DDP 每张 GPU 保存**完整的一份**模型状态（权重 + 梯度 + 优化器状态）。对于 N=8 的情况，优化器状态被完全冗余复制了 8 份，浪费了 7/8 的显存。

ZeRO 的核心思想：**每张 GPU 只存 1/N 自己负责更新的那部分状态**，不需要的部分通过通信按需获取，从而消除冗余。通信总量与 DDP 相同（都是 ~2Ψ），但内存降低了 N 倍。

---

### Q4：DeepSpeed 初始化时，`deepspeed.initialize()` 做了哪些工作？

**答**：

1. 自动调用 `dist.init_process_group("nccl")`（如果尚未初始化）
2. 根据 ds_config 决定 ZeRO Stage，将模型参数重新分片
3. 将普通优化器包装为 `DeepSpeedZeroOptimizer`（含梯度分片逻辑）
4. 设置 FP16/BF16 Loss Scaler（自动动态损失缩放）
5. 返回 `DeepSpeedEngine`，提供 `.backward()` 和 `.step()` 统一接口

---

### Q5：什么是损失缩放（Loss Scaling）？为什么 BF16 不需要它？

**答**：FP16 的最小正规数约 6×10⁻⁸，训练中梯度值可能更小，导致"下溢"变成 0。损失缩放通过在反向传播前将 loss 乘以大数（如 65536），使梯度落入 FP16 表示范围，参数更新前再除回去。

BF16 的指数位数（8位）与 FP32 相同，动态范围等同于 FP32（~10⁻³⁸），不存在下溢问题，无需损失缩放。

---

### Q6：如何将现有 PyTorch DDP 训练代码迁移到 DeepSpeed？需要改哪几行？

**答**：主要改 4 处：

1. 删除 `dist.init_process_group()` 和 `DDP()` 包装
2. 用 `deepspeed.initialize()` 替换，返回 `model_engine`
3. `loss.backward()` → `model_engine.backward(loss)`
4. `optimizer.step(); scheduler.step(); optimizer.zero_grad()` → `model_engine.step()`（一行搞定）

新增 `ds_config.json` 配置文件，启动命令改为 `deepspeed --num_gpus=8 train.py`。

---

### Q7：`ds_config.json` 中的 `gradient_accumulation_steps` 和 `train_micro_batch_size_per_gpu` 如何影响全局 batch size？

**答**：

```
全局 batch = train_micro_batch_size_per_gpu × gradient_accumulation_steps × GPU 数量
```

例如：`micro_batch=4`，`accum=8`，`8 GPU` → 全局 batch = 256。

梯度累积的意义：可以在不增加显存的前提下增大等效 global batch（显存仅受 micro_batch 大小影响）。

## ⭐⭐ 进阶题

### Q8：ZeRO 底层使用什么通信原语？与 DDP 的 All-Reduce 有何区别？

**答**：ZeRO 将 All-Reduce 拆分为 **Reduce-Scatter + All-Gather**：

- **Reduce-Scatter**：每 GPU 将自己的梯度贡献给全局，但只**接收**自己负责的 1/N 部分的全局求和 → 产生梯度分片
- **All-Gather**：每 GPU 广播自己的参数分片，所有 GPU 收到完整参数 → 按需重建

两者合计通信量（~2Ψ）与 All-Reduce 完全相同，但 ZeRO 在 Reduce-Scatter 后不立即 All-Gather，只保留 1/N 数据 → 节省 N 倍内存而无额外通信代价。

---

### Q9：ZeRO Stage 3 的前向传播是如何工作的？参数怎样按需重建？

**答**：ZeRO Stage 3 下，每张 GPU 只保存 1/N 的参数分片。前向传播时按层执行：

1. **All-Gather** 当前层所有 GPU 的参数分片 → 得到完整参数
2. 执行当前层的前向计算
3. **释放**完整参数，只保留自己的分片

关键优化：**预取（Prefetch）**——在计算第 i 层时，同时 All-Gather 第 i+1 层的参数，隐藏通信延迟。通过 `"overlap_comm": true` 启用。

反向传播方向相反：再次 All-Gather → 计算梯度 → Reduce-Scatter 梯度 → 释放完整参数。

---

### Q10：Activation Checkpointing（梯度检查点）的原理和代价是什么？

**答**：正常训练中，前向传播的所有中间激活值（用于反向传播计算梯度）都保存在显存中，对于大 batch 和长序列，这可能高达几十 GB。

Activation Checkpointing 的策略：**只在选定的检查点边界保存激活，其余的反向传播时重新计算**。

- **显存节省**：~90%（激活值）
- **计算代价**：额外执行一次前向传播，总计算量增加 ~33%
- **何时开启**：当激活值显存 > 总显存的 20-30%，或使用长序列（seq_len > 2048）

---

### Q11：ZeRO-Infinity 相比 ZeRO Stage 3 的核心差异是什么？

**答**：ZeRO Stage 3 仅将模型状态分片到 GPU 显存；ZeRO-Infinity 进一步将参数和优化器状态**卸载（Offload）**到 CPU RAM 甚至 NVMe SSD：

| 层级             | 带宽     | ZeRO-Infinity 用途           |
| ---------------- | -------- | ---------------------------- |
| GPU HBM          | ~2 TB/s  | 实际计算                     |
| CPU RAM（PCIe）  | ~16 GB/s | 优化器状态、参数 Offload     |
| NVMe（通过 CPU） | ~6 GB/s  | 超大模型参数、优化器 Offload |

核心技术：异步预取（参数从 CPU/NVMe 取到 GPU 的过程与 GPU 计算重叠），CPU 上执行 Adam 优化步骤（利用 AVX512 并行），`pin_memory=true` 提升 PCIe DMA 速度。

代价：吞吐量显著下降（~30-60%），主要瓶颈在 PCIe/NVMe 带宽。

---

### Q12：DeepSpeed Pipeline Parallelism 中的"气泡"问题是什么？如何用 1F1B 调度缓解？

**答**：流水线并行将模型按层切分到不同 GPU Stage。朴素调度中，Stage N 必须等待 Stage N-1 的输出，导致大量空闲时间（气泡），气泡比例 = (Stage数 - 1) / micro-batch数。

**1F1B（One-Forward-One-Backward）调度**：交叉执行前向和反向，一旦最后一个 Stage 完成第一个 micro-batch 的前向，立即开始其反向传播，而不等待所有 micro-batch 完成前向。这样前向和反向在流水线中"交织"，大幅减少气泡。

气泡比例从 ~(K-1)/M 降低到 ~(K-1)/(M×K)（K = Stage 数，M = micro-batch 数）。增大 M 可以进一步压缩气泡。

---

### Q13：ZeRO Stage 3 保存 Checkpoint 有什么注意事项？

**答**：ZeRO Stage 3 下每张 GPU 只有 1/N 的参数，直接 `model.state_dict()` 得到的是分片，无法直接用于推理。

正确做法：

1. 使用 `model_engine.save_checkpoint()` 保存 DeepSpeed 格式（包含分片信息，恢复训练用）
2. 在 ds_config 中设置 `"stage3_gather_16bit_weights_on_model_save": true`，调用 `model_engine.module.save_pretrained()` 保存完整 HuggingFace 格式
3. 手动 All-Gather：调用 `deepspeed.utils.zero_to_fp32.get_fp32_state_dict_from_zero_checkpoint()` 合并分片

### Q14：如何在 HuggingFace Trainer 中使用 DeepSpeed？

**答**：只需在 `TrainingArguments` 中添加 `deepspeed="ds_config.json"` 参数：

```python
training_args = TrainingArguments(
    output_dir="./output",
    per_device_train_batch_size=4,
    bf16=True,
    deepspeed="ds_config.json",  # 就这一行！
    ...
)
trainer = Trainer(model=model, args=training_args, ...)
trainer.train()
```

HuggingFace Trainer 会自动处理 DeepSpeed 初始化、checkpoint 保存和分布式设置。

## ⭐⭐⭐ 高级题

### Q15：ZeRO vs Megatron Tensor Parallelism，各自适合什么场景？两者可以结合吗？

**答**：

| 维度         | ZeRO（数据并行 + 状态分片）             | Megatron Tensor Parallel            |
| ------------ | --------------------------------------- | ----------------------------------- |
| **本质**     | 每张卡存全部层，每层 1/N 的参数         | 每张卡存某些层矩阵的部分行/列       |
| **通信模式** | All-Gather + Reduce-Scatter（在时间上） | All-Reduce（在每一层的计算中）      |
| **适用场景** | 数据并行扩展，模型宽度适中              | 单层参数量极大（宽层），紧密 NVLink |
| **易用性**   | 高（几乎不改模型代码）                  | 低（需要修改矩阵乘法实现）          |

两者可以结合形成 **3D 并行**（DeepSpeed + Megatron）：

```
3D 并行 = 数据并行（ZeRO） × 流水线并行 × 张量并行

示例：256 GPU 训 GPT-3
  数据并行：8（ZeRO Stage 1）
  流水线并行：4（按层切分）
  张量并行：8（单层矩阵分片）
```

ZeRO 处理优化器状态冗余，Megatron 处理单层参数过大的问题，两者正交互补。

### Q16：如何估算给定模型和训练配置下的训练吞吐量？MFU 的意义是什么？

**答**：

**理论 FLOPs 估算**：LLM 前向传播约 2×参数量 FLOPs，训练（含反向）约 6×参数量：

```
FLOPs/token = 6 × Ψ（Ψ 为参数量）
7B 模型：6 × 7×10⁹ = 4.2×10¹⁰ FLOPs/token
```

**MFU（Model FLOPs Utilization）**：

```
MFU = 实际 FLOPs/s / GPU 峰值 FLOPs/s
    = (FLOPs/token × tokens/s/GPU) / GPU_peak_FLOPS

A100 BF16 峰值 = 312 TFLOPs/s
若 7B 模型跑 3000 tokens/s/GPU：
  MFU = (4.2×10¹⁰ × 3000) / (312×10¹²) ≈ 40%
```

MFU > 50% 为优秀水平；< 30% 通常意味着存在通信瓶颈、数据加载瓶颈或配置不当。

### Q17：多节点训练时，NCCL 通信性能差的常见原因和排查方法？

**答**：

**常见原因**：

1. InfiniBand 未启用，降级为 TCP（带宽从 200 GB/s 降至 ~10 GB/s）
2. NCCL 选择了错误的网络接口
3. MTU 设置不当导致分片
4. RoCE/IB 的 RDMA 未正确配置

**排查步骤**：

```bash
# 1. 确认 IB 设备可见
ibstat

# 2. 运行 nccl-tests 测量实际带宽
./build/all_reduce_perf -b 1G -e 1G -f 2 -g 8 -n 20

# 3. 开启 NCCL 调试日志
NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=INIT torchrun ...

# 4. 强制指定 IB 设备和 GID
export NCCL_IB_HCA=mlx5_0
export NCCL_IB_GID_INDEX=3
```

实际测量带宽与 `nccl-tests` 理论值差距 > 20% 时，通常是 IB 配置问题。

### Q18：请设计一个在 4 节点 × 8 GPU（共 32 张 A100 80GB）上训练 LLaMA-70B 的完整并行策略。

**答**：LLaMA-70B 全量训练显存需求：70B × 16 = 1120 GB，32 张 80GB = 2560 GB（约 2.3×）。

**推荐策略**：ZeRO Stage 3（不需要 CPU Offload）

```
理论每卡显存（ZeRO Stage 3，N=32）：
  参数：70B × 2 / 32 = 4.4 GB
  梯度：70B × 2 / 32 = 4.4 GB
  优化器状态：70B × 12 / 32 = 26.3 GB
  激活值（batch=2, seq=4096）：~8 GB
  合计：~43 GB < 80 GB ✅
```

**配置要点**：

```json
{
  "zero_optimization": {
    "stage": 3,
    "overlap_comm": true,
    "stage3_prefetch_bucket_size": 5e7,
    "stage3_param_persistence_threshold": 1e6,
    "stage3_gather_16bit_weights_on_model_save": true
  },
  "bf16": { "enabled": true },
  "train_micro_batch_size_per_gpu": 2,
  "gradient_accumulation_steps": 8
}
```

**全局 batch**：2 × 8 × 32 = 512，配合 cosine LR schedule 和线性 warmup。

如果未来扩展到 70B+ 或需要更大吞吐：叠加 Tensor Parallel（组内 4 卡）+ ZeRO（组间 8 个进程组），形成 3D 并行。

## 场景题

### Q19：你接到任务，在 8 张 A100 80GB 上训练 LLaMA-13B，但每次都 OOM，如何系统排查？

**答**：按照以下步骤：

1. **确认实际显存需求**：13B × 16 = 208 GB > 8 × 80 = 640 GB（理论够），OOM 可能来自激活值。

2. **加 `"memory_breakdown": true`**，查看哪一项占用最多。

3. **决策树**：
   - 若 `model_states` 过大 → 升级 ZeRO Stage（2 → 3）
   - 若 `activation` 过大 → 启用 `activation_checkpointing`，或减小 `per_device_train_batch_size`
   - 若 `grad_buffer` 过大 → 减小 `reduce_bucket_size`（从 5e8 降到 2e8）

4. **推荐配置**：ZeRO Stage 2 + Activation Checkpointing，每卡约 55 GB（13B Stage 2）+ 激活值减少后 < 80 GB。

### Q20：线上推理场景，DeepSpeed-Inference 和 vLLM 该如何选择？

**答**：

| 场景                                 | 推荐                                                  |
| ------------------------------------ | ----------------------------------------------------- |
| 追求极致吞吐，高并发请求             | vLLM（PagedAttention + Continuous Batching 优势明显） |
| 已有 DeepSpeed 训练基础，快速部署    | DeepSpeed-MII（生态一致，配置简单）                   |
| 需要 Dynamic SplitFuse 降低 P99 延迟 | DeepSpeed-MII                                         |
| 需要广泛模型支持（如最新架构）       | vLLM（社区更活跃，更新更快）                          |
| 需要 INT4/FP8 量化                   | TensorRT-LLM（最高效，但迁移成本大）                  |

两者都支持张量并行，DeepSpeed-MII 在稳定高并发场景下的延迟分布更均匀（Dynamic SplitFuse 的优势），vLLM 在突发流量下整体吞吐更高。
