## ⭐ 基础题

### Q1：消息队列的三大核心价值是什么？

**参考答案**：

1. **解耦**：生产者和消费者独立演进，互不感知
2. **异步**：生产者发完消息立即返回，不等消费者处理
3. **削峰**：突发流量被队列缓冲，消费者按自身能力匀速处理

---

### Q2：Kafka 为什么吞吐量这么高？

**参考答案**：

四个核心设计：

1. **顺序写磁盘**：append-only log，顺序写速度接近内存
2. **零拷贝**：sendfile 系统调用，数据直接从磁盘到网卡
3. **分区并行**：多 Partition 分布在多 Broker 上，读写并行
4. **批量+压缩**：Producer 批量发送，Snappy/LZ4 压缩减少网络 I/O

---

### Q3：Kafka 的 Consumer Group 是什么？消费者数量和分区数的关系？

**参考答案**：

Consumer Group 是一组消费者的逻辑组。同一组内，每个 Partition 只被一个 Consumer 消费。

- 消费者数 < 分区数：部分消费者处理多个分区
- 消费者数 = 分区数：一对一，最佳并行
- 消费者数 > 分区数：多余消费者空闲

---

### Q4：At-most-once、At-least-once、Exactly-once 分别是什么？

**参考答案**：

| 语义          | 含义     | 风险       | 实现           |
| ------------- | -------- | ---------- | -------------- |
| At-most-once  | 最多一次 | 可能丢消息 | 发送不重试     |
| At-least-once | 至少一次 | 可能重复   | 重试+Ack       |
| Exactly-once  | 精确一次 | 最复杂     | 幂等+事务+去重 |

大多数系统选择 At-least-once + 消费端幂等。

---

### Q5：Kafka 和 RabbitMQ 的核心区别是什么？如何选型？

**参考答案**：

- **Kafka**：分布式日志，高吞吐，消息持久保留。适合日志、事件流、大数据管道
- **RabbitMQ**：传统消息队列，灵活路由（Exchange），微秒级延迟。适合任务队列、RPC

选型：吞吐优先 → Kafka；路由灵活+低延迟 → RabbitMQ。

---

### Q6：什么是消息的顺序性？Kafka 如何保证？

**参考答案**：

Kafka 只保证**同一 Partition 内消息有序**。跨 Partition 不保证全局有序。

保证特定消息有序的方法：

- 指定 key（如 order_id）发送，相同 key 路由到同一 Partition
- 只用 1 个 Partition（牺牲并行度，不推荐）

---

### Q7：什么是死信队列（DLQ）？什么时候使用？

**参考答案**：

消息因重试耗尽/格式错误/业务异常无法处理时，转入 DLQ 而非丢弃。

用途：

- 后续人工审查或定时重试
- 避免"毒消息"阻塞正常消费
- 监控 DLQ 长度作为系统健康指标

---

### Q8：Kafka 的 offset 管理机制是什么？

**参考答案**：

Offset 是消费者在 Partition 中的消费位置。Kafka 0.9+ 将 offset 存储在内部 Topic `__consumer_offsets` 中。

两种提交方式：

- **自动提交**：定时提交（可能重复消费或丢失）
- **手动提交**：消费者处理完后主动提交（更可靠）

## ⭐⭐ 进阶题

### Q9：Kafka 的 ISR 机制是什么？acks 参数如何影响可靠性？

**参考答案**：

ISR（In-Sync Replicas）= 与 Leader 保持同步的副本集。

| acks   | 含义         | 可靠性                | 性能 |
| ------ | ------------ | --------------------- | ---- |
| 0      | 不等确认     | 最低（可能丢）        | 最高 |
| 1      | Leader 确认  | 中（Leader 挂可能丢） | 中   |
| all/-1 | ISR 全部确认 | 最高                  | 最低 |

生产建议：`acks=all` + `min.insync.replicas=2` + 3 副本。

---

### Q10：如何处理消息积压？

**参考答案**：

1. **短期**：临时增加消费者实例（不超过分区数）
2. **中期**：优化消费逻辑（批量处理、异步 I/O、减少外部调用）
3. **紧急**：建临时 Topic，旧消费者只转发不处理，新消费者集群处理

**预防**：监控消费延迟（Consumer Lag），设置告警。

---

### Q11：Kafka 如何实现 Exactly-Once 语义？

**参考答案**：

三层保障：

1. **幂等 Producer**：`enable.idempotence=true`，每条消息带 PID+序列号，Broker 去重
2. **事务**：`transactional.id`，跨分区原子写入
3. **Consumer 端**：将 offset 提交和业务处理放在同一个事务中（如写入数据库）

---

### Q12：RabbitMQ 的 Exchange 类型有哪些？分别适用什么场景？

**参考答案**：

| Exchange | 路由规则                         | 场景               |
| -------- | -------------------------------- | ------------------ |
| Direct   | 精确匹配 routing key             | 任务分发到指定队列 |
| Fanout   | 广播到所有绑定队列               | 通知所有服务       |
| Topic    | 通配符（`*` 一个词, `#` 多个词） | 日志分级路由       |
| Headers  | 匹配消息头                       | 复杂路由条件       |

---

### Q13：Kafka 的分区重平衡（Rebalance）是什么？有什么问题？

**参考答案**：

Consumer Group 成员变化时（加入/退出/崩溃），Kafka 重新分配分区给消费者。

**问题**：Rebalance 期间所有消费者暂停消费（Stop-The-World），大 Group 可能耗时几十秒。

**优化**：

- 使用 CooperativeStickyAssignor（增量 Rebalance）
- 设置合理的 session.timeout.ms 和 heartbeat.interval.ms
- 避免消费者频繁上下线

---

### Q14：如何保证消息不丢失？

**参考答案**：

三端保障：

1. **Producer 端**：`acks=all` + 失败重试
2. **Broker 端**：副本数 ≥ 3 + `min.insync.replicas=2` + 刷盘策略
3. **Consumer 端**：手动提交 offset（处理完再提交）

---

### Q15：什么是 Kafka Connect 和 Kafka Streams？

**参考答案**：

- **Kafka Connect**：数据管道工具，将外部系统（MySQL/ES/S3）与 Kafka 对接。Source Connector 导入，Sink Connector 导出
- **Kafka Streams**：轻量级流处理库（不是独立集群），嵌入 Java 应用中处理 Kafka 数据

---

### Q16：Pulsar 相比 Kafka 的核心优势是什么？

**参考答案**：

1. **计算存储分离**：Broker 无状态 + BookKeeper 存储，独立扩缩
2. **多租户原生支持**：Tenant → Namespace → Topic 层级隔离
3. **分层存储**：热数据在 BookKeeper，冷数据自动转 S3/HDFS
4. **统一消息模型**：同时支持队列和流（Kafka 偏流，RabbitMQ 偏队列）

---

## ⭐⭐⭐ 高级题

### Q17：如何设计一个支持延迟消息的消息队列？

**参考答案**：

方案 1（RabbitMQ 插件）：`rabbitmq_delayed_message_exchange` 插件
方案 2（时间轮）：多级时间轮（类似 Kafka/Netty 的 HashedWheelTimer）
方案 3（排序队列）：Redis ZSET 存储消息，score=到期时间戳，定时扫描

Kafka 不原生支持延迟消息，常用方案：按延迟级别建不同 Topic（delay-5s/delay-1m/delay-1h）。

---

### Q18：Kafka Controller 的作用是什么？选举机制如何工作？

**参考答案**：

Controller 是 Kafka 集群的"管理者"，负责：

- 分区 Leader 选举
- Broker 上下线感知
- 分区副本重分配

选举：在 ZooKeeper 模式下通过抢占 `/controller` 临时节点；在 KRaft 模式下通过 Raft 选举。

---

### Q19：如何实现跨机房消息同步？

**参考答案**：

- **Kafka MirrorMaker 2**：基于 Kafka Connect，支持双向同步、自动 offset 映射
- **Pulsar Geo-Replication**：原生支持跨数据中心异步复制
- **自建方案**：消费源集群 → 写入目标集群 + 去重

关键问题：网络延迟导致的消息乱序、冲突解决、环形复制避免。

---

### Q20：如何从 Kafka 迁移到 Pulsar（或反向）而不停服？

**参考答案**：

双写双读方案：

1. Producer 同时写 Kafka 和 Pulsar
2. Consumer 同时从两个集群消费（去重）
3. 验证数据一致后，逐步切换 Consumer 到新集群
4. 最后切换 Producer

---

### Q21：Event Sourcing 和 CQRS 与消息队列的关系？

**参考答案**：

- **Event Sourcing**：将状态变更记录为不可变事件序列（Kafka 的 append-only log 天然适合）
- **CQRS**：读写分离，写端生成事件 → 消息队列 → 读端消费事件更新物化视图

Kafka 作为事件存储：利用 log compaction 保留每个 key 的最新状态。

---

### Q22：Flink 和 Kafka Streams 的区别？如何选型？

**参考答案**：

|            | Flink                       | Kafka Streams          |
| ---------- | --------------------------- | ---------------------- |
| **部署**   | 独立集群                    | 嵌入应用（无额外集群） |
| **数据源** | Kafka + 文件 + 数据库 + ... | 仅 Kafka               |
| **复杂度** | 高（状态管理/Checkpoint）   | 低（轻量级）           |
| **适用**   | 大规模流处理/复杂事件处理   | 简单流转换/聚合        |

## 🎯 场景题

### Q23：设计一个电商订单超时取消系统。

**参考答案**：

方案：延迟消息

1. 下单时发送延迟消息（30 分钟后投递）
2. 消费者收到后检查订单状态：已支付 → 忽略；未支付 → 取消订单 + 释放库存

实现：RabbitMQ 延迟插件 / Kafka 延迟 Topic + 定时消费 / Redis ZSET 轮询。

---

### Q24：日志收集系统每天 10TB 数据，如何设计从采集到分析的完整管道？

**参考答案**：

```
应用 → Filebeat/Fluentd（采集）→ Kafka（缓冲+分发）
  → Flink（实时分析/告警）
  → Elasticsearch（搜索/仪表盘）
  → S3/HDFS（归档/离线分析）
```

Kafka 分区：按服务名做 key，保证同一服务的日志有序。保留 7 天热数据，Tiered Storage 冷数据转 S3。

---

### Q25：你的系统在消息消费时发现大量重复消息，如何排查和解决？

**参考答案**：

**排查**：

1. 检查 Producer 是否重试导致重复发送（网络超时 + 重试）
2. 检查 Consumer 是否 Rebalance 导致重复消费（offset 提交前 Rebalance）
3. 检查是否有多个 Consumer Group 消费同一 Topic

**解决**：

1. Producer：开启幂等（`enable.idempotence=true`）
2. Consumer：手动提交 offset + 业务去重表（Redis/DB 唯一键）
3. 消息体携带唯一 ID（如 UUID），消费端查重后处理
