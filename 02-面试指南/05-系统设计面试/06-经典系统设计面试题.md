### Q9: 布隆过滤器在短链系统中如何使用？误判率如何计算？

<details>
<summary>参考答案</summary>

布隆过滤器（Bloom Filter）是一种空间效率极高的概率性数据结构，在短链系统中用于**快速判断一个短链是否已存在**，避免昂贵的数据库查询。

#### 为什么需要布隆过滤器

在使用 Hash 截断方案生成短链时，可能产生冲突。每次生成新短链都需要检查是否已存在：

```
方案 A（无布隆过滤器）：
  生成短链 → 查询数据库是否存在 → 不存在 → 插入
  问题：每次都要查数据库，18 亿条记录的查询开销很大

方案 B（有布隆过滤器）：
  生成短链 → 布隆过滤器判断 → "一定不存在" → 直接插入
                              → "可能存在" → 查数据库确认
  优势：99%+ 的查询在内存中完成，极少访问数据库
```

#### 布隆过滤器工作原理

```
插入元素 "abc":
  hash1("abc") = 3  →  位数组第 3 位置 1
  hash2("abc") = 7  →  位数组第 7 位置 1
  hash3("abc") = 11 →  位数组第 11 位置 1

  位数组: [0,0,0,1,0,0,0,1,0,0,0,1,0,0,0]
                ↑           ↑           ↑

查询元素 "xyz":
  hash1("xyz") = 3  →  第 3 位 = 1 ✓
  hash2("xyz") = 5  →  第 5 位 = 0 ✗ → 一定不存在！

查询元素 "def":
  hash1("def") = 3  →  第 3 位 = 1 ✓
  hash2("def") = 7  →  第 7 位 = 1 ✓
  hash3("def") = 11 →  第 11 位 = 1 ✓
  → 可能存在（也可能是误判！需要查数据库确认）
```

#### 误判率计算

布隆过滤器的误判率（False Positive Rate）公式：

```
FPR ≈ (1 - e^(-kn/m))^k

其中：
  m = 位数组大小（bit）
  n = 已插入元素数量
  k = 哈希函数数量

最优哈希函数数量：k = (m/n) × ln2 ≈ 0.693 × (m/n)
```

**实际案例计算**：

```
已知：
  n = 18 亿条短链
  目标误判率 FPR = 1%（0.01）

求：需要多大的位数组？

公式：m = -n × ln(FPR) / (ln2)^2
  m = -18亿 × ln(0.01) / (0.693)^2
  m = -18亿 × (-4.605) / 0.48
  m ≈ 173 亿 bit ≈ 2.02 GB

最优哈希函数数量：
  k = 0.693 × (173亿/18亿) ≈ 6.66 ≈ 7 个
```

#### 在短链系统中的完整应用

```python
import mmh3
from bitarray import bitarray

class BloomFilter:
    def __init__(self, size: int, num_hashes: int):
        self.size = size
        self.num_hashes = num_hashes
        self.bit_array = bitarray(size)
        self.bit_array.setall(0)

    def add(self, item: str):
        for seed in range(self.num_hashes):
            index = mmh3.hash(item, seed) % self.size
            self.bit_array[index] = 1

    def might_contain(self, item: str) -> bool:
        for seed in range(self.num_hashes):
            index = mmh3.hash(item, seed) % self.size
            if not self.bit_array[index]:
                return False  # 一定不存在
        return True  # 可能存在

# 使用示例
bf = BloomFilter(size=20_000_000_000, num_hashes=7)

def create_short_url(long_url):
    short_code = generate_hash(long_url)
    if not bf.might_contain(short_code):
        # 一定不存在，直接插入
        db.insert(short_code, long_url)
        bf.add(short_code)
        return short_code
    else:
        # 可能存在，查数据库确认
        if not db.exists(short_code):
            db.insert(short_code, long_url)
            bf.add(short_code)
            return short_code
        else:
            # 真的冲突了，重新生成
            return create_short_url(long_url + salt)
```

#### 布隆过滤器的局限性

| 局限 | 说明 | 解决方案 |
|------|------|---------|
| 不支持删除 | 无法将元素从过滤器中移除 | 使用 Counting Bloom Filter |
| 误判 | 存在假阳性 | 控制误判率 + 数据库兜底 |
| 不可扩容 | 位数组大小固定 | 预估容量或使用 Scalable Bloom Filter |

### Q10: Feed 流系统中的"大 V 问题"是什么？如何用混合模式解决？

<details>
<summary>参考答案</summary>

大 V 问题是 Feed 流系统中最经典的工程挑战之一，直接决定了系统的架构选型。

#### 什么是大 V 问题

在纯推模式（Fan-out on Write）下，当一个拥有海量粉丝的大 V 发布内容时，系统需要将这条内容写入**每一个粉丝的收件箱**。

```
Elon Musk 发布一条推文（假设 5000 万粉丝）：
  → 需要写入 5000 万个收件箱
  → 每次写入 100 字节，总写入量 = 5000万 × 100B = 5GB
  → 即使每秒写入 10 万条，也需要 500 秒（8 分钟）才能完成
  → 在这 8 分钟内，部分粉丝看不到最新推文
```

**核心矛盾**：
- **写放大（Write Amplification）**：一次发布触发数千万次写入
- **延迟不可接受**：Fan-out 完成前，部分用户看不到新内容
- **资源浪费**：5000 万粉丝中，可能只有 10% 是活跃用户

#### 混合模式（Hybrid Approach）

**核心思想**：根据用户类型选择不同的 Fan-out 策略。

```
┌───────────────────────────────────────────────┐
│              混合模式架构                        │
│                                               │
│  发布动态                                       │
│    ├─ 普通用户（粉丝 < 10万）→ 推模式            │
│    │    → Fan-out 到所有粉丝收件箱               │
│    │                                           │
│    └─ 大V用户（粉丝 ≥ 10万）→ 拉模式            │
│         → 只写发件箱，不做 Fan-out               │
│                                               │
│  读取时间线                                     │
│    用户 B 打开首页：                             │
│    ├─ 读取 B 的收件箱（推模式的内容，已排好序）    │
│    ├─ 读取 B 关注的大V 的发件箱（拉模式，实时查）  │
│    └─ 合并两部分，按时间排序，返回                │
└───────────────────────────────────────────────┘
```

#### 关键实现细节

**1. 大 V 阈值如何确定？**

```python
# 方案：动态阈值，基于系统负载调整
VIP_THRESHOLD = 100_000  # 粉丝数阈值

def on_publish(user_id, content):
    follower_count = get_follower_count(user_id)

    if follower_count < VIP_THRESHOLD:
        # 推模式：异步 Fan-out
        fan_out_to_followers(user_id, content)
    else:
        # 拉模式：只写发件箱
        write_to_outbox(user_id, content)
```

**2. 读取时如何合并？**

```python
def get_timeline(user_id):
    # 第一部分：收件箱（推模式的内容）
    inbox_posts = redis.zrevrange(f"inbox:{user_id}", 0, 50)

    # 第二部分：关注的大V 的最新内容（拉模式）
    vip_followings = get_vip_followings(user_id)
    vip_posts = []
    for vip_id in vip_followings:
        posts = redis.zrevrange(f"outbox:{vip_id}", 0, 10)
        vip_posts.extend(posts)

    # 合并排序
    all_posts = inbox_posts + vip_posts
    all_posts.sort(key=lambda p: p.timestamp, reverse=True)

    return all_posts[:50]  # 返回最新 50 条
```

**3. 性能优化**

- **缓存大 V 发件箱**：大 V 的最新内容缓存在 Redis，避免数据库查询
- **限制拉取范围**：每个大 V 只拉取最新 N 条，避免全量扫描
- **预计算活跃用户**：只对最近 7 天登录过的用户做 Fan-out
- **异步 Fan-out**：使用消息队列异步推送，不阻塞发布流程

#### 业界实践

| 公司 | 策略 |
|------|------|
| Twitter | 混合模式，阈值约 10 万粉丝 |
| Instagram | 混合模式 + 推荐算法排序 |
| 微信朋友圈 | 纯推模式（好友数上限 5000，无大 V 问题） |
| 微博 | 混合模式 + 热度分层 |

### Q11: 即时通讯系统如何保证消息不丢失？描述 ACK/重传/去重机制

<details>
<summary>参考答案</summary>

消息的可靠投递是 IM 系统的核心挑战。网络不稳定、服务器故障、客户端崩溃都可能导致消息丢失。

#### 消息投递的三种语义

| 语义 | 含义 | 实现难度 |
|------|------|---------|
| At-Most-Once | 最多投递一次（可能丢失） | 最简单 |
| At-Least-Once | 至少投递一次（可能重复） | 中等 |
| Exactly-Once | 恰好投递一次（不丢不重） | 最难 |

IM 系统通常采用 **At-Least-Once + 客户端去重** 来逼近 Exactly-Once。

#### ACK 确认机制

```
发送方 A                 服务器 S                  接收方 B
  │                        │                        │
  │──── 发送消息 ─────────→│                        │
  │                        │──── 转发消息 ─────────→│
  │                        │                        │
  │←──── Server ACK ───────│                        │
  │   (服务器已收到)        │←──── Client ACK ───────│
  │                        │      (B 已收到)         │
  │                        │                        │
  │←──── 已读回执 ──────────│←──── 已读通知 ──────────│
  │      (可选)             │      (可选)             │
```

**两级 ACK 的含义**：
1. **Server ACK**：服务器确认收到消息并已持久化，保证消息不丢失
2. **Client ACK**：接收端确认已收到消息，服务器可以停止重试

#### 重传机制

当 ACK 超时未收到时，触发重传：

```python
class MessageSender:
    def __init__(self):
        self.pending_acks = {}  # msg_id -> (message, retry_count, send_time)
        self.MAX_RETRIES = 3
        self.ACK_TIMEOUT = 5  # 秒

    async def send_message(self, message):
        msg_id = message['client_msg_id']
        self.pending_acks[msg_id] = (message, 0, time.time())
        await self.ws.send(json.dumps(message))
        # 启动超时检查
        asyncio.create_task(self._check_ack_timeout(msg_id))

    async def _check_ack_timeout(self, msg_id):
        await asyncio.sleep(self.ACK_TIMEOUT)
        if msg_id in self.pending_acks:
            msg, retry_count, _ = self.pending_acks[msg_id]
            if retry_count < self.MAX_RETRIES:
                # 重传
                self.pending_acks[msg_id] = (msg, retry_count + 1, time.time())
                await self.ws.send(json.dumps(msg))
                asyncio.create_task(self._check_ack_timeout(msg_id))
            else:
                # 超过最大重试次数，标记为发送失败
                self._mark_failed(msg_id)

    def on_ack_received(self, msg_id):
        # 收到 ACK，移除待确认列表
        self.pending_acks.pop(msg_id, None)
```

#### 去重机制

重传可能导致消息重复投递，需要在接收端去重：

```python
class MessageReceiver:
    def __init__(self):
        # 使用集合记录已处理的消息 ID（保留最近 N 条）
        self.processed_msg_ids = OrderedDict()
        self.MAX_DEDUP_SIZE = 10000

    def on_message_received(self, message):
        msg_id = message['client_msg_id']

        # 检查是否已处理过
        if msg_id in self.processed_msg_ids:
            # 重复消息，丢弃但仍需发送 ACK
            self.send_ack(msg_id)
            return

        # 新消息，处理并记录
        self.processed_msg_ids[msg_id] = True
        if len(self.processed_msg_ids) > self.MAX_DEDUP_SIZE:
            self.processed_msg_ids.popitem(last=False)

        # 处理消息（展示给用户）
        self.display_message(message)
        # 发送 ACK
        self.send_ack(msg_id)
```

#### 关键设计点

**1. `client_msg_id` 的生成**

```python
import uuid
import time

def generate_client_msg_id(user_id: str) -> str:
    """客户端生成全局唯一消息 ID"""
    timestamp = int(time.time() * 1000)
    random_part = uuid.uuid4().hex[:8]
    return f"{user_id}_{timestamp}_{random_part}"
```

**2. 服务端持久化时机**

消息必须在发送 Server ACK **之前**完成持久化：

```
错误顺序：收到消息 → 发 ACK → 持久化（如果持久化失败，消息丢失）
正确顺序：收到消息 → 持久化 → 发 ACK（确保 ACK 代表已持久化）
```

**3. 离线消息处理**

```
用户 B 离线时：
  A 发消息 → 服务器持久化 → 发 Server ACK 给 A
  → 尝试推送给 B（失败，B 不在线）
  → 消息存入 B 的离线消息队列

用户 B 上线时：
  B 连接服务器 → 拉取离线消息 → 逐条 ACK
```

### Q12: 群聊场景中，写扩散和读扩散如何选择？大群（万人群）怎么处理？

<details>
<summary>参考答案</summary>

群聊的消息存储和分发策略是 IM 系统设计中的核心问题。群的规模决定了最佳方案。

#### 写扩散（Write Diffusion）

**原理**：一条消息写入**每个群成员的收件箱**（消息同步表），每人一份。

```
群 G 有 3 个成员：A、B、C
A 在群里发了一条消息 M

存储结构：
  sync_table_A: [..., M(seq=101)]
  sync_table_B: [..., M(seq=205)]
  sync_table_C: [..., M(seq=87)]
```

```sql
-- 写扩散的表结构
CREATE TABLE message_sync (
    user_id     BIGINT NOT NULL,
    sequence    BIGINT NOT NULL,  -- 用户维度的递增序号
    msg_id      BIGINT NOT NULL,
    PRIMARY KEY (user_id, sequence)
);

-- 写入时：为每个群成员插入一条记录
INSERT INTO message_sync (user_id, sequence, msg_id) VALUES
  (user_A, next_seq_A, msg_001),
  (user_B, next_seq_B, msg_001),
  (user_C, next_seq_C, msg_001);
```

**优点**：
- 读取简单：每个用户只查自己的同步表
- 多端同步天然支持：每个设备记录自己的 sequence 偏移量
- 统一入口：所有会话的消息通过一张表拉取

**缺点**：
- 写放大：群成员越多，写入量越大
- 存储冗余：N 个成员存 N 份

#### 读扩散（Read Diffusion）

**原理**：消息只在**群的消息表**中存一份，成员读取时去群的时间线查询。

```
群 G 的消息表：
  group_msg_table_G: [M1, M2, M3, ..., M(newest)]

每个用户记录自己在群 G 的已读位置：
  A 在群 G 的已读位置：msg_id = 95
  B 在群 G 的已读位置：msg_id = 100
```

```sql
-- 读扩散的表结构
CREATE TABLE group_message (
    group_id    BIGINT NOT NULL,
    msg_id      BIGINT NOT NULL,
    sender_id   BIGINT NOT NULL,
    content     TEXT,
    created_at  TIMESTAMP,
    PRIMARY KEY (group_id, msg_id)
);

-- 已读位置表
CREATE TABLE group_read_position (
    user_id     BIGINT NOT NULL,
    group_id    BIGINT NOT NULL,
    last_read_msg_id BIGINT DEFAULT 0,
    PRIMARY KEY (user_id, group_id)
);

-- 读取未读消息
SELECT * FROM group_message
WHERE group_id = ? AND msg_id > ?
ORDER BY msg_id ASC LIMIT 50;
```

**优点**：
- 写入简单：只写一份
- 存储高效：无冗余

**缺点**：
- 读取复杂：用户加入多个群时，需要查多个群的消息表
- 多端同步复杂：需要额外记录每个设备在每个群的已读位置

#### 选择策略

| 群规模 | 推荐方案 | 原因 |
|--------|---------|------|
| 小群（< 200 人） | 写扩散 | 写入量可控，读取效率高 |
| 大群（200~2000 人） | 读扩散 | 避免写放大，存储节约 |
| 超大群（> 2000 人） | 读扩散 + 推送通知 | 必须读扩散，否则写入量爆炸 |

#### 万人群的特殊处理

万人群（如 Discord 服务器、钉钉全员群）面临独特挑战：

```
┌──────────────────────────────────────────────────┐
│              万人群优化方案                         │
│                                                  │
│  1. 消息存储：纯读扩散，群消息表只存一份             │
│                                                  │
│  2. 推送策略：                                     │
│     ├─ 在线成员：通过 WebSocket 实时推送消息通知     │
│     ├─ 离线成员：不推送具体内容，只记录未读计数       │
│     └─ 免打扰模式：不推送，用户主动打开时拉取        │
│                                                  │
│  3. 消息拉取优化：                                  │
│     ├─ 分页加载：每次只拉 50 条                     │
│     ├─ 热点缓存：最新 200 条消息缓存在 Redis        │
│     └─ 冷数据：历史消息从 HBase/Cassandra 查询      │
│                                                  │
│  4. @功能特殊处理：                                 │
│     ├─ @all → 全员推送                             │
│     └─ @具体人 → 只推送给被 @ 的人                  │
└──────────────────────────────────────────────────┘
```

### Q13: BM25 算法相比 TF-IDF 有什么改进？核心公式是什么？

<details>
<summary>参考答案</summary>

BM25（Best Matching 25）是信息检索领域最经典的相关性算法，是 TF-IDF 的重大改进，至今仍是 Elasticsearch、Lucene 等搜索引擎的默认排序算法。

#### TF-IDF 的问题

TF-IDF 的核心思想正确（词频越高越重要，文档频率越高越不重要），但存在两个实际问题：

**问题一：词频饱和度缺失**

TF-IDF 中，词频（TF）是线性增长的。一个词在文档中出现 100 次的 TF 值是出现 1 次的 100 倍。但在实际中，一个词出现 10 次和出现 100 次，其重要性差距远没有 10 倍。

```
TF-IDF:  TF(t,d) = count(t in d)
  "机器学习" 出现 1 次 → TF = 1
  "机器学习" 出现 100 次 → TF = 100  (100 倍重要？不合理！)
```

**问题二：文档长度未归一化**

长文档天然包含更多词，TF 值更高，导致长文档被过度优先。

#### BM25 的改进

BM25 通过两个参数解决了上述问题：

**核心公式**：

```
BM25(q, d) = Σ IDF(qi) × [TF(qi, d) × (k1 + 1)] / [TF(qi, d) + k1 × (1 - b + b × |d|/avgdl)]
```

各部分解释：

```
IDF(qi) = ln[(N - n(qi) + 0.5) / (n(qi) + 0.5) + 1]
  N = 总文档数
  n(qi) = 包含词 qi 的文档数

TF 饱和函数 = TF × (k1 + 1) / (TF + k1 × ...)
  k1 控制词频饱和速度，通常取 1.2~2.0
  当 k1 → 0 时，TF 被忽略（只看 IDF）
  当 k1 → ∞ 时，退化为原始 TF

文档长度归一化 = 1 - b + b × |d| / avgdl
  b 控制文档长度惩罚强度，通常取 0.75
  |d| = 当前文档长度
  avgdl = 所有文档平均长度
  当 b = 0 时，不考虑文档长度
  当 b = 1 时，完全按文档长度归一化
```

#### 直观对比

```
           TF 值
  TF-IDF:   │          ╱
             │        ╱
             │      ╱      ← 线性增长，无饱和
             │    ╱
             │  ╱
             │╱
             └───────────── 词频

  BM25:     │
             │       ____── ← 趋近饱和（k1 控制）
             │     ╱
             │   ╱
             │  ╱
             │╱
             └───────────── 词频
```

#### Python 实现

```python
import math
from collections import Counter

class BM25:
    def __init__(self, documents: list[list[str]], k1=1.5, b=0.75):
        self.k1 = k1
        self.b = b
        self.docs = documents
        self.N = len(documents)
        self.avgdl = sum(len(d) for d in documents) / self.N

        # 计算每个词的文档频率
        self.df = Counter()
        for doc in documents:
            unique_terms = set(doc)
            for term in unique_terms:
                self.df[term] += 1

    def idf(self, term: str) -> float:
        n = self.df.get(term, 0)
        return math.log((self.N - n + 0.5) / (n + 0.5) + 1)

    def score(self, query: list[str], doc_index: int) -> float:
        doc = self.docs[doc_index]
        doc_len = len(doc)
        tf_counter = Counter(doc)
        total_score = 0.0

        for term in query:
            tf = tf_counter.get(term, 0)
            idf_val = self.idf(term)
            numerator = tf * (self.k1 + 1)
            denominator = tf + self.k1 * (1 - self.b + self.b * doc_len / self.avgdl)
            total_score += idf_val * numerator / denominator

        return total_score

    def search(self, query: list[str], top_k=10) -> list[tuple[int, float]]:
        scores = [(i, self.score(query, i)) for i in range(self.N)]
        scores.sort(key=lambda x: x[1], reverse=True)
        return scores[:top_k]
```

#### 参数调优建议

| 参数 | 默认值 | 调大效果 | 调小效果 |
|------|-------|---------|---------|
| k1 | 1.2~2.0 | 更重视高词频 | 削弱词频影响 |
| b | 0.75 | 更惩罚长文档 | 减少长度影响 |

**实际经验**：对于中文搜索，由于中文文档长度差异大，`b` 通常设置为 0.3~0.5 效果更好。

### Q14: 秒杀系统中如何用 Redis+Lua 脚本实现库存预扣减？为什么需要原子操作？

<details>
<summary>参考答案</summary>

库存预扣减是秒杀系统中最关键的技术点。Redis + Lua 脚本的组合能够在保证原子性的同时提供极高的性能。

#### 为什么需要原子操作

先看一个**非原子操作**导致超卖的案例：

```python
# 错误示例：非原子操作（会超卖）
def seckill_wrong(item_id, user_id):
    stock = redis.get(f"stock:{item_id}")  # 步骤 1：读取库存
    if int(stock) > 0:                     # 步骤 2：判断库存
        redis.decr(f"stock:{item_id}")     # 步骤 3：扣减库存
        return "success"
    return "sold_out"
```

**并发问题**：

```
时间线    线程 A                    线程 B
  T1     读取库存 = 1
  T2                              读取库存 = 1
  T3     判断 1 > 0 → True
  T4                              判断 1 > 0 → True
  T5     扣减库存 → stock = 0
  T6                              扣减库存 → stock = -1  ← 超卖！
```

步骤 1~3 不是原子操作，存在**竞态条件（Race Condition）**。

#### Redis + Lua 解决方案

Lua 脚本在 Redis 中是**原子执行**的，整个脚本作为一个操作，不会被其他命令打断。

```lua
-- seckill.lua：库存预扣减脚本
-- KEYS[1] = 库存 key，如 "stock:item_001"
-- KEYS[2] = 已购买用户集合 key，如 "purchased:item_001"
-- ARGV[1] = 用户 ID

-- 第一步：检查用户是否已购买（防止重复购买）
local purchased = redis.call('SISMEMBER', KEYS[2], ARGV[1])
if purchased == 1 then
    return -1  -- 已购买
end

-- 第二步：检查并扣减库存（原子操作）
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil or stock <= 0 then
    return 0   -- 库存不足
end

-- 第三步：扣减库存 + 记录用户
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])

return 1  -- 扣减成功
```

#### Python 调用端

| 方案 | 原子性 | 条件判断 | 性能 |

Lua 脚本是唯一能同时满足**原子性**和**条件判断**的方案。

- Lua 脚本执行时间：通常 < 1ms
- 注意：Lua 脚本执行期间会阻塞其他命令，因此脚本要尽量精简

### Q15: GFS 中 Chunk 大小为什么设置为 64MB？太大或太小有什么问题？

<details>
<summary>参考答案</summary>

Chunk 大小的选择是分布式文件存储系统中最基础也最关键的设计决策，它影响系统的元数据开销、网络效率和并发度。

#### GFS 选择 64MB 的原因

Google File System（GFS）的设计目标是存储**大文件**（通常数百 MB 到数 GB），面向的工作负载是**顺序读写**而非随机读写。

在此背景下，64MB 的 Chunk 大小是多个因素权衡的结果：

**1. 减少 Master 元数据量**

```
假设存储 1PB 数据：

Chunk = 64MB 时：
  元数据条目数 = 1PB / 64MB = 1600 万条
  每条元数据约 64 字节（chunk handle + 副本位置 + 版本号）
  总元数据 = 1600万 × 64B ≈ 1GB → 可放入内存

Chunk = 4KB 时（传统文件系统块大小）：
  元数据条目数 = 1PB / 4KB = 2560 亿条
  总元数据 = 2560亿 × 64B ≈ 16TB → 远超内存容量！
```

Master 将所有元数据保存在**内存**中以实现快速查找，Chunk 越小元数据越多，内存压力越大。

**2. 减少客户端与 Master 的交互**

客户端每次读写新的 Chunk 时都需要向 Master 请求 Chunk 的位置信息。Chunk 越大，单次读写跨越的 Chunk 数量越少，与 Master 的交互次数越少。

```
读取 1GB 文件：
  Chunk = 64MB → 需要 16 次与 Master 交互
  Chunk = 4KB  → 需要 26 万次与 Master 交互
```

**3. 减少网络开销**

每个 Chunk 的读写都需要建立网络连接。Chunk 越大，单次传输量越多，TCP 连接的建立和管理开销摊薄。

#### 太大 vs 太小的影响

| 维度 | Chunk 太小（如 4KB） | Chunk 太大（如 1GB） | 64MB（平衡） |
|------|---------------------|---------------------|-------------|
| 元数据量 | 巨大，Master 内存不够 | 极少 | 适中 |
| 内部碎片 | 少 | 大量小文件浪费空间 | 可接受 |
| 并发度 | 高（更多 Chunk 可并行） | 低（Chunk 粒度太粗） | 适中 |
| 热点问题 | 不明显 | 严重（小文件集中在少数 Chunk） | 可管理 |
| 网络效率 | 低（频繁建连） | 高 | 高 |

#### 热点问题详解

当 Chunk 较大且存储小文件时，一个 Chunk 可能只存一个小文件，该文件被频繁访问时，对应的 ChunkServer 成为热点：

```
Chunk A (64MB) 中只存了一个 1KB 的热点配置文件
→ 所有对该文件的请求都集中到 Chunk A 所在的 ChunkServer
→ 形成热点

GFS 的应对方案：
1. 提高热点 Chunk 的副本数
2. 客户端随机选择副本读取（负载均衡）
3. 应用层可以在文件名中加随机后缀分散存储
```

#### HDFS 的演进

HDFS 将默认 Block 大小从 64MB 提升到了 **128MB**（Hadoop 2.x 起），原因是：
- 硬件进步，网络带宽和磁盘吞吐量大幅提升
- 大数据场景下文件更大，128MB 能进一步减少 NameNode 内存压力
- MapReduce 任务的粒度与 Block 大小相关，128MB 减少了 Map 任务数量

</details>

### Q16: 分布式文件存储中如何实现故障恢复？数据如何保证不丢失？

<details>
<summary>参考答案</summary>

分布式文件存储系统面临的核心问题是：**硬件故障是常态而非异常**。Google 的统计数据表明，一个拥有数千台服务器的集群中，每天都会有机器故障。

#### 三层故障恢复机制

```
┌─────────────────────────────────────────┐
│           故障恢复三层架构                │
│                                         │
│  第一层：检测（快速发现故障）             │
│    └─ 心跳机制：ChunkServer → Master     │
│                                         │
│  第二层：恢复（保证数据不丢失）           │
│    └─ 副本重新复制 + Checksum 校验       │
│                                         │
│  第三层：预防（减少故障影响）             │
│    └─ 跨机架副本策略 + Master 高可用      │
└─────────────────────────────────────────┘
```

#### 第一层：心跳检测

```
ChunkServer 定期向 Master 发送心跳：

┌────────────┐    HeartBeat (每 3 秒)    ┌────────┐
│ChunkServer1│ ──────────────────────→  │ Master │
│ChunkServer2│ ──────────────────────→  │        │
│ChunkServer3│ ──────────────────────→  │        │
│ChunkServer4│ ────── X (超时) ─────→  │        │
└────────────┘                          └────────┘
                                           │
                                   检测到 CS4 故障
                                   标记 CS4 上的所有
                                   Chunk 为"副本不足"
```

心跳内容包含：
- ChunkServer 持有的 Chunk 列表
- 各 Chunk 的版本号
- ChunkServer 的磁盘使用率、负载等指标

#### 第二层：副本恢复

当某个 Chunk 的有效副本数低于目标值（默认 3）时，Master 启动重新复制：

```python
# 伪代码：副本恢复逻辑
def check_and_recover_chunks():
    for chunk in all_chunks:
        alive_replicas = get_alive_replicas(chunk)

        if len(alive_replicas) < TARGET_REPLICAS:
            # 需要恢复
            missing_count = TARGET_REPLICAS - len(alive_replicas)

            source = select_best_source(alive_replicas)

                initiate_chunk_copy(source, target, chunk)
```

**恢复优先级**：

| 优先级 | 条件 | 原因 |
|--------|------|------|
| 最高 | 只剩 1 个副本 | 再丢就永久丢失 |
| 高 | 只剩 2 个副本 | 风险较大 |
| 中 | 活跃文件的副本不足 | 影响正在使用的数据 |
| 低 | 冷数据的副本不足 | 不影响在线服务 |

#### Checksum 校验

每个 Chunk 被分成 64KB 的块，每个块存储一个 32-bit 的 Checksum：

```
┌──────────────────────────────────────────┐
│                 Chunk (64MB)              │
├──────────┬──────────┬──────────┬─────────┤
│ Block 1  │ Block 2  │ Block 3  │ ...     │
│ (64KB)   │ (64KB)   │ (64KB)   │         │
│ CRC=A1B2 │ CRC=C3D4 │ CRC=E5F6 │         │
└──────────┴──────────┴──────────┴─────────┘
```

读取时校验流程：
1. 读取数据块和对应的 Checksum
2. 计算数据块的 CRC32
3. 与存储的 Checksum 比对
4. 不匹配 → 数据损坏 → 从其他副本读取 → 通知 Master 重新复制

#### 第三层：跨机架副本策略

```
机架 1              机架 2              机架 3
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│ ChunkServer1 │  │ ChunkServer3 │  │ ChunkServer5 │
│  [Chunk A-1] │  │  [Chunk A-2] │  │              │
│              │  │              │  │              │
│ ChunkServer2 │  │ ChunkServer4 │  │ ChunkServer6 │
│              │  │              │  │  [Chunk A-3] │
└──────────────┘  └──────────────┘  └──────────────┘

Chunk A 的 3 个副本分布在 3 个不同机架上
→ 单机故障：不影响（还有 2 个副本）
→ 整个机架故障（交换机坏了）：不影响（还有 2 个副本在其他机架）
→ 两个机架同时故障：只有 1 个副本（概率极低，但仍可恢复）
```

#### Master 高可用

Master 是单点，如何保证其可用性？

```
┌──────────────┐    操作日志同步    ┌──────────────┐
│  Master      │ ────────────────→│  Shadow       │
│  (Active)    │                  │  Master       │
│              │                  │  (Standby)    │
│  - 内存元数据 │                  │  - 只读副本    │
│  - 操作日志   │                  │  - 热备       │
└──────────────┘                  └──────────────┘
       │
       │  操作日志持久化到多台机器
       ↓
┌──────────────┐
│  Operation   │
│  Log Store   │
│  (多副本)     │
└──────────────┘
```

- 操作日志实时同步到 Shadow Master
- Master 故障时，Shadow Master 接管（需要重新加载 ChunkServer 汇报的信息）
- 元数据的修改以操作日志形式持久化，可重放恢复

```python
class SnowflakeIDGenerator:
    """
    64 位 ID 结构：
    | 1 bit (符号) | 41 bit (时间戳) | 10 bit (机器ID) | 12 bit (序列号) |
    """
    def __init__(self, machine_id: int):
        self.machine_id = machine_id & 0x3FF  # 10 bit
        self.sequence = 0
        self.last_timestamp = -1
        self.epoch = 1704067200000  # 2024-01-01 基准时间

    def next_id(self) -> int:
        timestamp = int(time.time() * 1000) - self.epoch
        if timestamp == self.last_timestamp:
            self.sequence = (self.sequence + 1) & 0xFFF
            if self.sequence == 0:
                timestamp = self._wait_next_ms(timestamp)
        else:
            self.sequence = 0
        self.last_timestamp = timestamp
        return (timestamp << 22) | (self.machine_id << 12) | self.sequence
```

#### 第三步：端到端加密（E2EE）

**核心原理**：使用 Signal Protocol（Double Ratchet 算法），确保只有通信双方能解密消息，服务器无法读取。

```
Alice 和 Bob 的端到端加密流程：

1. 密钥交换（首次通信）
   ┌───────┐                              ┌───────┐
   │ Alice │                              │  Bob  │
   └───┬───┘                              └───┬───┘
       │                                       │
       │  ① 生成长期身份密钥对 (IK_A)           │
       │  ② 生成预签名密钥 (SPK_A)              │
       │  ③ 生成一次性密钥 (OPK_A)              │
       │                                       │
       │──── 公钥上传到服务器 ────→ 服务器 ←────│
       │                                       │
       │  ④ Alice 获取 Bob 的公钥包             │
       │  ⑤ X3DH 协议生成共享密钥              │
       │  ⑥ 使用共享密钥初始化 Double Ratchet   │
       │                                       │

2. 消息加密
   Alice 发送消息 "Hello"
   ├─ 用当前 Ratchet 密钥加密 → 密文 "x8f2a..."
   ├─ 附带 Alice 的 Ratchet 公钥
   └─ 发送给服务器（服务器只看到密文）

3. 密钥轮转（Perfect Forward Secrecy）
   每条消息使用不同的密钥
   → 即使某个密钥泄露，也无法解密其他消息
```

```python
# 简化的 E2EE 消息发送流程（伪代码）
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
import os

class E2EESession:
    def __init__(self, shared_secret: bytes):
        self.root_key = shared_secret
        self.chain_key = self._derive_chain_key(shared_secret)
        self.message_number = 0

    def encrypt_message(self, plaintext: str) -> dict:
        # 从链式密钥派生消息密钥
        message_key = self._derive_message_key(self.chain_key, self.message_number)
        # 推进链式密钥
        self.chain_key = self._advance_chain(self.chain_key)
        self.message_number += 1

        # AES-256-GCM 加密
        nonce = os.urandom(12)
        aesgcm = AESGCM(message_key)
        ciphertext = aesgcm.encrypt(nonce, plaintext.encode(), None)

        return {
            "ciphertext": ciphertext,
            "nonce": nonce,
            "message_number": self.message_number - 1
        }

    def decrypt_message(self, encrypted: dict) -> str:
        message_key = self._derive_message_key(
            self.chain_key, encrypted["message_number"]
        )
        aesgcm = AESGCM(message_key)
        plaintext = aesgcm.decrypt(
            encrypted["nonce"], encrypted["ciphertext"], None
        )
        return plaintext.decode()
```

多设备同步的核心挑战是：用户可能在手机、平板、电脑上同时登录，每个设备都需要看到完整的消息历史。

```python
# Map 阶段：将文档分词，输出 (词项, 文档信息) 对
def map_phase(doc_id: str, content: str):
    tokens = tokenize(content)  # 分词
    for position, token in enumerate(tokens):
        emit(token, (doc_id, position))

# Reduce 阶段：合并同一词项的所有文档信息
def reduce_phase(token: str, postings: list):
    # 按文档 ID 排序，构建倒排列表
    posting_list = sorted(postings, key=lambda x: x[0])
    index_store.write(token, posting_list)
```

**索引分片策略**：

```
10 亿网页的倒排索引太大（通常 TB 级），需要分片：

方案一：按文档分片（Document Partitioning）
  Shard 1: 文档 1~2.5亿 的完整倒排索引
  Shard 2: 文档 2.5亿~5亿 的完整倒排索引
  ...
  查询时：广播到所有 Shard，合并结果

方案二：按词项分片（Term Partitioning）
  Shard 1: 词项 A~F 的倒排列表
  Shard 2: 词项 G~M 的倒排列表
  ...
  查询时：只查询相关词项所在的 Shard

业界选择：方案一（文档分片），因为负载更均衡
```

#### 第四步：查询与排序

```
用户查询 "分布式搜索引擎" 的全链路：

1. 查询解析
   "分布式搜索引擎" → 分词 → ["分布式", "搜索引擎"]
   → 查询扩展：["分布式", "搜索引擎", "搜索", "引擎"]

2. 倒排检索（分布式）
   → 广播到所有 Index Shard
   → 每个 Shard 内做倒排列表交集
   → 每个 Shard 返回 Top-K 候选文档

3. 粗排（BM25）
   → 基于 BM25 计算每个文档的相关性分数
   → 从每个 Shard 选出 Top-100

4. 精排（ML 模型）
   → 合并所有 Shard 的候选文档
   → 使用机器学习模型综合打分
   → 特征：BM25 分数、PageRank、点击率、新鲜度、用户画像
   → 返回最终 Top-10

5. 结果展示
   → 生成摘要（Snippet）：从文档中提取包含查询词的上下文
   → 高亮关键词
   → 返回给前端
```

```python
# 基于 Trie + 热度排序的搜索补全

class TrieNode:
    def __init__(self):
        self.children = {}
        self.is_end = False
        self.hot_queries = []  # (query, frequency) 按热度排序

class AutoComplete:
    def __init__(self):
        self.root = TrieNode()

    def insert(self, query: str, frequency: int):
        node = self.root
        for char in query:
            if char not in node.children:
                node.children[char] = TrieNode()
            node = node.children[char]
            # 更新路径上每个节点的热门查询
            self._update_hot_queries(node, query, frequency)
        node.is_end = True

    def suggest(self, prefix: str, top_k=10) -> list:
        node = self.root
        for char in prefix:
            if char not in node.children:
                return []
            node = node.children[char]
        return [q for q, _ in node.hot_queries[:top_k]]

    def _update_hot_queries(self, node, query, freq):
        # 维护每个节点的 Top-K 热门查询
        for i, (q, f) in enumerate(node.hot_queries):
            if q == query:
                node.hot_queries[i] = (query, freq)
                node.hot_queries.sort(key=lambda x: -x[1])
                return
        node.hot_queries.append((query, freq))
        node.hot_queries.sort(key=lambda x: -x[1])
        node.hot_queries = node.hot_queries[:10]
```

#### 第二步：小文件问题

**为什么小文件是问题？**

```
假设 Master 使用 150 字节元数据管理一个文件：

大文件场景（1PB 数据，每个文件 1GB）：
  文件数 = 1PB / 1GB = 100 万个
  元数据 = 100万 × 150B = 150MB → 轻松放入内存

小文件场景（1PB 数据，每个文件 100KB）：
  文件数 = 1PB / 100KB = 100 亿个
  元数据 = 100亿 × 150B = 1.5TB → 远超内存容量！

同时小文件还带来：
  - 大量随机 I/O（无法利用顺序读优势）
  - Master 成为瓶颈（元数据操作太频繁）
  - 数据块利用率低（64MB 的 Chunk 只存 100KB 数据）
```

```python
# SequenceFile 合并小文件示例
class SequenceFileWriter:
    def __init__(self, output_path: str):
        self.output = open(output_path, 'wb')
        self.index = {}  # filename -> (offset, length)
        self.current_offset = 0

    def append(self, filename: str, data: bytes):
        self.index[filename] = (self.current_offset, len(data))
        # 写入 Key（文件名长度 + 文件名）
        key_bytes = filename.encode()
        self.output.write(len(key_bytes).to_bytes(4, 'big'))
        self.output.write(key_bytes)
        # 写入 Value（数据长度 + 数据）
        self.output.write(len(data).to_bytes(4, 'big'))
        self.output.write(data)
        self.current_offset += 8 + len(key_bytes) + len(data)

    def close(self):
        # 写入索引到文件末尾
        import json
        index_bytes = json.dumps(self.index).encode()
        self.output.write(index_bytes)
        self.output.write(len(index_bytes).to_bytes(4, 'big'))
        self.output.close()
```

**跨数据中心一致性策略**：

```
策略一：同步复制（强一致）
  写入流程：
    Client → DC-A 写入 → 同步复制到 DC-B → 两个 DC 都确认 → 返回成功
  优点：数据一致性强
  缺点：跨数据中心延迟高（通常 10~50ms），写入性能差
  适用：金融、交易类数据

策略二：异步复制（最终一致）
  写入流程：
    Client → DC-A 写入 → 返回成功 → 异步复制到 DC-B
  优点：写入延迟低
  缺点：DC-A 故障时可能丢失少量数据（RPO > 0）
  适用：日志、非关键数据

策略三：半同步复制（折中方案）
  写入流程：
    Client → DC-A 写入 + 同步复制到 DC-B（只等 1 个远程副本确认）
    → DC-A 本地 + DC-B 1 副本确认 → 返回成功
    → DC-B 其余副本异步复制
  兼顾性能和可靠性
```

**故障切换流程**：

```python
# 跨数据中心故障切换（伪代码）
class DisasterRecovery:
    def __init__(self):
        self.primary_dc = "DC-A"
        self.standby_dc = "DC-B"
        self.heartbeat_interval = 3  # 秒
        self.failure_threshold = 5   # 连续 5 次心跳失败触发切换

    def monitor_primary(self):
        consecutive_failures = 0
        while True:
            if self.heartbeat(self.primary_dc):
                consecutive_failures = 0
            else:
                consecutive_failures += 1
                if consecutive_failures >= self.failure_threshold:
                    self.failover()
                    break
            time.sleep(self.heartbeat_interval)

    def failover(self):
        """故障切换到备用数据中心"""
        # 1. 确认主 DC 确实不可用（避免脑裂）
        if self.double_check_primary():
            return  # 误判，取消切换

        # 2. Standby Master 提升为 Active
        self.promote_standby_master()

        # 3. DNS 更新，将流量切换到 DC-B
        self.update_dns(self.standby_dc)

        # 4. 通知运维团队
        self.alert("Failover completed: DC-A → DC-B")

        # 5. DC-A 恢复后，作为新的 Standby 重新同步数据
```

#### 追问链

**追问 1：如何处理脑裂问题（Split-Brain）？**

- 引入第三方仲裁（如 ZooKeeper 集群或独立监控服务）
- 使用 Fencing 机制：旧 Master 被隔离后无法写入
- STONITH（Shoot The Other Node In The Head）：确保旧 Master 完全下线

**追问 2：跨数据中心的数据一致性如何验证？**

- 后台 Checksum 对比任务：定期比较两个 DC 的数据校验和
- 使用 Merkle Tree 快速发现不一致的数据块
- 不一致时从主 DC 重新复制

**追问 3：纠删码（Erasure Coding）能否替代 3 副本？**

- 3 副本：存储开销 200%，但恢复速度快（直接复制）
- 纠删码（如 RS(6,3)）：存储开销 50%，但恢复需要计算
- 适用于冷数据（不频繁访问），热数据仍推荐 3 副本

**追问 4：如何优化跨数据中心的数据传输？**

- 带宽调度：业务低峰期批量传输
- 数据压缩：LZ4/Zstd 压缩后传输，压缩比约 2~5 倍
- 增量同步：只传输变化的 Chunk，而非全量

### Q23: 你负责的短链系统遭遇了热点 Key 攻击（某短链每秒百万次访问），如何应对？

<details>
<summary>参考答案</summary>

热点 Key 攻击是线上系统最常见的高可用挑战之一。某个短链突然被大量访问（可能是社交媒体病毒式传播，也可能是恶意 DDoS），会导致 Redis 单节点和后端数据库被压垮。

#### 场景分析

```
正常情况：
  短链 "abc1234" → 100 QPS（正常热度）

异常场景：
  短链 "abc1234" → 1,000,000 QPS（百万级热点）
  → Redis Cluster 中该 Key 被 Hash 到某个固定节点
  → 该节点成为瓶颈，CPU 100%
  → 甚至影响该节点上的其他 Key 的访问
```

#### 应急处理方案（分钟级响应）

**第一步：流量识别**

```python
# 实时监控热点 Key
class HotKeyDetector:
    def __init__(self, threshold=10000):
        self.counter = {}  # key -> count
        self.window_start = time.time()
        self.threshold = threshold  # QPS 阈值

    def record_access(self, key: str):
        current = time.time()
        # 每秒重置计数器
        if current - self.window_start >= 1:
            # 检查热点
            for k, count in self.counter.items():
                if count > self.threshold:
                    self.on_hot_key_detected(k, count)
            self.counter = {}
            self.window_start = current
        self.counter[key] = self.counter.get(key, 0) + 1

    def on_hot_key_detected(self, key: str, qps: int):
        # 触发热点 Key 保护机制
        alert(f"Hot key detected: {key}, QPS: {qps}")
        enable_local_cache(key)
```

**第二步：多级缓存分散压力**

```
                     100 万 QPS

            ┌────────────▼────────────┐

            └────────────┬────────────┘
                         │ 20 万 QPS
            ┌────────────▼────────────┐
            │    Nginx 本地缓存        │  ← 拦截 90%
            │  proxy_cache, TTL = 1s  │
            └────────────┬────────────┘
                         │ 2 万 QPS
            ┌────────────▼────────────┐
            │   应用层本地缓存         │  ← 拦截 95%
            │  Guava Cache, TTL = 1s  │
            └────────────┬────────────┘

            ┌────────────▼────────────┐

```

**第三步：Redis 热点 Key 分片**

```python
# 将一个热点 Key 拆分为多个分片 Key
import random

HOT_KEY_REPLICAS = 32  # 分片数

def get_with_hot_key_protection(short_code: str) -> str:
    """分散热点 Key 到多个 Redis 节点"""
    # 正常查询
    result = redis.get(f"url:{short_code}")
    if result:
        return result

    # 热点 Key 模式：随机选择一个分片 Key
    shard_id = random.randint(0, HOT_KEY_REPLICAS - 1)
    result = redis.get(f"url:{short_code}:shard:{shard_id}")
    if result:
        return result

    # 缓存未命中，查数据库并回填所有分片
    result = db.query(short_code)
    if result:
        for i in range(HOT_KEY_REPLICAS):
            redis.setex(f"url:{short_code}:shard:{i}", 60, result)
    return result

def enable_hot_key_sharding(short_code: str):
    """为某个 Key 开启热点分片"""
    original_value = redis.get(f"url:{short_code}")
    if original_value:
        for i in range(HOT_KEY_REPLICAS):
            redis.setex(f"url:{short_code}:shard:{i}", 60, original_value)
```

```
  - 来源 IP 分散

  - 正常热点 → 扩容缓存 + CDN 加速
  - 恶意攻击 → IP 封禁 + 验证码 + WAF 规则
```

<summary>参考答案</summary>

```python
# 简化的 Feed 排序打分模型
class FeedRanker:
    def __init__(self, model):
        self.model = model  # 预训练的 ML 模型

    def score(self, user, post) -> float:
        features = self.extract_features(user, post)
        # 预测用户对这条内容的互动概率
        p_like = self.model.predict_proba(features, target='like')
        p_comment = self.model.predict_proba(features, target='comment')
        p_share = self.model.predict_proba(features, target='share')
        p_click = self.model.predict_proba(features, target='click')

        # 加权组合（不同互动类型权重不同）
        score = (
            p_like * 1.0 +
            p_comment * 2.0 +    # 评论价值更高
            p_share * 3.0 +      # 分享价值最高
            p_click * 0.5 +
            self.time_decay(post.created_at) * 0.3  # 时间衰减
        )
        return score

    def extract_features(self, user, post) -> dict:
        return {
            # 用户特征
            'user_age': user.age,
            'user_active_days': user.active_days,
            'user_avg_likes_per_day': user.avg_likes,

            # 内容特征
            'post_length': len(post.content),
            'post_has_image': post.has_image,
            'post_has_video': post.has_video,
            'post_likes_count': post.likes,
            'post_age_hours': post.age_in_hours,

            # 关系特征
            'author_is_close_friend': user.is_close_friend(post.author),
            'user_liked_author_last_7d': user.liked_author_count(post.author, 7),

            # 上下文特征
            'is_weekend': datetime.now().weekday() >= 5,
            'hour_of_day': datetime.now().hour,
        }

    def time_decay(self, created_at) -> float:
        """时间衰减函数：越新的内容分数越高"""
        age_hours = (datetime.now() - created_at).total_seconds() / 3600
        return 1.0 / (1.0 + age_hours / 24)  # 24 小时半衰期
```

```
为什么要保留时间线选项：
  - 用户信任感：担心推荐导致"信息茧房"
  - 完整性需求：用户想看到所有关注者的内容
  - 突发事件：推荐模型可能忽略低互动但重要的突发新闻
```

**2. 冷启动问题**

```
新用户没有行为数据，推荐模型无法工作：
  → 使用热门内容 + 注册时选择兴趣标签
  → 逐步收集用户行为数据，模型逐步接管

新内容没有互动数据：
  → 给新内容一个初始曝光量（Exploration）
  → 基于内容特征（文本、图片质量）做冷启动打分
```

### Q25: 秒杀系统上线后发现 Redis 主节点故障导致库存数据不一致，如何设计兜底方案？

<details>
<summary>参考答案</summary>

Redis 主节点故障是秒杀系统最危险的单点故障场景。由于 Redis 主从复制是异步的，主节点故障时可能丢失最近的库存扣减操作，导致超卖。

#### 故障场景还原

```
时间线：
  T1: 用户 A 秒杀成功，Redis 主节点扣减库存 1000 → 999
  T2: 用户 B 秒杀成功，Redis 主节点扣减库存 999 → 998
  T3: Redis 主节点宕机（此时 T1、T2 的写入还未同步到从节点）
  T4: Redis Sentinel 将从节点提升为新的主节点
  T5: 新主节点的库存 = 1000（丢失了 A、B 的扣减）
  T6: 用户 C 秒杀成功，库存 1000 → 999（但实际应该是 997）

结果：
  实际售出 3 件（A + B + C）
  Redis 显示售出 1 件
  → 超卖 2 件！
```

#### 完整兜底方案


#### 关键实现：数据库乐观锁

```python
# 订单消费者：数据库层面的最终防超卖
class OrderConsumer:
    def consume(self, message: dict):
        item_id = message['item_id']
        user_id = message['user_id']

        try:
            with db.transaction() as tx:
                # 第一步：乐观锁扣减库存
                result = tx.execute("""
                    UPDATE seckill_stock
                    SET stock = stock - 1,
                        sold = sold + 1,
                        version = version + 1
                    WHERE item_id = %s
                      AND stock > 0
                      AND version = %s
                """, (item_id, self.get_current_version(item_id)))

                if result.rowcount == 0:
                    # 数据库层面库存不足 → 回滚 Redis
                    self.rollback_redis(item_id, user_id)
                    self.notify_user(user_id, "抢购失败，库存不足")
                    return

                # 第二步：创建订单
                tx.execute("""
                    INSERT INTO seckill_order
                    (order_id, item_id, user_id, status, created_at)
                    VALUES (%s, %s, %s, 'CREATED', NOW())
                """, (generate_order_id(), item_id, user_id))

                # 第三步：提交事务
                tx.commit()
                self.notify_user(user_id, "抢购成功！请在15分钟内支付")

        except Exception as e:
            tx.rollback()
            self.rollback_redis(item_id, user_id)
            self.notify_user(user_id, "系统异常，请稍后查看订单")
            log.error(f"Order creation failed: {e}")

    def rollback_redis(self, item_id, user_id):
        """回滚 Redis 预扣减"""
        redis.incr(f"stock:{item_id}")
        redis.srem(f"purchased:{item_id}", user_id)
```

#### Redis 故障时的具体恢复流程

```python
# Redis 主节点故障恢复后的数据校正
class StockReconciler:
    """定期对账：Redis 库存 vs 数据库库存"""

    def reconcile(self, item_id: str):
        # 从数据库获取真实已售数量
        db_sold = db.query(
            "SELECT sold FROM seckill_stock WHERE item_id = %s", item_id
        ).sold

        # 从数据库获取总库存
        db_total = db.query(
            "SELECT total_stock FROM seckill_stock WHERE item_id = %s", item_id
        ).total_stock

        # 正确的剩余库存
        correct_stock = db_total - db_sold

        # 获取 Redis 当前库存
        redis_stock = int(redis.get(f"stock:{item_id}") or 0)

        if redis_stock != correct_stock:
            log.warn(
                f"Stock mismatch for {item_id}: "
                f"Redis={redis_stock}, DB={correct_stock}"
            )
            # 以数据库为准，修正 Redis
            redis.set(f"stock:{item_id}", correct_stock)

            # 同步已购买用户集合
            purchased_users = db.query(
                "SELECT user_id FROM seckill_order "
                "WHERE item_id = %s AND status != 'CANCELLED'",
                item_id
            )
            redis.delete(f"purchased:{item_id}")
            if purchased_users:
                redis.sadd(f"purchased:{item_id}",
                          *[u.user_id for u in purchased_users])

    def run_periodic_reconciliation(self):
        """每 30 秒执行一次对账"""
        while True:
            active_items = get_active_seckill_items()
            for item_id in active_items:
                self.reconcile(item_id)
            time.sleep(30)
```

#### 更高可靠性方案：Redis + 数据库双写

```python
# 方案：先写数据库，再写 Redis（保证最终一致性）
def seckill_with_db_first(item_id: str, user_id: str):
    # 快速判断（可能不准，但能挡住大部分请求）
    if redis.get(f"sold_out:{item_id}"):
        return "已售罄"

    # 先扣数据库（作为最终真相源）
    result = db.execute("""
        UPDATE seckill_stock
        SET stock = stock - 1, sold = sold + 1
        WHERE item_id = %s AND stock > 0
    """, item_id)

    if result.rowcount == 0:
        redis.set(f"sold_out:{item_id}", "1", ex=3600)
        return "库存不足"

    # 再更新 Redis 缓存（用于快速过滤）
    redis.decr(f"stock:{item_id}")

    # 创建订单
    create_order(item_id, user_id)
    return "抢购成功"
```

**该方案的 trade-off**：
- 优点：数据库是唯一真相源，不存在不一致问题
- 缺点：数据库承受更大压力，QPS 上限较低（约 5000）
- 适用：库存量不大（< 1 万件），参与人数可控的场景

#### 最终方案选择建议

| 场景 | 推荐方案 | 原因 |
|------|---------|------|
| 超高并发（百万 QPS） | Redis 预扣减 + DB 乐观锁兜底 + 定期对账 | 性能优先 |
| 中等并发（万级 QPS） | DB 直接扣减 + Redis 缓存过滤 | 简单可靠 |
| 金融级准确性 | 分布式事务（Seata/TCC） | 强一致性 |
