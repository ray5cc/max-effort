## 基础题（⭐）

**Q1. 什么是前端状态管理？为什么不能只用组件 state？**

<details>
<summary>参考答案</summary>

**思路分析：** 从"状态"的定义出发，解释组件 state 的局限性，引出全局状态管理的必要性。

**核心要点：**

前端"状态"就是驱动 UI 渲染的数据。组件内部的 `useState` / `useReducer` 只能管理当前组件的局部状态，当应用规模增长后会遇到三个核心问题：

1. **状态共享困难（Prop Drilling）**：兄弟组件或深层嵌套组件需要共享数据时，必须将 state 提升到公共祖先，再逐层传递 props，层级越深维护成本越高。

2. **状态一致性问题**：同一份数据在多个组件中各自管理一份拷贝，更新时容易出现不同步，导致 UI 不一致。

3. **生命周期不匹配**：组件卸载后 state 丢失。如果需要跨页面保留状态（如购物车、用户偏好），组件 state 无法满足。

```diagram
场景示例：电商应用中的购物车数量

  Header（显示购物车数量）
    ├── ProductPage（添加到购物车）
    │     └── ProductCard
    │           └── AddToCartButton（触发添加）
    └── CartPage（显示购物车列表）

如果不用状态管理，购物车数据需要从 App 层逐层传递 props + 回调函数，
任何中间组件的变动都可能影响数据传递链路。
```

状态管理库的核心价值：**将共享状态从组件树中抽离，放入独立的 store，任何组件都可以直接读写，无需经过中间层传递。**

</details>

**Q2. Redux 的三大原则是什么？请结合代码说明单向数据流。**

<details>
<summary>参考答案</summary>

**思路分析：** Redux 三大原则是面试高频基础题，需要说清楚每个原则解决什么问题。

**核心要点：**

**三大原则：**

| 原则 | 含义 | 解决的问题 |
|------|------|-----------|
| **Single Source of Truth** | 整个应用状态存储在一个 store 的对象树中 | 避免多处数据不一致 |
| **State is Read-Only** | 唯一改变 state 的方式是 dispatch action | 状态变更可追踪、可预测 |
| **Pure Reducers** | reducer 是纯函数，接收旧 state + action，返回新 state | 状态变更可测试、可回放 |

**单向数据流代码示例：**

```javascript
import { configureStore, createSlice } from '@reduxjs/toolkit';

// 1. 定义 slice（包含 reducer + action creators）
const counterSlice = createSlice({
  name: 'counter',
  initialState: { value: 0 },
  reducers: {
    increment: (state) => {
      state.value += 1; // Immer 让你用"可变"写法，底层自动转为不可变更新
    },
    incrementByAmount: (state, action) => {
      state.value += action.payload;
    },
  },
});

// 2. 创建 store
const store = configureStore({
  reducer: { counter: counterSlice.reducer },
});

// 3. 单向数据流
// View 触发 → dispatch(action) → reducer 计算新 state → store 通知 → View 更新
store.dispatch(counterSlice.actions.increment());
console.log(store.getState()); // { counter: { value: 1 } }

store.dispatch(counterSlice.actions.incrementByAmount(5));
console.log(store.getState()); // { counter: { value: 6 } }
```

```diagram
单向数据流图示：

  ┌──────────────────────────────────────────┐
  │                                          │
  ▼                                          │
View ──dispatch──▶ Action ──▶ Middleware ──▶ Reducer ──▶ Store
  ▲                                                       │
  │                                                       │
  └────────────── subscribe/selector ◀────────────────────┘
```

**关键点：** 数据永远是单向流动的，View 不能直接修改 state，必须通过 dispatch action，这使得每一次状态变更都有明确的来源，方便调试和回放（Redux DevTools 的时间旅行功能正是基于此）。

</details>

**Q3. Redux Toolkit 的 `createSlice` 解决了传统 Redux 的哪些痛点？**

<details>
<summary>参考答案</summary>

**思路分析：** 对比传统 Redux 和 RTK，说明 RTK 如何减少样板代码。

**核心要点：**

传统 Redux 的痛点和 RTK 的解决方案：

| 痛点 | 传统 Redux | Redux Toolkit |
|------|-----------|---------------|
| 样板代码多 | 手写 action type 常量 + action creator + reducer，三个文件 | `createSlice` 一个函数自动生成 |
| 不可变更新繁琐 | 手动展开嵌套对象 `{ ...state, user: { ...state.user, name } }` | 内置 Immer，直接写 `state.user.name = name` |
| Store 配置复杂 | 手动组合 middleware、DevTools、combineReducers | `configureStore` 一行搞定，自动集成 DevTools 和 thunk |
| 异步逻辑无标准 | redux-thunk / redux-saga / redux-observable 各有各的写法 | `createAsyncThunk` 提供标准化异步模式 |

```javascript
// ❌ 传统 Redux 写法（需要 3 个文件 / 大量样板代码）
// actionTypes.js
const ADD_TODO = 'todos/addTodo';

// actions.js
const addTodo = (text) => ({ type: ADD_TODO, payload: { text } });

// reducer.js
const todosReducer = (state = [], action) => {
  switch (action.type) {
    case ADD_TODO:
      return [...state, { id: Date.now(), text: action.payload.text, completed: false }];
    default:
      return state;
  }
};

// ✅ Redux Toolkit 写法（一个 createSlice 全搞定）
const todosSlice = createSlice({
  name: 'todos',
  initialState: [],
  reducers: {
    addTodo: (state, action) => {
      state.push({ id: Date.now(), text: action.payload, completed: false });
    },
    toggleTodo: (state, action) => {
      const todo = state.find((t) => t.id === action.payload);
      if (todo) todo.completed = !todo.completed;
    },
    removeTodo: (state, action) => {
      return state.filter((t) => t.id !== action.payload);
    },
  },
});

// 自动生成的 action creators
export const { addTodo, toggleTodo, removeTodo } = todosSlice.actions;
// 自动生成的 reducer
export default todosSlice.reducer;
```

**关键理解：** `createSlice` 内部使用 Immer 包装 reducer，所以虽然代码看起来在"直接修改"state（如 `state.push()`），实际上 Immer 会拦截这些操作并产生一个全新的不可变对象。这既保留了 Redux 不可变性的优势，又大幅降低了编码复杂度。

</details>

**Q4. Zustand 的核心理念是什么？为什么它比 Redux 更简洁？**

<details>
<summary>参考答案</summary>

**思路分析：** 从 API 设计和架构差异两个维度对比。

**核心要点：**

Zustand 的设计哲学是 **"最小 API 表面积"**——用最少的概念和代码实现状态管理。

**与 Redux 的核心区别：**

| 特性 | Redux (RTK) | Zustand |
|------|------------|---------|
| Provider 包裹 | 需要 `<Provider store={store}>` | 不需要，直接 import 使用 |
| 样板代码 | 较多（slice + store 配置） | 极少（一个 `create` 函数） |
| 底层机制 | 发布-订阅 + React Context | 发布-订阅 + 外部 store（基于闭包） |
| 不可变更新 | Immer（内置于 RTK） | 可选 Immer 中间件 |
| 状态读取 | `useSelector` + 手写选择器 | Hook 直接返回，带自动浅比较 |
| 包大小 | ~11KB (RTK) | ~1.1KB |

```typescript
import { create } from 'zustand';

// 定义 store —— 一个函数搞定
interface BearStore {
  bears: number;
  increasePopulation: () => void;
  removeAllBears: () => void;
  updateBears: (newBears: number) => void;
}

const useBearStore = create<BearStore>((set) => ({
  bears: 0,
  increasePopulation: () => set((state) => ({ bears: state.bears + 1 })),
  removeAllBears: () => set({ bears: 0 }),
  updateBears: (newBears) => set({ bears: newBears }),
}));

// 在组件中使用 —— 不需要 Provider
function BearCounter() {
  const bears = useBearStore((state) => state.bears);
  return <h1>{bears} bears around here</h1>;
}

function Controls() {
  const increasePopulation = useBearStore((state) => state.increasePopulation);
  return <button onClick={increasePopulation}>增加</button>;
}
```

**为什么不需要 Provider？** Zustand 的 store 是一个模块级闭包，状态存储在 React 组件树之外。组件通过 `useSyncExternalStore`（React 18+）订阅 store 变化。这意味着：
- 不会受到 React Context 重渲染的影响
- 可以在 React 组件外部访问和修改状态（如工具函数、API 拦截器中）
- 不需要在组件树顶层包裹 Provider

</details>

**Q5. 什么是服务端状态（Server State）和客户端状态（Client State）？各自用什么工具管理？**

<details>
<summary>参考答案</summary>

**思路分析：** 这是状态管理选型的核心前置知识，区分清楚才能选对工具。

**核心要点：**

| 维度 | 客户端状态（Client State） | 服务端状态（Server State） |
|------|--------------------------|--------------------------|
| 数据来源 | 前端自行产生 | 后端 API 返回 |
| 所有权 | 前端完全控制 | 后端拥有，前端只是缓存 | 
| 典型数据 | UI 状态（弹窗开关、主题、表单输入） | 用户列表、商品数据、订单信息 |
| 核心挑战 | 状态共享、状态同步 | 缓存失效、后台更新、乐观更新、分页 |
| 推荐工具 | Zustand / Jotai / Redux | TanStack Query / RTK Query / SWR |

```
类比：

客户端状态 = 你自己的笔记本
  → 你写什么就是什么，完全可控

服务端状态 = 图书馆的书
  → 你借来只是一份"副本"，别人可能同时在修改原本
  → 需要机制判断副本是否过期、何时重新借阅
```

```typescript
// 服务端状态管理示例：TanStack Query
import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query';

function UserList() {
  // 声明式获取 + 自动缓存 + 自动重新获取
  const { data: users, isLoading, error } = useQuery({
    queryKey: ['users'],
    queryFn: () => fetch('/api/users').then((res) => res.json()),
    staleTime: 5 * 60 * 1000,   // 5 分钟内认为数据新鲜
    gcTime: 30 * 60 * 1000,     // 30 分钟后垃圾回收
  });

  if (isLoading) return <div>加载中...</div>;
  if (error) return <div>加载失败</div>;
  return <ul>{users.map((u) => <li key={u.id}>{u.name}</li>)}</ul>;
}

// 客户端状态管理示例：Zustand
const useUIStore = create((set) => ({
  theme: 'light',
  sidebarOpen: true,
  toggleTheme: () => set((s) => ({ theme: s.theme === 'light' ? 'dark' : 'light' })),
  toggleSidebar: () => set((s) => ({ sidebarOpen: !s.sidebarOpen })),
}));
```

**最佳实践：** 不要用 Redux/Zustand 去管理服务端状态（如用户列表）——你会自己重复实现缓存、失效、重新获取等逻辑。TanStack Query / RTK Query 已经内置了这些能力。**客户端状态和服务端状态应该用不同的工具分别管理。**

</details>

**Q6. Context API 的工作原理是什么？它有哪些性能问题？**

<details>
<summary>参考答案</summary>

**思路分析：** Context 是 React 内置方案，面试中常考其性能陷阱。

**核心要点：**

**工作原理：** `React.createContext` 创建上下文对象，`Provider` 在组件树上层提供值，任何深层子组件通过 `useContext` 直接消费。React 内部通过对 context value 的引用比较（`Object.is`）来决定是否通知消费者更新。

**性能问题——全量重渲染：**

```jsx
// ❌ 性能陷阱：value 是新对象引用，每次 App 渲染都会触发 ALL 消费者重渲染
function App() {
  const [user, setUser] = useState({ name: 'Alice' });
  const [theme, setTheme] = useState('dark');

  return (
    // 每次渲染 { user, theme, setUser, setTheme } 都是新对象
    <AppContext.Provider value={{ user, theme, setUser, setTheme }}>
      <Header />     {/* 只用 theme，但 user 变了也会重渲染 */}
      <UserPanel />  {/* 只用 user，但 theme 变了也会重渲染 */}
      <Sidebar />    {/* 只用 theme，同上 */}
    </AppContext.Provider>
  );
}
```

**核心问题：**
1. **无法选择性订阅**：Consumer 无法只订阅 context 中的部分字段，value 变了就全部重渲染
2. **引用不稳定**：每次父组件渲染都创建新的 value 对象引用
3. **跳不过中间组件**：即使中间组件用 `React.memo`，如果它消费了 context，memo 也无效

```jsx
// ✅ 优化方案 1：拆分 Context
const ThemeContext = createContext();
const UserContext = createContext();

function App() {
  const [user, setUser] = useState({ name: 'Alice' });
  const [theme, setTheme] = useState('dark');

  return (
    <ThemeContext.Provider value={theme}>
      <UserContext.Provider value={user}>
        <Header />     {/* 只消费 ThemeContext，user 变了不受影响 */}
        <UserPanel />  {/* 只消费 UserContext，theme 变了不受影响 */}
      </UserContext.Provider>
    </ThemeContext.Provider>
  );
}

// ✅ 优化方案 2：useMemo 稳定引用
function App() {
  const [user, setUser] = useState({ name: 'Alice' });
  const [theme, setTheme] = useState('dark');

  const value = useMemo(() => ({ user, theme, setUser, setTheme }), [user, theme]);

  return (
    <AppContext.Provider value={value}>
      <Content />
    </AppContext.Provider>
  );
}
```

**结论：** Context 适合低频变更的全局配置（主题、语言、认证信息），不适合高频变更的状态管理。如果需要细粒度更新，应选择 Zustand、Jotai 等专用库。

</details>

**Q7. MobX 的核心概念有哪些？它与 Redux 的本质区别是什么？**

<details>
<summary>参考答案</summary>

**思路分析：** MobX 和 Redux 代表两种完全不同的状态管理哲学——响应式 vs 函数式。

**核心要点：**

**MobX 四大核心概念：**

| 概念 | 作用 | 类比 |
|------|------|------|
| `observable` | 将数据标记为可观察的响应式状态 | Excel 单元格的值 |
| `action` | 修改 observable 状态的方法 | 手动修改单元格 |
| `computed` | 从 observable 派生的缓存计算值 | Excel 公式（`=SUM(A1:A10)`） |
| `reaction` / `autorun` | 状态变化时自动执行的副作用 | Excel 的条件格式/图表自动更新 |

```typescript
import { makeAutoObservable, runInAction } from 'mobx';
import { observer } from 'mobx-react-lite';

// Store 定义
class TodoStore {
  todos: Todo[] = [];
  filter: 'all' | 'active' | 'completed' = 'all';

  constructor() {
    makeAutoObservable(this); // 自动推断 observable / action / computed
  }

  // computed：只有 todos 或 filter 变化时才重新计算
  get filteredTodos() {
    switch (this.filter) {
      case 'active':
        return this.todos.filter((t) => !t.completed);
      case 'completed':
        return this.todos.filter((t) => t.completed);
      default:
        return this.todos;
    }
  }

  get stats() {
    return {
      total: this.todos.length,
      completed: this.todos.filter((t) => t.completed).length,
    };
  }

  // action：直接修改状态
  addTodo(text: string) {
    this.todos.push({ id: Date.now(), text, completed: false });
  }

  toggleTodo(id: number) {
    const todo = this.todos.find((t) => t.id === id);
    if (todo) todo.completed = !todo.completed;
  }

  // 异步 action
  async fetchTodos() {
    const response = await fetch('/api/todos');
    const todos = await response.json();
    runInAction(() => {
      this.todos = todos; // 异步回调中修改状态需要 runInAction
    });
  }
}

// 组件使用 —— 必须用 observer 包裹
const TodoList = observer(({ store }: { store: TodoStore }) => (
  <ul>
    {store.filteredTodos.map((todo) => (
      <li key={todo.id} onClick={() => store.toggleTodo(todo.id)}>
        {todo.text}
      </li>
    ))}
  </ul>
));
```

**MobX vs Redux 本质区别：**

| 维度 | Redux | MobX |
|------|-------|------|
| 编程范式 | 函数式（纯函数 reducer） | 面向对象 + 响应式 |
| 状态修改 | 不可变（返回新对象） | 可变（直接修改，Proxy 拦截） |
| 数据流 | 显式单向（action → reducer → store） | 隐式响应式（修改即触发依赖更新） |
| 样板代码 | 较多（即使用 RTK） | 较少（`makeAutoObservable` 自动推断） |
| 可预测性 | 极高（每次变更都有完整 action 记录） | 相对低（状态变更链路较隐式） |
| 学习曲线 | 概念多但逻辑清晰 | 概念少但 Proxy 机制有隐坑 |

</details>

**Q8. Jotai 和 Recoil 都是"原子化"状态管理，"原子化"是什么意思？**

<details>
<summary>参考答案</summary>

**思路分析：** 解释原子化（atomic）的含义，与传统"中心化 store"对比。

**核心要点：**

**原子化状态管理**是一种自底向上的状态组织方式：

```diagram
传统中心化 store（Redux/Zustand）：
┌─────────────────────────────┐
│         Global Store         │
│  ┌─────┬─────┬─────┬─────┐  │
│  │user │theme│todos│cart  │  │
│  └─────┴─────┴─────┴─────┘  │
└─────────────────────────────┘
↑ 所有状态集中在一个 store 对象中

原子化状态（Jotai/Recoil）：
  [atom]  [atom]  [atom]  [atom]
   user    theme   todos   cart
    │        │       │      │
    └───┬────┘       └──┬───┘
        │               │
   [derived]        [derived]     ← 组合 atom 派生新状态
   userTheme        cartTotal
```

**类比：** 
- 中心化 store 像一个大仓库，所有货物放在同一间屋子里，取任何东西都要进这个屋子
- 原子化状态像乐高积木，每块积木（atom）是独立的最小单元，可以自由组合成任何形状

```typescript
// Jotai 示例
import { atom, useAtom } from 'jotai';

// 基础 atom —— 最小状态单位
const countAtom = atom(0);
const textAtom = atom('hello');

// 派生 atom（只读）—— 从其他 atom 计算得出
const doubledAtom = atom((get) => get(countAtom) * 2);

// 派生 atom（读写）
const uppercasedAtom = atom(
  (get) => get(textAtom).toUpperCase(),            // getter
  (get, set, newValue: string) => {                 // setter
    set(textAtom, newValue.toLowerCase());
  }
);

// 异步 atom
const userAtom = atom(async () => {
  const response = await fetch('/api/user');
  return response.json();
});

function Counter() {
  const [count, setCount] = useAtom(countAtom);
  const [doubled] = useAtom(doubledAtom); // 自动随 countAtom 更新

  return (
    <div>
      <p>Count: {count}, Doubled: {doubled}</p>
      <button onClick={() => setCount((c) => c + 1)}>+1</button>
    </div>
  );
}
```

**原子化的优势：**
1. **天然细粒度更新**：组件只订阅自己用到的 atom，其他 atom 变化不触发重渲染
2. **按需组合**：不需要预先规划整体 store 结构，新增状态只需新增 atom
3. **代码分割友好**：atom 可以定义在任何文件中，随用随导入
4. **无 Provider（Jotai）**：Jotai 的 atom 默认全局作用域，无需 Provider 包裹

</details>

**Q9. `createAsyncThunk` 是什么？如何处理异步请求的 loading/error 状态？**

<details>
<summary>参考答案</summary>

**思路分析：** RTK 标准化异步方案，重点说明三种状态处理。

**核心要点：**

`createAsyncThunk` 是 Redux Toolkit 提供的异步 action 创建工具。它接收一个字符串类型前缀和一个返回 Promise 的函数，自动 dispatch 三种 action：`pending`、`fulfilled`、`rejected`。

```typescript
import { createSlice, createAsyncThunk } from '@reduxjs/toolkit';

interface User {
  id: number;
  name: string;
  email: string;
}

interface UsersState {
  list: User[];
  loading: boolean;
  error: string | null;
}

// 创建异步 thunk
export const fetchUsers = createAsyncThunk<User[], void, { rejectValue: string }>(
  'users/fetchAll', // action type 前缀
  async (_, { rejectWithValue }) => {
    try {
      const response = await fetch('/api/users');
      if (!response.ok) {
        return rejectWithValue(`HTTP ${response.status}: ${response.statusText}`);
      }
      return await response.json();
    } catch (err) {
      return rejectWithValue('网络请求失败');
    }
  }
);

const usersSlice = createSlice({
  name: 'users',
  initialState: { list: [], loading: false, error: null } as UsersState,
  reducers: {},
  extraReducers: (builder) => {
    builder
      // pending：请求发出，显示 loading
      .addCase(fetchUsers.pending, (state) => {
        state.loading = true;
        state.error = null;
      })
      // fulfilled：请求成功，保存数据
      .addCase(fetchUsers.fulfilled, (state, action) => {
        state.loading = false;
        state.list = action.payload;
      })
      // rejected：请求失败，显示错误
      .addCase(fetchUsers.rejected, (state, action) => {
        state.loading = false;
        state.error = action.payload ?? '未知错误';
      });
  },
});

// 组件中使用
function UserList() {
  const dispatch = useAppDispatch();
  const { list, loading, error } = useAppSelector((state) => state.users);

  useEffect(() => {
    dispatch(fetchUsers());
  }, [dispatch]);

  if (loading) return <Spinner />;
  if (error) return <ErrorMessage message={error} />;
  return <ul>{list.map((u) => <li key={u.id}>{u.name}</li>)}</ul>;
}
```

**生命周期图示：**
```diagram
dispatch(fetchUsers())
  │
  ├──▶ users/fetchAll/pending   → loading = true
  │
  │   (等待 Promise 完成)
  │
  ├──▶ users/fetchAll/fulfilled → loading = false, list = data
  │    或
  └──▶ users/fetchAll/rejected  → loading = false, error = message
```

**注意：** 如果大量使用 `createAsyncThunk` 来获取服务端数据，建议考虑迁移到 RTK Query 或 TanStack Query，它们内置了缓存、去重、轮询等能力，不需要手动管理 loading/error 状态。

</details>

**Q10. XState 中的"状态机"是什么概念？它与普通变量管理状态有什么区别？**

<details>
<summary>参考答案</summary>

**思路分析：** XState 的核心是有限状态机思维，用"状态 + 事件 + 转换"建模 UI 逻辑。

**核心要点：**

**有限状态机（Finite State Machine, FSM）** 是一种数学模型，由以下要素组成：
- **有限数量的状态**（如 idle / loading / success / error）
- **事件**（触发状态转换的输入，如 FETCH / RETRY）
- **转换规则**（在某状态收到某事件时，转到哪个状态）

**类比：** 交通信号灯就是一个状态机——只有红/黄/绿三种状态，按固定规则转换，不可能从绿灯直接跳到红灯。

**普通变量 vs 状态机：**

```typescript
// ❌ 用布尔变量管理——容易出现非法状态组合
const [isLoading, setIsLoading] = useState(false);
const [isError, setIsError] = useState(false);
const [isSuccess, setIsSuccess] = useState(false);
// 问题：isLoading && isError && isSuccess 同时为 true 怎么办？
// 需要开发者自己保证互斥，但没有任何机制强制执行。

// ✅ 用状态机——从根本上消除非法状态
import { setup, assign } from 'xstate';
import { useMachine } from '@xstate/react';

const fetchMachine = setup({
  types: {
    context: {} as { data: any; error: string | null },
    events: {} as
      | { type: 'FETCH' }
      | { type: 'RESOLVE'; data: any }
      | { type: 'REJECT'; error: string }
      | { type: 'RETRY' },
  },
}).createMachine({
  id: 'fetch',
  initial: 'idle',
  context: { data: null, error: null },
  states: {
    idle: {
      on: { FETCH: 'loading' },
    },
    loading: {
      on: {
        RESOLVE: {
          target: 'success',
          actions: assign({ data: ({ event }) => event.data }),
        },
        REJECT: {
          target: 'failure',
          actions: assign({ error: ({ event }) => event.error }),
        },
      },
    },
    success: {
      on: { FETCH: 'loading' }, // 可以重新获取
    },
    failure: {
      on: { RETRY: 'loading' },
    },
  },
});

// 状态机保证：
// 1. idle 状态下只能接收 FETCH 事件
// 2. loading 状态下只能接收 RESOLVE 或 REJECT
// 3. 永远不会出现 "正在加载且已成功" 的矛盾状态
```

**状态机的价值：** 当业务流程有明确的状态和转换规则时（如表单提交流程、支付流程、多步骤向导），状态机能从建模层面消除 bug，而不是靠开发者的纪律来避免非法状态。

</details>

**Q11. RTK Query 和 TanStack Query 有什么区别？如何选择？**

<details>
<summary>参考答案</summary>

**思路分析：** 两者都是数据获取/缓存方案，但设计哲学和适用场景不同。

**核心要点：**

| 维度 | RTK Query | TanStack Query |
|------|-----------|----------------|
| 生态定位 | Redux 生态的一部分，内置于 RTK | 独立库，框架无关（React/Vue/Solid/Svelte） |
| 状态存储 | 数据存储在 Redux store 中 | 独立的 QueryClient 缓存 |
| API 定义 | 集中式 `createApi`，提前声明所有端点 | 分散式，在组件中按需定义 `useQuery` |
| 缓存失效 | 基于 tag 的自动失效（`providesTags` / `invalidatesTags`） | 基于 queryKey 的手动/自动失效 |
| 代码生成 | 支持从 OpenAPI/GraphQL schema 生成 | 需要第三方工具（如 orval） |
| 乐观更新 | 通过 `onQueryStarted` + 手动更新缓存 | 通过 `onMutate` + `setQueryData` |
| 包大小 | 约 12KB（不含 RTK 本身） | 约 13KB |
| DevTools | Redux DevTools | TanStack Query DevTools |

```typescript
// RTK Query —— 集中式 API 定义
import { createApi, fetchBaseQuery } from '@reduxjs/toolkit/query/react';

const api = createApi({
  baseQuery: fetchBaseQuery({ baseUrl: '/api' }),
  tagTypes: ['User'],
  endpoints: (builder) => ({
    getUsers: builder.query<User[], void>({
      query: () => '/users',
      providesTags: ['User'],
    }),
    addUser: builder.mutation<User, Partial<User>>({
      query: (body) => ({ url: '/users', method: 'POST', body }),
      invalidatesTags: ['User'], // 新增用户后自动重新获取用户列表
    }),
  }),
});

export const { useGetUsersQuery, useAddUserMutation } = api;

// TanStack Query —— 分散式按需定义
import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query';

function useUsers() {
  return useQuery({
    queryKey: ['users'],
    queryFn: () => fetch('/api/users').then((r) => r.json()),
  });
}

function useAddUser() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: (user: Partial<User>) =>
      fetch('/api/users', { method: 'POST', body: JSON.stringify(user) }).then((r) => r.json()),
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: ['users'] });
    },
  });
}
```

**选择建议：**
- **已有 Redux 项目** → RTK Query（深度集成，数据在同一个 store 中，可以在 reducer 中访问缓存数据）
- **新项目 / 非 Redux 项目** → TanStack Query（更灵活，社区更大，支持多框架）
- **全栈 TypeScript + OpenAPI** → RTK Query（代码生成更成熟）
- **需要精细控制缓存策略** → TanStack Query（queryKey 组合更灵活）

</details>

**Q12. Zustand 的中间件系统是怎样的？常用的中间件有哪些？**

<details>
<summary>参考答案</summary>

**思路分析：** Zustand 的中间件是高阶函数，通过包裹 `create` 的 state creator 来增强功能。

**核心要点：**

Zustand 的中间件采用函数组合（compose）模式，每个中间件包裹 state creator 函数，在创建 store 的过程中注入额外逻辑。

```typescript
import { create } from 'zustand';
import { devtools, persist, subscribeWithSelector, immer } from 'zustand/middleware';

interface TodoStore {
  todos: { id: number; text: string; done: boolean }[];
  addTodo: (text: string) => void;
  toggleTodo: (id: number) => void;
  removeDone: () => void;
}

const useTodoStore = create<TodoStore>()(
  // 中间件从外到内嵌套（洋葱模型）
  devtools(                          // 1. DevTools：连接 Redux DevTools
    persist(                         // 2. Persist：持久化到 localStorage
      immer(                         // 3. Immer：支持可变式更新
        subscribeWithSelector(       // 4. SubscribeWithSelector：支持选择器订阅
          (set) => ({
            todos: [],
            addTodo: (text) =>
              set((state) => {
                state.todos.push({ id: Date.now(), text, done: false });
              }, false, 'addTodo'),   // 第三个参数是 DevTools 中的 action 名称
            toggleTodo: (id) =>
              set((state) => {
                const todo = state.todos.find((t) => t.id === id);
                if (todo) todo.done = !todo.done;
              }, false, 'toggleTodo'),
            removeDone: () =>
              set((state) => {
                state.todos = state.todos.filter((t) => !t.done);
              }, false, 'removeDone'),
          })
        )
      ),
      { name: 'todo-storage' }       // persist 配置：存储 key
    ),
    { name: 'TodoStore' }            // devtools 配置：DevTools 中的 store 名称
  )
);
```

**常用中间件一览：**

| 中间件 | 作用 | 典型场景 |
|--------|------|---------|
| `devtools` | 连接 Redux DevTools，记录每次状态变更 | 开发调试 |
| `persist` | 将 store 持久化到 localStorage/sessionStorage/IndexedDB | 用户偏好、主题设置 |
| `immer` | 允许在 `set` 中使用可变式写法 | 复杂嵌套状态更新 |
| `subscribeWithSelector` | 支持选择器级别的订阅，只在选中值变化时触发回调 | React 外部监听特定字段 |

```typescript
// subscribeWithSelector 使用示例：在 React 外部监听状态变化
useTodoStore.subscribe(
  (state) => state.todos.length,   // 选择器
  (todosLength, prevLength) => {   // 回调
    console.log(`待办数量从 ${prevLength} 变为 ${todosLength}`);
  },
  { equalityFn: Object.is }       // 比较函数
);
```

</details>

**Q13. 如何优化 Context API 的性能？除了拆分 Context 还有什么方案？**

<details>
<summary>参考答案</summary>

**思路分析：** 从基础优化到高级模式，逐步递进。

**核心要点：**

**方案 1：拆分 Context（最常用）**

将不同变更频率的状态拆分到不同 Context 中，避免一个值变化触发所有消费者重渲染。

```tsx
// 将「状态」和「修改函数」分离到两个 Context
const StateContext = createContext<AppState>(null!);
const DispatchContext = createContext<Dispatch<Action>>(null!);

function AppProvider({ children }: { children: ReactNode }) {
  const [state, dispatch] = useReducer(reducer, initialState);

  return (
    <DispatchContext.Provider value={dispatch}>
      {/* dispatch 是 useReducer 返回的稳定引用，永远不变 */}
      <StateContext.Provider value={state}>
        {children}
      </StateContext.Provider>
    </DispatchContext.Provider>
  );
}

// 只需要触发操作的组件，不会因为 state 变化而重渲染
function AddButton() {
  const dispatch = useContext(DispatchContext); // dispatch 引用稳定
  return <button onClick={() => dispatch({ type: 'ADD' })}>添加</button>;
}
```

**方案 2：useMemo 稳定 value 引用**

```tsx
function Provider({ children }) {
  const [count, setCount] = useState(0);
  const [name, setName] = useState('');

  const value = useMemo(() => ({ count, name, setCount, setName }), [count, name]);

  return <AppContext.Provider value={value}>{children}</AppContext.Provider>;
}
```

**方案 3：订阅模式（Subscription Pattern）**

核心思路：Context 只传递一个不变的订阅器，组件自行订阅感兴趣的部分。这就是 `use-context-selector` 库的原理。

```tsx
import { createContext, useContextSelector } from 'use-context-selector';

const AppContext = createContext<AppState>(null!);

// 组件只在 count 变化时重渲染，name 变化无影响
function CountDisplay() {
  const count = useContextSelector(AppContext, (state) => state.count);
  return <div>{count}</div>;
}

// 组件只在 name 变化时重渲染
function NameDisplay() {
  const name = useContextSelector(AppContext, (state) => state.name);
  return <div>{name}</div>;
}
```

**方案 4：组件组合（Component Composition）**

不使用 Context，通过 children 或 render props 将内容"注入"，避免中间组件参与渲染链。

```tsx
// 将消费 context 的逻辑提升到上层，子组件通过 children 接收
function App() {
  return (
    <ThemeProvider>
      <Layout>
        <ThemedContent />
      </Layout>
    </ThemeProvider>
  );
}

// Layout 不消费 ThemeContext，所以 theme 变化不会触发 Layout 重渲染
function Layout({ children }: { children: ReactNode }) {
  return <div className="layout">{children}</div>;
}
```

**各方案适用场景：**

| 方案 | 适用场景 | 复杂度 |
|------|---------|--------|
| 拆分 Context | 状态可以按领域分组 | 低 |
| useMemo | 快速修复已有代码 | 低 |
| 订阅模式 | 需要细粒度选择器 | 中 |
| 组件组合 | 减少不必要的 Context 使用 | 低 |
| 迁移到 Zustand/Jotai | Context 性能问题严重且优化成本高 | 中 |

</details>

**Q14. Jotai 和 Recoil 有什么区别？为什么说 Jotai 是"Recoil 的精神继承者"？**

<details>
<summary>参考答案</summary>

**思路分析：** 两者都是原子化方案但实现差异大，Recoil 已逐渐不再活跃维护。

**核心要点：**

| 维度 | Recoil | Jotai |
|------|--------|-------|
| 维护状态 | Meta 开源，已不再活跃维护 | Pmndrs 社区维护，持续活跃 |
| Provider | 必须 `<RecoilRoot>` | 可选（默认全局 Provider） |
| Atom 标识 | 需要 `key` 字符串（全局唯一） | 不需要 key（对象引用即标识） |
| 包大小 | ~20KB | ~3.4KB |
| 异步支持 | `Suspense` + `selector` | 原生异步 atom + `Suspense` |
| 快照调试 | 内置 `useRecoilSnapshot` | 通过 DevTools 扩展 |
| TypeScript | 支持，但类型推导不完美 | 一等公民，类型推导优秀 |

```typescript
// Recoil —— 需要字符串 key
import { atom, selector, useRecoilState, useRecoilValue } from 'recoil';

const countState = atom({
  key: 'countState',   // ⚠️ 必须全局唯一，大型项目容易命名冲突
  default: 0,
});

const doubledState = selector({
  key: 'doubledState', // ⚠️ selector 也需要 key
  get: ({ get }) => get(countState) * 2,
});

// Jotai —— 不需要 key，对象引用即标识
import { atom, useAtom } from 'jotai';

const countAtom = atom(0);                           // 无需 key
const doubledAtom = atom((get) => get(countAtom) * 2); // 无需 key

// atomFamily 对比
// Recoil
const todoItemState = atomFamily({
  key: 'todoItem',
  default: (id) => ({ id, text: '', done: false }),
});

// Jotai（使用 atomFamily 工具函数或直接用 Map）
import { atomFamily } from 'jotai/utils';

const todoItemAtom = atomFamily(
  (id: number) => atom({ id, text: '', done: false })
);
```

**为什么选 Jotai：**
1. **无 key 冲突**：Recoil 在大型项目中 key 冲突是真实痛点
2. **包更小**：Jotai 约 3.4KB，Recoil 约 20KB
3. **更活跃**：Recoil 的 npm 下载量已被 Jotai 大幅超越
4. **API 更简洁**：Jotai 的 atom 就是 atom，不区分 atom 和 selector
5. **TypeScript 友好**：类型推导更完整，不需要手动标注

**迁移建议：** 新项目直接用 Jotai；Recoil 项目可以逐步迁移，两者 API 概念相似，迁移成本较低。

</details>

**Q15. Redux 中间件的原理是什么？请手写一个简单的 logger 中间件。**

<details>
<summary>参考答案</summary>

**思路分析：** 理解中间件的函数签名和执行时机是关键。

**核心要点：**

Redux 中间件的本质是 **对 `dispatch` 函数的增强**。它在 action 到达 reducer 之前提供了一个拦截层，可以用来处理异步、日志、错误上报等副作用。

**中间件签名（柯里化三层函数）：**

```
middleware = (storeAPI) => (next) => (action) => { ... }

storeAPI：包含 getState 和 dispatch 的对象
next：    下一个中间件的 dispatch（或原始 dispatch）
action：  当前被 dispatch 的 action
```

**执行流程：**
```diagram
dispatch(action)
  │
  ▼
middleware1 ──▶ middleware2 ──▶ middleware3 ──▶ 原始 dispatch ──▶ reducer
  ◀──────────── ◀──────────── ◀────────────── ◀────────────────
```

**手写 logger 中间件：**

```javascript
// 生产可用的 logger 中间件
const loggerMiddleware = (storeAPI) => (next) => (action) => {
  // 1. action 到达 reducer 之前
  console.group(`[Redux] ${action.type}`);
  console.log('Prev State:', storeAPI.getState());
  console.log('Action:', action);

  // 2. 传递给下一个中间件（或 reducer）
  const result = next(action);

  // 3. reducer 处理完毕之后
  console.log('Next State:', storeAPI.getState());
  console.groupEnd();

  return result;
};

// 手写 thunk 中间件（支持 dispatch 函数）
const thunkMiddleware = (storeAPI) => (next) => (action) => {
  // 如果 action 是函数，调用它并传入 dispatch 和 getState
  if (typeof action === 'function') {
    return action(storeAPI.dispatch, storeAPI.getState);
  }
  // 否则正常传递
  return next(action);
};

// 注册中间件
import { configureStore } from '@reduxjs/toolkit';

const store = configureStore({
  reducer: rootReducer,
  middleware: (getDefaultMiddleware) =>
    getDefaultMiddleware().concat(loggerMiddleware),
  // RTK 默认已包含 thunk 中间件，无需手动添加
});
```

**关键理解：** `next(action)` 和 `storeAPI.dispatch(action)` 的区别——`next` 将 action 传递给下一个中间件，而 `storeAPI.dispatch` 会重新走整个中间件链（从第一个开始）。在 thunk 中间件里用 `storeAPI.dispatch` 就是因为异步回调中的新 action 需要走完整链路。

</details>

**Q16. Zustand 中如何实现细粒度的状态选择（selector）以避免不必要的重渲染？**

<details>
<summary>参考答案</summary>

**思路分析：** Zustand 的 selector 是性能优化的关键，理解浅比较机制。

**核心要点：**

```typescript
import { create } from 'zustand';
import { useShallow } from 'zustand/react/shallow';

interface Store {
  user: { name: string; age: number };
  todos: { id: number; text: string }[];
  theme: string;
  updateUser: (name: string) => void;
  addTodo: (text: string) => void;
}

const useStore = create<Store>((set) => ({
  user: { name: 'Alice', age: 25 },
  todos: [],
  theme: 'light',
  updateUser: (name) => set((s) => ({ user: { ...s.user, name } })),
  addTodo: (text) => set((s) => ({ todos: [...s.todos, { id: Date.now(), text }] })),
}));

// ❌ 反模式：获取整个 store，任何字段变化都导致重渲染
function BadComponent() {
  const store = useStore(); // 订阅整个 store
  return <div>{store.user.name}</div>;
}

// ✅ 正确：选择单个原始值
function UserName() {
  const name = useStore((state) => state.user.name);
  // 只在 user.name 变化时重渲染，theme 或 todos 变化无影响
  return <div>{name}</div>;
}

// ✅ 正确：选择多个值时使用 useShallow
function UserInfo() {
  const { name, age } = useStore(
    useShallow((state) => ({ name: state.user.name, age: state.user.age }))
  );
  // useShallow 对返回对象做浅比较，只在 name 或 age 实际变化时重渲染
  return <div>{name}, {age}</div>;
}

// ✅ 正确：选择数组时用 useShallow
function TodoCount() {
  const todoTexts = useStore(
    useShallow((state) => state.todos.map((t) => t.text))
  );
  return <div>{todoTexts.join(', ')}</div>;
}

// ✅ 正确：使用自定义比较函数
function TodoList() {
  const todos = useStore(
    (state) => state.todos,
    (oldTodos, newTodos) => {
      // 只在数组长度变化时重渲染（忽略单个 todo 内容变化）
      return oldTodos.length === newTodos.length;
    }
  );
  return <div>{todos.length} items</div>;
}
```

**Zustand selector 的比较机制：**

1. **默认行为**：`Object.is` 严格相等比较（引用比较）
2. **`useShallow`**：对返回值做浅比较（一层属性逐个 `Object.is`）
3. **自定义 `equalityFn`**：完全自定义比较逻辑

**最佳实践：**
- 始终使用 selector 提取最小数据集
- 返回原始值（string/number/boolean）时无需额外处理
- 返回新对象/数组时用 `useShallow` 或自定义比较函数
- 避免在 selector 中做大量计算，必要时用 `useMemo` 缓存

**Q17. MobX 中 `computed` 和普通 getter 有什么区别？什么时候用 `reaction` vs `autorun`？**

<details>
<summary>参考答案</summary>

**思路分析：** MobX 的反应式机制中，computed 的缓存特性和 reaction/autorun 的差异是进阶考点。

**核心要点：**

**`computed` vs 普通 getter：**

| 特性 | `computed` (MobX) | 普通 getter |
|------|-------------------|------------|
| 缓存 | ✅ 依赖未变化时返回缓存结果 | ❌ 每次访问都重新计算 |
| 依赖追踪 | ✅ 自动追踪 observable 依赖 | ❌ 无追踪 |
| 惰性求值 | ✅ 只有被访问时才计算 | ✅ 只有被访问时才计算 |
| 触发更新 | ✅ 依赖变化时标记为 dirty | ❌ 不参与响应式系统 |

```typescript
import { makeAutoObservable } from 'mobx';

class OrderStore {
  items: { name: string; price: number; qty: number }[] = [];

  constructor() {
    makeAutoObservable(this);
  }

  // computed：有缓存，多次读取不会重新计算（除非 items 变了）
  get totalPrice() {
    console.log('计算 totalPrice'); // items 未变时不会输出
    return this.items.reduce((sum, item) => sum + item.price * item.qty, 0);
  }

  // computed：只在 totalPrice 变化时重算
  get taxAmount() {
    return this.totalPrice * 0.13;
  }

  addItem(item: { name: string; price: number; qty: number }) {
    this.items.push(item);
  }
}

const store = new OrderStore();
console.log(store.totalPrice); // "计算 totalPrice"，输出 0
console.log(store.totalPrice); // 不会再输出 "计算 totalPrice"，直接返回缓存的 0
```

**`autorun` vs `reaction`：**

```typescript
import { autorun, reaction } from 'mobx';

// autorun：立即执行一次 + 每当依赖变化时重新执行
// 用于"状态变化时自动做某事"的场景
const dispose1 = autorun(() => {
  console.log(`当前总价：${store.totalPrice}`);
  // 第一次调用时立即执行
  // 之后每当 totalPrice 变化时自动执行
});

// reaction：不立即执行，只在「跟踪表达式」的返回值变化时才执行
// 用于"只在特定条件变化时才做某事"的场景
const dispose2 = reaction(
  () => store.items.length,              // 跟踪表达式（data function）
  (length, previousLength) => {           // 效果函数（effect function）
    console.log(`商品数量从 ${previousLength} 变为 ${length}`);
    // 只在 items.length 变化时执行，items 内部属性变化不触发
  }
);

// 清理
dispose1();
dispose2();
```

**选择指南：**
- **`autorun`**：需要初始执行 + 需要对所有被追踪依赖的变化做出反应
- **`reaction`**：只需要对特定数据的变化做出反应，不需要初始执行，可以精确控制"什么变化才触发"

</details>

**Q18. TanStack Query 的缓存机制是怎样的？`staleTime` 和 `gcTime` 的区别是什么？**

<details>
<summary>参考答案</summary>

**思路分析：** TanStack Query 的核心竞争力就是缓存管理，理解这两个时间参数是关键。

**核心要点：**

```diagram
数据生命周期示意图：

Query 首次请求成功
    │
    │  staleTime（新鲜期）
    │  数据被标记为 "fresh"，不会自动重新请求
    │
    ▼
数据变为 "stale"（过期）
    │  但仍可从缓存读取，同时触发后台重新请求
    │
    │  组件卸载
    │
    ▼
进入 "inactive" 状态（无组件在使用此数据）
    │
    │  gcTime（垃圾回收计时器启动）
    │  倒计时期间，如果有新组件挂载并使用相同 queryKey，
    │  立即从缓存返回数据（同时后台刷新）
    │
    ▼
缓存被垃圾回收，下次请求重新获取
```

| 参数 | 默认值 | 含义 | 类比 |
|------|--------|------|------|
| `staleTime` | 0（立即过期） | 数据被认为"新鲜"的时间，新鲜期内不会重新请求 | 面包的保鲜期 |
| `gcTime` | 5 分钟 | 数据没有被任何组件使用后，缓存保留的时间 | 面包过期后在货架上保留多久才下架 |

```typescript
import { useQuery } from '@tanstack/react-query';

// 示例 1：实时性要求高的数据（如聊天消息）
const { data: messages } = useQuery({
  queryKey: ['messages', channelId],
  queryFn: () => fetchMessages(channelId),
  staleTime: 0,            // 立即过期，每次聚焦窗口都重新请求
  gcTime: 5 * 60 * 1000,   // 5 分钟无人使用后回收
  refetchInterval: 3000,   // 每 3 秒轮询
});

// 示例 2：变化不频繁的数据（如用户资料）
const { data: profile } = useQuery({
  queryKey: ['user', userId],
  queryFn: () => fetchUserProfile(userId),
  staleTime: 10 * 60 * 1000,  // 10 分钟内认为新鲜
  gcTime: 60 * 60 * 1000,     // 1 小时后回收
});

// 示例 3：几乎不变的数据（如国家列表）
const { data: countries } = useQuery({
  queryKey: ['countries'],
  queryFn: fetchCountries,
  staleTime: Infinity,         // 永不过期
  gcTime: Infinity,            // 永不回收
});
```

**常见误区澄清：**
- `staleTime` 不是"多久重新请求一次"，而是"这段时间内不需要重新请求"
- 数据过期不代表立即重新请求，而是在下次触发条件（如组件挂载、窗口聚焦）时才请求
- `gcTime` 原名 `cacheTime`，v5 改名以减少误解（它控制的是垃圾回收而非缓存）

**重新请求的触发条件（staleTime 到期后）：**
1. 新的组件挂载并使用相同 queryKey
2. 窗口重新获得焦点（`refetchOnWindowFocus`，默认开启）
3. 网络恢复连接（`refetchOnReconnect`，默认开启）
4. 手动调用 `queryClient.invalidateQueries()`

</details>

**Q19. 如何在 Zustand 中处理异步操作？与 Redux Thunk 有什么不同？**

<details>
<summary>参考答案</summary>

**思路分析：** Zustand 处理异步非常直观，没有额外概念。

**核心要点：**

Zustand 不需要中间件来处理异步——直接在 action 中写 async/await 即可，因为 Zustand 的 action 就是普通函数，没有 Redux 那种"action 必须是纯对象"的约束。

```typescript
import { create } from 'zustand';

interface ProductStore {
  products: Product[];
  loading: boolean;
  error: string | null;
  
  // 异步 action：直接写 async 函数
  fetchProducts: () => Promise<void>;
  createProduct: (data: CreateProductDTO) => Promise<Product>;
}

const useProductStore = create<ProductStore>((set, get) => ({
  products: [],
  loading: false,
  error: null,

  fetchProducts: async () => {
    // 1. 设置 loading
    set({ loading: true, error: null });

    try {
      const response = await fetch('/api/products');
      if (!response.ok) throw new Error(`HTTP ${response.status}`);
      const products = await response.json();

      // 2. 设置数据
      set({ products, loading: false });
    } catch (err) {
      // 3. 设置错误
      set({ error: (err as Error).message, loading: false });
    }
  },

  createProduct: async (data) => {
    const response = await fetch('/api/products', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(data),
    });
    const newProduct = await response.json();

    // 使用 get() 获取当前状态
    set({ products: [...get().products, newProduct] });
    return newProduct;
  },
}));

// 组件中使用
function ProductList() {
  const { products, loading, error, fetchProducts } = useProductStore();

  useEffect(() => {
    fetchProducts();
  }, [fetchProducts]);

  if (loading) return <Spinner />;
  if (error) return <ErrorBanner message={error} />;
  return <ProductGrid products={products} />;
}
```

**对比 Redux Thunk：**

| 维度 | Redux (createAsyncThunk) | Zustand |
|------|--------------------------|---------|
| 异步方式 | 需要 `createAsyncThunk` 包装 | 直接 async/await |
| 状态管理 | 自动生成 pending/fulfilled/rejected | 手动 set loading/error |
| 错误处理 | `rejectWithValue` | 标准 try/catch |
| 学习成本 | 需理解 thunk、extraReducers、builder | 零额外概念 |
| 灵活性 | 中等（需遵循 RTK 约定） | 高（就是普通函数） |
| 可追踪性 | 高（每个阶段都有 action 记录） | 低（DevTools 中只看到 set 调用） |

**总结：** Zustand 的异步更直观，但缺少 Redux 那种每个异步阶段都有 action 记录的可追踪性。对于需要严格审计异步流程的场景（如金融类应用），Redux 的结构化异步更有优势。

</details>

**Q20. XState 中的 parallel states（并行状态）和 guards（守卫）是什么？**

<details>
<summary>参考答案</summary>

**思路分析：** XState 的进阶特性，展示状态机在复杂场景中的表达力。

**核心要点：**

**并行状态（Parallel States）：** 同一个状态机中，多个子状态可以同时处于不同状态，互不影响。

```diagram
类比：一辆车的多个系统同时独立运行
  ├── 引擎：关闭 / 怠速 / 运转
  ├── 车灯：关闭 / 近光 / 远光
  └── 空调：关闭 / 制冷 / 制热

三个系统可以任意组合，互不影响。
```

```typescript
import { setup } from 'xstate';

const playerMachine = setup({
  types: {
    events: {} as
      | { type: 'TOGGLE_PLAY' }
      | { type: 'TOGGLE_MUTE' }
      | { type: 'TOGGLE_FULLSCREEN' },
  },
}).createMachine({
  id: 'player',
  type: 'parallel',  // 标记为并行状态机
  states: {
    // 子状态 1：播放控制
    playback: {
      initial: 'paused',
      states: {
        paused: { on: { TOGGLE_PLAY: 'playing' } },
        playing: { on: { TOGGLE_PLAY: 'paused' } },
      },
    },
    // 子状态 2：音量控制（与播放状态独立）
    volume: {
      initial: 'unmuted',
      states: {
        unmuted: { on: { TOGGLE_MUTE: 'muted' } },
        muted: { on: { TOGGLE_MUTE: 'unmuted' } },
      },
    },
    // 子状态 3：全屏控制（与上述两者都独立）
    display: {
      initial: 'normal',
      states: {
        normal: { on: { TOGGLE_FULLSCREEN: 'fullscreen' } },
        fullscreen: { on: { TOGGLE_FULLSCREEN: 'normal' } },
      },
    },
  },
});

// 可能的状态组合：
// { playback: 'playing', volume: 'muted', display: 'fullscreen' }
// { playback: 'paused', volume: 'unmuted', display: 'normal' }
// ... 共 2×2×2 = 8 种合法组合，全部由状态机保证合法
```

**守卫（Guards）：** 条件判断，只有满足条件时才允许状态转换。

```typescript
const paymentMachine = setup({
  types: {
    context: {} as { balance: number; amount: number },
    events: {} as
      | { type: 'PAY'; amount: number }
      | { type: 'TOP_UP'; amount: number },
  },
  guards: {
    hasSufficientBalance: ({ context, event }) => {
      return event.type === 'PAY' && context.balance >= event.amount;
    },
    isValidAmount: ({ event }) => {
      return 'amount' in event && event.amount > 0;
    },
  },
}).createMachine({
  id: 'payment',
  initial: 'idle',
  context: { balance: 100, amount: 0 },
  states: {
    idle: {
      on: {
        PAY: [
          {
            // 守卫 1：余额足够 → 进入处理
            guard: 'hasSufficientBalance',
            target: 'processing',
          },
          {
            // 守卫不满足 → 进入余额不足
            target: 'insufficientFunds',
          },
        ],
      },
    },
    processing: {
      // ... 处理支付
    },
    insufficientFunds: {
      on: {
        TOP_UP: {
          guard: 'isValidAmount',
          target: 'idle',
        },
      },
    },
  },
});
```

**Guards 的价值：** 把业务规则编码到状态机定义中，而不是分散在组件代码里。当业务规则变更时，只需修改状态机定义，不需要在各个组件中搜索和修改条件判断。

**Q21. 如何实现跨 store 的状态通信？比较 Redux、Zustand、Jotai 的方案。**

<details>
<summary>参考答案</summary>

**思路分析：** 大型应用中不可避免需要多个 store 之间的通信，不同方案有不同策略。

**核心要点：**

**Redux —— 单一 store，天然无跨 store 问题：**

Redux 只有一个 store，不同 slice 通过 `extraReducers` 监听其他 slice 的 action 来实现通信。

```typescript
// userSlice.ts
const userSlice = createSlice({
  name: 'user',
  initialState: { currentUser: null, isLoggedIn: false },
  reducers: {
    login: (state, action) => {
      state.currentUser = action.payload;
      state.isLoggedIn = true;
    },
    logout: (state) => {
      state.currentUser = null;
      state.isLoggedIn = false;
    },
  },
});

// cartSlice.ts —— 监听 user 的 logout action，自动清空购物车
const cartSlice = createSlice({
  name: 'cart',
  initialState: { items: [] },
  reducers: {
    addItem: (state, action) => { state.items.push(action.payload); },
  },
  extraReducers: (builder) => {
    // 当用户登出时，自动清空购物车
    builder.addCase(userSlice.actions.logout, (state) => {
      state.items = [];
    });
  },
});
```

**Zustand —— 多 store 之间通过 `get` / `subscribe` 通信：**

```typescript
// userStore.ts
const useUserStore = create<UserStore>((set) => ({
  user: null,
  login: async (credentials) => {
    const user = await authApi.login(credentials);
    set({ user });

    // 方式 1：直接调用其他 store 的 action
    useCartStore.getState().loadCartForUser(user.id);
    useNotificationStore.getState().fetchUnread(user.id);
  },
  logout: () => {
    set({ user: null });
    // 登出时清理其他 store
    useCartStore.getState().clearCart();
  },
}));

// 方式 2：使用 subscribe 监听其他 store 的变化
const useCartStore = create<CartStore>((set, get) => ({
  items: [],
  loadCartForUser: async (userId: string) => {
    const items = await cartApi.getItems(userId);
    set({ items });
  },
  clearCart: () => set({ items: [] }),
}));

// 在应用初始化时设置跨 store 订阅
useUserStore.subscribe(
  (state) => state.user,
  (user, prevUser) => {
    if (!user && prevUser) {
      // 用户登出，清空购物车
      useCartStore.getState().clearCart();
    }
  }
);
```

**Jotai —— 通过 atom 依赖天然组合：**

```typescript
import { atom } from 'jotai';

// 基础 atom
const userAtom = atom<User | null>(null);
const cartItemsAtom = atom<CartItem[]>([]);

// 派生 atom：自动依赖 userAtom 和 cartItemsAtom
const cartSummaryAtom = atom((get) => {
  const user = get(userAtom);
  const items = get(cartItemsAtom);

  if (!user) return { items: [], total: 0, discount: 0 };

  const total = items.reduce((sum, item) => sum + item.price * item.qty, 0);
  const discount = user.vipLevel > 2 ? total * 0.1 : 0;

  return { items, total, discount };

// 写入 atom：修改一个 atom 时联动修改另一个
const logoutAtom = atom(null, (get, set) => {
  set(userAtom, null);
  set(cartItemsAtom, []);    // 联动清空购物车
});
```

| 方案 | 跨 store 通信方式 | 优点 | 缺点 |
|------|-------------------|------|------|
| Redux | extraReducers 监听 action | 数据流清晰可追踪 | 单 store 可能膨胀 |
| Zustand | 直接调用 / subscribe | 灵活，无限制 | 依赖关系隐式，缺乏约束 |
| Jotai | atom 依赖图自动组合 | 声明式，依赖关系明确 | 复杂逻辑可能导致 atom 过多 |

- Q: 如果 Zustand 的 store A 和 store B 互相依赖怎么办？
- A: 避免循环依赖。可以抽取共享逻辑到独立的 store C，或使用事件总线模式解耦。

**Q22. TanStack Query 的乐观更新（Optimistic Updates）如何实现？如何处理回滚？**

<details>
<summary>参考答案</summary>

**思路分析：** 乐观更新是提升用户体验的重要模式，但错误处理是关键。

**核心要点：**

**乐观更新**：在服务端确认之前，先在本地"假设成功"地更新 UI，如果服务端返回失败则回滚到之前的状态。

```diagram
普通更新流程：
  点击 ──▶ 请求中(loading) ──▶ 成功 ──▶ 更新 UI
                                        ↑ 用户等待 200-500ms

乐观更新流程：
  点击 ──▶ 立即更新 UI ──▶ 后台请求 ──▶ 成功（UI 不变）
                                         失败（回滚 UI + 提示用户）
                ↑ 用户零等待感知
```

```typescript
import { useMutation, useQueryClient } from '@tanstack/react-query';

interface Todo {
  id: number;
  title: string;
  completed: boolean;
}

function useTodoToggle() {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: (todo: Todo) =>
      fetch(`/api/todos/${todo.id}`, {
        method: 'PATCH',
        body: JSON.stringify({ completed: !todo.completed }),
        headers: { 'Content-Type': 'application/json' },
      }).then((r) => {
        if (!r.ok) throw new Error('更新失败');
        return r.json();
      }),

    // 1. 乐观更新：在请求发出之前执行
    onMutate: async (toggledTodo) => {
      // 取消正在进行的请求，避免覆盖乐观更新
      await queryClient.cancelQueries({ queryKey: ['todos'] });

      // 保存当前数据快照（用于回滚）
      const previousTodos = queryClient.getQueryData<Todo[]>(['todos']);

      // 乐观更新缓存
      queryClient.setQueryData<Todo[]>(['todos'], (old) =>
        old?.map((todo) =>
          todo.id === toggledTodo.id
            ? { ...todo, completed: !todo.completed }
            : todo
        )
      );

      // 返回快照，传递给 onError 用于回滚
      return { previousTodos };
    },

    // 2. 请求失败：回滚到快照
    onError: (err, toggledTodo, context) => {
      if (context?.previousTodos) {
        queryClient.setQueryData(['todos'], context.previousTodos);
      }
      toast.error('操作失败，已恢复');
    },

    // 3. 无论成功失败，都重新获取最新数据以确保一致性
    onSettled: () => {
      queryClient.invalidateQueries({ queryKey: ['todos'] });
    },
  });
}

// 组件中使用
function TodoItem({ todo }: { todo: Todo }) {
  const toggleMutation = useTodoToggle();

  return (
    <label>
      <input
        type="checkbox"
        checked={todo.completed}
        onChange={() => toggleMutation.mutate(todo)}
        disabled={toggleMutation.isPending}
      />
      {todo.title}
    </label>
  );
}
```

**关键步骤总结：**

| 步骤 | 回调 | 作用 |
|------|------|------|
| 1 | `onMutate` | 取消进行中的查询 → 保存快照 → 乐观更新缓存 |
| 2 | `onError` | 使用快照回滚缓存 → 提示用户 |
| 3 | `onSettled` | 无论成功失败，重新获取最新数据 |

**追问：并发乐观更新怎么处理？**

当用户快速连续操作时（如快速 toggle 多个 todo），每次 `onMutate` 保存的快照是上一次乐观更新后的状态，不是服务端的真实状态。`onSettled` 中的 `invalidateQueries` 会在所有 mutation 结束后重新获取真实数据，确保最终一致性。

**Q23. 状态管理中的"状态协同"（State Colocation）原则是什么？如何判断状态应该放在哪里？**

<details>
<summary>参考答案</summary>

**思路分析：** 这是架构级别的问题，考查候选人对状态管理的整体理解。

**核心要点：**

**状态协同（State Colocation）** 的核心思想：**状态应该尽可能靠近使用它的地方。** 不是所有状态都需要放在全局 store 中。

```diagram
状态放置决策树：

  这个状态只有一个组件用到吗？
    ├── 是 → useState（组件内部状态）
    │
    └── 否 → 只有父子组件需要共享吗？
              ├── 是 → 提升到共同父组件（Lifting State Up）
              │
              └── 否 → 是服务端数据吗？
                        ├── 是 → TanStack Query / RTK Query（服务端缓存）
                        │
                        └── 否 → 跨多个不相关组件共享吗？
                                  ├── 是 → Zustand / Redux / Jotai（全局状态）
                                  │
                                  └── 否 → 是低频变更的全局配置吗？
                                            ├── 是 → Context API（主题/语言/认证）
                                            └── 否 → URL 状态 / 表单库
```

**状态分类与推荐方案：**

| 状态类型 | 特征 | 推荐方案 | 示例 |
|----------|------|---------|------|
| 局部 UI 状态 | 单组件内部 | `useState` / `useReducer` | 弹窗开关、输入值、hover 状态 |
| 共享 UI 状态 | 多组件共享 | Zustand / Jotai | 侧边栏状态、全局 loading |
| 服务端缓存 | API 返回数据 | TanStack Query / RTK Query | 用户列表、商品数据 |
| 表单状态 | 复杂表单验证 | React Hook Form / Formik | 注册表单、订单表单 |
| URL 状态 | 需要可分享/可书签 | URL 参数 / nuqs | 搜索条件、分页、筛选 |
| 全局配置 | 低频变更 | Context API | 主题、语言、认证 |
| 复杂业务流程 | 有明确状态转换 | XState | 支付流程、多步骤向导 |

**Q24. Redux 中 selector 的 memoization 如何实现？`createSelector` 的工作原理和陷阱是什么？**

<details>
<summary>参考答案</summary>

**思路分析：** Reselect 的 `createSelector` 是 Redux 性能优化的核心工具。

**核心要点：**

`createSelector`（来自 Reselect，RTK 已重新导出）创建记忆化的选择器函数。它缓存上一次的输入和输出，只有当输入变化时才重新计算。

```typescript
import { createSelector } from '@reduxjs/toolkit';

interface RootState {
  todos: { id: number; text: string; completed: boolean; category: string }[];
  filter: { status: string; category: string };
}

// 基础选择器（input selectors）—— 从 state 中提取原始数据
const selectTodos = (state: RootState) => state.todos;
const selectFilter = (state: RootState) => state.filter;

// 记忆化选择器（result selector）—— 组合计算
const selectFilteredTodos = createSelector(
  [selectTodos, selectFilter],
  (todos, filter) => {
    // 这个函数只在 todos 或 filter 引用变化时才执行
    console.log('重新计算 filteredTodos');
    return todos.filter((todo) => {
      const statusMatch =
        filter.status === 'all' ||
        (filter.status === 'active' && !todo.completed) ||
        (filter.status === 'completed' && todo.completed);
      const categoryMatch =
        filter.category === 'all' || todo.category === filter.category;
      return statusMatch && categoryMatch;
    });
  }
);

// 嵌套组合：selector 可以作为其他 selector 的输入
const selectTodoStats = createSelector([selectFilteredTodos], (filtered) => ({
  total: filtered.length,
  completed: filtered.filter((t) => t.completed).length,
  active: filtered.filter((t) => !t.completed).length,
}));
```

**⚠️ 常见陷阱：**

```typescript
// 陷阱 1：在组件内创建 selector → 每次渲染都是新实例，缓存失效
function TodoList({ category }: { category: string }) {
  // ❌ 每次渲染都创建新的 selector，memoization 无效
  const filteredTodos = useSelector(
    createSelector(
      [selectTodos],
      (todos) => todos.filter((t) => t.category === category)
    )
  );
}

// ✅ 方案 1：使用 useMemo 缓存 selector 实例
function TodoList({ category }: { category: string }) {
  const selectByCategory = useMemo(
    () =>
      createSelector([selectTodos], (todos) =>
        todos.filter((t) => t.category === category)
      ),
    [category]
  );
  const filteredTodos = useSelector(selectByCategory);
}

// ✅ 方案 2：使用 selector 工厂函数
const makeSelectByCategory = (category: string) =>
  createSelector([selectTodos], (todos) =>
    todos.filter((t) => t.category === category)
  );

function TodoList({ category }: { category: string }) {
  const selectByCategory = useMemo(() => makeSelectByCategory(category), [category]);
  const filteredTodos = useSelector(selectByCategory);
}
```

```typescript
// 陷阱 2：input selector 返回新引用 → 缓存永远失效
// ❌ 每次调用都返回新数组引用
const selectActiveIds = (state: RootState) =>
  state.todos.filter((t) => !t.completed).map((t) => t.id);
//   ↑ filter + map 每次都产生新数组

// ✅ 应该把 filter/map 放在 createSelector 的 result function 中
const selectActiveIds = createSelector(
  [selectTodos],
  (todos) => todos.filter((t) => !t.completed).map((t) => t.id)
);
```

**`createSelector` 内部原理：**
1. 调用所有 input selectors，收集返回值
2. 使用 `===` 比较每个返回值与上一次的返回值
3. 如果全部相同 → 直接返回上一次的计算结果
4. 如果有任何不同 → 调用 result function 重新计算，缓存新结果

**追问：** 默认的 `createSelector` 缓存大小是 1（只缓存最近一次），如果需要缓存多个结果怎么办？
- RTK 的 `createSelector` 支持 `memoizeOptions` 参数配置缓存大小
- 或者使用 `createSelectorCreator` 自定义缓存策略（如 LRU 缓存）

**Q25. MobX 的 Proxy 追踪机制是如何工作的？它有什么限制？**

<details>
<summary>参考答案</summary>

**思路分析：** MobX 底层依赖 ES6 Proxy 进行属性访问追踪，理解机制和限制是高级面试点。

**核心要点：**

**MobX 响应式追踪原理：**

MobX 使用 `Proxy` 包装 observable 对象。当在 `autorun`、`reaction` 或 `observer` 组件的渲染函数中访问属性时，MobX 会记录"谁在读取什么"，建立依赖关系图。

```
工作流程：

1. observer(Component) 渲染时，MobX 进入"追踪模式"
2. 渲染函数访问 store.user.name
   → Proxy 拦截 get 操作
   → MobX 记录：Component 依赖 store.user.name
3. 渲染函数访问 store.todos.length
   → Proxy 拦截 get 操作
   → MobX 记录：Component 依赖 store.todos
4. 渲染结束，追踪完成
5. 当 store.user.name 变化时
   → Proxy 拦截 set 操作
   → MobX 查找所有依赖此属性的 observer
   → 触发它们重新渲染
```

```typescript
import { observable, autorun, trace } from 'mobx';

const store = observable({
  user: { name: 'Alice', age: 25 },
  todos: [{ text: 'Buy milk' }],
});

// MobX 只追踪在"追踪上下文"中实际被访问的属性
autorun(() => {
  console.log(store.user.name);
  // MobX 追踪：store.user（对象访问）+ store.user.name（属性访问）
  // store.user.age 没有被访问，所以改变 age 不会触发此 autorun
  // store.todos 没有被访问，所以改变 todos 不会触发此 autorun
});

store.user.name = 'Bob';  // ✅ 触发 autorun
store.user.age = 30;      // ❌ 不触发（未被追踪）
store.todos.push({});     // ❌ 不触发（未被追踪）
```

**⚠️ Proxy 追踪的限制：**

```typescript
import { makeAutoObservable, runInAction } from 'mobx';

class Store {
  data = { a: 1, b: 2 };

  constructor() {
    makeAutoObservable(this);
  }
}

const store = new Store();

// 限制 1：解构会丢失响应性
autorun(() => {
  const { a } = store.data; // ❌ 解构在追踪上下文外读取值，之后就是普通变量了
  console.log(a);           // 不会在 store.data.a 变化时触发
});

// ✅ 正确：在追踪上下文中直接访问
autorun(() => {
  console.log(store.data.a); // ✅ Proxy 能拦截到属性访问
});

// 限制 2：异步代码中的追踪
autorun(async () => {
  console.log(store.data.a);        // ✅ 同步部分被追踪
  await someAsyncOperation();
  console.log(store.data.b);        // ❌ await 之后的访问不被追踪
  // 因为 MobX 的追踪是同步的，await 之后已经退出追踪上下文
});

// 限制 3：Map/Set 需要用 observable.map / observable.set
const store2 = observable({
  users: new Map(),  // ❌ 原生 Map 不是 observable
});

const store3 = observable({
  users: observable.map(), // ✅ 使用 MobX 的 observable.map
});
```

**追问：MobX 6 为什么从装饰器转向 `makeAutoObservable`？**
- 装饰器提案长期不稳定（Stage 2 → Stage 3 语法变更）
- `makeAutoObservable` 在 constructor 中一行代码完成，无需为每个属性手动标注
- 更好的 Tree Shaking 支持

**Q26. 如何设计一个支持撤销/重做（Undo/Redo）的状态管理方案？**

<details>
<summary>参考答案</summary>

**思路分析：** 考查对状态历史管理和不可变数据结构的理解。

**核心要点：**

**核心思路：** 维护一个状态历史栈，undo 回退到上一个快照，redo 前进到下一个快照。

```diagram
状态历史栈示意：

  past              present         future
┌────────────────┐  ┌──────┐  ┌────────────────┐
│ [S0, S1, S2]   │  │  S3  │  │ [S4, S5]       │
└────────────────┘  └──────┘  └────────────────┘

Undo: past 末尾弹出 → 变为 present，原 present 推入 future
Redo: future 末尾弹出 → 变为 present，原 present 推入 past
新操作: present 推入 past，future 清空
```

**方案 1：Zustand + temporal 中间件**

```typescript
import { create } from 'zustand';
import { temporal } from 'zundo';

interface CanvasStore {
  shapes: Shape[];
  selectedId: string | null;  // 不需要历史记录的 UI 状态
  addShape: (shape: Shape) => void;
  moveShape: (id: string, x: number, y: number) => void;
  deleteShape: (id: string) => void;
  selectShape: (id: string | null) => void;
}

const useCanvasStore = create<CanvasStore>()(
  temporal(
    (set) => ({
      shapes: [],
      selectedId: null,
      addShape: (shape) =>
        set((s) => ({ shapes: [...s.shapes, shape] })),
      moveShape: (id, x, y) =>
        set((s) => ({
          shapes: s.shapes.map((shape) =>
            shape.id === id ? { ...shape, x, y } : shape
          ),
        })),
      deleteShape: (id) =>
        set((s) => ({ shapes: s.shapes.filter((shape) => shape.id !== id) })),
      selectShape: (id) => set({ selectedId: id }),
    }),
    {
      // 配置：只追踪 shapes 的变化历史，忽略 selectedId
      partialize: (state) => ({
        shapes: state.shapes,
      }),
      limit: 50, // 最多保留 50 步历史
    }
  )
);

// 使用撤销/重做
function UndoRedoButtons() {
  const { undo, redo, pastStates, futureStates } = useCanvasStore.temporal.getState();

  return (
    <div>
      <button onClick={() => undo()} disabled={pastStates.length === 0}>
        撤销 ({pastStates.length})
      </button>
      <button onClick={() => redo()} disabled={futureStates.length === 0}>
        重做 ({futureStates.length})
      </button>
    </div>
  );
}
```

**方案 2：手动实现（适用于任何框架）**

```typescript
interface HistoryManager<T> {
  past: T[];
  present: T;
  future: T[];
}

function createHistoryManager<T>(initialState: T): HistoryManager<T> {
  return {
    past: [],
    present: initialState,
    future: [],
  };
}

function pushState<T>(history: HistoryManager<T>, newState: T): HistoryManager<T> {
  return {
    past: [...history.past, history.present],
    present: newState,
    future: [], // 新操作清空 future
  };
}

function undo<T>(history: HistoryManager<T>): HistoryManager<T> {
  if (history.past.length === 0) return history;
  const previous = history.past[history.past.length - 1];
  return {
    past: history.past.slice(0, -1),
    present: previous,
    future: [history.present, ...history.future],
  };
}

function redo<T>(history: HistoryManager<T>): HistoryManager<T> {
  if (history.future.length === 0) return history;
  const next = history.future[0];
  return {
    past: [...history.past, history.present],
    present: next,
    future: history.future.slice(1),
  };
}
```

**注意事项：**
- 不可变数据结构是前提——如果直接修改对象，历史快照会被污染
- 大型状态需考虑内存：使用 `limit` 限制历史深度，或用 structural sharing 减少内存占用
- 区分"可撤销状态"和"不可撤销状态"（如选中状态、滚动位置不需要撤销）

**Q28. 比较 Redux、Zustand、Jotai、MobX 的渲染性能优化策略。**

**思路分析：** 从"如何避免不必要的重渲染"角度对比各方案。

**核心要点：**

| 方案 | 更新粒度 | 优化机制 | 开发者需要做的 |
|------|---------|---------|---------------|
| Redux | Selector 级别 | `useSelector` + `createSelector` 记忆化 | 编写精确的 selector |
| Zustand | Selector 级别 | Selector + `useShallow` 浅比较 | 编写 selector + 选择比较策略 |
| Jotai | Atom 级别 | 天然 atom 粒度，只有订阅的 atom 变化才更新 | 合理拆分 atom |
| MobX | 属性级别 | Proxy 追踪精确到属性，`observer` 自动优化 | 用 `observer` 包裹组件 |

**各方案渲染优化代码对比：**

```typescript
// Redux：需要手动编写 selector
function UserInfo() {
  // ❌ 返回新对象引用，每次 store 变化都重渲染
  const user = useSelector((state) => ({
    name: state.user.name,
    email: state.user.email,
  }));

  // ✅ 使用 createSelector 缓存
  const selectUserInfo = useMemo(
    () => createSelector(
      [(s: RootState) => s.user.name, (s: RootState) => s.user.email],
      (name, email) => ({ name, email })
    ),
    []
  );
  const user2 = useSelector(selectUserInfo);
}

// Zustand：selector + useShallow
function UserInfo() {
  // ✅ 原始值 selector 天然高效
  const name = useStore((s) => s.user.name);

  // ✅ 对象用 useShallow
  const { name, email } = useStore(
    useShallow((s) => ({ name: s.user.name, email: s.user.email }))
  );
}

// Jotai：天然 atom 粒度
const nameAtom = atom((get) => get(userAtom).name);
const emailAtom = atom((get) => get(userAtom).email);

function UserInfo() {
  const [name] = useAtom(nameAtom);   // 只在 name 变化时更新
  const [email] = useAtom(emailAtom); // 只在 email 变化时更新
}

// MobX：observer 自动追踪
const UserInfo = observer(({ store }: { store: UserStore }) => {
  // MobX 自动追踪：渲染中访问了 store.name 和 store.email
  // 只有这两个属性变化时才重渲染，无需任何手动优化
  return (
    <div>
      <span>{store.name}</span>
      <span>{store.email}</span>
    </div>
  );
});
```

**性能优化便利度排序：**
1. **MobX** > **Jotai** > **Zustand** > **Redux**

MobX 和 Jotai 的优化几乎是自动的；Zustand 需要 selector 但比 Redux 简单；Redux 需要最多的手动优化工作。

**但这不意味着 MobX 一定"更好"——** 隐式的追踪在大型项目中可能导致难以调试的更新链路，而 Redux 的显式数据流虽然冗长但更易于追踪和调试。

```typescript
  province: z.string().min(1, '请选择省份'),
  city: z.string().min(1, '请选择城市'),

  address: {},
  payment: {},

        set((s) => ({ address: { ...s.address, ...data } })),

        const newErrors = { ...state.errors };

          if (key.startsWith(step)) delete newErrors[key];

        set({ errors: newErrors });
        return true;

          state.validateStep('basicInfo') &&
          state.validateStep('address') &&
          state.validateStep('payment')

        basicInfo: state.basicInfo,
        address: state.address,
        payment: state.payment,
      }),
    }
```

**Q30. 如何实现跨多个 store 的乐观更新和一致性回滚？**

<details>
<summary>参考答案</summary>

**思路分析：** 当一个用户操作需要同时更新多个 store 时，乐观更新的回滚变得复杂。

**核心要点：**

**场景：** 电商"加入购物车"操作，需要同时更新：
- 商品 store（库存 -1）
- 购物车 store（商品 +1）
- 用户 store（购物车角标 +1）

如果后端返回失败，三个 store 都需要回滚。

```typescript
// 事务式乐观更新管理器
class OptimisticTransaction {
  private rollbacks: (() => void)[] = [];
  private committed = false;

  addRollback(rollback: () => void) {
    this.rollbacks.push(rollback);
  }

  commit() {
    this.committed = true;
    this.rollbacks = [];
  }

  rollback() {
    if (this.committed) return;
    // 逆序回滚，确保依赖关系正确
    [...this.rollbacks].reverse().forEach((fn) => fn());
    this.rollbacks = [];
  }
}

// 各 Store 定义
const useProductStore = create<ProductStore>((set, get) => ({
  products: new Map<string, Product>(),

  optimisticDecrementStock: (productId: string) => {
    const prev = get().products.get(productId);
    if (!prev) return () => {};

    set((s) => {
      const updated = new Map(s.products);
      updated.set(productId, { ...prev, stock: prev.stock - 1 });
      return { products: updated };
    });

    // 返回回滚函数
    return () => {
      set((s) => {
        const updated = new Map(s.products);
        updated.set(productId, prev);
        return { products: updated };
      });
    };
  },
}));

const useCartStore = create<CartStore>((set, get) => ({
  items: [],

  optimisticAddItem: (product: Product) => {
    const prevItems = [...get().items];

    set((s) => ({
      items: [...s.items, { productId: product.id, name: product.name, qty: 1 }],
    }));

    return () => set({ items: prevItems });
  },
}));

const useUIStore = create<UIStore>((set, get) => ({
  cartBadge: 0,

  optimisticIncrementBadge: () => {
    const prevBadge = get().cartBadge;
    set({ cartBadge: prevBadge + 1 });
    return () => set({ cartBadge: prevBadge });
  },
}));

// 聚合操作：跨 store 乐观更新 + 事务回滚
async function addToCartWithOptimisticUpdate(product: Product) {
  const tx = new OptimisticTransaction();

  // 1. 乐观更新所有 store
  const rollbackStock = useProductStore.getState().optimisticDecrementStock(product.id);
  tx.addRollback(rollbackStock);

  const rollbackCart = useCartStore.getState().optimisticAddItem(product);
  tx.addRollback(rollbackCart);

  const rollbackBadge = useUIStore.getState().optimisticIncrementBadge();
  tx.addRollback(rollbackBadge);

  try {
    // 2. 发送请求
    await fetch('/api/cart/add', {
      method: 'POST',
      body: JSON.stringify({ productId: product.id }),
      headers: { 'Content-Type': 'application/json' },
    }).then((r) => {
      if (!r.ok) throw new Error('添加购物车失败');
    });

    // 3. 成功：提交事务
    tx.commit();
    toast.success('已加入购物车');
  } catch (error) {
    // 4. 失败：回滚所有 store
    tx.rollback();
    toast.error('操作失败，请重试');
  }
}

// 组件中使用
function AddToCartButton({ product }: { product: Product }) {
  const [loading, setLoading] = useState(false);

  const handleClick = async () => {
    setLoading(true);
    await addToCartWithOptimisticUpdate(product);
    setLoading(false);
  };

  return (
    <button onClick={handleClick} disabled={loading || product.stock <= 0}>
      {loading ? '添加中...' : '加入购物车'}
    </button>
  );
}
```

**核心设计要点：**

1. **每个 store 的乐观更新方法都返回回滚函数**：将回滚逻辑内聚在各自的 store 中
2. **事务管理器统一协调**：收集所有回滚函数，失败时逆序执行
3. **逆序回滚**：确保依赖关系正确（先加的后撤）
4. **commit 防止重复回滚**：成功后标记已提交，清空回滚队列

**追问：如果用户在请求过程中又做了其他操作怎么办？**

可以引入版本号或操作队列：每次操作生成唯一 ID，回滚时检查当前状态是否已被后续操作覆盖，如果是则跳过回滚（因为后续操作已经包含了正确的状态）。

```typescript
// bridge.ts —— Redux 和 Zustand 之间的桥接
import { store as reduxStore } from './redux/store';
import { create } from 'zustand';

// 从 Redux 读取数据供 Zustand store 使用
export function getReduxState<T>(selector: (state: RootState) => T): T {
  return selector(reduxStore.getState());
}

// 在 Zustand store 中订阅 Redux 变化
export function subscribeToRedux<T>(
  selector: (state: RootState) => T,
  callback: (value: T) => void
) {
  let currentValue = selector(reduxStore.getState());
  return reduxStore.subscribe(() => {
    const newValue = selector(reduxStore.getState());
    if (newValue !== currentValue) {
      currentValue = newValue;
      callback(newValue);
    }
  });
}
```

**跨应用状态共享的三个层级：**

```diagram

│  ┌─────────────────────────────────────────────────────┐  │
│  │  共享状态层（用户认证、主题、通知、权限）               │  │

│       ▲              ▲              ▲                     │

│  │ (React)  │   │ (Vue)    │  │ (React)  │              │
│  │ Zustand  │   │ Pinia    │  │ Redux    │              │
│  └──────────┘   └──────────┘  └──────────┘              │
└───────────────────────────────────────────────────────────┘
```

**方案：基于 CustomEvent 的发布-订阅 + 共享 Store**

```typescript
// shared-state.ts —— 框架无关的共享状态层

type Listener<T> = (state: T) => void;

class SharedStore<T extends Record<string, unknown>> {
  private state: T;
  private listeners = new Map<string, Set<Listener<any>>>();
  private namespace: string;

  constructor(namespace: string, initialState: T) {
    this.namespace = namespace;

    // 尝试从 window 上恢复已有状态（防止子应用重复初始化）
    const existing = (window as any).__SHARED_STORES__?.[namespace];
    this.state = existing ?? initialState;

    // 注册到全局
    (window as any).__SHARED_STORES__ = (window as any).__SHARED_STORES__ || {};
    (window as any).__SHARED_STORES__[namespace] = this.state;

    // 监听其他应用的状态变更
    window.addEventListener(`shared-state:${namespace}`, ((e: CustomEvent) => {
      this.state = { ...this.state, ...e.detail.changes };
      (window as any).__SHARED_STORES__[namespace] = this.state;
      this.notifyListeners(Object.keys(e.detail.changes));
    }) as EventListener);
  }

  getState(): Readonly<T> {
    return this.state;
  }

  setState(changes: Partial<T>, source = 'unknown') {
    this.state = { ...this.state, ...changes };
    (window as any).__SHARED_STORES__[this.namespace] = this.state;

    // 通知本地 listeners
    this.notifyListeners(Object.keys(changes));

    // 通知其他应用
    window.dispatchEvent(
      new CustomEvent(`shared-state:${this.namespace}`, {
        detail: { changes, source },
      })
    );
  }

  subscribe<K extends keyof T>(key: K, listener: Listener<T[K]>) {
    if (!this.listeners.has(key as string)) {
      this.listeners.set(key as string, new Set());
    }
    this.listeners.get(key as string)!.add(listener);

    return () => {
      this.listeners.get(key as string)?.delete(listener);
    };
  }

  private notifyListeners(changedKeys: string[]) {
    changedKeys.forEach((key) => {
      this.listeners.get(key)?.forEach((listener) => {
        listener(this.state[key as keyof T]);
      });
    });
  }
}

// 创建共享 store 实例
export const sharedAuthStore = new SharedStore('auth', {
  user: null as User | null,
  token: null as string | null,
  isAuthenticated: false,
});

export const sharedThemeStore = new SharedStore('theme', {
  mode: 'light' as 'light' | 'dark',
  primaryColor: '#1890ff',
});
```

```typescript
// React 子应用中使用：封装为 Hook
import { useSyncExternalStore } from 'react';

function useSharedState<T extends Record<string, unknown>, K extends keyof T>(
  store: SharedStore<T>,
  key: K
): T[K] {
  return useSyncExternalStore(
    (callback) => store.subscribe(key, callback),
    () => store.getState()[key]
  );
}

// React 子应用组件
function Header() {
  const user = useSharedState(sharedAuthStore, 'user');
  const theme = useSharedState(sharedThemeStore, 'mode');

  return (
    <header className={theme}>
      {user ? <span>欢迎，{user.name}</span> : <LoginButton />}
    </header>
  );
}
```

**方案对比：**

| 方案 | 优点 | 缺点 |
|------|------|------|
| CustomEvent + 全局 Store | 框架无关、简单 | 需要自己管理序列化 |
| qiankun globalState | 微前端框架内置 | 绑定 qiankun |
| Module Federation 共享模块 | 类型安全、可共享代码 | 构建配置复杂 |
| URL/Cookie/localStorage | 最简单 | 不实时、有大小限制 |
