## 1. 模块打包器

### Q1. ⭐ Webpack 的五大核心概念是什么？各自的作用是什么？

**考察点**：基础概念理解

**参考答案**：

| 概念                 | 作用                                                                                                                        |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| **Entry（入口）**    | 构建依赖图的起点，告诉 Webpack 从哪个文件开始解析                                                                           |
| **Output（输出）**   | 配置打包后文件的存放路径和文件名（支持 `[name]`、`[contenthash]` 占位符）                                                   |
| **Loader（加载器）** | 将非 JS 文件（CSS/TS/图片）转换为 Webpack 能处理的模块；执行顺序从右到左                                                    |
| **Plugin（插件）**   | 在构建生命周期的钩子点执行更宏观的任务，如压缩、HTML 注入、Bundle 分析                                                      |
| **Chunk（代码块）**  | Webpack 内部的代码分组单元；由 entry 产生 entry chunk，由 `import()` 产生 async chunk，由 `runtimeChunk` 产生 runtime chunk |

**追问**：Loader 和 Plugin 的区别？

> Loader 是文件转换器，作用于单个文件的内容转换（管道模式）；Plugin 是构建流程扩展点，通过订阅 Tapable 钩子影响整个构建流程，能做更宏观的事情（如生成 HTML、提取 CSS、分割代码）。

### Q2. ⭐⭐ 请描述 Webpack 的完整构建流程

**考察点**：编译原理理解

**参考答案**（分四个阶段）：

**1. 初始化阶段**

- 读取配置，实例化 `Compiler` 对象
- 遍历所有 Plugin，调用其 `apply(compiler)` 方法注册钩子

**2. 编译阶段（make）**

- 从 `entry` 出发，调用 `addEntry` 进入编译循环
- 对每个模块：调用对应 Loader 链转换源码 → 用 `acorn` 解析 AST → 递归处理 `require`/`import` 依赖
- 构建完整的模块依赖图

**3. 封装阶段（seal）**

- 依据依赖关系将模块分组为 Chunk
- 执行 `splitChunks`、`runtimeChunk` 等优化

**4. 输出阶段（emit）**

- 将 Chunk 渲染为最终字符串（注入 webpack runtime）
- 调用 `emit` 钩子，将文件写入 `output.path`

**关键**：整个流程基于 **Tapable 事件流**，Plugin 通过 `tap`/`tapAsync` 注册钩子，实现对每个阶段的介入。

### Q3. ⭐⭐ Webpack 和 Vite 的开发服务器有什么本质区别？

**考察点**：底层原理对比

**参考答案**：

**Webpack Dev Server（Bundle-based）**：

```
启动时：扫描所有模块 → 构建依赖图 → 打包成 bundle → 提供服务
缺点：项目越大，启动越慢（秒级到分钟级）
```

**Vite Dev Server（ESM-based）**：

```
启动时：
  1. esbuild 预构建 node_modules（毫秒级）
  2. 启动 HTTP 服务器，不打包源码
浏览器请求时：
  - 按需编译请求到的文件（单文件 esbuild 编译）
  - 返回原生 ESM 给浏览器
优点：启动时间与项目大小无关（始终毫秒级）
```

**HMR 差异**：

- Webpack HMR：需要重新打包受影响的模块链
- Vite HMR：通过 WebSocket 精确通知浏览器重新请求变更的单个模块，始终毫秒级

### Q4. ⭐⭐ 请解释 Vite 的依赖预构建（Pre-bundling）机制，为什么需要它？

**考察点**：Vite 原理深度

**参考答案**：

**原因一：CJS/UMD 转 ESM**

- 浏览器原生 ESM 只能处理 `import/export`
- `node_modules` 中大量包是 CommonJS 格式（`module.exports`）
- esbuild 将其转换为 ESM，使浏览器能直接加载

**原因二：减少网络请求**

- 某些包内部有数百个小模块（如 `lodash-es` 有 600+ 个文件）
- 每个 `import` 都会触发一次 HTTP 请求，造成请求瀑布
- esbuild 将整个包合并为单一 ESM 文件，只需一次请求

**缓存机制**：

- 预构建结果缓存到 `node_modules/.vite/deps/`
- 基于 `package.json`、`pnpm-lock.yaml` 和 Vite 版本生成 hash
- 哈希不变则直接使用缓存，不重复构建

### Q5. ⭐⭐⭐ Webpack 5 的 Module Federation 是什么？解决了什么问题？

**考察点**：微前端架构、高级特性

**参考答案**：

**是什么**：Module Federation 允许一个 JavaScript 应用在**运行时**从另一个独立部署的应用中动态加载代码模块。

**解决的问题**：

- 传统微前端（iframe/qiankun）共享依赖困难（每个子应用都加载一份 React）
- MF 通过 `shared` 配置，确保同版本依赖只加载一份（`singleton: true`）

**核心概念**：

- **Host**：消费远程模块的应用
- **Remote**：暴露模块的应用（通过 `exposes` 配置）
- **shared**：声明需要单例共享的依赖

**与传统方案对比**：

| 方案              | 构建时依赖 | 运行时共享 | 独立部署 |
| ----------------- | ---------- | ---------- | -------- |
| npm 包            | ✓          | ✗          | ✗        |
| CDN UMD           | ✗          | ✓          | ✓        |
| Module Federation | ✗          | ✓（自动）  | ✓        |

## 2. 性能优化

### Q6. ⭐ 什么是 Tree Shaking？它的实现原理是什么？

**考察点**：构建优化基础

**参考答案**：

**定义**：Tree Shaking 是一种通过静态分析消除 JavaScript bundle 中未被引用的"死代码"的优化技术，名字来自"摇动树使枯叶落下"的比喻。

**实现原理**（必须基于 ESM）：

```
ESM 静态分析（可 Tree Shaking）：
  import { add } from './math'  ← 编译期静态声明

  // 打包器在编译期即可知道：subtract 从未被引用
  export function add() { ... }
  export function subtract() { ... }  ← 标记为 dead code，删除
```

**CJS 为何不能 Tree Shaking**：

```js
// 动态引用，运行时才能确定
const utils = require("./math");
const fn = utils[Math.random() > 0.5 ? "add" : "subtract"];
```

**触发条件**：

1. 使用 ESM 语法（`import`/`export`）
2. `package.json` 中声明 `"sideEffects": false`（或列出有副作用文件）
3. Webpack `mode: 'production'` 或 `usedExports: true`

### Q7. ⭐⭐ 如何实现路由级代码分割？有哪些优化手段？

**考察点**：代码分割实战

**参考答案**：

**基础实现（React.lazy + Suspense）**：

```tsx
const Dashboard = lazy(() => import("./pages/Dashboard"));

function App() {
  return (
    <Suspense fallback={<Spinner />}>
      <Routes>
        <Route path="/dashboard" element={<Dashboard />} />
      </Routes>
    </Suspense>
  );
}
```

**优化手段**：

1. **预加载（Prefetch）**：鼠标悬停时触发预加载，用户点击时已缓存

   ```js
   const prefetch = () => import('./Dashboard');
   <Link onMouseEnter={prefetch} to="/dashboard">
   ```

2. **Magic Comments 控制加载策略**：

   ```js
   // webpackPrefetch：浏览器空闲时加载（link rel="prefetch"）
   import(/* webpackPrefetch: true */ "./Dashboard");
   // webpackPreload：与父 chunk 并行加载（link rel="preload"）
   import(/* webpackPreload: true */ "./Critical");
   ```

3. **命名 Chunk**：

   ```js
   import(/* webpackChunkName: "dashboard" */ "./Dashboard");
   ```

4. **Suspense 边界粒度**：将 Suspense 放在路由组件外层，避免每个页面都有 loading 状态

### Q8. ⭐⭐ 如何配置 Webpack 的长效缓存（Long-term Caching）策略？

**考察点**：缓存优化

**参考答案**：

**核心策略**：使用 `contenthash` 确保文件内容不变时 URL 不变

```js
output: {
  filename: 'js/[name].[contenthash:8].js',
  chunkFilename: 'js/[name].[contenthash:8].chunk.js',
},
optimization: {
  // 1. 将 runtime 单独抽出，避免其 hash 随业务代码变化
  runtimeChunk: 'single',
  // 2. 固定 moduleIds，避免新增/删除模块导致其他模块 hash 变化
  moduleIds: 'deterministic',
  chunkIds: 'deterministic',
  splitChunks: {
    cacheGroups: {
      // 3. 第三方库单独打包（变化少，长期缓存）
      vendors: {
        test: /node_modules/,
        name: 'vendors',
        chunks: 'all',
      },
    },
  },
},
```

**为什么要单独提取 runtimeChunk**？

Webpack runtime 包含模块解析逻辑，每次构建都可能变化。若不单独提取，业务代码文件会因 runtime 变化而导致 hash 改变，使缓存失效。

**HTTP 服务器配置**：

- HTML 文件：`Cache-Control: no-cache`（每次都验证）
- 带 hash 的 JS/CSS：`Cache-Control: max-age=31536000, immutable`（永久缓存）

### Q9. ⭐⭐⭐ webpack-bundle-analyzer 分析出 bundle 过大，你会如何排查和优化？

**考察点**：实战问题解决

**参考答案**：

**排查步骤**：

1. 运行 `ANALYZE=true npm run build`，打开可视化 treemap
2. 识别体积最大的模块

**常见问题及解法**：

| 问题                     | 原因                      | 解法                                                               |
| ------------------------ | ------------------------- | ------------------------------------------------------------------ |
| lodash 全量引入          | `import _ from 'lodash'`  | 改用 `import { debounce } from 'lodash-es'` 或 babel-plugin-lodash |
| moment.js 打包所有语言包 | 默认打包                  | 改用 `day.js`（2KB vs 300KB）或用 ContextReplacementPlugin         |
| antd/element-ui 全量引入 | `import Antd from 'antd'` | 按需引入 + babel-plugin-import                                     |
| 重复依赖                 | npm 依赖树多版本          | `npm dedupe`；`ModuleConcatenationPlugin` 作用域提升               |
| Source Map 泄露          | 生产环境打包了 source map | 使用 `hidden-source-map`，上传到 Sentry                            |

**SplitChunks 精细化控制**：

```js
cacheGroups: {
  // 将大型依赖单独分包
  echarts: {
    test: /[\\/]node_modules[\\/]echarts[\\/]/,
    name: 'echarts',
    chunks: 'async',  // 仅在用到时异步加载
    priority: 30,
  },
},
```

### Q11. ⭐⭐ 什么是幽灵依赖（Phantom Dependency）？pnpm 如何解决它？

**考察点**：依赖管理原理

**参考答案**：

**幽灵依赖**：代码中使用了未在 `package.json` 中声明的包。这些包因为是其他依赖的子依赖，被 npm/yarn 提升（hoist）到了顶层 `node_modules`，从而可以被引用。

**危害**：依赖链变化时，幽灵依赖可能消失，导致线上崩溃。

**npm/yarn 的扁平化结构（产生幽灵依赖）**：

```
node_modules/
├── express/          ← 你声明的依赖
├── body-parser/      ← express 的依赖，被提升到顶层 ← 幽灵依赖!
└── accepts/          ← 幽灵依赖!
```

**pnpm 的解决方案（严格依赖隔离）**：

- 只有在 `package.json` 的 `dependencies` 中声明的包，才会在顶层 `node_modules` 中有符号链接
- 未声明的包只存在于 `.pnpm/` 虚拟存储中，无法被直接引用
- 尝试引用幽灵依赖会立即报错，强制开发者显式声明

### Q12. ⭐⭐ 请解释 pnpm 的硬链接机制，它如何节省磁盘空间？

**考察点**：pnpm 深度原理

**参考答案**：

**全局内容寻址存储（CAS）**：

- 每个文件按其内容 hash 存储到 `~/.pnpm-store/v3/files/`
- 相同内容的文件只存一份（如 `react@18.2.0` 在 100 个项目中安装，磁盘只存一份）

**硬链接**：

- 项目 `node_modules` 中的每个文件都是指向全局存储的硬链接
- 硬链接共享同一个 inode，无需复制文件内容
- 删除项目不影响全局存储（其他项目的硬链接仍有效）

**符号链接**：

- `node_modules/react` 是指向 `node_modules/.pnpm/react@18.2.0/node_modules/react` 的符号链接
- Node.js 模块解析会跟随符号链接

**节省空间的效果**：

- 10 个项目共用 React 18：传统 npm 存 10 份（~400MB），pnpm 存 1 份（~40MB）

### Q13. ⭐⭐⭐ Monorepo 的主流方案有哪些？Turborepo 的缓存机制是怎样的？

**考察点**：大型项目架构

**参考答案**：

**主流方案对比**：

- **Turborepo**：轻量，专注任务编排和缓存，学习曲线低
- **Nx**：功能完整（代码生成/依赖图/增量测试），适合大型企业
- **Lerna v7**：历史最久，现与 Nx 整合，基础功能

**Turborepo 缓存机制**：

```
任务执行前：
  1. 计算"缓存 key" = 输入文件 hash + 任务配置 + 环境变量

  2. 查询本地缓存（.turbo/cache/）
     ├── 命中 → 直接恢复输出文件 + 终端输出，跳过执行
     └── 未命中 → 执行任务，保存结果到缓存

  3. 查询远程缓存（Vercel / 自建）
     → 团队成员共享缓存，CI 也可复用本地开发缓存
```

**关键配置（turbo.json）**：

```json
{
  "pipeline": {
    "build": {
      "dependsOn": ["^build"], // 依赖其他包先 build
      "inputs": ["src/**/*.ts"], // 哪些文件变化才重新构建
      "outputs": ["dist/**"], // 缓存哪些输出
      "cache": true
    }
  }
}
```

## 4. 代码质量

### Q14. ⭐ ESLint 和 Prettier 的职责分工是什么？如何避免冲突？

**考察点**：工具链基础

**参考答案**：

| 工具         | 职责         | 关注点                             |
| ------------ | ------------ | ---------------------------------- |
| **ESLint**   | 代码质量检查 | 潜在 bug、最佳实践、代码逻辑错误   |
| **Prettier** | 代码格式化   | 缩进、引号、分号、行宽等纯格式问题 |

**避免冲突**：

- 安装 `eslint-config-prettier`，它会关闭所有与 Prettier 冲突的 ESLint 格式规则
- 安装 `eslint-plugin-prettier`，将 Prettier 规则作为 ESLint 规则运行（可选，有性能开销）
- 更推荐：ESLint 只负责质量，Prettier 单独运行格式化，不混用

```js
// eslint.config.js
import prettierConfig from "eslint-config-prettier";
export default [
  // ...其他规则
  prettierConfig, // 放在最后，覆盖冲突的格式规则
];
```

### Q15. ⭐⭐ Husky + lint-staged + commitlint 的作用链是什么？

**考察点**：Git Hooks 工具链

**参考答案**：

**作用链**：

```
git commit
  → Husky 触发 pre-commit hook
    → lint-staged 对暂存文件执行 ESLint + Prettier（仅检查修改的文件，速度快）
      → 失败 → 阻止 commit，提示修复
      → 成功 → 继续
  → Husky 触发 commit-msg hook
    → commitlint 验证 commit message 格式
      → 不符合规范 → 阻止 commit
      → 符合规范 → commit 成功
```

**为什么用 lint-staged 而不是直接跑全量 lint？**

- 全量检查慢（大项目数分钟）
- lint-staged 只对 `git add` 暂存的文件执行检查，速度快（秒级）

**commitlint 规范（Conventional Commits）**：

```
feat: 新增用户登录功能
fix: 修复 Safari 下按钮样式问题
docs: 更新 API 接口文档
refactor: 重构订单计算逻辑
perf: 优化首页图片加载速度
```

### Q16. ⭐⭐ TypeScript strict 模式包含哪些检查？最重要的是哪几个？

**考察点**：TypeScript 工程实践

**参考答案**：

`strict: true` 等效于开启以下所有选项：

| 选项                           | 作用                                   | 重要程度     |
| ------------------------------ | -------------------------------------- | ------------ |
| `strictNullChecks`             | `null`/`undefined` 不能赋给其他类型    | ⭐⭐⭐最重要 |
| `noImplicitAny`                | 禁止隐式推断为 `any`                   | ⭐⭐⭐最重要 |
| `strictFunctionTypes`          | 函数参数逆变检查                       | ⭐⭐         |
| `strictPropertyInitialization` | 类属性必须在构造函数中初始化           | ⭐⭐         |
| `useUnknownInCatchVariables`   | `catch` 变量为 `unknown`（而非 `any`） | ⭐⭐         |
| `alwaysStrict`                 | 每个文件注入 `"use strict"`            | ⭐           |

**额外推荐**（strict 之外）：

- `noUncheckedIndexedAccess`：数组/对象索引返回 `T | undefined`，避免越界不报错
- `noImplicitReturns`：所有代码路径必须有返回值

### Q18. ⭐⭐ Tailwind CSS 的 Tree Shaking 是如何工作的？

**考察点**：CSS 工程化

**参考答案**：

Tailwind 通过 **PurgeCSS**（内置于 Tailwind v3+）实现"CSS Tree Shaking"：

**原理**：

1. 构建时扫描 `content` 配置的所有文件（HTML/JSX/TS等）
2. 使用正则匹配提取所有出现过的 CSS 类名字符串
3. 只生成实际用到的 class 对应的 CSS
4. 未使用的工具类全部移除

**生成前 vs 生成后**：

```
开发时：Tailwind 完整 CSS（~3MB）
生产构建：只包含项目用到的类（通常 < 30KB）
```

**重要陷阱**：不能用字符串拼接动态类名：

```jsx
// ✗ 错误：构建时扫描不到 'text-red-500' 和 'text-green-500'
const color = isError ? 'red' : 'green';
<div className={`text-${color}-500`}>

// ✓ 正确：完整类名必须出现在源码中
const cls = isError ? 'text-red-500' : 'text-green-500';
<div className={cls}>
```

### Q19. ⭐⭐⭐ 微前端的主流方案有哪些？如何选型？

**考察点**：架构设计

**参考答案**：

**主流方案**：

| 方案                  | 隔离强度               | 通信                 | 适用场景               |
| --------------------- | ---------------------- | -------------------- | ---------------------- |
| **Module Federation** | 弱（JS 沙箱可选）      | CustomEvent/全局状态 | 同技术栈，需共享依赖   |
| **qiankun**           | 中（JS 沙箱+CSS 隔离） | initGlobalState      | 已有系统改造，接入简单 |
| **iframe**            | 强（天然隔离）         | postMessage          | 安全要求高，异构系统   |
| **Web Components**    | 中（Shadow DOM）       | CustomEvent          | 框架无关组件           |

**选型建议**：

- 团队技术栈一致（React）→ **Module Federation**（零额外开销，共享 React）
- 遗留系统接入（Vue 2/3 混用）→ **qiankun**（接入成本低）
- 高安全性要求（银行/政务）→ **iframe**
- 新项目跨框架组件共享 → **Web Components**

**注意**：微前端引入了架构复杂性，应先评估是否真的需要它（独立部署需求是否强烈）。

## 6. 场景设计题

### Q20. ⭐⭐⭐ 场景题：一个中大型 React 应用首屏加载时间为 8 秒，如何优化到 2 秒以内？

**考察点**：综合性能优化

**参考答案（系统性分析）**：

**第一步：诊断定位**

```
1. Lighthouse 审计（分析 FCP/LCP/TTI）
2. webpack-bundle-analyzer 分析 bundle 组成
3. Chrome DevTools Network 面板分析加载瀑布流
4. Coverage 面板分析未使用代码比例
```

**第二步：Bundle 瘦身（通常影响最大）**

```
优化前后对比示例：
  优化前：main.js 2.3MB（未压缩）

  1. 路由级代码分割（React.lazy）→ 首屏只加载当前页面代码
     效果：main.js 200KB

  2. 第三方库优化
     - moment → dayjs (-300KB)
     - lodash → lodash-es 按需引入 (-200KB)
     - antd 按需引入 (-500KB)

  3. 动态引入大型依赖（echarts/monaco-editor）
     → 仅在需要时异步加载

  优化后：main.js ~150KB
```

**第三步：加载策略优化**

```
1. 开启 Gzip/Brotli 压缩（服务端/CDN）
   → 150KB → ~50KB
2. HTTP/2 多路复用（消除队头阻塞）
3. 关键资源预加载：<link rel="preload" as="script">
4. 第三方库走 CDN（利用浏览器缓存 + 并行加载）
5. 图片懒加载 + WebP 格式
```

**第四步：缓存策略**

```
1. contenthash 长效缓存（JS/CSS）
2. Service Worker 缓存（PWA）
3. CDN 边缘缓存
```

**预期效果**：通过以上综合优化，FCP 从 8s → < 2s 是可实现的目标。

### Q21. ⭐⭐⭐ 场景题：如何为 10+ 个前端项目搭建统一的工程化体系？

**考察点**：工程化架构设计

**参考答案**：

**架构方案（Monorepo + 共享配置）**：

```
my-org/
├── packages/
│   ├── eslint-config/     ← 共享 ESLint 配置
│   ├── tsconfig/          ← 共享 TypeScript 配置
│   ├── prettier-config/   ← 共享 Prettier 配置
│   ├── ui-components/     ← 共享组件库
│   └── utils/             ← 共享工具函数
└── apps/
    ├── web-portal/        ← 各业务项目
    ├── admin-dashboard/
    └── mobile-h5/
```

**统一配置包**：

```json
// packages/eslint-config/package.json
{ "name": "@myorg/eslint-config" }

// apps/web-portal/.eslintrc.js
module.exports = { extends: ['@myorg/eslint-config'] }
```

**CI/CD 统一流水线**：

```yaml
# 使用 Turborepo 增量构建，只构建受 PR 影响的包
turbo run build test lint --filter=...[origin/main]
```

**关键收益**：

- 代码规范统一（ESLint/Prettier/TS 配置一致）
- 共享组件/工具零复制（workspace 本地引用）
- 构建缓存共享（Turborepo 远程缓存，CI 提速 80%+）
- 版本管理统一（Changesets 管理包版本发布）
