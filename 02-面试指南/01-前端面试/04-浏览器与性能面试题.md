## ⭐ 基础题

### Q1: 浏览器输入 URL 到页面展示的完整过程

**难度**: ⭐ | **高频指数**: ★★★★★

> 💡 **面试官意图**: 考察你对浏览器工作全链路的理解深度，从网络层到渲染层是否都清楚。这是一道涵盖面极广的经典题，回答质量直接反映候选人的知识体系。

**思路分析**：按照时间顺序，可以分为 **网络阶段** 和 **渲染阶段** 两大部分，由粗到细逐层展开。

**参考答案**：

**一、网络阶段**

1. **URL 解析**：浏览器判断输入是 URL 还是搜索关键词。如果是 URL，补全协议（如添加 `https://`）
2. **DNS 解析**：将域名解析为 IP 地址，查找顺序：浏览器缓存 → 操作系统缓存 → hosts 文件 → 本地 DNS 服务器 → 递归查询根域名服务器
3. **TCP 三次握手**：客户端发送 SYN → 服务器返回 SYN+ACK → 客户端发送 ACK，建立可靠连接
4. **TLS 握手**（HTTPS）：协商加密算法、交换密钥、验证证书
5. **HTTP 请求**：发送 GET 请求，包含请求头（Cookie、User-Agent 等）
6. **服务器处理并返回响应**：返回状态码、响应头（Cache-Control 等）、响应体（HTML）

**二、渲染阶段**

7. **HTML 解析 → DOM 树**：逐行解析 HTML 标签，构建 DOM（Document Object Model）
8. **CSS 解析 → CSSOM 树**：解析所有 CSS（外联、内联、行内），构建 CSSOM
9. **构建 Render Tree**：合并 DOM 和 CSSOM，排除不可见元素（`display: none`、`<head>`）
10. **Layout（布局）**：计算每个节点的精确位置和大小
11. **Paint（绘制）**：生成绘制指令列表（颜色、边框、阴影等）
12. **Composite（合成）**：将不同图层通过 GPU 合成最终页面，显示到屏幕

```
URL输入 → DNS解析 → TCP握手 → TLS握手 → HTTP请求 → 响应返回
                                                        ↓
                       HTML解析→DOM → CSS解析→CSSOM → RenderTree
                                                        ↓
                                    Layout → Paint → Composite → 显示
```

### Q2: HTML 解析过程中遇到 script 标签会怎样？defer vs async 区别

**难度**: ⭐ | **高频指数**: ★★★★★

> 💡 **面试官意图**: 考察对 HTML 解析阻塞机制的理解，以及实际开发中如何选择脚本加载策略。

**思路分析**：关键在于区分"下载"和"执行"两个阶段，以及它们在不同模式下是否阻塞 HTML 解析。

**参考答案**：

**默认行为（无 defer/async）**：
HTML 解析遇到 `<script>` 标签时会**暂停解析**，等待脚本下载完成并执行后才继续解析 HTML。这就是 JS 阻塞解析的原因。

**三种模式对比**：

```
普通 <script>:
HTML:  ──解析──┤  暂停  ├──解析──
JS:            └下载+执行┘

<script defer>:
HTML:  ──────────解析──────────→ DOMContentLoaded
JS:    └──下载──┘            └执行┘
                              ↑ DOM 解析完后、DOMContentLoaded 前执行
                              ↑ 多个 defer 按顺序执行

<script async>:
HTML:  ────解析────┤暂停├──解析──
JS:    └──下载──┘ └执行┘
                  ↑ 下载完就立即中断 HTML 执行
                  ↑ 多个 async 不保证顺序
```

| 属性    | 下载     | 执行时机       | 是否阻塞 HTML | 执行顺序   |
| ------- | -------- | -------------- | ------------- | ---------- |
| 无      | 阻塞     | 下载后立即     | ✅ 阻塞       | 按文档顺序 |
| `defer` | 并行下载 | DOM 解析完后   | ❌ 不阻塞     | 按文档顺序 |
| `async` | 并行下载 | 下载完立刻执行 | ⚠️ 执行时阻塞 | 不保证顺序 |

**使用建议**：

- **defer**：适合依赖 DOM 的业务脚本（如 `app.js`）
- **async**：适合独立的第三方脚本（如统计、广告）
- **默认**：已经放在 `</body>` 前的脚本，差别不大

### Q3: 重排、重绘、合成的区别？如何减少重排

**难度**: ⭐ | **高频指数**: ★★★★★

> 💡 **面试官意图**: 考察渲染流水线理解深度，以及实际编码中的性能意识。

**参考答案**：

**三者区别**：

| 类型                 | 触发条件                                                         | 涉及阶段                   | 性能代价   |
| -------------------- | ---------------------------------------------------------------- | -------------------------- | ---------- |
| **重排 (Reflow)**    | 几何属性变化 (width, height, margin, padding, display, position) | Layout → Paint → Composite | ★★★★★ 最高 |
| **重绘 (Repaint)**   | 外观属性变化 (color, background, box-shadow, visibility)         | Paint → Composite          | ★★★☆☆ 中等 |
| **合成 (Composite)** | transform, opacity 变化                                          | 仅 Composite               | ★☆☆☆☆ 最低 |

**减少重排的方法**：

1. **批量 DOM 操作**：使用 `DocumentFragment` 或一次性修改 `innerHTML`
2. **读写分离**：先读取所有布局属性，再集中修改（避免强制同步布局）
3. **离线操作**：操作前 `display: none`，操作完再显示（隐藏元素的修改不触发重排）
4. **避免逐条修改样式**：使用 `className` 或 `cssText` 一次性修改
5. **动画用 transform**：`transform: translateX()` 代替 `left`

```javascript
// ❌ 差：每次循环都强制重排
for (let i = 0; i < 100; i++) {
  el.style.left = el.offsetLeft + 1 + "px"; // 读→写→读→写...
}

// ✅ 好：读写分离
let left = el.offsetLeft; // 只读一次
for (let i = 0; i < 100; i++) {
  left += 1;
}
el.style.left = left + "px"; // 只写一次
```

### Q4: 什么是 HTTP 强缓存和协商缓存？

**难度**: ⭐ | **高频指数**: ★★★★★

> 💡 **面试官意图**: 缓存是性能优化的第一道防线，考察对缓存策略的全面理解。

**参考答案**：

**强缓存**：浏览器直接使用本地缓存，不发请求给服务器。

| Header          | 说明                               | 示例                            |
| --------------- | ---------------------------------- | ------------------------------- |
| `Cache-Control` | 指定缓存策略（HTTP/1.1，优先级高） | `max-age=31536000`              |
| `Expires`       | 过期时间（HTTP/1.0，绝对时间）     | `Thu, 01 Jan 2027 00:00:00 GMT` |

`Cache-Control` 常用值：

- `max-age=300`：缓存 300 秒
- `no-cache`：不直接使用缓存，每次都通过协商验证
- `no-store`：完全不缓存
- `immutable`：缓存期内即使用户刷新也不重新验证
- `private`：仅客户端缓存（不允许 CDN 缓存）
- `public`：允许中间代理缓存

**协商缓存**：强缓存失效后，浏览器发请求给服务器验证资源是否改变。

| 请求头              | 响应头          | 对比方式       |
| ------------------- | --------------- | -------------- |
| `If-None-Match`     | `ETag`          | 资源内容哈希值 |
| `If-Modified-Since` | `Last-Modified` | 最后修改时间   |

```
流程：
① 浏览器携带 If-None-Match: "abc123" 发送请求
② 服务器对比 ETag
  - 相同 → 返回 304 Not Modified（用缓存，不传输响应体）
  - 不同 → 返回 200 OK + 新资源 + 新 ETag
```

**最佳实践**：

- HTML：`Cache-Control: no-cache`（每次都验证，确保获取最新版本）
- CSS/JS/图片（带 hash 文件名如 `app.a1b2c3.js`）：`Cache-Control: max-age=31536000, immutable`

### Q5: 同源策略是什么？跨域有哪些解决方案

**难度**: ⭐ | **高频指数**: ★★★★☆

> 💡 **面试官意图**: 考察对浏览器安全模型的理解，以及实际处理跨域的能力。

**参考答案**：

**同源策略 (Same-Origin Policy)**：浏览器安全机制，限制从一个源加载的文档或脚本与来自另一个源的资源进行交互。

**同源定义**：协议 + 域名 + 端口 三者完全相同。

```
https://example.com:443/page
  ↑         ↑         ↑
 协议      域名       端口

https://example.com/api    ✅ 同源
http://example.com/api     ❌ 协议不同
https://api.example.com    ❌ 域名不同
https://example.com:8080   ❌ 端口不同
```

**跨域方案**：

| 方案            | 原理                                            | 适用场景                    |
| --------------- | ----------------------------------------------- | --------------------------- |
| **CORS**        | 服务端设置 `Access-Control-Allow-Origin` 响应头 | 最主流，API 接口            |
| **代理服务器**  | 同源的后端服务器代替浏览器发请求                | 开发环境 Vite/Webpack proxy |
| **JSONP**       | 利用 `<script>` 标签不受同源限制                | 仅支持 GET，已过时          |
| **postMessage** | `window.postMessage()` 跨窗口通信               | iframe 通信                 |
| **WebSocket**   | 建立时通过 HTTP 升级协议，建立后不受同源限制    | 实时通信                    |

**CORS 详解**：

```
简单请求（GET/POST/HEAD，无自定义头）：
浏览器 ──────────────────────────→ 服务器
       GET /api  Origin: https://a.com
       ←──────────────────────────
       Access-Control-Allow-Origin: https://a.com

预检请求（PUT/DELETE/自定义头/非简单Content-Type）：
浏览器 ──── OPTIONS 预检 ────────→ 服务器
       Origin: https://a.com
       Access-Control-Request-Method: PUT
       ←──────────────────────────
       Access-Control-Allow-Origin: https://a.com
       Access-Control-Allow-Methods: PUT
       Access-Control-Max-Age: 86400  (缓存预检结果)

       ──── 正式 PUT 请求 ────────→
```

### Q6: CSS 和 JS 是如何阻塞渲染的

**难度**: ⭐ | **高频指数**: ★★★★☆

> 💡 **面试官意图**: 考察对关键渲染路径的理解，这直接影响首屏性能优化能力。

**参考答案**：

**CSS 阻塞渲染**：

- CSS **不阻塞 DOM 构建**（HTML 解析不会停下来等 CSS）
- CSS **阻塞 Render Tree 构建和页面渲染**（需要 CSSOM 才能合并生成 Render Tree）
- CSS **阻塞其后 JS 的执行**（JS 可能会读取样式信息，所以必须等 CSSOM 构建完）

**JS 阻塞解析**：

- 普通 `<script>` **阻塞 DOM 解析**（下载+执行完才继续解析 HTML）
- `defer` 不阻塞解析，DOM 解析完后按顺序执行
- `async` 下载不阻塞，但执行时阻塞解析

**优化关键渲染路径**：

```html
<!-- 1. 内联关键 CSS（首屏所需的最小化 CSS） -->
<style>
  /* 首屏关键样式 */
  .hero { ... }
  .nav { ... }
</style>

<!-- 2. 非关键 CSS 异步加载 -->
<link
  rel="stylesheet"
  href="non-critical.css"
  media="print"
  onload="this.media='all'"
/>

<!-- 3. JS 使用 defer -->
<script src="app.js" defer></script>

<!-- 4. 预加载关键资源 -->
<link rel="preload" href="critical.css" as="style" />
<link rel="preload" href="hero.webp" as="image" />
```

### Q7: Cookie / localStorage / sessionStorage / IndexedDB 区别

**难度**: ⭐ | **高频指数**: ★★★★☆

> 💡 **面试官意图**: 考察客户端存储机制的全面理解和选型能力。

**参考答案**：

| 特性            | Cookie                          | localStorage      | sessionStorage    | IndexedDB                  |
| --------------- | ------------------------------- | ----------------- | ----------------- | -------------------------- |
| **容量**        | 4KB                             | 5-10MB            | 5-10MB            | 无限制（受磁盘空间限制）   |
| **生命周期**    | 可设置过期时间                  | 永久（手动清除）  | 当前 Tab 关闭清除 | 永久（手动清除）           |
| **服务器通信**  | 每次请求自动携带                | ❌ 不发送         | ❌ 不发送         | ❌ 不发送                  |
| **跨 Tab 共享** | ✅ 同源共享                     | ✅ 同源共享       | ❌ 仅当前 Tab     | ✅ 同源共享                |
| **API**         | `document.cookie`（字符串操作） | `getItem/setItem` | `getItem/setItem` | 异步 API（事务型）         |
| **数据类型**    | 字符串                          | 字符串            | 字符串            | 结构化数据（对象、文件等） |

**使用场景**：

- **Cookie**：身份认证 token（设置 `HttpOnly` + `Secure` + `SameSite`）
- **localStorage**：用户偏好设置、主题、语言
- **sessionStorage**：表单草稿、一次性数据
- **IndexedDB**：大量结构化数据、离线缓存（如 PWA）

**Cookie 安全属性**：

```
Set-Cookie: token=abc123;
  HttpOnly;      // JS 无法通过 document.cookie 读取（防 XSS 窃取）
  Secure;        // 仅 HTTPS 传输
  SameSite=Lax;  // 防 CSRF（Lax=导航请求携带，Strict=完全不跨站携带）
  Path=/;
  Max-Age=86400;
```

### Q8: 什么是 BFC？触发条件和应用场景

**难度**: ⭐ | **高频指数**: ★★★☆☆

> 💡 **面试官意图**: 考察对 CSS 布局机制的底层理解。

**参考答案**：

**BFC (Block Formatting Context)** 是一个独立的渲染区域，内部的布局不影响外部元素。

**类比**：BFC 就像一个有围墙的院子——院子里怎么折腾（子元素怎么布局），院墙外的人完全不受影响。

**触发条件**（创建新的 BFC）：

| 条件                          | 说明                               |
| ----------------------------- | ---------------------------------- |
| `overflow` 非 `visible`       | `overflow: hidden / auto / scroll` |
| `display: flow-root`          | 专门用于创建 BFC（最佳语义）       |
| `float` 非 `none`             | `float: left / right`              |
| `position: absolute / fixed`  | 脱离文档流                         |
| `display: inline-block`       | -                                  |
| `display: flex / grid` 的子项 | 弹性/网格项                        |

**应用场景**：

1. **清除浮动**（父元素包裹浮动子元素）：

```css
.parent {
  display: flow-root; /* 创建 BFC → 包裹浮动子元素 */
}
.child {
  float: left;
}
```

2. **防止 margin 塌陷**（上下相邻元素的 margin 合并）：

```css
/* 包裹其中一个元素在 BFC 中，阻止 margin 合并 */
.wrapper {
  display: flow-root;
}
```

3. **自适应两栏布局**（防止文字环绕浮动元素）：

```css
.sidebar {
  float: left;
  width: 200px;
}
.main {
  display: flow-root;
} /* 创建 BFC → 不与浮动元素重叠 */
```

### Q9: DOMContentLoaded 和 load 事件的区别

**难度**: ⭐ | **高频指数**: ★★★☆☆

> 💡 **面试官意图**: 考察对页面加载生命周期的理解。

**参考答案**：

| 事件                 | 触发时机                            | 包含哪些                               |
| -------------------- | ----------------------------------- | -------------------------------------- |
| **DOMContentLoaded** | HTML 解析完成、DOM 树构建完毕后触发 | ✅ DOM 就绪 / ❌ 不等图片、CSS、iframe |
| **load**             | 页面所有资源都加载完成后触发        | ✅ DOM + 图片 + CSS + iframe 全部就绪  |

```
HTML 下载开始
    ↓
    HTML 解析中...（遇到 CSS/JS 可能暂停）
    ↓
DOM 解析完成
    ↓
━━━ DOMContentLoaded 触发 ━━━     ← jQuery 的 $(document).ready()
    ↓
    图片、CSS、iframe 等继续加载...
    ↓
━━━ load 触发 ━━━                  ← window.onload
    ↓
    用户关闭/离开页面
    ↓
━━━ beforeunload / unload 触发 ━━━
```

```javascript
// DOMContentLoaded：DOM 就绪，可以操作 DOM
document.addEventListener("DOMContentLoaded", () => {
  console.log("DOM 就绪，可以操作元素");
  document.getElementById("app").innerHTML = "loaded";
});

// load：所有资源就绪
window.addEventListener("load", () => {
  console.log("页面完全加载，图片都显示了");
});

// 注意：如果 <script> 放在 </body> 前（推荐做法），
// DOMContentLoaded 的差异就不大了
```

### Q10: 什么是 CSRF 和 XSS？如何防御

**难度**: ⭐ | **高频指数**: ★★★★☆

> 💡 **面试官意图**: 前端安全基础，尤其是在涉及用户数据或支付场景时必须掌握。

**参考答案**：

#### XSS（跨站脚本攻击）

**原理**：攻击者将恶意脚本注入到网页中，在用户浏览器中执行。

| 类型       | 描述                                   | 示例                           |
| ---------- | -------------------------------------- | ------------------------------ |
| **存储型** | 恶意脚本存入数据库，其他用户访问时触发 | 评论区注入 `<script>`          |
| **反射型** | 恶意脚本通过 URL 参数注入              | `?q=<script>alert(1)</script>` |
| **DOM型**  | 前端 JS 代码直接操作不安全的输入       | `innerHTML = userInput`        |

**防御方法**：

- **输出转义**：将 `< > " ' &` 等字符转义为 HTML 实体
- **CSP (Content Security Policy)**：限制脚本只能从指定来源加载
- **HttpOnly Cookie**：JS 无法通过 `document.cookie` 读取 Cookie
- **避免 `innerHTML`**：使用 `textContent` 或框架的自动转义
- **输入验证**：后端对用户输入进行白名单校验

```http
# CSP 响应头示例
Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.example.com; style-src 'self' 'unsafe-inline'
```

#### CSRF（跨站请求伪造）

**原理**：攻击者诱导已登录用户访问恶意页面，利用用户的 Cookie 自动发送伪造请求。

```
用户登录了 bank.com（Cookie 存在浏览器中）
    ↓
用户访问恶意网站 evil.com
    ↓
evil.com 中有隐藏表单：<form action="bank.com/transfer" method="POST">
    ↓
浏览器自动携带 bank.com 的 Cookie 发送请求
    ↓
bank.com 认为是用户本人操作 → 转账成功 💀
```

**防御方法**：

- **SameSite Cookie**：`SameSite=Lax` 或 `Strict` — 跨站请求不携带 Cookie
- **CSRF Token**：服务端生成随机 token，表单提交时验证
- **验证 Origin/Referer**：检查请求来源是否来自自己的域名
- **双重 Cookie 验证**：将 token 同时放在 Cookie 和请求参数中对比

### Q11: 深入解释渲染流水线各阶段

**难度**: ⭐⭐ | **高频指数**: ★★★★★

> 💡 **面试官意图**: 基础题要求能说出流程，进阶要求理解每个阶段的细节和优化切入点。

**思路分析**：在 Q1/Q3 的基础上深入每个阶段的内部机制，重点说清楚各阶段的输入输出和优化策略。

**参考答案**：

**1. HTML 解析 → DOM**

- 浏览器接收字节流 → 解码为字符 → 分词(Tokenizer) → 构建节点 → DOM 树
- **增量解析**：不必等整个文件下载完就开始解析
- **预加载扫描器**：在主解析器被 JS 阻塞时，预扫描后续 HTML 提前发起资源请求

**2. CSS 解析 → CSSOM**

- CSSOM 构建是**全量的**——必须解析完所有 CSS 才能确定最终样式（因为层叠、继承机制）
- CSS **阻塞渲染不阻塞解析**：DOM 解析继续，但 Render Tree 要等 CSSOM

**3. Render Tree**

- 遍历 DOM 树的每个可见节点，找到对应的 CSSOM 规则
- `display: none` → 不进入 Render Tree
- `visibility: hidden` → 进入 Render Tree（占位但不可见）
- `::before` / `::after` 伪元素 → 进入 Render Tree

**4. Layout（重排）**

- 输入：Render Tree + 视口尺寸
- 输出：每个节点的盒模型（位置 x/y + 大小 width/height）
- 全局布局 vs 增量布局（仅脏节点及其后代重新计算）

**5. Paint（绘制）**

- 遍历 Render Tree，生成绘制指令列表（Display List）
- 决定绘制顺序（z-index、层叠上下文）
- 分层：具有特定属性的元素（`position: fixed`, `will-change`, `transform`）提升为独立的 **Compositing Layer**

**6. Composite（合成）**

- Compositor Thread（独立于 Main Thread）将各图层最终合成
- 送入 GPU 栅格化为像素 → 显示到屏幕
- `transform` / `opacity` 动画可以完全在 Compositor Thread 完成，**不阻塞主线程**

```
Main Thread:
[DOM] → [Style] → [Layout] → [Paint] → 生成 Layer List
                                              │
Compositor Thread:                            ▼
                                     [合成 Layers] → [Raster → GPU]
```

- Composite Layer 过多会有什么问题？（GPU 内存消耗增大，Layer 合成本身有开销）
- 什么是层爆炸 (Layer Explosion)？如何避免？

### Q12: V8 引擎的执行管道和 JIT 编译原理

**难度**: ⭐⭐ | **高频指数**: ★★★★☆

> 💡 **面试官意图**: 考察对 JavaScript 运行时的深层理解，能否解释 V8 如何让 JS 跑得快。

**参考答案**：

**V8 执行管道**：

```
Source Code
    │
    ▼
  Parser (一次扫描 + 懒解析)
    │  → 完全解析被调用的函数 → AST
    │  → 懒解析未调用的函数（仅预解析签名）
    ▼
  Ignition (解释器)
    │  → AST → 字节码 (Bytecode)
    │  → 解释执行字节码
    │  → 同时收集类型反馈 (Type Feedback / Feedback Vector)
    ▼
  Sparkplug (基线编译器)
    │  → 将字节码快速编译为非优化机器码
    │  → 编译速度极快（毫秒级）
    ▼
  Maglev (中间层 JIT)
    │  → 基于类型反馈的中等优化
    │  → 比 Sparkplug 慢一些但生成更好的代码
    ▼
  TurboFan (优化编译器)
    │  → 热点函数深度优化
    │  → 内联、逃逸分析、冗余消除、类型特化
    │  → 生成接近 C++ 质量的机器码
    ▼
  Deoptimization (去优化)
    → 类型假设被打破 → 回退到 Ignition
```

**关键概念**：

1. **懒解析 (Lazy Parsing)**：第一次只解析顶层代码和被立即调用的函数，未调用的函数只做预解析（检查语法错误、记录作用域）。这大幅加快了初始启动速度。

2. **类型反馈**：Ignition 执行时记录每个操作遇到的数据类型。例如 `a + b` 执行了 1000 次都是整数加法，TurboFan 就假设它"总是整数加法"并生成特化代码。

3. **去优化**：如果 `a + b` 突然传入了字符串，类型假设被打破，优化后的机器码失效，必须回退到 Ignition 重新解释执行。

```javascript
// 演示去优化
function add(a, b) {
  return a + b;
}

// 正常优化路径
for (let i = 0; i < 100000; i++) {
  add(i, i + 1); // Ignition → Sparkplug → TurboFan（整数加法）
}

// 💥 去优化触发
add("hello", " world"); // 类型改变 → Deopt → 回退 Ignition
```

**追问方向**：

- 什么是 Hidden Class？它如何影响属性访问速度？
- Inline Cache（IC）的单态/多态/超多态是什么意思？

### Q13: 浏览器的事件循环与渲染时机的关系

**难度**: ⭐⭐ | **高频指数**: ★★★★★

> 💡 **面试官意图**: 事件循环是前端的核心机制，进阶考点在于微任务、rAF 与渲染的精确时序。

**参考答案**：

**事件循环完整流程**：

```
┌────────────────────────────────────────────────────────┐
│                                                        │
│  ① 执行一个宏任务 (Task/Macrotask)                      │
│     - <script> 执行                                    │
│     - setTimeout/setInterval 回调                      │
│     - I/O 回调                                         │
│     - UI 事件回调                                       │
│                                                        │
│  ② 清空微任务队列 (Microtask Queue)                     │
│     - Promise.then/catch/finally                       │
│     - MutationObserver                                 │
│     - queueMicrotask()                                 │
│     ⚠️ 如果微任务中又产生微任务，继续执行直到清空            │
│                                                        │
│  ③ 是否需要渲染？（16.6ms 一帧，不是每次循环都渲染）       │
│     ├── 否 → 回到 ①                                    │
│     └── 是 ↓                                           │
│                                                        │
│  ④ requestAnimationFrame 回调                          │
│                                                        │
│  ⑤ 渲染（Style → Layout → Paint → Composite）          │
│                                                        │
│  ⑥ 空闲时间？→ requestIdleCallback 回调                 │
│                                                        │
│  └────────── 回到 ① ───────────────────────────────────┘
```

**经典面试题**：

```javascript
console.log("1"); // 同步

setTimeout(() => console.log("2"), 0); // 宏任务

Promise.resolve().then(() => console.log("3")); // 微任务

requestAnimationFrame(() => console.log("4")); // rAF

Promise.resolve().then(() => console.log("5")); // 微任务

console.log("6"); // 同步

// 输出顺序：1 → 6 → 3 → 5 → 4 → 2
// 解释：同步代码先执行(1,6) → 微任务清空(3,5) → rAF(4) → 宏任务(2)
```

**关键要点**：

- **微任务在渲染前执行**：`Promise.then()` 中的 DOM 修改在同一帧渲染
- **rAF 在渲染前执行**：最佳的动画操作时机
- **微任务可能无限循环**：如果微任务中不断产生新的微任务，会阻塞渲染

```javascript
// ⚠️ 危险：微任务无限循环会冻结页面
function recursiveMicrotask() {
  Promise.resolve().then(recursiveMicrotask);
}
recursiveMicrotask(); // 页面完全无响应！
```

### Q14: 如何排查和修复内存泄漏（DevTools Memory）

**难度**: ⭐⭐ | **高频指数**: ★★★★☆

> 💡 **面试官意图**: 考察实际调试能力，能否系统性地排查生产环境的内存问题。

**参考答案**：

**排查步骤**：

**Step 1: 确认内存泄漏**

- 打开 Chrome DevTools → Performance Monitor 面板
- 观察 JS Heap Size：如果持续增长不回落 → 可能有泄漏

**Step 2: Heap Snapshot 对比分析**

```
① 执行一次 GC（DevTools → Memory → Collect garbage 按钮）
② 录制 Snapshot 1（基准）
③ 执行可疑操作（如反复打开/关闭弹窗）
④ 执行一次 GC
⑤ 录制 Snapshot 2
⑥ 在 Snapshot 2 中选择 "Comparison" 对比 Snapshot 1
⑦ 按 "Size Delta" 排序，找到增长最多的对象类型
⑧ 展开查看 Retainers（谁引用了它，导致无法被 GC）
```

**Step 3: Allocation Timeline 定位**

```
① Memory → "Allocation instrumentation on timeline"
② 执行操作
③ 蓝色条 = 新分配对象，灰色条 = 已回收
④ 找到持续蓝色不变灰的区间
⑤ 选中该区间，查看分配堆栈
```

**常见泄漏场景及修复**：

```javascript
// 1. 未清理的事件监听器
// ❌ 组件卸载时未解绑
useEffect(() => {
  window.addEventListener("resize", handleResize);
  // 缺少 cleanup！
}, []);

// ✅ 修复：返回清理函数
useEffect(() => {
  window.addEventListener("resize", handleResize);
  return () => window.removeEventListener("resize", handleResize);
}, []);

// 2. 未清理的定时器
// ❌
useEffect(() => {
  const id = setInterval(fetchData, 5000);
  // 缺少 clearInterval！
}, []);

// ✅
useEffect(() => {
  const id = setInterval(fetchData, 5000);
  return () => clearInterval(id);
}, []);

// 3. 闭包持有大对象
// ❌
function setup() {
  const hugeData = new Array(1000000).fill("x");
  return () => console.log(hugeData.length); // hugeData 无法被回收
}

// ✅
function setup() {
  const hugeData = new Array(1000000).fill("x");
  const length = hugeData.length; // 只保留需要的值
  return () => console.log(length);
}
```

### Q15: Core Web Vitals 各指标含义及优化方法

**难度**: ⭐⭐ | **高频指数**: ★★★★☆

> 💡 **面试官意图**: 考察对 Google 性能标准的了解，以及实际优化经验。

**参考答案**：

#### LCP (Largest Contentful Paint) — 最大内容绘制

**定义**：视口中最大可见元素完成渲染的时间。LCP 元素通常是：`<img>`、`<video>` 封面、背景图、大块文字节点。

**目标**：≤ 2.5s

**优化策略**：

1. **预加载 LCP 资源**：`<link rel="preload" as="image" href="hero.webp">`
2. **优化 TTFB**：使用 CDN、服务端缓存、边缘渲染(SSR/SSG)
3. **避免客户端渲染延迟 LCP**：SSR/SSG 让 LCP 元素在首次 HTML 中就存在
4. **图片优化**：使用 WebP/AVIF + 合适尺寸 + fetchpriority="high"

```html
<!-- 提升 LCP 图片的优先级 -->
<img src="hero.webp" fetchpriority="high" alt="Hero" />
```

#### INP (Interaction to Next Paint) — 交互到下一次绘制

**定义**：用户整个会话中**最慢的一次交互延迟**（从输入到下一帧像素更市新）。2024 年正式替代 FID。

**目标**：≤ 200ms

**INP = Input Delay + Processing Time + Presentation Delay**

**优化策略**：

1. **拆分长任务**：将 > 50ms 的任务拆成小块，用 `scheduler.yield()` 让出主线程
2. **Web Worker**：计算密集型任务移出主线程
3. **减少 DOM 操作复杂度**：简化 DOM 结构、使用虚拟列表
4. **debounce/throttle**：减少高频交互的事件处理

```javascript
// 使用 scheduler.yield() 拆分长任务
async function processItems(items) {
  for (const item of items) {
    process(item);
    // 每处理一个，让出主线程让浏览器响应用户交互
    await scheduler.yield();
  }
}
```

#### CLS (Cumulative Layout Shift) — 累积布局偏移

**定义**：页面生命周期内所有意外布局偏移的分数总和。

**目标**：≤ 0.1

**优化策略**：

1. 图片/视频设置明确的 `width` 和 `height` 或 `aspect-ratio`
2. 不在已有内容上方动态插入内容（如广告、横幅）
3. 字体加载使用 `font-display: swap` + 预加载
4. 使用 CSS `contain` 限制布局影响范围

### Q16: 浏览器多进程架构的设计思路与优势

**难度**: ⭐⭐ | **高频指数**: ★★★☆☆

> 💡 **面试官意图**: 考察对浏览器整体架构的理解，而非仅仅渲染层面。

**参考答案**：

**Chrome 主要进程**：

| 进程             | 职责                                           | 数量          |
| ---------------- | ---------------------------------------------- | ------------- |
| Browser Process  | 地址栏、标签栏、前进后退、权限管理、子进程管理 | 1 个          |
| Renderer Process | 解析 HTML/CSS、执行 JS、页面渲染               | 每个站点 1 个 |
| GPU Process      | 所有 Tab 共享的 GPU 绘制                       | 1 个          |
| Network Service  | 网络请求（独立于 Browser Process）             | 1 个          |
| Utility Process  | 音频、视频解码等                               | 按需          |

**设计思路**：

1. **稳定性**：进程隔离 → 一个 Tab 崩溃不影响其他 Tab
2. **安全性**：Site Isolation → 不同站点运行在不同进程，无法直接访问彼此内存（防 Spectre）
3. **性能隔离**：一个 Tab 的 JS 死循环不会冻结整个浏览器
4. **沙箱 (Sandbox)**：Renderer Process 运行在沙箱中，限制文件系统、网络等底层能力

**代价**：

- 内存开销：每个进程都有独立的内存空间（V8 实例、CSSOM 等）。Chrome 因此被称为"内存大户"
- 进程间通信 (IPC)：跨进程通信有性能开销

**Chrome 的内存优化策略**：

- Tab 长时间不活跃 → 自动丢弃 Renderer Process（Tab Discarding）
- 来自同一站点的多个 Tab 可能共享 Renderer Process
- 内存压力大时合并不常用站点的进程

### Q17: Service Worker 的工作原理和生命周期

**难度**: ⭐⭐ | **高频指数**: ★★★☆☆

> 💡 **面试官意图**: PWA 核心技术，考察离线缓存和网络代理的理解。

**参考答案**：

**Service Worker 是什么**：
运行在浏览器后台的 JS 脚本，独立于主线程。充当浏览器与网络之间的**代理服务器**，可以拦截网络请求、缓存资源、实现离线访问。

**生命周期**：

```
① 注册 (Register)
    ↓
② 安装 (Installing)  →  install 事件  →  预缓存关键资源
    ↓
③ 等待 (Waiting)     →  等待旧版本 SW 被替换（除非 skipWaiting()）
    ↓
④ 激活 (Activating)  →  activate 事件  →  清理旧缓存
    ↓
⑤ 运行中 (Activated) →  fetch 事件    →  拦截请求，返回缓存/网络
    ↓
⑥ 冗余 (Redundant)   →  被新版本替换或注册失败
```

```javascript
// 注册 Service Worker
if ("serviceWorker" in navigator) {
  navigator.serviceWorker.register("/sw.js");
}

// sw.js
const CACHE_NAME = "v1";
const URLS_TO_CACHE = ["/", "/styles.css", "/app.js"];

// install 事件：预缓存关键资源
self.addEventListener("install", (event) => {
  event.waitUntil(
    caches.open(CACHE_NAME).then((cache) => cache.addAll(URLS_TO_CACHE)),
  );
  self.skipWaiting(); // 跳过等待，立即激活
});

// activate 事件：清理旧缓存
self.addEventListener("activate", (event) => {
  event.waitUntil(
    caches
      .keys()
      .then((names) =>
        Promise.all(
          names
            .filter((name) => name !== CACHE_NAME)
            .map((name) => caches.delete(name)),
        ),
      ),
  );
});

// fetch 事件：缓存优先策略
self.addEventListener("fetch", (event) => {
  event.respondWith(
    caches
      .match(event.request)
      .then((cached) => cached || fetch(event.request)),
  );
});
```

**常见缓存策略**：
| 策略 | 说明 | 适用 |
|------|------|------|
| Cache First | 先查缓存，没有才请求网络 | 静态资源、字体 |
| Network First | 先请求网络，失败用缓存 | API 数据 |
| Stale While Revalidate | 返回缓存，同时后台更新 | 非关键数据 |

### Q18: 预加载扫描器 (Preload Scanner) 如何工作

**难度**: ⭐⭐ | **高频指数**: ★★★☆☆

> 💡 **面试官意图**: 冷门但体现深度——说明你对浏览器解析细节有研究。

**参考答案**：

当主 HTML 解析器遇到 `<script>`（没有 async/defer）时会暂停，等待脚本下载和执行。如果浏览器就这样傻等，后面的 `<img>`、`<link>` 等资源就得排队。

**预加载扫描器 (Speculative Preload Scanner)** 是浏览器的优化机制：当主解析器被阻塞时，预加载扫描器继续向前扫描 HTML，提前发现并发起对后续资源（CSS、JS、图片等）的下载请求。

```
HTML: <script src="a.js"></script> <link href="b.css"> <img src="c.jpg">

没有预加载扫描器：
Main Parser:  [解析] [等a.js下载] [执行a.js] [解析link] [下载b.css] [解析img] [下载c.jpg]
                                                 ↑ 串行，非常慢

有预加载扫描器：
Main Parser:   [解析] [等a.js下载…] [执行a.js] [继续解析]
Preload Scanner:      [提前发现b.css和c.jpg，并行下载]
                                       ↑ 并行加载，显著更快
```

**注意**：预加载扫描器**只能发现 HTML 中静态声明的资源**。以下情况它无能为力：

- JS 动态创建的 `<img>` 或 `<link>`
- CSS 中的 `background-image: url(...)`
- CSS `@import`（需要 CSS 解析后才发起请求）

**这就是为什么我们需要 `<link rel="preload">`**——显式告诉浏览器"这个资源很重要，请提前下载"。

### Q19: Chrome 合成器架构：主线程 vs 合成器线程 vs 光栅化线程

**难度**: ⭐⭐⭐ | **高频指数**: ★★★☆☆

> 💡 **面试官意图**: 考察对浏览器渲染管道的底层理解，能否解释为什么 `transform` 动画不卡。

**参考答案**：

Chrome 的 Renderer Process 中，渲染工作分布在三类线程上：

```
┌──────────────────────────────────────────────────────────┐
│  Main Thread (主线程)                                     │
│  ─────────────────────                                    │
│  • 执行 JavaScript                                       │
│  • 解析 HTML/CSS                                         │
│  • 计算 Style、Layout                                    │
│  • 生成 Paint Records (绘制指令)                          │
│  • 确定哪些元素需要独立图层                                │
│  产出 → Layer List (图层列表 + 绘制指令)                   │
├──────────────────────────────────────────────────────────┤
│  Compositor Thread (合成器线程)                            │
│  ─────────────────────                                    │
│  • 接收 Main Thread 的 Layer List                        │
│  • 将图层切分为 Tiles（图块，通常 256×256）               │
│  • 决定哪些 Tiles 需要光栅化（优先视口内的）               │
│  • 将 Tiles 交给 Raster Thread                           │
│  • 接收光栅化结果，组合成 Compositor Frame                 │
│  • 直接处理某些动画（transform/opacity）不走 Main Thread   │
│  • 将最终帧提交给 GPU Process                             │
├──────────────────────────────────────────────────────────┤
│  Raster Thread(s) (光栅化线程，多个)                       │
│  ─────────────────────                                    │
│  • 根据绘制指令将 Tiles 转为位图 (Bitmap)                 │
│  • 可以使用 GPU 加速光栅化 (GPU Rasterization)            │
└──────────────────────────────────────────────────────────┘
```

**为什么 `transform` 动画不卡？**

```
使用 left/top 的动画：
每帧：Main Thread [JS→Style→Layout→Paint] → Compositor Thread [合成] → GPU
                    ↑ Main Thread 很忙 → 如果 JS 执行久了，动画卡顿

使用 transform 的动画：
首次：Main Thread [创建图层] → Compositor Thread
后续帧：Compositor Thread [直接修改图层变换矩阵] → GPU
         ↑ 不经过 Main Thread → JS 再忙也不影响动画
```

这就是为什么我们说"将动画属性限制在 `transform` 和 `opacity` 上可以实现 60fps"——因为这些属性可以完全在合成器线程处理。

### Q20: Hidden Class 和 Inline Cache 对性能的影响

**难度**: ⭐⭐⭐ | **高频指数**: ★★★★☆

> 💡 **面试官意图**: 考察对 V8 内部优化机制的理解，能否写出 V8 友好的代码。

**参考答案**：

#### Hidden Class（隐藏类/内部形状）

V8 为每个 JS 对象维护一个隐藏的类型描述（Hidden Class / Map / Shape），记录对象的属性名称、顺序和偏移量。

```javascript
// V8 内部为对象创建 Hidden Class 的过程
const obj = {}; // HC0: {} (空 Hidden Class)
obj.x = 1; // HC1: {x: @offset0}（从 HC0 过渡到 HC1）
obj.y = 2; // HC2: {x: @offset0, y: @offset1}

// 如果另一个对象按相同顺序添加属性 → 共享 Hidden Class
const obj2 = {};
obj2.x = 10; // HC1 (共享)
obj2.y = 20; // HC2 (共享)
```

**过渡链 (Transition Chain)**：

```
HC0 {}  ──添加x──▶  HC1 {x}  ──添加y──▶  HC2 {x, y}
                     ↑
                   obj 和 obj2 都经过这条链 → 共享 Hidden Class
```

**性能影响**：共享 Hidden Class 的对象，V8 可以用固定偏移量访问属性（类似 C struct），极快。不共享 → 无法预测偏移 → 每次都要查哈希表，很慢。

#### Inline Cache（内联缓存）

当执行 `obj.x` 这样的属性访问时，V8 会缓存"对象的 Hidden Class → 属性值的内存偏移"的映射：

```
单态 IC (Monomorphic): 只见过 1 种 HC → 直接用缓存的偏移 → 最快
多态 IC (Polymorphic): 见过 2-4 种 HC → 线性查找缓存 → 较快
超多态 IC (Megamorphic): > 4 种 HC → 退化为通用查找 → 慢
```

```javascript
function getX(obj) {
  return obj.x;
}

// 调用 1000 次传入相同形状的对象 → 单态 IC → 极快
for (let i = 0; i < 1000; i++) {
  getX({ x: i, y: i }); // 始终 {x, y} 形状
}

// 如果传入不同形状 → IC 退化
getX({ x: 1, y: 2 }); // HC_A
getX({ x: 1, y: 2, z: 3 }); // HC_B
getX({ x: 1, name: "a" }); // HC_C
getX({ x: 1, flag: true }); // HC_D
getX({ x: 1, count: 0 }); // HC_E → 超过 4 种 → Megamorphic
```

**最佳实践**：

1. 使用 class 或工厂函数，确保所有对象形状一致
2. 在构造函数中初始化所有属性
3. 不要动态添加/删除属性
4. 保持传入函数的参数类型稳定

**追问方向**：

- V8 的 `delete` 操作为什么慢？（会将对象退化为字典模式）
- 什么时候 V8 会放弃 Hidden Class 使用字典模式？

### Q22: HTTP/2 Server Push vs 103 Early Hints 对比

**难度**: ⭐⭐⭐ | **高频指数**: ★★★☆☆

> 💡 **面试官意图**: 考察对现代 HTTP 协议演进的了解。

**参考答案**：

#### HTTP/2 Server Push（已废弃）

服务器在返回 HTML 的同时，主动"推送"关键子资源（CSS、JS），不等浏览器解析 HTML 后再请求。

**问题**：

- 服务器不知道浏览器是否已有缓存 → 推送已缓存的资源造成浪费
- CDN 支持不佳
- 优先级控制复杂
- Chrome 106+ 移除了 HTTP/2 Server Push 支持

#### 103 Early Hints（推荐方案）

```
HTTP/1.1 103 Early Hints        # 服务器先发一个"提示"
Link: </style.css>; rel=preload; as=style
Link: </app.js>; rel=preload; as=script

... 服务器处理请求中（可能需要查数据库等） ...

HTTP/1.1 200 OK                 # 正式响应
Content-Type: text/html
<html>...</html>
```

**对比**：

| 特点             | Server Push                | 103 Early Hints                |
| ---------------- | -------------------------- | ------------------------------ |
| 浏览器能否拒绝？ | 能（RST_STREAM），但有开销 | ✅ 自然支持——有缓存就不下载    |
| CDN 支持         | 差                         | ✅ Cloudflare、Fastly 等已支持 |
| 是否浪费带宽     | ⚠️ 不检查缓存              | ✅ 浏览器自己判断              |
| 实现复杂度       | 较高                       | 低（服务端只需发响应头）       |
| 当前状态         | 已被 Chrome 废弃           | ✅ 推荐使用                    |

**103 Early Hints 的价值**：在服务器"思考"期间（数据库查询、SSR 渲染），浏览器已经开始并行下载 CSS/JS/字体，节约了宝贵的等待时间。

```
└──────────────────────┘
```

**时间切片示例**：

```javascript
// 使用 requestIdleCallback 分批渲染
function renderChunked(items, container) {
  let index = 0;
  const CHUNK_SIZE = 20;

  function renderChunk(deadline) {
    while (index < items.length && deadline.timeRemaining() > 1) {
      const end = Math.min(index + CHUNK_SIZE, items.length);
      const fragment = document.createDocumentFragment();

      for (let i = index; i < end; i++) {
        const el = document.createElement("div");
        el.textContent = items[i].name;
        fragment.appendChild(el);
      }

      container.appendChild(fragment);
      index = end;
    }

    if (index < items.length) {
      requestIdleCallback(renderChunk);
    }
  }

  requestIdleCallback(renderChunk);
}
```

### Q24: requestIdleCallback vs requestAnimationFrame 调度策略

**难度**: ⭐⭐⭐ | **高频指数**: ★★★☆☆

> 💡 **面试官意图**: 考察对浏览器帧调度的精确理解。

**参考答案**：

| 特性         | requestAnimationFrame (rAF) | requestIdleCallback (rIC)              |
| ------------ | --------------------------- | -------------------------------------- |
| **执行时机** | 每帧渲染前（16.6ms 一帧）   | 帧内空闲时间                           |
| **保证执行** | ✅ 每帧都执行（页面可见时） | ❌ 不保证（可能完全没有空闲时间）      |
| **适用场景** | 动画、DOM 读写、样式计算    | 非紧急任务（分析、预加载、日志）       |
| **超时机制** | 无                          | 可设置 `timeout`，超时后下一帧强制执行 |
| **取消**     | `cancelAnimationFrame(id)`  | `cancelIdleCallback(id)`               |

```
一帧（约 16.6ms）的时间分配：

|← JS 执行 →|← Style →|← Layout →|← Paint →|← Idle →|
|    rAF      |                                | rIC    |
|             |← 这些是渲染工作 →              |        |
```

```javascript
// rAF：适合必须每帧执行的工作
function smoothAnimation() {
  element.style.transform = `translateX(${x++}px)`;
  requestAnimationFrame(smoothAnimation);
}
requestAnimationFrame(smoothAnimation);

// rIC：适合可延迟的低优先级工作
requestIdleCallback(
  (deadline) => {
    // deadline.timeRemaining() 返回当前帧剩余空闲时间（ms）
    while (deadline.timeRemaining() > 0 && tasks.length > 0) {
      processTask(tasks.shift());
    }

    if (tasks.length > 0) {
      requestIdleCallback(processRemainingTasks);
    }
  },
  { timeout: 2000 },
); // 最多等 2 秒，超时后强制执行

// React 的 Fiber 架构启发自类似的调度思想：
// 将渲染工作拆分为可中断的单元，空闲时执行，紧急任务优先
```

**注意事项**：

- rIC 的 `timeRemaining()` 最大值为 50ms（不是一帧的 16.6ms）
- rIC 中**不应该修改 DOM**（会触发强制布局计算）
- Safari 不支持 rIC → 需要 polyfill 或 `setTimeout(fn, 0)` 降级

### Q26: 用户反馈页面越用越卡（内存泄漏排查流程）

**难度**: 🎯 | **高频指数**: ★★★★☆

> 💡 **面试官意图**: 考察实际排查内存问题的系统方法和工具使用能力。

**参考答案**：

**排查流程**：

```
① 复现问题
   - 确认操作路径：哪些操作后变卡？（如反复切换页面、弹窗打开关闭）
   - 打开 DevTools → Performance Monitor → 观察 JS Heap Size

② 确认是内存泄漏
   - 执行可疑操作 → 观察内存曲线
   - 内存只涨不跌（即使手动 GC 也不回落） → 确认泄漏

③ 定位泄漏源
   - Memory → Heap Snapshot → 操作前后对比
   - 按 "Retained Size" 排序 → 找到异常大的对象
   - 查看 Retainers（GC Root 到泄漏对象的引用链）

④ 常见泄漏类型检查清单
```

| 泄漏类型      | 表现                       | 排查方法                             | 修复                        |
| ------------- | -------------------------- | ------------------------------------ | --------------------------- |
| 事件监听器    | addEventListener 未 remove | Elements → Event Listeners           | 组件卸载时 remove           |
| 定时器        | setInterval 未 clear       | Heap Snapshot 搜索 closure           | clearInterval               |
| 闭包          | 闭包引用大对象             | Retainers 链中发现 closure → context | 解除引用或只保存必要值      |
| 脱离 DOM 引用 | JS 变量引用已移除的 DOM    | Snapshot Filter → Detached           | 置 null                     |
| React State   | 卸载组件后仍 setState      | Console 警告                         | AbortController / cleanup   |
| Map/Set       | 作为缓存无限增长           | Snapshot 中 Map size 持续增长        | 使用 WeakMap/WeakRef 或 LRU |

```javascript
// ✅ 使用 WeakRef + FinalizationRegistry 做缓存
const cache = new Map();
const registry = new FinalizationRegistry((key) => {
  cache.delete(key); // 对象被 GC 后自动清理缓存条目
});

function cacheObject(key, obj) {
  cache.set(key, new WeakRef(obj));
  registry.register(obj, key);
}

function getCached(key) {
  const ref = cache.get(key);
  return ref?.deref(); // 如果对象已被 GC，返回 undefined
}
```

**3. 加载策略**

- **首屏图片**：`<link rel="preload">` + `fetchpriority="high"` + 不加 `loading="lazy"`
- **非首屏图片**：`loading="lazy"` 原生懒加载（浏览器在图片即将进入视口时才发起请求）
- **缩略图**：先加载模糊小图(LQIP)，再加载高清图

```javascript
  data-src="product-full.webp"             // 真实图片
  class="lazyload blur-up"
  alt="商品"
>
```

### Q28: SPA 页面白屏时间长如何优化

**难度**: 🎯 | **高频指数**: ★★★★★

> 💡 **面试官意图**: 考察对 SPA 渲染模式缺陷的理解和解决方案的广度。

**参考答案**：

**为什么 SPA 白屏时间长？**

```
传统 SPA (CSR) 渲染流程：
① 下载空壳 HTML（<div id="root"></div>）
② 下载 JS Bundle (可能 1MB+)
③ JS 执行、框架初始化
④ 发起 API 请求获取数据
⑤ 渲染 DOM

用户看到白屏的时间 = ①+②+③+④+⑤ 的总和
```

**优化方案矩阵**：

| 方案               | 原理                                   | 白屏改善 | 复杂度 | 适用场景               |
| ------------------ | -------------------------------------- | -------- | ------ | ---------------------- |
| **SSR**            | 服务端渲染完整 HTML                    | ★★★★★    | 高     | SEO 要求高、内容型页面 |
| **SSG**            | 构建时预渲染                           | ★★★★★    | 低     | 博客、文档、营销页     |
| **流式 SSR**       | 边生成边发送 HTML (React 18 Streaming) | ★★★★★    | 中     | 大型页面、数据驱动     |
| **预渲染**         | 构建时用 Headless Chrome 渲染          | ★★★★☆    | 低     | 不想引入 SSR 的项目    |
| **骨架屏**         | 先显示页面骨架结构                     | ★★★☆☆    | 低     | 任何 SPA               |
| **Code Splitting** | 减少首屏 JS 体积                       | ★★★★☆    | 低     | 所有 SPA               |

**方案一：SSR + Streaming (React 18)**

```jsx
// server.js — 流式 SSR
import { renderToPipeableStream } from "react-dom/server";

app.get("/", (req, res) => {
  const { pipe } = renderToPipeableStream(<App />, {
    bootstrapScripts: ["/app.js"],
    onShellReady() {
      res.setHeader("Content-Type", "text/html");
      pipe(res); // 立即发送 Shell HTML → 用户先看到框架
    },
  });
});
```

**方案二：骨架屏** (最小改造成本)

```html
<!-- index.html 中直接内联骨架屏 -->
<div id="root">
  <!-- 骨架屏内容：JS 加载完后会被替换 -->
  <div class="skeleton">
    <div class="skeleton-header"></div>
    <div class="skeleton-content">
      <div class="skeleton-line"></div>
      <div class="skeleton-line short"></div>
    </div>
  </div>
</div>
<style>
  .skeleton-line {
    height: 16px;
    background: linear-gradient(90deg, #f0f0f0 25%, #e0e0e0 50%, #f0f0f0 75%);
    background-size: 200% 100%;
    animation: shimmer 1.5s infinite;
    border-radius: 4px;
    margin-bottom: 12px;
  }
  @keyframes shimmer {
    to {
      background-position: -200% 0;
    }
  }
</style>
```

**方案三：CSR 优化组合拳**

```
① JS Bundle 体积优化
   - 路由级 Code Splitting
   - 动态 import() 懒加载非首屏组件
   - Bundle Analyzer 找到体积大户并替换（如 moment.js → dayjs）

② 资源加载并行化
   - <link rel="preload"> 预加载关键 JS/CSS
   - <link rel="preconnect"> 预连接 API 域名
   - API 请求尽早发起（不等 JS 框架初始化完成）

③ 缩短 TTFB
   - CDN 加速 HTML 和 JS 资源
   - 开启 Brotli/gzip 压缩
   - 103 Early Hints 提前告知浏览器下载资源
```

**综合方案 — 时间线对比**：

```
纯 CSR：
[空白HTML] [下载JS 1.5s] [执行JS 0.5s] [API 0.5s] [渲染]
|______________ 白屏 3s+ _______________|

CSR + 优化后：
[骨架屏HTML] [下载JS 0.5s + API并行] [渲染]
|_ 白屏0.2s _|_____ 交互1.2s ________|

SSR + Streaming：
[Shell HTML→立即显示] [Streaming数据→逐区渲染] [Hydration→可交互]
|_ 白屏<0.5s _|______ 逐步可见 ________|__ 完全可交互 __|
```
