### ⭐ 基础题

**Q1. TCP 三次握手的流程是什么？为什么是三次而不是两次？**

**参考答案：**

**三次握手流程：**
```
客户端 ──[SYN, seq=x]──────────────────→ 服务器
客户端 ←──[SYN+ACK, seq=y, ack=x+1]─── 服务器
客户端 ──[ACK, ack=y+1]──────────────→  服务器
                连接建立，可以传输数据
```

**为什么需要三次（不能两次）：**

1. **两次握手无法确认客户端的接收能力：** 服务器发出 SYN+ACK 后，不知道客户端是否收到（网络可能丢包）。三次握手中，客户端的 ACK 确认了它收到了服务器的 SYN+ACK。

2. **防止历史连接（旧 SYN 包）被接受：** 若之前有一个因网络延迟而滞留的 SYN 包到达服务器，服务器发出 SYN+ACK。在两次握手情况下，服务器会认为连接已建立（浪费资源）。三次握手中，客户端会发送 RST（因为它根本没发这个 SYN），服务器中止这个无效连接。

**三次握手确认了：**
- 客户端的**发送**和服务器的**接收**能力 ✓（第1次）
- 服务器的**发送**和客户端的**接收**能力 ✓（第2次）
- 客户端**已知道**连接已建立 ✓（第3次，服务器通过这次 ACK 确认）

**Q2. TCP 四次挥手的流程是什么？为什么需要 TIME_WAIT 状态？**

**参考答案：**

**四次挥手流程：**
```
主动关闭方 ──[FIN]──→  被动关闭方（进入 CLOSE_WAIT）
主动关闭方 ←──[ACK]── 被动关闭方
（被动方继续发送剩余数据）
主动关闭方 ←──[FIN]── 被动关闭方（进入 LAST_ACK）
主动关闭方 ──[ACK]──→  被动关闭方（进入 CLOSED）
主动关闭方进入 TIME_WAIT（2MSL 后 CLOSED）
```

**为什么是四次而非三次：** 收到 FIN 后，被动关闭方可能还有数据要发送，所以 ACK 和 FIN 必须分开发送（两次）。

**TIME_WAIT 的两个目的（2MSL = 2 × Maximum Segment Lifetime）：**

1. **确保最后的 ACK 能到达对方：** 若最后的 ACK 丢失，被动关闭方会重发 FIN，TIME_WAIT 状态的主动关闭方能正确响应（再次发送 ACK），而不是发送 RST。

2. **让本次连接的所有报文在网络中消失：** 确保网络中不存在属于此连接的延迟到达报文，防止被下一个使用相同四元组（src IP, src port, dst IP, dst port）的新连接误收。

**TIME_WAIT 过多的危害：** 客户端端口资源耗尽（Linux 默认可用端口 1024-65535）。优化：`net.ipv4.tcp_tw_reuse=1`（在有时间戳支持时复用 TIME_WAIT 连接）。

**Q3. HTTP/1.1 相比 HTTP/1.0 有哪些重要改进？**

**参考答案：**

**1. 持久连接（Persistent Connection）：**
- HTTP/1.0：每个请求-响应后关闭 TCP 连接（需要 `Connection: keep-alive` 头显式开启）
- HTTP/1.1：默认持久连接（`Connection: keep-alive`），同一连接可发送多个请求，减少三次握手次数

**2. 管道化（Pipelining）：**
- 客户端可以不等第一个请求响应，就发送第二个请求
- 但服务器响应必须按序，存在**队头阻塞（Head-of-Line Blocking）**问题
- 实际上大多数浏览器默认禁用管道化（实现复杂且效果差）

**3. 分块传输编码（Chunked Transfer Encoding）：**
- 不需要预先知道响应体大小，可以流式发送（`Transfer-Encoding: chunked`）
- 用于动态生成的内容

**4. 虚拟主机支持（Host 头字段必须：）：**
- 一个 IP 可以托管多个域名（`Host: example.com`），是现代 Web 共享主机的基础

**5. 缓存控制增强：**
- 新增 `Cache-Control` 头，提供比 HTTP/1.0 的 `Expires` 更精细的缓存策略
- 新增条件请求：`If-None-Match`/`ETag`，`If-Modified-Since`/`Last-Modified`

**Q4. HTTPS 是什么？它在 HTTP 的基础上增加了什么？**

**参考答案：**

HTTPS = HTTP + TLS（Transport Layer Security）

**TLS 在 HTTP 基础上增加了三项保证：**

1. **加密（Confidentiality）：** 数据在传输过程中被对称加密（如 AES-256-GCM），即使被截获也无法读取内容

2. **完整性（Integrity）：** 使用 AEAD（Authenticated Encryption with Associated Data）算法（如 GCM 模式），任何篡改都能被检测

3. **身份认证（Authentication）：** 服务器提供数字证书，客户端验证证书是否由可信 CA 签发、是否与域名匹配，防止中间人攻击（MITM）

**工作层次：**
```
应用层:  HTTP（明文）
            ↕
传输层:  TLS（加密/完整性/认证）
            ↕
传输层:  TCP（可靠传输）
            ↕
网络层:  IP
```

**性能影响：** TLS 握手增加 1-2 个 RTT（TLS 1.2 需要 2 RTT，TLS 1.3 只需 1 RTT，再次连接可 0 RTT），以及加密/解密的 CPU 开销（现代 CPU 硬件 AES 加速后影响很小，通常 < 5%）。

**Q5. 什么是 TCP 的粘包问题？如何解决？**

**参考答案：**

**粘包根本原因：** TCP 是**字节流**协议，没有消息边界。发送方发送的多个"消息"可能被合并为一个 TCP 包（Nagle 算法合并小包），或一个大消息被拆分为多个 TCP 包。

```
发送方依次发送：[Message1: 10B] [Message2: 20B]
接收方可能接收到：[10B + 20B = 30B 的完整流]
或接收到：[15B][15B] (拆包)
```

**解决方案：**

1. **固定长度消息：** 每条消息固定 N 字节（简单但浪费，不灵活）

2. **分隔符：** 消息间用特殊字节序列分隔
   - HTTP 头部：`\r\n\r\n` 作为头部结束符
   - Redis RESP 协议：`\r\n` 分隔
   - 缺点：消息内容中不能含有分隔符（或需要转义）

3. **长度前缀（Length-Value，最常用）：**
   - 每条消息前置 N 字节的长度字段
   - 接收方先读 N 字节得到长度 L，再读 L 字节得到消息体
   - 大多数自定义二进制协议（如 Dubbo/Kafka）采用此方案

4. **TLV（Type-Length-Value）：** 包含类型、长度、值三字段，支持可扩展的消息格式（如 Protocol Buffers）

**Q6. 什么是 DNS 解析过程？从浏览器输入 URL 到获得 IP 地址经历了哪些步骤？**

**参考答案：**

```
浏览器输入 https://www.example.com

Step 1: 本地缓存检查
  → 浏览器 DNS 缓存（几秒到几分钟）
  → OS DNS 缓存（/etc/hosts 文件 + 系统解析器缓存）

Step 2: 本地 DNS 解析器（Local Resolver）
  → 查询配置的 DNS 服务器（通常是 ISP 的 DNS 或 8.8.8.8）

Step 3: 递归解析（若本地 DNS 无缓存）
  → DNS Resolver → Root Name Server（.）→ 返回 .com 的 NS 地址
  → DNS Resolver → TLD Name Server（.com）→ 返回 example.com 的 NS 地址
  → DNS Resolver → Authoritative Name Server（example.com）→ 返回 www.example.com 的 A/AAAA 记录

Step 4: 返回 IP 地址（带 TTL）
  → 本地 DNS 解析器缓存结果（TTL 时间内）
  → 返回给浏览器

Step 5: 浏览器使用 IP 发起 TCP + TLS 连接
```

**DNS 记录类型：**
- **A**：域名 → IPv4 地址
- **AAAA**：域名 → IPv6 地址
- **CNAME**：域名 → 另一个域名（别名）
- **MX**：邮件服务器
- **TXT**：任意文本（SPF/DKIM 邮件验证）
- **NS**：权威名称服务器

**Q7. HTTP/2 的多路复用（Multiplexing）是如何工作的？它解决了什么问题？**

**参考答案：**

**HTTP/1.1 的问题（队头阻塞）：**
- 即使开启管道化（Pipelining），服务器也必须**按序**响应
- 第一个响应慢（大文件/复杂计算）→ 阻塞后续所有响应
- 浏览器绕过方案：每个域名开 6-8 个并行连接，浪费资源

**HTTP/2 多路复用原理：**

HTTP/2 将所有数据封装为**帧（Frame）**，并引入 **Stream** 概念：
- 一个 TCP 连接上可以并发多个独立的 Stream（每个请求/响应是一个 Stream）
- 每个 Stream 有唯一 ID（客户端发起的为奇数：1, 3, 5, ...）
- 不同 Stream 的帧可以**交错发送**（Interleaving）

```
TCP 连接中的帧传输：
Stream 1 帧 → Stream 3 帧 → Stream 1 帧 → Stream 5 帧 → Stream 3 帧 → ...
（多个流的帧交错传输，接收方根据 Stream ID 重组）
```

**Stream 的帧传输不需要等待其他 Stream 完成** → 解决了 HTTP 层的队头阻塞。

**残留问题（TCP 层队头阻塞）：** TCP 的丢包重传会阻塞**所有** Stream，直到丢失的包被重传并按序交付。这是 HTTP/3（QUIC）要解决的问题。

**Q8. TLS 1.3 相比 TLS 1.2 做了哪些重要改进？**

**参考答案：**

**1. 握手 RTT 减少：1-RTT 而非 2-RTT**

TLS 1.2 需要 2 个 RTT（ClientHello → ServerHello + Cert + Done → ClientKey + Finished → ServerFinished）。

TLS 1.3 客户端在 `ClientHello` 中直接包含 ECDHE 公钥（`key_share`），服务器第一次响应就可以计算出共享密钥，握手仅需 1 RTT。

**2. 0-RTT 会话恢复（Session Resumption）**

基于 PSK（Pre-Shared Key / Session Ticket），再次连接时客户端在第一个消息中直接携带应用数据（0-RTT）。注意：0-RTT 数据不具备前向保密性，且有重放攻击风险（应只用于幂等操作）。

**3. 强制前向保密（Forward Secrecy）**

TLS 1.2 支持静态 RSA 密钥交换（用服务器私钥直接加密 Pre-Master Secret），如果服务器私钥泄露，历史流量可被解密。TLS 1.3 移除了静态 RSA，**只允许 ECDHE 临时密钥交换**，每次会话的密钥独立，历史记录无法被解密。

**4. 精简密码套件（5 种，全部 AEAD）**

移除了 RC4、3DES、CBC 模式、SHA-1/MD5 等弱算法，只保留 AES-GCM、AES-CCM、ChaCha20-Poly1305 等安全算法。

**5. 加密 ServerHello 之后的握手消息（Certificate、CertificateVerify）**

TLS 1.2 的证书是明文传输的，攻击者可以知道你访问了哪个网站的证书。TLS 1.3 将 `Certificate` 和 `CertificateVerify` 加密传输（使用握手密钥），提升了隐私保护。

**Q9. 解释 WebSocket 的握手过程和帧格式，以及它与 HTTP 长轮询的区别。**

**参考答案：**

**WebSocket 升级握手：**

```http
# 客户端请求：
GET /ws HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==  ← 随机 16 字节 Base64
Sec-WebSocket-Version: 13

# 服务器响应：
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
# Accept = Base64(SHA1(Key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"))
```

**握手后：** TCP 连接转为 WebSocket 协议，双方可以互发帧（全双工）。

**WebSocket 帧格式（关键字段）：**
- FIN (1bit)：是否最后一个分片
- Opcode (4bit)：0x1=文本, 0x2=二进制, 0x8=关闭, 0x9=Ping, 0xA=Pong
- MASK (1bit)：客户端→服务器必须掩码（4字节随机掩码 XOR 数据）
- Payload Length (7/16/64 bit)：可变长度字段

**vs HTTP 长轮询：**

| | 长轮询（Long Polling）| WebSocket |
|--|----------------------|-----------|
| 方向 | 单向（服务器→客户端响应后关闭）| 全双工（同时双向）|
| 延迟 | 有（每次响应后需重建连接）| 极低（持久连接）|
| HTTP 兼容 | 完全兼容 | 需要 Upgrade 支持 |
| 服务器推送 | 间接（等待客户端发起）| 直接 |
| 适用场景 | 低频率通知（新邮件）| 高频率实时（聊天/游戏）|

**Q10. TCP 的拥塞控制有哪几个算法？慢启动阶段为什么叫"慢"启动？**

**参考答案：**

**TCP 拥塞控制四个算法（RFC 5681 Reno 为基础）：**

1. **慢启动（Slow Start）：**
   - 初始 `cwnd = 1 MSS`（或 10 MSS，RFC 6928）
   - 每收到一个 ACK，`cwnd += 1 MSS`（指数增长，每 RTT 翻倍）
   - 增长到 `ssthresh` 时进入拥塞避免

2. **拥塞避免（Congestion Avoidance）：**
   - `cwnd >= ssthresh` 后，每 RTT 只 `cwnd += 1 MSS`（线性增长）
   - 更保守地探测带宽上限

3. **快速重传（Fast Retransmit）：**
   - 收到 3 个重复 ACK 时，立即重传丢失包（不等超时）
   - 进入快速恢复：`ssthresh = cwnd/2`, `cwnd = ssthresh + 3`

4. **快速恢复（Fast Recovery）：**
   - 在快速重传后，进入快速恢复状态
   - 每收到重复 ACK，`cwnd++`（维持数据发送）
   - 收到新 ACK（确认重传成功），`cwnd = ssthresh`，退出快速恢复

**"慢"启动的含义：**

慢启动的"慢"不是指增长速度慢（实际上是**指数增长**，非常快），而是相对于 TCP 之前的"快速启动"策略（直接以完整窗口发送）——慢启动从 **1 个包开始**，逐渐增加，因此叫"慢"启动。

**历史背景：** 1988 年 Van Jacobson 引入慢启动之前，新连接直接发送满窗口数据，导致大量丢包，造成了著名的"拥塞崩溃（Congestion Collapse）"。

**Q11. 解释 HTTP/3 和 QUIC 协议，它如何彻底解决队头阻塞问题？**

**参考答案：**

**HTTP/2 残留的 TCP 队头阻塞：**

HTTP/2 虽然在 HTTP 层实现了多路复用，但底层使用 TCP。TCP 丢包时，其可靠性保证要求丢失的包被重传且按序交付，在此期间所有 Stream 的数据交付都被阻塞，即使其他 Stream 的数据已经到达。

**QUIC 的解决方案：**

QUIC 在 UDP 之上实现了**Stream 级别的独立可靠传输**：
- 每个 Stream 有独立的有序交付队列
- 某个 Stream 的包丢失 → 只影响该 Stream，其他 Stream 继续正常交付
- 从根本上消除了 TCP 层的队头阻塞

**QUIC 其他关键特性：**

| 特性 | 说明 |
|------|------|
| 集成 TLS 1.3 | 握手+加密合一，新连接 1-RTT，会话恢复 0-RTT |
| Connection Migration | 用 Connection ID 标识连接（非 IP:Port），网络切换不断连 |
| 用户态实现 | 运行在 UDP 之上，无需修改内核，更新灵活 |
| 前向纠错（FEC）| 可选，减少丢包重传的影响 |

**HTTP/3 = HTTP/2 语义 + QUIC 传输**，保留了 HPACK 头部压缩（升级为 QPACK 以适应 QUIC 的乱序特性）。

**Q12. 什么是 DNS over HTTPS（DoH）？它解决了什么安全问题？**

**参考答案：**

**传统 DNS 的安全问题：**
1. **明文传输（UDP 53 端口）**：DNS 查询不加密，ISP/任何中间人可以监听你的所有 DNS 查询
2. **DNS 劫持**：中间人可以伪造 DNS 响应，将域名解析到恶意 IP
3. **DNS 污染**：在某些网络环境下，DNS 响应被篡改

**DoH（DNS over HTTPS，RFC 8484）：**
- 将 DNS 查询封装在 HTTPS 请求中（`Content-Type: application/dns-message`）
- 使用 HTTPS 的 TLS 加密，隐藏查询内容，防止窃听和篡改
- 请求路径：`https://dns.google/dns-query?dns=...`（或 Cloudflare `1.1.1.1`）

**vs DoT（DNS over TLS，RFC 7858）：**
- DoT 使用独立端口 853，网络管理员可以通过封锁 853 端口阻止
- DoH 使用 443 端口（与正常 HTTPS 混合），难以被屏蔽
- DoT 延迟略低（无 HTTP 层开销），但 DoH 更难被过滤

**Q13. 详细描述 TLS 1.2 完整握手过程中的密钥派生，以及前向保密是如何实现的。**

**参考答案：**

**TLS 1.2 + ECDHE 完整握手密钥派生：**

```
Step 1: 客户端发送 ClientHello
  - 随机数 client_random（32 bytes）
  - 支持的加密套件列表

Step 2: 服务器发送 ServerHello + Certificate + ServerKeyExchange
  - 随机数 server_random（32 bytes）
  - 选择的加密套件
  - Certificate：服务器证书（含 RSA/ECDSA 公钥）
  - ServerKeyExchange：
      临时 ECDHE 公钥（server_ecdhe_pub）
      + 用服务器私钥对 (client_random + server_random + server_ecdhe_pub) 的签名
      （签名证明这个临时 ECDHE 公钥确实是该服务器生成的，防止 MITM）

Step 3: 客户端发送 ClientKeyExchange
  - 客户端临时 ECDHE 公钥（client_ecdhe_pub）

Step 4: 双方独立计算 Pre-Master Secret
  - pre_master_secret = ECDH(server_ecdhe_pub, client_ecdhe_priv)
                      = ECDH(client_ecdhe_pub, server_ecdhe_priv)
  （ECDH 的特性：双方使用对方公钥和自己私钥计算出相同的值）

Step 5: 派生 Master Secret（PRF = HMAC-SHA256/SHA384）
  master_secret = PRF(pre_master_secret, "master secret",
                      client_random + server_random, 48 bytes)

Step 6: 派生会话密钥（密钥块 Key Block）
  key_block = PRF(master_secret, "key expansion",
                  server_random + client_random, key_block_len)
  从中提取：
    client_write_key  → 客户端→服务器的数据加密密钥
    server_write_key  → 服务器→客户端的数据加密密钥
    client_write_IV   → 客户端加密的初始向量
    server_write_IV   → 服务器加密的初始向量
```

**前向保密（Forward Secrecy）的实现：**

使用 **ECDHE（临时 ECDH）**：服务器每次握手都生成新的临时 ECDH 密钥对（`server_ecdhe_priv/pub`），使用后丢弃。

即使将来服务器的长期 RSA/ECDSA 私钥泄露：
- 攻击者可以验证之前的证书签名
- 但**无法获得临时 ECDHE 私钥**（已丢弃）
- 因此**无法计算 Pre-Master Secret → 无法解密历史会话流量**

对比：若使用静态 RSA 密钥交换（TLS 1.3 已移除），`pre_master_secret` 用服务器 RSA 公钥加密，私钥泄露后历史流量全部可解密。

**Q14. 在高并发场景下，如何解决 TIME_WAIT 过多的问题？每种方案的原理是什么？**

**参考答案：**

**TIME_WAIT 过多的原因：** 大量短连接（如 HTTP/1.0 或没有连接复用的 HTTP/1.1），主动关闭方留下大量 TIME_WAIT 状态连接，占用端口资源（端口耗尽后新连接失败）。

**解决方案：**

**方案 1：`net.ipv4.tcp_tw_reuse = 1`（推荐）**
```bash
sysctl -w net.ipv4.tcp_tw_reuse=1
```
允许新连接复用处于 TIME_WAIT 状态的连接（要求新连接的时间戳大于 TIME_WAIT 连接的时间戳，依赖 TCP 时间戳选项 `tcp_timestamps=1`）。安全，不影响数据完整性。

**方案 2：`net.ipv4.tcp_fin_timeout` 缩短**
```bash
sysctl -w net.ipv4.tcp_fin_timeout=15  # 默认 60 秒
```
缩短 FIN_WAIT_2 和 TIME_WAIT 的超时时间（TIME_WAIT = 2*MSL，Linux 实际 MSL=30s，可调整）。

**方案 3：扩大端口范围**
```bash
sysctl -w net.ipv4.ip_local_port_range="1024 65535"
```

**方案 4：HTTP 连接复用（根本解决方案）**
- 开启 HTTP Keep-Alive（HTTP/1.1 默认）
- 使用连接池复用 TCP 连接
- 升级到 HTTP/2（单连接多路复用）

**方案 5：`net.ipv4.tcp_tw_recycle = 1`（不推荐，已废弃）**
- 快速回收 TIME_WAIT 连接，不等 2MSL
- 在 NAT 环境下可能导致连接失败（同一 NAT 后的不同客户端时间戳可能乱序）
- Linux 4.12 内核已移除此选项

**Q15. 解释 TCP 滑动窗口和拥塞控制窗口的关系，以及流量控制与拥塞控制的区别。**

**参考答案：**

**两种窗口：**

- **接收窗口（rwnd，Receiver Window）：** 接收方缓冲区的剩余空间，通过 TCP 头的 Window 字段通告给发送方。**流量控制**用——防止发送方压垮接收方。

- **拥塞窗口（cwnd，Congestion Window）：** 发送方根据拥塞控制算法（慢启动/拥塞避免）维护的内部变量。**拥塞控制**用——防止发送方压垮网络。

**实际发送量 = min(rwnd, cwnd)**

```
例：
  rwnd = 64KB（接收方告知，接收缓冲区还有 64KB）
  cwnd = 32KB（拥塞控制认为网络容量约 32KB）
  → 实际可发送 32KB
  
  rwnd = 16KB（接收方缓冲区快满了）
  cwnd = 32KB
  → 实际可发送 16KB（受流量控制限制）
```

**流量控制 vs 拥塞控制：**

| | 流量控制（Flow Control）| 拥塞控制（Congestion Control）|
|--|------------------------|-------------------------------|
| 目的 | 防止接收方缓冲区溢出 | 防止网络链路拥塞 |
| 依据 | 接收方通告的 rwnd | 丢包/RTT 变化（网络反馈）|
| 机制 | 滑动窗口 | 慢启动/拥塞避免/快速恢复 |
| 控制对象 | 端到端（发送方-接收方）| 网络整体 |
| RFC | RFC 793 | RFC 5681 |

**Q16. HTTP 缓存机制是如何工作的？强缓存和协商缓存的区别是什么？**

**参考答案：**

**强缓存（不向服务器发请求）：**

浏览器检查本地缓存是否过期：
- `Cache-Control: max-age=3600`（相对时间，推荐，优先级更高）
- `Expires: Wed, 21 Oct 2025 07:28:00 GMT`（绝对时间，HTTP/1.0，受客户端时钟影响）

缓存未过期 → 直接使用本地缓存，返回 `200 OK (from cache)`，**不发送网络请求**。

**协商缓存（向服务器验证是否有更新）：**

强缓存过期后，浏览器发请求到服务器验证：

| 客户端发送 | 服务器响应（未修改）| 服务器响应（已修改）|
|-----------|------------------|------------------|
| `If-None-Match: "etag_value"` | `304 Not Modified` | `200 OK` + 新 `ETag` |
| `If-Modified-Since: date` | `304 Not Modified` | `200 OK` + 新 `Last-Modified` |

`304 Not Modified` 只返回响应头，不返回 body，节省带宽。

**ETag vs Last-Modified 的优先级：** ETag 优先级更高（`ETag` 是内容哈希，精确；`Last-Modified` 只有秒级精度，且文件修改时间改变不代表内容改变）。

**Cache-Control 指令：**

```
public: 任何缓存可存储（CDN、代理等）
private: 只有浏览器可存储（用户私有内容）
no-cache: 必须向服务器验证（走协商缓存，不走强缓存）
no-store: 不缓存（敏感数据）
must-revalidate: 缓存过期后必须验证，不允许使用过期缓存
s-maxage: CDN 缓存时间（覆盖 max-age）
stale-while-revalidate=N: 返回旧缓存同时后台更新（SWR 模式）
```

**Q17. 什么是跨域资源共享（CORS）？浏览器的同源策略是什么？**

**参考答案：**

**同源策略（Same-Origin Policy）：** 浏览器安全基石。"同源"要求**协议 + 域名 + 端口**完全相同。不同源的 JavaScript 不能读取对方的响应、Cookie、DOM。

**CORS（Cross-Origin Resource Sharing）：** HTTP 头部机制，允许服务器声明哪些跨域请求是允许的。

**简单请求（直接发送，附带 CORS 头）：**
- 方法：GET/POST/HEAD
- 头部：只包含简单字段（Content-Type 限于 form 格式等）

```http
# 请求
GET /data HTTP/1.1
Origin: https://frontend.example.com

# 响应
Access-Control-Allow-Origin: https://frontend.example.com
Access-Control-Allow-Credentials: true  # 允许携带 Cookie
```

**预检请求（Preflight，OPTIONS 方法）：**
- 非简单请求（如 `Content-Type: application/json` 或自定义头）先发 OPTIONS 请求
- 服务器返回允许的方法和头部，浏览器再发实际请求

```http
# 预检请求
OPTIONS /data HTTP/1.1
Origin: https://frontend.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: Content-Type, Authorization

# 预检响应
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://frontend.example.com
Access-Control-Allow-Methods: GET, POST, PUT
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 86400  # 预检结果缓存时间（秒）
```

**Q18. HTTPS 证书链验证的详细过程是什么？什么是证书透明度（Certificate Transparency）？**

**参考答案：**

**证书链验证步骤：**

1. **链的构建：** 从服务器证书开始，查找颁发者（Issuer），找到中间 CA 证书，直到找到系统信任的 Root CA。

2. **签名验证（每个证书）：** 用上级证书的公钥验证当前证书的签名。服务器证书由中间 CA 签名，中间 CA 由 Root CA 签名，Root CA 自签名（系统预置）。

3. **有效期验证：** 检查每个证书的 NotBefore 和 NotAfter 字段是否包含当前时间。

4. **域名验证：** 检查证书的 CN（Common Name）或 SAN（Subject Alternative Name）是否与请求的域名匹配（支持通配符 `*.example.com`）。

5. **撤销检查（OCSP/CRL）：**
   - OCSP（Online Certificate Status Protocol）：实时查询 CA 的 OCSP 服务器
   - CRL（Certificate Revocation List）：下载证书吊销列表（较慢）
   - OCSP Stapling（推荐）：服务器预先查询 OCSP 并将响应缓存在 TLS 握手中

**证书透明度（Certificate Transparency, CT）：**

为防止 CA 私下颁发伪造证书（如伪造 google.com 的证书）：

- 所有受信任 CA 颁发的证书必须记录到公开的 **CT Log**（基于 Merkle 树，不可篡改）
- 每个证书颁发时获得一个 **SCT（Signed Certificate Timestamp）**（CT Log 的签名凭证）
- 浏览器在 TLS 握手中检查 SCT，证书未在 CT Log 中则拒绝

这样，任何 CA 颁发的伪造证书都会被公开，域名所有者可以监控（如 Google 的 crt.sh 网站）。

**Q19. 介绍 HTTP 请求走私（Request Smuggling）攻击原理。**

**参考答案：**

**背景：** 现代 Web 架构通常有前端代理（CDN/负载均衡）+ 后端服务器，两者都需要解析 HTTP 请求边界。

**攻击原理：** HTTP 规定两种指定请求体大小的方式：
- `Content-Length`：明确的字节长度
- `Transfer-Encoding: chunked`：分块传输，用 `0\r\n\r\n` 标记结束

当前端代理和后端服务器对请求边界的解析不一致时，攻击者可以"走私"一个额外的请求到后端：

**CL.TE 攻击（前端用 Content-Length，后端用 Transfer-Encoding）：**
```http
POST / HTTP/1.1
Host: example.com
Content-Length: 49
Transfer-Encoding: chunked

e\r\n
SMUGGLED DATA\r\n
0\r\n
\r\n
GET /secret HTTP/1.1
Host: evil.com
Foo: x
```

前端看到 `Content-Length: 49`，转发 49 字节到后端。后端使用 chunked 解析，处理完 `e\r\n...0\r\n\r\n` 后，`GET /secret HTTP/1.1...` 被当作**下一个请求的开头**，由下一个用户的请求完成——可以读取其他用户的请求、绕过 ACL、缓存投毒等。

**防御：** 
- 前后端统一解析方式（都用 CL 或都用 TE）
- 后端拒绝模糊请求（同时含 CL 和 TE 的请求）
- 使用 HTTP/2（帧格式定义了精确的消息边界，无此问题）

**Q20. 解释 TCP 的 Nagle 算法，以及什么场景下应该禁用它。**

**参考答案：**

**Nagle 算法的目的：** 减少网络中小包（Tiny Packet）数量，提高网络利用率。

**核心逻辑：**
```
if (有数据要发送):
    if (未确认的数据量 == 0 或 待发送数据 >= MSS):
        立即发送
    else:
        等待，将小数据缓存，直到收到 ACK 或缓存满 MSS 再发送
```

**Nagle 算法与延迟 ACK（Delayed ACK）的交互问题：**

TCP 接收方默认有延迟 ACK（等待 40-200ms 再 ACK，期望合并 ACK 与响应数据）。

```
客户端发 16B 小包 → 服务器
服务器：延迟 ACK 等 40ms
客户端：Nagle 等 ACK 再发下一个包
结果：双方都在等对方，延迟 40ms + Nagle 缓存时间！
```

这是著名的 **Nagle + Delayed ACK 性能问题**，在 SSH/MySQL 客户端等交互式应用中表现明显。

**禁用 Nagle 的场景（`TCP_NODELAY` 选项）：**

```c
int flag = 1;
setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &flag, sizeof(flag));
```

- **SSH、Telnet 等交互式应用**：用户每次击键都需要立即发送，Nagle 引入额外延迟
- **在线游戏客户端**：实时性要求高，每帧状态更新不能等待缓存
- **MySQL/PostgreSQL 客户端库**：默认开启 TCP_NODELAY（或 MySQL 的 `CLIENT_NO_DELAY`）
- **延迟敏感的金融交易系统**：微秒级延迟要求

**不应禁用：** 批量文件传输、大数据量上传——Nagle 减少了大量小包，提高了吞吐量。
