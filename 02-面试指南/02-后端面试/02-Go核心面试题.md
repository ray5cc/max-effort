**Q1. Go 的协程（Goroutine）与线程的区别是什么？为什么 Go 可以轻松创建百万个 Goroutine？**

**参考答案：**

| | OS 线程 | Goroutine |
|--|---------|-----------|
| 创建代价 | 重（内核操作，~1MB 栈）| 轻（Go runtime，初始 ~2KB 栈）|
| 栈大小 | 固定（通常 1-8MB）| 动态增长（2KB → 1GB，按需扩缩）|
| 调度 | OS 内核抢占（毫秒级）| Go runtime 协作/抢占（微秒级）|
| 上下文切换 | 重（保存寄存器、TLB 刷新等）| 轻（只保存少量寄存器 + 栈指针）|
| 通信 | 共享内存 + 锁 | Channel（CSP 模型）|
| 数量 | 通常 <10,000（受 OS 限制）| 百万级（受内存限制）|

**可以创建百万 Goroutine 的原因：**
1. **初始栈极小**（2KB vs 线程 1MB），100万 goroutine 仅需约 2GB 内存
2. **M:N 调度**：少量 OS 线程（M，通常等于 CPU 核数）多路复用大量 Goroutine（G），调度在用户态完成，无系统调用开销
3. **动态栈**：栈按需扩缩，不会预先占用大量内存

**Q2. 解释 Go 的 GMP 调度模型中 G、M、P 各自的职责。**

**参考答案：**

- **G（Goroutine）**：代表一个轻量级"任务"。包含栈、程序计数器（`gobuf.pc`）、状态等信息。`struct g` 定义在 `src/runtime/runtime2.go`。

- **M（Machine，OS Thread）**：真正执行代码的 OS 线程。每个 M 需要绑定一个 P 才能运行用户 Goroutine。M 的数量不受 GOMAXPROCS 限制，阻塞中的 M 没有 P。

- **P（Processor，逻辑处理器）**：调度上下文，数量由 `GOMAXPROCS` 决定（默认等于 CPU 核数）。P 持有：本地 Goroutine 运行队列（`runq`，最多 256 个）、`mcache`（无锁内存分配器）。

**关键关系：**
- 同一时刻最多有 `GOMAXPROCS` 个 M 在**并行**执行 Goroutine（每个 M 绑定一个 P）
- 阻塞在系统调用的 M 会与 P 解绑，P 可以绑定空闲 M 继续运行其他 Goroutine
- 全局运行队列（`sched.runq`）存放溢出的 Goroutine，本地队列空时从全局队列取

**Q3. Go Channel 的基本使用规则是什么？向已关闭的 Channel 发送数据会发生什么？**

**参考答案：**

**Channel 基本行为：**

| 操作 | nil channel | 空 channel | 非空 channel | 已满 channel | 已关闭 channel |
|------|------------|-----------|-------------|-------------|---------------|
| 发送 | 永远阻塞 | 阻塞 | 成功 | 阻塞 | **panic** |
| 接收 | 永远阻塞 | 阻塞 | 成功 | 成功 | 返回零值, ok=false |
| 关闭 | panic | 成功 | 成功 | 成功 | panic（重复关闭）|

**向已关闭 Channel 发送数据：`panic: send on closed channel`**

**从已关闭 Channel 接收：** 返回零值（`false, ok`），不 panic。

**最佳实践：**
- 由**发送方**关闭 Channel（接收方不应关闭）
- 多发送方场景：用 `sync.Once` 或额外的 done channel 协调关闭
- 用 `v, ok := <-ch` 判断 channel 是否已关闭

**Q4. `defer` 的执行顺序是什么？它在哪些场景下特别有用？**

**参考答案：**

**执行顺序：** `defer` 以 **LIFO（后进先出）** 顺序执行——最后注册的 defer 最先执行，类似栈。

```go
func main() {
    defer fmt.Println("1")
    defer fmt.Println("2")
    defer fmt.Println("3")
}
// 输出: 3, 2, 1
```

**参数求值时机：** defer 注册时，函数参数**立即求值**（不是在执行时求值）：

```go
x := 1
defer fmt.Println(x)  // x 的值在此处求值为 1
x = 2
// 输出 1，不是 2
```

**defer + 命名返回值** 可以修改返回值：

```go
func f() (result int) {
    defer func() { result++ }()  // 可以修改 result
    return 0   // 实际返回 1
}
```

**适用场景：**
- 资源清理（`defer file.Close()`）
- 互斥锁释放（`defer mu.Unlock()`）
- 错误处理（`defer func() { if err != nil { ... } }()`）
- 性能追踪（`defer trace(time.Now())`）

**Q5. Go 中 `make` 和 `new` 的区别是什么？**

**参考答案：**

| | `new(T)` | `make(T, ...)` |
|--|----------|----------------|
| 适用类型 | 任意类型 | 仅 slice/map/channel |
| 返回值 | `*T`（指针）| T（值，已初始化）|
| 初始化 | 零值（未初始化内部结构）| 初始化内部数据结构（可用）|
| 用途 | 分配内存并清零 | 创建可用的引用类型 |

```go
p := new(int)       // *int，指向零值 int
s := make([]int, 5) // []int，len=5, cap=5，内部数组已分配
m := make(map[string]int) // map，内部哈希表已初始化

// 错误用法（不使用 make 的 map 是 nil，写入会 panic）
var m map[string]int
m["key"] = 1  // panic: assignment to entry in nil map
```

**Q6. 解释 Go 的 `interface{}` 和泛型（Generics）的区别及各自适用场景。**

**参考答案：**

**`interface{}`（空接口，Go 1.18 前通用做法）：**
- 运行时多态：需要类型断言，性能损耗（反射/断言）
- 编译时无类型检查：类型错误在运行时才暴露
- 适用：确实不知道类型（如 `fmt.Println`、`json.Marshal`）

**泛型（Go 1.18+，类型参数）：**
- 编译时多态：编译器生成特化代码，无运行时类型检查开销
- 编译时类型安全：类型错误在编译时发现
- 代码复用：同一算法适用多种类型，无需重复实现

```go
// interface{} 版本（类型不安全）
func Max(a, b interface{}) interface{} {
    if a.(int) > b.(int) { return a }  // 运行时 panic 风险
    return b
}

// 泛型版本（类型安全，性能更好）
func Max[T constraints.Ordered](a, b T) T {
    if a > b { return a }
    return b
}

result := Max(3, 5)    // 编译时确定 T=int
result2 := Max(3.0, 5.0) // T=float64
```

**适用场景：** 数据结构（栈、堆、树）、算法（排序、搜索）、通用工具函数 → 泛型；序列化/反序列化、运行时动态类型 → `interface{}`。

**Q7. 详细解释 Go Channel 的底层 `hchan` 结构体，以及一次发送操作的完整流程。**

**参考答案：**

**`hchan` 结构体关键字段（`src/runtime/chan.go`）：**

```go
type hchan struct {
    qcount   uint           // 环形缓冲区中的元素数量
    dataqsiz uint           // 缓冲区容量（make(chan T, n) 的 n）
    buf      unsafe.Pointer // 指向环形缓冲区
    elemsize uint16         // 元素大小
    closed   uint32         // 是否关闭
    sendx    uint           // 发送索引（写入位置）
    recvx    uint           // 接收索引（读取位置）
    recvq    waitq          // 阻塞等待接收的 goroutine 队列
    sendq    waitq          // 阻塞等待发送的 goroutine 队列
    lock     mutex          // 互斥锁（保护所有字段）
}
```

**发送操作 `ch <- v` 的三种情况：**

**情况 1：有等待的接收者（`recvq` 非空）**
- 直接将数据从发送方拷贝到接收方（无需经过 buffer）
- `goready()` 唤醒接收方 goroutine（设为 `_Grunnable`）
- **零拷贝优化**（直接内存拷贝，跳过 buffer）

**情况 2：有缓冲且缓冲未满**
- 将数据拷贝到 `buf[sendx]`
- `sendx = (sendx + 1) % dataqsiz`（环形）
- `qcount++`

**情况 3：无缓冲或缓冲已满**
- 创建 `sudog`（包含当前 goroutine + 数据指针）
- 将 `sudog` 加入 `sendq` 队列
- `gopark()` 挂起当前 goroutine（设为 `_Gwaiting`）
- 等待接收方唤醒

**Q8. 解释 Go 的工作窃取（Work Stealing）调度策略，以及它如何提高 CPU 利用率。**

**参考答案：**

**问题背景：** 如果只有简单的全局队列，所有 P 都从全局队列取 Goroutine，需要加锁竞争，成为瓶颈。

**Go 的两级队列：**
- **本地队列（Local Queue）**：每个 P 有独立的本地队列（环形缓冲区，容量 256），入队/出队无锁
- **全局队列（Global Queue）**：溢出的 Goroutine 和系统 Goroutine 放这里

**调度优先级（`schedule()` 函数）：**
1. 每 61 次从全局队列取一个（防止全局队列饥饿）
2. 从 `runnext`（最高优先级，刚创建或刚唤醒的 Goroutine）取
3. 从本地队列取
4. 都空时：工作窃取（`findRunnable()` → `stealWork()`）

**工作窃取（`stealWork`）：**
- 随机选择一个目标 P，偷取其本地队列的**一半** Goroutine
- 遍历所有 P 尝试 4 次（随机起始位置，避免热点竞争）
- 都失败：检查 netpoll（网络 I/O 就绪的 Goroutine），最后 `stopm()` 休眠 M

**CPU 利用率提升：**
- 某 P 的 Goroutine 执行完或阻塞 → 从其他繁忙 P 窃取任务
- 工作分布更均匀，避免某些 CPU 核空闲而另一些过载
- 无需中央调度器，减少锁竞争

**Q9. Go 的内存分配器如何处理小对象、大对象和微对象？**

**参考答案：**

Go 内存分配器基于 TCMalloc 思想，三级分配架构（`mcache → mcentral → mheap`）：

**三类对象：**

**1. 微对象（Tiny Object，< 16B 且无指针）：**
- 使用 `mcache.tiny` 指向的 16B 块，多个微对象合并到同一 16B 块（`tinyoffset` 追踪使用量）
- 极低开销，适合大量小字符串/整型

**2. 小对象（Small Object，16B ≤ size ≤ 32KB）：**
- 按大小分到 67 种 size class（8B, 16B, 24B, ..., 32KB）
- 分配路径：`mcache.alloc[sizeclass]`（无锁 O(1)）→ `mcentral.partial`（加互斥锁）→ `mheap`（全局锁 + 向 OS 申请）
- 每个 P 的 `mcache` 是线程局部缓存，避免全局锁竞争

**3. 大对象（Large Object，> 32KB）：**
- 直接从 `mheap` 分配（按页为单位，`npages = roundup(size)/pageSize`）
- 创建独立的 `mspan` 管理
- 相对较少，全局锁可接受

**span（`mspan`）：** 由若干连续 page 组成，管理同一 size class 的对象分配。`mspan.freeindex` 标记下一个可用对象位置（bump pointer，无锁）。

**Q10. 解释 Go 垃圾收集器中的混合写屏障（Hybrid Write Barrier）是如何防止对象漏标的。**

**参考答案：**

**漏标（Missing Mark）问题：** 并发标记过程中，用户程序修改了引用关系，可能导致本应存活的对象被误回收：

```
初始状态：A（黑色）→ B（灰色）→ C（白色）

应用程序执行：
  1. A.ptr = C  （黑色对象 A 新增对白色 C 的引用）
  2. B.ptr = nil（C 原来的引用者 B 删除对 C 的引用）

结果：C 现在只被黑色 A 引用，但 A 已黑（不再扫描），C 永远无法变黑
     → C 在 GC 结束时仍是白色 → 被错误回收！
```

**Go 1.14 混合写屏障（`writePointer(slot, ptr)`）：**

```go
// 在指针写入时触发（JIT 插入）:
func writePointer(slot *pointer, ptr pointer) {
    // 1. 将 *slot（旧值）着灰色（Yuasa 删除屏障）
    shade(*slot)
    // 2. 如果当前 goroutine 的栈尚未被扫描（灰色栈），将 ptr（新值）也着灰色
    if current_stack_is_grey {
        shade(ptr)
    }
    // 3. 执行实际写入
    *slot = ptr
}
```

**修复漏标：**
- 操作 1（`A.ptr = C`）：slot 旧值是 B，`shade(B)` 将 B 着灰色；若 A 在灰色栈上，`shade(C)` 将 C 着灰色
- 操作 2（`B.ptr = nil`）：slot 旧值是 C，`shade(C)` 将 C 着灰色
- 最终 C 一定会变灰色，被扫描并最终变黑色 → 不会被误回收 ✓

**优势：** Go 1.14 的混合写屏障不需要在 GCMarkTermination 阶段 STW 重新扫描所有 goroutine 栈（Dijkstra 插入屏障需要），大幅减少最终 STW 时间。

**Q11. Go 的 `select` 语句是如何实现的？多个 case 就绪时如何保证公平性？**

**参考答案：**

**`select` 编译为 `runtime.selectgo()`。**

**实现步骤：**

1. **加锁（按地址顺序）：** 对所有涉及的 channel 加锁（按 channel 地址排序，防止死锁）

2. **第一次遍历（按随机 pollorder）：** 检查每个 case 是否可以立即执行
   - send case：channel 有空间 / 有等待的接收者？
   - recv case：channel 有数据 / 有等待的发送者 / 已关闭？
   - 找到可就绪的 case → 立即执行并返回

3. **所有 case 未就绪：**
   - 有 `default` → 解锁，执行 default，返回 `-1`
   - 无 `default` → 将当前 goroutine 的 `sudog` 注册到所有 case 的 channel 等待队列中

4. **挂起等待：** `gopark()` 将当前 goroutine 变为 `_Gwaiting`

5. **被唤醒（某 channel 就绪）：**
   - 从其他 channel 的等待队列中移除未被选中的 `sudog`
   - 返回被选中的 case 索引

**公平性（随机化）：** `pollorder` 是对 case 索引的随机排列（通过 `cheaprand()`）。每次 `selectgo` 都生成新的随机顺序，确保多个就绪 case 时等概率选择，防止某个 case 始终被优先选中导致饥饿。

**Q12. 解释 Go interface 的 `iface` 和 `eface` 结构，以及接口方法调用的底层过程。**

**参考答案：**

**eface（空接口 `interface{}`）：**
```go
type eface struct {
    _type *_type         // 动态类型的类型描述符（nil if nil）
    data  unsafe.Pointer // 指向实际数据（值类型内联，引用类型为指针）
}
```

**iface（带方法的接口）：**
```go
type iface struct {
    tab  *itab          // 接口表（类型信息 + 方法指针表）
    data unsafe.Pointer // 指向实际数据
}

type itab struct {
    inter *interfacetype  // 接口类型描述符
    _type *_type           // 实现类型描述符
    hash  uint32           // 类型哈希（类型断言快速比较）
    _     [4]byte
    fun   [1]uintptr       // 方法指针数组（按接口方法定义顺序）
}
```

**接口方法调用汇编（伪代码）：**
```go
var a Animal = Dog{Name: "Rex"}
a.Speak()
// 编译后等价于:
itab := a.tab                 // 加载 itab 指针
speak_fn := itab.fun[0]       // 取第 0 个方法（Speak）的函数指针
receiver := a.data            // 加载接收者数据
speak_fn(receiver)            // 调用
```

**itab 缓存：** Go 运行时维护 `itabTable`（哈希表）缓存 `(interface_type, concrete_type) → *itab` 映射，第一次使用时计算并缓存，后续直接查表，避免重复计算方法指针。

**Q13. 描述 Goroutine 泄漏（Goroutine Leak）的常见场景和检测/修复方法。**

**参考答案：**

**Goroutine 泄漏：** 创建的 goroutine 由于某种原因永远无法退出，持续占用内存（每个 goroutine 至少 2KB 栈）和调度资源。

**常见泄漏场景：**

**场景 1：向无接收者的 channel 发送（死循环阻塞）**
```go
func leaky() {
    ch := make(chan int)
    go func() {
        ch <- 1  // 没有接收者，永远阻塞！
    }()
    // 函数返回，但 goroutine 永远在等待
}
```

**场景 2：从无发送者的 channel 接收**
```go
func leaky() {
    ch := make(chan int)
    go func() {
        v := <-ch  // 没有发送者，永远阻塞！
        _ = v
    }()
}
```

**场景 3：Context 未传递导致无法取消**
```go
func leaky(ctx context.Context) {
    go func() {
        // 没有使用 ctx，无法外部取消
        for {
            time.Sleep(time.Second)
        }
    }()
}
```

**检测方法：**

```go
// 1. 运行时检查
runtime.NumGoroutine()  // 监控 goroutine 数量趋势

// 2. pprof（最常用）
import _ "net/http/pprof"
// http://localhost:6060/debug/pprof/goroutine?debug=1 查看所有 goroutine 栈

// 3. goleak 测试库（golangci-lint 集成）
func TestXxx(t *testing.T) {
    defer goleak.VerifyNone(t)  // 测试结束后检查是否有新的 goroutine 泄漏
    // ...
}
```

**修复原则：** 所有 goroutine 必须有退出条件（context 取消 / done channel / 错误）。

**Q14. 解释 Go 栈的动态增长机制，以及 "hot split" 问题为何在 Go 1.4 后消失。**

**参考答案：**

**动态栈增长机制：**

编译器在每个函数入口插入栈溢出检查：
```asm
MOVQ SP, CX
CMPQ CX, stackguard0(goroutine)  ; SP < stackguard0 ?
JBE  morestack                   ; 是则调用 morestack
```

`morestack()` 流程：
1. 分配新栈（原大小 × 2）
2. 将整个旧栈内容复制到新栈
3. **指针重写**：扫描旧栈中所有指针，将指向旧栈地址的指针更新为新栈对应地址
4. 释放旧栈
5. 继续执行

**Go 1.3 之前：分段栈（Segmented Stacks）与 Hot Split 问题**

分段栈在需要更多空间时，分配**新的栈段**（链表形式），不复制，而是链接到旧段。

**Hot Split 问题：**
```
函数 foo() 调用 bar()：
  foo 的栈帧在旧段（快满）
  bar 的栈帧在新段
  每次 foo() 调用 bar() 时：
    - 分配新段（将当前段标记为 foo 的边界）
    - 调用 bar（在新段执行）
    - 返回到 foo（释放新段，回到旧段）
  如果这个调用在热循环中：频繁分配/释放栈段 → 严重性能抖动！
```

**Go 1.4 改为连续栈（Contiguous Stacks）：**
每次增长时完整复制整个栈到更大的连续内存，彻底消除跨段调用的开销。代价是偶尔的 O(n) 复制，但分摊下来仍比分段栈的频繁分配/释放好。

**Q15. 分析以下 Go 代码的问题并修复：**

```go
func processItems(items []int) []int {
    results := make([]int, 0)
    var mu sync.Mutex
    var wg sync.WaitGroup
    
    for _, item := range items {
        wg.Add(1)
        go func() {
            defer wg.Done()
            result := process(item)
            mu.Lock()
            results = append(results, result)
            mu.Unlock()
        }()
    }
    
    wg.Wait()
    return results
}
```

**参考答案：**

**问题：闭包捕获循环变量 `item`**

```go
for _, item := range items {
    go func() {
        result := process(item)  // 闭包捕获 item 的引用，不是值
    }()
}
```

`item` 在循环中被复用（同一个变量，值不断更新）。所有 goroutine 的闭包共享同一个 `item` 变量的引用，到执行时大多数 goroutine 读到的是循环结束时的最后一个值。

**修复方案：**

```go
// 方法1：参数传递（推荐，Go 1.22 之前的标准做法）
for _, item := range items {
    item := item  // 在循环体内重新声明，创建新变量（shadow）
    wg.Add(1)
    go func() {
        defer wg.Done()
        result := process(item)
        mu.Lock()
        results = append(results, result)
        mu.Unlock()
    }()
}

// 方法2：通过函数参数传递
for _, item := range items {
    wg.Add(1)
    go func(it int) {
        defer wg.Done()
        result := process(it)
        mu.Lock()
        results = append(results, result)
        mu.Unlock()
    }(item)  // 值传递
}

// 注意：Go 1.22 起，for 循环每次迭代创建新变量，自动修复此问题
```

**额外改进：使用 channel 替代 mutex 更符合 Go 风格**
```go
func processItems(items []int) []int {
    resultCh := make(chan int, len(items))
    var wg sync.WaitGroup
    
    for _, item := range items {
        item := item
        wg.Add(1)
        go func() {
            defer wg.Done()
            resultCh <- process(item)
        }()
    }
    
    go func() {
        wg.Wait()
        close(resultCh)
    }()
    
    var results []int
    for r := range resultCh {
        results = append(results, r)
    }
    return results
}
```

**Q16. 解释 Go 的 `sync.Map` 与带 `sync.Mutex` 的 `map` 的区别，以及 `sync.Map` 的适用场景。**

**参考答案：**

**`sync.Map` 内部结构：**

```go
type Map struct {
    mu     Mutex
    read   atomic.Value  // 存储 readOnly{m: map[any]*entry, amended: bool}
    dirty  map[any]*entry  // 包含最新数据的脏 map（加 mu 才能访问）
    misses int            // read miss 计数（超过阈值时将 dirty 提升为 read）
}
```

**`sync.Map` 的优化策略（适读多写少）：**

- **读操作（Load）：** 先无锁读取 `read` map（原子操作）→ 命中则直接返回，无锁竞争
- **写操作（Store/Delete）：** 加锁更新 `dirty` map
- **read 和 dirty 的同步：** 当 miss 次数 > dirty 长度时，将 `dirty` 提升为新 `read`（O(1)，只是原子赋值）

**vs `map + sync.Mutex`：**

| | `map + RWMutex` | `sync.Map` |
|--|-----------------|-----------|
| 实现 | 读取加 RLock，写入加 Lock | 读取无锁（原子），写入加锁 |
| 读并发 | 多读可并发（RLock）| 读完全无锁（更快）|
| 写并发 | 写排他 | 写加锁 |
| 迭代 | 需持锁 | `Range()` 不需要持锁 |

**`sync.Map` 适用场景（官方文档明确说明）：**
1. **读多写少**：key 一旦写入后基本只读（缓存场景）
2. **多 goroutine 读取不相交的 key 集合**：每个 goroutine 只写自己的 key

**不适合场景：** 频繁更新同一批 key（dirty map 频繁提升，开销不低）→ 此时 `map + RWMutex` 更简单高效。

**Q17. Go 程序如何处理 panic 和 recover？两者的底层机制是什么？**

**参考答案：**

**panic 机制：**

```go
// panic 在 src/runtime/panic.go 中实现
// gopanic():
// 1. 创建 _panic 结构体，加入 goroutine 的 _panic 链表（头插）
// 2. 遍历 goroutine 的 _defer 链表（LIFO 顺序执行 defer）
// 3. 如果某个 defer 调用了 recover（gorecover()），停止 panic 传播
// 4. 遍历完所有 defer 仍未 recover → 打印堆栈，goroutine 退出
//    → 若是主 goroutine 或所有 goroutine 退出 → 程序终止
```

**recover 机制：**

```go
// gorecover() 只在 defer 函数中直接调用时有效：
// 1. 检查当前是否在 panic 处理中（_panic 链表非空）
// 2. 将 _panic.recovered = true
// 3. 清除 panic，恢复正常执行（从 defer 之后继续）

func safeOp() (err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("recovered: %v", r)
        }
    }()
    // 可能 panic 的操作
    riskyOperation()
    return nil
}
```

**关键限制：**
- `recover()` 只能在**直接被 `defer` 调用的函数**中有效
- `defer func() { go func() { recover() }() }()` — **无效**（在子 goroutine 中 recover 无法捕获父 goroutine 的 panic）
- 每个 goroutine 的 panic 只能被同一 goroutine 中的 recover 捕获

**`_panic` 和 `_defer` 链表：** 每个 goroutine 结构体（`g`）包含 `_panic *_panic` 和 `_defer *_defer` 字段，分别维护活跃的 panic 和 defer 链。

**Q18. 如何分析和优化 Go 程序的内存分配？介绍 pprof 的使用方式。**

**参考答案：**

**常见内存问题：**
1. 频繁的小对象分配 → GC 压力大
2. 大对象或切片频繁扩容 → 内存碎片 / 不必要的复制
3. Goroutine 泄漏 → 内存持续增长
4. 缓存/数据结构不释放 → 内存泄漏

**pprof 内存分析：**

```go
// 方式 1：HTTP 服务（推荐生产环境）

go http.ListenAndServe(":6060", nil)

// 采样堆内存
go tool pprof http://localhost:6060/debug/pprof/heap

// 方式 2：代码中采集
import "runtime/pprof"
f, _ := os.Create("mem.prof")
pprof.WriteHeapProfile(f)

// 方式 3：测试中
go test -memprofile=mem.prof -bench=BenchmarkXxx
go tool pprof mem.prof
```

**pprof 关键命令：**
```
(pprof) top10          # 显示内存占用最多的 10 个函数
```
