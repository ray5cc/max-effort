## ⭐ 基础题

### Q1: 微服务架构相比单体架构有什么优势和劣势？

**面试官意图**：考察对微服务的全面理解，不只停留在优势层面。

**参考答案**：

**优势**：

| 方面 | 说明 |
|------|------|
| 独立部署 | 修改一个服务不影响其他服务，发布风险降低 |
| 独立扩缩容 | 热点服务（如商品搜索）可以单独扩容，而非整体扩容 |
| 技术多样性 | 不同服务可以选择最适合的语言和数据库 |
| 团队自治 | 小团队端到端负责，降低协作成本 |
| 故障隔离 | 一个服务崩溃不会（理论上）拖垮整个系统 |

**劣势**：

| 方面 | 说明 |
|------|------|
| 分布式复杂度 | 网络不可靠、分布式事务、数据一致性难保证 |
| 运维成本高 | 需要成熟的 CI/CD、监控、日志聚合、链路追踪基础设施 |
| 调试困难 | 一个请求跨越多个服务，定位问题链路长 |
| 数据一致性 | 无法使用单一数据库事务，需要 Saga 等最终一致性方案 |
| 团队能力要求高 | 需要 DevOps 文化、对分布式系统有深入理解 |

**关键结论**：微服务不是银弹，它将代码层面的复杂度转移到了运维层面。团队规模小（<20人）、业务不复杂时，Modular Monolith 通常是更好的选择。

### Q2: 如何进行服务拆分？DDD 的 Bounded Context 怎么指导拆分？

**面试官意图**：考察是否有方法论指导拆分，而不是拍脑袋。

**参考答案**：

服务拆分的核心方法论来自**领域驱动设计（DDD）**中的**限界上下文（Bounded Context）**——在同一个 Bounded Context 内的概念有一致的含义，跨上下文时同一个词可能有不同的含义。

**拆分四维度**：
1. **业务领域**：不同业务领域的功能拆分为不同服务（如用户 vs 订单）
2. **变更频率**：频繁变动的模块与稳定模块分离（如促销规则 vs 基础认证）
3. **团队边界**：一个团队能完整负责的范围作为一个服务
4. **数据边界**：数据归属明确且跨域访问少的模块拆分

**拆分示例（电商系统）**：

```
用户上下文 → 用户服务 (User Service)
商品上下文 → 商品服务 (Product Service)
订单上下文 → 订单服务 (Order Service)
支付上下文 → 支付服务 (Payment Service)
库存上下文 → 库存服务 (Inventory Service)
```

**反模式要提**：
- **过度拆分**：每个 CRUD 一个服务 → 网络开销爆炸
- **分布式单体**：服务间高度耦合，改一个要同时改多个
- **共享数据库**：破坏自治性，本质上还是单体

### Q3: REST 和 gRPC 的区别是什么？各自适用什么场景？

**面试官意图**：考察对服务间通信协议的理解和选型能力。

**参考答案**：

| 维度 | REST | gRPC |
|------|------|------|
| 协议 | HTTP/1.1 (通常) | HTTP/2 |
| 数据格式 | JSON（文本） | Protocol Buffers（二进制） |
| 性能 | 一般 | 高（序列化速度快 5-10x，体积小） |
| 类型安全 | 弱（需额外 JSON Schema 约束） | 强（.proto IDL 自动生成代码） |
| 流式通信 | 不原生支持（需 SSE/WebSocket） | 原生支持（服务端流/客户端流/双向流） |
| 浏览器兼容 | 天然兼容 | 需要 gRPC-Web 代理 |
| 可读性 | 高（JSON 人类可读） | 低（二进制需反序列化） |

**选型建议**：
- **REST**：对外 API（给前端/第三方）、简单 CRUD、快速原型
- **gRPC**：内部服务间通信（高性能/强类型）、需要流式通信的场景

```protobuf
// gRPC 接口定义示例
service OrderService {
  rpc CreateOrder (CreateOrderRequest) returns (Order);
  rpc StreamOrderUpdates (OrderQuery) returns (stream OrderUpdate);
}
```

### Q4: 服务注册与发现是什么？有哪些常见方案？

**面试官意图**：考察对微服务基础设施的理解。

**参考答案**：

微服务实例的 IP 和端口是动态的（容器重启、弹性伸缩），不能硬编码。**服务发现**解决"如何找到目标服务的地址"的问题。

**两种模式**：
- **客户端发现**：调用方从注册中心获取实例列表，自己做负载均衡（如 Consul + 客户端 SDK）
- **服务端发现**：调用方请求负载均衡器，由它转发到实际实例（如 K8s Service + kube-proxy）

**常见注册中心**：

| 方案 | 一致性 | 特点 |
|------|--------|------|
| Consul | CP (Raft) | 多数据中心、内置健康检查 |
| etcd | CP (Raft) | K8s 底层存储、强一致性 |
| Nacos | CP+AP | 配置中心 + 注册中心二合一 |
| K8s Service | DNS | 原生集成、零额外运维成本 |

**生产实践**：在 K8s 环境中，通常直接使用 K8s Service（通过 DNS 或 ClusterIP），无需额外部署注册中心。

### Q5: API 网关在微服务中起什么作用？

**面试官意图**：考察对微服务入口层的理解。

**参考答案**：

API 网关是微服务架构的统一入口，所有外部请求都通过网关转发到后端服务。

**核心职责**：
1. **路由**：根据 URL 路径分发请求到对应服务
2. **认证/鉴权**：统一验证 JWT/OAuth Token
3. **限流/熔断**：保护后端服务不被流量压垮
4. **协议转换**：HTTP → gRPC（前端用 REST，内部用 gRPC）
5. **请求聚合**：将多个服务的响应合并为一个（减少前端请求次数）
6. **日志/监控**：统一的请求日志和指标收集

**常见方案**：Kong（插件丰富）、APISIX（高性能、国产）、Spring Cloud Gateway（Java 生态）、Envoy（Service Mesh 数据面）

**BFF 模式补充**：不同客户端（Web/App/小程序）的需求不同，可以为每类端创建独立的 BFF 层在网关后面做数据聚合和裁剪。

### Q6: CAP 定理在微服务架构中如何体现？

**面试官意图**：考察对分布式系统理论基础的理解。

**参考答案**：

**CAP 定理**：在网络分区（P）发生时，分布式系统只能在一致性（C）和可用性（A）之间二选一。

在微服务中：
- **CP 场景**：支付服务选择 CP——宁可暂时不可用，也不能出现"扣款成功但订单失败"的不一致
- **AP 场景**：商品展示服务选择 AP——即使数据可能稍有延迟（缓存旧价格），也要保证用户能正常浏览

**实际应用**：
- 注册中心选型：Consul/etcd 偏 CP（强一致），Eureka 偏 AP（高可用）
- 数据库策略：核心交易用强一致性（同步等待），非核心业务用最终一致性（异步事件）
- 缓存策略：Cache-Aside 模式下，短暂的缓存与数据库不一致是可接受的（AP）

> **关键点**：CAP 是在网络分区时的权衡，正常情况下可以同时满足 C 和 A。实际设计中更常用的是 **BASE 理论**（Basically Available, Soft State, Eventually Consistent）。

### Q7: 微服务架构中每个服务一个数据库的策略有什么好处和挑战？

**面试官意图**：考察对 Database per Service 模式的理解。

**参考答案**：

**好处**：
- **松耦合**：一个服务的数据库 Schema 变更不影响其他服务
- **技术多样性**：用户服务用 PostgreSQL，搜索服务用 Elasticsearch，缓存用 Redis
- **独立扩缩容**：热点服务的数据库可以独立做读写分离

**挑战**：
- **数据一致性**：无法用数据库事务保证跨服务一致性，需要 Saga 模式
- **跨服务查询困难**：以前一个 JOIN 就能搞定的查询，现在需要 API 组合
- **数据冗余**：不同服务可能存储同一实体的不同视角（如订单服务和库存服务都有商品 ID）

**跨服务查询的解决方案**：
1. **API 组合模式**：由 API 网关或 BFF 调用多个服务并组合结果
2. **CQRS + 事件**：写入各自数据库，通过事件同步到统一的读模型（比如数据仓库）
3. **数据湖/数据仓库**：ETL 汇总到中心化的查询数据库

### Q8: 什么是幂等性？微服务中为什么特别重要？

**面试官意图**：考察对分布式系统中幂等性的重要理解。

**参考答案**：

**幂等性**：同一个操作执行一次和执行多次的结果完全相同。数学表达：$f(f(x)) = f(x)$。

**为什么在微服务中特别重要**？因为网络不可靠——请求可能因为超时被重试，一条消息可能被重复投递。如果操作不是幂等的，重试就会产生副作用。

**示例**：
- ❌ 非幂等：`POST /account/balance/add?amount=100`（重试两次就加了 200）
- ✅ 幂等：`PUT /account/balance/set?amount=1100`（重试多少次结果一样）

**实现幂等的常见方法**：

| 方法 | 说明 | 适用场景 |
|------|------|---------|
| **唯一请求 ID** | 客户端生成唯一 ID，服务端去重 | 支付、下单 |
| **乐观锁（版本号）** | 更新时带上版本号，版本不匹配则拒绝 | 库存扣减 |
| **数据库唯一约束** | 利用唯一索引防止重复插入 | 创建订单 |
| **状态机** | 只允许合法的状态转换 | 订单状态流转 |

```sql
-- 利用唯一约束保证幂等：重复插入同一 idempotency_key 会报错
INSERT INTO payments (idempotency_key, user_id, amount, status)
VALUES ('pay-abc-123', 'user-1', 100.00, 'PENDING')
ON CONFLICT (idempotency_key) DO NOTHING;
```

### Q9: 微服务之间如何进行安全认证？

**面试官意图**：考察服务间通信安全方案。

**参考答案**：

**外部→网关认证**：
- **JWT（JSON Web Token）**：客户端登录获取 JWT，每次请求在 Header 中携带。网关验证签名和过期时间后转发给后端服务。

**服务间认证（内部通信）**：
- **mTLS（双向 TLS）**：服务之间使用证书互相验证身份。Service Mesh（如 Istio）可以自动管理证书的签发和轮换，应用无感知。

```
[外部客户端]                           [服务间通信]

Client → JWT Token → API Gateway      Service A ←mTLS→ Service B
                   ↓ 验证JWT           (Envoy 自动处理证书)
              用户服务/订单服务
```

**最佳实践**：
- 外部用 JWT + OAuth 2.0 / OIDC
- 内部用 mTLS（Service Mesh 零信任网络）
- API 网关统一鉴权，后端服务只信任经过网关验证的请求
- 敏感操作（如支付）增加额外的服务间签名验证

### Q10: 微服务的 12-Factor 原则是什么？

**面试官意图**：考察对云原生应用开发最佳实践的了解。

**参考答案**：

**12-Factor App** 是 Heroku 联合创始人提出的云原生应用开发方法论，特别适合微服务：

| # | 因素 | 微服务中的实践 |
|---|------|--------------|
| 1 | 代码基 (Codebase) | 每个服务一个独立代码仓库 |
| 2 | 依赖 (Dependencies) | 显式声明依赖（go.mod / requirements.txt） |
| 3 | 配置 (Config) | 配置通过环境变量注入，不硬编码 |
| 4 | 后端服务 (Backing Services) | 数据库/缓存/消息队列视为可替换的附加资源 |
| 5 | 构建/发布/运行 (Build, Release, Run) | CI 构建镜像 → CD 发布 → K8s 运行 |
| 6 | 进程 (Processes) | 无状态进程（状态存数据库/缓存） |
| 7 | 端口绑定 (Port Binding) | 每个服务自包含 HTTP Server |
| 8 | 并发 (Concurrency) | 通过水平扩展进程（Pod 副本数） |
| 9 | 易处置性 (Disposability) | 快速启动、优雅关闭 |
| 10 | 开发/生产一致 (Dev/Prod Parity) | Docker 保证环境一致 |
| 11 | 日志 (Logs) | 日志输出到 stdout，由日志聚合平台收集 |
| 12 | 管理进程 (Admin Processes) | 数据库迁移等运维任务作为一次性进程运行 |

> 关键补充：12-Factor 已有多年历史，2026 年还应关注 **Beyond 12-Factor**，如可观测性（观测三支柱）、安全（零信任）、API 优先设计、GitOps 发布流程。

## ⭐⭐ 进阶题

### Q11: 详细讲解 Saga 模式的两种实现方式——编排型和协调型。

**面试官意图**：考察对分布式事务解决方案的深入理解。

**参考答案**：

Saga 模式将一个长事务拆分为多个本地事务，每个本地事务都有对应的补偿操作。

**编排型 Saga (Orchestration)**：

由一个中心协调器（Saga Orchestrator）来调度所有步骤：

```
[Saga 协调器]
    ├── ① create_order()     → [订单服务] → OK
    ├── ② deduct_stock()     → [库存服务] → OK
    ├── ③ charge_payment()   → [支付服务] → FAIL ❌
    ├── ④ compensate_stock() → [库存服务] → 恢复库存
    └── ⑤ cancel_order()     → [订单服务] → 取消订单
```

- **优点**：流程集中，容易理解和调试；补偿逻辑清晰
- **缺点**：协调器可能成为单点；协调器逻辑可能膨胀

**协调型 Saga (Choreography)**：

没有中心协调器，各服务通过发布/订阅事件"接力"：

```
订单服务 发布 OrderCreated
   → 库存服务 消费 → 扣库存 → 发布 StockDeducted
      → 支付服务 消费 → 扣款失败 → 发布 PaymentFailed
         → 库存服务 消费 → 恢复库存 → 发布 StockRestored
            → 订单服务 消费 → 取消订单
```

- **优点**：去中心化，松耦合；没有单点
- **缺点**：流程分散在各服务中，全局流程难以理解和调试；增加新步骤需要修改多个服务

**选型建议**：
- 步骤 ≤ 4 步、参与服务少：协调型
- 步骤多、流程复杂、需要清晰版本管理：编排型

### Q12: 断路器的三种状态是如何工作的？如何配置？

**面试官意图**：考察对容错模式的细节理解。

**参考答案**：

断路器（Circuit Breaker）防止一个失败的服务拖垮调用方。三个状态：

```
┌─────────┐  失败率>阈值  ┌──────┐  超时后  ┌──────────┐
│ Closed  │ ──────────→ │ Open │ ──────→ │Half-Open │
│ (正常)   │              │(熔断) │         │(试探)     │
└────┬────┘              └──┬───┘         └─────┬────┘
     │                      │                    │
     └── 成功 ←─────── 试探成功 ────────────────┘
                        试探失败 → 回到 Open
```

**状态详解**：

| 状态 | 行为 | 转换条件 |
|------|------|---------|
| **Closed** | 正常转发请求，同时统计失败率 | 失败率 > 阈值（如 50%）→ Open |
| **Open** | 快速失败（立即返回降级响应，不调用后端） | 等待超时（如 30s）→ Half-Open |
| **Half-Open** | 放入少量请求（如 5 个）测试后端是否恢复 | 成功率高 → Closed；仍然失败 → Open |

**关键配置项**：
- `failureRateThreshold`: 失败率阈值（如 50%）
- `slidingWindowSize`: 统计窗口大小（如最近 100 个请求）
- `waitDurationInOpenState`: Open 状态等待时间（如 30 秒）
- `permittedNumberOfCallsInHalfOpenState`: Half-Open 状态允许通过的请求数

**降级策略**：Open 状态下返回什么？
- 缓存数据（上次正常响应）
- 默认值
- 友好的错误信息

### Q13: 分布式追踪是如何实现的？OpenTelemetry 的工作原理是什么？

**面试官意图**：考察对可观测性基础设施的理解。

**参考答案**：

**核心概念**：
- **Trace**：一个请求的完整调用链（由一个 TraceID 标识）
- **Span**：Trace 中的一个操作单元（一次 RPC 调用、一次数据库查询）
- **Context Propagation**：在服务间传递 TraceID 和 SpanID（通过 HTTP Header 或 gRPC Metadata）

```
Trace: abc-123
├── Span 1: API Gateway (0ms - 100ms)
│   ├── Span 2: Auth Service (5ms - 20ms)
│   └── Span 3: Order Service (25ms - 95ms)
│       ├── Span 4: DB Query (30ms - 45ms)
│       └── Span 5: Payment Service (50ms - 90ms)  ← 瓶颈！
```

**OpenTelemetry 工作流**：

```
┌──────────┐   ┌──────────────────┐   ┌─────────────┐
│ 应用代码  │ → │  OTel SDK        │ → │ OTel        │ → Jaeger (Tracing)
│ (自动埋点)│   │  (Tracer/Meter/  │   │ Collector   │ → Prometheus (Metrics)
│          │   │   Logger Provider)│   │ (接收/处理/  │ → Loki (Logging)
└──────────┘   └──────────────────┘   │  导出)       │
                                      └─────────────┘
```

**Context 传播（HTTP Header）**：
```
traceparent: 00-abc123-span456-01
tracestate: vendor=value
```

**关键点**：OpenTelemetry 统一了三大可观测信号（Traces/Metrics/Logs）的 API 和数据格式，替代了之前各自独立的 Jaeger SDK、Prometheus SDK 等。

### Q14: 如何保证微服务间消息的最终一致性？

**面试官意图**：考察对消息可靠性和一致性的理解。

**参考答案**：

**问题根源**：服务 A 修改了本地数据库后发消息给 Kafka，但如果发消息失败了怎么办？本地事务成功 + 消息发送不是原子的。

**解决方案**：

**方案一：Transactional Outbox（事务性发件箱）**

将消息写入本地数据库的 outbox 表（与业务操作在同一个事务中），再由独立进程轮询 outbox 表发送到消息队列。

```
BEGIN TRANSACTION;
  INSERT INTO orders (id, ...) VALUES (...);             -- 业务操作
  INSERT INTO outbox (id, topic, payload) VALUES (...);  -- 消息写入同一事务
COMMIT;

-- 独立进程（Debezium CDC / 定时轮询）
-- 读取 outbox 表未发送的记录 → 发到 Kafka → 标记已发送
```

**方案二：CDC (Change Data Capture)**

使用 Debezium 监听数据库 binlog，将数据变更自动发布到 Kafka。无需修改业务代码。

**方案三：消费端幂等**

即使消息重复投递，消费端保证处理结果幂等：
- 唯一消息 ID + 去重表
- 数据库唯一约束
- 乐观锁版本号

### Q15: 四种限流算法的原理和适用场景分别是什么？

**面试官意图**：考察对限流实现细节的理解。

**参考答案**：

**1. 令牌桶 (Token Bucket)**

固定速率向桶中放入令牌，请求到来时消耗一个令牌。桶满时多余令牌丢弃。

```
速率: 10 token/s, 桶容量: 50
┌───────────────┐
│ 🪙🪙🪙🪙🪙... │ ← 10个/秒匀速放入
│ (最多50个)    │
└──────┬────────┘
       │ 取走1个token
    [请求]
```

- ✅ **允许突发**：桶满时可以一次消耗 50 个令牌（短暂突发）
- 适用：API 网关限流（允许短时突发但控制平均速率）

**2. 漏桶 (Leaky Bucket)**

请求进入桶中排队，以固定速率匀速流出。桶满则拒绝。

- ❌ 不允许突发，严格匀速
- 适用：流量整形、保护下游

**3. 固定窗口 (Fixed Window)**

将时间划分为固定长度的窗口（如每分钟），窗口内计数。

- ⚠️ **窗口边界突刺问题**：窗口末尾 50 个请求 + 下个窗口开头 50 个请求 = 100 个请求集中在 1 秒内
- 适用：简单场景，精度要求不高

**4. 滑动窗口 (Sliding Window)**

结合固定窗口和滑动日志的优点，按比例计算当前窗口和上一个窗口的请求数。

- ✅ 解决了固定窗口的边界突刺问题
- 适用：精确限流

| 算法 | 允许突发 | 精度 | 实现复杂度 | 代表实现 |
|------|---------|------|-----------|---------|
| 令牌桶 | ✅ | 高 | 中 | Guava RateLimiter |
| 漏桶 | ❌ | 高 | 中 | Nginx limit_req |
| 固定窗口 | ⚠️ 边界突刺 | 低 | 低 | Redis INCR + EXPIRE |
| 滑动窗口 | ✅ | 高 | 中 | Redis Sorted Set |

### Q16: 如何处理微服务中的分布式事务？

**面试官意图**：考察对分布式事务解决方案全貌的理解。

**参考答案**：

分布式事务的几种方案对比：

| 方案 | 原理 | 一致性 | 性能 | 适用场景 |
|------|------|--------|------|---------|
| **2PC** | 协调者两阶段提交（Prepare + Commit） | 强一致 | 低（阻塞） | 传统数据库分布式事务 |
| **TCC** | Try-Confirm-Cancel 三阶段 | 强一致 | 中 | 金融等强一致场景 |
| **Saga** | 本地事务 + 补偿 | 最终一致 | 高 | 微服务主流方案 |
| **Outbox + CDC** | 本地事务写 outbox + 异步发消息 | 最终一致 | 高 | 消息驱动型微服务 |

**微服务中的推荐优先级**：
1. **首选**：尽量设计为不需要分布式事务（业务上容忍最终一致）
2. **常用**：Saga 模式（编排型/协调型）
3. **可靠消息**：Transactional Outbox + CDC
4. **特殊场景**：TCC（需要强一致时）
5. **避免**：2PC（性能差、可用性低，微服务中几乎不用）

### Q17: CQRS 和 Event Sourcing 是什么？它们如何配合使用？

**面试官意图**：考察对高级架构模式的理解。

**参考答案**：

**CQRS (Command Query Responsibility Segregation)**：
- **Command（写）**：处理创建/更新/删除操作
- **Query（读）**：处理查询操作
- 核心思想：读和写的模型分离，各自优化

**Event Sourcing（事件溯源）**：
- 不存储当前状态，而是存储所有状态变更事件
- 当前状态 = replay(all events)
- 类比：Git 存储的是每次 commit（diff），而不是文件快照

```
写路径:
  Command → Validate → Append Event to Event Store
           ("OrderCreated", "ItemAdded", "OrderPaid")

读路径:
  Event Store → Projection → Materialized View → Query
  (事件流)       (投影器)      (物化视图/读库)     (查询)
```

**配合方式**：
1. 写端使用 Event Sourcing 存事件
2. 事件通过投影器（Projector）消费，更新为读优化的物化视图
3. 读端直接查询物化视图

**适用场景**：审计日志要求高（金融）、需要时间旅行（回溯到任意时间点的状态）、高读写比且读写性能要求差异大的系统。

**注意**：CQRS + Event Sourcing 引入很高的复杂度，不适合简单的 CRUD 应用。

### Q18: 微服务中 per-service 数据库后，跨服务 JOIN 怎么解决？

**面试官意图**：考察对数据分散后的查询方案理解。

**参考答案**：

**问题**：单体时一个 SQL JOIN 就能关联用户表和订单表。微服务后，用户数据在用户服务的 PostgreSQL，订单数据在订单服务的 MongoDB，无法 JOIN。

**解决方案**：

**方案一：API Composition（API 组合）**

由 BFF 或 API 网关调用多个服务，在内存中组合结果：

```
BFF/API Gateway:
  users = userService.getUsers(ids)
  orders = orderService.getOrdersByUserIds(ids)
  return merge(users, orders)  // 内存中关联
```

- ✅ 实现简单
- ❌ 数据量大时性能差（N+1 调用问题）

**方案二：CQRS + Event（事件驱动的读模型）**

各服务通过事件将变更同步到统一的读数据库（如 Elasticsearch），由读模型支持复杂查询：

```
用户服务 → UserUpdated → [Kafka] → [Read DB 投影器] → Elasticsearch
订单服务 → OrderCreated →                              (宽表/聚合视图)
```

- ✅ 查询性能好（预计算的物化视图）
- ❌ 实时性有延迟、维护投影器成本

**方案三：数据仓库 (Data Warehouse)**

各服务数据通过 ETL 定期汇总到数据仓库（如 BigQuery/ClickHouse），供分析查询使用：

- ✅ 适合报表、分析类查询
- ❌ 不适合实时在线查询

**选型建议**：在线查询用 API Composition（简单场景）或 CQRS（复杂场景）；离线分析用数据仓库。

### Q19: 详细解释 Service Mesh 的原理。Istio 和 Envoy 是如何配合的？

**面试官意图**：考察对服务网格架构的深入理解。

**参考答案**：

**Service Mesh 架构**由两部分组成：

**数据面 (Data Plane) — Envoy**：
- 以 Sidecar 方式部署在每个服务 Pod 中
- 拦截所有进出流量
- 执行负载均衡、重试、超时、熔断、mTLS 加密

**控制面 (Control Plane) — Istiod**：
- 管理和配置所有 Envoy Sidecar
- 包含三个核心组件（已合并为 Istiod）：
  - **Pilot**：将路由规则下发给 Envoy（xDS API）
  - **Citadel**：管理证书（自动签发和轮换 mTLS 证书）
  - **Galley**：配置验证和分发

```
┌───── Pod A ──────┐     ┌───── Pod B ──────┐
│ ┌─────┐ ┌──────┐│     │┌──────┐ ┌─────┐ │
│ │App A│↔│Envoy ││←───→││Envoy │↔│App B│ │
│ └─────┘ └──┬───┘│     │└──┬───┘ └─────┘ │
└────────────┼────┘     └───┼──────────────┘
             │ xDS          │ xDS
         ┌───▼──────────────▼───┐
         │       Istiod         │
         │ (Pilot+Citadel+      │
         │  Galley)             │
         └──────────────────────┘
```

**流量管理示例（金丝雀发布）**：

```yaml
# VirtualService: 90% → v1, 10% → v2
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: order-service
spec:
  hosts: [order-service]
  http:
    - route:
        - destination: { host: order-service, subset: v1 }
          weight: 90
        - destination: { host: order-service, subset: v2 }
          weight: 10
```

**与传统库的对比**：
- Hystrix/Ribbon 需要在代码中引入 SDK，只支持 Java
- Service Mesh 语言无关，升级只需更新 Sidecar，但增加了约 1-2ms 的延迟和运维复杂度

### Q20: 微服务如何做灰度发布（金丝雀发布）？

**面试官意图**：考察发布策略的实际操作能力。

**参考答案**：

**金丝雀发布**：先将少量流量（如 5%）导向新版本，观察指标正常后逐步增大比例，最终全量切换。

**实现方式**：

**方式一：K8s + Ingress（简单）**

部署两个 Deployment（v1 和 v2），通过 Ingress 的 canary annotation 分流：

```yaml
# Canary Ingress
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: order-canary
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "10"  # 10% 流量
```

**方式二：Istio VirtualService（精细）**

支持基于权重、Header、Cookie 等多维度分流：

```yaml
# 基于 Header 分流（仅内测用户走 v2）
http:
  - match:
      - headers:
          x-canary:
            exact: "true"
    route:
      - destination: { host: order-service, subset: v2 }
  - route:
      - destination: { host: order-service, subset: v1 }
```

**方式三：Argo Rollouts（自动化）**

定义完整的灰度策略，自动根据指标推进或回滚：

```yaml
strategy:
  canary:
    steps:
      - setWeight: 5
      - pause: { duration: 5m }   # 观察 5 分钟
      - setWeight: 20
      - pause: { duration: 10m }
      - setWeight: 50
      - pause: { duration: 10m }
```

**关键监控指标**：
- 错误率（新版本 vs 旧版本）
- p99 延迟
- 业务指标（转化率、下单量等）

如果新版本的指标异常，自动回滚到旧版本。

### Q21: 如何设计一个高可用的微服务架构？

**面试官意图**：考察架构设计的综合能力。

**参考答案**：

高可用微服务架构需要在多个层面做设计：

**1. 服务层**：

- 限流保护核心服务

**3. 数据层**：
- 数据库主从复制（至少 1 主 1 从）
- 跨可用区部署
- 定时备份 + 定期恢复演练

**4. 基础设施层**：
- 多可用区（AZ）部署，容忍单 AZ 故障
- CDN + 全球负载均衡
- 基础设施即代码（Terraform），随时可重建

**5. 可观测性层**：
- 全链路追踪（OpenTelemetry + Jaeger）

- 故障自愈（K8s HPA + PDB + 自动重启）

|-----|-----------|------|
| 99.9% | ~8.7 小时 | 单机房冗余 |
| 99.99% | ~52 分钟 | 多可用区 + 自动故障转移 |
| 99.999% | ~5 分钟 | 多区域 + 全球负载均衡 |

### Q22: 微服务的测试策略是什么？Contract Test 是什么？

**面试官意图**：考察对微服务测试方法论的理解。

**参考答案**：

微服务的测试策略遵循**测试金字塔**：

```
        △  少    E2E 测试（端到端）
       ╱ ╲       集成测试 / Contract 测试
      ╱   ╲      
     ╱     ╲     单元测试
    ▔▔▔▔▔▔▔  多
```

**各层测试**：

| 层级 | 范围 | 工具 | 速度 |
|------|------|------|------|
| 单元测试 | 单个函数/类 | JUnit/pytest/go test | 极快 |
| 集成测试 | 服务 + 数据库 / 外部依赖 | Testcontainers | 中等 |
| **契约测试** | 服务间接口契约 | Pact / Spring Cloud Contract | 快 |
| E2E 测试 | 整个系统 | Playwright/Cypress | 慢 |

**Contract Test（契约测试）详解**：

解决的问题：服务 A 调用服务 B 的 API，如何保证 B 的接口变更不会破坏 A？

```
Provider (服务 B)          Consumer (服务 A)
     │                          │
     │  ← 契约文件 (Pact) →      │
     │                          │
     ▼                          ▼
验证：我的 API 是否          生成：我期望的请求
满足契约中的约定？            和响应是什么样的？
```

- **Consumer 端**：编写测试描述"我期望调用 GET /users/123 返回 {id, name, email}"
- **Provider 端**：运行契约验证，确认实际 API 满足消费者的期望

**优势**：不需要启动所有服务就能验证服务间接口兼容性，比 E2E 测试快得多。

### Q23: 如何从单体迁移到微服务？

**面试官意图**：考察实际迁移经验和方法论。

**参考答案**：

**绞杀者无花果模式（Strangler Fig Pattern）**——不是一次性重写，而是逐步将单体功能迁移到微服务，新旧系统并行运行。

```
阶段 1:                    阶段 2:                    阶段 3:
[单体]                     [单体(缩小)]               [微服务集群]
 ├── 用户模块              [API 网关]                 [API 网关]
 ├── 商品模块   →           ├── 用户微服务    →         ├── 用户微服务
 ├── 订单模块               ├── 商品微服务              ├── 商品微服务
 └── 支付模块               └── [单体]                 ├── 订单微服务
                                ├── 订单模块             └── 支付微服务
                                └── 支付模块
```

**迁移步骤**：

1. **添加 API 网关**：在单体前面加 API 网关（或反向代理），所有请求先经过网关
2. **识别边界**：用 DDD 方法识别 Bounded Context
3. **先拆最独立的**：找耦合度最低的模块先拆（比如通知服务、用户服务）
4. **数据双写过渡**：迁移期间新旧系统双写，验证数据一致后切换
5. **逐步切流**：通过网关路由规则逐步将流量从单体切到新微服务
6. **废弃旧代码**：确认微服务稳定后，从单体中删除对应模块

**关键原则**：
- **禁止大爆炸重写**：渐进式迁移，每次只迁一个模块
- **保持旧系统运行**：新旧并行期间，旧系统作为兜底
- **数据迁移最难**：优先用事件驱动同步数据，避免直接操作数据库

### Q25: 设计一个电商下单流程（涉及订单/库存/支付服务）

**面试官意图**：考察微服务架构的实际设计能力。

**参考答案**：

**需求**：用户下单 → 扣库存 → 扣款 → 确认订单。任何步骤失败都要回滚。

**架构方案**：使用编排型 Saga + 消息队列

```
[用户] → [API 网关] → [订单服务]
                        │
                   [Saga 协调器]
                        │
         ┌──────────────┼──────────────┐
         ▼              ▼              ▼
    [库存服务]      [支付服务]     [通知服务]
    (Redis预扣)    (支付网关)     (异步通知)
```

**流程设计**：

```
正向流程:
1. 订单服务创建订单(PENDING) + 写 outbox event
2. Saga 协调器消费 OrderCreated → 调用库存服务
3. 库存服务预扣库存(Redis 原子操作) → StockReserved
4. Saga 消费 StockReserved → 调用支付服务
5. 支付服务发起扣款 → PaymentCompleted
6. Saga 消费 PaymentCompleted → 订单确认(CONFIRMED)
7. 异步通知用户

补偿流程(支付失败):
5'. PaymentFailed → 恢复库存 → 取消订单(CANCELLED)
```

**关键设计点**：
- **幂等性**：每个操作都用幂等键（订单 ID）保证重试安全
- **超时处理**：每步设置超时（如库存扣减 3s），超时触发补偿
- **库存防超卖**：Redis `DECRBY` 原子操作 + Lua 脚本判断库存是否充足
- **支付异步回调**：支付结果通过回调通知，不轮询（防止延迟和资源浪费）

```lua
-- Redis Lua 脚本：原子扣减库存
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock >= tonumber(ARGV[1]) then
    redis.call('DECRBY', KEYS[1], ARGV[1])
    return 1  -- 成功
else
    return 0  -- 库存不足
end
```

### Q26: 微服务调用链路延迟突增（P99 从 50ms 飙到 2s），如何排查？

**面试官意图**：考察线上问题排查能力。

**参考答案**：

**排查思路——从全局到局部，从表象到根因**：

**Step 1：全局确认**
- 看 Grafana Dashboard：哪个服务的延迟突增？是全部还是特定服务？
- 看时间线：与什么事件相关（发布？流量突增？）

**Step 2：链路追踪定位**
- Jaeger 查看慢请求的 Trace：找到延迟最高的 Span
- 例如：发现 Order Service → Payment Service 的调用从 10ms 变成 1.5s

**Step 3：定位目标服务**
- Payment Service 自身延迟高？还是它依赖的下游（数据库/第三方支付）慢？
- 查看 Payment Service 的 RED 指标：
  - 请求量是否暴增？（限流问题）
  - 错误率是否升高？（服务异常）
  - 资源使用（CPU/内存/连接池）是否饱和？

**Step 4：排查资源瓶颈**
```
常见根因清单:
1. 数据库慢查询（缺索引/锁等待/连接池耗尽）
2. GC 风暴（Java Full GC / Go STW）
3. 连接池耗尽（HTTP 连接池/数据库连接池）
4. 线程池满（请求排队等待）
5. 网络抖动（跨 AZ 延迟/DNS 解析慢）
6. 下游服务超时（第三方支付网关响应慢）
7. 限流/熔断触发（请求被排队或拒绝）
```

**Step 5：确认根因并修复**
- 临时措施：限流/降级/扩容/重启
- 根因修复：加索引/调整连接池/修复内存泄漏/优化 GC

**追问方向**：如果是间歇性延迟突增怎么排查？（可能是 GC 导致的 STW、网络抖动）

### Q27: 发生服务雪崩时如何应急处理？

**面试官意图**：考察应急响应能力和容错架构理解。

**参考答案**：

**雪崩场景**：一个底层服务（如数据库）变慢 → 调用方线程池被占满 → 调用方也变慢 → 上游的上游也被拖死 → 整个系统级联崩溃。

**应急处理（按优先级）**：

**第一步：隔离和止血（5 分钟内）**
- 触发故障服务的断路器：对故障服务直接熔断，返回降级响应
- 限流：降低到核心流量入口的允许速率
- 快速扩容：如果是流量导致的，紧急扩容 Pod 副本数

**第二步：降级非核心功能**
- 关闭推荐、评论、个性化等非核心服务
- 核心链路（下单/支付）保持最小可用
- 静态兜底页（CDN 缓存的备用页面）

**第三步：定位根因**
- Jaeger 查链路：哪个环节开始变慢
- 资源检查：CPU/内存/连接池/数据库连接
- 最近变更：是否有新版本发布

**第四步：恢复**
- 修复根因后，逐步恢复流量（不要一次全开）
- 逐步关闭降级开关
- 密切关注指标 30 分钟

**预防措施（架构层面）**：
- **所有服务配置断路器**（Resilience4j / Istio）
- **设置合理超时**（每个外部调用必须有 timeout）
- **隔舱模式**（不同调用使用不同的线程池/连接池）
- **定期混沌工程演练**（Chaos Monkey / LitmusChaos）

### Q28: 设计一个支持百万级用户的微服务架构

**面试官意图**：考察大规模系统的架构设计综合能力。

**参考答案**：

**需求明确**：百万级日活用户的电商平台，峰值 QPS ~5万，支持秒杀场景。

**整体架构**：

```
               ┌─────────────┐
[用户] ──CDN──→│  全球负载均衡  │
               │ (Cloudflare) │
               └──────┬──────┘
                      │
               ┌──────▼──────┐
               │  API Gateway │
               │ (Kong/APISIX) │
               │ 认证/限流/路由 │
               └──────┬──────┘
                      │
    ┌─────────────────┼──────────────────┐
    │                 │                  │
┌───▼───┐      ┌─────▼─────┐     ┌──────▼─────┐
│用户服务│      │ 商品服务    │     │  订单服务   │
│(3 Pod)│      │(5 Pod+CDN) │     │(10 Pod)    │
│ PG    │      │  PG+ES     │     │  PG+Redis  │
└───────┘      └────────────┘     └────────────┘
    │                 │                  │
    └─────────── Kafka 集群 ────────────┘
                      │
    ┌─────────────────┼──────────────────┐
┌───▼───┐      ┌─────▼─────┐     ┌──────▼─────┐
│支付服务│      │ 库存服务    │     │  通知服务   │
│(3 Pod)│      │(5 Pod)    │     │(3 Pod)     │
│ PG    │      │ Redis+PG  │     │  Redis     │
└───────┘      └────────────┘     └────────────┘
```

**关键设计点**：

**1. 接入层**：
- CDN 缓存静态资源和商品详情页
- API 网关限流（令牌桶，每用户 100 req/s）
- DDoS 防护（Cloudflare/AWS Shield）

**2. 服务层**：
- 无状态设计，K8s HPA 自动扩缩容
- 核心服务（订单/支付）至少 3 副本，跨 AZ 部署
- gRPC 内部通信 + REST 外部 API

**3. 数据层**：
- 读写分离：主库写，从库读（1 主 2 从）
- 热点数据 Redis 缓存（商品详情 TTL 5分钟）
- 库存预扣减 Redis 原子操作

**4. 秒杀场景专项**：
- 前端：按钮倒计时 + 请求排队（避免同一时刻海量请求）
- 网关：秒杀接口独立限流（令牌数 = 库存数 × 3）
- 服务：Redis 原子扣减库存，异步创建订单
- 数据库：不在秒杀时直接写入，靠 Kafka 削峰

**5. 可观测性**：
- OpenTelemetry 全链路追踪
- Prometheus + Grafana 监控（RED 方法）
- PagerDuty/飞书 告警通知

- 数据量增长后如何做分库分表？
- 如何保证 99.99% 的 SLA？
