## ⭐ 基础题

---

**Q1. MongoDB 为什么被称为文档数据库？它和关系型数据库最本质的差异是什么？**

**参考答案：**

MongoDB 的基本存储单元是文档，而不是关系型数据库里的行。文档本质上是一个层级化对象，可以包含嵌套对象和数组。

最本质的差异在于建模方式：

- 关系型数据库强调把数据拆成多张表，通过主外键关系和 join 拼装。
- MongoDB 强调把一个业务聚合对象尽量放进一个文档里，直接按对象读取。

类比：

- 关系库像把员工信息拆进多张 Excel 表。
- MongoDB 像给每个员工建一份完整档案袋。

MongoDB 的优势在于：

- 结构灵活
- 层级对象表达自然
- 对象聚合读取方便
- 原生复制与分片能力较成熟

但它并不天然优于关系库。遇到复杂 join、强约束、多表事务频繁的场景，PostgreSQL 往往更合适。

---

**Q2. BSON 和 JSON 有什么区别？为什么 MongoDB 不直接存 JSON 文本？**

**参考答案：**

BSON 是 Binary JSON，是 MongoDB 的实际存储与传输编码格式。

区别在于：

- JSON 主要是文本交换格式，适合人读。
- BSON 是二进制格式，适合机器解析和类型表达。

JSON 的局限：

- 没有原生日期类型
- 不区分 int32、int64、double
- 不方便表达二进制
- 无原生 ObjectId

而 BSON 支持：

- Date
- Binary
- ObjectId
- Decimal128
- Int32 / Int64 / Double 区分

MongoDB 不直接存 JSON 文本，是因为数据库需要：

- 更高效的序列化与反序列化
- 更明确的数据类型边界
- 更适合索引、比较和存储引擎处理

面试里一个高频点是：BSON 并不一定在任何场景都比 JSON 更小，因为字段名同样要存储，且某些结构会有额外元信息，但它对数据库内部处理更友好。

---

**Q3. MongoDB 中 `_id` 字段有什么作用？默认 ObjectId 有什么特点？**

**参考答案：**

`_id` 是每个文档的主键字段，默认必须唯一。若应用未指定，MongoDB 通常会自动生成 ObjectId。

ObjectId 的核心特点：

- 12 字节
- 包含时间相关信息，因此整体趋势上递增
- 冲突概率极低
- 适合分布式环境下自动生成主键

它带来的工程价值：

- 不依赖中心化发号器
- 作为默认索引插入位置相对稳定
- 可以大致反映生成时间

但也要注意：

- ObjectId 不是严格有序业务 ID
- 不要把它直接暴露成业务语义编号
- 若分片键设计不当，单靠 ObjectId 不能解决热点问题

---

**Q4. MongoDB 说自己“Schema 灵活”，是不是意味着生产环境不需要 Schema？**

**参考答案：**

不是。更准确地说，MongoDB 是“Schema 可选且易演进”，不是“不要 Schema”。

生产环境里至少有三层 Schema：

1. 应用层 DTO/实体模型
2. 数据库层 validator，例如 `$jsonSchema`
3. 索引、唯一约束、字段规范

如果完全没有 Schema 约束，会出现：

- 字段名混乱
- 同字段类型不一致
- 查询和聚合逻辑越来越复杂
- 数据质量无法保证

所以 MongoDB 的正确实践不是放弃建模，而是：

- 允许演进
- 接受局部冗余
- 但保持明确的数据契约

---

**Q5. Embedding 和 Referencing 分别是什么？什么时候选哪一个？**

**参考答案：**

Embedding 是把关联数据直接内嵌进一个文档。

Referencing 是将关联数据拆成多个文档，通过字段引用关联。

判断标准通常看四点：

1. 是否总是一起读写
2. 生命周期是否一致
3. 数量是否受控
4. 是否需要独立查询、独立索引、独立扩展

适合 Embedding 的场景：

- 订单里的 `items`
- 用户的少量地址
- 配置项子结构

适合 Referencing 的场景：

- 用户和海量订单
- 商品和海量评论
- 可无限增长的行为日志

一个常见误区是“一对多就必须引用”。这在 MongoDB 不成立。一对多只要“多”的规模受控，也完全可以内嵌。

---

**Q6. 什么是单字段索引、复合索引、多键索引、文本索引、TTL 索引？**

**参考答案：**

这是 MongoDB 最常见的几类索引：

- 单字段索引：索引一个字段，例如 `{ userId: 1 }`
- 复合索引：多个字段组合，例如 `{ userId: 1, status: 1, createdAt: -1 }`
- 多键索引：当被索引字段是数组时自动形成
- 文本索引：支持轻量全文搜索
- TTL 索引：让文档在一定时间后自动过期删除

每类索引的用途不同：

- 单字段索引用于简单过滤
- 复合索引用于核心业务查询，是最重要的索引类型
- 多键索引用于标签、数组字段
- 文本索引适合简单站内搜索，不适合复杂搜索平台
- TTL 索引适合会话、临时数据、日志保留

生产环境里最值钱的能力，不是记住这些名字，而是会根据查询模式设计索引。

---

**Q7. MongoDB 的单文档操作为什么常被说成“天然适合业务原子更新”？**

**参考答案：**

MongoDB 的单文档更新具有原子性。这意味着一个文档内的多个字段更新，可以作为一个不可分割的操作完成。

例如扣减库存：

```javascript
db.inventory.updateOne(
  { sku: "sku-1", stock: { $gte: 1 } },
  { $inc: { stock: -1 } },
);
```

这个操作把“条件检查”和“更新”合并到一个原子动作里。

这带来的好处是：

- 很多业务不必一上来就用事务
- 只要合理建模，让强一致范围落在单文档内，系统会简单很多

MongoDB 的一个核心建模思想，就是尽量让一个业务聚合在单文档内闭合，从而最大化利用单文档原子性。

---

**Q8. MongoDB 的 Text Index 能不能替代 Elasticsearch？**

**参考答案：**

一般不能。

MongoDB 的 Text Index 适合：

- 轻量级全文检索
- 小规模站内搜索
- 关键词匹配为主的场景

但如果你需要：

- 复杂打分
- 分词策略高度可控
- 召回/排序模型定制
- 高级搜索分析能力

那么专业搜索引擎通常更合适。

面试里答这题的关键不是“能不能”，而是明确边界：MongoDB Text Index 是数据库内建的实用能力，不是完整搜索平台的替代物。

---

**Q9. TTL 索引有哪些典型场景和注意事项？**

**参考答案：**

TTL 索引最常用于：

- 登录会话
- 验证码
- 临时任务结果
- 某类只保留 N 天的日志

示例：

```javascript
db.sessions.createIndex({ expireAt: 1 }, { expireAfterSeconds: 0 });
```

注意事项：

1. TTL 删除依赖后台线程扫描，不保证精确到秒
2. 它是“最终过期”，不是强实时删除
3. 对非常大规模过期数据，删除过程本身也可能带来负载
4. 字段值类型要正确，一般是 `Date`

如果业务要求“某一秒必须立刻删除”，TTL 索引通常不够，需要应用层或调度系统配合。

## ⭐⭐ 进阶题

**Q10. 设计 MongoDB 复合索引时，字段顺序应该怎么确定？**

**参考答案：**

字段顺序通常由三类因素共同决定：

1. 高频过滤条件
2. 排序要求
3. 字段选择性

例如查询：

```javascript
db.orders
  .find({ userId: 1001, status: "PAID" })
  .sort({ createdAt: -1 })
  .limit(20);
```

常见合理索引是：

```javascript
{ userId: 1, status: 1, createdAt: -1 }
```

原因：

- 先按过滤字段缩小范围
- 再利用索引顺序满足排序
- 避免额外内存排序

此外要遵守前缀原则：

- 这个索引能支持 `userId`
- 支持 `userId + status`
- 支持 `userId + status + createdAt`
- 但不适合只查 `status`

面试里不要只回答“高选择性字段放前面”。这是不完整的。排序和查询形态同样决定顺序。

---

**Q11. 什么是 Covered Query？为什么它重要？**

**参考答案：**

Covered Query 指查询所需字段都可以直接从索引中得到，因此不需要回表读取完整文档。

例如已有索引：

```javascript
db.orders.createIndex({ userId: 1, status: 1, createdAt: -1 });
```

查询：

```javascript
db.orders.find(
  { userId: 1001, status: "PAID" },
  { _id: 0, userId: 1, status: 1, createdAt: 1 },
);
```

如果这些字段都在索引中，MongoDB 可直接返回结果。

重要性在于：

- 减少文档读取
- 降低 I/O
- 提升缓存命中效率
- 对大文档场景尤其有价值

类比：

- 一般索引查询像先查目录卡片，再去库房取原件。
- Covered Query 像目录卡片本身就包含全部答案，不用进库房。

---

**Q12. Multikey 索引有什么特点？有哪些使用限制？**

**参考答案：**

当索引字段是数组时，MongoDB 会自动创建 Multikey 索引。数组中每个元素都会参与索引。

例如：

```javascript
db.articles.createIndex({ tags: 1 });
```

文档中 `tags: ["mongodb", "database", "nosql"]` 会生成多个索引项。

优点：

- 很适合标签、分类、多值属性

问题与限制：

- 数组很大时索引膨胀明显
- 更新大数组成本高
- 多个数组字段组合进同一复合索引要特别谨慎，存在限制与复杂性

面试里最好强调：数组字段很方便，但不是“无限长度也能免费使用”的特性。

---

**Q13. MongoDB 的聚合管道为什么说像流水线？优化聚合时先看什么？**

**参考答案：**

聚合管道是按 stage 顺序处理文档的数据流模型，因此常被类比为流水线。

常见 stage：

- `$match`
- `$project`
- `$group`
- `$sort`
- `$unwind`
- `$lookup`

优化时先看三点：

1. 能否尽早 `$match`，减少输入量
2. 能否尽早 `$project`，减少字段量
3. 是否能利用索引支持前面的过滤或排序

此外要关注：

- 大 `$group` 会吃内存
- 大 `$sort` 会吃内存
- 大 `$lookup` 会让在线路径变重

正确理解聚合的关键是：它不是免费的“万能分析器”，而是要和索引、数据模型、输入规模一起设计。

---

**Q14. 什么是 Replica Set？MongoDB 如何实现高可用？**

**参考答案：**

Replica Set 是 MongoDB 的复制与高可用机制。一个复制集通常有一个 Primary 和多个 Secondary。

工作方式：

- Primary 接收写请求
- Secondary 复制并回放 Primary 的 oplog
- 当 Primary 故障时，复制集通过选举选出新的 Primary

高可用的关键点：

- 多数派原则
- 自动选主
- 驱动自动发现主节点
- 合理配置 readPreference / writeConcern

需要强调：高可用不等于完全无感。故障切换期间通常仍会有短暂写失败和重试。

---

**Q15. oplog 是什么？它和 binlog 类似吗？**

**参考答案：**

`oplog` 是 MongoDB 复制集里的操作日志，位于 `local.oplog.rs`。Secondary 通过读取并回放 oplog 来保持同步。

它和 MySQL binlog 在理念上相似，都是变更流水，但语境不同：

- 都能承载复制所需的变更记录
- 都是高可用/同步链路的核心

MongoDB 面试里更重要的是回答清楚它的工程意义：

1. Secondary 根据 oplog 追赶 Primary
2. oplog 大小决定节点可接受的脱机恢复窗口
3. 若 Secondary 落后太久而 oplog 已被覆盖，可能需要全量重同步

所以监控 oplog 窗口非常关键。

---

**Q16. Replica Set 故障切换时，应用会遇到哪些现象？如何正确处理？**

**参考答案：**

Primary 故障或 step down 时，应用通常会遇到：

- 短暂写失败
- `NotPrimary`、`PrimarySteppedDown` 等错误
- 正在进行的事务或请求被中断
- 某些读请求发生重路由

正确处理方式：

1. 使用官方驱动和复制集连接串
2. 启用驱动提供的重试写、重试读能力
3. 对幂等操作设计应用层重试
4. 不要把单次主节点切换等同于整个服务崩溃

面试官想听到的不只是“会切主”，而是你知道切主会在客户端表现成什么。

---

**Q17. readConcern 和 writeConcern 分别解决什么问题？**

**参考答案：**

`writeConcern` 决定写入成功的确认标准。

例如：

- `w:1` 表示 Primary 本地确认即可
- `w:"majority"` 表示多数节点确认才返回成功
- `j:true` 表示要求 journal 持久化语义更强

`readConcern` 决定读取时对一致性的要求，例如：

- `local`
- `majority`
- `snapshot`
- `linearizable`

它们本质上是在调节：

- 数据新鲜度
- 一致性强度
- 延迟与吞吐成本

很多线上“读写不一致”的根因，并不是 MongoDB 不支持一致性，而是应用没搞清 readConcern / writeConcern 的语义组合。

---

**Q18. MongoDB 的多文档事务适合什么场景？为什么说它不该成为默认建模手段？**

**参考答案：**

多文档事务适合：

- 跨多个文档的原子一致性要求
- 金融类强一致操作
- 订单与库存必须同成同败的场景
- 某些迁移或批处理逻辑

但它不该成为默认建模手段，因为：

- 事务有额外状态维护成本
- 长事务会拖慢系统
- 跨分片事务成本更高
- 它掩盖了错误的数据建模

MongoDB 的正确思路通常是：

1. 优先按聚合根建模
2. 优先利用单文档原子性
3. 只有确实跨文档不可避免时再用事务

---

**Q19. MongoDB 事务有哪些限制与实践建议？**

**参考答案：**

实践上要记住这些限制方向：

- 事务应尽量短
- 不要在事务中做大范围扫描
- 不要在事务中等待外部接口
- 涉及 shard 越多，代价越高
- 高并发下冲突和重试成本会更明显

最佳实践：

1. 小事务、短事务
2. 清晰的重试机制
3. 避免把批处理硬塞进事务
4. 对冲突敏感场景做热点拆分

面试时如果你能明确说出“MongoDB 支持事务，但设计上仍然提倡尽量把一致性闭合在单文档内”，通常会加分。

---

**Q20. 什么是分片？为什么不能等到单机扛不住了再随便选一个分片键？**

**参考答案：**

分片是 MongoDB 的水平扩展机制。核心思想是把数据拆到多个 shard 上存储和处理。

分片键决定：

- 数据怎么分布
- 写入是否均匀
- 查询是否能精准路由
- 是否出现热点 shard

不能“随便选一个字段”做 shard key，因为错误 shard key 会导致：

- 所有新写都打到单个 shard
- 大量 scatter-gather
- 数据迁移频繁且收益有限
- 集群规模越大越难救

分片键本质上是“分布模型 + 查询模型”的联合设计，不是容量告急时的临时开关。

## ⭐⭐⭐ 高级题

---

**Q21. Range Sharding 和 Hashed Sharding 的区别是什么？各自适用什么场景？**

**参考答案：**

Range Sharding 按 shard key 的范围分布数据。

优点：

- 范围查询性能好
- 路由可精确命中特定 shard 范围

缺点：

- 如果 key 单调递增，容易形成写热点

Hashed Sharding 对 shard key 哈希后分布。

优点：

- 分布均匀
- 适合高并发写入

缺点：

- 范围查询路由能力差

适用建议：

- 以范围查询为核心时优先考虑 Range
- 以高并发写均匀分布为核心时优先考虑 Hashed

面试里最好的回答不是二选一，而是说清楚“局部性”和“均匀性”的权衡。

---

**Q22. 什么是热点分片？你会如何避免？**

**参考答案：**

热点分片是指某个 shard 承担了远高于其他 shard 的请求量或写入量。

典型成因：

- 用递增时间字段做 range shard key
- 租户分布极不均匀
- 某些业务热点值集中命中单 shard

避免方法：

1. 选择更均匀的 shard key
2. 对单调递增键考虑 hashed 或复合设计
3. 用真实流量压测候选 shard key
4. 避免所有在线流量围绕同一热点文档或热点 tenant

如果已经发生热点，常见补救包括：

- 改 shard key 或重构数据模型
- 做逻辑分桶
- 把热点数据独立拆分

但这些通常代价高，所以最好的策略仍是前期设计到位。

---

**Q23. 什么是 Scatter-Gather？为什么它在分片集群里危险？**

**参考答案：**

Scatter-Gather 指 `mongos` 无法根据查询条件精准定位 shard，只能把请求广播到所有 shard，再汇总结果。

危险在于：

- shard 数越多，广播成本越高
- 每次请求都拉高集群总资源占用
- 尾延迟会被最慢 shard 拉长

产生原因通常是：

- 查询条件不包含 shard key
- shard key 设计与核心访问模式不匹配

解决思路：

1. 让高频查询尽量包含 shard key
2. 选择更契合访问模式的 shard key
3. 把全局扫描型分析任务与在线查询隔离

---

**Q24. MongoDB 深分页为什么慢？常见替代方案是什么？**

**参考答案：**

深分页慢，主要因为 `skip(N)` 不是“跳到第 N 条”，而是往往需要扫描并丢弃前面的结果。

例如：

```javascript
db.orders.find({ userId: 1001 }).sort({ createdAt: -1 }).skip(100000).limit(20);
```

这会让数据库做大量无意义遍历。

替代方案通常是 seek pagination，也叫基于游标的分页：

```javascript
db.orders
  .find({
    userId: 1001,
    createdAt: { $lt: lastSeenCreatedAt },
  })
  .sort({ createdAt: -1 })
  .limit(20);
```

如果排序字段可能重复，通常再加 `_id` 作为稳定游标。

这种方案的优势：

- 更稳定
- 不会随页数增加而线性变慢
- 更适合大数据集在线分页

---

**Q25. 线上 MongoDB 出现慢查询，你会如何排查？**

**参考答案：**

我的排查顺序通常是：

1. 先看慢查询具体语句和时间分布
2. 用 `explain("executionStats")` 看执行计划
3. 判断是否 COLLSCAN、阻塞排序、keys/docs examined 异常
4. 检查索引是否缺失、顺序错误、命中率低
5. 判断是不是工作集超出内存，导致频繁磁盘读
6. 检查是否有热点文档、热点 shard、复制延迟、chunk migration 干扰
7. 检查是否为聚合、事务、大数组更新等业务特定问题

这里最常见的误区是：

- 一上来调参数
- 甚至还没看 explain 就想改硬件

慢查询排查的根，通常仍然是：

- 查询模式
- 索引设计
- 数据模型

**Q26. MongoDB 中“低选择性字段索引”为什么常常效果一般？**

**参考答案：**

低选择性字段指取值种类少、命中比例高的字段，例如：

- `status` 只有 `NEW/PAID/CLOSED`
- `gender` 只有几个枚举值

如果单独给这种字段建索引，查询时可能仍然要扫大量索引项，收益有限。

例如 `status = PAID` 命中 80% 数据时，数据库可能宁可全表扫描，或者即使命中索引，效果也不好。

更合理的做法是：

- 把它和高区分度字段一起设计复合索引
- 同时兼顾排序字段

这类题主要考你是否理解：索引不是“有就快”，而是要看选择性和访问路径。

---

**Q27. 从 MySQL 迁移到 MongoDB，最容易踩的坑是什么？**

**参考答案：**

最容易踩的坑不是技术命令，而是思维惯性。

典型错误：

1. 仍然按三范式强行拆集合
2. 过度依赖 `$lookup`
3. 不接受适度冗余
4. 把事务当成默认手段
5. 不重视文档大小与数组增长
6. 不建立 schema 规范与 validator

正确迁移思路：

1. 先从业务聚合根重构数据模型
2. 明确高频读路径和写路径
3. 再决定哪些字段嵌入、哪些引用
4. 用真实查询设计索引，而不是把 MySQL 索引原样照搬

本质上，从 MySQL 到 MongoDB 的迁移，更像是一次建模方法迁移，而不是一次语法迁移。

---

**Q28. MongoDB 和 PostgreSQL 怎么选？如果团队两者都能用，你会怎么做决策？**

**参考答案：**

我会按核心访问模式来决策，而不是按技术偏好。

更倾向 MongoDB 的情况：

- 业务对象天然文档化
- 字段经常变化
- 半结构化数据多
- 读取以聚合对象为主
- 需要原生分片扩展

更倾向 PostgreSQL 的情况：

- 强事务链路多
- 复杂 join 和分析查询多
- 数据关系稳定
- 约束和 SQL 能力极其重要

如果两者都能做，我会追问三个问题：

1. 核心在线请求是“取一个完整对象”还是“做复杂关联查询”？
2. 数据结构未来半年是一致稳定，还是快速迭代？
3. 扩展瓶颈更可能在单机写、分布式扩容，还是在复杂分析？

选型的关键不是“谁更高级”，而是谁更贴近系统的真实矛盾。

---

**Q29. MongoDB 7/8 时代与早期版本相比，有哪些实践认知需要更新？**

**参考答案：**

需要更新的认知主要有三类：

1. 不要再用很老的版本印象判断 MongoDB
2. 查询执行与索引能力在持续增强
3. 事务、分片、聚合已经是成熟生产能力，但仍有边界

几个具体点：

- 现代版本的查询执行器和 explain 结果与旧版本可能不同
- 7.x 时代值得关注 columnstore index 等新能力
- 复制集、事务、分片都是常规能力，但仍需按场景设计

这题的关键是答出“MongoDB 已经是成熟分布式数据库”，同时不神化它。

---

**Q30. 如果一个团队把所有业务都放进 MongoDB，你会重点审查哪些架构风险？**

**参考答案：**

我会重点审查六类风险：

1. 数据模型是否失控，集合内文档是否过度异构
2. 是否存在无限增长数组与超大文档风险
3. 是否把复杂关系查询都留给 `$lookup`
4. 索引是否由真实访问模式驱动，还是堆了很多无效索引
5. 是否存在错误 shard key、热点分片、scatter-gather
6. 是否明确了一致性边界、read/write concern 策略和事务使用边界

如果这六点都答不上来，那么“全放 MongoDB”通常不是技术自信，而是架构失控的前兆。

---

## 面试收尾建议

MongoDB 面试最容易失分的地方，不是不会写命令，而是回答停留在“它很灵活、适合 JSON”。

更好的表达应该是：

- 我知道它为什么灵活。
- 我知道灵活背后的代价。
- 我知道如何建模、建索引、设 concern、选 shard key。
- 我知道什么时候它合适，什么时候 PostgreSQL 更合适。

当你能把这些说清楚，MongoDB 就不再只是一个 NoSQL 名词，而是一套你能真正驾驭的工程工具。
