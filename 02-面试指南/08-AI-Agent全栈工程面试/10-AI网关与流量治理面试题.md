## 参考答案

### Q1: AI 网关的定义与区别

<details>
<summary>参考答案</summary>

**AI 网关是专为 LLM/AI 模型调用设计的 API 代理层，在传统网关功能上增加了 Token 计量、模型路由、Fallback、成本管控等 AI 特有能力。**

#### 类比理解

传统 API 网关像高速收费站——验票、计数、限速。AI 网关则像一个智能调度中心——不仅收费限速，还能根据路况（模型价格/延迟/可用性）动态选择最优路线（模型提供商），甚至帮你省钱（缓存/级联）。

#### 核心差异

| 维度 | 传统 API 网关 | AI 网关 |
|------|-------------|---------|
| 计费单位 | 请求次数 | Token 用量（prompt + completion） |
| 响应模式 | 单次 JSON 响应 | SSE 流式响应 |
| 路由依据 | URL/Header | 模型名 + 成本 + 延迟 + 可用性 |
| 容错机制 | 重试 + 熔断 | Fallback 链（多提供商切换） |
| 缓存 | URL + 参数 | Prompt 语义缓存 |
| 核心价值 | 安全 + 流量控制 | 成本管控 + 多模型统一管理 |

#### 面试追问

- **用 Kong/APISIX 加插件能替代 AI 网关吗**？部分能力可以，但 Token 计量、SSE 代理、模型 Fallback 等需要深度定制
- **主流 AI 网关有哪些**？LiteLLM（开源首选）、Portkey、Helicone、One API（国内）

</details>

### Q2: Virtual Key 概念

<details>
<summary>参考答案</summary>

**Virtual Key 是 AI 网关为每个用户/团队生成的虚拟 API Key，映射到后端真实的模型提供商 Key，实现权限隔离和成本追踪。**

#### 工作原理

```
前端应用 → Virtual Key "vk-team-a-xxx"
                ↓
AI 网关：查找 vk-team-a 的配置
  - 绑定模型：gpt-4o, claude-3.5-sonnet
  - 月预算上限：$5,000
  - 速率限制：100 RPM
  - 已使用：$3,200
                ↓
后端真实 Key：sk-openai-xxx / sk-anthropic-xxx
（用户永远看不到真实 Key）
```

#### 核心价值

1. **安全隔离**：真实 Key 不暴露给开发者，泄露 Virtual Key 可随时吊销
2. **成本追踪**：每个 Virtual Key 独立计量 Token 消耗
3. **权限控制**：可限制可用模型、速率、预算
4. **审计能力**：追踪每个调用来源

</details>

### Q3: LiteLLM 统一 API 实现

<details>
<summary>参考答案</summary>

**LiteLLM 通过 Provider-Model 映射 + 统一的 OpenAI 格式 API 实现 100+ 模型提供商的统一调用。**

#### 核心机制

```python
# 统一调用接口（OpenAI 格式）
from litellm import completion

# 调用 OpenAI
response = completion(model="gpt-4o", messages=[...])

# 调用 Anthropic（同样的接口）
response = completion(model="claude-3.5-sonnet", messages=[...])

# 调用自托管 vLLM
response = completion(model="openai/my-model", 
                      api_base="http://vllm:8000/v1",
                      messages=[...])
```

#### 实现原理

1. **模型名映射**：`claude-3.5-sonnet` → Anthropic API 格式转换
2. **参数适配**：统一的 temperature/max_tokens 转换为各家格式
3. **流式适配**：不同提供商的 SSE 格式统一为 OpenAI 格式
4. **错误映射**：各家错误码统一为标准 HTTP 状态码

#### 面试追问

- **如何处理各家特有参数**？通过 `extra_body` 透传特有参数
- **流式响应如何统一**？每个 Provider 有独立的 StreamHandler 转换器

</details>

### Q4: 三种路由策略对比

<details>
<summary>参考答案</summary>

**延迟优先选最快、成本优先选最便宜、负载均衡分散压力。实际生产中通常组合使用。**

#### 详细对比

| 策略 | 决策依据 | 适用场景 | 代价 |
|------|---------|---------|------|
| 延迟优化 | 选历史 P50 延迟最低的模型 | 实时对话、代码补全 | 成本可能更高 |
| 成本优化 | 选每 token 价格最低的模型 | 批处理、后台任务 | 延迟不可控 |
| 负载均衡 | 按权重分配到多个后端 | 高可用、分散风险 | 非最优延迟/成本 |

#### 组合策略示例

```yaml
routing:
  strategy: "cascade"
  tiers:
    - name: "cost-first"
      models: ["gpt-4o-mini"]
      condition: "complexity == 'simple'"
    - name: "quality-first"
      models: ["gpt-4o", "claude-3.5-sonnet"]
      condition: "complexity == 'complex'"
      sub_strategy: "latency-optimized"
      fallback: "load-balanced"
```

**面试要点**：说出"我们在生产中用级联+延迟优化的组合策略"比只说一种更加分。

</details>

### Q5: 模型级联（Cascade Routing）

<details>
<summary>参考答案</summary>

**简单问题用便宜小模型，复杂问题用高级大模型，整体节省 40-70% 成本。**

#### 实现架构

```
用户请求 → 复杂度分类器（小模型/规则）
              ↓
      ┌── SIMPLE ──→ GPT-4o-mini（$0.15/1M tokens）
      │                ↓
      │           质量检查通过？ → 返回结果
      │                ↓ 不通过
      └── COMPLEX ──→ GPT-4o（$2.50/1M tokens）
                       → 返回结果
```

#### 分类器方案

| 方案 | 准确率 | 成本 | 延迟 |
|------|--------|------|------|
| 关键词规则 | 60-70% | 零 | 0ms |
| 小模型分类 | 80-90% | 极低 | 50ms |
| 历史数据训练 | 90%+ | 离线成本 | 10ms |

#### 成本计算示例

```
月请求 100 万次，不分级：全用 GPT-4o → 月费 $5,000
分级后：70% 简单(GPT-4o-mini) + 30% 复杂(GPT-4o)
  = 700K × $0.15/M + 300K × $2.50/M = $105 + $750 = $855
  节省 83%!
```

#### 面试追问

- **分类错误怎么办**？简单→复杂误分只是多花钱，复杂→简单误分影响质量。可以加质量检查兜底
- **如何评估质量**？用 LLM-as-Judge 自动评估回答质量，低于阈值自动 fallback 到大模型

</details>

### Q6: Fallback 链设计

<details>
<summary>参考答案</summary>

**多提供商 Fallback 是 AI 服务高可用的核心。设计原则：快速检测 → 自动切换 → 冷却恢复。**

#### Fallback 链示例

```
Primary: GPT-4o (OpenAI)
  ↓ 失败/超时
Fallback-1: Claude-3.5-Sonnet (Anthropic)
  ↓ 失败/超时
Fallback-2: Gemini-1.5-Pro (Google)
  ↓ 失败/超时
Fallback-3: 自托管 vLLM (LLaMA-70B)
  ↓ 失败/超时
降级响应: "服务暂时繁忙，请稍后重试"
```

#### 关键设计点

1. **超时策略**：TTFT 超时 5s 触发 Fallback（不等整个生成完成）
2. **错误分类**：区分可重试（429/503）和不可重试（400/401）错误
3. **Circuit Breaker**：连续失败 5 次 → 自动熔断 30s → 半开探测 → 恢复
4. **Fallback 代价**：不同模型输出风格可能不一致，需要 Prompt 适配层

#### 面试追问

- **流式响应中间失败怎么办**？已输出的无法撤回，可以记录断点，切换模型后从断点续生成（但体验较差），更好的做法是设置首包超时快速 Fallback

</details>

### Q7: Circuit Breaker 在 AI 网关中的应用

<details>
<summary>参考答案</summary>

**熔断器防止持续调用已故障的提供商，避免雪崩效应。三态模型：Closed → Open → Half-Open。**

#### 三态转换

```
Closed（正常）── 连续失败 5 次 ──→ Open（熔断）
     ↑                                    │
     │                              等待 30 秒
     │                                    ↓
     └─── 探测成功 ─── Half-Open（半开探测）
                              │
                        探测失败 → 回到 Open
```

#### AI 场景的特殊考虑

| 传统 Circuit Breaker | AI Circuit Breaker |
|---------------------|-------------------|
| 失败 = HTTP 5xx | 失败 = 5xx + 超时 + 429 |
| 固定阈值 | 按模型独立计数 |
| 恢复后全量恢复 | 渐进式恢复（10% → 50% → 100%） |

#### 代码示例

```python
class AICircuitBreaker:
    def __init__(self, failure_threshold=5, recovery_timeout=30):
        self.failures = 0
        self.state = "CLOSED"
        self.last_failure_time = None
    
    def call(self, model, messages):
        if self.state == "OPEN":
            if time.time() - self.last_failure_time > self.recovery_timeout:
                self.state = "HALF_OPEN"
            else:
                raise CircuitOpenError("熔断中，请求转发到 Fallback")
        
        try:
            response = llm_call(model, messages)
            self.on_success()
            return response
        except Exception as e:
            self.on_failure()
            raise
```

</details>

### Q8: Nginx 代理 SSE 配置

<details>
<summary>参考答案</summary>

**SSE 代理的核心是关闭所有缓冲层，让数据逐字节透传。**

#### 关键配置

```nginx
location /v1/chat/completions {
    proxy_pass http://backend;
    
    # 1. 关闭 Nginx 缓冲（最重要！）
    proxy_buffering off;
    proxy_cache off;
    
    # 2. 设置 SSE 需要的 Header
    proxy_set_header Connection '';
    proxy_http_version 1.1;
    chunked_transfer_encoding off;
    
    # 3. 超时设置（LLM 生成可能很慢）
    proxy_read_timeout 300s;
    proxy_send_timeout 300s;
    
    # 4. 告诉上游（如 CDN/ALB）也不要缓冲
    add_header X-Accel-Buffering no;
}
```

#### 常见坑

| 问题 | 原因 | 解决 |
|------|------|------|
| 卡顿后大段文字 | proxy_buffering 默认 on | `proxy_buffering off` |
| 60s 超时断开 | proxy_read_timeout 默认 60s | 增加到 300s |
| CDN 缓存整个响应 | CDN 默认缓冲 | `X-Accel-Buffering: no` |
| HTTP/1.1 最多 6 连接 | 浏览器限制 | 升级 HTTP/2 |

#### 面试追问

- **后端框架如何确保不缓冲**？Python: `StreamingResponse`；Node: `res.write()` + `res.flush()`
- **如何验证 SSE 正常工作**？`curl -N` 观察是否逐行输出

</details>

### Q9: Prompt Caching vs Semantic Caching

<details>
<summary>参考答案</summary>

**Prompt Caching 缓存完全相同的前缀（节省计算），Semantic Caching 缓存语义相似的查询（节省 API 调用）。**

#### 对比

| 维度 | Prompt Caching | Semantic Caching |
|------|---------------|-----------------|
| 匹配方式 | 精确前缀匹配 | 语义相似度（embedding 距离） |
| 实现层 | 推理引擎（vLLM/SGLang） | AI 网关（应用层） |
| 节省什么 | GPU 计算（Prefill） | API 调用费用（整个请求） |
| 命中条件 | 完全相同的 token 序列 | 语义相似度 > 阈值 |
| 风险 | 无（精确匹配） | 可能返回不够精确的缓存 |
| 节省幅度 | 50-90% Prefill 时间 | 100% API 费用（命中时） |

#### Semantic Caching 实现

```python
def semantic_cache_lookup(query, threshold=0.95):
    query_embedding = embed(query)
    # 在向量数据库中搜索相似查询
    results = vector_db.search(query_embedding, top_k=1)
    if results[0].score > threshold:
        return cached_responses[results[0].id]  # 命中缓存
    return None  # 未命中，正常调用 LLM
```

#### 面试追问

- **Semantic Caching 的阈值如何设置**？太高（0.99）→命中率低；太低（0.8）→返回不相关结果。通常 0.92-0.95
- **Anthropic 的 Prompt Caching**：直接在 API 层缓存 system prompt，节省 90% 费用且零延迟

</details>

### Q11: 防止 API 调用风暴

<details>
<summary>参考答案</summary>

**多层防御：速率限制 + 预算硬上限 + 异常检测 + 告警自动熔断。**

#### 真实案例分析

```
Bug 场景：一个无限循环的 Agent 每秒调用 10 次 GPT-4o
  → 每次 1000 tokens（$0.0025）
  → 每秒 $0.025
  → 每小时 $90
  → 一个周末 $4,320
  → 如果 10 个实例：$43,200 💰
```

#### 防御层级

```
第1层：速率限制（RPM/TPM）
  → 每个 Key 最多 60 RPM / 100K TPM

第2层：日预算上限
  → 单 Key 日消耗 > $100 → 自动禁用

第3层：异常检测
  → 日消耗 > 历史均值 3x → 告警 + 人工确认

第4层：全局熔断
  → 组织月消耗 > 月预算 → 全部降级到小模型
```

#### 实现要点

```python
# Redis 实时限流
async def check_rate_limit(key_id: str):
    # 检查 RPM
    rpm = await redis.incr(f"rpm:{key_id}:{current_minute}")
    if rpm > MAX_RPM:
        raise RateLimitError()
    
    # 检查日预算
    daily_cost = await redis.get(f"cost:{key_id}:{today}")
    if float(daily_cost or 0) > DAILY_BUDGET:
        raise BudgetExceededError()
```

### Q12: 统一错误处理和重试策略

<details>
<summary>参考答案</summary>

**统一错误分类 + 指数退避重试 + 按错误类型选择策略。**

#### 错误统一分类

```python
class LLMError:
    RETRYABLE = {
        429: "Rate Limited",      # 可重试（等待后重试）
        500: "Server Error",      # 可重试（立即重试）
        503: "Service Unavailable" # 可重试（Fallback）
    }
    NON_RETRYABLE = {
        400: "Bad Request",       # 不重试（修复请求）
        401: "Unauthorized",      # 不重试（检查 Key）
        404: "Model Not Found"    # 不重试（检查模型名）
    }
    FALLBACK = {
        "timeout": "Fallback",    # 超时 → 切换提供商
        "context_length": "Truncate"  # 超长 → 截断重试
    }
```

#### 重试策略

```
429 Rate Limit:
  → 读取 Retry-After header
  → 指数退避：1s → 2s → 4s → 8s
  → 最多重试 3 次

500 Server Error:
  → 立即重试 1 次（可能是瞬时错误）
  → 失败则 Fallback 到其他提供商

Timeout:
  → 不重试同一提供商
  → 直接 Fallback（用户在等待）

Context Length Exceeded:
  → 自动截断 Prompt（保留 system + 最新消息）
  → 或降级到支持更长上下文的模型
```

#### 面试追问

- **OpenAI 和 Anthropic 的错误格式差异**？网关层统一转换为标准格式，内部维护映射表
- **流式响应中间出错怎么办**？记录已输出内容，切换提供商后可以要求"继续"

</details>
