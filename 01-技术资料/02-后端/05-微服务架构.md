## 1. 为什么需要微服务

### 1.1 单体架构的痛点

想象一家**大型百货公司**——所有部门（服装、餐饮、电器、生鲜）都在同一栋楼里运营。当餐饮区需要装修时，整栋楼都得停业；当电器区要扩大面积时，得重新规划楼层布局。这就是**单体架构（Monolith）**的现实困境。

单体架构的四大核心痛点：

| 痛点 | 表现 | 影响 |
|------|------|------|
| **代码膨胀** | 所有功能在一个代码库，百万行代码难以理解 | 新人上手慢，改一个功能要理解全局 |
| **部署耦合** | 修改一行代码需要重新部署整个应用 | 发布周期长（从天到周），风险高 |
| **团队瓶颈** | 多团队共享代码库，频繁冲突 | 合并冲突、协作效率低、代码审查堆积 |
| **技术栈锁定** | 整个应用使用同一语言/框架 | 无法为特定模块选择最优技术 |

### 1.2 微服务：从百货公司到商业综合体

**微服务架构**就像一个**商业综合体（Shopping Mall）**——每家店铺独立运营（独立团队、独立装修、独立营业时间），但共用停车场、电梯、空调等基础设施。一家店铺装修不影响其他店铺营业。

```
单体架构 (百货公司)              微服务架构 (商业综合体)
┌─────────────────────┐     ┌──────┐ ┌──────┐ ┌──────┐
│  用户模块 │ 商品模块  │     │ 用户  │ │ 商品  │ │ 订单  │
│  ─────── │ ──────── │     │ 服务  │ │ 服务  │ │ 服务  │
│  订单模块 │ 支付模块  │     │ (Go)  │ │(Java) │ │(Node) │
│  ─────── │ ──────── │     │ MySQL │ │ PG    │ │ Mongo │
│       共享数据库      │     └───┬──┘ └───┬──┘ └───┬──┘
│       (MySQL)        │         │        │        │
└─────────────────────┘     ====== 消息总线 / API 网关 ======
```

### 1.3 微服务不是银弹

> **"微服务不会让问题消失，只是把复杂度从代码转移到运维。"** — Martin Fowler

微服务引入的新挑战：
- **分布式系统复杂度**：网络不可靠、分布式事务、数据一致性
- **运维成本激增**：数十甚至数百个服务的部署、监控、日志聚合
- **调试困难**：一个请求可能跨越 10+ 个服务，定位问题如同大海捞针

### 1.4 演进路线

通常企业不会一步到位，而是渐进演进：

```
Monolith → Modular Monolith → Microservices
(单体)      (模块化单体)        (微服务)
```

**Modular Monolith** 是一个务实的中间态：在单体内部按模块严格划分边界（类似 Java Module 或 Maven 多模块），保持独立部署单元但避免分布式复杂度。只有当某些模块确实需要独立扩缩容、独立技术栈时，才拆分为微服务。

## 2. 微服务核心原则

### 2.1 单一职责 (Single Responsibility)

每个服务**只做一件事并把它做好**，就像 Unix 哲学中的命令行工具。用户服务只管用户的注册、登录、权限；订单服务只管订单的创建、状态流转。

判断是否违反单一职责的信号：
- 修改一个功能时需要同时改两个服务
- 一个服务的 README 需要超过一页纸来描述它做什么

### 2.2 自治性 (Autonomy)

自治是微服务最核心的特征，体现在三个维度：

| 维度 | 含义 | 实践 |
|------|------|------|
| **独立部署** | 一个服务的发布不依赖其他服务 | 独立 CI/CD 流水线、独立版本号 |
| **独立数据库** | 每个服务拥有自己的数据存储 | 不允许服务直接访问其他服务的数据库 |
| **独立团队** | 一个团队完整负责一个或几个服务 | 从开发到运维（You Build It, You Run It） |

### 2.3 去中心化 (Decentralization)

**数据治理去中心化**：不再要求所有服务使用同一个数据库或同一种数据库。用户服务可以用 PostgreSQL，缓存服务可以用 Redis，搜索服务可以用 Elasticsearch。

**技术选型去中心化**：每个团队可以选择最适合的语言和框架。但要注意，过度多样化会导致维护成本上升，实际中通常限制在 2-3 种主力语言。

### 2.4 为失败设计 (Design for Failure)

在分布式系统中，**故障是常态而不是意外**。网络会断、服务会崩、数据库会慢。因此每个服务都必须：
- 设置合理的**超时**，而非无限等待
- 实现**断路器**，避免级联故障
- 设计**降级策略**，核心功能在部分服务不可用时仍能工作
- 保证**幂等性**，同一请求重试多次结果一致

### 2.5 Conway's Law 与团队组织

> **"系统的架构会映射为组织的沟通结构。"** — Melvin Conway (1967)

这意味着：如果你的组织按技术层分团队（前端组、后端组、DBA 组），你大概率会得到一个分层架构而不是微服务架构。要做好微服务，需要**跨功能团队（Cross-functional Team）**——每个团队包含开发、测试、运维能力，完整负责一个业务领域。

```
❌ 按技术层分团队              ✅ 按业务领域分团队
┌───────────────┐           ┌────────┐ ┌────────┐ ┌────────┐
│  前端团队      │           │ 用户团队│ │ 商品团队│ │ 订单团队│
├───────────────┤           │ ─前端  │ │ ─前端  │ │ ─前端  │
│  后端团队      │           │ ─后端  │ │ ─后端  │ │ ─后端  │
├───────────────┤           │ ─DBA   │ │ ─DBA   │ │ ─DBA   │
│  DBA 团队     │           │ ─DevOps│ │ ─DevOps│ │ ─DevOps│
└───────────────┘           └────────┘ └────────┘ └────────┘
```

## 3. 服务拆分策略

### 3.1 DDD 的 Bounded Context 划分边界

**领域驱动设计（DDD）** 是微服务拆分的理论基石，其核心概念是**限界上下文（Bounded Context）**。

类比：Bounded Context 就像**国家领土**——每个国家有自己的法律（业务规则）、货币（数据模型）和语言（术语定义）。同一个词"订单"在不同上下文中含义不同：
- 在**销售上下文**中：订单 = 客户购买记录（含价格、优惠）
- 在**物流上下文**中：订单 = 配送任务（含地址、重量、时效）
- 在**财务上下文**中：订单 = 应收账款（含税金、对账信息）

```
              电商系统 DDD 上下文映射
┌──────────────┐    ┌──────────────┐
│   用户上下文   │← →│  认证上下文   │
│  User         │    │  Account     │
│  Profile      │    │  Credential  │
└──────┬───────┘    └──────────────┘
       │ 客户关系
┌──────▼───────┐    ┌──────────────┐
│   商品上下文   │← →│  库存上下文   │
│  Product      │    │  StockItem   │
│  Category     │    │  Warehouse   │
└──────┬───────┘    └──────┬───────┘
       │ 商品引用            │ 库存扣减
┌──────▼───────┐    ┌──────▼───────┐
│   订单上下文   │← →│  支付上下文   │
│  Order        │    │  Payment     │
│  OrderItem    │    │  Refund      │
└──────────────┘    └──────────────┘
```

### 3.2 拆分依据（四维度）

| 维度 | 判断标准 | 示例 |
|------|---------|------|
| **业务领域** | 属于不同业务领域的功能应拆分 | 用户管理 vs 订单管理 |
| **变更频率** | 频繁变更的模块与稳定模块分离 | 促销规则(频变) vs 用户认证(稳定) |
| **团队边界** | 不同团队负责的模块应拆分 | 搜索团队 → 搜索服务 |
| **数据边界** | 数据归属不同且交互有限的模块应拆分 | 商品数据 vs 订单数据 |

### 3.3 拆分反模式

**❌ 过度拆分（Nano-service）**

将每个函数或 CRUD 操作都拆成一个服务。结果：网络开销暴涨，一个简单请求需要调用 20+ 个服务。

> **经验法则**：一个服务应该由一个 5-8 人的小团队能够完整开发和维护（Two-Pizza Team）。

**❌ 数据共享（Shared Database）**

多个服务直接共享一个数据库。这破坏了自治性——修改一张表可能影响所有服务。

```
❌ 共享数据库                    ✅ 独立数据库
┌──────┐ ┌──────┐ ┌──────┐   ┌──────┐ ┌──────┐ ┌──────┐
│用户服务│ │订单服务│ │支付服务│   │用户服务│ │订单服务│ │支付服务│
└───┬──┘ └───┬──┘ └───┬──┘   └───┬──┘ └───┬──┘ └───┬──┘
    │        │        │          │        │        │
    ▼        ▼        ▼          ▼        ▼        ▼
 ┌─────────────────────┐     ┌─────┐  ┌─────┐  ┌─────┐
 │     共享 MySQL       │     │MySQL│  │PG   │  │Mongo│
 └─────────────────────┘     └─────┘  └─────┘  └─────┘
```

**❌ 分布式单体（Distributed Monolith）**

名义上拆成了多个服务，但服务间高度耦合——改一个服务需要同时修改和部署其他服务。只得到了分布式的复杂度，没得到微服务的好处。

### 3.4 拆分示例：电商系统

```
电商平台微服务拆分
├── 用户服务 (User Service)         — 注册/登录/权限/个人信息
├── 商品服务 (Product Service)      — 商品CRUD/分类/搜索
├── 订单服务 (Order Service)        — 下单/状态流转/退款
├── 支付服务 (Payment Service)      — 支付渠道对接/退款
├── 库存服务 (Inventory Service)    — 库存管理/扣减/预留
├── 通知服务 (Notification Service) — 短信/邮件/推送
└── 网关服务 (API Gateway)          — 路由/认证/限流
```

## 4. 服务间通信

### 4.1 同步通信

#### 4.1.1 REST (HTTP/JSON)

REST 是最通用的同步通信方式：基于 HTTP 协议，使用 JSON 作为数据格式，几乎所有语言和平台都能支持。

**优点**：简单通用、易调试（浏览器/curl 直接测）、生态丰富
**缺点**：性能一般（文本序列化/HTTP 1.1 短连接）、没有强类型约束

```
GET /api/users/123 HTTP/1.1
Host: user-service
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json
{
  "id": "123",
  "name": "Alice",
  "email": "alice@example.com"
}
```

#### 4.1.2 gRPC (Protocol Buffers + HTTP/2)

gRPC 是 Google 开源的高性能 RPC 框架，**内部服务间通信的首选方案**。

**核心优势**：
- **Protocol Buffers**：二进制序列化，体积小、解析快（比 JSON 快 5-10x）
- **HTTP/2**：多路复用、头部压缩、长连接
- **双向流（Bidirectional Streaming）**：支持服务端流、客户端流、双向流
- **强类型 IDL**：.proto 文件定义接口，自动生成多语言代码

```protobuf
// user_service.proto
syntax = "proto3";
package user;

service UserService {
  // 一元调用：请求-响应
  rpc GetUser(GetUserRequest) returns (User);
  // 服务端流：服务端连续推送多个用户
  rpc ListUsers(ListUsersRequest) returns (stream User);
  // 一元调用：创建用户
  rpc CreateUser(CreateUserRequest) returns (User);
}

message User {
  string id = 1;
  string name = 2;
  string email = 3;
  int64 created_at = 4;
}

message GetUserRequest {
  string id = 1;
}

message ListUsersRequest {
  int32 page_size = 1;
  string page_token = 2;
}

message CreateUserRequest {
  string name = 1;
  string email = 2;
}
```

Go gRPC 客户端调用：

```go
// Go gRPC 客户端调用
conn, err := grpc.Dial("user-service:50051",
    grpc.WithTransportCredentials(insecure.NewCredentials()),
)
if err != nil {
    log.Fatalf("failed to dial: %v", err)
}
defer conn.Close()

client := pb.NewUserServiceClient(conn)

// 一元调用
user, err := client.GetUser(ctx, &pb.GetUserRequest{Id: "123"})
if err != nil {
    log.Fatalf("GetUser failed: %v", err)
}
fmt.Printf("User: %s (%s)\n", user.Name, user.Email)

// 服务端流
stream, err := client.ListUsers(ctx, &pb.ListUsersRequest{PageSize: 10})
if err != nil {
    log.Fatalf("ListUsers failed: %v", err)
}
for {
    user, err := stream.Recv()
    if err == io.EOF {
        break
    }
    fmt.Printf("User: %s\n", user.Name)
}
```

#### 4.1.3 GraphQL（BFF 层）

GraphQL 让前端自由选择需要的字段，避免 Over-fetching / Under-fetching 问题。通常用于**BFF（Backend for Frontend）层**聚合多个微服务数据。

```graphql
# 前端一次请求获取用户及其订单
query {
  user(id: "123") {
    name
    email
    orders(last: 5) {
      id
      total
      status
    }
  }
}
```

### 4.2 异步通信：消息队列

#### 4.2.1 事件驱动架构 (EDA)

异步通信通过消息队列实现**松耦合**——服务之间不直接调用，而是通过事件（Event）交互。

类比：同步调用像**打电话**，必须双方同时在线；异步通信像**发微信**，发出去就行，对方什么时候看都行。

```
同步调用（打电话）                 异步通信（发微信）
订单服务 ──请求──→ 库存服务       订单服务 ──发事件──→ [消息队列]
         ←响应──                              ←消费── 库存服务
(必须等响应才能继续)               (发完就走，库存服务异步处理)
```

#### 4.2.2 命令 vs 事件

| 类型 | 语义 | 示例 | 耦合度 |
|------|------|------|--------|
| **命令 (Command)** | "请做某件事" | `DeductInventory{sku, qty}` | 高：需要知道接收方 |
| **事件 (Event)** | "某件事发生了" | `OrderCreated{orderId, items}` | 低：不关心谁来消费 |

**事件优于命令**：事件使发布方不需要知道谁会处理这个消息，新增消费者无需修改发布方代码。

#### 4.2.3 发布-订阅模式

```
                   ┌──→ [库存服务] — 扣减库存
          发布      │
[订单服务] ──→ [Kafka Topic: order.created] ──→ [通知服务] — 发送短信
                   │
                   └──→ [数据服务] — 更新统计
```

### 4.3 通信方式对比

| 维度 | REST | gRPC | GraphQL | 消息队列 |
|------|------|------|---------|---------|
| **协议** | HTTP/1.1+JSON | HTTP/2+Protobuf | HTTP+JSON | AMQP/自定义协议 |
| **性能** | 一般 | 高（5-10x） | 一般 | 取决于队列实现 |
| **耦合度** | 中 | 中 | 中 | 低 |
| **实时性** | 同步 | 同步/流 | 同步 | 异步 |
| **类型安全** | 弱（JSON Schema） | 强（IDL） | 强（Schema） | 弱 |
| **适用场景** | 外部 API / 简单 CRUD | 内部服务间高性能调用 | BFF / 前端聚合 | 解耦 / 削峰 / 最终一致性 |
| **代表框架** | Spring MVC/Gin/Express | grpc-go/grpc-java | Apollo/Hasura | Kafka/RabbitMQ/Pulsar |

## 5. API 网关

### 5.1 网关职责

API 网关是微服务的"大门"，所有外部请求都通过网关进入。类比：API 网关就像**酒店前台**——不管你要去游泳池还是餐厅，都先到前台登记。

```
客户端 ──→ [API 网关] ──→ 用户服务
              │        ──→ 商品服务
              │        ──→ 订单服务
              ├── 路由：/api/users → 用户服务
              ├── 认证：验证 JWT Token
              ├── 限流：每个用户 100 req/s
              ├── 协议转换：HTTP → gRPC
              └── 聚合：合并多个服务的响应
```

**核心功能**：

| 功能 | 说明 |
|------|------|
| **路由** | 根据 URL 路径或 Header 将请求分发到对应的后端服务 |
| **认证/鉴权** | 统一验证 JWT/OAuth Token，避免每个服务重复实现 |
| **限流/熔断** | 保护后端服务不被流量洪峰压垮 |
| **协议转换** | 外部 HTTP/JSON → 内部 gRPC/Protobuf |
| **请求聚合** | 将多个微服务的响应聚合成一个给前端 |
| **日志/监控** | 统一的请求日志和指标收集 |

### 5.2 常见网关方案

| 方案 | 语言 | 特点 | 适用场景 |
|------|------|------|---------|
| **Kong** | Lua/OpenResty | 插件丰富、社区活跃、声明式配置 | 通用 API 管理 |
| **APISIX** | Lua/OpenResty | 高性能、etcd 存储、国产开源 | 高并发场景 |
| **Spring Cloud Gateway** | Java | Spring 生态、响应式 | Java/Spring 技术栈 |
| **Envoy** | C++ | L4/L7 代理、xDS 动态配置 | Service Mesh 数据面 |

### 5.3 BFF 模式 (Backend for Frontend)

不同端（Web / App / 小程序）对 API 的需求不同。BFF 为每个端提供量身定制的 API 聚合层。

```
[Web App]  → [Web BFF]  ──→ 用户服务
[iOS App]  → [Mobile BFF] ──→ 商品服务
[小程序]   → [Mini BFF]  ──→ 订单服务
```

### 5.4 Kong 网关配置示例

```yaml
# Kong 声明式配置 (kong.yml)
_format_version: "3.0"
services:
  - name: user-service
    url: http://user-svc:8080
    routes:
      - name: user-route
        paths:
          - /api/users
        strip_path: true
    plugins:
      - name: rate-limiting
        config:
          minute: 100
          policy: local
      - name: jwt
        config:
          claims_to_verify:
            - exp
```

## 6. 服务注册与发现

### 6.1 为什么需要服务发现？

在微服务中，服务实例的 IP 和端口是动态变化的（容器重启、弹性扩缩容）。不可能把地址写死在配置文件里。

类比：服务发现就像**电话簿**——服务启动时"登记号码"（注册），调用方需要时"查号码"（发现）。实例下线时自动"注销号码"。

### 6.2 两种发现模式

```
客户端发现 (Client-Side Discovery)
┌──────┐    ①查询     ┌──────────┐
│调用方 │ ──────────→ │ 注册中心  │
│      │ ←────────── │(Consul)   │
│      │  ②返回实例列表 └──────────┘
│      │  ③负载均衡+直连     ↑ 注册/心跳
│      │ ──────────→ ┌──────┴─────┐
└──────┘             │ 服务实例 A/B│
                     └────────────┘

服务端发现 (Server-Side Discovery)
┌──────┐  ①请求  ┌─────────┐  ②转发  ┌────────────┐
│调用方 │ ──────→│负载均衡器│ ──────→│ 服务实例 A/B│
└──────┘        │(K8s SVC) │        └────────────┘
                └────┬────┘              ↑ 注册
                     │ 查询              │
                ┌────▼────┐              │
                │ 注册中心 │──────────────┘
                └─────────┘
```

| 模式 | 优点 | 缺点 | 代表 |
|------|------|------|------|
| 客户端发现 | 去中心化、灵活 | 客户端需集成 SDK | Consul + Ribbon |
| 服务端发现 | 客户端简单 | 负载均衡器可能成为瓶颈 | K8s Service + kube-proxy |

### 6.3 注册中心对比

| 注册中心 | 一致性模型 | 健康检查 | 特点 |
|---------|-----------|---------|------|
| **Consul** | CP (Raft) | HTTP/TCP/gRPC/Script | 多数据中心、KV 存储、Service Mesh |
| **etcd** | CP (Raft) | 需自行实现 | K8s 底层存储、强一致性 |
| **Nacos** | CP+AP 可切换 | TCP/HTTP | 配置中心 + 注册中心二合一 |
| **K8s Service** | 基于 DNS | kubelet LivenessProbe | 原生集成、免运维 |

### 6.4 健康检查机制

注册中心需要知道服务是否"活着"，通常有三种方式：
- **心跳上报**：服务定期向注册中心发送心跳（TTL 模式）
- **主动探测**：注册中心主动调用服务的 `/health` 端点
- **脚本检查**：执行自定义脚本判断服务状态

```json
// Consul 健康检查配置
{
  "service": {
    "name": "user-service",
    "port": 8080,
    "check": {
      "http": "http://localhost:8080/health",
      "interval": "10s",
      "timeout": "3s",
      "deregister_critical_service_after": "60s"
    }
  }
}
```

## 7. 分布式数据管理

### 7.1 Database per Service

微服务的核心原则之一是**每个服务拥有自己的数据库**。这保证了数据自治，但也带来了新的挑战——跨服务的数据一致性如何保证？

### 7.2 Saga 模式

传统单体应用通过数据库事务保证 ACID。微服务中无法使用跨库事务（分布式事务代价太高），因此引入 **Saga 模式**——将一个长事务拆分为多个本地事务，通过补偿机制保证最终一致性。

#### 编排型 Saga (Orchestration)

由一个中心协调器（Saga Orchestrator）来统一调度各步骤：

```
[Saga 协调器]
    │
    ├── ①创建订单 → [订单服务] → 成功
    │
    ├── ②扣减库存 → [库存服务] → 成功
    │
    ├── ③扣款 → [支付服务] → ❌ 失败！
    │
    ├── ④补偿：恢复库存 → [库存服务]
    │
    └── ⑤补偿：取消订单 → [订单服务]
```

```python
# 编排型 Saga 伪代码
class OrderSaga:
    def execute(self, order):
        try:
            # 正向流程
            self.order_service.create_order(order)
            self.inventory_service.deduct_stock(order.items)
            self.payment_service.charge(order.user_id, order.total)
            self.order_service.confirm_order(order.id)
        except PaymentError:
            # 补偿流程（反向执行）
            self.inventory_service.restore_stock(order.items)
            self.order_service.cancel_order(order.id)
        except InventoryError:
            self.order_service.cancel_order(order.id)
```

#### 协调型 Saga (Choreography)

没有中心协调器，各服务通过事件"接力"：

```
[订单服务]            [库存服务]            [支付服务]
    │                     │                     │
    ├─ OrderCreated ─────→│                     │
    │                     ├─ StockDeducted ────→│
    │                     │                     ├─ PaymentFailed
    │                     │←─ CompensateStock ──┤
    │←─ CancelOrder ──────┤                     │
```

| 方式 | 优点 | 缺点 | 适合场景 |
|------|------|------|---------|
| 编排型 | 流程清晰、易理解 | 协调器可能成为单点 | 复杂业务流程 |
| 协调型 | 去中心化、松耦合 | 流程分散、难调试 | 简单流程 |

### 7.3 Event Sourcing 与 CQRS

**Event Sourcing（事件溯源）**：不存储当前状态，而是存储所有状态变更事件。当前状态通过重放事件计算得出。

类比：银行账户不是只记录"余额 1000 元"，而是记录每笔交易：+5000（工资）→ -200（餐饮）→ -3800（房租）。任何时刻的余额都能通过重放交易计算出来。

**CQRS（Command Query Responsibility Segregation）**：将读和写分离到不同的模型。写模型处理命令（事件溯源），读模型维护针对查询优化的视图。

```
写路径 (Command)                    读路径 (Query)
[API] → [Command Handler]          [API] → [Query Handler]
           │                                    │
           ▼                                    ▼
     [Event Store]  ──投影──→  [Read DB (物化视图)]
     (Append Only)              (PostgreSQL/ES/Redis)
```

### 7.4 最终一致性 vs 强一致性

| 特性 | 强一致性 | 最终一致性 |
|------|---------|-----------|
| **定义** | 写入后立即所有节点可见 | 过一段时间后所有节点一致 |
| **延迟** | 高（需要同步等待） | 低（返回响应即可） |
| **可用性** | 低（网络分区时不可用） | 高（允许暂时不一致） |
| **适用** | 金融交易、库存超卖 | 用户画像、排行榜、通知 |

**微服务绝大多数场景选择最终一致性**——用户下单后，他的订单列表可能延迟 1-2 秒才能看到最新订单，这是可接受的。

## 8. 弹性与容错

### 8.1 断路器 (Circuit Breaker)

断路器灵感来自电路中的保险丝——当某个服务频繁失败时，直接"熔断"不再调用，防止级联故障拖垮整个系统。

```
                 Circuit Breaker 状态机

         失败次数达到阈值            超时计时器到期
    ┌──────────────────┐     ┌──────────────────┐
    │                  ▼     │                  ▼
┌───┴───┐         ┌───┴───┐          ┌──────────┐
│Closed │         │ Open  │          │Half-Open │
│(正常)  │         │(熔断)  │          │(试探)     │
└───┬───┘         └───┬───┘          └────┬─────┘
    │                  │                   │
    │   所有请求       快速失败        放入少量请求
    │   正常转发       不调用后端      测试后端是否恢复
    │                                     │
    └──── 成功 ←──────────────────────────┘
                试探成功 → 回到 Closed
                试探失败 → 回到 Open
```

**三个状态**：
- **Closed（关闭/正常）**：请求正常通过，统计失败率
- **Open（打开/熔断）**：快速失败，不再调用下游服务（返回降级响应）
- **Half-Open（半开/试探）**：允许少量请求通过，测试下游是否恢复

### 8.2 超时与重试

**超时**：给每个外部调用设置合理的超时时间。没有超时的调用是定时炸弹——下游服务卡住会拖死上游。

**重试策略——指数退避 + 抖动**：

```
第 1 次重试: 等待 1s + random(0, 0.5s)
第 2 次重试: 等待 2s + random(0, 1.0s)
第 3 次重试: 等待 4s + random(0, 2.0s)
第 4 次重试: 等待 8s + random(0, 4.0s)  ← 最大重试次数
```

抖动（Jitter）的目的是避免**雷群效应（Thundering Herd）**——如果所有客户端都在完全相同的时间重试，会形成流量洪峰。

### 8.3 隔舱模式 (Bulkhead)

类比：泰坦尼克号有多个水密舱——即使一个舱室进水，其他舱室不受影响。

在微服务中，隔舱模式通过隔离资源池来防止级联故障：

```
[服务 A]
├── 线程池 1 (30线程) ──→ 调用用户服务
├── 线程池 2 (30线程) ──→ 调用订单服务（故障！）
└── 线程池 3 (30线程) ──→ 调用商品服务

即使订单服务的线程池耗尽，
用户服务和商品服务的调用不受影响。
```

### 8.4 限流算法

| 算法 | 原理 | 允许突发 | 精度 | 适用场景 |
|------|------|---------|------|---------|
| **令牌桶** | 固定速率放入令牌，请求消耗令牌 | ✅ 桶满时可突发 | 高 | API 网关（允许短时突发） |
| **漏桶** | 请求进入桶，匀速流出 | ❌ 严格匀速 | 高 | 流量整形（匀速消费） |
| **固定窗口** | 固定时间窗口内计数 | ⚠️ 边界突刺 | 低 | 简单场景 |
| **滑动窗口** | 滑动时间窗口统计 | ✅ 平滑 | 高 | 精确限流 |

### 8.5 优雅降级

当核心服务不可用时，提供降级后的"兜底"响应，而非直接报错：

- **缓存兜底**：商品服务不可用时，返回缓存的商品信息（可能不是最新价格）
- **默认值**：推荐服务不可用时，返回热门商品列表
- **功能裁剪**：评论服务不可用时，商品页正常显示，评论区显示"暂不可用"

## 9. 可观测性

### 9.1 三大支柱

微服务的可观测性建立在三大支柱之上：

```
              可观测性 (Observability)
              /        |        \
         Metrics    Logging    Tracing
         (指标)      (日志)     (链路追踪)
         
Metrics：系统"当前状态"的数字 → 发现有问题
Logging：系统"发生了什么"的记录 → 定位问题
Tracing：请求"经过了哪些服务" → 理解因果关系
```

### 9.2 分布式追踪

当一个请求跨越 10+ 个服务时，如何知道延迟发生在哪里？**分布式追踪**通过在请求中传播 **TraceID** 和 **SpanID** 来串联完整调用链。

```
[用户请求]
  │
  ▼ TraceID: abc-123
┌─────────────────────────────────────────────────┐
│ Span 1: API Gateway (20ms)                      │
│   ├── Span 2: User Service (15ms)               │
│   │    └── Span 4: User DB Query (5ms)          │
│   └── Span 3: Order Service (80ms)  ← 慢！       │
│        ├── Span 5: Inventory Service (30ms)      │
│        └── Span 6: Payment Service (40ms)        │
└─────────────────────────────────────────────────┘
```

**OpenTelemetry (OTel)** 是 CNCF 的标准可观测性框架，统一了 Metrics / Logging / Tracing 的 API 和数据格式：

```
应用 + OTel SDK → OTel Collector → Jaeger (Tracing)
                                 → Prometheus (Metrics)
                                 → Loki (Logging)
```

### 9.3 Prometheus + Grafana 监控栈

```yaml
# Prometheus 拉取配置
scrape_configs:
  - job_name: 'user-service'
    kubernetes_sd_configs:
      - role: pod
    relabel_configs:
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
        action: keep
        regex: true
```

### 9.4 结构化日志

微服务中日志必须是**结构化**的（JSON 格式），并且携带 **correlation ID**（与 TraceID 关联），否则无法跨服务串联分析。

```json
{
  "timestamp": "2026-03-17T10:30:00Z",
  "level": "ERROR",
  "service": "order-service",
  "traceId": "abc-123",
  "spanId": "span-5",
  "message": "Failed to deduct inventory",
  "error": "timeout after 3s",
  "orderId": "ORD-456",
  "sku": "SKU-789",
  "userId": "USER-123"
}
```

### 9.5 关键指标方法论

**RED 方法**（适用于请求驱动的服务）：
- **R**ate — 每秒请求数
- **E**rror — 错误率
- **D**uration — 请求延迟分布（p50/p95/p99）

**USE 方法**（适用于资源类指标）：
- **U**tilization — 资源使用率（CPU/内存/磁盘）
- **S**aturation — 资源饱和度（队列长度、等待线程数）
- **E**rrors — 资源错误（网络丢包、磁盘 I/O 错误）

## 10. 服务网格（Service Mesh）

### 10.1 什么是 Service Mesh？

类比：Service Mesh 就像**智能高速公路系统**——路上的摄像头、测速仪、交通信号灯（Sidecar Proxy）统一管理交通流量，而司机（应用代码）只需要专注开车，不需要自己判断哪条路通畅。

Service Mesh 将微服务治理能力（负载均衡、熔断、加密、追踪）从应用代码中抽离出来，下沉到基础设施层。

### 10.2 Sidecar 模式

每个服务实例旁边部署一个**代理（Sidecar Proxy）**，所有进出流量都经过这个代理。

```
┌──────────────────────────────┐
│           Pod                │
│  ┌──────────┐  ┌──────────┐ │
│  │  App     │←→│  Envoy   │ │←→ 外部流量
│  │ (业务代码)│  │ (Sidecar)│ │
│  └──────────┘  └──────────┘ │
└──────────────────────────────┘

数据面 (Data Plane)                控制面 (Control Plane)
┌──────────┐  ┌──────────┐       ┌──────────┐
│ Envoy A  │←→│ Envoy B  │  ←──→ │  Istiod  │
└──────────┘  └──────────┘       │ (Pilot+  │
┌──────────┐  ┌──────────┐       │  Citadel+│
│ Envoy C  │←→│ Envoy D  │  ←──→ │  Galley) │
└──────────┘  └──────────┘       └──────────┘
```

### 10.3 Istio 核心功能

| 功能类别 | 具体能力 |
|---------|---------|
| **流量管理** | 金丝雀发布、A/B 测试、故障注入、超时重试、镜像流量 |
| **安全** | mTLS（零信任网络）、RBAC 授权策略 |
| **可观测性** | 自动注入链路追踪、生成 Prometheus 指标 |

```yaml
# Istio VirtualService：将 10% 流量导向 v2 版本（金丝雀发布）
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: user-service
spec:
  hosts:
    - user-service
  http:
    - route:
        - destination:
            host: user-service
            subset: v1
          weight: 90
        - destination:
            host: user-service
            subset: v2
          weight: 10
```

### 10.4 Service Mesh vs 传统库

| 维度 | 传统库 (Hystrix/Ribbon) | Service Mesh (Istio) |
|------|------------------------|---------------------|
| **侵入性** | 需要在代码中引入 SDK | 应用无感知（Sidecar 注入） |
| **语言限制** | 通常只支持 Java | 支持任何语言 |
| **升级** | 需要修改代码重新部署 | 升级 Sidecar 即可 |
| **性能** | 无额外网络跳转 | 增加一跳延迟（~1-2ms） |
| **运维复杂度** | 低 | 高（需要运维 Istio 控制面） |

## 常见陷阱与最佳实践

### 陷阱

| # | 陷阱 | 后果 | 正确做法 |
|---|------|------|---------|
| 1 | 一开始就拆微服务 | 不了解业务边界导致频繁重构 | 先 Modular Monolith，业务稳定后再拆 |
| 2 | 服务间共享数据库 | 耦合度等同于单体 | 每个服务一个数据库 |
| 3 | 同步调用链过长 | 延迟叠加、级联故障 | 异步消息 + 事件驱动 |
| 4 | 没有全链路追踪 | 出问题时无法定位 | 上线前先搭可观测性 |
| 5 | 忽略 API 版本管理 | 服务升级时调用方崩溃 | 语义化版本 + 向后兼容 |

### 最佳实践

1. **从 Modular Monolith 开始**：只有当明确需要独立部署、独立扩缩容时，才拆分为微服务
2. **先搭可观测性**：先建好监控、日志、追踪基础设施，再拆服务
3. **API 优先 (API First)**：先定义好接口契约（OpenAPI / Protobuf），再实现
4. **拥抱最终一致性**：绝大多数业务不需要强一致性，Saga + 事件驱动足以
5. **自动化一切**：CI/CD、基础设施即代码（IaC）、自动扩缩容
6. **限制技术多样性**：2-3 种主力语言，统一的日志/监控/部署标准
7. **Contract Testing**：用 Pact 等工具保证服务间接口的兼容性
