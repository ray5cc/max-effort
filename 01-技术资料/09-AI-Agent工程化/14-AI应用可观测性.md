## TL;DR 速览

- AI 可观测性 = **Metrics（指标）+ Traces（追踪）+ Logs（日志）**，三大支柱缺一不可
- LLM 调用链追踪需要覆盖：**用户请求 → Prompt 组装 → 模型调用 → Token 流式返回 → 后处理**
- **LangSmith/LangFuse** 是 LLM 应用专用的可观测性平台，提供 Prompt 版本管理和评估
- 核心监控指标：**TTFT、TPS、Token 成本、Error Rate、KV Cache 使用率**
- **OpenTelemetry** 是通用追踪标准，可与 LLM 专用指标结合实现全链路可观测
- 生产环境必须有 **成本看板**：按团队/模型/功能维度统计 Token 消耗和费用
- **告警分级**：P0（服务不可用）→ P1（性能严重退化）→ P2（成本异常）→ P3（质量下降）

## 1. 为什么 AI 应用需要专门的可观测性？

### 1.1 AI 应用的特殊性

传统 Web 应用的可观测性主要关注**请求延迟、错误率、吞吐量**。AI 应用在此基础上增加了全新的维度：

| 维度 | 传统应用 | AI 应用 |
|------|---------|---------|
| 延迟 | 固定、可预测 | 变长（输出越长延迟越高） |
| 成本 | 按 CPU/内存计费 | 按 Token 计费，成本不可预测 |
| 质量 | 二元（对/错） | 连续（回答质量有高低） |
| 可复现性 | 确定性 | 非确定性（temperature > 0） |
| 依赖 | 内部服务 | 外部 LLM 提供商（不可控） |

**类比**：监控传统应用就像监控一条生产线——产品合格率、生产速度都是可量化的。监控 AI 应用像是监控一个创意工作室——除了效率指标外，还要评估"创作质量"。

### 1.2 不可观测的代价

- **成本失控**：某团队的一个循环调用 Bug，一夜之间消耗 $50,000
- **质量退化**：模型提供商默默切换到较差的模型版本，无人发现
- **性能问题**：KV Cache 耗尽导致延迟飙升，用户大量流失
- **排障困难**：Agent 多步执行中某步出错，没有追踪链路无法定位

## 3. LLM 调用链追踪

### 3.1 OpenTelemetry 集成

```python
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter

# 初始化追踪器
provider = TracerProvider()
provider.add_span_processor(
    BatchSpanProcessor(OTLPSpanExporter(endpoint="http://otel-collector:4317"))
)
trace.set_tracer_provider(provider)
tracer = trace.get_tracer("ai-service")

async def handle_chat(request):
    with tracer.start_as_current_span("chat_request") as span:
        span.set_attribute("user.id", request.user_id)
        span.set_attribute("model.name", request.model)
        
        # RAG 检索
        with tracer.start_as_current_span("rag_retrieval") as rag_span:
            docs = await retrieve(request.query)
            rag_span.set_attribute("retrieval.doc_count", len(docs))
            rag_span.set_attribute("retrieval.top_score", docs[0].score)
        
        # LLM 调用
        with tracer.start_as_current_span("llm_call") as llm_span:
            response = await llm.chat(messages, stream=True)
            llm_span.set_attribute("llm.prompt_tokens", response.usage.prompt_tokens)
            llm_span.set_attribute("llm.completion_tokens", response.usage.completion_tokens)
            llm_span.set_attribute("llm.cost_usd", calculate_cost(response.usage))
            llm_span.set_attribute("llm.ttft_ms", response.ttft_ms)
```

### 3.2 Agent 多步执行追踪

```python
async def trace_agent_execution(task: str):
    with tracer.start_as_current_span("agent_execution") as root:
        root.set_attribute("agent.task", task)
        step_count = 0
        total_tokens = 0
        
        for step in agent.run(task):
            step_count += 1
            with tracer.start_as_current_span(f"agent_step_{step_count}") as step_span:
                step_span.set_attribute("step.type", step.type)  # "think" | "tool_call" | "respond"
                
                if step.type == "tool_call":
                    step_span.set_attribute("tool.name", step.tool_name)
                    step_span.set_attribute("tool.args", json.dumps(step.args))
                    step_span.set_attribute("tool.success", step.success)
                
                total_tokens += step.tokens_used
        
        root.set_attribute("agent.total_steps", step_count)
        root.set_attribute("agent.total_tokens", total_tokens)
```

## 4. LangSmith / LangFuse 工程实践

### 4.1 LangFuse（开源方案）

LangFuse（github.com/langfuse/langfuse）是开源的 LLM 可观测性平台：

```python
from langfuse import Langfuse
from langfuse.decorators import observe

langfuse = Langfuse(
    public_key="pk-xxx",
    secret_key="sk-xxx",
    host="https://langfuse.your-domain.com"
)

@observe()  # 自动追踪函数调用
async def chat_with_rag(query: str, user_id: str):
    # RAG 检索 — 自动记录为子 Span
    docs = await retrieve_documents(query)
    
    # LLM 调用 — 自动记录 Token、延迟、成本
    response = await llm.chat(
        messages=build_messages(query, docs),
        model="gpt-4o"
    )
    
    return response

@observe()
async def retrieve_documents(query: str):
    embedding = await embed(query)
    results = await vector_db.search(embedding, top_k=10)
    reranked = await rerank(query, results)
    return reranked[:5]
```

## 6. 成本监控与优化

### 6.1 成本归因

```sql
-- 按团队统计月度成本
SELECT 
    team,
    model,
    SUM(prompt_tokens) AS total_prompt_tokens,
    SUM(completion_tokens) AS total_completion_tokens,
    SUM(cost_usd) AS total_cost,
    COUNT(*) AS request_count,
    AVG(cost_usd) AS avg_cost_per_request
FROM llm_usage_logs
WHERE created_at >= DATE_TRUNC('month', CURRENT_DATE)
GROUP BY team, model
ORDER BY total_cost DESC;
```

### 6.2 成本异常检测

```python
class CostAnomalyDetector:
    """基于移动平均的成本异常检测"""
    
    def check_anomaly(self, team: str, current_cost: float) -> bool:
        # 获取最近 7 天的日均成本
        avg_daily_cost = self.get_avg_daily_cost(team, days=7)
        
        # 如果当日成本超过均值的 3 倍，触发告警
        if current_cost > avg_daily_cost * 3:
            self.alert(
                level="P2",
                message=f"团队 {team} 今日成本 ${current_cost:.2f}，"
                        f"为近 7 日均值 ${avg_daily_cost:.2f} 的 "
                        f"{current_cost/avg_daily_cost:.1f} 倍"
            )
            return True
        return False
```

## 7. 告警策略设计

### 7.1 告警分级

| 级别 | 触发条件 | 响应时间 | 通知方式 |
|------|---------|---------|---------|
| P0 Critical | 服务完全不可用 / 错误率 > 50% | 5 分钟 | 电话 + PagerDuty |
| P1 High | TTFT P99 > 10s / 错误率 > 5% | 15 分钟 | Slack + 短信 |
| P2 Medium | 日成本超预算 3 倍 / GPU 利用率 < 10% | 1 小时 | Slack |
| P3 Low | 质量指标下降 / 缓存命中率下降 | 次日 | 邮件 |

### 7.2 告警规则示例

```yaml
# Prometheus Alerting Rules
groups:
  - name: ai-service-alerts
    rules:
      - alert: LLMServiceDown
        expr: up{job="llm-service"} == 0
        for: 1m
        labels:
          severity: P0
        annotations:
          summary: "LLM 服务不可用"
          
      - alert: HighErrorRate
        expr: |
          sum(rate(llm_request_total{status="error"}[5m]))
          / sum(rate(llm_request_total[5m])) > 0.05
        for: 5m
        labels:
          severity: P1
        annotations:
          summary: "LLM 请求错误率超过 5%"
          
      - alert: HighTTFT
        expr: histogram_quantile(0.99, rate(llm_ttft_seconds_bucket[5m])) > 10
        for: 5m
        labels:
          severity: P1
        annotations:
          summary: "TTFT P99 超过 10 秒"
          
      - alert: KVCacheExhaustion
        expr: gpu_kv_cache_usage_percent > 95
        for: 2m
        labels:
          severity: P1
        annotations:
          summary: "KV Cache 使用率超过 95%，可能导致请求排队"
```

## 8. 常见陷阱与最佳实践

### ❌ 陷阱 1：只监控请求延迟，忽略 TTFT

```python
# ❌ 错误：只关注总延迟
duration = time.time() - start_time
metrics.record("latency", duration)

# ✅ 正确：分别监控 TTFT 和 TPS
metrics.record("ttft", first_token_time - start_time)
metrics.record("tps", total_tokens / (end_time - first_token_time))
metrics.record("total_latency", end_time - start_time)
```

### ❌ 陷阱 2：不做成本归因

```python
# ❌ 错误：只看总成本，不知道谁花了多少
total_cost = sum(all_requests_cost)

# ✅ 正确：按团队/功能/用户维度归因
metrics.record("cost", cost, labels={
    "team": request.team,
    "feature": request.feature,  # "chat" | "search" | "agent"
    "model": request.model,
    "user_tier": request.user_tier  # "free" | "pro"
})
```

### ❌ 陷阱 3：日志中记录完整 Prompt（隐私风险）

```python
# ❌ 错误：日志中包含用户的完整输入
logger.info(f"LLM call: prompt={user_prompt}")

# ✅ 正确：只记录元数据，必要时脱敏
logger.info("llm_call", 
    prompt_tokens=len(tokenize(user_prompt)),
    prompt_hash=hashlib.sha256(user_prompt.encode()).hexdigest()[:8],
    model="gpt-4o"
)
```

### ❌ 陷阱 4：告警阈值一成不变

```yaml
# ❌ 错误：硬编码固定阈值
# 业务增长后，正常流量可能触发告警
- alert: HighQPS
  expr: rate(requests_total[5m]) > 100

# ✅ 正确：基于历史基线的动态阈值
- alert: QPSAnomaly
  expr: |
    rate(requests_total[5m]) 
    > avg_over_time(rate(requests_total[5m])[7d:1h]) * 3
```

### ❌ 陷阱 5：不监控 LLM 提供商的 SLA

```python
# ❌ 错误：假设 OpenAI/Anthropic 总是可用的

# ✅ 正确：监控每个提供商的可用性和延迟
for provider in ["openai", "anthropic", "azure"]:
    metrics.record("provider_availability", 
        1 if is_healthy(provider) else 0,
        labels={"provider": provider})
    metrics.record("provider_latency",
        measure_latency(provider),
        labels={"provider": provider})
```

### 9.1 LLM 质量自动评估

# 使用 LLM-as-Judge 自动评估回答质量
async def auto_evaluate(question, answer, context):
    eval_prompt = f"""评估以下回答的质量（1-5 分）：
    问题：{question}
    参考上下文：{context}
    回答：{answer}
    
    评分维度：
    - 准确性（是否与上下文一致）
    - 完整性（是否回答了问题的所有方面）

    score = await llm.generate(eval_prompt)
    return parse_score(score)
