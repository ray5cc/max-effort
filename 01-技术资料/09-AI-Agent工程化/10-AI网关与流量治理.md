## TL;DR 速览

- AI 网关是连接应用层与 LLM 提供商之间的**统一中间层**，核心职责：路由、认证、限流、可观测性
- **LiteLLM** 支持 100+ 模型提供商的统一 API 适配，是目前最流行的开源 AI 网关
- **Virtual Keys** 实现多租户隔离，每个团队/用户独立的 API Key 和配额管理
- **智能路由** 包含三种策略：延迟优化、成本优化、负载均衡，可按场景动态切换
- **Fallback 链 + Circuit Breaker** 是生产环境必备的高可用机制
- **Prompt Caching** 和 **Semantic Caching** 可减少 30-70% 的 API 调用成本

## 1. 为什么需要 AI 网关？

### 1.1 现实场景

想象你经营一家跨国公司，需要同时使用多家快递公司（如顺丰、DHL、FedEx）。每家快递的下单接口、价格体系、查询 API 都不一样。你可以：
- **方案 A**：每个部门自己对接每家快递——代码重复、无法统一管控
- **方案 B**：建一个统一的"快递中台"——所有部门通过一个接口下单，中台自动选择最优快递

AI 网关就是 LLM 世界的"快递中台"。

### 1.2 核心痛点

| 痛点 | 没有网关 | 有网关 |
|------|---------|--------|
| API 适配 | 每个业务线独立对接 OpenAI/Anthropic/Google 等 | 统一 OpenAI 格式，网关自动转换 |
| 成本管控 | 无法追踪每个团队的 Token 消耗 | Virtual Keys + Token 计量 + 预算告警 |
| 高可用 | 单一提供商故障 = 服务中断 | 自动 Fallback 到备用提供商 |
| 安全 | API Key 散落在各个服务中 | 集中管理，应用层不接触真实 Key |
| 可观测性 | 无法统一追踪请求链路 | 全链路日志、延迟监控、成本看板 |

### 1.3 行业实践

- **OpenAI** 自身就是一个巨大的 AI 网关（路由到不同的模型集群）
- **Cloudflare AI Gateway** 提供商业级 AI 流量管理
- **字节跳动/阿里云** 内部 AI 中台本质上就是定制化的 AI 网关
- **Portkey** 和 **LiteLLM** 是开源领域的领先方案

## 2. AI 网关核心架构

### 2.1 七层架构设计

```
┌──────────────────────────────────────────────────────┐
│                    应用层 (Clients)                    │
│          Chat App / Agent / RAG Pipeline              │
└───────────────────────┬──────────────────────────────┘
                        │ OpenAI-compatible API
┌───────────────────────▼──────────────────────────────┐
│                    AI 网关 (Gateway)                   │
│  ┌────────────┐  ┌──────────┐  ┌───────────────┐    │
│  │ 认证 & 限流 │  │ 路由引擎  │  │ 成本管控引擎  │    │
│  └─────┬──────┘  └────┬─────┘  └──────┬────────┘    │
│        │              │               │              │
│  ┌─────▼──────────────▼───────────────▼────────┐     │
│  │              中间件链 (Middleware)             │     │
│  │  Logging → Cache → Transform → Retry        │     │
│  └─────────────────────┬───────────────────────┘     │
│                        │                             │
│  ┌─────────────────────▼───────────────────────┐     │
│  │           Provider 适配层 (Adapters)          │     │
│  │  OpenAI │ Anthropic │ Google │ Azure │ ...  │     │
│  └─────────────────────┬───────────────────────┘     │
└────────────────────────┬─────────────────────────────┘
                         │
┌────────────────────────▼─────────────────────────────┐
│              LLM 提供商 / 自托管推理引擎               │
│    GPT-4o │ Claude │ Gemini │ vLLM │ SGLang          │
└──────────────────────────────────────────────────────┘
```

### 2.2 请求处理流程

```
Request → 认证校验 → 限流检查 → 缓存查询
  → [命中] → 返回缓存结果
  → [未命中] → 路由决策 → Provider 适配 → 转发请求
    → [成功] → 写入缓存 → Token计量 → 返回结果
    → [失败] → Fallback → 重试 → [最终失败] → 返回错误
```

## 3. LiteLLM 工程实践

### 3.1 LiteLLM 架构（github.com/BerriAI/litellm）

LiteLLM 是最流行的开源 AI 网关，核心价值在于提供统一的 OpenAI 格式 API，内部自动适配 100+ 模型提供商。

**快速部署**：

```bash
# Docker 部署（推荐）
docker run -d \
  --name litellm \
  -p 4000:4000 \
  -e OPENAI_API_KEY=sk-xxx \
  -e ANTHROPIC_API_KEY=sk-ant-xxx \
  -v $(pwd)/config.yaml:/app/config.yaml \
  ghcr.io/berriai/litellm:main-latest \
  --config /app/config.yaml
```

**核心配置文件**：

```yaml
# config.yaml
model_list:
  # OpenAI 模型
  - model_name: gpt-4o
    litellm_params:
      model: openai/gpt-4o
      api_key: os.environ/OPENAI_API_KEY
      
  # Anthropic 模型
  - model_name: claude-sonnet
    litellm_params:
      model: anthropic/claude-sonnet-4-20250514
      api_key: os.environ/ANTHROPIC_API_KEY
      
  # 自托管 vLLM
  - model_name: llama-70b
    litellm_params:
      model: openai/meta-llama/Llama-3.1-70B-Instruct
      api_base: http://vllm-service:8000/v1
      api_key: "none"

  # 同一模型多个提供商（用于 Fallback）
  - model_name: gpt-4o
    litellm_params:
      model: azure/gpt-4o
      api_base: https://my-azure.openai.azure.com
      api_key: os.environ/AZURE_API_KEY

# 路由策略
router_settings:
  routing_strategy: latency-based-routing
  num_retries: 3
  timeout: 60
  allowed_fails: 2

# 通用设置  
general_settings:
  master_key: sk-master-key-xxx
  database_url: postgresql://user:pass@db:5432/litellm
  enable_jwt_auth: true
```

### 3.2 统一 API 调用

LiteLLM 的核心价值 — 所有模型使用相同的 OpenAI 格式 API：

```python
import litellm

# 调用 OpenAI
response = litellm.completion(
    model="gpt-4o",
    messages=[{"role": "user", "content": "Hello"}]
)

# 调用 Anthropic — 接口完全相同！
response = litellm.completion(
    model="anthropic/claude-sonnet-4-20250514",
    messages=[{"role": "user", "content": "Hello"}]
)

# 调用自托管 vLLM — 接口完全相同！
response = litellm.completion(
    model="openai/llama-70b",
    api_base="http://vllm:8000/v1",
    messages=[{"role": "user", "content": "Hello"}]
)

# 流式调用
response = litellm.completion(
    model="gpt-4o",
    messages=[{"role": "user", "content": "Write a poem"}],
    stream=True
)
for chunk in response:
    print(chunk.choices[0].delta.content, end="")
```

## 4. 多模型路由策略

> 📖 **深入学习**：路由算法的底层实现与健康检查机制请参阅 [LLM服务编排与成本治理 §4](./11-LLM服务编排与成本治理.md#4-多模型路由与负载均衡)

### 4.1 路由策略对比

| 策略 | 原理 | 适用场景 |
|------|------|---------|
| 延迟优化 | 选择历史延迟最低的提供商 | 实时交互类应用 |
| 成本优化 | 选择单位 Token 最便宜的模型 | 批处理、非实时任务 |
| 负载均衡 | Round-Robin 或加权轮询 | 多提供商分散风险 |
| 智能路由 | 根据请求内容选择最适合的模型 | 质量与成本平衡 |
| 模型级联 | 小模型先试，不确定时升级到大模型 | 成本敏感场景 |

### 4.2 模型级联（Cascade Routing）实践

```python
# 模型级联：简单问题用便宜模型，复杂问题用高级模型
import litellm

async def cascade_route(messages):
    # 第一层：用小模型判断复杂度
    classifier = await litellm.acompletion(
        model="gpt-4o-mini",
        messages=[{
            "role": "system",
            "content": "Classify if this query is SIMPLE or COMPLEX. Reply only SIMPLE or COMPLEX."
        }] + messages,
        max_tokens=10
    )
    
    complexity = classifier.choices[0].message.content.strip()
    
    if complexity == "SIMPLE":
        # 简单问题用便宜模型
        return await litellm.acompletion(model="gpt-4o-mini", messages=messages)
    else:
        # 复杂问题用高级模型
        return await litellm.acompletion(model="gpt-4o", messages=messages)
```

### 4.3 LiteLLM 路由配置

```yaml
# config.yaml — 延迟优化路由
router_settings:
  routing_strategy: latency-based-routing
  # 路由基于最近 N 次请求的平均延迟
  routing_strategy_args:
    ttl: 300  # 延迟数据有效期（秒）
    lowest_latency_buffer: 0.1  # 10% 的延迟容忍度

# 成本优化路由
router_settings:
  routing_strategy: cost-based-routing

# 自定义权重路由  
router_settings:
  routing_strategy: usage-based-routing
  # 70% 流量到 OpenAI，30% 到 Azure
```

## 5. 认证授权与多租户

### 5.1 Virtual Keys 体系

Virtual Keys 是 AI 网关的核心安全机制——应用层不接触真实的提供商 API Key：

```
应用 A (key: vk-team-a-xxx)  ──┐
                                ├→ AI 网关 → 真实 API Key → OpenAI
应用 B (key: vk-team-b-xxx)  ──┘
```

**LiteLLM Virtual Key 管理**：

```bash
# 创建 Virtual Key（通过 API）
curl -X POST http://gateway:4000/key/generate \
  -H "Authorization: Bearer sk-master-key" \
  -H "Content-Type: application/json" \
  -d '{
    "duration": "30d",
    "models": ["gpt-4o", "claude-sonnet"],
    "max_budget": 100.0,
    "tpm_limit": 100000,
    "rpm_limit": 1000,
    "metadata": {"team": "backend", "project": "chatbot"}
  }'
```

### 5.2 RBAC 与团队管理

```yaml
# 角色定义
# admin: 管理所有 Key、查看全局统计
# team_admin: 管理本团队的 Key 和预算
# user: 使用分配的 Key 调用 API

# 团队预算隔离
general_settings:
  enable_jwt_auth: true
  
litellm_settings:
  max_budget: 10000  # 全局月度预算上限 $10,000
  budget_duration: 1mo
```

## 6. 成本管控与优化

### 6.1 Token 计量与计费

LiteLLM 自动追踪每次调用的 Token 消耗和成本：

```sql
-- 查询各团队的月度消耗
SELECT 
  metadata->>'team' AS team,
  SUM(prompt_tokens) AS total_prompt_tokens,
  SUM(completion_tokens) AS total_completion_tokens,
  SUM(spend) AS total_spend
FROM litellm_spendlogs
WHERE starttime >= DATE_TRUNC('month', CURRENT_DATE)
GROUP BY metadata->>'team'
ORDER BY total_spend DESC;
```

### 6.2 Prompt Caching

主流提供商（OpenAI、Anthropic、Google）都支持 Prompt Caching，对于共享系统提示词的场景可节省大量成本：

```python
# Anthropic Prompt Caching 示例
response = litellm.completion(
    model="anthropic/claude-sonnet-4-20250514",
    messages=[
        {
            "role": "system",
            "content": [
                {
                    "type": "text",
                    "text": very_long_system_prompt,  # 长系统提示词
                    "cache_control": {"type": "ephemeral"}  # 标记为可缓存
                }
            ]
        },
        {"role": "user", "content": user_query}
    ]
)
# 首次调用: 正常价格
# 后续调用: 缓存命中部分价格降低 90%
```

### 6.3 Semantic Caching

```python
# LiteLLM 语义缓存配置
litellm_settings:
  cache: true
  cache_params:
    type: redis
    host: redis
    port: 6379
    
    # 语义缓存（基于 Embedding 相似度）
    supported_call_types: ["acompletion", "completion"]
    similarity_threshold: 0.95  # 相似度阈值
    ttl: 3600  # 缓存有效期
```

**成本优化策略总结**：

| 策略 | 节省比例 | 实现复杂度 | 适用场景 |
|------|---------|-----------|---------|
| Prompt Caching | 50-90% | 低 | 共享系统提示词 |
| Semantic Caching | 30-50% | 中 | 高频相似查询 |
| 模型级联 | 40-70% | 中 | 混合难度查询 |
| Batch API | 50% | 低 | 非实时任务 |

## 7. 高可用与容错设计

### 7.1 Fallback 链

```yaml
# LiteLLM Fallback 配置
model_list:
  - model_name: gpt-4o
    litellm_params:
      model: openai/gpt-4o         # 主选
  - model_name: gpt-4o
    litellm_params:
      model: azure/gpt-4o          # 备选 1
  - model_name: gpt-4o
    litellm_params:
      model: anthropic/claude-sonnet-4-20250514  # 备选 2

router_settings:
  num_retries: 3
  timeout: 30
  fallbacks: [
    {"gpt-4o": ["azure/gpt-4o", "anthropic/claude-sonnet-4-20250514"]}
  ]
```

### 7.2 Circuit Breaker 模式

```python
# 当某个提供商连续失败 N 次后，暂时停止向其发送请求
router_settings:
  allowed_fails: 3          # 允许连续失败次数
  cooldown_time: 60          # 熔断冷却时间（秒）
  # 3 次连续失败后，该提供商被暂时移出路由池 60 秒
```

**类比**：像家里的电路保险丝，当电流过大（连续故障）时自动断开，保护整个电路（系统），冷却后自动恢复。

### 7.3 限流保护

```yaml
# 多层限流
general_settings:
  # 全局限流
  global_max_parallel_requests: 1000
  
# Per-Key 限流（创建 Key 时指定）
# tpm_limit: 100000  # Token per Minute
# rpm_limit: 1000    # Request per Minute
```

## 8. Nginx/OpenResty 在 AI 场景的应用

### 8.1 为什么 AI 场景需要 Nginx？

在企业架构中，AI 网关（如 LiteLLM）前面通常还会部署 Nginx 作为反向代理和负载均衡器：

```
Client → Nginx (L7) → LiteLLM Gateway → LLM Provider
                 │
                 ├─ SSL 终结
                 ├─ IP 限流
                 ├─ 负载均衡（多个 LiteLLM 实例）
                 └─ SSE 流式代理
```

### 8.2 SSE 流式代理配置

AI 应用的流式输出是 Nginx 配置的关键挑战：

```nginx
# nginx.conf — AI 网关反向代理
upstream litellm_backend {
    server litellm-1:4000;
    server litellm-2:4000;
    keepalive 32;
}

server {
    listen 443 ssl;
    server_name ai-gateway.example.com;

    # SSL 配置
    ssl_certificate /etc/ssl/certs/server.crt;
    ssl_certificate_key /etc/ssl/keys/server.key;

    location /v1/ {
        proxy_pass http://litellm_backend;
        
        # 关键：SSE 流式传输配置
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_buffering off;           # 禁用缓冲，实现实时流式传输
        proxy_cache off;
        chunked_transfer_encoding on;
        
        # 超时设置（LLM 生成可能较慢）
        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
        
        # 请求头传递
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Request-ID $request_id;
    }
}
```

## 9. 常见陷阱与最佳实践

### ❌ 陷阱 1：API Key 硬编码在应用代码中

```python
# ❌ 错误：API Key 散落在各个微服务中
client = OpenAI(api_key="sk-real-key-xxx")

# ✅ 正确：通过 AI 网关的 Virtual Key 调用
client = OpenAI(
    api_key="vk-team-backend-xxx",  # Virtual Key
    base_url="http://ai-gateway:4000/v1"
)
```

### ❌ 陷阱 2：没有 Fallback 机制

```yaml
# ❌ 错误：只配置一个提供商，故障 = 全站不可用
model_list:
  - model_name: gpt-4o
    litellm_params:
      model: openai/gpt-4o

# ✅ 正确：配置多提供商 Fallback
model_list:
  - model_name: gpt-4o
    litellm_params:
      model: openai/gpt-4o
  - model_name: gpt-4o
    litellm_params:
      model: azure/gpt-4o  # 备选
```

### ❌ 陷阱 3：Nginx 开启了 proxy_buffering

```nginx
# ❌ 错误：默认 proxy_buffering on，SSE 流式响应被缓冲
location /v1/ {
    proxy_pass http://backend;
    # proxy_buffering 默认为 on
}

# ✅ 正确：显式关闭 buffering
location /v1/ {
    proxy_pass http://backend;
    proxy_buffering off;
    proxy_cache off;
}
```

### ❌ 陷阱 4：不设置预算上限

```bash
# ❌ 错误：不设上限，一个 Bug 可能烧掉数万美元
# 某团队的循环调用 Bug 导致一夜之间消耗 $50,000

# ✅ 正确：设置多层预算防护
curl -X POST http://gateway:4000/key/generate \
  -d '{"max_budget": 500, "budget_duration": "1d"}'
# 每日预算 $500，超出自动拒绝
```

### ❌ 陷阱 5：忽略流式场景的超时设置

```nginx
# ❌ 错误：使用默认 60 秒超时
proxy_read_timeout 60s;  # LLM 长输出可能超过 60 秒

# ✅ 正确：根据最大生成长度设置合理超时
proxy_read_timeout 300s;  # 5 分钟，足够大部分生成任务
```

## 10. 延伸与前沿

### 10.1 AI 网关的标准化趋势

- **OpenAI API 成为事实标准**：几乎所有 LLM 提供商都兼容 OpenAI API 格式
- **MCP 协议互操作**：AI 网关开始集成 MCP 协议，为 Agent 提供工具发现和调用能力
- **A2A 协议**：Google 提出的 Agent-to-Agent 协议，AI 网关可作为 A2A 的路由层

### 10.2 新兴开源方案

- **Portkey**（github.com/Portkey-ai/gateway）：专注于可观测性的 AI 网关
- **Kong AI Gateway**：基于 Kong 的 AI 插件生态
- **MLflow AI Gateway**：面向 ML 平台的网关方案

### 10.3 未来趋势

1. **智能化路由**：基于请求语义自动选择最适合的模型（不只是负载均衡）
2. **统一 Agent 网关**：AI 网关 + MCP Server + A2A Hub 合为一体
3. **边缘 AI 网关**：在 CDN 边缘节点部署小模型，大模型回源
