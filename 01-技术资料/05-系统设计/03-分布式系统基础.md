## 1. 为什么需要分布式系统？

### 单机的三个瓶颈

想象你经营一家餐厅：

- **性能瓶颈**：一个厨师做菜速度再快，也无法同时服务 1000 桌客人 → **需要多个厨师（水平扩展）**
- **可用性风险**：唯一的厨师请假了，餐厅就关门 → **需要备用厨师（冗余）**
- **容量限制**：一个冰箱放不下所有食材 → **需要多个冰箱（分片存储）**

分布式系统就是用多台机器协作解决这三个问题。但它也引入了新问题：**网络延迟、部分故障、数据一致性**。

### 核心挑战

| 挑战       | 类比                         | 说明                           |
| ---------- | ---------------------------- | ------------------------------ |
| 网络不可靠 | 电话可能断线                 | 消息可能丢失、延迟、乱序、重复 |
| 时钟不同步 | 每个人的手表时间不一样       | 无法用本地时间判断事件先后     |
| 部分故障   | 一个厨师倒下，其他厨师不知道 | 无法区分"节点挂了"和"网络断了" |

## 2. CAP 定理与一致性模型

### 2.1 CAP 定理

**CAP 定理**（Eric Brewer, 2000）：分布式系统最多只能同时满足三项中的两项：

```
        C（一致性）
       / \
      /   \
     /     \
    CP      CA  ← CA 在网络分区时不可能
   /         \      （网络必然可能分区）
  /           \
 P（分区容忍）── AP
```

- **C（Consistency）一致性**：所有节点看到相同的数据
- **A（Availability）可用性**：每个请求都能得到响应
- **P（Partition Tolerance）分区容忍**：网络分区时系统仍能工作

**关键理解**：因为网络分区是不可避免的（P 必须有），实际选择只有 **CP** 或 **AP**：

| 选择 | 含义                             | 典型系统                 |
| ---- | -------------------------------- | ------------------------ |
| CP   | 网络分区时牺牲可用性，保证一致性 | ZooKeeper, etcd, HBase   |
| AP   | 网络分区时牺牲一致性，保证可用性 | Cassandra, DynamoDB, DNS |

### 2.2 一致性级别

从强到弱：

| 级别           | 含义                         | 类比                                   |
| -------------- | ---------------------------- | -------------------------------------- |
| **线性一致性** | 任何读操作都能看到最近的写   | 所有人看同一块白板                     |
| **顺序一致性** | 所有节点看到相同顺序         | 看同一个录像（可能有延迟，但顺序一致） |
| **因果一致性** | 有因果关系的操作顺序一致     | 回复一定在原消息之后看到               |
| **最终一致性** | 停止写入后，最终所有节点一致 | 谣言传播——最终所有人都会知道           |

### 2.3 PACELC 理论

CAP 的扩展：即使**没有分区**（正常情况），也要在 **延迟（Latency）** 和 **一致性（Consistency）** 之间选择。

```
如果 Partition：选 A（可用）还是 C（一致）？
否则（Else）：选 L（低延迟）还是 C（强一致）？
```

## 3. 共识算法：Raft

### 3.1 为什么需要共识？

多台机器要对"谁是 leader"、"当前数据是什么"达成一致意见。类比：一个委员会要做决定，但成员之间通过写信沟通（可能丢信），怎么确保多数人同意？

### 3.2 Raft 的三个角色

```
┌─────────┐     ┌─────────┐     ┌─────────┐
│ Leader  │────▶│ Follower│     │ Follower│
│（领导者）│     │（跟随者）│     │（跟随者）│
└─────────┘     └─────────┘     └─────────┘
     │                               │
     │          ┌─────────┐          │
     └────────▶│ Follower│◀─────────┘
                │（跟随者）│
                └─────────┘

   选举超时 → Follower 变成 Candidate → 获得多数票 → 成为 Leader
```

### 3.3 Raft 的三个子问题

**1. 领导选举（Leader Election）**

- 每个节点有一个随机选举超时时间（150-300ms）
- 超时未收到 Leader 心跳 → 变成 Candidate → 向其他节点请求投票
- 获得多数票 → 成为新 Leader
- **随机超时**确保不会所有节点同时发起选举

**2. 日志复制（Log Replication）**

```
客户端请求 → Leader 追加到本地日志 → 发送给所有 Follower
→ 多数 Follower 确认 → Leader 提交该条目 → 回复客户端
```

**3. 安全性（Safety）**

- 一个 term 内最多一个 Leader
- Leader 的日志一定包含所有已提交的条目
- Candidate 的日志必须足够新才能赢得选举

### 3.4 工程实现

| 系统        | 共识算法   | 用途                |
| ----------- | ---------- | ------------------- |
| etcd        | Raft       | Kubernetes 状态存储 |
| Consul      | Raft       | 服务发现 + KV 存储  |
| TiKV        | Multi-Raft | 分布式事务 KV       |
| CockroachDB | Multi-Raft | 分布式 SQL          |

## 4. 分布式事务

### 4.1 为什么分布式事务困难？

单机事务靠 ACID 保证。但当数据分布在多台机器上，一个操作可能需要跨多个节点提交。**任何一个节点可能在任何时刻故障**。

### 4.2 两阶段提交（2PC）

```
阶段 1（准备）：
  协调者 → 所有参与者："请准备提交"
  参与者 → 协调者："准备好了" 或 "失败"

阶段 2（提交/回滚）：
  如果所有参与者都说"准备好了"：
    协调者 → 所有参与者："提交！"
  否则：
    协调者 → 所有参与者："回滚！"
```

**问题**：协调者故障 → 参与者永远阻塞等待（**阻塞问题**）。

### 4.3 Saga 模式

将大事务拆成一系列小事务，每个小事务有**补偿操作**：

```
订单流程 Saga：
  T1: 创建订单
  T2: 扣减库存
  T3: 扣减余额

如果 T3 失败：
  C2: 恢复库存（T2 的补偿）
  C1: 取消订单（T1 的补偿）
```

**优势**：无阻塞，每个服务独立事务
**劣势**：不保证隔离性，补偿逻辑编写复杂

### 4.4 TCC（Try-Confirm-Cancel）

```
Try：预留资源（如冻结 100 元）
Confirm：确认操作（扣除冻结的 100 元）
Cancel：释放资源（解冻 100 元）
```

适用于需要强一致性的场景（支付、转账）。

## 5. 负载均衡与服务发现

### 5.1 负载均衡策略

| 策略                | 原理                         | 适用场景        |
| ------------------- | ---------------------------- | --------------- |
| 轮询（Round Robin） | 依次分配请求                 | 服务器性能均匀  |
| 加权轮询            | 按权重分配（性能好的权重大） | 服务器性能不均  |
| 最少连接            | 分配给当前连接最少的服务器   | 长连接场景      |
| 一致性哈希          | 按 key 的哈希值路由          | 有状态服务/缓存 |
| 随机                | 随机选一台                   | 简单场景        |

### 5.2 服务发现

**问题**：微服务数百个实例动态上下线，客户端怎么知道去连谁？

**方案 1：客户端发现**

```
服务 A → 查询注册中心（Consul/Eureka） → 获得服务 B 的地址列表 → 自行选择
```

**方案 2：服务端发现**

```
服务 A → 负载均衡器（Nginx/ALB） → 负载均衡器查询注册中心 → 路由到服务 B
```

**Kubernetes 的方案**：通过 Service + kube-proxy 实现透明的服务发现和负载均衡。

## 6. 数据分片与一致性哈希

### 6.1 为什么需要分片？

当数据量超过单台机器的容量（比如 10TB 数据，单机只有 2TB 磁盘），需要把数据分散到多台机器上。

### 6.2 分片策略

**范围分片**：按 key 的范围分（如 A-M 到节点 1，N-Z 到节点 2）

- 优点：范围查询高效
- 缺点：可能数据倾斜（热点 key 都在一个分片）

**哈希分片**：`hash(key) % N` 决定分到哪个节点

- 优点：数据均匀分布
- 缺点：增减节点时需要**大量数据迁移**

### 6.3 一致性哈希

**解决问题**：普通哈希在节点数变化时，几乎所有 key 都要重新分配。一致性哈希只影响相邻节点。

```
想象一个环形钟表（0 到 2³²-1）：

        0
       / \
     N1   \        节点和 key 都映射到环上
    /       N3     每个 key 顺时针找到的第一个节点
   |         |     就是它的归属节点
    \       /
     N2   /
       \ /
        ↓

添加新节点 N4：只有 N4 逆时针到 N3 之间的 key 需要迁移
删除节点 N2：只有 N2 上的 key 迁移到下一个节点
```

**虚拟节点**：一个物理节点映射多个虚拟节点到环上，解决数据不均匀问题。

## 7. 分布式缓存策略

### 7.1 缓存模式

| 模式              | 读                            | 写                | 适用           |
| ----------------- | ----------------------------- | ----------------- | -------------- |
| **Cache-Aside**   | 先查缓存，miss 查 DB 后写缓存 | 先写 DB，再删缓存 | 通用（最常用） |
| **Read-Through**  | 缓存自己负责从 DB 加载        | -                 | 封装好的缓存层 |
| **Write-Through** | -                             | 同步写缓存+DB     | 一致性要求高   |
| **Write-Behind**  | -                             | 异步批量写 DB     | 写密集场景     |

### 7.2 缓存常见问题

**缓存穿透**：查询不存在的 key，每次都打到 DB

- 解决：布隆过滤器 / 缓存空值

**缓存击穿**：热点 key 过期瞬间，大量请求涌入 DB

- 解决：互斥锁（只允许一个请求重建缓存）/ 逻辑过期（永不真正过期）

**缓存雪崩**：大量 key 同时过期

- 解决：过期时间加随机值 / 多级缓存（L1 本地 + L2 Redis）

### 8.1 可观测性三大支柱

| 支柱                   | 工具                          | 作用                          |
| ---------------------- | ----------------------------- | ----------------------------- |
| **日志（Logs）**       | ELK、Loki                     | 记录离散事件（错误、审计）    |

| **链路追踪（Traces）** | Jaeger、Zipkin、OpenTelemetry | 跟踪请求在微服务间的完整路径  |

### 8.2 容错模式

| 模式         | 原理                       | 类比                                   |
| ------------ | -------------------------- | -------------------------------------- |
| **重试**     | 失败后重新尝试（指数退避） | 打电话占线，过一会再打                 |
| **超时**     | 限制等待时间               | 等公交超过 10 分钟就打车               |
| **熔断**     | 错误率过高时直接拒绝       | 保险丝——电流过大自动断开保护电路       |
| **限流**     | 限制请求速率               | 地铁高峰限流进站                       |
| **舱壁隔离** | 不同服务用不同资源池       | 泰坦尼克号的水密舱——一个进水不影响其他 |

### 8.3 熔断器状态机

```
    正常请求
       ↓
  ┌─────────┐    错误率超过阈值    ┌─────────┐
  │  CLOSED  │ ──────────────────▶ │   OPEN   │
  │（正常通过）│                     │（快速失败）│
  └─────────┘                     └─────────┘
       ↑                               │
       │    探测请求成功               等待超时
       │                               │
  ┌─────────┐                          │
  │HALF-OPEN │ ◀────────────────────────┘
  │（试探通过）│
  └─────────┘
```

## 9. 分布式锁

### 9.1 为什么需要分布式锁？

**类比**：单机程序中，多个线程抢同一个资源用 `synchronized` / `mutex`。但在分布式系统中，多个服务实例运行在不同机器上，本地锁完全无效——你需要一个**所有机器都认可的"全局锁管家"**。

**典型场景**：

- 电商秒杀：多个服务实例同时扣减库存
- 定时任务：多个实例中只有一个执行
- 分布式 ID 生成：防止重复

### 9.2 Redis 分布式锁

**基本实现**：

```python
import redis
import uuid
import time

class RedisLock:
    def __init__(self, client, key, ttl=10):
        self.client = client
        self.key = f"lock:{key}"
        self.ttl = ttl
        self.token = str(uuid.uuid4())  # 唯一标识，防止误释放

    def acquire(self, timeout=5):
        """获取锁，带超时"""
        end = time.time() + timeout
        while time.time() < end:
            if self.client.set(self.key, self.token, nx=True, ex=self.ttl):
                return True
            time.sleep(0.01)
        return False

    def release(self):
        """释放锁（Lua 脚本保证原子性）"""
        lua_script = """
        if redis.call("GET", KEYS[1]) == ARGV[1] then
            return redis.call("DEL", KEYS[1])
        else
            return 0
        end
        """
        self.client.eval(lua_script, 1, self.key, self.token)
```

**为什么释放锁要用 Lua 脚本？** 因为"检查是否是自己的锁"和"删除锁"必须是原子操作。否则：

1. A 检查：是我的锁 ✓
2. A 的锁过期，B 获取了新锁
3. A 删除锁 → 删掉了 B 的锁！

### 9.3 Redlock 算法

单 Redis 实例的锁有单点故障问题。Redis 作者 antirez 提出 **Redlock**：

```
前提：N 个独立的 Redis 实例（推荐 N=5）

获取锁：
  1. 记录当前时间 T1
  2. 依次向 N 个实例发送 SET key value NX EX ttl
  3. 如果在 N/2+1 个实例上成功获取 → 锁获取成功
  4. 实际有效期 = ttl - (当前时间 - T1)
  5. 如果失败 → 向所有实例发送 DEL 释放

关键点：
  - 使用多数派（N/2+1），即使少数节点宕机也能正常工作
  - 时钟漂移容忍：有效期会扣除获取锁的耗时
```

> **争议**：Martin Kleppmann 在其著名博文 "How to do distributed locking" 中指出 Redlock 在 GC 暂停、时钟跳变等场景下可能不安全。如果需要绝对正确性，应使用 ZooKeeper / etcd 等共识系统。

### 9.4 ZooKeeper / etcd 分布式锁

基于共识协议的锁更加可靠：

```
ZooKeeper 临时顺序节点实现：
  /locks/resource1/
    ├── lock-0000000001  (Client A 创建)
    ├── lock-0000000002  (Client B 创建)
    └── lock-0000000003  (Client C 创建)

  规则：序号最小的节点持有锁
  Client A (0001) → 我是最小的，获取锁
  Client B (0002) → 我不是最小的，监听 0001 的删除事件
  Client C (0003) → 监听 0002 的删除事件

  Client A 完成后删除 0001 → Client B 收到通知 → B 获取锁

  优势：Client 断开连接 → 临时节点自动删除 → 自动释放锁（无需 TTL）
```

## 10. 逻辑时钟

### 10.1 为什么不能用物理时钟？

分布式系统中的不同机器各自有独立时钟，即使用 NTP 同步也会有**毫秒级误差**。两个事件 A 和 B，仅凭物理时间戳无法确定因果关系。

**类比**：两个人在不同城市写日记，各自手表差 5 分钟。仅凭日记上的时间无法判定"A 的第 3 条笔记是否在 B 的第 2 条之前写的"。

### 10.2 Lamport 时钟

**规则**：

1. 每个进程维护一个计数器 C
2. 本地事件：C = C + 1
3. 发送消息：消息带上当前 C，C = C + 1
4. 接收消息：C = max(C, 消息中的 C) + 1

```
进程 P1: ●(1) ──send──▶ ●(2) ── ●(3) ──────────── ●(6)
                                                       ↑ recv
进程 P2: ●(1) ── ●(2) ─── ●(3) ──send──▶ ●(4) ── ●(5)
                                 ↓ recv
进程 P3: ●(1) ────────── ●(4) ── ●(5) ──────────── ●(6)

Lamport 时钟保证：如果 A → B（A 因果先于 B），则 C(A) < C(B)
但反过来不成立：C(A) < C(B) 不代表 A → B（可能是并发的）
```

### 10.3 向量时钟（Vector Clock）

向量时钟可以检测**并发**：每个进程维护一个 N 维向量。

```
3 个进程的向量时钟：

P1: [1,0,0] → [2,0,0] → send → [3,0,0] ─────────────── [4,2,3]
                                                            ↑ recv
P2: [0,1,0] → [0,2,0] ── recv → [3,3,0] → send → [3,4,0]
                                              ↓ recv
P3: [0,0,1] ───────────── [0,0,2] → recv → [3,4,3]

判断因果关系：
  向量 A ≤ 向量 B（每一位都 ≤）→ A 因果先于 B
  否则 → A 和 B 并发

例：[2,0,0] < [3,3,0] → 因果关系
   [3,4,0] 与 [0,0,2] → 并发！（3>0 但 0<2）
```

**实际应用**：Amazon Dynamo 使用向量时钟检测写冲突，在多个副本同时写入时保留所有版本让客户端解决冲突。

## 11. CRDT（无冲突复制数据类型）

### 11.1 什么是 CRDT？

**类比**：想象多个人在不同白板上写字。传统方式需要一个"裁判"决定冲突（强一致性）。CRDT 的设计让所有人随意写，最终自动合并且结果一定一致——**数学上保证无冲突**。

CRDT（Conflict-free Replicated Data Type）是一种特殊的数据结构，满足：

- 任意副本可以独立修改
- 副本间可以以任意顺序同步
- 最终一定收敛到相同状态

### 11.2 两种 CRDT 类型

| 类型      | 全称            | 同步方式             | 示例                 |
| --------- | --------------- | -------------------- | -------------------- |
| **CmRDT** | Operation-based | 同步操作（增、删）   | 适合有可靠广播的场景 |
| **CvRDT** | State-based     | 同步完整状态 + merge | 适合间歇性连接的场景 |

### 11.3 常见 CRDT 数据结构

**G-Counter（只增计数器）**：

```
每个节点维护自己的计数器：
  Node A: {A: 5, B: 0, C: 0}
  Node B: {A: 0, B: 3, C: 0}
  Node C: {A: 0, B: 0, C: 7}

  merge: {A: max(5,0,0), B: max(0,3,0), C: max(0,0,7)} = {A:5, B:3, C:7}
  总值: 5 + 3 + 7 = 15

  无论以什么顺序 merge，结果总是 15！
```

**LWW-Register（Last-Writer-Wins 寄存器）**：

```
每次写入带时间戳，merge 时取时间戳最大的值
  Node A: {value: "hello", ts: 100}
  Node B: {value: "world", ts: 200}

  merge → {value: "world", ts: 200}  (B 的写入更晚)
```

**OR-Set（Observed-Remove Set）**：

```
每个添加操作带唯一标签，删除只标记看到的标签
  可以安全地处理"添加 X"和"删除 X"的并发冲突
  添加总是赢（如果你没看到某个添加，你的删除不影响它）
```

## 12. Gossip 协议

### 12.1 核心思想

**类比**：想象一个八卦在学校里传播。一个人知道了一个消息，告诉几个朋友，朋友再告诉他们的朋友...很快全校都知道了。没有"广播站"，纯靠口口相传。

Gossip（流言）协议就是这个过程：每个节点**随机选几个邻居**交换信息，经过 O(log N) 轮后所有节点都会收到消息。

### 12.2 三种 Gossip 变体

| 变体                | 行为                           | 类比           |
| ------------------- | ------------------------------ | -------------- |
| **Anti-entropy**    | 定期与随机节点同步全部状态     | 定期对账       |
| **Rumor-mongering** | 传播新消息直到足够多节点知道   | 传八卦         |
| **Aggregation**     | 计算分布式聚合值（如平均负载） | 问卷调查取平均 |

### 12.3 工业应用

- **Cassandra**：使用 Gossip 传播节点状态（存活/负载/Schema）
- **Redis Cluster**：节点间通过 Gossip 交换集群拓扑
- **Consul**：使用 SWIM（改进的 Gossip）做成员发现和故障检测
- **区块链**：交易和区块通过 Gossip 在 P2P 网络中传播

## 常见陷阱

1. **不要追求强一致**：大多数业务场景用最终一致性就够了，强一致性的代价是延迟和可用性
2. **幂等性设计**：分布式系统中重试不可避免，所有写操作必须幂等（做一次和做多次结果一样）
3. **不要信任时钟**：不同机器的时钟可能差几百毫秒，用逻辑时钟（Lamport/向量时钟）代替物理时钟排序事件
4. **做好容量规划**：分片后增加节点需要数据迁移，提前规划比事后扩容容易得多
