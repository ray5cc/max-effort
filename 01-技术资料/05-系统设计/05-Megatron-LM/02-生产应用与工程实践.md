## 1. 环境搭建

### 问题：为什么不直接 pip install megatron-lm？

Megatron-LM 强依赖 CUDA 版本、APEX 的 C++ 扩展和 TransformerEngine 的 FP8 支持。源码安装需要精确匹配 CUDA Toolkit 和 PyTorch 版本，手动配置极易出错。

**推荐方案：使用 NVIDIA NGC 官方容器**，所有依赖已预编译。

### 1.1 使用 NGC 容器（推荐）

```bash
# 拉取 PyTorch NGC 容器（已包含 CUDA、cuDNN、NCCL）
docker pull nvcr.io/nvidia/pytorch:24.01-py3

# 启动容器（挂载数据目录，开放所有 GPU）
docker run --gpus all --ipc=host --ulimit memlock=-1 \
    -v /data:/data \
    -v /checkpoints:/checkpoints \
    -it nvcr.io/nvidia/pytorch:24.01-py3 bash

# 在容器内克隆 Megatron-LM
git clone https://github.com/NVIDIA/Megatron-LM
cd Megatron-LM
pip install -e .
```

### 1.2 安装 APEX（融合算子，显著提升训练速度）

APEX 提供融合的 LayerNorm、Adam 优化器等，比 PyTorch 原生实现快 15-30%：

```bash
git clone https://github.com/NVIDIA/apex
cd apex
# --cpp_ext: 编译 C++ 扩展（融合 LayerNorm）
# --cuda_ext: 编译 CUDA 扩展（融合 Adam，mixed precision）
pip install -v \
    --disable-pip-version-check \
    --no-cache-dir \
    --no-build-isolation \
    --config-settings "--build-option=--cpp_ext" \
    --config-settings "--build-option=--cuda_ext" \
    ./
# 编译约需 10-20 分钟，完成后验证：
python -c "import apex; print('APEX OK')"
```

### 1.3 安装 TransformerEngine（FP8 训练支持）

NVIDIA H100 / H800 支持 FP8 精度，可将吞吐量再提升约 30%：

```bash
pip install transformer-engine[pytorch]
# 验证 FP8 支持
python -c "import transformer_engine; print('TE OK')"
```

### 1.4 安装 FlashAttention（序列长度 > 1024 必备）

```bash
# 需要 ninja 构建系统
pip install ninja
pip install flash-attn --no-build-isolation
# 安装约需 15 分钟（需要编译 CUDA 代码）
python -c "import flash_attn; print(flash_attn.__version__)"
```

### 1.5 多节点环境额外配置

## 2. 选择并行策略——经验法则

### 问题：我有 64 张 A100，训练一个 70B 模型，TP/PP/DP 分别设多少？

### 2.1 三个维度的选择原则

**TP（张量并行度）**——受限于节点内 GPU 数量：
- TP 的 All-Reduce 必须走 NVLink 才有效，否则通信成为瓶颈
- DGX A100 节点有 8 张 GPU，NVLink 互联，因此 **TP ≤ 8**
- 对于较小模型（< 20B），TP=1 或 TP=2 即可；更大模型用 TP=4 或 TP=8

**PP（流水线并行度）**——受限于 micro-batch 数量：
- 需要 `m ≥ 4 × PP` 才能将气泡比例控制在 ~20% 以下
- 如果 `global_batch_size = micro_batch_size × m × DP`，则 m 受全局 batch size 约束
- **PP 不宜过大**，否则需要非常大的 batch 才能填满流水线

**DP（数据并行度）**——填满剩余的 GPU：
- `DP = total_GPUs / (TP × PP)`
- 更大的 DP 带来更大的全局 batch size，通常有利于收敛速度

### 2.2 并行策略速查表

| 模型规模 | 总 GPU 数 | TP | PP | DP | 每 GPU 参数（亿） |
|---------|-----------|----|----|----|--------------------|
| 7B | 8 | 1 | 1 | 8 | 8.75 |
| 13B | 8 | 2 | 1 | 4 | 16.25 |
| 13B | 16 | 2 | 2 | 4 | 8.13 |
| 70B | 64 | 4 | 4 | 4 | 17.5 |
| 175B | 512 | 8 | 8 | 8 | 27.3 |
| 530B | 1024 | 8 | 16 | 8 | 41.4 |

### 2.3 显存估算公式

快速估算每张 GPU 所需显存（混合精度训练，含优化器状态）：

```
每 GPU 显存（GB） =
    模型参数数（B）× 16 bytes / (TP × PP)            ← 权重 + 梯度 + Adam
    + seq_len × batch_per_gpu × hidden × layers_per_gpu × 34 × 2B  ← 激活值
    + 常数项（约 3-5 GB，框架开销）
```

示例：13B 模型，TP=2，PP=2，seq=2048，micro_batch=2，hidden=5120，每 GPU 8 层：

```
权重相关：13B × 16 / (2×2) = 52 GB
激活值：2048 × 2 × 5120 × 8 × 34 × 2B ≈ 11.5 GB
总计：约 63-65 GB  ← A100 80GB 可以装下
```

### 2.4 全局 Batch Size 设计

全局 batch size 影响模型收敛质量，工业界常用经验值：

```
全局 batch size（tokens）= micro_batch × seq_len × num_micro_batches × DP

GPT-3 训练配置：
  micro_batch = 4
  seq_len = 2048
  num_micro_batches = 32
  DP = 8
  → 全局 batch size = 4 × 2048 × 32 × 8 = 2,097,152 tokens ≈ 2M tokens
```

Chinchilla 论文建议的 batch size schedule：从小（~0.5M tokens）线性增大到目标值。

## 3. 训练脚本参数详解

### 问题：pretrain_gpt.py 有几十个参数，哪些是关键的？

以下是一个完整注释的训练脚本，适用于单节点 8 GPU 训练 7B 模型：

```bash
#!/bin/bash
# pretrain_7b_single_node.sh
# 适用场景：8×A100 80GB 单节点，训练 7B GPT 模型

# ============================================================
# 模型结构参数
# ============================================================
GPT_ARGS="
    --num-layers 32 \
    --hidden-size 4096 \
    --num-attention-heads 32 \
    --seq-length 2048 \
    --max-position-embeddings 2048 \
    --norm-epsilon 1e-5 \
    --use-rotary-position-embeddings \
    --no-position-embedding \
    --swiglu \
    --ffn-hidden-size 11008 \
"
# --swiglu: 使用 SwiGLU 激活函数（LLaMA 风格），比 GELU 效果更好
# --ffn-hidden-size: FFN 中间层维度（LLaMA 用 8/3 × hidden_size，取整到 256 倍数）
# --use-rotary-position-embeddings: 使用 RoPE 位置编码

# ============================================================
# 并行策略参数（关键！）
# ============================================================
PARALLELISM_ARGS="
    --tensor-model-parallel-size 1 \
    --pipeline-model-parallel-size 1 \
    --sequence-parallel \
"
# 7B 模型单节点无需 TP/PP，8 卡全做 DP
# --sequence-parallel: 开启序列并行（在 TP > 1 时有效，节省激活显存）

# ============================================================
# 训练超参数
# ============================================================
TRAINING_ARGS="
    --micro-batch-size 4 \
    --global-batch-size 256 \
    --lr 3e-4 \
    --min-lr 3e-5 \
    --train-iters 100000 \
    --lr-decay-iters 100000 \
    --lr-decay-style cosine \
    --lr-warmup-fraction 0.01 \
    --clip-grad 1.0 \
    --weight-decay 0.1 \
    --adam-beta1 0.9 \
    --adam-beta2 0.95 \
    --adam-eps 1e-8 \
    --init-method-std 0.01 \
"
# --micro-batch-size: 单张 GPU 单次处理的 batch size
# --global-batch-size: 全局 batch size = micro × gradient_acc_steps × DP
# Megatron 自动计算 gradient_accumulation_steps = global / (micro × DP)

# ============================================================
# 数据集参数
# ============================================================
DATA_ARGS="
    --data-path ./data/my-gpt2_text_document \
    --vocab-file ./vocab.json \
    --merge-file ./merges.txt \
    --tokenizer-type GPT2BPETokenizer \
    --data-impl mmap \
    --split 949,50,1 \
"
# --data-path: MMapIndexedDataset 的前缀（不含 .bin/.idx）
# --split: train/valid/test 的比例（千分比，需合计 1000）
# --data-impl mmap: 使用内存映射，必须配合预处理好的 .bin/.idx 文件

# ============================================================
# 精度参数
# ============================================================
PRECISION_ARGS="
    --bf16 \
    --no-query-key-layer-scaling \
"
# --bf16: 使用 BF16（在 A100/H100 上推荐，比 FP16 更稳定）
# --fp16: 如果是 V100 等不支持 BF16 的 GPU，改用此参数

# ============================================================
# 日志与检查点参数
# ============================================================
OUTPUT_ARGS="
    --log-interval 100 \
    --save-interval 10000 \
    --eval-interval 1000 \
    --eval-iters 10 \
    --tensorboard-dir ./tensorboard \
    --log-throughput \
    --log-timers-to-tensorboard \
"
# --log-interval: 每 N 步打印一次训练日志
# --save-interval: 每 N 步保存一次检查点
# --log-throughput: 打印 tokens/s 和 MFU 等吞吐指标

# ============================================================
# 优化参数
# ============================================================
OPTIMIZATION_ARGS="
    --use-flash-attn \
    --recompute-activations \
    --recompute-granularity selective \
"
# --use-flash-attn: 使用 FlashAttention 2（内存效率极高）
# --recompute-activations: 激活值重计算（牺牲 30% 计算换取 50% 激活显存）
# --recompute-granularity selective: 只对昂贵层（如 attention）做重计算

# ============================================================
# 启动训练
# ============================================================
torchrun \
    --nproc_per_node=8 \
    --nnodes=1 \
    --node_rank=0 \
    --master_addr=localhost \
    --master_port=29500 \
    pretrain_gpt.py \
    $GPT_ARGS \
    $PARALLELISM_ARGS \
    $TRAINING_ARGS \
    $DATA_ARGS \
    $PRECISION_ARGS \
    $OUTPUT_ARGS \
    $OPTIMIZATION_ARGS \
    --save ./checkpoints \
    --load ./checkpoints \
    --exit-on-missing-checkpoint
```

### 3.1 多节点启动方式

## 4. 数据预处理

### 问题：我有 500GB 的原始文本，如何转成 Megatron 需要的格式？

### 4.1 准备原始数据

Megatron 的数据预处理脚本接受 JSONL 格式，每行一个 JSON 对象，包含 `text` 字段：

```jsonl
{"text": "第一段训练文本，可以是任意长度的自然语言内容。段落之间用换行分隔。"}
{"text": "第二段训练文本。多个句子可以在同一个 text 字段内，用正常标点分隔。"}
{"text": "GitHub issue 内容、代码文档等混合数据都可以放入 text 字段。"}
```

对于不同来源的数据集，先统一转换为此格式：

```python
# convert_to_jsonl.py
import json

def convert_pile_to_jsonl(input_file, output_file):
    with open(input_file, 'r') as fin, open(output_file, 'w') as fout:
        for line in fin:
            sample = json.loads(line)
            # Pile 数据集的字段是 "text"，直接转换
            out = {"text": sample["text"]}
            fout.write(json.dumps(out, ensure_ascii=False) + '\n')
```

### 4.2 执行预处理

```bash
# 单文件预处理
python tools/preprocess_data.py \
    --input /data/raw/train.jsonl \
    --output-prefix /data/processed/train \
    --vocab-file ./tokenizer/vocab.json \
    --merge-file ./tokenizer/merges.txt \
    --tokenizer-type GPT2BPETokenizer \
    --append-eod \
    --workers 16 \
    2>&1 | tee preprocess.log

# 多文件并行预处理（适用于超大数据集）
for shard in /data/raw/shard_*.jsonl; do
    shard_name=$(basename $shard .jsonl)
    python tools/preprocess_data.py \
        --input $shard \
        --output-prefix /data/processed/$shard_name \
        --vocab-file ./tokenizer/vocab.json \
        --merge-file ./tokenizer/merges.txt \
        --tokenizer-type GPT2BPETokenizer \
        --append-eod \
        --workers 8 &
done
wait
echo "All shards processed"
```

## 5. 检查点格式转换

### 问题：训练完成的 Megatron 检查点怎么在 HuggingFace 中使用？

### 5.1 将 Megatron 检查点合并为单文件

训练结束后，检查点被切分为 `TP × PP` 份，需要先合并：

```bash
# 将 TP=4, PP=4 的检查点合并为 TP=1, PP=1
python tools/checkpoint/util.py \
    --model-type GPT \
    --load-dir ./checkpoints/iter_0100000 \
    --save-dir ./checkpoints_merged/ \
    --target-tensor-parallel-size 1 \
    --target-pipeline-parallel-size 1 \
    --megatron-path /path/to/Megatron-LM
```

### 5.2 转换为 HuggingFace 格式

```bash
# 使用新版转换工具（Megatron-LM core 格式）
python tools/checkpoint/convert.py \
    --model-type GPT \
    --loader megatron_core \
    --saver huggingface \
    --target-tensor-parallel-size 1 \
    --target-pipeline-parallel-size 1 \
    --load-dir ./checkpoints/iter_0100000 \
    --save-dir ./hf_model \
    --tokenizer-model ./tokenizer/tokenizer.model
```

转换后的目录结构：

```
hf_model/
├── config.json          ← HuggingFace 模型配置
├── tokenizer.json       ← tokenizer 配置
├── tokenizer.model      ← SentencePiece 模型（如使用）
├── pytorch_model.bin    ← 模型权重（< 10GB 时单文件）
└── pytorch_model.bin.index.json  ← 大模型时的分片索引
```

### 5.3 验证转换结果

```python
from transformers import AutoModelForCausalLM, AutoTokenizer
import torch

model = AutoModelForCausalLM.from_pretrained("./hf_model", torch_dtype=torch.bfloat16)
tokenizer = AutoTokenizer.from_pretrained("./hf_model")

# 简单推理测试
inputs = tokenizer("人工智能的未来发展方向是", return_tensors="pt")
with torch.no_grad():
    outputs = model.generate(**inputs, max_new_tokens=50)
print(tokenizer.decode(outputs[0]))
```

## 6. MFU 计算与监控

### 问题：训练日志里的 "TFLOPs: 312"，这算高还是低？

**MFU（Model FLOPs Utilization）**= 模型实际利用的算力 / GPU 理论峰值算力。它是衡量训练效率最直接的指标。

### 6.1 理论 FLOPs 计算

Transformer 模型每个 token 的前向+反向 FLOPs（近似公式）：

```
FLOPs per token ≈ 6 × N

其中 N = 模型参数量（注意力层和 FFN 层的权重数之和）

更精确的公式（包含注意力计算本身）：
FLOPs per token = 6N + 12 × n_layers × n_heads × d_head × seq_len
                ≈ 6N（当 d_model >> seq_len 时，后一项可忽略）
```

### 6.2 从训练日志计算 MFU

Megatron-LM 的训练日志示例：

```
 iteration       500/  100000 | consumed samples:      128000 |
 elapsed time per iteration (ms): 1250.3 |
 learning rate: 3.000E-04 | global batch size:   256 |
 lm loss: 3.021E+00 | loss scale: 1.0 |
 grad norm: 0.421 |
 num zeros: 0.0 |
 TFLOPs: 156.3           ← 每张 GPU 的实际 TFLOPs
```

手动验证：

```python
# 配置参数
N = 7e9          # 7B 模型参数量
tokens_per_iter = 256 * 2048  # global_batch × seq_len = 524288
iter_time_s = 1.250           # 每步耗时（秒）
num_gpus = 8
gpu_peak_tflops = 312         # A100 BF16 峰值

# 计算 MFU
actual_flops_per_gpu = 6 * N * tokens_per_iter / iter_time_s / num_gpus
mfu = actual_flops_per_gpu / (gpu_peak_tflops * 1e12)

print(f"每 GPU 实际 TFLOPs: {actual_flops_per_gpu/1e12:.1f}")
print(f"MFU: {mfu*100:.1f}%")
# 典型输出: MFU: 50.1%
```

### 6.3 MFU 基准与优化

| MFU 范围 | 评价 | 常见原因 |
|---------|------|---------|
| > 60% | 优秀 | 充分利用 NVLink 和 FlashAttention |
| 45-60% | 良好 | 正常生产水平 |
| 30-45% | 一般 | 通信成为瓶颈，或 batch size 太小 |
| < 30% | 差 | 严重的通信或 IO 瓶颈 |

**提升 MFU 的实践方法**：

```bash
# 1. 增大 micro-batch-size（提高 GPU 计算密度）
--micro-batch-size 8   # 从 4 改为 8（如显存允许）

# 2. 开启 FlashAttention（减少内存 IO）
--use-flash-attn

# 3. 关闭 activation recompute（如显存充足）
# 去掉 --recompute-activations

# 4. 使用 BF16（比 FP16 更稳定，无需 loss scaling）
--bf16

# 5. 使用融合算子
--use-fused-rmsnorm     # 融合的 RMSNorm
--use-fused-swiglu      # 融合的 SwiGLU
```

## 7. 常见问题调试

### 7.1 NCCL 通信超时

**现象**：训练中途报 `NCCL timeout` 或 `Watchdog caught collective operation timeout`。

```bash
# 诊断：查看 IB 状态
ibstat | grep -E "State|Physical state"
# 期望：State: Active, Physical state: LinkUp

# 解决方案 1：增大 NCCL 超时时间
export NCCL_IB_TIMEOUT=23        # IB 超时（单位：4ms，23 → 约 33 秒）
export NCCL_ASYNC_ERROR_HANDLING=1  # 启用异步错误处理

# 解决方案 2：检查 IB 配置
export NCCL_IB_DISABLE=0          # 确保使用 IB
export NCCL_IB_HCA=mlx5_0         # 指定 IB 网卡
export NCCL_NET_GDR_LEVEL=5       # 启用 GPUDirect RDMA

# 解决方案 3：添加训练参数
# --exit-interval 0 可防止 idle worker 被杀死
```

### 7.2 OOM（显存不足）

**现象**：`CUDA out of memory. Tried to allocate X GiB`。

```bash
# 按显存消耗从大到小排查：

# 1. 降低 micro-batch-size
--micro-batch-size 2    # 从 4 降到 2

# 2. 开启激活值重计算（用计算换显存）
--recompute-activations
--recompute-granularity full    # 更激进：重计算全部激活

# 3. 检查点保存时 OOM → 使用异步保存
--async-save

# 4. 增大 TP（减少每 GPU 参数量）
--tensor-model-parallel-size 4  # 从 2 改为 4

# 5. 减小序列长度（临时调试）
--seq-length 1024   # 从 2048 降到 1024
```

### 7.3 训练 Loss 不收敛或 NaN

**现象**：Loss 突然变成 `nan` 或者一直不下降。

```bash
# 原因 1：学习率过大
--lr 1e-4        # 从 3e-4 降低

# 原因 2：梯度爆炸
--clip-grad 0.5  # 降低梯度裁剪阈值（默认 1.0）

# 原因 3：FP16 溢出（改用 BF16）
--bf16           # 替换 --fp16

# 原因 4：初始化问题
--init-method-std 0.006  # 降低初始化标准差（= 1/sqrt(hidden_size)）

# 调试工具：观察 loss scale 变化
# 训练日志中 "loss scale: X" 如果持续下降，说明有溢出
```

### 7.4 各 PP 阶段显存不均衡

**现象**：某些 PP 阶段 OOM，其他阶段还有剩余。

```bash
# 原因：Embedding 层和最后的 loss 层额外占用显存
# 第一个和最后一个 PP 阶段通常显存使用更多

# 解决方案：调整层分配
--num-layers-per-virtual-pipeline-stage 2  # 使用交错调度时，每个虚拟阶段层数

# 或者手动分配（部分版本支持）：
# 让首尾 stage 少几层，中间 stage 多几层
```

### 7.5 流水线气泡过大，吞吐低

```bash
# 诊断：计算气泡比例
# bubble = (pp - 1) / (num_micro_batches + pp - 1)

# 解决方案 1：增大 num_micro_batches（通过增大 global_batch_size）
--global-batch-size 512   # 从 256 增大到 512

# 解决方案 2：使用交错式流水线
--num-layers 96
--pipeline-model-parallel-size 8
--virtual-pipeline-model-parallel-size 12  # 每 GPU 12 个虚拟阶段，每阶段 1 层
```

## 总结

从一个空目录到完成 13B 模型预训练，关键步骤回顾：

```
原始文本数据
    │
    ▼ preprocess_data.py
MMapIndexedDataset（.bin + .idx）
    │
    ▼ torchrun pretrain_gpt.py
3D 并行训练（TP × PP × DP）
    │
    ├── 监控：loss、TFLOPs、MFU、grad norm
    ├── 检查点：每 5000 步保存一次
    │
    ▼ tools/checkpoint/convert.py
HuggingFace 格式模型
    │
    ▼ lm-evaluation-harness
标准基准评测结果
```

**最重要的几条实践经验**：
1. **先在单节点跑通**，验证数据、模型配置和并行策略，再扩展到多节点
2. **MFU 是最重要的效率指标**，低于 40% 要排查通信和数据 IO 瓶颈
3. **micro-batch 数量要远大于 PP 度**，否则流水线气泡浪费计算资源
4. **BF16 优于 FP16**，无需 loss scaling，训练更稳定
5. **FlashAttention + 序列并行**是序列长度 > 2048 时的标配

详细原理请参阅 [00-项目综述与技术原理](./00-项目综述与技术原理.md)，代码实现细节见 [01-架构详解与核心组件](./01-架构详解与核心组件.md)。
