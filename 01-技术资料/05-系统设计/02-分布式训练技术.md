## 1. 显存危机——为什么模型放不下

### 问题：7B 参数 = 14GB，为什么还是 OOM？

你买了 8 张 A100 80GB 显卡，总显存 640GB，理论上放下一个 70B 模型（~140GB in FP16）绰绰有余。但一启动训练，立刻 OOM。这是为什么？

**关键洞察**：训练不只是存模型权重，还要存梯度和优化器状态。

### 1.1 混合精度训练的完整显存账单

现代大模型训练几乎都采用"混合精度训练"（Mixed Precision Training）——前向/反向用 FP16 加速计算，但优化器步骤用 FP32 保持数值稳定。

**类比**：把模型想象成一家工厂。FP16 权重是生产线上的"工作零件"（轻便高效），FP32 主权重是仓库里的"黄金母版"（精确但笨重），优化器状态是记录每条生产线历史运行数据的"日志本"（Adam 需要两本：一阶矩 + 二阶矩）。

对于一个参数量为 Ψ 的模型，每个参数需要以下存储：

| 状态 | 精度 | 字节/参数 | 说明 |
|------|------|----------|------|
| 模型权重（用于前向/反向） | FP16 | 2 | 参与实际计算 |
| 梯度 | FP16 | 2 | 反向传播产生 |
| 主权重（FP32 副本） | FP32 | 4 | 优化器步骤使用 |
| Adam 一阶矩 m₁ | FP32 | 4 | 梯度的指数滑动平均 |
| Adam 二阶矩 m₂ | FP32 | 4 | 梯度平方的指数滑动平均 |
| **合计** | — | **16** | **每个参数 16 字节** |

```
每参数显存 = 2(FP16权重) + 2(FP16梯度) + 4(FP32主权重) + 4(m₁) + 4(m₂) = 16 字节
```

### 1.2 实际计算：7B 和 70B 模型

```
7B  模型：7 × 10⁹ × 16 字节 = 112 GB
13B 模型：13 × 10⁹ × 16 字节 = 208 GB
70B 模型：70 × 10⁹ × 16 字节 = 1120 GB
```

```
┌─────────────────────────────────────────────────────────┐
│               70B 模型训练显存需求分解                    │
│                                                          │
│  FP16 权重   ████████████  140 GB  (12.5%)              │
│  FP16 梯度   ████████████  140 GB  (12.5%)              │
│  FP32 主权重 ████████████████████████  280 GB  (25%)    │
│  Adam m₁    ████████████████████████  280 GB  (25%)    │
│  Adam m₂    ████████████████████████  280 GB  (25%)    │
│                                                          │
│  总计：1120 GB    8×A100(80GB) = 640 GB  ❌ 放不下！    │
└─────────────────────────────────────────────────────────┘
```

### 1.3 DDP 的致命缺陷：每张卡存全份

传统的 **DistributedDataParallel（DDP）** 是这样工作的：每张 GPU 都保存**完整的一份**模型状态（权重 + 梯度 + 优化器状态），仅在反向传播后 All-Reduce 梯度。

```
┌──────────────────── DDP 显存分布 ────────────────────────┐
│                                                          │
│  GPU 0: [完整权重 + 梯度 + 优化器状态] = 1120 GB (70B)   │
│  GPU 1: [完整权重 + 梯度 + 优化器状态] = 1120 GB (70B)   │
│  GPU 2: [完整权重 + 梯度 + 优化器状态] = 1120 GB (70B)   │
│  ...                                                     │
│  GPU 7: [完整权重 + 梯度 + 优化器状态] = 1120 GB (70B)   │
│                                                          │
│  ⚠️  8 张卡存了 8 份完全相同的优化器状态！               │
│  总冗余：1120 GB × 8 = 8960 GB，而实际只需要 1120 GB    │
└──────────────────────────────────────────────────────────┘
```

**核心问题**：我们在 8 张 GPU 上存了 8 份完全相同的优化器状态！这是巨大的浪费——Adam 优化器状态（m₁ + m₂ + FP32主权重）占了 12 字节/参数，共 840GB，却冗余存了 8 次。

## 2. ZeRO 核心思想——停止无谓的复制

### 2.1 一个直觉性问题

既然每张 GPU 在前向/反向传播结束后才需要"自己负责的那部分参数"的优化器状态，那么：**每张 GPU 只存 1/N 的优化器状态不就够了吗？**

ZeRO（Zero Redundancy Optimizer）就是这个思想的系统化实现。它分三个阶段，逐步消除冗余。

### 2.2 ZeRO Stage 1：优化器状态分片

**只分片优化器状态**（FP32 主权重 + m₁ + m₂），每张 GPU 只存 1/N。

```
┌─────────────────── ZeRO Stage 1（N=8 GPUs）──────────────────┐
│                                                               │
│  GPU 0: [FP16权重(全)] + [FP16梯度(全)] + [优化器状态 1/8]   │
│  GPU 1: [FP16权重(全)] + [FP16梯度(全)] + [优化器状态 1/8]   │
│  ...                                                          │
│  GPU 7: [FP16权重(全)] + [FP16梯度(全)] + [优化器状态 1/8]   │
│                                                               │
└───────────────────────────────────────────────────────────────┘
```

**每卡显存（字节/参数）**：
```
2 (FP16权重) + 2 (FP16梯度) + 12/N (优化器状态)
= 4 + 12/8 = 4 + 1.5 = 5.5 字节/参数（N=8 时）

70B 模型：70B × 5.5 = 385 GB → 每卡 48 GB ✅
```

相比 DDP 每卡 1120 GB，节省约 **2.9×**。

### 2.3 ZeRO Stage 2：优化器状态 + 梯度分片

在 Stage 1 的基础上，**也对梯度进行分片**。每张 GPU 只保存负责更新的那 1/N 参数的梯度。

```
┌─────────────────── ZeRO Stage 2（N=8 GPUs）──────────────────┐
│                                                               │
│  GPU 0: [FP16权重(全)] + [FP16梯度 1/8] + [优化器状态 1/8]  │
│  GPU 1: [FP16权重(全)] + [FP16梯度 1/8] + [优化器状态 1/8]  │
│  ...                                                          │
│                                                               │
└───────────────────────────────────────────────────────────────┘
```

**每卡显存（字节/参数）**：
```
2 (FP16权重) + (2 + 12)/N (梯度 + 优化器状态)
= 2 + 14/8 = 2 + 1.75 = 3.75 字节/参数（N=8 时）

70B 模型：70B × 3.75 = 262 GB → 每卡 33 GB ✅（比 Stage 1 再省 1.5×）
```

### 2.4 ZeRO Stage 3：全状态分片（包括参数）

**连 FP16 参数本身也分片**。每张 GPU 只保存 1/N 的参数。前向传播时，用 All-Gather 临时重建当前层所需的参数，用完即丢。

```
┌─────────────────── ZeRO Stage 3（N=8 GPUs）──────────────────┐
│                                                               │
│  GPU 0: [FP16权重 1/8] + [FP16梯度 1/8] + [优化器状态 1/8]  │
│  GPU 1: [FP16权重 1/8] + [FP16梯度 1/8] + [优化器状态 1/8]  │
│  ...                                                          │
│                                                               │
│  需要某层参数时：临时 All-Gather → 计算 → 立即释放            │
│                                                               │
└───────────────────────────────────────────────────────────────┘
```

**每卡显存（字节/参数）**：
```
(2 + 2 + 12)/N = 16/N 字节/参数

N=8：16/8 = 2 字节/参数
70B 模型：70B × 2 = 140 GB → 每卡 17.5 GB ✅✅✅
```

**这才是 ZeRO 的终极目标**：8 张 A100(80GB) 训练 70B 模型成为可能！

### 2.5 各阶段汇总对比

| 策略 | 每卡显存（字节/参数） | 70B 模型每卡显存 | 相对 DDP 节省 |
|------|-------------------|--------------------|--------------|
| DDP（基线） | 16 | 140 GB | 1× |
| ZeRO Stage 1 | 4 + 12/N | ~48 GB（N=8） | ~2.9× |
| ZeRO Stage 2 | 2 + 14/N | ~33 GB（N=8） | ~4.3× |
| ZeRO Stage 3 | 16/N | ~17.5 GB（N=8） | ~8× |

```
显存节省示意（N=8，70B 模型，单位 GB）：

DDP       ████████████████████████████████████████ 140 GB/卡
Stage 1   █████████████████ 48 GB/卡
Stage 2   ███████████ 33 GB/卡
Stage 3   █████ 17.5 GB/卡
```

### 2.6 ZeRO 的通信开销

ZeRO 不是免费的——Stage 3 在前向和反向各需要一次 All-Gather，反向还需要 Reduce-Scatter：

| 策略 | 额外通信量（相比 DDP All-Reduce） |
|------|--------------------------------|
| Stage 1 | 与 DDP 相同（优化器 Scatter 后 All-Gather 参数更新） |
| Stage 2 | 与 DDP 相同（Reduce-Scatter 梯度） |
| Stage 3 | 1.5× DDP（额外的前向 All-Gather） |

在高速互联（NVLink 600 GB/s）下，Stage 3 的通信开销通常可被计算掩盖，实际吞吐损失 5-15%。

## 3. ZeRO-Infinity——突破 GPU 显存上限

### 问题：即使 Stage 3 也装不下万亿参数模型怎么办？

ZeRO Stage 3 在 8×80GB A100 上仅能训练 ~320B 参数的模型（8×80GB / 2 字节）。GPT-3 175B 勉强可以，但更大的模型（如 1T 参数）仍然无解。

### 3.1 存储层级利用

ZeRO-Infinity 将存储层级从 GPU 显存扩展到整台服务器的所有存储：

```
┌────────────────────────────────────────────────────────────┐
│               ZeRO-Infinity 存储层级                        │
│                                                            │
│  GPU VRAM    ████  80 GB/卡    带宽: ~2 TB/s (NVLink)     │
│      ↕ PCIe 4.0: ~16 GB/s                                 │
│  CPU RAM     ████████████████████  1-2 TB/节点             │
│      ↕ NVMe: ~6 GB/s                                       │
│  NVMe SSD    ████████████████████████████  数十 TB         │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

### 3.2 各层级卸载策略

**参数卸载（Param Offload）**：将 FP16 参数分片存入 CPU RAM，前向传播时按层异步预取到 GPU。

**优化器卸载（Optimizer Offload）**：FP32 主权重、m₁、m₂ 全部存入 CPU RAM，优化器 step 在 CPU 上执行（CPU Adam 用 AVX512 并行加速）。

**NVMe 卸载**：参数和优化器状态可进一步卸载到 NVMe，通过 DMA 异步 I/O 实现传输与计算重叠。

### 3.3 带宽成为瓶颈

| 传输路径 | 峰值带宽 | 实际场景 |
|---------|---------|---------|
| GPU HBM（内部） | ~2 TB/s | All-Gather 参数重建 |
| NVLink（GPU↔GPU） | 600 GB/s | 节点内多卡通信 |
| PCIe 4.0（GPU↔CPU） | 16 GB/s | 参数/优化器卸载 |
| NVMe（CPU↔SSD） | 6 GB/s | NVMe 卸载 |

**关键设计**：异步预取（Prefetch）——在计算第 i 层时，同时从 CPU/NVMe 预取第 i+1 层的参数，隐藏传输延迟。

### 3.4 什么时候用 ZeRO-Infinity？

| 场景 | 推荐策略 |
|------|---------|
| 7B-70B，8×A100 | ZeRO Stage 2 或 Stage 3 |
| 70B-200B，8×A100 | ZeRO Stage 3 |
| 200B+，单节点 | ZeRO-Infinity + CPU Offload |
| 1T+，多节点 | ZeRO-Infinity + NVMe Offload + 流水线并行 |

### 3.5 ZeRO-Infinity 配置示例

```python
# ds_config_infinity.json（关键部分）
{
  "zero_optimization": {
    "stage": 3,
    "offload_optimizer": {
      "device": "cpu",        # 优化器状态卸载到 CPU RAM
      "pin_memory": true      # 锁页内存，加速 PCIe DMA
    },
    "offload_param": {
      "device": "nvme",       # 参数卸载到 NVMe（极端情况）
      "nvme_path": "/local_nvme/zero_params",
      "pin_memory": true,
      "buffer_count": 5,
      "buffer_size": 1e8
    },
    "stage3_max_live_parameters": 1e9,
    "stage3_max_reuse_distance": 1e9
  }
}
```

**注意**：NVMe Offload 仅在 CPU RAM 也不够用时才启用。优先考虑 CPU Offload，NVMe Offload 的 I/O 延迟会使吞吐量下降 60-80%。

## 4. DeepSpeed-Inference——推理端的优化

### 问题：训练优化不能直接用于推理

训练优化（ZeRO 分片）专为**参数更新**设计；推理的目标是**最小化单次请求延迟**，两者优化方向不同。

### 4.1 Kernel Fusion（算子融合）

推理时，大量小型 CUDA Kernel 的启动开销（Launch Overhead）会显著拖慢速度。DeepSpeed-Inference 将多个算子融合为一个 Kernel：

```
融合前（3 个 Kernel 调用）：
  LayerNorm → [等待] → QKV Linear → [等待] → Softmax

融合后（1 个 Kernel 调用）：
  LayerNorm + QKV Linear + Softmax  （一次完成）
```

典型融合场景：Transformer 层中的 `LayerNorm + 线性层`，以及 `GeLU + 线性层`。

### 4.2 INT8 量化推理

训练用 FP16 保精度，推理可进一步压缩到 INT8（甚至 INT4），显著提升吞吐量：

```
显存占用对比（7B 模型）：
  FP16（BF16）：~14 GB
  INT8：        ~7 GB   （节省 2×，吞吐提升 1.5-2×）
  INT4：        ~3.5 GB （节省 4×，精度损失需评估）
```

DeepSpeed-Inference 支持 SmoothQuant 量化方案，通过将量化难度从激活值"平滑"到权重，减少精度损失。

### 4.3 与 TensorRT 的对比

| 维度 | DeepSpeed-Inference | TensorRT |
|------|--------------------|----|
| 目标模型 | LLM（Transformer） | 通用神经网络 |
| 量化支持 | INT8（SmoothQuant） | INT8/INT4/FP8 |
| 灵活性 | 高（Python 原生） | 低（需 ONNX 转换） |
| 最大优化程度 | 中高 | 极高（平台绑定） |
| 适用场景 | 研究/生产 LLM 推理 | 生产部署（高吞吐静态场景） |

### 4.4 DeepSpeed-Inference 快速体验

```python
import deepspeed
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("meta-llama/Llama-2-7b-hf")
model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-2-7b-hf",
    torch_dtype=torch.float16
)

# 用 DeepSpeed-Inference 包装模型
ds_engine = deepspeed.init_inference(
    model,
    mp_size=1,              # 张量并行 GPU 数量（单卡填 1）
    dtype=torch.float16,
    replace_method="auto",  # 自动替换为 DeepSpeed 优化后的 Kernel
    replace_with_kernel_inject=True  # 启用 Kernel 注入（Fused Attention 等）
)

model = ds_engine.module

# 推理（接口不变）
inputs = tokenizer("DeepSpeed 推理优化的原理是", return_tensors="pt").to("cuda")
with torch.no_grad():
    outputs = model.generate(**inputs, max_new_tokens=100)
print(tokenizer.decode(outputs[0]))
```

`replace_with_kernel_inject=True` 会将模型中的 Transformer 层替换为 DeepSpeed 融合版本，在 A100 上通常能获得 1.5-2× 的推理加速。

## 5. ZeRO vs FSDP vs Megatron 对比

### 问题：三个框架都能训练大模型，该选哪个？

**类比**：ZeRO 是"把同一批货物分给 N 辆车运"；Megatron 是"把货物切成 N 份，每辆车运不同部分，协同工作"；FSDP 是 PyTorch 官方版的 ZeRO，生态更原生。

| 维度 | ZeRO（DeepSpeed） | FSDP（PyTorch） | Megatron-LM |
|------|------------------|----------------|-------------|
| **核心思想** | 数据并行 + 状态分片 | 数据并行 + 状态分片 | 模型并行（张量/流水线） |
| **分片粒度** | 优化器/梯度/参数 | 参数（全量分片） | 层/矩阵行列 |
| **易用性** | 高（改动少） | 中（需适配 FSDP API） | 低（需大量代码改造） |
| **通信效率** | 高（NVLink 下接近最优） | 高（与 ZeRO 相当） | 极高（流水线并行减少通信） |
| **最大模型规模** | 数万亿（ZeRO-Infinity） | ~数千亿（需大量节点） | 数千亿（已验证 GPT-3 级别） |
| **HuggingFace 集成** | 一行配置 | 支持（accelerate） | 复杂 |
| **适用场景** | 大模型微调/预训练（中小团队） | PyTorch 原生优先（大团队） | 超大规模预训练（头部机构） |
| **典型用户** | 微软、各研究机构 | Meta、学术界 | NVIDIA、各大科技公司 |

### 实战选型建议

```
是否需要修改 PyTorch 代码？
    ├─ 尽量少改 → DeepSpeed（只需 ds_config.json）
    └─ 可以改 → 
        ├─ 追求 PyTorch 原生生态 → FSDP（torch >= 2.0）
        └─ 超大规模（1000 亿+ 预训练）→ Megatron-LM

单机 8×A100 训练 7B-70B？
    → DeepSpeed ZeRO Stage 2/3（最省事）

多机多卡训练 200B+ ？
    → DeepSpeed ZeRO-Infinity 或 Megatron + DeepSpeed 混合
```

## 总结

DeepSpeed ZeRO 通过三个递进阶段，系统性地消除了分布式训练中的状态冗余：

1. **ZeRO Stage 1**：分片优化器状态，~3× 显存节省，通信量不变
2. **ZeRO Stage 2**：+ 分片梯度，~4× 显存节省，通信量不变  
3. **ZeRO Stage 3**：+ 分片参数，~8× 显存节省，通信量约 1.5×
4. **ZeRO-Infinity**：将 CPU RAM 和 NVMe 纳入存储层级，支持万亿参数训练

核心洞察：**冗余是可以消除的——只要在需要时用通信换回完整信息**。这也是 ZeRO 和 Megatron 并行策略的根本区别：ZeRO 是"按需重建"，Megatron 是"永久分工"。

## 1. DeepSpeed Engine——初始化的魔法

### 问题：为什么只改几行代码就能从 DDP 切换到 ZeRO？

**类比**：DeepSpeedEngine 就像一个"超级外壳"，把你原有的模型、优化器、学习率调度器全部包裹进去，在不改变使用接口的情况下，悄悄替换掉底层的内存管理和通信逻辑。

### 1.1 初始化

调用 `deepspeed.initialize()` 后，你得到的不再是普通的 `nn.Module`，而是一个 `DeepSpeedEngine` 实例：

```python
import deepspeed

model_engine, optimizer, train_dataloader, lr_scheduler = deepspeed.initialize(
    model=model,                        # 你的原始 nn.Module
    optimizer=optimizer,                # 可选，也可在 ds_config 中指定
    model_parameters=model.parameters(),
    training_data=train_dataset,        # 可选
    config="ds_config.json",            # 核心配置文件
    lr_scheduler=lr_scheduler           # 可选
)
```

`deepspeed.initialize()` 内部完成以下工作：
1. 调用 `dist.init_process_group()`（如果还未初始化）
2. 根据 `ds_config.json` 决定使用哪个 ZeRO Stage
3. 将模型参数按 ZeRO 策略**重新分片**到各 GPU
4. 将优化器替换为 `DeepSpeedZeroOptimizer`（包含分片逻辑）
5. 设置 GradScaler（FP16 损失缩放）

### 1.2 训练循环的改变

DeepSpeedEngine 刻意保持与 PyTorch 接近的 API，降低迁移门槛：

```python
# ─────────────── 纯 PyTorch DDP ───────────────
for batch in dataloader:
    loss = model(batch)         # 前向
    loss.backward()             # 反向（DDP 自动 All-Reduce 梯度）
    optimizer.step()            # 优化器步骤
    optimizer.zero_grad()       # 清零梯度

# ─────────────── DeepSpeed ────────────────────
for batch in dataloader:
    loss = model_engine(batch)          # 前向（内部触发 ZeRO All-Gather）
    model_engine.backward(loss)         # 反向（内部触发 ZeRO Reduce-Scatter）
    model_engine.step()                 # 优化器步骤 + 自动 zero_grad
    # 无需手动 zero_grad！engine 自动处理
```

## 2. ZeRO 通信原语——Reduce-Scatter + All-Gather

### 问题：ZeRO 的通信和 DDP 有何本质区别？

DDP 使用 **All-Reduce** 同步梯度；ZeRO 将 All-Reduce 拆分为 **Reduce-Scatter + All-Gather**，这一拆分是实现分片的关键。

### 2.1 All-Reduce（DDP 基线）

每张 GPU 将梯度发送给所有其他 GPU，每张 GPU 最终都得到全局求和的完整梯度。

```
4 GPU All-Reduce 示意（每 GPU 有 4 个梯度碎片 g0-g3）：

GPU 0: [g0₀, g1₀, g2₀, g3₀]
GPU 1: [g0₁, g1₁, g2₁, g3₁]  →  所有 GPU 得到 [g0₀+g0₁+g0₂+g0₃, ...]
GPU 2: [g0₂, g1₂, g2₂, g3₂]     （全量完整梯度，4× 冗余存储）
GPU 3: [g0₃, g1₃, g2₃, g3₃]

通信量：2 × (N-1)/N × Ψ ≈ 2Ψ  （N 很大时）
```

### 2.2 Reduce-Scatter（产生梯度分片）

每张 GPU 发送全部梯度，但只**接收**自己负责的 1/N 份（已被 N 卡求和）：

```
4 GPU Reduce-Scatter 示意：

输入：
GPU 0: [g0₀, g1₀, g2₀, g3₀]
GPU 1: [g0₁, g1₁, g2₁, g3₁]
GPU 2: [g0₂, g1₂, g2₂, g3₂]
GPU 3: [g0₃, g1₃, g2₃, g3₃]

输出（每卡只保留 1/4）：
GPU 0: [G0 = g0₀+g0₁+g0₂+g0₃]  ← 只有 g0 的全局和
GPU 1: [G1 = g1₀+g1₁+g1₂+g1₃]  ← 只有 g1 的全局和
GPU 2: [G2 = g2₀+g2₁+g2₂+g2₃]  ← 只有 g2 的全局和
GPU 3: [G3 = g3₀+g3₁+g3₂+g3₃]  ← 只有 g3 的全局和

通信量：(N-1)/N × Ψ ≈ Ψ
```

每张 GPU 现在只需更新自己负责的那 1/N 参数 → **梯度分片天然实现**。

### 2.3 All-Gather（重建完整参数）

每张 GPU 广播自己的参数分片，所有 GPU 收集后得到完整参数：

```
4 GPU All-Gather 示意：

输入（每卡只有 1/4 参数）：
GPU 0: [P0]   GPU 1: [P1]   GPU 2: [P2]   GPU 3: [P3]

输出（所有卡得到完整参数）：
所有 GPU: [P0, P1, P2, P3]

通信量：(N-1)/N × Ψ ≈ Ψ
```

### 2.4 为什么 Reduce-Scatter + All-Gather = All-Reduce？

```
通信量对比：
  All-Reduce:               2Ψ  （发 Ψ + 收 Ψ）
  Reduce-Scatter + All-Gather: Ψ + Ψ = 2Ψ  （完全相同！）
```

**关键点**：两者通信量相同，但 ZeRO 在 Reduce-Scatter 之后不做 All-Gather，只保留 1/N 份数据 → 内存节省 N× 而通信成本不增加。All-Gather 只在前向传播需要参数时才按需执行。

## 3. 参数分片——前向传播时如何重建参数

### 问题：ZeRO Stage 3 的参数被拆散了，前向传播怎么能正常运行？

**类比**：想象一本百科全书被撕成 8 份分给 8 个学生。每次需要查阅某一章时，临时把那章的所有碎片拼回来，用完就散开。ZeRO Stage 3 就是这样管理参数的。

### 3.1 前向传播时序

```
时刻 t0: 计算第 0 层
  ├── All-Gather Layer 0 的参数（从 N 卡收集）
  ├── 执行 Layer 0 的前向计算
  └── 丢弃 Layer 0 的完整参数（只保留本卡分片）

时刻 t1: 计算第 1 层
  ├── All-Gather Layer 1 的参数
  │   （与 t0 的计算重叠：预取！）
  ├── 执行 Layer 1 的前向计算
  └── 丢弃 Layer 1 的完整参数

...以此类推，每层只在显存中短暂存在完整参数...
```

### 3.2 反向传播时序

反向传播方向相反，但同样需要完整参数（计算梯度需要参数）：

```
时刻 t_L: 计算最后一层（第 L 层）的梯度
  ├── All-Gather Layer L 的参数（再次重建！）
  ├── 计算 Layer L 的梯度
  ├── Reduce-Scatter 该层的梯度（每卡只留 1/N）
  └── 丢弃 Layer L 的完整参数

...逆序处理直到第 0 层...
```

### 3.3 预取（Prefetch）优化

如果不做预取，All-Gather 会阻塞计算：

```
无预取（串行）：
  [All-Gather L0] → [Compute L0] → [All-Gather L1] → [Compute L1] → ...
   ←─ 等待 ─→      ←─ 计算 ─→   ←── 等待 ──→     ←── 计算 ──→

有预取（重叠）：
  [All-Gather L0] → [Compute L0]
                       ↓ 同时
                    [All-Gather L1] → [Compute L1]
                                         ↓ 同时
                                      [All-Gather L2] → ...
  GPU 通信单元和计算单元并行工作，有效隐藏通信延迟
```

在 ds_config.json 中通过 `"overlap_comm": true` 启用。

### 3.4 显存峰值分析

使用 ZeRO Stage 3 时，显存峰值出现在"参数重建"时刻：

```
峰值显存 ≈ (1层完整参数) + (所有层的1/N分片) + (当前层激活值)

例：LLaMA-7B，单层约 134M 参数（2 bytes × 134M = 268 MB）
32层总分片（N=8）：7B × 2 / 8 = 1.75 GB
激活值（batch=4）：~2 GB（取决于序列长度）
峰值：~4 GB（+ 优化器状态分片 ~2 GB）= ~6 GB/卡
```

## 4. Activation Checkpointing 集成

### 问题：前向传播的激活值也占用大量显存

**类比**：激活值就像流水线上的"半成品"——反向传播计算梯度时需要用到它们。正常流程是把半成品全部存在仓库里，但仓库（显存）不够用了。

解决方案：**只存关键检查点，其余的用完就扔，需要时重新计算**（以计算换存储）。

### 4.1 激活值显存估算

对于 LLaMA-7B（32层，4096隐层维度），批大小为 8，序列长 2048：

```
每层激活值 ≈ batch_size × seq_len × hidden_dim × bytes
           ≈ 8 × 2048 × 4096 × 2 = 128 MB

32 层合计 ≈ 32 × 128 MB = 4 GB（不算 Attention 矩阵）
加上 Attention 激活 ≈ 再多 ~30 GB

总激活值：~34 GB（batch=8，seq=2048）
```

这比参数本身（14 GB FP16）还大！

### 4.2 DeepSpeed 中启用

```python
from deepspeed.runtime.activation_checkpointing import checkpointing

# 方式 1：通过 deepspeed.checkpointing 替换 torch.utils.checkpoint
deepspeed.checkpointing.checkpoint(function, *args)

# 方式 2：在 ds_config.json 中全局启用
{
  "activation_checkpointing": {
    "partition_activations": true,      # 激活值也分片到多卡
    "cpu_checkpointing": false,         # 是否卸载到 CPU（极端省显存）
    "contiguous_memory_optimization": true,
    "number_checkpoints": null,         # null 表示对所有层
    "synchronize_checkpoint_boundary": false,
    "profile": false
  }
}
```

### 4.3 计算开销

激活重计算需要额外执行一次前向传播：

```
显存节省：~90%（只保留检查点边界处的激活）
计算开销：+33%（额外执行一次前向计算）
```

**经验法则**：当 GPU 显存 < 需求的 1.3×，开启激活重计算；否则跳过以节省训练时间。

## 5. 混合精度训练

### 问题：FP16 精度不够怎么办？

FP16 的表示范围是 [6×10⁻⁸, 65504]。在深度学习中，很多梯度值非常小（如 1×10⁻⁷），会直接"下溢"（Underflow）变成 0。

### 5.1 损失缩放（Loss Scaling）

解决方案：**在反向传播前将 loss 乘以一个大数（scale factor）**，使梯度值放大到 FP16 可表示的范围；更新参数前再除回去。

```python
# 伪代码（DeepSpeed 自动处理这些）
loss_scaled = loss * scale_factor          # 放大（如 scale=65536）
loss_scaled.backward()                     # 反向传播（梯度在 FP16 范围内）
gradients /= scale_factor                  # 缩放回正常值（FP32 中进行）
optimizer.step()                           # FP32 主权重更新
```

### 5.2 BF16 vs FP16

```
FP16：符号(1位) + 指数(5位) + 尾数(10位)  → 精度高，范围窄，需要 Loss Scaling
BF16：符号(1位) + 指数(8位) + 尾数(7位)  → 精度低，范围宽，无需 Loss Scaling

BF16 与 FP32 具有相同的指数位数（8位），因此动态范围一致，
梯度下溢的风险极低，推荐在 Ampere 架构（A100）及以上使用 BF16。
```

### 5.3 ZeRO-3 中的主权重管理

ZeRO Stage 3 + FP16 的挑战：FP32 主权重也被分片了，优化器 step 需要先 All-Gather FP32 主权重，更新后再 Reduce-Scatter 回去。

```
ZeRO-3 参数更新流程：

1. [Reduce-Scatter] 将 FP16 梯度聚合到对应 GPU 的分片
2. 每 GPU 将自己负责的 FP16 梯度转换为 FP32
3. 用 FP32 梯度更新 FP32 主权重分片（本地操作，无通信）
4. 将更新后的 FP32 主权重截断为 FP16
5. [All-Gather] 广播更新后的 FP16 参数供下一步前向使用
```

```json
    "min_loss_scale": 1                  // scale 的下限，防止缩得过小
  },
  "gradient_clipping": 1.0,              // 梯度裁剪阈值（全局 L2 范数）

  "gradient_accumulation_steps": 4,      // 梯度累积步数

```

### 6.2 关键参数调优指南

| 参数 | 小 → 大的效果 |
|------|-------------|
| `reduce_bucket_size` | 更低峰值内存 ← → 更高通信效率 |
| `train_micro_batch_size_per_gpu` | 更低显存占用 ← → 更高 GPU 利用率 |
| `gradient_accumulation_steps` | 增大等效全局 batch 而不增加显存 |
| `initial_scale_power` | 过大导致早期 overflow，过小导致精度损失 |

## 7. Pipeline Parallelism in DeepSpeed

### 问题：ZeRO 是数据并行维度的优化，那模型太宽（单层参数太多）怎么办？

**流水线并行**（Pipeline Parallelism）将模型按层切分到不同 GPU，适合模型深度大（层数多）的场景。

### 7.1 PipelineModule 定义

```python
from deepspeed.pipe import PipelineModule, LayerSpec

class LlamaLayer(nn.Module):
    """一个 LLaMA Transformer 层"""
    def __init__(self, config):
        super().__init__()
        self.attn = LlamaAttention(config)
        self.mlp = LlamaMLP(config)
        self.norm1 = RMSNorm(config.hidden_size)
        self.norm2 = RMSNorm(config.hidden_size)

    def forward(self, x):
        x = x + self.attn(self.norm1(x))
        x = x + self.mlp(self.norm2(x))
        return x

# 将 32 层模型切分为 4 个流水线阶段
model = PipelineModule(
    layers=[
        LayerSpec(EmbeddingLayer, vocab_size, hidden_dim),   # Stage 0
        *[LayerSpec(LlamaLayer, config) for _ in range(32)], # Stage 0-3
        LayerSpec(LMHeadLayer, hidden_dim, vocab_size),       # Stage 3
    ],
    num_stages=4,    # 切分为 4 个 Stage，分配到 4 个 GPU 组
    loss_fn=cross_entropy_loss
)
```

### 7.2 流水线气泡与 1F1B 调度

朴素流水线并行有大量"气泡"（Bubble）——等待上游 Stage 数据的空闲时间：

```
朴素调度（4 Stage，4 micro-batch）：
  Stage 0: [F0][F1][F2][F3][  ][  ][  ][B3][B2][B1][B0]
  Stage 1: [  ][F0][F1][F2][F3][  ][  ][  ][B3][B2][B1]
  Stage 2: [  ][  ][F0][F1][F2][F3][  ][  ][  ][B3][B2]
  Stage 3: [  ][  ][  ][F0][F1][F2][F3][B3][B2][B1][B0]
  气泡比例 = (Stage数-1) / micro-batch数 = 3/4 = 75%！

1F1B 调度（Interleaved 1-Forward-1-Backward）：
  Stage 0: [F0][F1][F2][F3][B0][B1][B2][B3]
  Stage 1: [  ][F0][F1][B0][F2][B1][F3][B2][B3]
  ...
  气泡比例 ≈ (Stage数-1) / (micro-batch数 × Stage数) → 趋近于 0
```

DeepSpeed 默认使用 1F1B 调度，通过增加 micro-batch 数可以进一步压缩气泡。

## 8. DeepSpeed-MII 推理服务

### 8.2 Dynamic SplitFuse

MII 引入的核心推理调度技术，解决 Prefill（计算密集）和 Decode（访存密集）阶段资源利用率失衡的问题：

```
传统方案（Continuous Batching）：
  长 Prefill 请求 → 阻塞短 Decode 请求 → 高延迟

Dynamic SplitFuse：
  将长 Prefill 请求拆分为多个小块（Split）
  将多个 Decode 请求合并处理（Fuse）
  每次迭代固定 token 预算，Prefill + Decode 共同消耗

效果：
  - Decode 延迟更稳定（P99 延迟降低 2-4×）
  - 整体吞吐提升 1.5-2×（相比 vLLM Continuous Batching）
```

## 总结

DeepSpeed 的架构设计遵循"**用通信换内存，用异步换延迟**"的核心原则：

1. **DeepSpeedEngine** 封装了 ZeRO 所有复杂性，接口与 PyTorch 保持兼容
2. **Reduce-Scatter + All-Gather** 是 ZeRO 的通信基础，总量与 DDP 相同但实现了分片
3. **按需 All-Gather** + **预取** 使 Stage 3 的通信开销几乎被完全隐藏
4. **ds_config.json** 是控制所有优化行为的统一入口，`reduce_bucket_size` 和 `overlap_comm` 是最重要的性能参数
5. **Pipeline Parallelism** 可与 ZeRO 组合，形成"3D 并行"（数据并行 + 流水线并行 + 张量并行）

## 2. PyTorch → DeepSpeed 最小改动

### 问题：我现有 DDP 训练代码能不能少改点？

答：可以，改动主要集中在**初始化**和**训练步骤**，其余代码几乎不动。

### 2.1 对比：纯 PyTorch DDP vs DeepSpeed

**BEFORE（纯 PyTorch DDP）**：

```python
import torch
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP

# ── 初始化 ──────────────────────────────────────────────────
dist.init_process_group("nccl")                     # 必须手动初始化
local_rank = int(os.environ["LOCAL_RANK"])
torch.cuda.set_device(local_rank)

model = MyModel().cuda()
model = DDP(model, device_ids=[local_rank])         # 包装 DDP
optimizer = AdamW(model.parameters(), lr=1e-4)
scheduler = get_linear_schedule_with_warmup(optimizer, ...)

# ── 训练循环 ─────────────────────────────────────────────────
for epoch in range(num_epochs):
    for batch in dataloader:
        inputs = batch["input_ids"].cuda()
        labels = batch["labels"].cuda()

        outputs = model(inputs, labels=labels)      # 前向
        loss = outputs.loss

        loss.backward()                             # 反向（DDP 自动 All-Reduce）

        torch.nn.utils.clip_grad_norm_(             # 手动梯度裁剪
            model.parameters(), max_norm=1.0
        )

        optimizer.step()                            # 优化器步骤
        scheduler.step()
        optimizer.zero_grad()                       # 手动清零梯度

# ── 启动命令 ─────────────────────────────────────────────────
# torchrun --nproc_per_node=8 train.py
```

**AFTER（DeepSpeed）**：

```python
import deepspeed                                    # 只需导入 deepspeed

# ── 初始化 ──────────────────────────────────────────────────
# 无需手动 dist.init_process_group()！deepspeed.initialize 自动处理

model = MyModel()                                   # 注意：不需要 .cuda()
optimizer = AdamW(model.parameters(), lr=1e-4)
scheduler = get_linear_schedule_with_warmup(optimizer, ...)

model_engine, optimizer, _, lr_scheduler = deepspeed.initialize(
    model=model,
    optimizer=optimizer,
    lr_scheduler=scheduler,
    config="ds_config.json"                         # 所有配置集中在这里
)

# ── 训练循环 ─────────────────────────────────────────────────
for epoch in range(num_epochs):
    for batch in dataloader:
        inputs = batch["input_ids"].to(model_engine.local_rank)
        labels = batch["labels"].to(model_engine.local_rank)

        outputs = model_engine(inputs, labels=labels)   # 前向（自动 All-Gather）
        loss = outputs.loss

        model_engine.backward(loss)                     # 反向（自动 Reduce-Scatter）
        # 梯度裁剪通过 ds_config 的 gradient_clipping 字段控制，无需手动调用

        model_engine.step()                             # 优化器 + 自动 zero_grad + scheduler

# ── 启动命令 ─────────────────────────────────────────────────
# deepspeed --num_gpus=8 train.py
# 或：torchrun --nproc_per_node=8 train.py（需要在代码中用 deepspeed.init_distributed()）
```

**改动总结**：
- 删除 `dist.init_process_group`、`DDP` 包装
- 将 `optimizer.step()` + `scheduler.step()` + `optimizer.zero_grad()` 合并为 `model_engine.step()`
- 将 `loss.backward()` 改为 `model_engine.backward(loss)`
- 新增 `ds_config.json` 配置文件

## 3. ds_config.json for ZeRO Stage 2（单机 8 GPU）

### 推荐场景：7B-13B 模型，8×A100 40GB/80GB，显存够但优化器状态撑满

```json
{
  "zero_optimization": {
    "stage": 2,
    "overlap_comm": true,
    "contiguous_gradients": true,
    "reduce_scatter": true,
    "reduce_bucket_size": 5e8,
    "allgather_bucket_size": 5e8
  },
  "bf16": {
    "enabled": true
  },
  "gradient_clipping": 1.0,
  "train_micro_batch_size_per_gpu": 4,
  "gradient_accumulation_steps": 8,
  "steps_per_print": 50,
  "wall_clock_breakdown": false
}
```

### 3.1 关键参数详解

**`overlap_comm: true`**：通信与计算重叠。在进行梯度 Reduce-Scatter 的同时继续后续层的计算。单机 NVLink 连接时效果显著，建议始终开启。

**`contiguous_gradients: true`**：将所有梯度合并存储在一块连续内存中，减少内存碎片，提升 All-Reduce 效率。代价是需要额外 ~1× 梯度显存作为缓冲区，但通常值得。

**`reduce_bucket_size: 5e8`**：梯度缓冲区大小（字节），5×10⁸ = ~500MB。更大的桶 → 更高的 All-Reduce 效率（减少通信次数），但峰值显存增加。经验值：4-12 GPU 用 5e8，更多 GPU 考虑 2e8。

**全局 batch size 计算**：
```
全局 batch = train_micro_batch_size_per_gpu × gradient_accumulation_steps × GPU 数量
           = 4 × 8 × 8 = 256
```

## 4. ds_config.json for ZeRO Stage 3 + CPU Offload（多机）

### 推荐场景：70B 模型，8×A100 80GB，或更大规模多机训练

```json
{
  "zero_optimization": {
    "stage": 3,
    "offload_optimizer": {
      "device": "cpu",
      "pin_memory": true
    },
    "offload_param": {
      "device": "cpu",
      "pin_memory": true
    },
    "overlap_comm": true,
    "contiguous_gradients": true,
    "sub_group_size": 1e9,
    "reduce_bucket_size": 1e6,
    "stage3_prefetch_bucket_size": 1e6,
    "stage3_param_persistence_threshold": 1e6,
    "stage3_max_live_parameters": 1e9,
    "stage3_max_reuse_distance": 1e9,
    "stage3_gather_16bit_weights_on_model_save": true
  },
  "bf16": {
    "enabled": true
  },
  "gradient_clipping": 1.0,
  "train_micro_batch_size_per_gpu": 1,
  "gradient_accumulation_steps": 16
}
```

### 4.1 ZeRO Stage 3 特有参数详解

**`offload_optimizer.pin_memory: true`**：将 CPU 内存页锁定（Pinned Memory），避免操作系统将其 swap 出去，PCIe DMA 传输速度提升 ~2×。需要确保机器 RAM 充足（建议 ≥ 500 GB 训 70B）。

**`sub_group_size: 1e9`**：优化器步骤的分组大小（参数数量）。CPU Offload 时，按 sub_group 批量将 FP32 参数从 CPU 取回更新，再放回 CPU。值太小 → PCIe 往返次数多，延迟高；值太大 → 峰值 CPU 内存占用高。

**`stage3_prefetch_bucket_size: 1e6`**：前向传播预取的参数量（参数数量）。太大 → 显存浪费；太小 → 预取量不足，产生等待。建议设为单层参数量的 ~1.1×。

**`stage3_param_persistence_threshold: 1e6`**：参数数量少于此阈值的层（如 LayerNorm、Embedding 头部等小参数层）不参与分片，直接在每张 GPU 上全量保留。减少小层的 All-Gather 开销。

**`stage3_max_live_parameters: 1e9`**：GPU 上同时保留的活跃参数数量上限。超过此限制时，ZeRO 会主动释放已完成的层的参数。调小 → 更省显存；调大 → 减少 All-Gather 频率。

**`stage3_gather_16bit_weights_on_model_save: true`**：保存 checkpoint 时自动 All-Gather 所有分片的 FP16 参数，生成可直接加载的完整权重文件。**关闭此选项会导致保存的 checkpoint 只有分片，加载时需要特殊处理**。

## 5. HuggingFace Trainer 集成

### 问题：我在用 HuggingFace Trainer，如何接入 DeepSpeed？

只需**一行代码**——在 `TrainingArguments` 中指定 `deepspeed` 参数：

```python
from transformers import (
    AutoModelForCausalLM,
    AutoTokenizer,
    TrainingArguments,
    Trainer,
    DataCollatorForLanguageModeling
)
from datasets import load_dataset

# 加载模型和分词器
model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-2-7b-hf",
    torch_dtype=torch.bfloat16,
    trust_remote_code=True
)
tokenizer = AutoTokenizer.from_pretrained("meta-llama/Llama-2-7b-hf")

# 准备数据集
dataset = load_dataset("tatsu-lab/alpaca", split="train")

def tokenize_function(examples):
    return tokenizer(
        examples["text"],
        truncation=True,
        max_length=2048,
        padding="max_length"
    )

tokenized_dataset = dataset.map(tokenize_function, batched=True, remove_columns=dataset.column_names)

# 训练参数（只需加 deepspeed 这一行！）
training_args = TrainingArguments(
    output_dir="./llama2-7b-finetuned",
    per_device_train_batch_size=4,
    gradient_accumulation_steps=8,
    num_train_epochs=3,
    bf16=True,                          # A100 及以上使用 BF16
    learning_rate=2e-5,
    lr_scheduler_type="cosine",
    warmup_ratio=0.05,
    logging_steps=10,
    save_steps=500,
    save_total_limit=3,
    evaluation_strategy="steps",
    eval_steps=500,
    deepspeed="ds_config_stage2.json",  # ← 接入 DeepSpeed 就这一行！
    report_to="wandb",
    run_name="llama2-7b-alpaca"
)

trainer = Trainer(
    model=model,
    args=training_args,
    train_dataset=tokenized_dataset,
    eval_dataset=tokenized_dataset.select(range(200)),
    data_collator=DataCollatorForLanguageModeling(tokenizer, mlm=False)
)

trainer.train()
```

## 7. OOM 调试指南

### 问题：训练跑到一半 OOM 了，如何快速定位和解决？

### 7.1 如何读 DeepSpeed 内存报告

在 ds_config.json 中加入 `"memory_breakdown": true`，DeepSpeed 会在每步打印详细显存分解：

```
[2024-01-15 10:23:45] [INFO] [memory.py:47] MA 42.31 GB  Max_MA 43.68 GB  CA 44.00 GB ...
  ├── model_states: 28.5 GB    ← 权重+梯度+优化器状态
  ├── activation: 12.3 GB     ← 激活值（和 batch size 正相关）
  ├── grad_buffer: 1.8 GB     ← 梯度缓冲区（reduce_bucket_size 控制）
  └── other: 1.68 GB          ← CUDA context 等
```

### 7.2 OOM 决策树

```
训练出现 OOM？
│
├─ 是否刚刚开始就 OOM？
│   ├─ 是 → 模型太大，当前 ZeRO Stage 不够用
│   │       → 升级 ZeRO Stage（1→2→3）
│   └─ 否 → 训练中途 OOM，可能是 batch 大小或序列长度问题
│
├─ ZeRO Stage 已是 3，仍然 OOM？
│   ├─ 检查激活值大小（开启 activation_checkpointing）
│   └─ 开启 CPU Offload（offload_optimizer + offload_param）
│
├─ 已开 CPU Offload，仍然 OOM？
│   ├─ 降低 stage3_max_live_parameters
│   ├─ 减小 train_micro_batch_size_per_gpu（从 4 降到 1）
│   └─ 减小 max_seq_length（序列越长激活越大）
│
└─ 以上全试过，仍然 OOM？
    → 增加 GPU 数量，或使用更大显存的 GPU
```

### 7.3 参数调整优先级

| 操作 | 显存节省 | 训练速度影响 | 建议优先级 |
|------|---------|------------|----------|
| 减小 `train_micro_batch_size_per_gpu` | 大 | 小（可用 gradient_accumulation 补偿） | ⭐⭐⭐⭐⭐ |
| 开启 `activation_checkpointing` | 大 | -33%（重算激活） | ⭐⭐⭐⭐ |
| 升级到 ZeRO Stage 3 | 大 | -5~15%（额外通信） | ⭐⭐⭐⭐ |
| 开启 `offload_optimizer` | 极大 | -20~40%（PCIe 传输） | ⭐⭐⭐ |
| 开启 `offload_param` | 极大 | -40~60%（频繁 PCIe） | ⭐⭐ |
| 减小 `reduce_bucket_size` | 小 | 极小 | ⭐⭐ |

## 8. 常见陷阱与解决方案

### 8.1 梯度累积与 ZeRO 的同步时机

**问题**：在梯度累积时（`gradient_accumulation_steps > 1`），前 N-1 步不应该同步梯度，只有第 N 步才触发 All-Reduce/Reduce-Scatter。

**DeepSpeed 的处理**：DeepSpeed 自动追踪步数，在非同步步骤会跳过梯度同步。但使用自定义训练循环时，必须使用 `model_engine.no_sync()` 上下文管理器：

```python
for step, batch in enumerate(dataloader):
    is_accumulation_step = (step + 1) % gradient_accumulation_steps != 0

    if is_accumulation_step:
        # 前 N-1 步：只做前向+反向，不同步梯度
        with model_engine.no_sync():
            loss = model_engine(batch)
            model_engine.backward(loss)
    else:
        # 第 N 步：触发梯度同步 + 优化器更新
        loss = model_engine(batch)
        model_engine.backward(loss)
        model_engine.step()
```

实际上，`model_engine.backward()` 内部已自动处理此逻辑，**直接调用 `model_engine.step()` 时无需手动处理**。仅在绕开 engine step 时需注意。

### 8.2 Batch Size 线性缩放规则

增加 GPU 数量时，需要相应调整学习率：

```
线性缩放规则：
  原始设置：8 GPU，global_batch=256，lr=1e-4
  新设置：  16 GPU，global_batch=512，lr=2e-4  （lr 随 batch 线性增大）

实践中，学习率不宜超过 1e-3（不然训练发散），超过时需配合 warmup 步数增加
```

### 8.3 ZeRO-3 Checkpoint 保存与加载

**问题**：ZeRO-3 下，每张 GPU 只有 1/N 的参数，直接调用 `model.state_dict()` 只能得到分片，无法直接用于推理。

**正确保存方式**：

```python
# 方式 1：使用 DeepSpeed 内置的 save_checkpoint（推荐）
model_engine.save_checkpoint(
    save_dir="./checkpoint",
    tag="step_1000",
    exclude_frozen_parameters=False
)
# 加载时：
model_engine.load_checkpoint(
    load_dir="./checkpoint",
    tag="step_1000"
)

# 方式 2：保存可直接加载的 HuggingFace 格式（需要 gather_16bit_weights_on_model_save=true）
# 在 ds_config.json 中确保：
# "stage3_gather_16bit_weights_on_model_save": true

if model_engine.local_rank == 0:
    # 只在主进程保存，DeepSpeed 会自动 All-Gather 完整权重
    model_engine.module.save_pretrained("./hf_checkpoint")
    tokenizer.save_pretrained("./hf_checkpoint")
```

### 8.4 学习率调度与梯度累积的交互

**问题**：`scheduler.step()` 应该在每个 optimizer step 调用，还是每个 micro-batch 调用？

**答**：每个 optimizer step（即每 `gradient_accumulation_steps` 个 micro-batch）调用一次。DeepSpeed 的 `model_engine.step()` 会自动处理这个逻辑，无需手动干预。

如果你自定义了 scheduler，在传给 `deepspeed.initialize()` 的参数中指定，DeepSpeed 会在正确的时机调用。

## 9. 吞吐量基准测试

### 问题：各种 ZeRO 配置下，实际训练速度有多大差异？

### 9.1 基准测试方法

```python
import time
import torch
import deepspeed

def measure_throughput(model_engine, dataloader, num_steps=50):
    """测量训练吞吐量（tokens/sec/GPU）"""
    model_engine.train()

    # 预热（消除 JIT 编译等初始化开销）
    for i, batch in enumerate(dataloader):
        if i >= 5:
            break
        loss = model_engine(batch["input_ids"].cuda())
        model_engine.backward(loss)
        model_engine.step()

    torch.cuda.synchronize()
    start = time.time()

    total_tokens = 0
    for i, batch in enumerate(dataloader):
        if i >= num_steps:
            break
        seq_len = batch["input_ids"].shape[1]
        batch_size = batch["input_ids"].shape[0]

        loss = model_engine(batch["input_ids"].cuda(), labels=batch["labels"].cuda())
        model_engine.backward(loss.loss)
        model_engine.step()

        total_tokens += batch_size * seq_len

    torch.cuda.synchronize()
    elapsed = time.time() - start

    tokens_per_sec = total_tokens / elapsed
    # 所有 GPU 的平均值（分布式下 total_tokens 是每张卡的）
    return tokens_per_sec

# 同时计算 MFU（Model FLOPs Utilization）
def compute_mfu(model_params, tokens_per_sec_per_gpu, gpu_peak_flops=312e12):
    """
    model_params: 参数量（如 7e9）
    tokens_per_sec_per_gpu: 每张 GPU 处理的 tokens/s
    gpu_peak_flops: A100 BF16 = 312 TFLOPs/s
    
    LLM 训练每 token 的 FLOPs ≈ 6 × model_params（前向 2N + 反向 4N）
    """
    flops_per_token = 6 * model_params
    actual_flops = flops_per_token * tokens_per_sec_per_gpu
    mfu = actual_flops / gpu_peak_flops
    return mfu
```

### 9.2 实测数据（参考基准）

## 总结

将现有 PyTorch 训练代码迁移到 DeepSpeed 只需三步：

1. **安装 DeepSpeed**：`pip install deepspeed`，用 `ds_report` 验证
2. **修改训练代码**：用 `deepspeed.initialize()` 替换 DDP 初始化，用 `engine.backward()` 和 `engine.step()` 替换原有调用
3. **编写 ds_config.json**：根据模型大小和 GPU 数量选择 ZeRO Stage，调整 bucket size

**关键经验**：
- 单机 8 GPU 训 7B，首选 ZeRO Stage 2，无需 CPU Offload
- 训 70B 以上，ZeRO Stage 3 是必须的
- `overlap_comm: true` 几乎没有副作用，始终开启
- 遇到 OOM，先减小 batch size，再开 activation checkpointing，最后才考虑 CPU offload

## 1. 训练 175B 模型面临的三大挑战

### 问题：把 GPT-3 的训练脚本改成单卡会发生什么？

2020 年，OpenAI 发布 GPT-3，参数量 175 billion（1750 亿）。假设你拥有一张 A100 80GB 显卡，尝试用 `torch.nn.DataParallel` 直接训练它——结果是什么？

```
CUDA out of memory. Tried to allocate 2.62 TiB
```

连显存都装不下，更别说训练了。这不是调参能解决的问题，需要从架构层面重新设计。

### 1.1 挑战一：显存墙（Memory Wall）

混合精度训练（FP16 weights + FP32 optimizer states）下，每个参数需要约 **16 bytes** 的存储：

| 状态 | 精度 | 每参数字节数 |
|------|------|-------------|
| 模型权重 | FP16 | 2 bytes |
| 梯度 | FP16 | 2 bytes |
| Adam m（一阶矩） | FP32 | 4 bytes |
| Adam v（二阶矩） | FP32 | 4 bytes |
| FP32 权重备份 | FP32 | 4 bytes |
| **合计** | — | **16 bytes** |

对于 GPT-3 175B：

```
175 × 10^9 × 16 bytes = 2,800 GB = 2.8 TB
```

即使用 1024 张 A100 80GB（总计 81.9 TB 显存），单纯把模型复制到每张卡上根本不可能。**每张卡只能装 2.8 TB / 1024 ≈ 2.73 GB 的模型状态**——这就是并行的必要性。

### 1.2 挑战二：通信墙（Communication Wall）

数据并行中，每步训练结束后需要对所有 GPU 的梯度做 All-Reduce。

```
通信量 = 2 × (N-1)/N × 模型参数量 × 2 bytes
       ≈ 2 × 175B × 2 bytes ≈ 700 GB per step
```

即使使用 200 Gbps InfiniBand，传输 700 GB 也需要：

```
700 GB / (200 Gbps / 8) = 28 秒
```

而一个 forward+backward 只需几秒钟——通信成为严重瓶颈。

### 1.3 挑战三：计算量估算

训练 GPT-3 所需的总算力约为：

```
训练 FLOPs ≈ 6 × N × D
           = 6 × 175 × 10^9 × 300 × 10^9 tokens
           = 3.14 × 10^23 FLOPs
```

用 1024 张 A100（每张 312 TFLOPS BF16），在 50% MFU 下：

```
时间 = 3.14×10^23 / (1024 × 312×10^12 × 0.5) ≈ 34 天
```

**关键洞察**：必须在保持高 GPU 利用率的同时，将模型切分到多 GPU。三大问题指向同一个解决方案——**3D 并行**。

```
         单卡训练（不可行）
              │
              │ OOM for any model > 80B
              ▼
         数据并行（DP）
              │
              │ 每卡仍需完整模型，175B 无法放下
              ▼
         张量并行（TP）+ 流水线并行（PP）
              │
              │ 切分单个层 + 切分层数
              ▼
         3D 并行（DP × TP × PP）
              │
              │ 1024 GPUs，每卡只存 ~2GB 参数
              ▼
         GPT-3 训练成功 ✓
```

## 2. 数据并行（DP）——最熟悉的并行方式

### 问题：数据并行能训练 175B 模型吗？

数据并行是最直观的并行方式：**每张 GPU 持有完整模型的一份拷贝，处理不同的 mini-batch，最后同步梯度**。

### 2.1 工作流程

```
Batch B
    │
    ├──────────────────────────────────────┐
    │                                      │
    ▼                                      ▼
GPU 0 [完整模型]                      GPU 1 [完整模型]
  处理 B[0:N/2]                         处理 B[N/2:N]
    │                                      │
    └──────────── All-Reduce 梯度 ─────────┘
                      │
                  更新权重（相同更新）
```

每一步训练：
1. 各 GPU 独立进行 forward + backward，得到本地梯度
2. All-Reduce 同步所有 GPU 的梯度（取均值）
3. 各 GPU 使用相同梯度更新权重

### 2.2 数据并行的局限性

```python
# PyTorch DDP 示例
model = GPTModel(num_layers=32, hidden_size=4096)  # ~7B 参数
model = torch.nn.parallel.DistributedDataParallel(model)
# 每张 GPU 上都存着 7B × 16 bytes = 112 GB —— 必须是 A100 80GB 的两倍才够！
```

**核心限制**：数据并行要求每张 GPU 能装下**完整的**模型 + 优化器状态。对于 7B 模型（FP16 训练需 112 GB），单张 A100 80GB 根本放不下。

数据并行是 3D 并行的"外循环"——在模型已经被切分之后，再用数据并行增加吞吐量。

## 3. 张量并行（TP）——切分单个层

### 问题：一个 Linear 层的权重矩阵有 2 GB，怎么放到 4 张卡上？

GPT-3 中的 FFN 子层宽度为 4 × hidden\_size = 4 × 12288 = 49152。第一个线性层的权重矩阵大小为 12288 × 49152 = 6 亿参数（约 1.2 GB FP16）。张量并行的核心思想：**直接切分权重矩阵，让每张 GPU 只持有其中一部分**。

### 3.1 列并行线性（Column-Parallel Linear）

权重矩阵 W 形状为 `[H, 4H]`，沿**列**方向切分为 N 份：

```
GPU 0: W_0 形状 [H, 4H/N]
GPU 1: W_1 形状 [H, 4H/N]
...
GPU N-1: W_{N-1} 形状 [H, 4H/N]
```

前向传播：

```
输入 X [batch, seq, H]  ──── broadcast 到所有 GPU ────►
  GPU 0: Y_0 = X @ W_0   形状 [batch, seq, 4H/N]
  GPU 1: Y_1 = X @ W_1   形状 [batch, seq, 4H/N]
  ...
  （前向无需通信，每 GPU 独立计算）
```

反向传播时，输入 X 的梯度需要 All-Reduce（因为每个 GPU 都用了完整的 X）。

### 3.2 行并行线性（Row-Parallel Linear）

权重矩阵 W 形状为 `[4H, H]`，沿**行**方向切分为 N 份：

```
GPU 0: W_0 形状 [4H/N, H]
GPU 1: W_1 形状 [4H/N, H]
...
```

前向传播：

```
每 GPU 拿到不同的输入片段（来自上一层的列并行输出）：
  GPU 0: Z_0 = Y_0 @ W_0   形状 [batch, seq, H]（部分结果）
  GPU 1: Z_1 = Y_1 @ W_1   形状 [batch, seq, H]（部分结果）
  ...
  All-Reduce：Z = Z_0 + Z_1 + ... + Z_{N-1}   ← 必须通信
```

### 3.3 MLP 子层的张量并行

将列并行和行并行组合，MLP 子层只需 **2 次 All-Reduce**（前向 1 次，反向 1 次）：

```
输入 X [seq, batch, H]
   │
   │（广播到所有 GPU，或使用 sequence parallel，见下）
   ▼
[GPU0: col_lin_0] [GPU1: col_lin_1]  ...  ← 第一个 Linear（列并行）
   │ GELU 本地计算
   ▼
[GPU0: row_lin_0] [GPU1: row_lin_1]  ...  ← 第二个 Linear（行并行）
   │
   ▼
All-Reduce → 输出 Y [seq, batch, H]       ← 唯一的 All-Reduce
```

### 3.4 Self-Attention 子层的张量并行

注意力头天然可以并行——不同 GPU 负责不同的注意力头：

```
Q, K, V 投影：列并行
  GPU 0 计算 head 0...(H/N-1)
  GPU 1 计算 head (H/N)..(2H/N-1)
  ...

输出投影：行并行
  每 GPU 计算本地注意力结果对应的输出
  All-Reduce 汇总
```

每个 Transformer Block 总共只需 **2 次 All-Reduce**（Attention 输出后 1 次，MLP 输出后 1 次）。

### 3.5 序列并行（Sequence Parallelism）

张量并行的一个问题：每次 All-Reduce 前后，LayerNorm 和 Dropout 只运行在 GPU 0 上，浪费其他 GPU 算力；同时激活值需要完整保存在内存中。

**解决方案**：将 LayerNorm 和 Dropout 沿 sequence 维度切分：

```
序列长度 S，TP=4：
  GPU 0: seq[0:S/4]
  GPU 1: seq[S/4:S/2]
  GPU 2: seq[S/2:3S/4]
  GPU 3: seq[3S/4:S]

通信替换：
  All-Reduce → Reduce-Scatter（进入 TP 区域时）
             + All-Gather（离开 TP 区域时）
```

序列并行将激活显存降低 TP 倍，是大批量训练的关键。

## 4. 流水线并行（PP）——切分模型层

### 问题：张量并行只能扩展到一个节点内（8 张 NVLink 连接的 GPU），如何跨节点切分？

张量并行的 All-Reduce 通信延迟敏感，只适合 NVLink 高带宽连接（单向 600 GB/s）。跨节点的 InfiniBand 带宽仅有 200 Gbps，远不够。需要一种**通信量少、延迟不敏感**的并行方式。

**流水线并行**：将模型按层切分，不同节点负责不同的层，激活值沿流水线传递。

### 4.1 朴素流水线（GPipe 风格）

```
GPU 0: Layer 0-7     GPU 1: Layer 8-15    GPU 2: Layer 16-23    GPU 3: Layer 24-31
─────────────────────────────────────────────────────────────────────────────────
Micro-batch 1:
  [fwd_GPU0 →] [fwd_GPU1 →] [fwd_GPU2 →] [fwd_GPU3 →]
               ← loss 计算
  [bwd_GPU3 ←] [bwd_GPU2 ←] [bwd_GPU1 ←] [bwd_GPU0 ←]
```

**时间线**（纵轴为时间，横轴为 GPU）：

```
时间 →
GPU0: [F1][F2][F3][F4][  bubble  ][B4][B3][B2][B1]
GPU1:    [F1][F2][F3][F4][bubble][B4][B3][B2][B1]
GPU2:       [F1][F2][F3][F4][  ][B4][B3][B2][B1]
GPU3:          [F1][F2][F3][F4][B4][B3][B2][B1]
```

**流水线气泡（Pipeline Bubble）**：GPU 等待数据的空闲时间，比例为：

```
气泡比例 = (p - 1) / (m + p - 1)

其中：
  p = 流水线阶段数
  m = micro-batch 数量
```

当 p=8，m=1 时，气泡比例 = 7/8 = **87.5%**——几乎全是气泡！
当 p=8，m=32 时，气泡比例 = 7/39 ≈ **18%**——可以接受。
**必须让 m >> p** 才能有效利用 GPU。

### 4.2 1F1B（One Forward One Backward）调度

相比 GPipe（先跑完所有 micro-batch 的 forward，再跑 backward），1F1B 交错执行：

```
时间 →
GPU0: [F1][F2][F3][F4][B1][F5][B2][F6][B3][F7][B4][B5][B6][B7]
GPU1:    [F1][F2][F3][F4][B1][F5][B2][F6][B3][F7][B4][B5][B6][B7]
GPU2:       [F1][F2][F3][B1][F4][B2][F5][B3][F6][B4][B5][B6][B7]
GPU3:          [F1][F2][B1][F3][B2][F4][B3][F5][B4][B5][B6][B7]
```

优势：**在稳定阶段，每张 GPU 只需保存 1 个 micro-batch 的激活**（而非 m 个），大幅节省显存。气泡比例与 GPipe 相同，但显存效率更高。

### 4.3 交错式流水线（Interleaved Pipeline / Virtual Stages）

进一步减少气泡：让每张 GPU 持有 k 个**不连续的**层块（虚拟阶段），而非 1 个连续块。

```
普通 PP（p=4，每 GPU 2 层，共 8 层）：
  GPU0: [L0, L1]
  GPU1: [L2, L3]
  GPU2: [L4, L5]
  GPU3: [L6, L7]

交错 PP（p=4，k=2，每 GPU 各持有两块）：
  GPU0: [L0, L1] + [L4, L5]
  GPU1: [L2, L3] + [L6, L7]
  （层流转顺序：L0→L2→L4→L6→L1→L3→L5→L7）
```

气泡比例降为：

```
气泡比例 = (p - 1) / (m·k + p - 1)
```

k=2 时气泡减半，代价是每次传递需要通信 **2k 次**而非 **2 次**。

## 5. 3D 并行——TP × PP × DP 的组合

### 问题：如何把 1024 张 GPU 组织成高效的训练集群？

### 5.1 三维进程网格

将 1024 张 GPU 组织为三维网格 `[DP, PP, TP]`：

```
3D 进程拓扑（TP=8, PP=16, DP=8）：

   DP 维度（8组）
   ┌─────────────────────────────────────────┐
   │  PP 流水线 0（16个节点）                 │
   │  ┌──────────────────────────────┐       │
   │  │  [TP组 0: GPU 0-7]  节点 0   │       │
   │  │  [TP组 1: GPU 8-15] 节点 1   │       │
   │  │  ...                         │       │
   │  │  [TP组15: GPU 120-127] 节点15 │       │
   │  └──────────────────────────────┘       │
   │  PP 流水线 1（另 16 节点）              │
   │  ...（共 8 组独立的 PP 流水线）          │
   └─────────────────────────────────────────┘

总计：8（DP）× 16（PP）× 8（TP）= 1024 GPUs ✓
```

### 5.2 通信拓扑设计原则

| 并行类型 | 通信操作 | 通信量 | 推荐互连 |
|---------|---------|--------|---------|
| TP | All-Reduce / All-Gather | 大（每层 2 次） | NVLink（节点内） |
| PP | Point-to-Point（激活） | 中（每 micro-batch） | InfiniBand（节点间） |
| DP | All-Reduce（梯度） | 大（每步 1 次） | InfiniBand（节点间） |

**黄金法则**：
- **TP 组放在同一个 DGX 节点内**（8 张 GPU，NVLink 600 GB/s 单向）
- **PP 和 DP 跨节点**，利用 InfiniBand 的低延迟特性

```
一个 DGX A100 节点（8 GPUs，NVLink 互连）
┌──────────────────────────────────────────┐
│  GPU0──GPU1──GPU2──GPU3──GPU4──GPU5──GPU6──GPU7  │
│  ←────────── TP 组，高频 All-Reduce ──────────→  │
└──────────────────────────────────────────┘
         │ InfiniBand 200 Gbps
         ▼
其他节点（PP 下一阶段，或 DP 副本）
```

### 5.3 实际案例：530B 参数 Megatron-Turing NLG

| 参数 | 值 |
|------|-----|
| 模型参数 | 530B |
| GPU 数量 | 2240 × A100 80GB |
| TP 度 | 8 |
| PP 度 | 35 |
| DP 度 | 8 |
| 总计 | 8 × 35 × 8 = 2240 ✓ |
| Micro-batch 数 | 280 |
| 训练时间 | ~84 天 |

## 6. 显存分析——175B 模型需要多少 GPU

### 6.1 参数切分后的每 GPU 显存

采用 TP=8, PP=16, DP=8（共 1024 GPUs）训练 GPT-3 175B：

```
每 GPU 参数量 = 175B / (TP × PP)
             = 175B / (8 × 16)
             = 175B / 128
             ≈ 1.37B 参数
```

权重显存：

```
1.37B × 16 bytes（混合精度）= 21.9 GB
```

### 6.2 激活值显存

激活值不随 TP×PP 缩放那么好（尤其序列方向）。对于序列长度 2048，batch size 1：

```
每层激活 ≈ seq_len × batch × hidden × 34（精确系数，含 attention 中间值）
        = 2048 × 1 × 12288 × 34 × 2 bytes（FP16）
        ≈ 1.7 GB per transformer layer
```

PP=16 意味着每 GPU 负责 96/16 = 6 层：

```
激活显存 ≈ 6 × 1.7 GB = 10.2 GB（不开 activation checkpointing）
```

序列并行将激活显存再降低 TP=8 倍 → **约 1.3 GB**。

### 6.3 完整显存预算

| 项目 | 显存（GB） |
|------|-----------|
| 模型权重（FP16） | 5.5 |
| 梯度（FP16） | 5.5 |
| Adam 优化器状态（FP32） | 11.0 |
| 激活值（序列并行） | 1.3 |
| 框架开销（NCCL buffer 等） | ~3 |
| **合计** | **~26 GB** |

A100 80GB 留有充足余量，可以增大 batch size 以提高吞吐。

## 7. Megatron vs DeepSpeed vs FSDP 定位

### 7.1 三种框架的设计哲学

| 维度 | Megatron-LM | DeepSpeed ZeRO | PyTorch FSDP |
|------|-------------|----------------|--------------|
| **核心策略** | 模型并行（TP + PP）| 参数/梯度/优化器分片 | 全参数分片（类 ZeRO-3）|
| **适用规模** | ≥ 20B，尤其 100B+ | 1B - 70B | 1B - 70B |
| **易用性** | 需修改模型代码 | 配置文件驱动，透明 | PyTorch 原生 API |
| **TP 支持** | ✅ 核心功能 | ❌（需配合 Megatron）| ❌ |
| **PP 支持** | ✅ 1F1B + 交错 | ❌ | ❌ |
| **通信效率** | 极高（TP 用 NVLink）| 中等（ZeRO-3 通信量大）| 中等 |
| **Activation Recompute** | ✅ 细粒度控制 | ✅ | ✅ |
| **代表模型** | Megatron-Turing 530B | BLOOM 176B | LLaMA 2 |

### 7.2 选择建议

```
模型参数量
     │
     ├── < 7B ──→ PyTorch FSDP 或 DeepSpeed ZeRO-2
     │            （单节点或少量节点，工程简单）
     │
     ├── 7B - 70B ──→ DeepSpeed ZeRO-3 或 FSDP
     │               （不需要修改模型架构）
     │
     └── > 70B ──→ Megatron-LM（或 Megatron + DeepSpeed 混合）
                   （TP + PP 是这个规模的唯一选择）
```

**实践中最强组合**：Megatron-LM 的 TP + PP，外加 DeepSpeed 的 ZeRO-1 管理优化器状态，外层 DP。这是训练 100B+ 模型的业界标准配置。

## 总结

Megatron-LM 的 3D 并行是训练超大规模语言模型的工程基石：

1. **TP（张量并行）**：切分单个层的权重矩阵，减少每 GPU 参数量，利用节点内 NVLink 高带宽
2. **PP（流水线并行）**：切分模型层数，用 1F1B 调度减少显存，跨节点传递激活值
3. **DP（数据并行）**：在已有 TP×PP 切分的基础上，通过多副本增加吞吐量
4. **关键比例**：TP × PP × DP = 总 GPU 数，且 m（micro-batch 数）>> p（PP 度）

下一步：[架构详解与核心组件](./01-架构详解与核心组件.md) ——深入代码，理解进程组初始化和 ColumnParallelLinear 的实现。

## 1. 进程组初始化

### 问题：8 张 GPU 同时运行，如何知道自己属于哪个 TP 组、哪个 PP 阶段？

分布式训练启动时，每个进程拿到一个全局 rank（0 到 world\_size-1）。Megatron-LM 的任务是把这些 rank **映射到三维网格**中，并为每个维度创建 NCCL 通信组。

### 1.1 initialize_model_parallel 核心逻辑

以 8 个 GPU、TP=2、PP=2、DP=2 为例（8 = 2×2×2）：

```
全局 rank 编号：0  1  2  3  4  5  6  7

三维网格排列（TP 是最内层，DP 是最外层）：
  DP=0, PP=0: rank [0, 1]   ← TP 组
  DP=0, PP=1: rank [2, 3]   ← TP 组
  DP=1, PP=0: rank [4, 5]   ← TP 组
  DP=1, PP=1: rank [6, 7]   ← TP 组
```

对应的三种进程组：

```
TP 组（共 4 组，每组 2 个 rank，负责同一层的不同切片）：
  [0, 1]  [2, 3]  [4, 5]  [6, 7]

PP 组（共 4 组，每组 2 个 rank，负责不同层的流水传递）：
  [0, 2]  [1, 3]  [4, 6]  [5, 7]

DP 组（共 4 组，每组 2 个 rank，持有相同层的不同数据副本）：
  [0, 4]  [1, 5]  [2, 6]  [3, 7]
```

代码骨架（简化自 `megatron/core/parallel_state.py`）：

```python
def initialize_model_parallel(
    tensor_model_parallel_size: int = 1,
    pipeline_model_parallel_size: int = 1,
):
    world_size = torch.distributed.get_world_size()
    data_parallel_size = world_size // (
        tensor_model_parallel_size * pipeline_model_parallel_size
    )

    # 创建所有 TP 组
    # 遍历 DP 和 PP 维度，找到同属一个 TP 组的 ranks
    for i in range(pipeline_model_parallel_size):
        for j in range(data_parallel_size):
            start_rank = i * tensor_model_parallel_size + \
                         j * pipeline_model_parallel_size * tensor_model_parallel_size
            end_rank = start_rank + tensor_model_parallel_size
            ranks = range(start_rank, end_rank)
            group = torch.distributed.new_group(ranks)
            if torch.distributed.get_rank() in ranks:
                _TENSOR_MODEL_PARALLEL_GROUP = group

    # 类似地创建 PP 组和 DP 组
    # PP 组：同一个 DP 副本中，不同流水阶段的 ranks
    # DP 组：相同 TP + PP 位置，不同数据副本的 ranks
```

## 2. ColumnParallelLinear 和 RowParallelLinear 实现

### 问题：矩阵乘法切分后，梯度如何正确回传？

### 2.1 自定义 Autograd 函数：通信操作的前向/反向

Megatron-LM 使用 4 个自定义函数将通信操作无缝嵌入反向传播：

| 函数名 | 前向 | 反向 |
|--------|------|------|
| `copy_to_tensor_model_parallel_region` | 恒等（Identity） | All-Reduce |
| `reduce_from_tensor_model_parallel_region` | All-Reduce | 恒等 |
| `scatter_to_tensor_model_parallel_region` | Scatter | All-Gather |
| `gather_from_tensor_model_parallel_region` | All-Gather | Reduce-Scatter |

这种设计的妙处：**通信操作对 PyTorch autograd 透明**，梯度自动通过这些函数传递。

```python
class _CopyToModelParallelRegion(torch.autograd.Function):
    """前向：恒等映射（不通信）；反向：All-Reduce（汇总输入梯度）"""
    @staticmethod
    def forward(ctx, input_):
        return input_  # 什么都不做

    @staticmethod
    def backward(ctx, grad_output):
        # 反向时对梯度做 All-Reduce（因为所有 TP rank 用了相同的输入）
        return _reduce(grad_output)

class _ReduceFromModelParallelRegion(torch.autograd.Function):
    """前向：All-Reduce（汇总部分结果）；反向：恒等（梯度直接分发）"""
    @staticmethod
    def forward(ctx, input_):
        return _reduce(input_)  # 汇总所有 TP rank 的部分输出

    @staticmethod
    def backward(ctx, grad_output):
        return grad_output  # 梯度已经正确分配，直接回传
```

### 2.2 ColumnParallelLinear 完整实现骨架

```python
class ColumnParallelLinear(torch.nn.Module):
    """
    将输出维度 output_size 按 TP 度切分，每个 rank 持有 output_size/N 列。
    
    权重形状：[output_size_per_partition, input_size]
    """
    def __init__(
        self,
        input_size: int,
        output_size: int,
        bias: bool = True,
        gather_output: bool = True,  # 是否在输出时 All-Gather
        skip_bias_add: bool = False,
    ):
        super().__init__()
        world_size = mpu.get_tensor_model_parallel_world_size()
        # 每个 rank 只持有 1/N 的输出维度
        self.output_size_per_partition = divide(output_size, world_size)

        # 权重和偏置只初始化本 rank 对应的切片
        self.weight = Parameter(torch.empty(
            self.output_size_per_partition,
            input_size,
            dtype=args.params_dtype,
        ))
        _initialize_affine_weight_gpu(self.weight, ...)

    def forward(self, input_: torch.Tensor):
        # 1. 对输入做标记：前向恒等，反向 All-Reduce
        #    （确保输入梯度在所有 TP rank 间正确累加）
        input_parallel = copy_to_tensor_model_parallel_region(input_)

        # 2. 本地矩阵乘法（无通信）
        # input_parallel: [seq, batch, input_size]
        # weight:         [output_size/N, input_size]
        # output_parallel:[seq, batch, output_size/N]
        output_parallel = F.linear(input_parallel, self.weight, self.bias)

        # 3. 是否 All-Gather 拼接完整输出
        if self.gather_output:
            # All-Gather: [seq, batch, output_size]
            output = gather_from_tensor_model_parallel_region(output_parallel)
        else:
            # 保持切分状态（下一层是 RowParallelLinear 时使用）
            output = output_parallel
        return output
```

### 2.3 RowParallelLinear 完整实现骨架

```python
class RowParallelLinear(torch.nn.Module):
    """
    将输入维度 input_size 按 TP 度切分，每个 rank 持有 input_size/N 行。
    
    权重形状：[output_size, input_size_per_partition]
    """
    def __init__(
        self,
        input_size: int,
        output_size: int,
        bias: bool = True,
        input_is_parallel: bool = False,  # 输入是否已经是切分状态
    ):
        super().__init__()
        world_size = mpu.get_tensor_model_parallel_world_size()
        self.input_size_per_partition = divide(input_size, world_size)
        self.input_is_parallel = input_is_parallel

        self.weight = Parameter(torch.empty(
            output_size,
            self.input_size_per_partition,
            dtype=args.params_dtype,
        ))

    def forward(self, input_: torch.Tensor):
        # 1. 输入已经是切分的（来自 ColumnParallelLinear 的输出）
        if self.input_is_parallel:
            input_parallel = input_
        else:
            # 将完整输入 Scatter 到各 rank
            input_parallel = scatter_to_tensor_model_parallel_region(input_)

        # 2. 本地矩阵乘法：得到部分输出
        # input_parallel: [seq, batch, input_size/N]
        # weight:         [output_size, input_size/N]
        # output_parallel:[seq, batch, output_size]（但每个 rank 只有部分贡献）
        output_parallel = F.linear(input_parallel, self.weight)

        # 3. All-Reduce：将各 rank 的部分输出求和得到完整结果
        output = reduce_from_tensor_model_parallel_region(output_parallel)

        # 偏置只在最后一步加（避免每个 rank 重复加）
        if not self.skip_bias_add:
            output = output + self.bias if self.bias is not None else output
        return output
```

### 2.4 MLP 子层的完整数据流

```
输入 X [seq, batch, H]
    │
    │ copy_to_tensor_model_parallel_region
    │ （前向：恒等；反向：All-Reduce 输入梯度）
    ▼
ColumnParallelLinear（W1: [H, 4H/N] per rank）
    │ 本地计算: X @ W1.T  →  [seq, batch, 4H/N]
    ▼
GELU（本地，无通信）
    │ [seq, batch, 4H/N]
    ▼
RowParallelLinear（W2: [H/N, H] → 实际 [4H/N, H]）
    │ 本地计算: partial_out  →  [seq, batch, H]（部分和）
    ▼
All-Reduce（reduce_from_tensor_model_parallel_region）
    │ 汇总各 rank 的部分和
    ▼
输出 Y [seq, batch, H]
```

整个 MLP 子层只有 **1 次 All-Reduce**（前向），反向传播自动触发另外 1 次。

## 3. MegatronModule 与标准 nn.Module 的区别

### 问题：Megatron 的 Embedding 为什么要特别处理？

标准 `nn.Embedding` 的词汇表可能很大（GPT-3 用 50257 个 token），Embedding 权重形状为 `[vocab_size, hidden_size]`。直接放在所有 GPU 上是浪费。

### 3.1 词汇表并行（VocabParallelEmbedding）

```python
class VocabParallelEmbedding(torch.nn.Module):
    """
    将词汇表切分到 TP 组，每个 rank 只持有部分 token 的 embedding。
    
    vocab_size=50000, TP=4:
      rank 0: token [0, 12500)
      rank 1: token [12500, 25000)
      rank 2: token [25000, 37500)
      rank 3: token [37500, 50000)
    """
    def forward(self, input_):
        # 超出本 rank 范围的 token 置 0（mask）
        input_mask = (input_ < self.vocab_start_index) | \
                     (input_ >= self.vocab_end_index)
        masked_input = input_.clone() - self.vocab_start_index
        masked_input[input_mask] = 0
        
        # 本地 lookup
        output_parallel = F.embedding(masked_input, self.weight, ...)
        output_parallel[input_mask, :] = 0.0
        
        # All-Reduce：合并各 rank 的贡献（非本 rank 的部分为 0）
        output = reduce_from_tensor_model_parallel_region(output_parallel)
        return output
```

## 4. 流水线调度——micro-batches 如何流动

### 问题：8 个 PP 阶段上的 32 个 micro-batches，执行顺序是什么？

### 4.1 1F1B 调度的三个阶段

```
流水线启动（Startup）阶段：填充流水线
  GPU 0: [F1][F2][F3][F4][F5][F6][F7][F8]
  GPU 1:    [F1][F2][F3][F4][F5][F6][F7][F8]
  ...
  GPU 7:                              [F1]

稳定（Steady-state）阶段：交替 F 和 B
  GPU 0: [B1][F9][B2][F10][B3][F11]...
  GPU 7: [F2][B1][F3][B2][F4][B3]...

排空（Drain）阶段：流水线清空
  GPU 7:                    [B8][B7]...[B1]
```

### 4.2 关键通信原语

```python
# megatron/core/pipeline_parallel/schedules.py

def recv_forward(tensor_shape, dtype):
    """从流水线上一阶段接收前向激活"""
    if not is_pipeline_first_stage():
        tensor = torch.empty(tensor_shape, dtype=dtype, device=device)
        torch.distributed.recv(tensor, src=get_pipeline_model_parallel_prev_rank())
        return tensor
    return None

def send_forward(output_tensor):
    """将前向激活发送到流水线下一阶段"""
    if not is_pipeline_last_stage():
        torch.distributed.send(
            output_tensor,
            dst=get_pipeline_model_parallel_next_rank()
        )

def recv_backward(tensor_shape, dtype):
    """从流水线下一阶段接收反向梯度"""
    if not is_pipeline_last_stage():
        tensor = torch.empty(tensor_shape, dtype=dtype, device=device)
        torch.distributed.recv(tensor, src=get_pipeline_model_parallel_next_rank())
        return tensor
    return None

def send_backward(grad_tensor):
    """将反向梯度发送到流水线上一阶段"""
    if not is_pipeline_first_stage():
        torch.distributed.send(
            grad_tensor,
            dst=get_pipeline_model_parallel_prev_rank()
        )
```

### 4.3 1F1B 稳定阶段的执行循环

```python
# 简化的 1F1B 调度伪代码
for micro_batch_id in range(num_micro_batches):
    # 接收来自上游的激活
    input_tensor = recv_forward(tensor_shape, dtype)
    
    # 执行前向
    output_tensor = forward_step(data_iterator, model, input_tensor)
    
    # 发送激活给下游
    send_forward(output_tensor)
    
    # 如果已经有完成的 micro-batch 可以反向
    if can_backward:
        output_tensor_grad = recv_backward(tensor_shape, dtype)
        input_tensor_grad = backward_step(optimizer, input_tensor,
                                          output_tensor, output_tensor_grad)
        send_backward(input_tensor_grad)
```

### 4.4 梯度累积与流水线的关系

流水线并行中，每个 PP 阶段积累来自所有 micro-batch 的梯度，最后统一做一次参数更新：

```python
# 全局 batch size = micro_batch_size × gradient_accumulation_steps × DP
# 每个 PP stage 每次优化器步骤处理的 tokens 数：
tokens_per_optimizer_step = (
    micro_batch_size         # 每个 micro-batch 的 batch size
    × seq_length             # 序列长度
    × num_micro_batches      # micro-batch 数
)
```

## 6. 数据管道——IndexedDataset

### 问题：用 HuggingFace datasets 加载 1TB 训练数据，为什么会卡住？

HuggingFace datasets 在大规模场景下有几个问题：
- 随机访问性能差（Arrow 格式不支持高效 seek）
- 多进程预处理时内存占用高
- 不支持高效的 sequence packing（填充不同长度文档到固定长度）

### 6.1 MMapIndexedDataset 格式

Megatron 使用自定义的内存映射二进制格式：

```
my-gpt2_text_document.bin  ← 原始 token id（int16 或 int32 数组）
my-gpt2_text_document.idx  ← 索引文件（每个文档的起止位置）
```

索引文件结构：

```
Header: magic number (8 bytes) + version (8 bytes) + dtype (1 byte)
sizes[]:     每个文档的 token 数（uint32 数组）
pointers[]:  每个文档在 .bin 文件中的字节偏移（uint64 数组）
```

读取时使用 `numpy.memmap`，避免把整个文件加载进内存：

```python
class MMapIndexedDataset(torch.utils.data.Dataset):
    def __getitem__(self, idx):
        ptr = self._index.pointers[idx]
        size = self._index.sizes[idx]
        # 直接从磁盘读取，操作系统负责缓存
        return self._bin_buffer[ptr:ptr + size]
```

### 6.3 Sequence Packing

训练时，多个短文档会被拼接（pack）到一个固定长度的序列中，减少 padding 浪费：

```
文档 A: [tok1, tok2, ..., tokN, <eod>]
文档 B: [tok1, tok2, ..., tokM, <eod>]
文档 C: [tok1, ..., tokK, <eod>]

打包后（seq_len=2048）：
[A_tok1...A_tokN, <eod>, B_tok1...B_tokM, <eod>, C_tok1...C_tokK, <eod>, pad...]
```

Megatron 的 `GPTDataset` 自动处理跨文档边界的 sequence 构建。

## 7. FlashAttention 集成

### 问题：标准 Self-Attention 的显存是 O(S²)，序列长 4096 时光 Attention 就爆显存？

标准 Attention 需要存储 `[batch, heads, seq, seq]` 的注意力矩阵：

```
4096² × 32 heads × batch 4 × 2 bytes = 4 GB  ← 仅注意力矩阵！
```

FlashAttention 通过 IO-aware 的 tiling 算法，将内存复杂度降至 O(S)。

### 7.1 Megatron 中的 FlashAttention 调用

```python
# megatron/core/transformer/dot_product_attention.py

from flash_attn.flash_attn_interface import flash_attn_varlen_func

class FlashSelfAttention(torch.nn.Module):
    def forward(self, q, k, v, attention_mask=None):
        # q, k, v: [batch, seq, num_heads, head_dim]
        output = flash_attn_varlen_func(
            q.view(-1, self.num_heads, self.head_dim),
            k.view(-1, self.num_heads, self.head_dim),
            v.view(-1, self.num_heads, self.head_dim),
            cu_seqlens_q,      # cumulative sequence lengths（用于 varlen）
            cu_seqlens_k,
            max_seqlen_q,
            max_seqlen_k,
            dropout_p=self.attention_dropout if self.training else 0.0,
            causal=True,       # GPT 用 causal mask
            softmax_scale=self.scale,
        )
        return output.view(batch_size, seq_len, -1)
```

### 7.2 与序列并行的配合

开启序列并行时，注意力层的输入已经按序列维度切分：

```
TP rank 0: q[0:S/4], k[0:S/4], v[0:S/4]
TP rank 1: q[S/4:S/2], k[S/4:S/2], v[S/4:S/2]
...

每个 rank 只计算自己负责的序列段的注意力，
但 KV 需要 All-Gather 才能计算跨序列段的注意力。

解决方案（Megatron 的 context_parallel）：
  ring-attention 或 all-gather KV 后本地计算
```

---

## 8. 交错式流水线调度详解

### 问题：1F1B 的气泡比例已经不错了，还能继续优化吗？

### 8.1 普通流水线 vs 交错流水线

```
普通 PP（p=4, m=8）：
  每 GPU 持有连续的 N/4 层
  GPU 0: [L0-L7]
  GPU 1: [L8-L15]
  GPU 2: [L16-L23]
  GPU 3: [L24-L31]

  气泡比例 = (4-1)/(8+4-1) = 3/11 ≈ 27%

交错 PP（p=4, k=2, m=8）：
  每 GPU 持有 2 个不连续的 4 层块
  GPU 0: [L0-L3] + [L16-L19]
  GPU 1: [L4-L7] + [L20-L23]
  GPU 2: [L8-L11] + [L24-L27]
  GPU 3: [L12-L15] + [L28-L31]

  气泡比例 = (4-1)/(8×2+4-1) = 3/19 ≈ 16%
```

### 8.2 交错调度的通信代价

普通 PP 每个 micro-batch 有 `2×(p-1)` 次 P2P 通信（前向 p-1 次 send，反向 p-1 次 send）。

交错 PP 每个 micro-batch 有 `2×(p-1)×k` 次 P2P 通信（k 倍增加）。

### 8.3 何时使用交错调度

```python
# pretrain_gpt.py 或配置文件中
args.virtual_pipeline_model_parallel_size = k  # 虚拟阶段数 k

# 使用条件（经验法则）：
# 1. num_micro_batches 较小（m < 4 × p）
# 2. 节点间带宽充足（P2P 通信开销可以接受）
# 3. 模型层数是 p × k 的整数倍

# 例如：GPT-3 96 层，p=8，k=12 → 每 GPU 12 个块，每块 1 层
```

当 m 远大于 p 时，普通 1F1B 的气泡已经足够小，交错调度带来的额外通信不值得。交错调度适合 **m 较小但需要大 PP 度**的场景。

## 2. 选择并行策略——经验法则

### 问题：我有 64 张 A100，训练一个 70B 模型，TP/PP/DP 分别设多少？

### 2.1 三个维度的选择原则

**TP（张量并行度）**——受限于节点内 GPU 数量：
- TP 的 All-Reduce 必须走 NVLink 才有效，否则通信成为瓶颈
- DGX A100 节点有 8 张 GPU，NVLink 互联，因此 **TP ≤ 8**
- 对于较小模型（< 20B），TP=1 或 TP=2 即可；更大模型用 TP=4 或 TP=8

**PP（流水线并行度）**——受限于 micro-batch 数量：
- 需要 `m ≥ 4 × PP` 才能将气泡比例控制在 ~20% 以下
- 如果 `global_batch_size = micro_batch_size × m × DP`，则 m 受全局 batch size 约束
- **PP 不宜过大**，否则需要非常大的 batch 才能填满流水线

**DP（数据并行度）**——填满剩余的 GPU：
- `DP = total_GPUs / (TP × PP)`
- 更大的 DP 带来更大的全局 batch size，通常有利于收敛速度

### 2.2 并行策略速查表

| 模型规模 | 总 GPU 数 | TP | PP | DP | 每 GPU 参数（亿） |
|---------|-----------|----|----|----|--------------------|
| 7B | 8 | 1 | 1 | 8 | 8.75 |
| 13B | 8 | 2 | 1 | 4 | 16.25 |
| 13B | 16 | 2 | 2 | 4 | 8.13 |
| 70B | 64 | 4 | 4 | 4 | 17.5 |
| 175B | 512 | 8 | 8 | 8 | 27.3 |
| 530B | 1024 | 8 | 16 | 8 | 41.4 |

### 2.3 显存估算公式

快速估算每张 GPU 所需显存（混合精度训练，含优化器状态）：

```
每 GPU 显存（GB） =
    模型参数数（B）× 16 bytes / (TP × PP)            ← 权重 + 梯度 + Adam
    + seq_len × batch_per_gpu × hidden × layers_per_gpu × 34 × 2B  ← 激活值
    + 常数项（约 3-5 GB，框架开销）
```

示例：13B 模型，TP=2，PP=2，seq=2048，micro_batch=2，hidden=5120，每 GPU 8 层：

```
权重相关：13B × 16 / (2×2) = 52 GB
激活值：2048 × 2 × 5120 × 8 × 34 × 2B ≈ 11.5 GB
总计：约 63-65 GB  ← A100 80GB 可以装下
```

### 2.4 全局 Batch Size 设计

全局 batch size 影响模型收敛质量，工业界常用经验值：

```
全局 batch size（tokens）= micro_batch × seq_len × num_micro_batches × DP

GPT-3 训练配置：
  micro_batch = 4
  seq_len = 2048
  num_micro_batches = 32
  DP = 8
  → 全局 batch size = 4 × 2048 × 32 × 8 = 2,097,152 tokens ≈ 2M tokens
```

Chinchilla 论文建议的 batch size schedule：从小（~0.5M tokens）线性增大到目标值。

```bash
#!/bin/bash
# pretrain_7b_single_node.sh
# 适用场景：8×A100 80GB 单节点，训练 7B GPT 模型

# ============================================================
# 模型结构参数
# ============================================================
GPT_ARGS="
    --num-layers 32 \
    --hidden-size 4096 \
    --num-attention-heads 32 \
    --seq-length 2048 \
    --max-position-embeddings 2048 \
    --norm-epsilon 1e-5 \
    --use-rotary-position-embeddings \
    --no-position-embedding \
    --swiglu \
    --ffn-hidden-size 11008 \
"
# --swiglu: 使用 SwiGLU 激活函数（LLaMA 风格），比 GELU 效果更好
# --ffn-hidden-size: FFN 中间层维度（LLaMA 用 8/3 × hidden_size，取整到 256 倍数）
# --use-rotary-position-embeddings: 使用 RoPE 位置编码

# ============================================================
# 并行策略参数（关键！）
# ============================================================
PARALLELISM_ARGS="
    --tensor-model-parallel-size 1 \
    --pipeline-model-parallel-size 1 \
    --sequence-parallel \
"
# 7B 模型单节点无需 TP/PP，8 卡全做 DP
# --sequence-parallel: 开启序列并行（在 TP > 1 时有效，节省激活显存）

# ============================================================
# 训练超参数
# ============================================================
TRAINING_ARGS="
    --micro-batch-size 4 \
    --global-batch-size 256 \
    --lr 3e-4 \
    --min-lr 3e-5 \
    --train-iters 100000 \
    --lr-decay-iters 100000 \
    --lr-decay-style cosine \
    --lr-warmup-fraction 0.01 \
    --clip-grad 1.0 \
    --weight-decay 0.1 \
    --adam-beta1 0.9 \
    --adam-beta2 0.95 \
    --adam-eps 1e-8 \
    --init-method-std 0.01 \
"
# --micro-batch-size: 单张 GPU 单次处理的 batch size
# --global-batch-size: 全局 batch size = micro × gradient_acc_steps × DP
# Megatron 自动计算 gradient_accumulation_steps = global / (micro × DP)

# ============================================================
# 数据集参数
# ============================================================

    --data-path ./data/my-gpt2_text_document \

# --split: train/valid/test 的比例（千分比，需合计 1000）

# ============================================================

# ============================================================

    --log-interval 100 \
    --save-interval 10000 \
    --eval-interval 1000 \
    --eval-iters 10 \
    --tensorboard-dir ./tensorboard \
    --log-throughput \
    --log-timers-to-tensorboard \
"
# --log-interval: 每 N 步打印一次训练日志
# --save-interval: 每 N 步保存一次检查点
# --log-throughput: 打印 tokens/s 和 MFU 等吞吐指标

# ============================================================
# 优化参数
# ============================================================
OPTIMIZATION_ARGS="
    --use-flash-attn \
    --recompute-activations \
    --recompute-granularity selective \
"
# --use-flash-attn: 使用 FlashAttention 2（内存效率极高）
# --recompute-activations: 激活值重计算（牺牲 30% 计算换取 50% 激活显存）
```

```python
# convert_to_jsonl.py
import json

def convert_pile_to_jsonl(input_file, output_file):
    with open(input_file, 'r') as fin, open(output_file, 'w') as fout:
        for line in fin:
            sample = json.loads(line)
            # Pile 数据集的字段是 "text"，直接转换
            out = {"text": sample["text"]}
            fout.write(json.dumps(out, ensure_ascii=False) + '\n')
```

## 6. MFU 计算与监控

### 问题：训练日志里的 "TFLOPs: 312"，这算高还是低？

**MFU（Model FLOPs Utilization）**= 模型实际利用的算力 / GPU 理论峰值算力。它是衡量训练效率最直接的指标。

### 6.1 理论 FLOPs 计算

Transformer 模型每个 token 的前向+反向 FLOPs（近似公式）：

```
FLOPs per token ≈ 6 × N

其中 N = 模型参数量（注意力层和 FFN 层的权重数之和）

更精确的公式（包含注意力计算本身）：
FLOPs per token = 6N + 12 × n_layers × n_heads × d_head × seq_len
                ≈ 6N（当 d_model >> seq_len 时，后一项可忽略）
```

### 6.2 从训练日志计算 MFU

Megatron-LM 的训练日志示例：

```
 iteration       500/  100000 | consumed samples:      128000 |
 elapsed time per iteration (ms): 1250.3 |
 learning rate: 3.000E-04 | global batch size:   256 |
 lm loss: 3.021E+00 | loss scale: 1.0 |
 grad norm: 0.421 |
 num zeros: 0.0 |
 TFLOPs: 156.3           ← 每张 GPU 的实际 TFLOPs
```

手动验证：

```python
# 配置参数
N = 7e9          # 7B 模型参数量
tokens_per_iter = 256 * 2048  # global_batch × seq_len = 524288
iter_time_s = 1.250           # 每步耗时（秒）
num_gpus = 8
gpu_peak_tflops = 312         # A100 BF16 峰值

# 计算 MFU
actual_flops_per_gpu = 6 * N * tokens_per_iter / iter_time_s / num_gpus
mfu = actual_flops_per_gpu / (gpu_peak_tflops * 1e12)

print(f"每 GPU 实际 TFLOPs: {actual_flops_per_gpu/1e12:.1f}")
print(f"MFU: {mfu*100:.1f}%")
# 典型输出: MFU: 50.1%
```

### 6.3 MFU 基准与优化

| MFU 范围 | 评价 | 常见原因 |
|---------|------|---------|
| > 60% | 优秀 | 充分利用 NVLink 和 FlashAttention |
| 45-60% | 良好 | 正常生产水平 |
| 30-45% | 一般 | 通信成为瓶颈，或 batch size 太小 |
| < 30% | 差 | 严重的通信或 IO 瓶颈 |

**提升 MFU 的实践方法**：

```bash
# 1. 增大 micro-batch-size（提高 GPU 计算密度）
--micro-batch-size 8   # 从 4 改为 8（如显存允许）

# 2. 开启 FlashAttention（减少内存 IO）
--use-flash-attn

# 3. 关闭 activation recompute（如显存充足）
# 去掉 --recompute-activations

# 4. 使用 BF16（比 FP16 更稳定，无需 loss scaling）
--bf16

# 5. 使用融合算子
--use-fused-rmsnorm     # 融合的 RMSNorm
--use-fused-swiglu      # 融合的 SwiGLU
```

## 7. 常见问题调试

### 7.1 NCCL 通信超时

**现象**：训练中途报 `NCCL timeout` 或 `Watchdog caught collective operation timeout`。

```bash
# 诊断：查看 IB 状态
ibstat | grep -E "State|Physical state"
# 期望：State: Active, Physical state: LinkUp

# 解决方案 1：增大 NCCL 超时时间
export NCCL_IB_TIMEOUT=23        # IB 超时（单位：4ms，23 → 约 33 秒）
export NCCL_ASYNC_ERROR_HANDLING=1  # 启用异步错误处理

# 解决方案 2：检查 IB 配置
export NCCL_IB_DISABLE=0          # 确保使用 IB
export NCCL_IB_HCA=mlx5_0         # 指定 IB 网卡
export NCCL_NET_GDR_LEVEL=5       # 启用 GPUDirect RDMA

# 解决方案 3：添加训练参数
# --exit-interval 0 可防止 idle worker 被杀死
```

### 7.2 OOM（显存不足）

**现象**：`CUDA out of memory. Tried to allocate X GiB`。

```bash
# 按显存消耗从大到小排查：

# 1. 降低 micro-batch-size
--micro-batch-size 2    # 从 4 降到 2

# 2. 开启激活值重计算（用计算换显存）
--recompute-activations
--recompute-granularity full    # 更激进：重计算全部激活

# 3. 检查点保存时 OOM → 使用异步保存
--async-save

# 4. 增大 TP（减少每 GPU 参数量）
--tensor-model-parallel-size 4  # 从 2 改为 4

# 5. 减小序列长度（临时调试）
--seq-length 1024   # 从 2048 降到 1024
```

### 7.3 训练 Loss 不收敛或 NaN

**现象**：Loss 突然变成 `nan` 或者一直不下降。

```bash
# 原因 1：学习率过大
--lr 1e-4        # 从 3e-4 降低

# 原因 2：梯度爆炸
--clip-grad 0.5  # 降低梯度裁剪阈值（默认 1.0）

# 原因 3：FP16 溢出（改用 BF16）
--bf16           # 替换 --fp16

# 原因 4：初始化问题
--init-method-std 0.006  # 降低初始化标准差（= 1/sqrt(hidden_size)）

# 调试工具：观察 loss scale 变化
# 训练日志中 "loss scale: X" 如果持续下降，说明有溢出
```

### 7.4 各 PP 阶段显存不均衡

**现象**：某些 PP 阶段 OOM，其他阶段还有剩余。

```bash
# 原因：Embedding 层和最后的 loss 层额外占用显存
# 第一个和最后一个 PP 阶段通常显存使用更多

# 解决方案：调整层分配
--num-layers-per-virtual-pipeline-stage 2  # 使用交错调度时，每个虚拟阶段层数

# 或者手动分配（部分版本支持）：
# 让首尾 stage 少几层，中间 stage 多几层
```

### 7.5 流水线气泡过大，吞吐低

```bash
# 诊断：计算气泡比例
# bubble = (pp - 1) / (num_micro_batches + pp - 1)

# 解决方案 1：增大 num_micro_batches（通过增大 global_batch_size）
--global-batch-size 512   # 从 256 增大到 512

# 解决方案 2：使用交错式流水线
--num-layers 96
--pipeline-model-parallel-size 8
--virtual-pipeline-model-parallel-size 12  # 每 GPU 12 个虚拟阶段，每阶段 1 层
```

## 8. 预训练完整流程示例

### 端到端 Cookbook：从原始数据到可用模型

这是一个 13B 参数模型的完整训练案例（16×A100 80GB，两个节点）。

#### 阶段一：数据准备（预计 2-4 小时）

```bash
# Step 1: 下载并清洗数据（以 C4 数据集为例）
python scripts/download_c4.py --output-dir /data/raw/c4/ --num-proc 32

# Step 2: 数据清洗和格式转换
python scripts/clean_and_convert.py \
    --input-dir /data/raw/c4/ \
    --output-dir /data/jsonl/ \
    --min-length 100 \    # 过滤掉过短文档
    --dedup               # 去重

# Step 3: 分词预处理（并行处理 8 个分片）
for i in {0..7}; do
    python tools/preprocess_data.py \
        --input /data/jsonl/shard_${i}.jsonl \
        --output-prefix /data/processed/c4_shard_${i} \
        --vocab-file ./tokenizer/vocab.json \
        --merge-file ./tokenizer/merges.txt \
        --tokenizer-type GPT2BPETokenizer \
        --append-eod \
        --workers 8 &
done
wait

# Step 4: 验证数据
python -c "
from megatron.core.datasets.indexed_dataset import MMapIndexedDataset
import glob
total = 0
for f in glob.glob('/data/processed/c4_shard_*.bin'):
    prefix = f.replace('.bin', '')
    ds = MMapIndexedDataset(prefix)
    total += sum(ds.sizes)
    print(f'{prefix}: {len(ds)} docs, {sum(ds.sizes)/1e9:.2f}B tokens')
print(f'总计: {total/1e9:.2f}B tokens')
"

# Step 5: 创建数据混合配置
DATA_PATH=""
for i in {0..7}; do
    DATA_PATH="$DATA_PATH 0.125 /data/processed/c4_shard_${i}"
done
```

#### 阶段二：启动训练（预计数天）

```bash
# 节点 0 执行（同时在节点 1 执行相同脚本，改 node_rank=1）
torchrun \
    --nproc_per_node=8 \
    --nnodes=2 \
    --node_rank=0 \
    --master_addr=node01 \
    --master_port=29500 \
    pretrain_gpt.py \
    --num-layers 40 \
    --hidden-size 5120 \
    --num-attention-heads 40 \
    --seq-length 2048 \
    --tensor-model-parallel-size 2 \
    --pipeline-model-parallel-size 2 \
    --micro-batch-size 2 \
    --global-batch-size 1024 \
    --lr 2e-4 \
    --train-iters 200000 \
    --lr-decay-style cosine \
    --lr-warmup-iters 2000 \
    --data-path $DATA_PATH \
    --vocab-file ./tokenizer/vocab.json \
    --merge-file ./tokenizer/merges.txt \
    --tokenizer-type GPT2BPETokenizer \
    --data-impl mmap \
    --split 980,10,10 \
    --bf16 \
    --use-flash-attn \
    --recompute-activations \
    --sequence-parallel \
    --save ./checkpoints/13b \
    --load ./checkpoints/13b \
    --save-interval 5000 \
    --log-interval 50 \
    --eval-interval 500 \
    --eval-iters 20 \
    --tensorboard-dir ./tensorboard/13b \
    --log-throughput \
    2>&1 | tee train_13b.log
```

#### 阶段三：监控关键指标

训练过程中持续观察：

```bash
# 实时查看训练日志
tail -f train_13b.log | grep -E "loss|TFLOPs|MFU|grad norm"

# 关键指标及健康范围
# lm loss:    初始约 10.0，稳定后应降至 2.5-3.5
# grad norm:  应保持在 0.1-2.0 之间，偶尔到 5 可接受
# TFLOPs:     A100 上 7B 模型期望 >150，13B 期望 >120
# loss scale: FP16 时应稳定在较大值（如 32768），持续下降说明溢出

# TensorBoard 可视化
tensorboard --logdir ./tensorboard/13b --port 6006 &
# 浏览器打开 http://localhost:6006
```

#### 阶段四：检查点管理

```bash
# 列出所有检查点
ls ./checkpoints/13b/

# 恢复中断的训练（Megatron 自动从最新检查点恢复）
# 只需重新运行训练脚本，--load 参数会自动找到最新的 iter
```

## 总结

从一个空目录到完成 13B 模型预训练，关键步骤回顾：

```
原始文本数据
    │
    ▼ preprocess_data.py
MMapIndexedDataset（.bin + .idx）
    │
    ▼ torchrun pretrain_gpt.py
3D 并行训练（TP × PP × DP）
    │
    ├── 监控：loss、TFLOPs、MFU、grad norm
    ├── 检查点：每 5000 步保存一次
    │
    ▼ tools/checkpoint/convert.py
HuggingFace 格式模型
    │
    ▼ lm-evaluation-harness
标准基准评测结果
```

**最重要的几条实践经验**：
1. **先在单节点跑通**，验证数据、模型配置和并行策略，再扩展到多节点
2. **MFU 是最重要的效率指标**，低于 40% 要排查通信和数据 IO 瓶颈
3. **micro-batch 数量要远大于 PP 度**，否则流水线气泡浪费计算资源
4. **BF16 优于 FP16**，无需 loss scaling，训练更稳定
5. **FlashAttention + 序列并行**是序列长度 > 2048 时的标配
