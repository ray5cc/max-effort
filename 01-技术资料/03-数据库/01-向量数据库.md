## 1. 问题的起点：语义相似性

想象你在 Stack Overflow 上搜索 "how to reverse a list in Python"。传统数据库会用 `LIKE '%reverse%list%'` 做字符串匹配——但如果某篇文章写的是 "flip array elements Python"，它就找不到了，哪怕含义完全一样。

**SQL 的局限：**

```sql
-- 这个查询只能匹配字符，不能匹配含义
SELECT * FROM docs WHERE content LIKE '%reverse list%';
-- "flip array" 和 "reverse list" 语义相同，但完全匹配不到
```

真正的语义搜索需要理解：

- "猫" 和 "cat" 是同一个概念
- "银行" 在金融语境和河岸语境含义不同
- "苹果手机" 和 "iPhone" 指的是同一件事

这就是向量数据库要解决的核心问题。

## 2. Embedding：用数字表达意义

**Embedding（嵌入向量）** 是将文本（或图像、音频）转化为一组数字的技术。

类比：就像用 GPS 坐标表示地球上的位置。北京是 `(39.9, 116.4)`，上海是 `(31.2, 121.5)`，两个城市在地图上很近，坐标差值也很小。Embedding 做的是同样的事——把"意义"映射到高维空间里的坐标。

```
"我爱吃苹果"     → [0.23, -0.51, 0.87, 0.12, ...]  # 384 维向量
"我喜欢水果"     → [0.21, -0.48, 0.89, 0.15, ...]  # 非常接近！
"量子计算原理"   → [-0.72, 0.33, -0.21, 0.94, ...]  # 距离很远
```

一个常用模型 `all-MiniLM-L6-v2` 产生 384 维向量。OpenAI `text-embedding-ada-002` 产生 1536 维。

**Embedding 捕获语义的原理：**
训练时，模型在大量文本上学习到：经常出现在相同上下文中的词语，它们的向量应该相近。"猫" 和 "狗" 经常出现在宠物相关的句子里，所以它们的向量方向相似。

```
向量空间示意（简化为 2D）：

     猫  狗
      ↑  ↑      ← 宠物方向
      |  |
------+--+-----→ 大小方向
      |
    小鱼          ← 宠物食物，位置居中
      |
    汽车          ← 完全不相关，距离很远
```

## 3. 向量搜索问题

给定一个查询向量 `q`，在 100 万个向量中找到最相近的 K 个——这就是 **K-Nearest Neighbor (KNN)** 问题。

**暴力搜索（Brute Force）：**

```python
import numpy as np

def brute_force_knn(query, vectors, k=5):
    # 计算 query 与所有向量的距离
    distances = np.linalg.norm(vectors - query, axis=1)
    # 找最小的 k 个
    indices = np.argsort(distances)[:k]
    return indices

# 100 万个 384 维向量：每次查询需要 384 × 1,000,000 次乘法
# 耗时约 500ms — 太慢了！
```

**复杂度分析：**
| 数据量 | 暴力搜索耗时 | HNSW 耗时 |
|--------|------------|----------|
| 1 万 | ~5ms | <1ms |
| 10 万 | ~50ms | <1ms |
| 100 万 | ~500ms | ~2ms |
| 1 亿 | ~50s | ~5ms |

这就是为什么需要 **近似最近邻（ANN, Approximate Nearest Neighbor）** 算法——用极少的精度损失换取巨大的速度提升。

## 4. HNSW 算法：图上的捷径

**HNSW（Hierarchical Navigable Small World）** 是目前最流行的 ANN 算法，Chroma 默认使用它。

### 核心思想：跳表 + 图

类比：想象你要在一个城市找咖啡馆。高速公路让你快速到达大区域（高层），然后走支路到街道（低层），最后步行找到门牌（最底层）。

```
HNSW 层次结构：

Layer 2 (最稀疏):  A -------- E
                   |
Layer 1:           A --- B --- E --- F
                   |    |     |
Layer 0 (最密集):  A-B--C-D--E-F--G-H   ← 所有节点都在这一层
```

### 构建阶段（插入节点）

```python
# 伪代码：插入一个新向量
def insert(new_vector):
    # 1. 随机决定该节点出现在哪些层（指数分布）
    max_layer = random_level()  # 大多数只在 Layer 0，少数到更高层

    # 2. 从最高层开始，贪心找到最近的节点
    entry_point = find_entry_point()

    # 3. 逐层下降，在每层选择 M 个最近邻建立连接
    for layer in range(max_layer, 0, -1):
        neighbors = search_layer(new_vector, entry_point, layer)
        connect(new_vector, neighbors[:M])  # M 是超参数，默认 16
```

### 搜索阶段（查询）

```
搜索过程（找与 Q 最相近的节点）：

Layer 2:  从 A 出发 → 跳到 E（更近）→ 下降
           A -------- E ← 在 E 处找到更近的邻居

Layer 1:  从 E 出发 → 跳到 F（更近）→ 下降
           E --- F

Layer 0:  从 F 出发 → 精细搜索 → 找到 G（最近）
           E-F--G-H
              ↑
           最终答案：G
```

**为什么快？**

- 高层节点少，快速缩小搜索范围（像高速公路）
- 低层密集搜索，保证精度
- 复杂度：O(log N) vs 暴力搜索的 O(N)

### HNSW 关键参数

```python
# 在 Chroma 中设置 HNSW 参数
collection = client.create_collection(
    name="my_collection",
    metadata={
        "hnsw:space": "cosine",       # 距离度量
        "hnsw:construction_ef": 200,  # 构建时候选集大小（更大=更准但更慢）
        "hnsw:M": 16,                 # 每个节点的最大连接数（更大=更准但更多内存）
        "hnsw:search_ef": 100,        # 搜索时候选集大小（查询时可调）
    }
)
```

## 5. 距离度量：如何衡量相似

### 余弦相似度（Cosine Similarity）

**测量两个向量的夹角**，忽略长度。

```
向量 A = [1, 2, 3]
向量 B = [2, 4, 6]  ← 是 A 的两倍，但方向相同

cosine_similarity(A, B) = A·B / (|A| × |B|) = 1.0  ← 完全相同！

向量 C = [3, 0, 0]  ← 垂直方向
cosine_similarity(A, C) = 0.0  ← 完全不相关
```

**适用场景：** 文本 Embedding。因为同一段话用不同长度表达（短摘要 vs 长文章），其向量的方向（语义）相同，但长度不同——余弦相似度正确地认为它们相似。

### L2 距离（欧氏距离）

**测量两点之间的直线距离**。

```python
import numpy as np

A = np.array([1, 2, 3])
B = np.array([4, 6, 3])
l2_distance = np.linalg.norm(A - B)  # sqrt((3)² + (4)² + (0)²) = 5.0
```

**适用场景：** 图像 Embedding、地理位置、密集数值特征。当向量的绝对大小有意义时使用。

### 内积（Inner Product / Dot Product）

```python
inner_product = np.dot(A, B)  # A·B
```

**适用场景：** 推荐系统（用户偏好向量 × 物品特征向量），当向量已经归一化时等价于余弦相似度。

### 选择指南

```
选择距离度量：
┌─────────────────────────────────────────┐
│ 我的数据是什么？                          │
├─────────────────┬───────────────────────┤
│ 文本 Embedding  │ → cosine（推荐）        │
│ 图像特征向量    │ → L2                   │
│ 推荐系统评分    │ → inner product        │
│ 地理坐标        │ → L2                   │
│ 已归一化向量    │ → cosine ≈ inner product│
└─────────────────┴───────────────────────┘
```

## 6. Chroma 的定位

Chroma 的设计哲学是 **"开发者优先"**：

```python
# 5 行代码，一个向量数据库跑起来了
import chromadb
client = chromadb.Client()
collection = client.create_collection("demo")
collection.add(documents=["Hello world", "AI is amazing"], ids=["1", "2"])
results = collection.query(query_texts=["machine learning"], n_results=1)
```

**核心特点：**

- 🐍 纯 Python，无需额外服务（in-process 模式）
- 🔋 自带 Embedding 模型（all-MiniLM-L6-v2），无需配置
- 📦 `pip install chromadb` 即开始
- 🔌 深度集成 LangChain、LlamaIndex
- 📊 Documents + Embeddings + Metadata 三合一存储

**适用场景：**

- RAG（检索增强生成）原型开发
- 中小规模语义搜索（<100 万向量）
- AI 应用 Demo 和 PoC

## 8. Chroma 实战教程

前面我们看到了 Chroma 的 5 行极简用法，但真实项目中你需要持久化存储、外部 Embedding 模型、元数据过滤等能力。本节提供一个从零到可运行的完整教程。

### 8.1 安装与快速开始

```bash
# 安装 Chroma（Python 3.9+）
pip install chromadb

# 如果需要使用 Sentence Transformers 作为 Embedding 模型
pip install sentence-transformers
```

```python
import chromadb

# 方式一：内存模式（重启丢失）——适合快速实验
client = chromadb.Client()

# 方式二：持久化模式（数据存到磁盘）——适合开发和小型生产
client = chromadb.PersistentClient(path="./my_chroma_db")

# 创建或获取一个 Collection（类似数据库中的"表"）
collection = client.get_or_create_collection(
    name="tech_articles",
    metadata={"hnsw:space": "cosine"}  # 指定距离度量
)

# 添加文档——Chroma 会自动调用内置模型生成 Embedding
collection.add(
    documents=[
        "Redis 是基于内存的高性能键值数据库，支持 RDB 和 AOF 两种持久化方式",
        "PostgreSQL 是功能最强大的开源关系型数据库，支持 JSON、全文搜索和向量搜索",
        "MongoDB 是流行的文档数据库，使用 BSON 格式存储数据",
        "MySQL 的 InnoDB 引擎使用 B+ 树索引，支持行级锁和 MVCC",
        "Kafka 是分布式消息队列，适合高吞吐量的流式数据处理",
    ],
    metadatas=[
        {"category": "cache",    "year": 2024, "difficulty": "中级"},
        {"category": "rdbms",    "year": 2024, "difficulty": "高级"},
        {"category": "nosql",    "year": 2023, "difficulty": "中级"},
        {"category": "rdbms",    "year": 2024, "difficulty": "高级"},
        {"category": "mq",       "year": 2024, "difficulty": "高级"},
    ],
    ids=["doc1", "doc2", "doc3", "doc4", "doc5"]
)

# 语义搜索
results = collection.query(
    query_texts=["哪个数据库适合做缓存？"],
    n_results=3
)

print("最相关的文档：")
for doc, dist in zip(results["documents"][0], results["distances"][0]):
    print(f"  [{dist:.4f}] {doc[:50]}...")
```

### 8.2 使用外部 Embedding 模型

Chroma 内置的默认模型是 `all-MiniLM-L6-v2`（384 维），对中文支持有限。在生产场景中，你可能需要更强的模型。

**使用 Sentence Transformers（本地，免费）：**

```python
from chromadb.utils import embedding_functions

# 中文优化模型
embed_fn = embedding_functions.SentenceTransformerEmbeddingFunction(
    model_name="BAAI/bge-large-zh-v1.5"  # 1024维，中文SOTA
)

collection = client.get_or_create_collection(
    name="chinese_docs",
    embedding_function=embed_fn,
    metadata={"hnsw:space": "cosine"}
)

# 后续 add / query 时 Chroma 会自动使用这个模型
collection.add(
    documents=["深度学习是机器学习的一个子领域", "神经网络由多层感知器组成"],
    ids=["dl1", "dl2"]
)
```

**使用 OpenAI Embedding API：**

```python
import os

openai_ef = embedding_functions.OpenAIEmbeddingFunction(
    api_key=os.environ["OPENAI_API_KEY"],
    model_name="text-embedding-3-small"  # 1536维，$0.02/1M tokens
)

collection = client.get_or_create_collection(
    name="openai_docs",
    embedding_function=openai_ef
)
```

**手动传入预计算的向量：**

```python
import numpy as np

# 假设你已经用自己的模型生成了向量
my_embeddings = np.random.randn(3, 384).tolist()  # 实际使用真实模型输出

collection.add(
    embeddings=my_embeddings,  # 直接传向量，不传 documents 也行
    documents=["文档A", "文档B", "文档C"],
    ids=["a", "b", "c"]
)
```

### 8.3 元数据过滤（where 与 where_document）

类比：在图书馆找书时，你不仅想找"内容最相关"的书，还想限定"2024 年出版、中级难度"——这就是元数据过滤。

**where 过滤（基于 metadata 字段）：**

```python
# 只在 category="rdbms" 的文档中搜索
results = collection.query(
    query_texts=["索引优化"],
    n_results=3,
    where={"category": {"$eq": "rdbms"}}
)

# 复合条件：category 是 rdbms 或 cache，且 year >= 2024
results = collection.query(
    query_texts=["数据库性能优化"],
    n_results=5,
    where={
        "$and": [
            {"category": {"$in": ["rdbms", "cache"]}},
            {"year": {"$gte": 2024}}
        ]
    }
)

# 支持的操作符：
# $eq, $ne       等于/不等于
# $gt, $gte      大于/大于等于
# $lt, $lte      小于/小于等于
# $in, $nin      在列表中/不在列表中
# $and, $or      逻辑组合
```

**where_document 过滤（基于文档内容的全文匹配）：**

```python
# 语义搜索 + 内容必须包含"持久化"
results = collection.query(
    query_texts=["数据库高可用方案"],
    n_results=5,
    where_document={"$contains": "持久化"}
)

# 组合过滤：metadata + 文档内容
results = collection.query(
    query_texts=["缓存架构"],
    n_results=3,
    where={"difficulty": {"$eq": "高级"}},
    where_document={"$contains": "Redis"}
)
```

### 8.4 更新与删除

```python
# 更新文档（按 ID）
collection.update(
    ids=["doc1"],
    documents=["Redis 7.0 支持 Function、Multi-part AOF 等新特性"],
    metadatas=[{"category": "cache", "year": 2025, "difficulty": "高级"}]

# Upsert：存在则更新，不存在则插入
collection.upsert(
    ids=["doc6"],
    documents=["ClickHouse 是列式 OLAP 数据库，适合大数据分析"],
    metadatas=[{"category": "olap", "year": 2025, "difficulty": "高级"}]
)

# 删除
collection.delete(ids=["doc3"])

# 按条件删除
collection.delete(where={"category": {"$eq": "nosql"}})
```

## 9. pgvector — PostgreSQL 向量扩展

### 9.1 为什么 pgvector 很重要？

类比：想象你已经有了一个装修完毕的厨房（PostgreSQL），突然需要做面包。你可以花大钱买一台独立的面包房设备（独立向量数据库），也可以买一台嵌入式面包机放在现有厨房里（pgvector）。如果你的面包需求不是特别大，嵌入式方案明显更划算。

**pgvector** 是 PostgreSQL 的开源向量扩展，让你可以**用 SQL 做向量搜索**。对于已经使用 PostgreSQL 的团队，这意味着：

- **零额外基础设施**：不需要部署、运维另一套数据库
- **完整 ACID 事务**：向量数据和业务数据在同一个事务中更新
- **SQL 一站式查询**：向量搜索 + 标量过滤 + JOIN + 聚合，一条 SQL 搞定
- **成熟的备份和高可用**：复用 PostgreSQL 的 pg_dump、流复制、Patroni 等

```
传统架构（两套系统）：
┌───────────┐     ┌──────────────┐
│ PostgreSQL │     │ Milvus/Chroma│
│ (业务数据) │     │ (向量数据)    │
└─────┬─────┘     └──────┬───────┘
      │                   │
      └───────┬───────────┘
          应用层负责同步

pgvector 架构（一套系统）：
┌──────────────────────────┐
│ PostgreSQL + pgvector     │
│ (业务数据 + 向量数据)     │
```

### 9.3 向量搜索与距离运算符

pgvector 提供三种距离运算符：

```sql
-- <-> : L2 距离（欧氏距离），值越小越相似
SELECT title, embedding <-> '[0.1, 0.2, ...]' AS distance
FROM documents
ORDER BY embedding <-> '[0.1, 0.2, ...]'
LIMIT 5;

-- <=> : 余弦距离（1 - cosine_similarity），值越小越相似
-- 推荐用于文本 Embedding
SELECT title, embedding <=> '[0.1, 0.2, ...]' AS cosine_distance
FROM documents
ORDER BY embedding <=> '[0.1, 0.2, ...]'
LIMIT 5;

-- <#> : 负内积距离（negative inner product），值越小越相似
-- 推荐用于推荐系统
SELECT title, embedding <#> '[0.1, 0.2, ...]' AS neg_inner_product
FROM documents
ORDER BY embedding <#> '[0.1, 0.2, ...]'
LIMIT 5;
```

```
距离运算符速记：
┌──────────┬────────────────────┬──────────────────────┐
│ 运算符    │ 距离类型            │ 适用场景              │
├──────────┼────────────────────┼──────────────────────┤
│ <->      │ L2 (欧氏距离)      │ 图像特征、地理位置     │
│ <=>      │ 余弦距离            │ 文本 Embedding（推荐） │
│ <#>      │ 负内积              │ 推荐系统              │
└──────────┴────────────────────┴──────────────────────┘
```

### 9.4 索引：IVFFlat vs HNSW

没有索引时，pgvector 做暴力扫描（精确但慢）。数据量超过几万条时，必须建索引。

**IVFFlat 索引：**

```sql
-- IVFFlat：基于倒排文件的索引，构建快，内存友好
-- lists 参数 ≈ sqrt(总行数)，如 100万行 → lists = 1000
CREATE INDEX ON documents
USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 100);

-- 查询时调整 probes（探测的聚类数，越大越准但越慢）
SET ivfflat.probes = 10;  -- 默认 1，建议 lists/10 作为起点

SELECT title, embedding <=> '[0.1, 0.2, ...]' AS distance
FROM documents
ORDER BY embedding <=> '[0.1, 0.2, ...]'
LIMIT 10;
```

**HNSW 索引（推荐）：**

```sql
-- HNSW：召回率更高，查询更快，但构建时间更长、内存更大
CREATE INDEX ON documents
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 200);

-- 查询时调整 ef_search（候选集大小，越大越准）
SET hnsw.ef_search = 100;  -- 默认 40

SELECT title, embedding <=> '[0.1, 0.2, ...]' AS distance
FROM documents
ORDER BY embedding <=> '[0.1, 0.2, ...]'
LIMIT 10;
```

**IVFFlat vs HNSW 对比：**

| 特性     | IVFFlat            | HNSW                 |
| -------- | ------------------ | -------------------- |
| 构建速度 | 快（需要全量数据） | 慢（增量构建）       |
| 查询速度 | 中等               | 极快                 |
| 召回率   | 中等（85-95%）     | 高（95-99%）         |
| 内存占用 | 低                 | 较高                 |
| 增量插入 | 需重建索引         | 支持在线插入         |
| 适用场景 | 数据不频繁变化     | 读多写少、高精度要求 |

> **重要提示**：IVFFlat 索引需要在有数据之后才能创建（因为需要训练聚类中心）。如果表是空的就建索引，所有数据都会被分到一个桶里，等于没有索引。HNSW 没有这个限制。

### 9.5 混合搜索：SQL WHERE + 向量相似度

pgvector 最大的杀手特性——用一条 SQL 同时做标量过滤和向量搜索：

```sql
-- 在 "cache" 类别中，找语义最相关的文档，且创建时间在最近30天
SELECT title, content, category,
       embedding <=> '[0.1, 0.2, ...]' AS distance
FROM documents
WHERE category = 'cache'
  AND created_at > NOW() - INTERVAL '30 days'
ORDER BY embedding <=> '[0.1, 0.2, ...]'
LIMIT 5;

-- 更复杂的查询：向量搜索 + JOIN
SELECT d.title, d.content, u.username,
       d.embedding <=> '[0.1, 0.2, ...]' AS distance
FROM documents d
JOIN users u ON d.author_id = u.id
WHERE d.category IN ('cache', 'rdbms')
  AND u.is_active = true
ORDER BY d.embedding <=> '[0.1, 0.2, ...]'
LIMIT 10;
```

## 10. 核心索引算法详解

HNSW 是目前最流行的 ANN 算法，但在不同场景下，IVF、PQ 和 ScaNN 各有其不可替代的优势。本节深度剖析这些算法的原理。

### 10.1 IVF（Inverted File Index）— 邮政编码式搜索

**类比：** 想象你要在一座百万人口的城市里找到某个人。暴力搜索就是挨家挨户敲门；IVF 就像邮政编码系统——先根据地址确定邮编区域（聚类），然后只在那几个区域里找人。

**原理：**

```
构建阶段：
1. 对所有向量运行 K-Means 聚类，得到 nlist 个聚类中心（质心/centroid）
2. 每个向量被分配到最近质心的"桶"中

                 ●  ●
            ●  ● ★ ●         ●  ●
           ●  ●  ●        ● ★ ●
            (簇A)          (簇B)  ●

    ★ = 质心（centroid）
    ● = 数据点

查询阶段：
1. 计算查询向量 Q 与所有 nlist 个质心的距离
2. 选择最近的 nprobe 个质心
3. 只在这 nprobe 个簇内做精确搜索

    Q（查询向量）
    ↓ 计算与所有质心的距离
    ↓ 选 nprobe=2 个最近的簇
    ↓ 只在簇 A 和簇 B 内搜索
    → 找到 top-K
```

**关键参数：**

```
nlist（以类比说明）：
  = 把城市分成多少个邮编区域
  - 太少（如 10）：每个区域太大，搜索慢
  - 太多（如 100000）：质心太多，计算质心距离变慢
  - 推荐：sqrt(N) 到 4 × sqrt(N)

nprobe（以类比说明）：
  = 查几个邮编区域
  - nprobe=1：最快，但目标可能在相邻区域边界处，漏掉
  - nprobe=nlist：等于暴力搜索
  - 推荐起点：nlist / 10
```

**IVF 的变体组合：**

```
IVF_FLAT：簇内存储原始向量，精确计算距离
  → 内存大，但召回率高

IVF_PQ：簇内用 PQ 压缩向量
  → 内存极小（可缩小 10-50 倍），适合十亿级

IVF_SQ8：簇内用 int8 标量量化（float32→int8）
  → 内存缩小 4 倍，精度损失很小

IVF_HNSW：用 HNSW 加速质心搜索（替代暴力遍历质心）
  → 当 nlist 很大时，质心搜索更快
```

### 10.2 PQ（Product Quantization）— 调色板压缩术

**类比：** 想象你有一张 24 位色彩的照片（1600 万种颜色），但你想把它存成 GIF 格式（只有 256 色）。PQ 做的事情类似——但更精细：它把照片分成 8 个区域，每个区域独立用自己的 256 色调色板来压缩。

**原理分步讲解：**

```
第 1 步：将高维向量分成 m 个子向量

原始向量（d=256维）：[v₀, v₁, v₂, ..., v₂₅₅]
                      ↓ 分成 m=8 段，每段 d/m=32 维
子向量1: [v₀...v₃₁]
子向量2: [v₃₂...v₆₃]
...
子向量8: [v₂₂₄...v₂₅₅]

第 2 步：对每段独立训练 K 个码字（码本 codebook）

子空间1 的训练数据:                 子空间1 的码本（256个码字）:
  [0.23, -0.51, ..., 0.12]          码字 0: [0.20, -0.50, ..., 0.10]
  [0.21, -0.48, ..., 0.15]   K-Means   码字 1: [0.22, -0.49, ..., 0.13]
  [0.19, -0.52, ..., 0.11]  -------→   ...
  ...                                   码字 255: [-0.71, 0.33, ..., 0.94]

第 3 步：量化 = 用最近码字的索引替代原始子向量

原始子向量 [0.23, -0.51, ..., 0.12]
  → 最近的码字是码字 42
  → 存储：42（1 byte）

整条向量压缩后：[42, 157, 3, 89, 221, 14, 66, 200]
  = 8 bytes（原来 256 × 4 = 1024 bytes）
  压缩比：128:1  🔥
```

**距离计算——查找表（ADC）：**

PQ 的另一大亮点是计算距离时不需要解压缩：

```
查询向量 Q 也分成 8 段子向量：Q₁, Q₂, ..., Q₈

预计算查找表（对每个子空间）：
  table[i][j] = distance(Qᵢ, codebook_i[j])
  大小：m × K = 8 × 256 = 2048 个浮点数

计算某条数据向量的距离：
  PQ码 = [42, 157, 3, 89, 221, 14, 66, 200]
  距离 = table[1][42] + table[2][157] + table[3][3] + ... + table[8][200]
  = 8 次查表 + 7 次加法（vs 原来的 256 次乘法 + 255 次加法）

速度提升：约 32 倍  🔥
```

**OPQ 优化（Optimized Product Quantization）：**

PQ 直接按维度顺序切割子空间，但不同维度之间可能有相关性。OPQ 先用一个正交矩阵旋转向量空间，让各维度方差分布更均匀，再做 PQ。这样量化误差可以降低 20-30%。

### 10.3 ScaNN（Google）— 分数感知量化

**ScaNN (Scalable Nearest Neighbors)** 是 Google 在 2020 年开源的 ANN 库，核心创新是**各向异性向量量化（Anisotropic Vector Quantization, AVQ）**。

**传统量化的问题：**

```
传统 PQ/VQ 的目标：最小化量化误差（让量化后的向量尽可能接近原始向量）
  min ||v - q(v)||²   ← v 是原始向量，q(v) 是量化后的向量

但搜索时我们关心的是：内积排序是否正确
  我们需要保证：如果 <q, v₁> > <q, v₂>，那么 <q, q(v₁)> > <q, q(v₂)>

这两个目标不完全一致！
```

**ScaNN 的核心思想（各向异性量化）：**

```
                    ← 查询方向
          v         ← 原始向量
         /|
        / |
       /  |
  q(v)    |  误差   传统量化：最小化 ||v - q(v)||²
          |         各方向的误差一视同仁

ScaNN 的做法：
  在查询方向上的误差权重更高
  在垂直于查询方向的误差可以更大（反正不影响内积排序）

  → 相同的压缩比下，内积排序的准确率更高
```

**ScaNN 的性能表现**（ANN-Benchmarks 数据）：

在相同召回率（95%）下，ScaNN 通常比 HNSW 和 FAISS-IVF 有更高的 QPS，尤其在最大化内积（MIPS）场景下优势明显。

### 10.4 算法对比总表

| 特性         | HNSW                   | IVF_FLAT            | PQ / IVF_PQ          | ScaNN                 |
| ------------ | ---------------------- | ------------------- | -------------------- | --------------------- |
| **核心结构** | 多层跳表图             | K-Means 聚类        | 子空间码本量化       | 树 + 各向异性量化     |
| **类比**     | 高速公路→城市道路→步行 | 邮政编码区域搜索    | 照片调色板压缩       | 分数感知的智能压缩    |
| **构建时间** | O(N log N)，较慢       | O(N)，快（K-Means） | O(N)，含码本训练     | O(N log N)            |
| **查询时间** | O(log N)，极快         | O(N/nlist × nprobe) | 与 IVF 相同+查表加速 | O(log N)              |
| **内存占用** | 高（向量+图结构）      | 高（存完整向量）    | 极低（压缩 10-100x） | 中等                  |
| **召回率**   | 95-99%（最高）         | 85-95%              | 80-92%               | 90-97%                |
| **增量插入** | ✅ 支持                | ❌ 需重建           | ❌ 需重建            | ❌ 需重建             |
| **最佳场景** | 内存充足、读多写少     | 数据不频繁变化      | 十亿级、内存受限     | 推荐系统（MIPS）      |
| **代表实现** | hnswlib, Faiss         | Faiss, Milvus       | Faiss, Milvus        | google-research/scann |

```
选择索引算法的决策树：

数据量与内存预算？
├── 数据量 < 100万，内存充足
│   → HNSW（最高精度，最低延迟）
│
├── 数据量 100万-10亿，内存有限
│   ├── 能接受 85-92% 召回率？
│   │   → IVF_PQ（内存极小）
│   └── 需要 95%+ 召回率？
│       → IVF_FLAT 或 IVF_SQ8
│
├── 场景是推荐系统（最大化内积）？
│   → ScaNN
│
└── 数据量 > 10亿，只有 SSD？
    → DiskANN
```

### 11.1 Embedding 模型选型指南（2026）

```
模型                               维度    语言      成本           特点
─────────────────────────────────────────────────────────────────────────────
```

**选型决策树：**

```
你的场景需要什么？
├── 快速原型验证
│   → all-MiniLM-L6-v2（小、快、免费）
│
├── 生产中文 RAG
│   ├── 可以调 API → text-embedding-3-small（便宜、质量好）
│   └── 必须私有部署 → BAAI/bge-large-zh 或 bge-m3
│
├── 多语言场景
│   → Cohere embed-v3 或 bge-m3
│
├── 需要稠密+稀疏混合检索
│   → bge-m3（同时输出稠密向量和稀疏向量）
│
└── 最高精度，预算充足
    → text-embedding-3-large（可用 dimensions 参数截断到 1024 降低成本）
```

**关键原则：**

- **一致性至上**：索引和查询必须用同一个模型，否则向量空间不对齐，搜索结果会很差
- **维度不是越大越好**：384 维到 1024 维的提升明显，1024 到 3072 的收益递减
- **Matryoshka Embedding**：OpenAI text-embedding-3 系列支持维度截断，如将 3072 维截断到 1024 维，质量损失很小但存储减少 3 倍

### 11.2 文档分块策略（Chunking for RAG）

分块方式直接影响检索质量。类比：如果把整本《红楼梦》作为一个向量存进去，那用户问"林黛玉第一次出场的描写"时，整本书的 Embedding 无法精确代表这个局部信息。必须"切小块"。

**三种主流分块策略：**

```
1. 固定大小分块（Fixed-size Chunking）
   ─────────────────────────────────────
   原理：按字符/token 数切割，带重叠

   chunk_size=512, overlap=50

   文档：[██████████████████████████████████████████]
   块1：  [███████████]
   块2：        [███████████]     ← overlap 区域
   块3：              [███████████]

   优点：简单、一致
   缺点：可能从句子中间切断

2. 递归分块（Recursive Chunking）
   ─────────────────────────────────────
   原理：按层次分隔符依次尝试：\n\n → \n → 。→ 空格 → 字符

   先按段落分：如果段落 < max_size，保留
               如果段落 > max_size，按句子分
               如果句子 > max_size，按字数分

   优点：尊重文本结构，不会在奇怪的地方切断
   缺点：块大小不均匀

3. 语义分块（Semantic Chunking）
   ─────────────────────────────────────
   原理：计算相邻句子的 Embedding 相似度，在相似度骤降处切割

   句子1 ←0.92→ 句子2 ←0.88→ 句子3 ←0.35→ 句子4 ←0.91→ 句子5
                                      ↑
                               在这里切割（话题转换点）

   优点：语义完整，块边界最自然
   缺点：需要额外计算 Embedding，较慢
```

**实践建议：**

- 通用文档（博客、新闻）：递归分块，chunk_size=500-1000 tokens，overlap=50-100
- 技术文档（代码、API 文档）：按 Markdown 标题（## / ###）分块
- 法律/合同文本：语义分块，保证条款完整性
- 对话记录：按轮次分块

### 11.3 混合搜索：稠密向量 + 稀疏 BM25

纯向量搜索有盲区——当用户查询包含专有名词、错误拼写、精确 ID 时，语义搜索可能不如关键词搜索。混合搜索结合两者优势。

**类比：** 找房子时，你既看"离地铁近、学区好"这种模糊需求（语义搜索），也看"3室2厅、朝南"这种精确条件（关键词搜索）。好的房产中介会同时考虑两方面。

```
混合搜索架构：

用户查询："Redis sentinel 哨兵模式配置"
    │
    ├── 稠密向量搜索（语义）
    │   → Embedding → ANN 搜索
    │   → 命中："Redis 高可用方案"、"主从复制与故障转移"
    │
    └── 稀疏 BM25 搜索（关键词）
        → 分词 + TF-IDF 匹配
        → 命中："Redis sentinel 配置教程"、"sentinel.conf 参数详解"
    │
    ↓ 融合（Reciprocal Rank Fusion）
    最终排序：
    1. "Redis sentinel 配置教程"        (BM25精确命中 + 语义相关)
    2. "Redis 高可用方案"              (语义高度相关)
    3. "sentinel.conf 参数详解"         (BM25精确命中)
```

**RRF（Reciprocal Rank Fusion）融合公式：**

```
RRF_score(d) = Σ 1 / (k + rank_i(d))

k = 60（常数，防止高排名文档权重过大）
rank_i(d) = 文档 d 在第 i 路检索中的排名

示例：
文档 X 在向量搜索中排第 3，在 BM25 中排第 1
RRF_score(X) = 1/(60+3) + 1/(60+1) = 0.0159 + 0.0164 = 0.0323

文档 Y 在向量搜索中排第 1，在 BM25 中不在前 100
RRF_score(Y) = 1/(60+1) + 0 = 0.0164

→ 文档 X 排在 Y 前面（两路都命中 > 一路排名特别高）
```

**支持混合搜索的数据库：**

| 数据库             | 实现方式                                |
| ------------------ | --------------------------------------- |
| Weaviate           | 内置 BM25 + 向量双路搜索，原生 RRF 融合 |
| Qdrant             | 稀疏向量 + 稠密向量，Fusion 查询 API    |
| Milvus 2.4         | 多向量字段 + WeightedRanker             |
| Vespa              | 原生混合检索，最灵活的排序表达式        |
| pgvector + pg_trgm | 向量搜索 + PostgreSQL 全文搜索          |

### 11.4 重排序（Reranking）

ANN 搜索返回 top-K 后，可以用更精确的模型重新排序，进一步提升精度。

```
检索流程（两阶段）：

第一阶段：双编码器（Bi-encoder）快速召回 top-100
  查询 → 查询向量 ─┐
                    ├── ANN 搜索 → 快（毫秒级）
  文档 → 文档向量 ─┘              但查询和文档独立编码，信息损失

第二阶段：交叉编码器（Cross-encoder）精确重排 top-100 → top-10
  [查询, 文档1] → Cross-encoder → 分数 0.95  ← 查询和文档拼接输入
  [查询, 文档2] → Cross-encoder → 分数 0.87     能捕获词级交互
  [查询, 文档3] → Cross-encoder → 分数 0.92     但很慢（不能用 ANN）
  ...
  → 按分数重排，取 top-10
```

**常用重排模型（2026）：**

- `BAAI/bge-reranker-v2-m3`：多语言，开源，中文效果好
- `Cohere Rerank`：API 服务，使用简单
- `cross-encoder/ms-marco-MiniLM-L-6-v2`：轻量英文重排

### 11.5 扩展与运维

**分片策略（Sharding）：**

```
当单机装不下所有数据时，需要分片：

策略一：按 hash 分片
  shard = hash(doc_id) % num_shards
  优点：负载均衡
  缺点：查询要广播到所有分片

策略二：按语义分片
  先聚类，同一簇的文档放在同一分片
  优点：查询可以只路由到相关分片
  缺点：数据分布可能不均

策略三：按时间/业务维度分片
  如按月份分片，最近的数据热分片用 HNSW，历史数据冷分片用 IVF_PQ
```

**监控指标：**

```
向量数据库核心监控指标：

性能指标：
├── 查询延迟 P50/P95/P99（SLO 通常 < 100ms）
├── QPS（每秒查询数）
└── 索引构建时间

质量指标：
├── Recall@K（定期用测试集评估，应 > 95%）
├── MRR（Mean Reciprocal Rank）
└── NDCG@K（Normalized Discounted Cumulative Gain）

资源指标：
├── 内存使用率（HNSW 会占大量内存）
├── Growing segment 大小（Milvus: 过大说明写入积压）
└── Compaction 频率与耗时
```

**小结：** Chroma 让向量数据库从"复杂基础设施"变成了"一个 Python 包"。理解 HNSW 算法和 Embedding 原理，是高效使用所有向量数据库的基础。pgvector 让已有 PostgreSQL 用户无需额外基础设施即可拥抱向量搜索，而 IVF、PQ、ScaNN 等索引算法的深度理解，能帮助你在十亿级场景下做出正确的架构选型。
