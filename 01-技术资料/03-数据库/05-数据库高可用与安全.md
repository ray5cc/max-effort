## 1. 为什么需要数据库高可用与安全

- **停机=损失**：数据库是状态核心，故障直接导致业务中断、订单失败。
- **合规要求**：金融/医疗需满足 RTO/RPO、审计、加密与访问控制。
- **攻击面扩大**：暴露在公网、第三方接入、内部越权都会放大风险。

> 类比：银行金库。高可用像备用金库与运钞路线，安全则是门禁、监控和保险箱。

## 2. 核心概念（是什么）

- **RTO/RPO**：恢复时间/恢复点目标，驱动备份频率与复制模式。
- **拓扑模式**：主从/主备、半同步、多主/多活、分片。
- **复制类型**：物理复制（WAL/redo）、逻辑复制（binlog/CDC）、同步/异步/半同步。
- **一致性模型**：强一致、多数派、最终一致；写放大 vs 延迟取舍。
- **安全域**：身份鉴别、访问控制、加密（静态/传输/字段）、审计。

## 3. 高可用与容灾设计（怎么做）

### 3.1 拓扑与复制

| 场景 | 推荐拓扑 | 复制策略 | 取舍 |
| --- | --- | --- | --- |
| 同城跨 AZ | 主库 + 同步/半同步 1-2 副本 | 半同步（关键表），异步（非关键表） | 写延迟↑，RPO≈0 |
| 跨区域容灾 | 主库 + 异步远程备库 | 逻辑/物理异步 | 低延迟 vs 可能丢最新数据 |
| 读多写少 | 主从 + 读写分离 | 异步复制，延迟监控与只读保护 | 一致性风险需强制读主场景 |

**复制要点**

- MySQL：`rpl_semi_sync_master_enabled=ON` 控制半同步；延迟监控 `Seconds_Behind_Master`；防止 GTID 回退。
- PostgreSQL：`synchronous_standby_names` 设置多数派；`wal_level=logical` 支持 CDC；`replication slot` 防止 WAL 被清理。

### 3.2 失败检测与切换

- **健康检查**：多探针（SQL 检查+延迟+复制位点），冷却时间防误切。
- **故障切换**：预先约定优先级，保持 GTID/Lsn 单调；切主后旧主上锁为只读。
- **读写分离保护**：只读库开启 `super_read_only`/`hot_standby_feedback`，防止误写；驱动/连接池配置主从路由与降级。

### 3.3 备份与恢复

- **全量+增量**：每日全量 + 5 分钟 binlog/WAL 归档；定期做“恢复演练”。
- **备份一致性**：快照前 `FLUSH TABLES WITH READ LOCK` 或使用备份工具（XtraBackup、pg_basebackup）；对象存储版本化。
- **恢复校验**：恢复到新实例执行校验 SQL/校验和，对账关键表行数。

## 4. 安全与合规防护（怎么做）

### 4.1 身份与访问控制

- 强制 IAM/LDAP 集中身份，最小权限账号，生产禁用 `root/superuser` 日常操作。
- SQL 白名单/参数化查询，禁止拼接；管理口令存管在 KMS/Secret Manager。

### 4.2 加密与脱敏

- **传输加密**：TLS 必开，校验证书；禁用弱算法。
- **静态加密**：磁盘/表空间加密（TDE）；字段级加密保护身份证/卡号。
- **日志脱敏**：审核日志掩码（如手机号中间四位）。

### 4.3 审计与告警

- **审计内容**：主体/角色、源 IP、SQL 摘要、目标库表、影响行数、结果、trace_id。
- **告警**：高危操作（DDL、权限变更）、异常登录、复制延迟、备份失败。
- **不可篡改存储**：WORM/对象存储版本化，必要时写入链式哈希。

### 4.4 防护与隔离

- VPC 私网访问，最小暴露；跳板机+多因子登录。
- 速率限制与 WAF 防止暴力破解；数据库防火墙阻断危险 SQL 模式。
- 多租户隔离：库/Schema/行级策略，避免租户 ID 由客户端直接决定访问范围。

## 5. 实践案例：跨可用区 MySQL/PG 架构

**目标**：RTO ≤ 3 分钟，RPO ≤ 30 秒，支持读写分离。

1) **拓扑**：Region 内主库 + 半同步副本，跨区域异步备库；Proxy 层支持读写路由与故障切换。  
2) **复制**：主→同城副本开启半同步；主→远程备库异步 + 关键表 CDC 投递到对象存储。  
3) **切换**：健康探针发现复制延迟>5s 或主库不可达时，Promote 半同步副本；旧主强制只读并比对 GTID/Lsn。  
4) **备份**：每日全量快照，binlog/WAL 5 分钟归档；每周演练“恢复到指定时间点 (PITR)”。  
5) **安全**：TLS 强制；账号按角色最小化；审计日志写入 WORM；DDL、权限变更触发 PagerDuty 告警。

ASCII 示意：

```
Client ─▶ Proxy/Router ─▶ Primary (AZ1, semi-sync)
                          │
                          ├─▶ Replica (AZ2, semi-sync; candidate)
                          └─▶ DR Replica (Remote, async)

Backups: Full (daily) + Binlog/WAL archive (5m) → Object Storage
```

## 6. 常见陷阱与最佳实践

- **陷阱：只备不演练** → 定期 PITR 演练并记录 RTO/RPO。  
- **陷阱：异步切主导致数据回退** → 关键表半同步，多数派；切换前比对位点，必要时拒绝提升。  
- **陷阱：读写分离脏读** → 强制关键事务读主，或基于会话一致性等待位点追平。  
- **陷阱：长效高权限账号** → 短期凭证 + 审批 + 审计，定期轮换。  
- **最佳实践**：  
  - 以 SLO/RTO/RPO 反推拓扑和成本；按表分级（账务强一致、日志最终一致）。  
  - 监控复制延迟、慢查询、锁等待，与告警闭环。  
  - 策略即代码：权限、审计、备份策略版本化，纳入评审与回滚。  
  - 数据脱敏与最小留痕，防止日志/备份泄露敏感字段。
