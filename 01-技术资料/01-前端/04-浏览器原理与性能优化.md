## 1. 为什么需要深入理解浏览器

想象一下这样的场景：你的团队刚上线了一个电商首页，产品经理拿着 Google Analytics 报告找到你——**页面平均加载时间 5.2 秒，跳出率 53%**。根据 Google 的研究数据，页面加载时间从 1 秒增加到 3 秒，跳出概率增加 32%；增加到 5 秒，跳出概率增加 90%。

你尝试了一些常见的"优化技巧"：压缩图片、开启 gzip、加个 loading 动画……但效果有限。为什么？因为你在**盲猜瓶颈**，而不是**系统性分析**。

这就像一个病人发烧，不做检查就直接吃退烧药——可能管用，但也可能掩盖了真正的病因。

**深入理解浏览器原理的价值在于**：

- **定位瓶颈**：知道渲染流水线的每个阶段，才能用 DevTools 精准定位哪一步慢
- **避免无效优化**：你以为优化了 JS 执行速度，但瓶颈其实在 Layout 阶段
- **理解框架设计决策**：React 的虚拟 DOM、Vue 的响应式系统，底层都在解决浏览器的渲染效率问题
- **写出高性能代码**：了解重排成本，你会自然而然避免在循环中读取 `offsetHeight`
- **面试硬通货**：浏览器原理是前端面试的必考高频题，需要体系化理解而非碎片化记忆

本文将从浏览器的多进程架构开始，完整走一遍"从 URL 到像素"的全链路，帮助你建立系统性的知识框架。

## 2. 浏览器架构

### 2.1 从单进程到多进程

早期浏览器（如 IE6）是单进程架构——所有 Tab、插件、渲染引擎都跑在一个进程里。结果就是：一个 Tab 崩了，整个浏览器都崩了。一个恶意网页可以访问其他 Tab 的数据。

**类比**：单进程浏览器像一个所有部门挤在同一间办公室的小公司。财务部着火了（崩溃），所有人都得跑（整个浏览器挂掉）。而现代浏览器是一栋写字楼，每个部门有独立的楼层和安全门。

### 2.2 Chrome 多进程架构

现代 Chrome 采用多进程架构，主要包含以下进程：

```
┌─────────────────────────────────────────────────────┐
│                  Browser Process                     │
│  (地址栏、书签、前进/后退、网络请求调度、权限管理)        │
├────────────┬────────────┬───────────┬───────────────┤
│  Renderer  │  Renderer  │    GPU    │   Network     │
│  Process   │  Process   │  Process  │   Service     │
│  (Tab A)   │  (Tab B)   │  (绘制)   │  (网络请求)    │
├────────────┴────────────┼───────────┼───────────────┤
│      Plugin Process     │  Storage  │   Utility     │
│      (扩展/插件)         │  Process  │   Process     │
└─────────────────────────┴───────────┴───────────────┘
```

| 进程 | 职责 | 类比 |
|------|------|------|
| **Browser Process** | UI 管理、用户输入、子进程调度 | 公司总经理办公室 |
| **Renderer Process** | HTML/CSS/JS 解析与渲染，每个 Tab 独立 | 各项目组工位 |
| **GPU Process** | 所有 Tab 共享的 GPU 绘制，合成图层 | 公司打印室 |
| **Network Service** | 网络请求（从 Browser Process 独立出来） | 公司收发室 |
| **Plugin Process** | 每个插件一个进程（如 Flash，现已淘汰） | 外包团队 |
| **Utility Process** | 音频解码、数据解压等通用服务 | 后勤部 |

### 2.3 进程隔离与安全

**Site Isolation（站点隔离）** 是 Chrome 67 引入的安全特性：不同站点的页面一定运行在不同的 Renderer Process 中。

```
site-a.com (Tab 1)  →  Renderer Process A
site-b.com (Tab 2)  →  Renderer Process B
site-a.com 的 iframe 嵌入 site-c.com  →  site-c.com 在独立 Renderer Process C
```

这意味着：
- **崩溃隔离**：Tab A 的渲染进程崩溃，Tab B 完全不受影响
- **安全隔离**：恶意网页的 JS 代码无法直接访问其他站点进程的内存（防御 Spectre 等侧信道攻击）
- **性能隔离**：一个 Tab 的 JS 死循环不会冻结其他 Tab

### 2.4 Renderer Process 内部线程

每个 Renderer Process 内部又有多个线程：

```
Renderer Process
├── Main Thread          # 解析 HTML/CSS, 执行 JS, 计算布局, 绑定事件
├── Compositor Thread    # 接收滚动/动画, 合成图层, 发送给 GPU
├── Raster Thread(s)     # 光栅化（将绘制指令转为像素）
└── Worker Thread(s)     # Web Worker / Service Worker
```

**关键洞察**：JavaScript 执行和 DOM 渲染跑在同一个 **Main Thread** 上，这就是为什么长时间运行的 JS 会阻塞页面交互。

## 3. 导航与网络请求流程

### 3.1 完整链路：从 URL 到响应

当你在地址栏输入 `https://www.example.com` 并按下回车，背后发生了什么？

**类比**：这个过程就像网购下单——你输入地址（URL），快递系统要 **查找收件地址**（DNS）→ **建立运输路线**（TCP）→ **加密包装**（TLS）→ **发送请求**（HTTP Request）→ **收到包裹**（HTTP Response）。

```
用户输入 URL
    │
    ▼
① DNS 解析：域名 → IP 地址
    │  www.example.com → 93.184.216.34
    ▼
② TCP 三次握手：建立可靠连接
    │  SYN → SYN-ACK → ACK
    ▼
③ TLS 握手（HTTPS）：协商加密
    │  ClientHello → ServerHello → 证书验证 → 密钥交换
    ▼
④ HTTP 请求发送
    │  GET / HTTP/1.1  Host: www.example.com
    ▼
⑤ 服务器处理并返回响应
    │  HTTP/1.1 200 OK  Content-Type: text/html
    ▼
⑥ 浏览器接收响应，开始解析
    │  HTML → DOM, CSS → CSSOM, JS → 执行
    ▼
⑦ 渲染页面
```

### 3.2 DNS 解析的层层缓存

DNS 解析并不是每次都去根服务器查询，有层层缓存机制：

```
浏览器 DNS 缓存  →  操作系统 DNS 缓存  →  路由器缓存  →  ISP DNS 服务器  →  根域名服务器
     (最快)                                                                    (最慢)
```

### 3.3 HTTP 缓存策略

HTTP 缓存是性能优化的第一道防线，分为**强缓存**和**协商缓存**：

```
浏览器请求资源
    │
    ├── 强缓存命中？（检查 Cache-Control / Expires）
    │   ├── yes → 直接用缓存，不发请求（200 from cache）
    │   └── no ↓
    │
    ├── 协商缓存（发请求给服务器验证）
    │   │  请求头携带 If-None-Match / If-Modified-Since
    │   ├── 资源未变 → 304 Not Modified（用缓存）
    │   └── 资源已变 → 200 OK（返回新资源）
    │
    └── 无缓存 → 200 OK（正常返回）
```

| 策略 | Header | 说明 | 优先级 |
|------|--------|------|--------|
| **强缓存** | `Cache-Control: max-age=31536000` | 1 年内不再请求 | 最高 |
| **强缓存** | `Expires: Thu, 01 Jan 2027 00:00:00 GMT` | 过期时间（绝对时间，不推荐） | 低于 Cache-Control |
| **协商缓存** | `ETag` / `If-None-Match` | 文件内容哈希 | 高 |
| **协商缓存** | `Last-Modified` / `If-Modified-Since` | 最后修改时间 | 低于 ETag |

**最佳实践**：
- HTML 文件：`Cache-Control: no-cache`（每次协商验证，确保获取最新版）
- CSS/JS/图片（带 hash 文件名）：`Cache-Control: max-age=31536000, immutable`（长期强缓存）

### 3.4 Resource Hints：预加载优化

浏览器提供了多种资源提示机制，让我们可以提前准备后续需要的资源：

```html
<!-- DNS 预解析：提前解析第三方域名的 DNS -->
<link rel="dns-prefetch" href="//api.example.com">

<!-- 预连接：提前完成 DNS + TCP + TLS 握手 -->
<link rel="preconnect" href="https://cdn.example.com" crossorigin>

<!-- 预加载：提前加载当前页面必需的关键资源（高优先级） -->
<link rel="preload" href="/fonts/main.woff2" as="font" type="font/woff2" crossorigin>
<link rel="preload" href="/css/critical.css" as="style">

<!-- 预获取：空闲时提前加载下一个页面可能用到的资源（低优先级） -->
<link rel="prefetch" href="/next-page.js">

<!-- 预渲染（Chrome 新方案：Speculation Rules API） -->
<script type="speculationrules">
{
  "prerender": [{"urls": ["/next-page"]}]
}
</script>
```

| Resource Hint | 做了什么 | 使用场景 |
|---------------|---------|---------|
| `dns-prefetch` | 仅 DNS 解析 | 第三方域名（统计、广告） |
| `preconnect` | DNS + TCP + TLS | 关键第三方 CDN、API |
| `preload` | 下载资源（高优先级） | 字体、关键 CSS、首屏图 |
| `prefetch` | 空闲时下载（低优先级） | 下一页面的 JS/CSS |
| `modulepreload` | 预加载 ES Module | 动态 `import()` 的模块 |

### 3.5 HTTP/2 与 HTTP/3 带来的变化

```
HTTP/1.1                    HTTP/2                      HTTP/3
─────────────               ──────────                  ──────────
一个连接一个请求              多路复用(一个连接多个流)       基于 QUIC/UDP
队头阻塞（线性等待）          头部压缩 (HPACK)             0-RTT 建连
需要域名分片 hack            服务器推送 (Server Push)      无队头阻塞
```

## 4. 渲染流水线

> 这是本文最核心的章节。理解渲染流水线是一切性能优化的基础。

### 4.1 渲染流水线全景

**类比**：渲染流水线就像装修一套房子：

| 阶段 | 类比 | 做了什么 |
|------|------|---------|
| HTML → DOM | 拿到户型图 | 解析 HTML 标签建立文档结构树 |
| CSS → CSSOM | 拿到装修方案 | 解析 CSS 规则建立样式树 |
| DOM + CSSOM → Render Tree | 合并成施工图 | 将可见元素和对应样式关联起来 |
| Layout | 量尺寸、定位置 | 计算每个元素的精确位置和大小 |
| Paint | 刷漆、贴壁纸 | 生成绘制指令（颜色、阴影、文字） |
| Composite | 拍照、分层叠加 | 将图层合成最终画面（GPU 加速） |

```
    HTML                CSS
     │                   │
     ▼                   ▼
   ┌─────┐           ┌──────┐
   │ DOM │           │CSSOM │
   └──┬──┘           └──┬───┘
      │                  │
      └───────┬──────────┘
              ▼
        ┌───────────┐
        │Render Tree│  (display:none 的元素不会出现在这里)
        └─────┬─────┘
              ▼
        ┌───────────┐
        │  Layout   │  计算位置和大小 (x, y, width, height)
        └─────┬─────┘
              ▼
        ┌───────────┐
        │  Paint    │  生成绘制指令列表 (draw rect, draw text...)
        └─────┬─────┘
              ▼
        ┌───────────┐
        │Composite  │  图层合成，发送给 GPU 渲染到屏幕
        └───────────┘
```

### 4.2 各阶段详解

#### DOM 构建

浏览器从网络接收到 HTML 字节流后：

```
字节 (Bytes)  →  字符 (Characters)  →  令牌 (Tokens)  →  节点 (Nodes)  →  DOM 树
```

```html
<html>
  <body>
    <p>Hello</p>
    <div><img src="photo.jpg"></div>
  </body>
</html>
```

生成的 DOM 树：

```
html
 └─ body
     ├─ p
     │  └─ "Hello"
     └─ div
        └─ img
```

**关键点**：DOM 构建是**增量的**——浏览器不需要等到整个 HTML 下载完才开始解析，收到一部分就解析一部分。

#### CSSOM 构建

CSS 的解析方式与 HTML 类似，但有一个关键区别：**CSSOM 构建是阻塞渲染的**。

```css
body { font-size: 16px; }
p { color: #333; font-weight: bold; }
div > img { width: 100%; }
```

浏览器不能只解析部分 CSS 就开始渲染，因为 CSS 有层叠和继承机制——后面的规则可能覆盖前面的。

#### Render Tree 构建

Render Tree = DOM + CSSOM，但注意：
- `display: none` 的元素**不在** Render Tree 中（完全从渲染中移除）
- `visibility: hidden` 的元素**在** Render Tree 中（占位但不可见）
- `<head>` 标签及其子元素不在 Render Tree 中

#### Layout（布局/重排）

Layout 阶段计算每个元素在视口中的精确几何信息：位置 (x, y) 和尺寸 (width, height)。

```javascript
// Layout 计算的结果类似于:
{
  element: 'div.container',
  x: 0, y: 0,
  width: 1200, height: 800,
  children: [
    { element: 'p', x: 16, y: 16, width: 1168, height: 24 }
  ]
}
```

Layout 是**递归的**——父元素的大小可能依赖子元素（如 `height: auto`），子元素的大小也可能依赖父元素（如 `width: 50%`）。

#### Paint（绘制）

Paint 阶段不是直接画像素，而是生成一系列**绘制指令**（Display List）：

```
DrawRect(0, 0, 1200, 800, color=#ffffff)     // 画背景
DrawText("Hello", 16, 16, font=16px, color=#333)  // 画文字
DrawImage(photo.jpg, 16, 56, 1168, 600)      // 画图片
DrawBorder(16, 56, 1168, 600, 1px solid #ccc) // 画边框
```

#### Composite（合成）

合成是现代浏览器的性能关键。浏览器将页面分成多个**图层 (Layers)**，各自独立绘制，最后由 **GPU** 将所有图层合成在一起。

哪些情况会创建独立图层？
- `transform` 或 `opacity` 动画
- `position: fixed`
- `will-change: transform`
- `<video>`, `<canvas>`, `<iframe>`
- CSS `filter`

### 4.3 重排 (Reflow) vs 重绘 (Repaint) vs 合成 (Composite Only)

这三个概念是性能优化的核心知识点：

```
┌─────────────────────────────────────────────────────────┐
│  重排 (Reflow/Layout)                                    │
│  触发全部流程：Layout → Paint → Composite                  │
│  代价：★★★★★ (最贵)                                      │
│  触发属性：width, height, margin, padding, display,       │
│          border, position, font-size, text-align         │
├─────────────────────────────────────────────────────────┤
│  重绘 (Repaint)                                          │
│  跳过 Layout：Paint → Composite                          │
│  代价：★★★☆☆                                             │
│  触发属性：color, background, box-shadow, border-color,   │
│          outline, visibility                             │
├─────────────────────────────────────────────────────────┤
│  仅合成 (Composite Only)                                  │
│  跳过 Layout 和 Paint：仅 Composite                       │
│  代价：★☆☆☆☆ (最便宜，GPU 处理)                           │
│  触发属性：transform, opacity                             │
└─────────────────────────────────────────────────────────┘
```

**实战示例：动画优化**

```css
/* ❌ 差：使用 left/top 做动画 → 每帧都触发重排 */
.box-bad {
  position: absolute;
  transition: left 0.3s;
}
.box-bad:hover {
  left: 100px;
}

/* ✅ 好：使用 transform 做动画 → 仅触发合成，GPU 处理 */
.box-good {
  transition: transform 0.3s;
}
.box-good:hover {
  transform: translateX(100px);
}
```

### 4.4 强制同步布局 (Forced Synchronous Layout)

这是一个经典的性能陷阱。正常情况下，DOM 修改不会立即触发 Layout，浏览器会**批量延迟**到下一帧处理。但如果你在修改 DOM 后**立即读取**布局信息，浏览器就不得不**提前触发布局**：

```javascript
// ❌ 强制同步布局：写→读→写→读（每次读都强制布局）
for (let i = 0; i < elements.length; i++) {
  elements[i].style.width = box.offsetWidth + 'px'; // 读 offsetWidth 强制布局！
}

// ✅ 优化：先读后写（只触发一次布局）
const width = box.offsetWidth; // 读一次
for (let i = 0; i < elements.length; i++) {
  elements[i].style.width = width + 'px'; // 只写
}
```

会触发强制布局的读取操作包括：
- `offsetTop/Left/Width/Height`
- `scrollTop/Left/Width/Height`
- `clientTop/Left/Width/Height`
- `getComputedStyle()`
- `getBoundingClientRect()`

### 4.5 关键渲染路径 (Critical Rendering Path)

关键渲染路径是指浏览器从接收到 HTML/CSS/JS 到首屏像素渲染的最短路径。优化目标是**尽可能缩短这条路径**：

```
优化策略：
1. 减少关键资源数量：内联首屏 CSS，延迟非关键 JS
2. 减少关键资源体积：压缩、最小化
3. 缩短关键路径长度：减少请求链的深度

首屏渲染 = HTML 下载 + CSS 下载(阻塞渲染) + JS 下载和执行(阻塞解析)
```

```html
<!-- 优化前：3个关键资源，串行加载 -->
<link rel="stylesheet" href="all.css">     <!-- 阻塞渲染 -->
<script src="analytics.js"></script>         <!-- 阻塞解析 -->
<script src="app.js"></script>               <!-- 阻塞解析 -->

<!-- 优化后：减少关键资源 -->
<style>/* 内联首屏关键 CSS */</style>
<link rel="stylesheet" href="non-critical.css" media="print" onload="this.media='all'">
<script src="analytics.js" defer></script>    <!-- 不阻塞解析 -->
<script src="app.js" defer></script>          <!-- 不阻塞解析 -->
```

### 4.6 GPU 加速与 `will-change`

`will-change` 属性告诉浏览器"这个元素即将发生变化"，让浏览器提前创建独立图层：

```css
/* 浏览器会为该元素创建独立的合成图层 */
.animated-element {
  will-change: transform;
}

/* ⚠️ 注意：不要滥用！每个图层都消耗 GPU 内存 */
/* ❌ 不要这样做 */
* { will-change: transform; }

/* ✅ 在需要时动态添加 */
.card:hover {
  will-change: transform;
}
.card.animating {
  transform: scale(1.05);
}
```

## 5. JavaScript引擎（V8）

### 5.1 V8 是什么？

V8 是 Google 开发的 JavaScript 引擎，用于 Chrome 浏览器和 Node.js。它将 JavaScript 代码直接编译为机器码执行，而不是传统的解释执行。

**类比**：想象你在看一本外文小说。**解释执行**就像请一个翻译逐句口译，你听一句翻一句；**JIT 编译**就像翻译发现有些段落你反复在看，于是把这些段落提前翻译好打印出来，下次直接看译文。

### 5.2 V8 执行管道

```
┌──────────┐     ┌────────┐     ┌──────────┐     ┌───────────┐
│  Source   │────▶│ Parser │────▶│   AST    │────▶│ Ignition  │
│  Code     │     │        │     │          │     │ (解释器)   │
└──────────┘     └────────┘     └──────────┘     │ → 字节码   │
                                                  └─────┬─────┘
                                                        │
                                    执行并收集类型反馈 (Type Feedback)
                                                        │
                            ┌───────────────────────────┤
                            │                           │
                            ▼                           ▼
                     ┌─────────────┐            ┌──────────────┐
                     │  Sparkplug  │            │   Maglev     │
                     │ (基线编译器)  │            │ (中间层优化)   │
                     │ 快速生成代码  │            │  较快的JIT    │
                     └─────────────┘            └──────┬───────┘
                                                       │
                                                热点代码 (Hot Code)
                                                       │
                                                       ▼
                                                ┌──────────────┐
                                                │  TurboFan    │
                                                │ (优化编译器)   │
                                                │ 生成高度优化   │
                                                │ 的机器码       │
                                                └──────────────┘
```

**各阶段说明**：

| 阶段 | 作用 | 速度 | 代码质量 |
|------|------|------|---------|
| **Parser** | 源码 → AST（语法树） | - | - |
| **Ignition** | AST → 字节码，解释执行 | 启动快 | 执行较慢 |
| **Sparkplug** | 字节码 → 基线机器码（无优化） | 编译快 | 比解释快 |
| **Maglev** | 中间层 JIT，基于类型反馈 | 编译较快 | 较好 |
| **TurboFan** | 重度优化 JIT，内联、逃逸分析等 | 编译慢 | 最优 |

### 5.3 JIT 编译原理

V8 采用**分层编译 (Tiered Compilation)** 策略：

1. **首次执行**：Ignition 解释字节码，同时收集类型信息（Type Feedback）
2. **温热代码**：函数被调用多次后，Sparkplug 快速编译为基线机器码
3. **热点代码**：频繁执行的函数交给 TurboFan 做深度优化（内联、常量折叠、类型特化）

```javascript
function add(a, b) {
  return a + b;
}

// 前几百次调用：Ignition 解释执行，收集到 a 和 b 都是数字
for (let i = 0; i < 10000; i++) {
  add(i, i + 1); // V8 发现：a 总是 number，b 总是 number
}

// TurboFan 优化后：直接生成 "整数加法" 的机器码，跳过类型检查
// 速度接近 C++ 的整数相加
```

### 5.4 去优化 (Deoptimization)

如果 TurboFan 基于类型假设做了优化，但后来传入了不同类型的参数，V8 必须**回退到 Ignition 重新解释执行**——这就是去优化。

```javascript
function add(a, b) {
  return a + b;
}

// TurboFan 优化为整数加法
for (let i = 0; i < 10000; i++) {
  add(i, i + 1);
}

// 💥 传入字符串 → 类型假设被打破 → 去优化！
add("hello", " world"); // Deoptimization! 回退到 Ignition
```

### 5.5 Hidden Class 和 Inline Cache

**Hidden Class（隐藏类）** 是 V8 为 JavaScript 对象赋予的内部类型结构。相同"形状"的对象共享同一个 Hidden Class，使得 V8 可以像访问 C++ struct 那样快速访问属性。

```javascript
// ✅ 好：相同属性顺序 → 共享 Hidden Class
function createPoint(x, y) {
  return { x, y };
}
const p1 = createPoint(1, 2);  // Hidden Class: HC0 {x @offset0, y @offset1}
const p2 = createPoint(3, 4);  // 共享 HC0 → 属性访问用固定偏移量，极快

// ❌ 差：不同属性顺序 → 不同 Hidden Class
const a = { x: 1, y: 2 };  // HC_A {x @0, y @1}
const b = { y: 2, x: 1 };  // HC_B {y @0, x @1} — 不同的 Hidden Class！
```

**Inline Cache（IC，内联缓存）** 是 V8 优化属性访问的机制。当一个函数多次处理相同 Hidden Class 的对象时，V8 会缓存属性的偏移量，跳过查找过程：

```javascript
function getX(point) {
  return point.x; // IC 缓存：point 的 Hidden Class → x 在 offset 0
}

// 单态 IC (Monomorphic)：最快，只见过一种 Hidden Class
getX({ x: 1, y: 2 }); // HC_A
getX({ x: 3, y: 4 }); // 还是 HC_A → IC 命中

// 多态 IC (Polymorphic)：见过 2-4 种 Hidden Class，依然较快
getX({ x: 1, name: "a" }); // HC_B → IC 变为多态

// 超多态 IC (Megamorphic)：超过 4 种 → 退化为哈希表查找，很慢
```

### 5.6 编写 V8 友好的代码

```javascript
// ✅ 1. 保持对象形状一致
class Point {
  constructor(x, y) {
    this.x = x;
    this.y = y;
  }
}

// ✅ 2. 避免动态添加属性
const obj = { a: 1, b: 2 }; // 一次性定义所有属性
// ❌ obj.c = 3; // 后续添加会改变 Hidden Class

// ✅ 3. 避免删除属性
// ❌ delete obj.a; // delete 会退化对象为慢模式(字典模式)

// ✅ 4. 保持函数参数类型稳定
function process(value) {
  return value * 2;
}
// 总是传 number，不要有时传 string
```

## 6. 内存管理与垃圾回收

### 6.1 JavaScript 的内存模型

JavaScript 运行时的内存分为：

```
V8 内存
├── Stack（栈）：存储原始类型值和对象引用指针
│   - 简单、快速、自动回收（函数返回时弹出）
│   - 大小有限（通常几 MB）
│
└── Heap（堆）：存储对象、数组、闭包等
    ├── New Space（新生代）：存放生命周期短的对象
    │   ├── From Space（活跃半区）
    │   └── To Space（空闲半区）
    │
    └── Old Space（老生代）：存放长期存活的对象
        ├── Old Pointer Space：包含指向其他对象的指针
        └── Old Data Space：只包含原始数据
```

### 6.2 垃圾回收算法

**类比**：想象一个图书馆。**新书架**（New Space）空间小但流转快——新上架的书，没人借就快速下架；**经典书架**（Old Space）空间大，放的都是经得起时间考验的书。

**新生代 GC：Scavenger（清道夫算法 / Semi-space）**

```
① 新对象分配到 From Space
② From Space 满了 → 触发 Scavenge
③ 遍历 From Space，将存活对象复制到 To Space
④ 清空 From Space
⑤ 交换 From 和 To 的角色

特点：速度极快（只复制存活对象），但浪费一半空间
晋升：对象在两轮 Scavenge 后仍存活 → 晋升到 Old Space
```

**老生代 GC：Mark-Sweep（标记清除）+ Mark-Compact（标记整理）**

```
Mark-Sweep：
① 从 GC Roots 开始遍历，标记所有可达对象（Mark）
② 遍历堆，释放未标记对象的内存（Sweep）
问题：产生内存碎片

Mark-Compact（Mark-Sweep 后可选执行）：
③ 将存活对象向内存一端移动，消除碎片（Compact）
```

**增量标记 (Incremental Marking)** 和 **并发标记 (Concurrent Marking)**：V8 将标记工作拆成小块穿插在 JS 执行间隙，或与 JS 并发执行，避免长时间暂停（Stop-The-World）。

### 6.3 常见内存泄漏场景

```javascript
// 1. 未清理的定时器
let data = loadHugeData();
setInterval(() => {
  process(data); // data 被闭包引用，永远无法被 GC
}, 1000);
// ✅ 修复：clearInterval

// 2. 闭包引用
function createHandler() {
  const element = document.getElementById('button');
  const hugeData = new Array(1000000).fill('x');

  element.addEventListener('click', () => {
    console.log(hugeData.length); // hugeData 被闭包持有
  });
}
// ✅ 修复：组件卸载时 removeEventListener，或将 hugeData 改为只保存 .length

// 3. 脱离 DOM 的引用
let detachedNode = document.createElement('div');
document.body.appendChild(detachedNode);
document.body.removeChild(detachedNode);
// detachedNode 变量仍然引用这个 DOM 节点 → 泄漏
// ✅ 修复：detachedNode = null;

// 4. 全局变量
function leak() {
  oops = 'this is global'; // 忘了 let/const → 绑定到 window
}
// ✅ 修复：严格模式 'use strict'
```

### 6.4 Chrome DevTools Memory 排查

```
排查步骤：
1. 打开 DevTools → Memory 面板
2. 选择 "Heap Snapshot"，录制初始快照 (Snapshot 1)
3. 执行可疑操作（如打开弹窗、切换页面）
4. 再录制一个快照 (Snapshot 2)
5. 关闭弹窗/返回，录制 Snapshot 3
6. 对比 Snapshot 1 和 3：如果 3 明显大于 1 → 存在泄漏
7. 在 Snapshot 3 中选择 "Comparison" 视图对比，查找增量对象

Timeline（时间线）模式：
1. 选择 "Allocation instrumentation on timeline"
2. 执行操作，观察蓝色柱（新分配）和灰色柱（已回收）
3. 持续增长的蓝色柱 → 泄漏嫌疑
```

## 7. 性能指标（Core Web Vitals）

### 7.1 为什么需要标准化的性能指标

过去，每个团队衡量性能的方式不一样——有人看 `DOMContentLoaded`，有人看 `window.onload`，有人看自定义 "首屏时间"。Google 提出 **Core Web Vitals**，统一了性能衡量标准，并直接影响搜索排名。

### 7.2 三大核心指标

#### LCP — Largest Contentful Paint（最大内容绘制）

**定义**：视口中最大的可见内容元素完成渲染的时间。通常是首屏大图、视频封面、或大块文字。

| 等级 | LCP 时间 |
|------|---------|
| 🟢 好 | ≤ 2.5 秒 |
| 🟡 需改进 | 2.5 - 4.0 秒 |
| 🔴 差 | > 4.0 秒 |

**优化方向**：
- 优化 LCP 资源的加载：`<link rel="preload">`
- 使用 CDN 缩短 TTFB
- 图片使用 WebP/AVIF + 合适尺寸
- 避免客户端渲染（CSR）导致 LCP 元素延迟出现

#### INP — Interaction to Next Paint（交互到下一次绘制）

**定义**：替代 FID（2024 年正式替换），衡量用户交互（点击/按键/触摸）到下一帧像素更新的延迟。INP 取整个页面生命周期中**最慢的那次交互**。

| 等级 | INP 时间 |
|------|---------|
| 🟢 好 | ≤ 200 毫秒 |
| 🟡 需改进 | 200 - 500 毫秒 |
| 🔴 差 | > 500 毫秒 |

**优化方向**：
- 减少 Main Thread 上的长任务（> 50ms）
- 使用 `requestIdleCallback` 延迟非关键工作
- 使用 `scheduler.yield()` 让出主线程
- 将计算密集型任务移到 Web Worker

#### CLS — Cumulative Layout Shift（累积布局偏移）

**定义**：页面加载期间，所有意外布局偏移的评分总和。比如图片加载导致文字下移，广告插入导致按钮位移。

| 等级 | CLS 分数 |
|------|---------|
| 🟢 好 | ≤ 0.1 |
| 🟡 需改进 | 0.1 - 0.25 |
| 🔴 差 | > 0.25 |

**优化方向**：
- 图片和视频设置明确的宽高（`width` / `height` 或 `aspect-ratio`）
- 不要在现有内容上方插入新内容
- 使用 `font-display: swap` + `<link rel="preload">` 优化字体
- 使用 CSS `contain` 限制布局影响范围

### 7.3 其他关键指标

| 指标 | 全称 | 含义 | 目标值 |
|------|------|------|--------|
| **TTFB** | Time to First Byte | 从请求发出到收到第一个字节 | ≤ 800ms |
| **FCP** | First Contentful Paint | 首次内容绘制（文字/图片） | ≤ 1.8s |
| **TBT** | Total Blocking Time | FCP 到 TTI 之间主线程被阻塞的总时间 | ≤ 200ms |
| **TTI** | Time to Interactive | 页面完全可交互的时间 | ≤ 3.8s |
| **SI** | Speed Index | 可见区域内容填充的速度 | ≤ 3.4s |

### 8.2 运行时优化

#### 防抖与节流

```javascript
// 防抖 (Debounce)：触发后等待一段时间才执行，期间再次触发则重新计时
// 适用：搜索输入、窗口 resize 结束后执行
function debounce(fn, delay) {
  let timer;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), delay);
  };
}

// 节流 (Throttle)：固定间隔执行一次，期间触发被忽略
// 适用：滚动事件、拖拽位置更新
function throttle(fn, interval) {
  let lastTime = 0;
  return function (...args) {
    const now = Date.now();
    if (now - lastTime >= interval) {
      lastTime = now;
      fn.apply(this, args);
    }
  };
}

// 使用
window.addEventListener('scroll', throttle(handleScroll, 100));
searchInput.addEventListener('input', debounce(handleSearch, 300));
```

#### requestAnimationFrame

```javascript
// ✅ 使用 rAF 做动画：确保在浏览器下一次渲染前执行
function animate() {
  element.style.transform = `translateX(${position}px)`;
  position += 2;

  if (position < 300) {
    requestAnimationFrame(animate);
  }
}
requestAnimationFrame(animate);

// ✅ 使用 rAF 批量 DOM 操作
function batchDOMUpdates(updates) {
  requestAnimationFrame(() => {
    updates.forEach(update => update());
  });
}
```

#### Intersection Observer + 懒加载

```javascript
// 通用懒加载方案
const observer = new IntersectionObserver(
  (entries) => {
    entries.forEach(entry => {
      if (entry.isIntersecting) {
        const img = entry.target;
        img.src = img.dataset.src;          // 加载真实图片
```

## 9. 常见陷阱与最佳实践

### 9.1 Top 5 性能陷阱

| # | 陷阱 | 问题 | 解决 |
|---|------|------|------|
| 1 | 在循环中读取 `offsetHeight` | 每次读取都触发强制同步布局 | 读取一次缓存，或使用 `getBoundingClientRect()` 一次读取 |
| 2 | 图片不设 width/height | 图片加载后触发巨大的布局偏移（CLS） | HTML 或 CSS 中显式设置宽高或 `aspect-ratio` |
| 3 | 阻塞渲染的 CSS/JS 全放 `<head>` | 所有资源下载完才首屏渲染 | 内联关键 CSS，非关键 CSS 用 `media` 延迟，JS 用 `defer` |
| 4 | 使用 `left/top` 做动画 | 每帧触发重排 → 卡顿 | 使用 `transform: translate()` → 仅合成 |
| 5 | 不拆分打包，所有 JS 一个 bundle | 首页加载完整个应用的代码 | 路由级 Code Splitting + 动态 `import()` |

### 9.2 性能优化检查清单

```
📋 上线前性能检查清单（Performance Checklist）

🔹 网络层
  □ 启用 HTTP/2 或 HTTP/3
  □ 开启 gzip/brotli 压缩
  □ 配置合理的 Cache-Control 策略
  □ 使用 CDN 加速静态资源
  □ DNS 预解析和预连接关键域名

🔹 资源层
  □ JS 路由级 Code Splitting
  □ Tree Shaking 移除未使用代码
  □ 图片使用 WebP/AVIF 格式
  □ 图片设置明确的宽高属性
  □ 懒加载非首屏图片 (loading="lazy")
  □ 字体使用 font-display: swap

🔹 渲染层
  □ 关键 CSS 内联到 <head>
  □ 非关键 CSS 异步加载
  □ JS 使用 defer/async 加载
  □ 动画使用 transform/opacity（避免 left/top）
  □ 避免强制同步布局
  □ 长列表使用虚拟滚动

🔹 监控层
  □ 实施 Core Web Vitals 监控（web-vitals）
  □ 设置 Lighthouse CI 自动化检测
  □ 建立性能预算 (Performance Budget)
  □ 定期 Review 第三方脚本的影响
```

### 9.3 性能优化的思维模型

最后，记住性能优化的核心思维：

1. **先测量，再优化**：不要凭感觉优化。用 DevTools Performance 面板和 Lighthouse 精准定位瓶颈
2. **优化瓶颈**：只优化最慢的那环。用 Amdahl 定律思考——如果渲染占 80% 时间，优化网络只能提升 20%
3. **权衡取舍**：每次优化都有成本。代码分割增加了请求数，缓存增加了缓存失效的复杂度
4. **面向用户体验**：Core Web Vitals 的设计理念是以用户感知为核心，不是追求跑分
5. **持续监控**：性能不是一次性工作。建立 CI 中的 Lighthouse 检查 + 线上 RUM 监控，防止性能退化
